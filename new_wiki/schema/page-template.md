# Wiki 페이지 표준 템플릿 — L0~L4 계층

> 목적(사용자 확정 목표 "적절성"): API 응답 구조만 궁금한 독자에게 변경 로그·설계 논의
> 과정은 노이즈다. 필요한 수준까지만 읽고 멈출 수 있도록, 그리고 더 깊이 필요하면
> 근원(Raw)까지 내려갈 수 있도록 모든 Wiki 페이지를 5단으로 쌓는다.

| 계층 | 내용 | 원칙 |
| --- | --- | --- |
| **L0 정체성** | ID·명칭·유형·프로그램/도메인·상태 — 표 형식 | 스캔 전용, 문장 없음 |
| **L1 TL;DR** | 1~3줄, 이 문서가 무엇인지 | 영업팀은 여기서 읽기를 멈춰도 된다 |
| **L2 핵심 콘텐츠** | 화면=레이아웃+필드표, API=경로/스키마 요약표, 요구사항=REQ 요지+확정상태 | 개발팀이 원하는 답의 90%가 여기 |
| **L3 상세·예외** | 검증 규칙 서술, 예외 표, DS 매핑 등 | 하위 섹션 — 필요할 때만 읽는다 |
| **L4 근거·이력** | 원문 인용, 왜 이렇게 정했나, 변경 이력 | 페이지 최하단 한 절로 몰거나 Raw 링크로 대체 |

## 문서 유형별 적용

- **화면 상세 스펙**: L2=§3 레이아웃+§4 필드표+§5 액션, L3=§6 예외/§7 DS매핑, L4=§8 미결 중
  해소된 것+§9 변경이력+근거강도 서술. 기존 9블록 서식(`templates/00-화면스펙서식.md`)의
  블록 구조는 유지하고 배치만 이 계층에 맞춘다.
- **API 계약서**: 정본(`openapi/*.json`)은 손대지 않는다(Tier 0). Wiki는 **화면×경로 요약표**
  (경로·메서드·스키마명·상태코드만, 프로즈 없음)를 L2로 두고 정확한 필드는 json 앵커로
  딥링크한다. "왜 이 경로인가"는 L4.
- **요구사항 명세서**: L2=REQ별 원문 요지 1~2문장+확정 상태 배지, L3=반영 위치(화면/도메인),
  L4=재정의 근거.
- **의사결정·정책**: 조항 하나하나(공유계약 등)는 L2=조항 요지 표, L4=DR 원문·결정 대장 인용.

## 독자군 진입

별도 파일로 쪼개지 않는다(파일이 늘수록 예전 편람처럼 "낡음"이 재발할 위험이 커진다).
대신 한 페이지 안에서 L0~L1까지 읽으면 영업팀이 이탈해도 되게 만들고, 개발팀은 L2로 계속
스크롤/점프한다. `wiki/00-index.md`에서만 "독자군별 추천 경로" 표로 안내한다.
