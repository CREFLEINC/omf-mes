# W-04-12 · 출하 확정·취소

## §0. 요약

- **개요**: 관리웹에서 물류 출하관리자가 미확정 출하를 최종 확정하거나 취소하는 판정·승인 화면. FR-IM-079(출하취소·P0)를 「확정 전에만 취소 가능」 하나로 충족하며, 되돌릴 수 있는 구간을 ERP 송신 이전으로 옮겨 「확정 후 취소」가 유발하는 분산 트랜잭션·ERP 거부·불일치를 구조적으로 없앤다.
- **주요 데이터**: `logistics.shipment`(`status_code`=미확정/확정/취소 값 정의만 필요 · `shipped_at` · `erp_delivery_no` · **`confirmed_at`·`confirmed_by` 컬럼 없음**), `integration.integration_message`(outbox), `app.operation_policy`(자동 확정 on/off·경과 시간 설정), `app.approval_request`(취소 요청 결재).
- **핵심 액션**: 미확정 출하 목록에서 대상 선택 → **확정**(ERP 송신 대기열 적재, 되돌릴 수 없음) 또는 **취소 요청**(사유 필수 → 승인 → 취소 실행, 재고 복구) → 24시간(설정 가능) 경과 시 **자동 확정**이 돌되 취소 요청 결재 중인 건은 자동 확정에서 제외된다.

> 작성일: 2026-08-07 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **v1.8 신설**(2026-08-07 사용자 확정) — ⭐⭐ **이 화면이 「확정 후 취소」 문제를 없앤다.** 되돌릴 구간을 **ERP 에 보내기 전**으로 옮겨 분산 트랜잭션·ERP 거부·불일치가 **구조적으로 사라진다.**

## §5. 액션·상태

### §5-1. ⭐⭐ 이 화면이 **분산 트랜잭션을 없앤다**

FR-IM-079 를 「확정 후 취소」로 설계하면 이렇게 된다.

```
확정 → ERP PGI 송신 → (나중에) 취소 → ERP 역전표 → ⛔ ERP 가 거부하면 불일치
```

**되돌릴 구간을 ERP 앞으로 옮기면 그 문제가 존재하지 않는다.**

```
출하 처리(미확정) → [ 취소 가능 · ERP 는 모른다 ] → 확정 → ERP 송신 → 끝
```

| 얻는 것 | |
| --- | --- |
| **분산 트랜잭션이 사라진다** | 취소가 **MES 내부 문제**로 축소 — `W-01-13` 이 이미 푼 형태 |
| **취소 판정 축이 3 → 1** | ERP·운송·고객납품 → **확정 여부** 하나 |
| **「고객이 받았습니까?」가 불필요** | 미확정이면 어차피 가능하고 확정 후면 어차피 불가다 |

⭐ **ERP 회계 모델과도 정렬된다** — PGI 는 회계 이벤트이고 회계 전표는 가볍게 취소되지 않는다. 「확정 = 되돌릴 수 없다」가 **ERP 의 모델과 같은 모양**이다. 두 시스템의 모델이 어긋날 때 생기는 것이 바로 불일치다.

### §5-2. 상태 셋 — **값 정의만으로 된다**

```
shipment.status_code   app.code_t   ← 모델 변경 없이 값만 정하면 된다
```

| 상태 | 뜻 | 이 화면 |
| --- | --- | --- |
| **미확정** | 실물은 나갔고 ERP 는 모른다 | ✅ 확정·취소 대상 |
| **확정** | ERP 로 갔다 | ⛔ **되돌릴 수 없다** |
| **취소** | 미확정 구간에서 되돌렸다 | 재고가 복구된다 |

⚠ **취소는 「없던 일」이 아니라 상태다** — 출하 기록은 남는다(B-3 이력 불변). `W-04-11` 의 「상태 복귀」와 같은 성격이다.

### §5-3. ⛔ 확정 후 취소 — **예외 경로를 두지 않는다**(사용자 확정)

> **원칙적으로 불가하다.** 반품 절차로도, 재고 조정으로도 우회로를 만들지 않는다.

**세 안을 검토하고 셋째를 택했다.**

| 안 | 왜 안 택했나 |
| --- | --- |
| 반품 절차로 보낸다 | 물건이 안 나갔는데 반품 전표를 만드는 것이 **데이터로 어색하다** |
| 재고 조정으로 맞춘다 | ⛔ **#78 에서 이미 「조정은 취소를 대신할 수 없다」고 답했다**(조정=증감 / 취소=역처리). 그 판정과 충돌한다 |
| **예외 경로를 만들지 않는다** ✅ | 드물게 생기는 사고는 **ERP 쪽에서 사람이 정리**하고 MES 는 다음 실사에서 맞춘다 |

⚠ **⛔ 확정 전 관문을 두껍게 하지 않는다**(2026-08-07 사용자 지적). UI 마찰로 검토를 강제하면 **경고 피로로 오히려 안 읽는다.** **확정 절차가 있다는 것이 기능의 몫이고, 실제로 보는가는 책임의 몫**이다.

**화면이 하는 것은 하나** — 확정 전에 **「확정 후에는 취소할 수 없습니다」**를 결과 구획에 적는다(J-7).

### §5-4. ⭐ 24시간 자동 확정 — **적체를 타이머가 막는다**

**100% 수동 확정은 검토를 오히려 무의미하게 만든다** — 전건을 눌러야 하면 아무것도 안 보고 누르게 된다. **자동을 켜 두고 문제 있는 건만 손이 가게** 하는 편이 실제 검토율이 높다.

| | |
| --- | --- |
| **기준 시각** | ⭐ **`shipped_at`**(실물 출하) — 「물건이 나간 지 24시간」이 업무 언어와 맞는다. 미확정 생성 시각을 쓰면 시스템 사정이 기준이 된다 |
| **on/off** | `operation_policy.value_boolean` |
| **경과 시간** | `value_numeric` — ⭐ **설정으로 둔다.** 구현 비용이 같고 「12시간으로」·「주말 때문에 48시간」이 반드시 온다 |
| 적용 범위 | `business_unit_id` — 사업장별 차등 |

⚠ **화면이 설정 상태를 상시 보인다** — 「자동 확정 ON · 24시간」. 꺼져 있는데 모르면 적체가 쌓인다.

### §5-5. ⚠ 자동 확정에서 **빼는 조건 하나** — 취소 요청 결재 중

**이건 편의가 아니라 버그 방지다.**

```
누군가 취소를 올림 → 승인 대기 → 24시간 경과 → 자동 확정 → ⛔ 취소가 영구히 불가능
```

**취소 의사가 명시적으로 표시된 건을 타이머가 덮으면** 승인자가 자리를 비운 사이에 창이 닫힌다.

**대응** — 대상 출하에 진행 중인 취소 요청(`approval_request`)이 있으면 **자동 확정에서 빼고 목록에 사유를 보인다.**

```
SH-…-0472  ⏸ 자동 확정 보류 — 취소 요청 결재 중 (AP-2026-0102)
```

⚠ **그 외에는 예외를 두지 않는다.** 수량 차이·검사 미완 같은 것은 **`W-04-04` 의 서버 관문 셋이 이미 막아** 미확정까지 오지도 않는다.

### §5-6. ⛔ 확정 시각·확정자를 담을 자리가 **없다** — 비대칭이 근거다

```
shipment   loaded_at ✅  shipped_at ✅  erp_delivery_no ✅
           confirmed_at ⛔  confirmed_by ⛔
```

⭐ **다른 두 테이블에는 둘 다 있다**(실측) — `planning.production_plan` · `logistics.subcontract_reconciliation`. **「확정한 사람을 남긴다」가 이 모델의 관행**이고 `shipment` 에만 빠져 있다.

**되돌릴 수 없는 행위일수록 누가 했는지가 중요하다.** 그리고 **자동/수동 구분에도 필요하다.**

| 운영 | `confirmed_at` | `confirmed_by` |
| --- | :-: | :-: |
| 아직 미확정 | 비어 있다 | 비어 있다 |
| **수동 확정** | 있다 | **있다** |
| **자동 확정** | 있다 | ⭐ **비운다** — 컬럼 하나로 구분된다 |

**A-11 로 물러난다** — 컬럼이 올 때까지 **확정 시각은 `updated_at` 으로 유추**하고 **확정자는 보이지 않는다.** 그 사실을 화면이 적는다. → §8-1 · **`[docs→데이터모델]` 이슈**.

### §5-7. ⚠ 적체 경고 — **회계가 아니라 연계 거부가 이유다**

**회계 전기일은 MES 소관이 아니다**(2026-08-07 사용자 지적). MES 는 **상차일·실물출하일·확정일·재고영업일 4종을 정확히 구분해 보내고** ERP 가 자기 정책으로 고른다. 인터페이스 설계의 일반 원칙 — **사건 시각을 보내고 해석은 수신 측이 한다.**

**그래도 적체 경고는 필요하고, 이유가 다르다.**

```
잘못된 이유   「회계 전기일이 밀린다」        ← 우리 소관이 아니다
옳은 이유     「ERP 가 마감된 기간을 거부한다」  ← 운영 지연의 결과
```

거부되면 실패가 `W-06-10`(연계 현황·재처리)으로 가고 사람이 ERP 담당과 풀어야 한다. **적체를 안 쌓는 것이 예방**이다.

| --- | --- |
| 미확정 건수 · 경과 구간별 | 24h 경과 · 3일 경과 |
| **이달 미확정 건수** | ⚠ 월말 경고 |
| 자동 확정 설정 상태 | ON/OFF · 시간 |

### §5-8. 취소는 **승인을 탄다** — `W-01-13` 과 같은 형태

미확정 구간의 취소라도 **재고가 되돌아간다.** 흔적을 담을 컬럼이 없으므로(`shipment` 에 `cancel*` 0건) **승인 기록이 이력을 대신한다**(A-11 보강).

```
[ 취소 요청 ] → approval_request 생성(사유 필수) → W-CO-09 승인 → 취소 실행
```

⚠ **실행 시점에 다시 판정한다**(J-8) — 승인을 기다리는 사이에 **자동 확정이 돌 수 있다.** §5-5 가 그것을 막지만, **막지 못한 경우**(설정을 끄고 켰다든지)를 위해 실행 시점에 상태를 다시 본다.

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐⭐ **되돌릴 수 있는 구간을 외부 시스템 경계 앞에 둔다** — 「확정 후 취소」를 설계하면 **분산 트랜잭션·보상·불일치**가 따라온다. 되돌릴 구간을 **외부에 보내기 전으로 옮기면 그 문제가 존재하지 않는다.** 우회가 아니라 제거다. B-8(외부 호출은 트랜잭션 밖)의 **되돌리기 판**이고, ERP·MES 두 모델을 같은 모양으로 맞추는 효과가 있다 (§5-1)
2. **되돌릴 수 없는 행위를 자동화할 때는 「명시적 반대 의사」를 타이머보다 우선한다** — 24시간 자동 확정이 **취소 요청 결재 중인 건**을 덮으면 취소가 영구히 불가능해진다. **사람이 이미 반대 의사를 표시한 건은 자동화에서 뺀다** — 그것이 자동화의 안전 조건이다 (§5-5)
3. **적체를 보이는 화면은 기본값이 「오늘」이 아니라 「미처리 전건」이고 정렬은 오래된 순이다** — 목록의 관행은 최신순인데, **적체 관리 화면에서는 오래된 것이 위험하다.** 기본값이 관행을 따르면 **가장 위험한 것이 마지막 페이지에 숨는다** (§5-7)
4. **확정 절차의 몫은 「절차가 있다는 것」까지다 — UI 마찰로 검토를 강제하지 않는다** — 경고를 늘리면 경고 피로로 오히려 안 읽는다. **확인 단계가 있다는 것이 기능의 몫이고, 실제로 보는가는 책임의 몫**이다. G-1·G-3 이 이미 「요구 시 표시」로 물러난 것과 같은 판단 (§5-3)
