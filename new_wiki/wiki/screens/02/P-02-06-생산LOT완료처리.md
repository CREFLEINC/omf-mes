# P-02-06 · 생산LOT 완료 처리

## §0. 요약

- **개요**: POP(1024×768 터치)에서 작업자·현장반장이 생산LOT의 완료 여부를 판정하는 화면. 누적 양품이 목표 수량에 도달하면 완료 처리, 미달이면 사유를 받아 미달 마감 처리한다 — 두 결말은 버튼을 분리해 사용자가 미달을 인지하지 못한 채 완료를 누르지 않게 한다. `can_complete_work` 단말 게이팅이 걸린다.
- **주요 데이터**: 생산LOT(`trace.lot` — 목표 수량·상태), 작업실적(`production.production_result`, 읽기 — 양품 수량만 사용), 실적→LOT 배분(`production_result_lot_allocation` — 누적 양품 합산의 근거), W/O(`production.work_order` — 미달 사유·완료 시각).
- **핵심 액션**: LOT 선택 → 누적 양품과 목표 대조(달성률 표시) → 목표 달성 시 **완료 처리**, 미달 시 사유 선택 후 **미달 마감**. 초과 달성은 막지 않는다. 라벨 출력(`P-02-07`)·포장(`P-02-08`)은 이 화면 밖.

> 작성일: 2026-08-04 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ★ **`can_complete_work` 게이팅**. 이 장에서 **「완료는 비강제다」**와 **미달 마감**을 다룬다.

## §5. 액션·상태

### §5-1. ★ 단말 게이팅 — `can_complete_work`

```
mdm.terminal_process.can_complete_work   boolean NOT NULL DEFAULT false
```

**3번째 실증**이다(`can_print_label` → `can_input_material` → 여기).

없으면 **두 버튼 모두 비활성** + 사유 표시(F-1). 「이 단말은 이 공정의 작업 완료 권한이 없습니다」.

### §5-2. 누적 양품은 계산 값이다

```
누적 양품 = Σ production_result_lot_allocation.allocated_qty   WHERE lot_id = 이 LOT
```

`trace.lot`에 누적 컬럼이 없으므로 **매번 합산**한다. 화면은 이 값을 목표(`initial_qty`)와 비교해 달성률을 보인다.

> **`W-01-09` §9-3**(저장 값이 아닌 계산 값은 출처를 명시한다)의 두 번째 사례다.

### §5-3. ★ R71 — 완료는 비강제다

**「완료 = 양품 목표 달성(비강제 — 미달 완료 = **별도 명시 액션**)」**(✅REQ-PR-0019)

| 상황 | 액션 | 결과 |
| --- | --- | --- |
| 누적 ≥ 목표 | **완료 처리** | LOT 상태 = 완료 |
| 누적 < 목표 | **미달 마감** | LOT 상태 = 미달 마감 · **사유 필수** |

**사유가 필수인 근거** — `work_order.completion_variance_reason_code`가 실재한다. 미달로 끝낸 이유를 남기지 않으면 나중에 수율 분석이 불가능하다.

> ⚠ **컬럼이 `work_order`에 있는데 판정은 LOT 단위다.** W/O 하나에 LOT이 여럿이면(선발행 N개) **어느 LOT의 미달 사유인지 구분되지 않는다.** §8-2.

### §5-4. 초과 생산 — 막지 않는다

**R27** — 「N = 계획값이지 상한이 아니다 · 초과 시 **추가 발번**」 · ✓확정 QA #27 「초과 달성 분류·실적 인정」

누적이 목표를 넘어도 **막지 않는다.** 화면은 「초과 달성」으로 표시하고 완료를 허용한다.

**남은 슬롯은 이 화면이 처리하지 않는다** — R27의 「미달 슬롯 = **S12 마감 자동 폐번**」은 W/O 마감(`W-02-05`) 소관이다. 이 화면은 LOT 하나만 본다.

### §5-5. 완료의 결과

```
┌─ 한 트랜잭션 ────────────────────────────┐
│ ① trace.lot.status_code   완료 / 미달마감 │
│ ② (미달 시) work_order                    │
│    completion_variance_reason_code 기록   │
└──────────────────────────────────────────┘
              ↓ 이 화면 밖
    P-02-07 LOT 라벨 출력 (양품만)
```

**라벨은 이 화면이 찍지 않는다.** S10 태스크 ②가 별도 화면(`P-02-07`)이고, §K-4(인쇄는 트랜잭션 밖)에 따라 완료와 인쇄를 묶지 않는다.

### §5-6. 세션 전제

`P-02-01`(작업 시작)이 **#67로 보류**되어 **세션을 여는 화면이 3차에 없다**(`P-02-03` §8-5).

이 화면은 세션을 **읽기만** 한다(머리에 표시). 완료 자체는 LOT과 W/O를 건드리므로 **세션이 없어도 성립**한다. 다만 「어느 세션에서 완료했는가」가 기록되지 않는다 — §8-4.

## §9. 이 장에서 나온 공유 계약 후보

1. **되돌릴 수 없고 의미가 다른 두 결말은 버튼을 나눈다** — 「완료」와 「미달 마감」이 같은 버튼이면 사용자가 미달을 인지하지 못한 채 누른다. R71의 「별도 명시 액션」이 그 요구다 (§3 · §5-3)
2. **정상이 아닌 결말에는 사유를 필수로 받는다** — 미달 마감·재발행(K-2)·오류 등록이 모두 같은 형태다. 사유 없이 끝내면 나중에 분석할 수 없다 (§5-3)
3. **계획값을 넘는 것을 막지 않는다** — 초과 달성은 실적으로 인정된다(QA #27). 시스템이 계획을 상한으로 강제하면 현장이 기록을 안 남긴다 (§5-4)
