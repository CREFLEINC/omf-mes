## 2. 6단계 — ⭐ **관문 3개가 이슈 4건을 코멘트 4건으로 바꿨다**

`[[contract-must-track-upstream]]`이 세운 **이슈 발행 전 관문 3개**를 적용했다.

```
① 없어야 정상인가   ② 이미 판정이 있는가   ③ 선후가 있는가
```

**넷 다 ②에 걸렸다** — 올릴 것이 이미 열린 이슈의 범위 안이었다. 새 이슈를 냈으면 같은 논의가 두 곳에서 갈라졌을 것이다.

| 올리려던 것 | 어디로 갔나 | 무엇을 더했나 |
| --- | :-: | --- |
| 다형 참조 유형↔테이블 규약 | **#68 코멘트** | 「세 곳」인 줄 알았는데 **실측 15쌍 · 14테이블**이었다. `audit_event` 전용 요청을 **횡단 규약**으로 넓혀 달라고 요청 |
| `inventory_adjustment_line` 신설 | **#88 코멘트** | 계약을 먼저 쓴 형태를 제시 · ⚠ **`adjustmentQty` 는 음수를 받아야 한다**(`qty_t` 는 `CHECK >= 0`) · 라인 사유 자리는 **#87 기준의 적용례**로 넘김 |
| 창고 내 이동 헤더 부재 | **#82 코멘트** | 계약이 결손을 그대로 물려받았다 — **정위치 복귀 대상은 찾을 수 있는데 옮길 오퍼레이션이 없다.** 원장에 쓰기 경로를 두지 않았으므로 「창고가 같으면 원장으로」가 계약에서는 성립하지 않는다 |
| 취소·역처리 화면 필요 여부 | **#78 코멘트** | 이슈가 남긴 질문(「재고조정이 입고 취소를 대신할 수 있나」)에 **답했다 — 대신할 수 없다.** 조정은 증감이고 취소는 원 거래를 가리키는 역처리다 |

### 2-1. ⭐ 실측이 주장을 세 배로 키웠다

`W-01-10` §5-3이 다형 참조를 **「세 번째 사례」**로 적었고 그것이 「세 곳 규칙」 충족 근거였다. 계약을 쓰며 물리 모델을 전수 확인하니 **15쌍**이었다.

```
app 4 · audit 1 · integration 1 · quality 1 · inventory 2 · logistics 4 · trace 2
```

**「세 곳이면 공통으로 올린다」는 우리 기준을 다섯 배로 넘겼다.** 규약 없이 두면 화면 15곳이 각자 해석한다.

### 3-1. ⭐⭐ **DS 실물 대조가 발행 직전에 두 건을 잡았다** — 「있다고 적었는데 없다」의 두 번째

착수 통지 규칙이 「`ds-gap.md` 판정을 옮기지 말고 **고정 커밋 실물을 보라**」고 정한 이유가 여기서 증명됐다.

| | 「없다고 적었는데 있었다」 | **「있다고 적었는데 없었다」** |
| --- | --- | --- |
| 사례 | `MatrixGrid` · G-7 · G-3 · `StatCard` · `Chart`/`Table` 정렬 — **5건** | 2026-08-03 `DatePicker`·`FileInput` · **2026-08-07 `Drawer`** — **2건** |
| 대가 | 중복 제작 — 낭비 | **프론트가 착수한 뒤에 막힌다 — 재작업** |

⛔ **후자는 이번이 두 번째다.** 첫 번째(2026-08-03)가 **판정 절차 ① 신설의 직접 원인**인데도 또 났다. 원인이 다르다 — 첫 번째는 인벤토리를 안 열고 기억으로 적은 것이고, 이번은 **스펙을 쓴 뒤 다시 보지 않은 것**이다. **절차 ① 은 스펙 작성 시점의 규칙이라 그 뒤의 어긋남을 잡지 못한다.**

고정 커밋 `a554d11` 설치본 실측:

| 스펙이 적은 것 | 실물 | 처리 |
| --- | :-: | --- |
| `Drawer` — `W-01-07` §7 이 `a` | ⛔ **없다.** `Dialog` 에 `placement` prop 도 없다 | **G-11 신설**(`b`) · 통지에 「`Dialog` 로 대체」 명시 |
| `Pagination` — `W-01-09` §7 이 `a` | ⛔ **없다.** `Table` 에도 페이지 prop 없음 | **G-12 신설**(`c`) · 통지 3건에 「제품이 만든다」 명시 |
| `Table` 서버 정렬 | ✅ **있다** — `sort`·`onSortChange` | 통지에 「됩니다」 명시 |
| `StatCard` 비숫자 값 | ✅ **있다** — `value: ReactNode` | — |

**`Drawer` 는 `W-02-08`·`W-03-01` 스펙에도 같은 오류로 적혀 있었다** — 두 화면의 ds-gap 행에 정정을 달았다. **세 곳이라 「세 곳 규칙」을 충족**하므로 DS 이슈 대상이다.

> ⚠ **발행 후에 알았으면 프론트가 없는 부품을 기대하고 만들다 막혔다.** 통지는 고치지 않는 시점 기록이므로 ⛔ 변경 통지를 따로 내야 했을 것이다.

## 4. 트랙 결산

### 4-1. 무엇이 풀렸나

```
착수 통지 발행 누계   8  →  14 장   (도메인 06 8 + 01 6)
API 계약 보유 화면   10  →  32 장
계약 정본 파일        1  →   2 개
검사기               1  →   4 개
```

⚠ **「지금 착수 가능한 화면 수」와 「발행 누계」는 다른 값이다.** 01 도메인 23장 중 지금 발행 가능했던 것은 **6장**이고(§3), 나머지 17장은 승인 계약·검사 계약·셸 부재로 대기한다.

### 4-2. 이 트랙이 스스로 정정한 것 — **다섯 번**

| # | 어디서 | 무엇 |
| :-: | --- | --- |
| 1 | 1단계 → 2단계 | 횡단 3종을 「먼저」로 잡았다가 **뒤집었다** — 승인이 주 기능인 화면은 4장뿐이다 |
| 2 | 2단계 → 3단계 | **`:depart` 삭제 · `:cancel` 0건 · 예약 쓰기 없음** — 테이블이 아니라 **버튼을 세니** 규약이 셋 뒤집혔다 |
| 3 | 1단계 → 3단계 | **착수 가능 7장 → 6장** — 「승인 불요」만 보고 세었고 계약 유무는 따로 봐야 했다 |
| 4 | 3단계 리뷰 | 계약이 **자기 규칙을 세 곳에서 안 지켰다**(C-8 · G-1 · B-1) |
| 5 | 4단계 리뷰 | **검사기가 산문에 걸려도 통과**하고 있었다 — 커버리지를 보증하려는 도구가 커버리지를 부풀렸다 |

**공통점 — 전부 「한 단계 더 좁게 보니 달랐다」이다.** 테이블 → 버튼 · 승인 유무 → 계약 유무 · 소절 본문 → 매핑표 첫 열 · 문서 판정 → 고정 커밋 실물.
