## 3. ⭐ 판정 1 — **`/quality/*` 를 06 계약과 나눠 쓴다** *(00-설계 §7-3 #1)*

**실측이 답을 줬다** — 접두어 공유는 **이미 저장소의 관행**이다.

```
/app         →  app-공통 · mdm-기준정보     두 계약
/logistics   →  logistics-01 · mdm-기준정보  두 계약
/planning    →  mdm-기준정보 · production-02 두 계약
⛔ 두 계약에 같은 경로  →  0건
```

⭐ **규칙이 이미 서 있었다 — 「접두어는 공유하되 경로는 한 계약에만 둔다」.** 03 도 그대로 따른다.

| | 06 계약(마스터) | **03 계약(실행)** |
| --- | --- | --- |
| `/quality/inspection-plans` · `-plan-versions` | ✅ | — |
| `/quality/defect-codes` · `cause-codes` | ✅ | — |
| `/quality/inspection-requests` · `-results` | — | ✅ |
| `/quality/defect-records` · `concessions` · `lot-holds` | — | ✅ |

**경로 충돌 0건** — 리소스 이름이 다르다.

## 4. ⭐⭐ 판정 2 — **`lot_hold` 쓰기는 `/quality/lot-holds` 로 낸다** *(00-설계 §7-3 #2)*

**01 계약이 이미 `GET /trace/lots/{lotId}/holds` 를 갖고 있다.** §3 의 규칙상 **같은 경로를 03 이 낼 수 없다.**

### 4-1. 두 축이 같은 테이블을 본다

| 축 | 경로 | 소유 | 무엇을 묻나 |
| --- | --- | :-: | --- |
| **물류** | `GET /trace/lots/{lotId}/holds` | **01** | 「이 LOT 이 막혀 있나」 — 재고·피킹 맥락 |
| **품질** | `/quality/lot-holds` | **03** | 「무엇을 왜 막았고 언제 풀 것인가」 — 판정 맥락 |

⭐ **`W-03-01` §5-3 이 이미 같은 것을 말했다** — `lot.status_code`(품질 판정)와 `lot_hold.status_code`(보류 건의 진행)는 **다른 축**이다. **축이 다르면 경로가 갈리는 것이 자연스럽다.**

### 4-2. ⭐ 규약 후보 — **두 계약이 한 테이블을 보면 소유는 쓰기를 가진 쪽이다**

```
한 테이블에 두 계약이 경로를 가지면
    소유 = 쓰기(POST·PUT·:동사)를 가진 계약
    상대 = 「부모에 매달린 읽기」만 갖는다   (GET /parents/{id}/children)
```

**01 이 스스로 그렇게 적었다** — 「읽기만 제공한다 — 보류를 걸고 푸는 것은 품질 도메인의 화면이다」.

## 5. ⭐ 판정 3 — **C9 와 C10 은 한 경로다** *(01-리소스도출 §9 #3)*

**버튼을 셌다.**

| 화면 | 버튼 | 전이 | 도착 상태 |
| --- | --- | :-: | --- |
| `W-03-03` 의심자재 등록 | **「보류 등록」** | **C10** | 보류 |
| `W-03-02` 판정·전이 처리 | **「전이 확정」**(→ Hold) | **C9** | Hold |

**두 화면이 각각 버튼 하나씩이고, 둘 다 `lot_hold` 행을 하나 만든다.**

### 5-1. 한 경로로 간 이유

⚠ **01 규칙은 「한 화면이 두 버튼이면 두 오퍼레이션」이다** — **다른 화면의 버튼 하나씩**은 이 규칙의 대상이 아니다.

| 물었다 | 답 |
| --- | --- |
| 만드는 행이 같은가 | ✅ **`lot_hold` 행 하나** — 같다 |
| 도착 상태가 같은가 | ⛔ 다르다 → **본문 인자** `targetLotStatusCode` |
| 필수 필드가 같은가 | ⛔ 다르다 → **§5-2 조건부 필수** |
| 업무 용어가 같은가 | ⛔ 다르다 → **`reasonCode` 가 가른다** |

⭐ **URL 은 업무 행위가 아니라 리소스를 가리킨다.** 업무 구분은 코드가 한다 — 01 이 `:confirm`·`:post` 를 「업무 용어가 아니라 전이의 성격으로」 지은 것과 같은 판단이다.

### 5-2. ⚠ 조건부 필수가 생긴다 — **도착 상태가 필드를 가른다**

```
targetLotStatusCode = 보류   →  releaseCondition  필수   ⭐ 화면이 필수로 만든다(A-9 ⓑ)
                    = Hold   →  releaseCondition  무의미  ⛔ 받지 않는다
```

**근거**: `W-03-02` §5-5 — **Hold 는 발신 전이가 0**이다. 풀 수 없으므로 해제 조건이 뜻을 잃는다.
`W-03-03` §5-4 — 보류는 **조건이 비면 영구히 안 풀린다**(아무도 조건을 모른다).

⚠ **`release_condition` 은 DB 에서 nullable 이다.** 계약이 조건부로 막는 것은 **A-9 ⓑ**(화면이 막는다)의 계약 판이다.

### 5-3. C7·C8 은 `:release` 하나다 — **도착 상태만 다르다**

```
POST /quality/lot-holds/{lotHoldId}:release   본문 targetLotStatusCode
    C7 재판정 합격  →  정상
    C8 재판정 불합격 →  불량(Hold)
```

⛔ **`PUT released_at` 이 아니다** — 구간 형 규칙 2(01-리소스도출 §3-2).

### 6-2. ⛔ 그래서 **불량코드 분포 뷰가 빈다**

## 8. ⭐ 임시 저장과 확정이 **두 오퍼레이션이다** — #62 와 부딪히지 않는다

`W-01-01` §5-2 와 `P-02-13` §5-9 **둘 다 버튼이 둘**이다 — 「임시 저장」·「검사 확정」.

⚠ **#62 확정(「검사자와 확정자를 분리하지 않는다」)과 헷갈리기 쉽다.**

| 축 | 무엇 | 판정 |
| --- | --- | --- |
| **사람** | 검사자 ≠ 확정자인가 | ✅ **#62 — 분리하지 않는다** |
| **시각** | 작성 중 ≠ 확정인가 | ⭐ **분리한다 — 버튼이 둘이다** |

⭐ **다른 축이다.** `W-01-01` §8-3 이 「판정 저장 = 확정이고 `confirmed_at` 은 **저장 시각**으로 채운다」고 한 것은 **`:confirm` 을 부른 시각**을 뜻한다. 임시 저장은 `confirmed_at` 을 채우지 않는다.

```
POST /quality/inspection-results        status = 작성중 · confirmed_at = null · Lot Status 전이 없음
PUT  …/{id}                             작성중인 것을 고친다
POST …/{id}:confirm                     status = 확정 · confirmed_at = now · ⭐ Lot Status 전이
```

⛔ **`:confirm` 이 A-3 을 강제한다** — `accepted + rejected + held = inspected` 가 아니면 **400**. 임시 저장은 통과시킨다(작성 중이므로).

## 9. `P-02-13` 의 **처분 선택은 계약에 싣지 않는다**

`P-02-13` §5-8 이 「불합격분에 대해 **처분을 사람이 고른다**」인데 **두 가지가 걸린다.**

| | |
| --- | --- |
| 스스로 **「잠정」**이라 했다 | 「확정 판정은 **불량창고 입고 후**」(**REQ-PR-0025**) |
| 담을 테이블이 **04 소관** | `disposition_decision.nonconformance_id` **NOT NULL** — 부적합을 04 가 만든다 |

⛔ **잠정값을 저장하면 04 의 확정값과 정본을 다툰다.** 저장하지 않는다 — 화면이 이미 「처분은 불량창고 입고 후 확정됩니다」를 보인다.

⚠ **`P-02-13` §5-8 이 「확정 판정은 `W-03-*` 에서 한다」고 적었는데 그런 03 화면이 없다** — **`W-04-07`(재작업/폐기 판정 의뢰)이다.** → 5단계에서 스펙 정정 후보로 넘긴다.
