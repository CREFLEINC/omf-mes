## 1. 목적과 경계

이 산출물은 관리웹 화면 구성과 사용자 액션별 API 호출 구조를 한눈에 이해하기 위한 프론트엔드·백엔드 협업 자료다. 화면의 구조, 상태, API 계약, 오류 표시 위치를 같은 Figma Design 파일에서 추적할 수 있게 한다.

- 기존 FigJam 업무 프로세스 도식을 대체하거나 직접 연결하지 않는다.
- Figma 파일 안에서는 세 화면을 기준정보 변경 업무의 읽기 순서로 배열한다.
- `docs/`·`uiux/`에 없는 필드, 업무 규칙, API를 새로 만들지 않는다.
- API 계약이 불완전한 항목은 가상의 계약으로 채우지 않고 `미결`로 표시한다.
- `@crefle/web-ui`를 앱 UI의 시각·컴포넌트 기준으로 사용한다. `crefle-doc`과 Material 3 커뮤니티 키트는 사용하지 않는다.

## 2. 선택한 접근

**DS 정합형 프로덕트 스캐폴드 + 우측 API Rail**을 사용한다.

현재 대상 Figma 파일의 `UI Scaffold v1` 페이지는 비어 있고 CREFLE 제품 라이브러리가 연결돼 있지 않다. 따라서 이번 파일럿에서 필요한 `@crefle/web-ui` 컴포넌트만 같은 파일의 로컬 UI Kit로 구성하고, 화면은 그 인스턴스로 조립한다. 디자인 시스템에 없는 제품 패턴은 기존 원시 컴포넌트의 조합으로 만들며 별도 DS 컴포넌트처럼 위장하지 않는다.

그레이스케일 와이어프레임은 실제 데이터 밀도·상태 강조를 검증하기 어려워 채택하지 않았다. 독자적인 고충실도 콘셉트 디자인은 구현 디자인 시스템과 어긋날 가능성이 있어 채택하지 않았다.

## 4. 시각 원칙

### 4.1 화면 기반

- 관리웹 대표 프레임: 1440px 데스크톱
- 셸: 좌측 내비게이션, 상단 전역 헤더, 본문 콘텐츠
- 본문: 업무 밀도가 높은 엔터프라이즈 UI. 장식보다 검색·비교·편집·상태 판독을 우선한다.
- 데이터 표: compact density
- 화면 안쪽 정렬과 간격은 `@crefle/web-ui` 토큰을 따른다.
- 화면과 API Rail은 하나의 `Screen + Contract` 섹션으로 묶는다.

### 4.2 글꼴과 색

- 기본 글꼴: `Spoqa Han Sans Neo`
- API 경로·헤더·상태코드: 가독 가능한 mono 계열
- 배경·텍스트·선·강조색은 `@crefle/web-ui`의 foundation/web 토큰에서 가져온다.
- 파랑: 정보·선택·호출, 초록: 성공, 주황: 경고·미결, 빨강: 차단·실패에만 사용한다.
- `ETag`, `If-Match`처럼 화면에 표시되지 않지만 구현에 중요한 값은 보라색 계약 주석으로 구분한다.

### 4.3 정보 밀도

- 실제 화면은 업무 정보만 포함한다. API 상세를 화면 내부에 넣지 않는다.
- API Rail은 화면 오른쪽에 고정 폭 세로 열로 배치한다.
- 화면 액션에는 `①`, `②` 형태의 Callout Badge를 붙이고 같은 번호의 API 카드와 대응시킨다.
- 긴 요청·응답 스키마 전체를 복사하지 않고 UI가 소비하거나 전송하는 핵심 필드만 요약한다.

## 5. 로컬 UI Kit

### 5.1 DS 기반 컴포넌트

파일럿에서 필요한 최소 범위만 만든다.

- 셸: `AppShell`, `PageHeader`, `Breadcrumb`
- 탐색: `Tabs`
- 입력: `TextField`, `Select`, `SearchInput`
- 액션: `Button`, `IconButton`
- 데이터: `Table`, Pagination
- 상태: `Chip`, `AlertBanner`, `EmptyState`, `Skeleton`
- 오버레이: 상세 Side Panel

각 컴포넌트는 사용 상태만 포함한다. 예를 들어 Button은 이번 범위에서 쓰는 primary, secondary, danger, disabled, loading만 구성한다.

### 5.2 제품 내부 조합

다음은 DS 원시 컴포넌트의 조합이며 `@crefle/web-ui`의 새로운 원시 컴포넌트로 간주하지 않는다.

- `MasterDetailShell`: 목록 + 상세/편집 영역
- `RevisionHeader`: Rev 번호, 상태, 유효기간, 편집 가능성
- `EditableSequenceTable`: 순서 변경 가능한 공정·검사항목 표
- `DiffViewer`: before/after 표 두 개와 변경 키 강조
- `ApiRail`: API 카드의 세로 묶음
- `ApiCallCard`: Method, Path, Trigger, 입출력, UI 결과, 오류
- `CalloutBadge`: 화면 액션과 API 카드를 연결하는 번호

## 6. 화면 설계

### 6.1 `W-06-01` Routing 등록·관리

대표 상태는 `목록 조회`, `작성중 Rev 편집`, `확정 Rev 읽기 전용`, `충돌` 네 가지다.

화면 구조:

1. PageHeader: 화면명, Breadcrumb, 현재 품목·Routing 요약
2. 좌측: 품목 검색과 Routing 보유 여부 필터, 품목 목록
3. 중앙 상단: Routing 코드, Rev, 상태, 유효기간, 신규 Rev 발행
4. 중앙 본문: 공정 순서, 공정, 명칭, 검사 여부 등 공정 행 편집
5. 보조 영역: 공정 의존관계와 Rev 비교 진입
6. 하단/헤더 액션: 저장, 확정, 폐기

주요 API 묶음:

- 품목·Routing 조회: `GET /mdm/items`, `GET /planning/routings`
- 상세·공정 조회: `GET /planning/routings/{routingId}`, `GET /planning/routings/{routingId}/operations`
- 헤더·공정 저장: `PUT /planning/routings/{routingId}`, `PUT /planning/routings/{routingId}/operations`
- 최초 생성: `POST /planning/routings`
- 신규 Rev: `POST /planning/routings/{routingId}:new-revision`
- 확정·폐기: `POST /planning/routings/{routingId}:confirm`, `POST /planning/routings/{routingId}:obsolete`
- 변경 이력: `GET /audit/events`

Rev 비교는 전용 API를 만들지 않는다. 비교할 두 Rev의 상세와 공정을 각각 조회하고 화면에서 비교한다.

### 6.2 `W-06-02` 검사기준 등록

대표 상태는 `목록 조회`, `작성중 버전 편집`, `확정 버전 읽기 전용`, `검증 경고` 네 가지다.

화면 구조:

1. PageHeader와 검사 유형(IQC/PQC/OQC) 탐색
2. 좌측: 공정·품목·검사유형 검색과 검사기준 목록
3. 중앙 상단: 검사기준 헤더, 버전, 상태, 승인 정보
4. 중앙 본문: 검사항목, 순서, 목표값, 상·하한, 단위, 검사 장비 편집 표
5. 경고 영역: 교정 만료 장비, 자격·값 범위 등 저장 전 검증
6. 액션: 신규 기준, 신규 버전, 저장, 확정, 승인, 폐기

주요 API 묶음:

- 기준 조회·생성: `GET/POST /quality/inspection-plans`
- 기준 상세: `GET /quality/inspection-plans/{inspectionPlanId}`
- 버전 조회·생성: `GET/POST /quality/inspection-plan-versions`
- 신규 Rev: `POST /quality/inspection-plan-versions/{inspectionPlanVersionId}:new-revision`
- 버전·항목 저장: `PUT /quality/inspection-plan-versions/{inspectionPlanVersionId}`, `PUT /quality/inspection-plan-versions/{inspectionPlanVersionId}/items`
- 항목 조회: `GET /quality/inspection-plan-versions/{inspectionPlanVersionId}/items`
- 확정·폐기: `POST /quality/inspection-plan-versions/{inspectionPlanVersionId}:confirm`, `POST /quality/inspection-plan-versions/{inspectionPlanVersionId}:obsolete`
- 승인: `POST /quality/inspection-plans/{inspectionPlanId}:approve`
- 변경 이력: `GET /audit/events`

엑셀 업로드는 매핑 열과 오류 반환 계약이 확정되지 않았으므로 활성 기능처럼 그리지 않는다. `계약 미결` 상태의 보조 액션 자리와 설명만 둔다.

### 6.3 `W-06-11` 마스터 변경관리

대표 상태는 `변경 이력`, `Rev 현황`, `diff 열림`, `ERP 정본 편집 불가` 네 가지다.

화면 구조:

1. PageHeader와 `변경 이력 / Rev 현황` Tabs
2. 변경 이력: 필수 기간, 대상 유형, 대상 검색, 변경 유형, 수행자 필터
3. 이력 Table: 발생시각, 대상, 변경 유형, 수행자, 단말, 사유
4. 행 확장 또는 Side Panel: before/after diff
5. Rev 현황: Routing/BOM 합성 목록, 상태, 유효기간, 참조 중 W/O
6. MES 정본: 해당 마스터 화면으로 이동
7. ERP 정본: 편집 비활성, 사유와 재동기화 경로 안내

주요 API 묶음:

- 이력 조회: `GET /audit/events` (`occurredFrom`, `occurredTo` 필수)
- Rev 현황: `GET /planning/routings`, `GET /planning/boms` 결과를 화면에서 합성
- 신규 Routing Rev: `W-06-01`로 이동한 뒤 그 화면의 API 사용
- ERP 정본 재동기화: `W-06-10`으로 이동하며 이 화면에서는 실행하지 않음

`참조 중 W/O`의 산출 API와 audit JSON 키 규약은 미결이다. 표의 칸은 유지하되 API Rail에 주황색 `계약 미결` 카드로 표시한다.

## 7. API Rail 규격

각 카드에는 다음 필드를 동일한 순서로 표시한다.

| 필드 | 내용 |
| --- | --- |
| Callout | 화면 액션과 같은 번호 |
| Method / Path | 실제 OpenAPI 경로 |
| Trigger | 화면 진입, 조회, 저장, 확정, 행 열기 등 |
| Request | UI가 전달하는 핵심 path/query/header/body |
| Response | UI가 실제 사용하는 값 |
| UI Result | Skeleton→Table, 저장중→완료, Dialog 열림 등 |
| Errors | 상태코드와 표시 위치 |
| Contract | `계약 있음`, `초안`, `미결`, `API 불필요` |

화면과 카드는 긴 커넥터 대신 동일한 Callout 번호로 대응한다. 선택한 액션을 빠르게 읽을 수 있도록 화면의 번호는 파랑, API 카드의 같은 번호는 같은 색을 쓴다.

## 8. 상태와 오류 처리

### 8.1 공통 화면 상태

각 화면은 필요한 상태만 별도 프레임 또는 Variant로 보여 준다.

- Initial / Loading / Empty / Ready
- Editing / Saving / Saved
- Read-only / Permission denied
- Validation error / Server error
- Optimistic lock conflict

Loading·Empty·Error 상태를 한 화면 위에 겹쳐 주석으로만 설명하지 않는다. 레이아웃 영향이 큰 상태는 별도 프레임으로 둔다.

### 8.2 오류 규칙

- `400`: 필드 검증 또는 현재 상태에서 허용되지 않는 동작. 해당 필드 인라인 또는 폼 상단 AlertBanner.
- `403`: 진입 또는 액션 권한 부족. 페이지/영역 단위 차단.
- `404`: 대상이 사라진 경우 목록 재조회와 안내.
- `409`: 낙관적 잠금 또는 재시도 가능한 경합. `최신 불러오기`를 제공하고 덮어쓰기 강제는 제공하지 않는다.
- `500`: 입력값을 유지하고 재시도 가능한 페이지/영역 오류로 표시한다.

### 8.3 낙관적 잠금

상세 `GET`의 `ETag`를 저장하고 수정 요청의 `If-Match`로 전송한다. 이 값은 업무 화면 필드로 노출하지 않고 API Rail의 계약 주석으로만 표시한다.

## 9. 검증 기준

### 9.1 구조 검증

- 여섯 페이지가 명세의 이름과 역할대로 존재한다.
- 화면 프레임과 API Rail이 같은 섹션에 묶여 있다.
- 모든 사용자 액션 Callout은 같은 번호의 API 카드 또는 `API 불필요/미결` 카드와 대응한다.
- 컴포넌트 인스턴스는 `90 · Local UI Kit`의 원본을 참조한다.

### 9.2 시각 검증

- 1440px 화면에서 잘림·겹침·0폭 텍스트가 없다.
- compact Table에서도 한국어 라벨과 합성 예시 데이터가 잘리지 않는다.
- 정상·경고·차단·미결이 색만이 아니라 아이콘·문구로도 구분된다.
- API Rail을 제외하고도 화면 자체가 실제 관리웹처럼 읽힌다.

### 9.3 계약 검증

- Method와 Path는 `deliverables/openapi/mdm-기준정보.json`과 일치한다.
- 화면 액션의 근거는 각 화면 상세 스펙 §5와 `deliverables/06-API-요구서.md` §3에 추적된다.
- API가 없는 정상 사례와 미결 사례를 구분한다.
- `ETag`/`If-Match`, 400/409 분리, 기간 필수 조회가 정확히 표현된다.

## 11. 완료 조건

파일럿은 다음을 모두 만족할 때 완료다.

1. 세 화면의 대표 화면과 주요 상태가 Figma Design에 존재한다.
2. 각 주요 액션이 실제 API 카드 또는 명시적 미결/불필요 카드와 대응한다.
3. `@crefle/web-ui` 기반 로컬 UI Kit 인스턴스로 화면이 조립돼 있다.
4. 세 화면을 업무 순서로 보는 Overview가 있다.
5. 구조 검사와 전체 페이지 스크린샷 검토에서 잘림·겹침·누락이 없다.
6. 기존 FigJam과 저장소의 사용자 작업 파일은 변경되지 않는다.
