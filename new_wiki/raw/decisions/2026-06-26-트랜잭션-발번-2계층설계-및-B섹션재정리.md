## 1. 배경 — B8과 "MES가 모든 트랜잭션 번호를 발행" 가정

✅ **B8 미결**: 입하·입고·출고·출하·반품·재고이동·재고실사 7개 트랜잭션 No의 **발번 주체**가 MES인지 ERP(G/R 트랜잭션)인지 미확정. `[창고제안]`(raw/02)은 G/R·이동증·엑셀실사를 ERP 측에 둠 → 정본 MES 기준 발번 경계 확정 필요(개념데이터모델 §8.1·미결 종합9).

🔶 **"MES가 7개 전부 발번" 가정의 약점**: 7개 중 **회계 전표 성격**(입고=G/R, 출하=PGI, 반품=credit memo, 재고실사=조정전표)은 ERP가 재고자산·매출·COGS·세금계산서의 *법적 장부(System of Record)*다. MES가 이 번호의 단독 주인이 되면 ① 단일원장 충돌(전표 번호 이중화·정합 부담), ② ERP 발원 트랜잭션의 순환 의존, ③ 채번 유일성·오프라인 회복력, ④ 회계 마감·세금계산서 법정연번, ⑤ 수정권한 경계 역전 — 의 전형적 문제가 발생.
→ **해법의 방향**: 발번 주체를 "MES vs ERP" 단일 선택으로 보지 말고, **계층을 분리**한다(2절).

## 2. 설계 개념 — 지시 / 작업지시 / 전표 3계층 분리

핵심 아이디어: 하나의 물류 사건을 **상위 지시(ERP) · 작업지시(MES) · 회계전표(ERP)** 세 객체로 나누고, 가운데(실행)를 항상 MES가 소유한다.

```
[ERP] 상위 지시(Order)        [MES] 작업지시(Work Order)         [ERP] 회계전표(Posting)
  사업 의도·계약·납기      →     실행: Picking·검사·Pack·LOT확정   →   재고평가·매출·COGS·세금
  (있을 수도/없을 수도)          (항상 생성, 지시를 nullable 참조)     (회계 발생 트랜잭션만)
```

**연결 규칙**
- 작업지시 → 상위지시 : **nullable FK, 0..1 : N**. ERP 지시가 없으면 MES 작업지시 **단독 생성(standalone)**, 있으면 그 지시를 **참조**. 1 ERP지시 → N MES작업지시(분할), N 지시 → 1 작업지시(혼적/통합)도 표현 가능.
- 회계전표 → 작업지시 결과 : 회계가 발생하는 트랜잭션만. MES 실행 완료를 트리거로 ERP가 전표 채번.

**근거와 위상**
- ✅ **생산은 이미 이 패턴**: `P/O(ERP 발주) ─1:N→ W/O(MES 작업지시) ─→ 작업실적`. 본 제안은 동일 패턴을 **물류 트랜잭션으로 확장**하는 것 → 시스템 전체가 하나의 멘탈 모델로 통일.
- 🔶 ISA-95 Level 4(지시·회계) ↔ Level 3(실행) 분리와 정확히 정합.

**장점**
- **일관성**: 생산·물류가 같은 "지시→작업지시→전표" 골격.
- **자율성**: ERP 지시가 없어도(예: 고객사에 ERP 출하지시 업무 부재) MES가 작업지시를 단독 생성해 동작.
- **명확한 책임경계**: 실물 실행은 MES, 회계 확정은 ERP — 소유 경계가 또렷.

**비용(설계 시 명시 필요)**
- ⚠ **객체·번호 증가**: 한 흐름에 지시 No + 작업지시 No + 전표 No(최대 3개) → 연계(I/F) **매핑·정합** 설계 증가. 참조키 규칙 명문화 필요.
- ⚠ **상태 동기화 규칙**: ERP 지시 취소 시 MES 작업지시 처리? 부분완료 시 지시 상태? 분할/통합 수량 정합? — 상태 전이 규칙 정의 필요.

## 3. 트랜잭션별 적용표

가운데 열(MES 작업지시)은 **전부 MES** = 본 설계의 핵심. 좌(상위지시)는 *있으면 참조*, 우(전표)는 *회계 발생분만*.

| 트랜잭션 | ERP 상위지시 (있으면 참조) | **MES 작업지시 (항상)** | ERP 회계전표 | 비고 |
| --- | --- | --- | --- | --- |
| 출하(Shipment) | 출하지시(납품) | **출하작업지시** (Pick·OQC·Pack) | 출하 PGI 전표 | ✅ ERD: ERP 출하지시→출하→P&P |
| 입하·입고(Receipt·GR) | P/O(발주) | **입고작업지시** (검수·적치·자재LOT발행) | G/R 전표 | ✅ 입고=자재LOT 발행 트랜잭션 |
| 출고(Issue, 생산투입) | W/O가 상위 | **불출작업지시** | GI 전표(소비) | 🔶 backflush 자연스러움 |
| 재고이동(StockMove) | (ERP 이동요청 or 없음) | **이동작업지시** | 동일 평가영역이면 **전표 없음** | 🔶 법인·공장 간이면 전표 발생 |
| 반품(Return) | ERP 반품지시(RMA) | **반품입고작업지시** | credit memo/전표 | ✅ 3유형 재고영향 상이 |
| 재고실사(StockTake) | (실사계획) | **실사작업지시**(카운팅) | **조정전표만** ERP | ⚠ 카운팅=MES, 조정=ERP 분리 |

**주의 (패턴이 부분 적용되는 경우)**
- ⚠ **재고실사·반품**: "작업"(카운팅·반품 실물입고)은 MES 작업지시로 깔끔하나, **차이 조정/credit memo는 순수 회계 사건** → MES 작업지시 없이 ERP 전표로만 처리. → *"작업이 없는 순수 회계 트랜잭션"*엔 작업지시가 안 붙는다.
- ⚠ **재고이동**: 동일 평가영역 내면 회계전표 자체가 없음(전표 칸 공백).
→ 그래서 "**거의** 모든 트랜잭션에 적용" 이 정확(전부가 아니라 *실행 계층이 있는* 트랜잭션).

## 4. 출하 예시 흐름 (이해 검증 + 보정)

내부 논의에서 확인한 흐름. 골격(ERP 지시→MES 실행→결과 회신)은 정확, **제품LOT 선택 시점**만 보정.

```
[ERP] 출하지시 생성 (품목·수량·고객·납기)             ← 출하지시 No (ERP)
   │ 연계
   ▼
[MES] 출하작업지시 수신/생성
   │  Picking ── 실물 제품LOT 선택 (FEFO·위치·가용재고)   ★ 여기서 LOT 확정
   │  출하검사(OQC)
   │  Packing ── 납품라벨·고객 바코드 발행
   │  고객 출하
   │ 실행 결과 송신 (실제 출하 제품LOT·수량·납품라벨)
   ▼
[ERP] 출하(PGI) 전표 발행 + 매출·COGS·세금계산서        ← 출하 전표 No (ERP)
```

- ✅ 개념데이터모델 출하 엔티티 정의·ERD와 정합("ERP 출하지시 기준 Picking→출하검사→Packing→고객 출하", 속성: 출하지시(ERP) 참조·출하 제품LOT·납품라벨·고객 바코드).
- 🔶 **제품LOT은 보통 ERP 출하지시가 아니라 MES Picking에서 확정**(실시간 실물 LOT 재고·FEFO·위치는 MES 영역). ERP 사전할당 방식도 가능하나 덜 일반적.
- ⚠ **현장 확인**: 출하지시에 LOT이 찍혀 오는가, Picking에서 MES가 고르는가? (A5 역추적 시작점과 직결.)

## 5. B 섹션 검증 재정리

**사용자 제안 2축은 타당**하다 — 단, B엔 ERP와 무관한 **순수 MES 내부 구조** 질문이 섞여 있어 **"2축 + 잔여 1축"** 으로 보면 깔끔하다.

- **L1 — ERP가 정본인 기준정보 데이터** *(= 제안 ①: "ERP에서 확인할 데이터 종류")*
  ✅ BOM·공정(Routing)은 ERP→MES **I/F 연계 동기화 대상**(개념데이터모델 ERP-MES I/F 연계정의)으로 ERP 정본이 거의 확실 → 키 구조는 **ERP 마스터**에서 확인. **B1·B2**가 해당.
  ⚠ **마스터별 ERP 소유 정도는 차등** — BOM·Routing은 ERP 정본이 디폴트지만, **검사 기준(B5)은 정본이 ERP QM·MES·별도 QMS 중 미정**이라 L1이 아니다. 일반적으로 검사 *결과*(합/불·Lot release)는 ERP, 검사 *기준*(검사항목·UCL/LCL/Target·SPC)은 QMS/MES에 둔다. 문서 내에서도 ERP 연계대상에 '품질'이 있으나(연계정의 속성) C1 송신원천 목록·I/F정의–기준정보 관계엔 빠져 정본 미확정 → **B5는 L2(소유경계)로 이동.**
- **L2 — MES↔ERP 트랜잭션 소유·발번 조율** *(= 제안 ②: "관리 트랜잭션의 조율")*
  2~3절의 지시–작업지시–전표 경계 결정 사안.
- **L3 — MES 내부 키·정규화 (잔여, ERP 무관)**
  MES 실행/이력 구조 — MES **DB 스키마+덤프**로 확정. (앞선 결론: B는 대체로 실데이터로 풀리되 B6은 DDL 필요)

### 항목별 재분류

| 항목 | 질문 요지 | 렌즈 | 무엇으로 확정 | 개정 확인 방법 |
| --- | --- | --- | --- | --- |
| B1 | BOM Rev/유효기간·식별자 | **L1** | ERP BOM 마스터 스키마+값 | 전산담당: ERP BOM 마스터에서 Rev·유효기간 컬럼·키 확인 |
| B2 | Routing 공정Ver·Sequence 키 | **L1** | ERP Routing 마스터 스키마 | 전산담당: ERP 공정/Routing 마스터 키 구성 확인 |
| B3 | 작업실적 발행 단위 | ✅ **확정**(2026-06-24) | — | 현장 실태만 확인 |
| B4 | 검사결과 헤더/라인 vs 평면 | **L3** | MES 검사실적 스키마+화면 | 품질담당: MES 검사실적 입력 화면/테이블 구조 |
| B5 | 검사기준 정본 + 품질기준값 식별자 | **L2(소유경계)+L3** | 정본=ERP QM/MES/별도 QMS 확정 + 키 구조 | 품질담당+전산담당: 검사기준 정본 시스템·ERP 연계 범위(결과만/기준까지)·식별자 |
| B6 | 설비/툴 이력 키, 화면ID=실 PK? | **L3**(DDL 필요) | MES DDL·발번규칙 | 설비담당: 실 PK·발번규칙(값만 보고 화면ID를 PK로 오인 금지) |
| B7 | 재고 키·LOT:Location·상태 | **L3**(키) + L2(정합) | MES 재고 스키마 + ERP 재고 정합 경계 | 물류담당: 재고 키 단위·상태컬럼 / 재고 정본·동기화 |
| B8 | 트랜잭션 발번 주체 | **L2** | 지시–작업지시–전표 3계층 경계 결정 | 전산+물류담당: 7개 트랜잭션을 3계층으로 분해해 소유 확정 |

**요지**
- ✅ 제안 2축은 B의 **5개** 를 포착 — L1(ERP 정본 기준정보)=**B1·B2**, L2(소유·정본 조율)=**B5·B7·B8**.
- 🔶 **잔여 2개(B4·B6)** 는 ERP·트랜잭션과 무관한 **MES 내부 정규화** → 별도 축으로 둔다.
- 🔶 **검증 방법 재배치**: L1은 *ERP 마스터 스키마 열람*, L3은 *MES DB 스키마+대표 덤프*로 사실상 닫힘. **대면 검증이 꼭 필요한 건 L2(B5 검사기준 정본·B8 발번) + B6(발번규칙)** 로 좁혀진다.
