## §1. 개요

### 1-1. 이 문서가 무엇인가

화면 상세 스펙 **확대 1차 13장 + 파일럿 `W-06-07`**에서 도출한 **기준정보 도메인 API 계약 초안**의 사람이 읽는 쪽이다. 산출물은 **한 쌍**이다.

| 파일 | 담는 것 |
| --- | --- |
| `06-API-요구서.md` *(이 문서)* | 화면 → API 매핑 · **왜 이 API가 필요한가**(근거 화면·절 번호) · 적합성 판정 · 공통 규약 대조 · 미착지가 무엇을 막는가 · 범위 밖 |
| `openapi/mdm-기준정보.json` | 경로 **73** · 스키마 **102** · 요청/응답 · 제약 · 상태코드 |

**필드표를 한 줄도 쓰지 않았다.** 같은 것이 여러 곳에 있고 서로 어긋난 것이 공유계약 **§I 확정↔하류 불일치 14건**의 원인이었다(`00-설계.md` §3-2). 요구서는 **왜·어디서**를 설명하고 **무엇**은 OpenAPI를 가리킨다.

### 1-2. 어디에 쓰이는가 — WBS P0.4의 초안 입력

WBS §4.2 **P0.4**가 「API 계약 v0 + 목업 서버」로 이미 계획돼 있고, 전략은 **계약 우선(Contract-first)**, 형식은 **OpenAPI**다. 다만 백엔드 공식 진행이 **데이터 모델링까지**라 P0.4가 아직 서 있지 않다.

> **→ 이 산출물은 P0.4의 초안 입력이다.** 계약으로 확정하고 소유하는 것은 **통합 Agent** 몫이며(변경 승인권도 그쪽 단일화), 우리는 **화면이 무엇을 요구하는지**를 근거와 함께 정리해 넘긴다. 이 문서에서 직접 계약을 확정하지 않는다.

### 1-3. 범위

**화면이 돌아가는 최소 완결**이다 — 대상 14화면이 저장하는 마스터의 CRUD + 그 화면들이 **선택 목록으로 필요로 하는 조회 전용**.

| --- | --- |
| **대상 화면 14** | `W-CO-02` · `W-06-01`~`06` · `W-06-07` · `W-06-10` · `W-06-11` · **`W-06-14`**(2026-08-07 추가) · ⭐ **`W-06-08` · `W-06-09` · `W-06-12`**(2026-08-18 복귀 — §3-12~3-14) |

### 2-1. 세 층으로 읽는다

> «(정합주: `00-설계.md` §3-1은 OpenAPI 파일을 `.yaml`로 적었으나 실제 산출은 `.json`이다 — 표준 라이브러리만 쓴다는 저장소 관행(`pip install` 금지)상 YAML 파서를 쓸 수 없어 검산·생성이 전부 `json` 모듈로 돌아간다. 형식만 다르고 OpenAPI 3.1 문서인 것은 같다.)»

### 2-2. 근거 추적 — `x-source-table` · `x-source-column`

물리 모델에 대응물이 있는 스키마 **64종**(전체 102종 중)에 `x-source-table`이, 그 프로퍼티에 `x-source-column`이 달려 있다. 「이 필드가 물리 모델의 어느 컬럼에서 왔나」를 읽는 사람이 바로 확인하기 위한 것이며, **검산 입력이 아니다**(`00-설계.md` §5-4). 물리 모델에 대응물이 없는 것(공통 응답 스키마 7종·`Editability`·`PageMeta` 등)에는 달지 않았다 — **없는 것이 정상**이다.

각 오퍼레이션의 `description`은 항상 `근거: W-06-07 §5-1 · 공유계약 B-4` 형태의 문구로 끝난다. **109개 오퍼레이션 전건**이 이 형태를 지킨다 — 근거가 없는 둘(`legal-entities`·`production-lines`)도 **「근거: 없음 — 어느 화면도 쓰지 않는다」**로 명시했다(§4-3).

### 2-3. 73개 경로를 규칙으로 읽는 법 — **리소스 패턴이 셋이다**

경로를 하나씩 외울 필요가 없다. **테이블의 컬럼 구성이 URL 모양을 결정**한다.

| # | 패턴 | 판별 | 경로 모양 | 낙관적 잠금 |
| :-: | --- | --- | --- | --- |
| **가** | **마스터 형** | `is_active` · `version_no` **있음** | `GET/POST 컬렉션` · `GET/PUT 상세` · `POST …:deactivate` | **있다** — `If-Match` + 409 |
| **나** | **부여·회수 형** | `created_at`·`created_by` **만** | `GET/PUT 하위 컬렉션` — **전체 치환** | **없다** — `version_no` 컬럼 자체가 없다 |
| **다** | **버전 마스터 형** | 헤더–버전–라인 + `status_code` + 유효기간 | 위 + `:new-revision` · `:confirm` · `:obsolete` | 헤더/버전 PUT에만 |

- **(가) 마스터 형** — 물리 삭제가 없다. 끄는 것은 `:deactivate` 하나뿐이며 되살리는 액션은 화면에 없어 만들지 않았다. 상세 응답에 **`editability`**(수정 가능 여부·사유·참조 건수)가 붙는다 — 화면이 참조를 세지 않는다(B-4).
- **(나) 부여·회수 형** — 개별 POST/DELETE가 아니라 **최종 상태를 통째로 보내는 PUT**이다. 체크박스 화면이 서버와 어긋날 여지가 없고 서버가 한 트랜잭션으로 반영한다. `is_active`가 없으므로 **B-4「물리 삭제 금지」를 적용하지 않는다**(적용하면 존재하지 않는 컬럼을 요구하게 된다 — B-6).
- **(다) 버전 마스터 형** — 확정 후 in-place 수정을 금지하고 변경은 신규 Rev로만 한다. **`:deactivate`를 쓰지 않는다**(끄는 것이 아니라 상태를 옮긴다). 첫 Rev를 만들 길이 없어 **부트스트랩 `POST` 컬렉션**을 따로 둔다 — 두 번째 이후는 반드시 `:new-revision`이다.
- **로그·이력 조회** — `/integration/messages` 4개 경로(`GET`·`POST :retry`·`POST :retry-batch`)와 `/audit/events` 1개는 세 패턴 밖이다. 로그성 조회 전용이므로 상태 관리·낙관적 잠금 규칙이 적용되지 않는다.

> ⚠ **「전체 치환」은 「행 교체」가 아니다.** `routing_operation`을 `production.work_order.routing_operation_id`가 **`NOT NULL`로** 참조한다(실측 4군데). `DELETE` 후 `INSERT`로 구현하면 **진행 중 작업지시가 무너진다.** 계약은 「최종 상태를 보내고 **서버가 기존 행을 유지하며 순서만 갱신**한다」이며, 이 문장이 OpenAPI `description`에 못박혀 있다.

### 2-4. 오류가 두 계열로 갈린다 — **409와 400을 섞지 않는다**

| 코드 | 뜻 | 스키마 | 언제 |
| :-: | --- | --- | --- |
| **409** | **낙관적 잠금 충돌 전용** | `ConflictResponse` — `conflictCause` 3값 `user`/`erpSync`/`workerLease` | **`If-Match` 헤더가 있는 경로에만.** 해결책이 **재로드**인 경우 |
| **400** | **업무 규칙 위반** | `ErrorResponse` — `errors[]`의 `scope`(필드/화면)·`code`·`uniqueScope` | 상태 잠김(`code: "STATE_LOCKED"`) · 라인 0건 확정(`LINE_REQUIRED`) · 유일 위반 · 짝 제약 · 범위 위반 |

**왜 나눴나.** 상태가 확정이라 편집이 막힌 것을 409로 내리면 화면이 「다른 사용자가 먼저 수정했습니다 · [최신 불러오기]」를 띄운다 — **재로드해도 풀리지 않는다.** 기존 3값이 전부 재로드·재시도로 풀리는 경합인데 상태 잠김만 그렇지 않다는 것이 결정적 증거였다(전체 치환 PUT에는 `If-Match`가 없고 `routing_operation_dependency`에는 `version_no` 컬럼 자체가 없다).

**유일한 예외**: `POST /integration/messages/{id}:retry`의 409는 `version_no`가 없는 테이블의 **워커 리스 충돌**이다(`conflictCause=workerLease`) — 낙관적 잠금은 아니지만 「재시도하면 풀린다」는 성질이 같아 409에 둔다. 공유계약 B-1 확장이 이미 이 경우를 3번째 원인으로 규정했다.

## §3. 화면 → API 매핑

`openapi/ui-요구목록.md`의 **화면 11 · 액션 80**을 전건 소화한다. 액션 이름과 활성 조건은 화면 스펙 §5-1 원문 그대로다.

### 3-0. 「없음」의 다섯 가지 — 이유가 다르면 대응이 다르다

「없음」을 한 덩어리로 두면 읽는 사람이 전부 결손으로 읽는다. **정상인 없음과 막힌 없음을 가른다.**

| 표기 | 뜻 | 나중에 무엇이 채우나 |
| --- | --- | --- |
| **범위 밖** | 이 스펙이 다루지 않는 도메인·화면의 소관 | 다른 스펙 |
| **미착지** | 물리 모델에 근거가 없어 지금 만들면 **지어내는 것**이 된다 | **이슈 해소**(번호 필수) |
| **선행 미결** | 화면 스펙 자신이 정책·자료를 미결로 남겼다 | 해당 화면 §8 미결 결정 |
| **소관 이동** | 엔드포인트는 이 스펙 안에 있고 **다른 화면이 실행을 소유**한다(중복 구현 금지) | — 정상 |
| **API 불필요** | 화면 안에서 끝난다(로컬 취소·이미 받은 데이터 펼침 등) | — 정상 |

집계는 §3-11에 둔다.
