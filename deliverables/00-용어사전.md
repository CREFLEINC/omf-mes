# 00 — 용어 사전

> 작성일: 2026-08-03 (**v1.1 — 2026-08-06 「계약 정본」 신설**) · 작성 주체: CREFLE OMF 팀
> **성격**: 이 프로젝트가 만들어 쓰는 말의 뜻을 모은 것. 편람 01~06과 `uiux/` 문서를 읽다 막히는 말이 있으면 여기를 본다.
> **왜 필요한가**: 설계를 진행하며 개념을 구분할 필요가 생길 때마다 말을 만들어 썼다. 만든 쪽에는 자명하지만 처음 읽는 사람에게는 아니다. **문서를 고치는 대신 사전을 둔다** — 96곳을 바꾸는 것보다 뜻을 한 곳에 적는 편이 싸고, 원문의 맥락도 보존된다.
> **범위**: 이 프로젝트의 조어와, 일반 용어인데 **이 프로젝트에서 좁은 뜻으로 쓰는 말**만 담는다. 일반적인 IT 용어는 담지 않는다.

## 1. 가장 자주 막히는 말

### 미착지 (未着地)

**결정은 났거나 화면이 요구하는데, 그것이 데이터베이스에 내려앉지 않은 상태.** 「아직 땅에 닿지 않았다」는 뜻이다.

두 종류가 섞여 있다.

| 종류 | 뜻 |
| --- | --- |
| **결정이 안 내려앉음** | 회의에서 확정했는데 물리 모델에 반영되지 않았다 |
| **화면이 요구하는데 없음** | 화면이 필요로 하는 컬럼·테이블이 애초에 없다 |

**예** — 2026-07-06 결정 12가 「불량코드와 공정은 N:M으로 조정한다」를 승인했으나, 2026-07-23 완성된 물리 모델은 조정 전 형태(`defect_code.process_id`, N:1)로 굳었다. 결정이 **착지하지 못했다.** 그래서 「공정 매핑」 API 엔드포인트를 만들 수 없다 — 없는 테이블을 스펙에 넣으면 개발자가 「만들어야 할 것」으로 읽기 때문이다.

**왜 세어 두는가** — 원칙이 「없는 것을 스키마에 지어 넣지 않는다」이므로, 그냥 두면 그 자리가 비어 보이고 나중에 「왜 이 API가 없지?」가 된다. **없는 이유와 무엇이 막히는지를 표로 남긴다.**

> 📍 `06-API-요구서.md` §5 (기준정보 도메인 16건) · 각 화면 상세 스펙 §8

**비슷하지만 다른 말** — [미결](#미결) · [범위 밖](#범위-밖)

## 2. 화면 설계

### 도식 근거 / 비도식 근거

화면을 도출한 **근거의 출처**를 가른다.

- **도식 근거** — FigJam 캔버스의 터치포인트(사용자가 시스템과 닿는 지점)에서 나온 것
- **비도식 근거** — 캔버스에 없지만 요구사항·결정 기록·데이터 모델에서 필요성이 드러난 것

화면은 **창작하지 않는다.** 둘 중 하나에 근거가 있어야 목록에 오른다. 비도식 근거 규칙을 적용해 v1.3에서 화면 6건 삭제·1건 통합·3건 신설이 일어났다.

### 신뢰도 3등급 — 확정 / 추정 / 미정

화면 목록의 각 행이 **얼마나 단단한가**를 표시한다.

| 등급 | 뜻 |
| --- | --- |
| **확정** | 도식과 배지가 명확하다 |
| **추정** | 성격 판단으로 도출했다 — 근거는 있으나 해석이 들어갔다 |
| **미정** | 고객 회신 대기(E1·E3·E4 등)로 **화면의 존재나 범위 자체가 유동적**이다 |

등급별 건수는 `uiux/2026-07-25-화면목록-IA/screen-inventory-ia.md` §1 이 갖는다 — 화면 수는 `python3 deliverables/verify-screen-inventory.py`.

### 근거 4면

화면 상세 스펙을 쓸 때 **반드시 대조하는 네 가지 입력**.

```
프로세스 편람(05)  ×  화면·IA(04)  ×  요구사항(01)  ×  물리 모델(SQL)
```

**넷이 서로 어긋나면 고치지 않는다.** §8 미결에 기록하고, 정본 수정은 각 소관에서 한다(물리 모델은 읽기 전용이므로 `[docs→데이터모델]` 이슈).

이 대조가 「확정 ↔ 하류 불일치」를 찾아내는 장치다 — 확대 1차에서 14건이 나왔다.

### 셸 (Shell)

**하나의 React 코드베이스에서 갈라져 나오는 세 프로그램.** 화면 ID의 첫 글자가 어느 셸인지 가리킨다.

| 기호 | 셸 | 형태 |
| :-: | --- | --- |
| **W** | 관리웹 | 브라우저 |
| **P** | POP | Electron 키오스크 (1024×768) |
| **M** | 모바일 | Capacitor Android (PDA) |

### 결번

**화면 ID 체계에서 비어 있는 번호.** 화면을 삭제·통합·이관하면 뒤 번호를 당기지 않고 그 번호를 비워 둔다. 과거 문서가 그 번호를 인용하고 있기 때문이다.

현재 12건 — `W-01-08` · `W-02-09` · `W-03-04` · `W-03-06`~`08` · `W-04-09` · `W-05-14` · `W-CO-07` · `M-01-03` · `M-04-02` 등.

### 계약 정본

**서버와 클라이언트가 주고받을 형태를 정한 OpenAPI 문서.** 경로 · 요청 · 응답 · 제약 · 상태코드가 들어 있다.

**⚠ [공유계약](#공유계약)과 다르다.** 둘 다 「계약」이라 부르지만 층이 다르다.

| | 무엇을 정하나 | 어디에 |
| --- | --- | --- |
| **공유계약** | **어떻게 쓸지의 규칙** — 화면을 가로지르는 규약 | `uiux/화면상세스펙-공통/공유계약.md` |
| **계약 정본** | **주고받을 형태 그 자체** | `deliverables/openapi/*.json` |

**둘은 서로를 대신하지 못한다.** 예를 들어 승인 워크플로우는 **규칙이 이미 촘촘하다** — 「승인자는 요청 시점에 사람으로 확정한다」(공유계약 §J-3) · 「사유는 필수」(§J-4) · 「결재는 되돌릴 수 없다」(§J-6). **그런데 `POST /app/approval-requests` 가 없으면** 프론트는 「품의 상신」 버튼이 어디로 보내야 하는지 모르고, 목 서버도 흉내 낼 것이 없다.

> **「계약이 없다」고 적을 때는 어느 쪽인지 밝힌다.** 대개는 **계약 정본**(부를 API가 없다)을 가리킨다.

**왜 이 말을 쓰나** — 설계 저장소가 정본이고 클라이언트 저장소로 **복사하지 않는다.** 복사해 두면 갱신이 갈리기 때문에, 클라이언트는 이 파일을 **참조하거나 빌드 시 가져간다.**

⚠ **`description` 에 적은 것은 공개된다** — 클라이언트의 타입 생성기가 주석으로 옮겨 공개 저장소에 커밋한다. 내부 서술은 `x-internal-note` 에 둔다(이슈 #92).

> 📍 `deliverables/openapi/` · 작성 방법은 `deliverables/06-API-요구서.md`

**비슷하지만 다른 말** — [공유계약](#공유계약) · [리소스 패턴 3종](#리소스-패턴-3종)

### 공유계약

**모든 화면 상세 스펙이 따르는 횡단 규약 문서.** 화면마다 따로 정하면 어긋나는 것들 — 유일 제약 위반 문구, 낙관적 잠금, 편집 가능성 판정, 순서 재배치, 오류 계열 — 을 한 곳에 모았다.

조항은 §A~§H로 나뉘고 각 조항에 번호가 붙는다(A-5, B-1 …). 현재 v0.4.1.

> 📍 `uiux/화면상세스펙-공통/공유계약.md`

### §I 불일치 대장

공유계약 안에 있는 표로, **확정 기록·설계 결정과 물리 모델이 어긋난 곳**을 모은 것. 확대 1차에서 14건이 발견됐다.

[미착지](#미착지-未着地)와 겹치지만 시점이 다르다 — §I는 「어긋났다」는 **발견의 기록**이고, 미착지는 그중 「그래서 지금 만들 수 없다」는 **작업의 제약**이다.

## 3. API 스펙

### 리소스 패턴 3종

OpenAPI의 오퍼레이션 109개는 세 가지 틀의 복제다. 이 셋을 알면 전체를 규칙으로 읽을 수 있다.

| 패턴 | 판별 | 형태 |
| --- | --- | --- |
| **마스터 형** | `is_active` 컬럼이 있다 | 목록·상세·생성·수정 + `:deactivate` |
| **부여·회수 형** | 연결 테이블 (`version_no` 없음) | **전체 치환 `PUT`** 하나. 409 없음 |
| **버전 마스터 형** | 헤더–버전–라인 구조 | `:new-revision` · `:confirm` · `:obsolete` |

세 패턴에 들지 않는 것은 로그·이력 조회 5개 경로뿐이다.

### 낙관적 잠금

**두 사람이 같은 행을 동시에 고칠 때 나중 저장이 앞 저장을 소리 없이 덮어쓰는 것을 막는 방법.**

화면을 여는 순간 잠그는 게 아니라(비관적), **저장하는 순간에만 어긋났는지 본다.** 행마다 판 번호(`version_no`)를 두고, 조회할 때 받은 번호를 저장할 때 되돌려 보낸다. 그사이 남이 고쳤으면 번호가 달라져 거부된다.

이 프로젝트에서는 판 번호를 **HTTP 헤더로** 주고받는다 — 응답의 `ETag`, 요청의 `If-Match`. 화면에는 표시하지 않는다(공유계약 A-4).

### 전체 치환

**목록의 순서를 바꿀 때, 바뀐 행만 보내지 않고 최종 순서 전체를 한 번에 보내는 것.**

순서 컬럼에 유일 제약이 걸린 곳에서는 행을 하나씩 바꾸면 **중간 상태가 반드시 제약을 위반한다**(1번과 2번을 맞바꾸는 도중 2번이 둘이 된다). 그래서 서버가 한 트랜잭션으로 처리한다.

⚠ **「전체 치환」은 행을 지우고 다시 만드는 것이 아니다.** 기존 행을 유지하며 순서만 갱신한다 — `work_order`가 공정 행을 `NOT NULL`로 참조하고 있어, 지웠다 다시 만들면 진행 중 작업지시가 무너진다.

> 📍 공유계약 A-5

### 수신본

**ERP에서 받아온 데이터.** MES가 만든 것이 아니므로 원칙적으로 **읽기 전용**이고, MES는 자기 확장 속성만 덧붙인다.

⚠ 현재 `code_group`·`code_value`·`department`는 **이것이 수신본인지 판정할 컬럼이 물리 모델에 없다.** 그래서 API가 쓰기를 열어 두고 있다 — 미착지 8번, 가장 위험한 항목으로 분류돼 있다.

### 적합성 5항목

API가 **화면에서 쓰기에 적절한가**를 재는 다섯 가지. 「필드가 물리 모델과 맞는가」가 아니라 「화면이 이걸로 돌아가는가」를 묻는다.

1. 화면 진입에 API를 몇 번 부르는가
2. 화면이 필요한 정보가 응답에 있는가
3. 화면이 안 쓰는 것을 담지 않았는가
4. 화면이 보여야 할 예외를 표현할 수 있는가
5. 화면의 상태 전이를 지원하는가

이 잣대가 **낙관적 잠금이 구현 불가였던 것**을 잡아냈다 — 저장에 판 번호를 요구하면서 어느 응답에도 그 값을 주지 않고 있었다.

### 「없음」 5분류

화면의 어떤 동작에 대응하는 API가 **없을 때**, 왜 없는지를 다섯으로 가른다. 빈칸으로 두면 누락으로 읽히기 때문이다.

| 분류 | 뜻 | 나중에 누가 채우나 |
| --- | --- | --- |
| **범위 밖** | 다른 도메인 소관이다 | 그 도메인 스펙 |
| **모델 미반영**([미착지](#미착지-未着地)) | 물리 모델에 근거가 없다 | 데이터 모델 담당 (이슈) |
| **선행 미결** | 화면 §8의 결정이 나야 한다 | 이 트랙·고객 |
| **소관 이동** | 엔드포인트는 있고 다른 화면이 소유한다 | 없음 (중복 구현 금지 표시) |
| **API 불필요** | 화면 안에서 끝난다 (로컬 정렬 등) | 없음 (정상) |

앞의 셋은 **막힌 것**이고 뒤의 둘은 **없는 게 정상**이다.

### editability / 편집 가능성

응답에 함께 실려 오는 **「이 행의 어느 부분을 고칠 수 있는가」**. 화면이 필드를 회색으로 만들지 판단하는 근거다. 규칙을 화면마다 다시 짜지 않게 서버가 알려 준다.

잠기는 이유는 값으로 온다.

- `RECEIVED_FROM_ERP` — ERP 수신본이라 원본 필드는 잠긴다
- `NOT_COUNTABLE` — 다른 곳에서 이 값을 몇 군데서 참조하는지 셀 수 없어 무조건 잠근다

## 4. 디자인시스템

### 갭 등급 a / b / c / d

화면이 요구하는 UI 요소가 디자인시스템(`@crefle/web-ui`)에 **없을 때**, 누가 만들어야 하는지를 가른다.

| 등급 | 상태 | 누가 |
| :-: | --- | --- |
| **a** | 그대로 있다 | 끝 |
| **b** | 컴포넌트는 있는데 변형·prop이 없다 | **DS 이슈**(확장 요청) |
| **c** | 기존 컴포넌트의 **조합**이다 | **제품이 소유**. 이슈 없음 |
| **d** | 진짜 새 원시 요소다 | 제품에서 먼저 만들고 [세 곳 규칙](#세-곳-규칙)으로 승격 |

### 세 곳 규칙

**새 컴포넌트를 디자인시스템에 올리는 기준** — 사용처가 **세 곳**에서 확인되면 승격 후보가 된다. 한두 곳에서 쓰는 것을 DS에 넣으면 공용 자산이 특정 화면에 오염되기 때문이다.

⚠ 「행 순서 UI가 필요한 곳」과 「서버 일괄 치환이 필요한 곳」은 **다른 목록**이다. 전자는 DS 갭(G-7), 후자는 공유계약(A-5) — 겹치지만 같지 않다.

## 5. 문서·소유

### 정본

**어긋났을 때 이기는 쪽.** 사본이 아니라 기준이라는 뜻이다.

| 대상 | 정본 |
| --- | --- |
| 화면 목록 | `uiux/…/screen-inventory-ia.md` |
| 필드·컬럼 | 물리 모델 SQL (읽기 전용) |
| 편람(01~06)과 원본 | **원본이 우선** — 어긋나면 편람을 갱신한다 |

### 확정 기록

**결정이 내려진 사실과 그 근거를 남긴 것.** 「검토 중」이나 「제안」과 구분한다. 날짜와 결정권자를 함께 적는다.

확정 기록이 있는데 하류(물리 모델·화면)에 반영되지 않으면 그것이 [미착지](#미착지-未着地)이고 [§I 불일치](#i-불일치-대장)다.

### 미결

**아직 정해지지 않아 지금 결정할 수 없는 것.** 각 화면 스펙 §8에 모은다.

[미착지](#미착지-未着地)와 다르다 — 미결은 **결정이 없는 것**이고, 미착지는 **결정은 있는데 반영이 없는 것**이다.

### 범위 밖

**이 문서·이 스펙이 다루지 않기로 한 것.** 빠뜨린 것이 아니라 의도적으로 제외한 것임을 표시한다. 어디서 다루는지를 함께 적는다.

### 이슈 접두 — `[uiux→docs]` / `[docs→데이터모델]`

GitHub 이슈 제목의 접두로 **어느 영역에서 어느 영역으로 보내는 요청인지**를 표시한다.

각 영역은 남의 문서를 직접 고치지 않는다. `docs/`와 물리 모델은 읽기 전용이고, 반영이 필요하면 이슈를 낸다. `[docs→데이터모델]` 계열은 **담당자 지정이 필수**다.
