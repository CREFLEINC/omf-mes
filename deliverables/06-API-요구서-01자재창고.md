## §1. 개요

### 1-1. 이 문서가 무엇인가

**계약 정본은 OpenAPI다. 이 문서는 그것이 왜 그렇게 생겼는지를 적는다.**

| | 담는 것 |
| --- | --- |
| `openapi/logistics-01자재창고.json` | **무엇을** — 경로 · 스키마 · 요청/응답 · 제약 · 상태코드 · `example` |
| **이 문서** | **왜·어디서** — 화면→API 매핑 · 적합성 판정 · 미착지가 무엇을 막는가 · 범위 밖 |

**필드표를 여기 쓰지 않는다.** 같은 것을 두 곳에 적은 것이 공유계약 §I 불일치 34건의 원인이었다.

### 1-2. 어디에 쓰이는가

프론트가 **화면 하나를 지금 시작해도 되는지** 판단하는 근거다. §3의 매핑에 「없음」이 없고 §5의 미착지가 그 화면을 건드리지 않으면 착수 통지를 낸다.

백엔드에는 **구현 대상 목록**이다. 물리 모델은 이미 있으므로(01~04 테이블 78개) 대부분은 옮기는 일이고, 모델이 없는 한 곳만 §5-2가 따로 표시한다.

## §2. 읽는 법

### 2-1. 세 층으로 읽는다

```
화면 상세 스펙 §5 액션        무엇을 하고 싶은가
        ↓  §3 매핑
OpenAPI 경로·오퍼레이션        어떻게 부르는가
        ↓  x-source-table / x-source-column
물리 모델 컬럼                 어디에 저장되는가
```

**세 층이 다 이어져야 계약이다.** 어느 한 층이 끊기면 §3의 「없음」 다섯 가지 중 하나로 분류한다(§3-0).

### 2-2. 근거 추적 — `x-source-table` · `x-source-column`

전 스키마에 붙어 있다. 필드 하나를 잡고 어느 테이블 어느 컬럼인지 바로 볼 수 있다. **비어 있는 것은 한 곳뿐**이고 그것이 §5-2의 조정 대상이다.

### 2-3. 55개 경로를 규칙으로 읽는 법 — **리소스 패턴이 여섯이다**

기준정보는 셋(마스터·부여회수·버전마스터)이었다. 01은 **업무 문서**라 셋이 더 필요했다.

| 패턴 | 판별 | 01 개수 | 생김새 |
| :-: | --- | :-: | --- |
| 가 | `is_active` + `version_no` | 1 | `GET`·`POST`·`PUT`·`:deactivate` |
| 나 | `created_at`·`created_by` 만 | 3 | 하위 컬렉션 `GET`·`PUT`(치환) |
| 다 | 헤더–버전–라인 | **0** | 01에는 없다 |
| **라** | **`status_code` + `version_no`** | **15** | `GET`·`POST`·`PUT`·`PUT …/lines`·**상태 전이 동사** |
| **마** | 파티션 + 멱등키 + append-only | 1 | **`GET` 만** |
| **바** | `GENERATED` 파생 | 1 | **`GET` 만** |

**업무 문서 형에 끄기(`:deactivate`)가 없다.** 문서는 끄는 것이 아니라 상태를 옮긴다.

**상태 전이 동사는 셋이다** — `:confirm`(더 못 고친다) · `:post`(재고가 움직인다) · `:request-approval`(승인 요청). 네 번째로 정했던 `:cancel`은 **하나도 쓰이지 않았다**(§5-1).

**문서 고유 동사는 넷** — `:split` · `:complete` · `:complete-temporary` · `:arrive` · `:close` · `:pick`.

### 2-4. 오류가 두 계열로 갈린다 — **409와 400을 섞지 않는다**

| | 뜻 | 화면이 하는 일 |
| :-: | --- | --- |
| **409** | 저장 충돌 — **다시 읽어 오면 풀린다** | 재로드 후 재시도 안내 |
| **400** | 검증·상태 위반 — **고쳐야 풀린다** | 인라인·배너 오류(`ErrorItem.scope`) |

**`STATE_LOCKED`가 400인 것이 핵심이다.** 확정·전기된 전표를 수정하려 한 것은 재로드해도 풀리지 않는다.

⚠ **`If-Match`를 받는 오퍼레이션은 전부 409를 선언한다.** 토큰을 받아 놓고 불일치 응답을 안 적으면 클라이언트가 두 계열을 섞는다 — 검사기가 이 조건을 지킨다(§2-5).

### 2-5. 검산

```bash
cd deliverables

# ① UI 요구 목록 재생성 — 화면 스펙 §5 액션 표에서 전건 추출
python3 verify-ui-coverage.py --domain 01     # → 화면 19 · 액션 109 (+ 표 없는 화면 4)
python3 test-verify-ui-coverage.py            # 회귀 테스트 14건

# ② 커버리지 축 — 그 액션이 이 문서 §3 매핑표에 다 있는가
python3 verify-mapping-coverage.py --domain 01
python3 test-verify-mapping-coverage.py       # 회귀 테스트 11건

# ③ 계약이 계약으로 성립하는가 — 구조 검사 9종
python3 openapi/check-structure.py

# ④ description 이 공개돼도 되는가 (#92)
python3 openapi/check-public-safe.py
```

**대조 규칙**: `openapi/ui-요구목록-01자재창고.md`의 액션 **109건**이 §3 매핑표에 하나도 빠짐없이 있어야 한다. 엔드포인트가 없는 액션도 **「없음 + 이유」로 한 행을 차지**한다. **빈칸은 누락이다.**

⚠ **「전건 소화」를 사람이 세지 않는다.** 기준정보 트랙에서는 눈으로 대조했는데, 109건에서는 몇 건이 빠져도 보이지 않는다 — ②가 그 대조를 기계로 한다. **실제로 초안에서 2건을 잡았다**(`W-01-05`의 「대체입고 예정 선택」·「반품 수량 입력」을 줄여 적어 대조에 걸리지 않았다).

⚠ **②는 §3 매핑표의 첫 열만 본다.** 소절 본문 전체를 대조하면 「조회」·「취소」처럼 짧은 액션이 **산문에 우연히 등장하기만 해도 통과**한다 — 커버리지를 보증하려는 도구가 커버리지를 부풀린다. 회귀 테스트가 이 경로를 잠근다.

⚠ **액션 표가 없는 화면 4장**(`W-01-01`·`W-01-02`·`W-01-10`·`M-01-01`)은 목록에 안 잡힌다. **§5 본문에서 사람이 읽어** §3-20~23에 따로 옮겼다 — 목록에 없다고 요구가 없는 것이 아니다.

## §3. 화면 → API 매핑

### 3-0. 「없음」의 다섯 가지 — 이유가 다르면 대응이 다르다

| 표기 | 뜻 | 나중에 무엇이 채우나 |
| --- | --- | --- |
| **범위 밖** | 이 스펙이 다루지 않는 도메인·화면의 소관 | 다른 스펙 |
| **미착지** | 계약·모델에 근거가 없어 지금 만들면 **지어내는 것**이 된다 | **횡단 계약 신설** 또는 이슈 해소 |
| **선행 미결** | 화면 스펙 자신이 정책·자료를 미결로 남겼다 | 해당 화면 §8 미결 결정 |
| **소관 이동** | 다른 화면이 실행을 소유한다(중복 구현 금지) | — 정상 |
| **API 불필요** | 화면 안에서 끝난다(스캔 입력·로컬 취소·요청 필드 채우기) | — 정상 |

집계는 §3-24에 둔다.

1. ⭐ **후속 판정을 서버가 한다** — 원천 참조가 다형(`source_document_type_code` + `source_document_id`)이라 규약이 없는데, 프런트가 「입고 → 출고·이동·투입」 관계표를 하드코딩하면 **유형이 늘 때마다 취소 판정이 조용히 틀린다**
2. ⭐ **실행 시점 재판정** — 승인을 기다리는 사이에 후속이 생기면 자동 실행은 그것을 못 본다. 재판정에 걸려도 **승인은 유효하고** 새 요청을 다시 올리지 않는다
3. **취소는 반드시 승인을 탄다** — 물류 문서 **12테이블에 `cancel*` 컬럼이 0건**이라 승인 기록이 이력을 대신한다. 승인 없는 취소 경로를 두면 **흔적 없는 취소**가 생긴다

⚠ **덮는 것은 6유형이다** — 발주·입하·입고·출고요청·피킹·이동요청. 외주 2문서는 **상태 컬럼 자체가 없고**(§I-37) 출하·생산품 입고는 다른 도메인이다. 화면은 유형 선택지에 두되 비활성으로 그린다.

⚠ **취소 실행 경로는 3리소스에만 있다** — 입하·입고·출고. FR-IM-076~078 이 그 셋만 요구했고, 출하 취소는 04 도메인이다.

### 5-1. ✅ **되돌리는 전이가 생겼다** — 초판의 `:cancel` 0건이 닫혔다 *(2026-08-07)*

> **초판 진단이 옳았고, 그 진단이 화면 신설로 이어졌다.** 아래는 초판 기록이고 **§5-1-1이 결과**다.

23장의 「취소」 버튼을 전수 확인했다. **전부 화면 이탈**(저장 전 복귀)이다.

```

M-01-06  M-01-01 로 복귀
W-01-11  W-01-03 으로 복귀
```

**문서를 취소 상태로 옮기는 액션이 화면에 0건**이므로 계약에도 만들지 않았다. 그 결과:

| 무엇이 막히나 | |
| --- | --- |
| 전기된 전표를 되돌리는 경로 | **없다.** 원장의 역처리 행을 만들 오퍼레이션이 없다 |
| 현재 유일한 보정 경로 | **실사 → 조정**(`W-01-04` → `W-01-12`) |

> **지어내지 않았다.** 화면 없는 오퍼레이션을 만들면 프론트가 부를 데가 없고 진짜 화면이 생기면 버린다. **취소·역처리 화면이 인벤토리에 필요한지**를 먼저 정해야 한다 → §8-1.
