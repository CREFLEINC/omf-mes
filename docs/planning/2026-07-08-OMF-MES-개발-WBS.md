### 3.3 확정된 구현 원칙 (전 작업 패키지 공통)

1. **설정형(configurable) 우선** — 점검 통제 3단계, ERP 송신 on/off, 중단 사유 코드, FEFO/FIFO 품목별, 알람 채널, 타발수 환산 등.
2. **기록은 생략하지 않는다** — 긴급 직행도 기록 2건 자동 생성, 전량 출고에도 출고 QR, 재생재도 내부 genealogy 완전 기록.
3. **연계 원본 읽기 전용 + MES 확장 속성만 편집** — 품목·BOM·P/O 등 ERP 수신 6종.
4. 정본 지도: LOT 3종·Routing·툴·검사기준·Location·예비품 = **MES 정본** / 품목·BOM·공통코드·조직·작업자·P/O = **ERP 정본** / 출하지시 = 고객사 엑셀 import.
5. 다국어 전범위(한/베, 사용자별 언어) · POP 사번 경량 인증(관리 화면 계정 권한과 이원화) · POP 로컬 버퍼링 + 자동 동기화(오프라인 내성).
6. 수불 원장이 재고의 정본(잔량은 파생, 상태 캐시 없음) · Lot Status 단일 판정 지점.

### 3.4 1차 범위에서 제외 확정된 것

SPC 관리도 분석(Xbar-R·Cp/Cpk — OMF-AI 페이즈 이연, 측정치 **수집·상하한 판정까지는 1차 포함**) · 설비 자동수집 Middleware 전면(표준 I/F 수신은 포함) · 설비 원격 제어(Safety) · 알람 다채널 에스컬레이션(SMS·스피커·경광등) · LOT 정/역추적 엔진 재개발(추적관리시스템 연계로 대체) · 보전 비용·자산·발주 · Early Warning/Analytics.

## 4. 병렬 개발 전략 — Agent coding 최적화 구조

### 4.1 병렬화의 3원칙

1. **계약 우선(Contract-first).** 물리 스키마 + 도메인별 API 계약(OpenAPI)을 W2에 확정하고 **목업 서버를 즉시 배포**한다. 이후 프론트 에이전트는 목업으로, 백엔드 에이전트는 계약 구현으로 서로를 기다리지 않는다 (전제 5-예1). 계약 변경은 통합 Agent를 거치는 명시적 이벤트로만 허용.
2. **소유권 분리.** 레인(작업 패키지)마다 소유 디렉터리/모듈을 배타적으로 할당해 머지 충돌을 구조적으로 차단한다. 도메인 간 결합 지점(01↔02 출고요청, 02↔03 PQC, 02↔05 작업 전 통제, 02→04 긴급 직행)은 직접 참조 금지 — 계약된 API/이벤트로만 통신.
3. **공통 기반 선행.** 여러 도메인이 소비하는 횡단 모듈(발번 엔진, 공통코드+다국어, 상태+이력 패턴, 사전발행 라벨 라이프사이클, 수불 원장, 인증/권한, 알림/공지)을 W2~W3에 라이브러리로 먼저 제공한다. 도메인 레인이 각자 구현하면 6벌 중복 + 정합 파탄이 된다.

### 4.3 통합 Agent 운영 (전제 5-예2)

- **통합 게이트 주 2회(수/금) [가설 — 운영하며 조정]**: 레인 브랜치 머지 → 계약-구현 정합 검사(스키마 diff·계약 테스트) → E2E 스모크(핵심 흐름: 입하→IQC→입고→출고→생산→PQC→제품입고→출하) → 도식스펙 대비 정합 점검.
- 통합 Agent의 소유물: 계약 저장소(OpenAPI·이벤트 스키마·DDL), 목업 서버, E2E 시나리오, 릴리스 브랜치. 계약 변경 승인권을 통합 Agent로 단일화해 레인 간 조율 비용을 없앤다.
- 사람 개입 지점: 통합 게이트 결과 리뷰, 계약 변경 승인, 주간 데모 [가설 — 팀 운영 방식에 따라 조정].
