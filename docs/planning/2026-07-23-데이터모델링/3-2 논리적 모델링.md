# MES 논리적 데이터 모델

> v3: ERPNext 벤치마킹 반영본(E-1~E-7). 변경 내역은 CHANGELOG.md 참조.
> v2: 요구사항 검토 반영본.

## 1. 논리 모델링 범위

본 논리 모델은 다음 업무 영역을 대상으로 한다.

1. 조직·창고·사용자 기준정보
2. 품목·BOM·라우팅
3. 생산오더·생산계획·작업지시
4. 작업 세션
5. 구매자재 입하·수입검사·입고
6. 재고·로케이션·취급단위
7. 생산출고·현장 인수·자재투입·반납
8. 생산실적·생산 LOT·공정 인계
9. 품질검사·불량·부적합·특채·재작업
10. LOT 계보 및 추적성
11. 사업부·공장·외주·외부창고 이동
12. 출하
13. 승인·예외·첨부·감사·ERP 연계
14. 사용자·부서·권한, 운영정책·채번규칙·발행이력

본 단계에서는 테이블 구조, 논리 식별자, 주요 속성, 관계와 무결성 규칙을 정의한다. 실제 DB 자료형, 인덱스 방식, 파티셔닝 등은 물리적 모델링에서 확정한다.

# 2. 논리 모델링 기본 원칙

## 2.1 식별자

모든 핵심 엔터티는 시스템 내부 식별자와 업무 식별자를 분리한다.

예:

```text
work_order_id       시스템 내부 PK
work_order_no       사용자가 확인하는 작업지시번호
```

* 내부 식별자: 변경 불가
* 업무번호: 업무규칙에 따라 생성
* 외부 시스템 번호: 별도 컬럼 또는 외부 식별번호 테이블로 관리

---

## 2.2 공통 컬럼

대부분의 업무 테이블은 다음 공통 속성을 가진다.

| 컬럼           | 의미         |
| ------------ | ---------- |
| `created_at` | 생성일시       |
| `created_by` | 생성 사용자     |
| `updated_at` | 최종 수정일시    |
| `updated_by` | 최종 수정 사용자  |
| `version_no` | 낙관적 잠금용 버전 |
| `is_active`  | 기준정보 사용 여부 |
| `remarks`    | 비고         |

업무이력 테이블은 가능한 한 수정하지 않고 신규 이벤트를 추가한다.

---

## 2.3 상태코드

상태값을 프로그램 문자열로 직접 관리하지 않고 코드 기준정보를 사용한다.

```text
code_group
 └─ code_value
```

예:

* 작업지시 상태
* 품질상태
* 재고상태
* 입하상태
* 출하상태
* 승인상태
* LOT 관계유형

---

## 2.4 원장과 현재값 분리

재고는 다음 두 구조를 분리한다.

```text
inventory_transaction
= 재고가 변한 원본 사건

inventory_balance
= 현재 시점의 재고 잔액
```

`inventory_balance`는 조회 성능을 위한 현재값이며, 원칙적으로 `inventory_transaction`을 통해서만 변경한다.

---

## 2.5 LOT와 재고 분리

LOT는 추적 식별자이고 재고는 특정 위치와 상태에 존재하는 수량이다.

```text
LOT M001
├─ 자재창고 A01 / 합격 / 가용: 300kg
├─ 자재창고 A02 / 합격 / 가용: 200kg
└─ 생산현장 / 합격 / 생산현장: 100kg
```

하나의 LOT에 여러 재고잔액이 존재할 수 있다.

# 3. 전체 논리 모델 구조

```text
조직·기준정보
 ├─ 부서·사용자·권한
 ├─ 생산라인·작업구역
 ├─ 품목·단위
 ├─ BOM
 ├─ 라우팅·공정
 ├─ 창고·로케이션
 └─ 작업자·설비·금형

생산계획
 └─ 작업지시
     ├─ 작업세션
     ├─ 자재투입
     ├─ 생산실적
     ├─ 검사대상
     └─ 생산 LOT

구매 P/O
 └─ 입하예정·입하
     └─ 수입검사
         └─ 입고·적치
             └─ 자재 LOT·재고

재고
 ├─ 예약
 ├─ 피킹
 ├─ 출고
 ├─ 이동
 ├─ 반납
 ├─ 생산품 입고
 ├─ 외주
 └─ 출하

LOT
 ├─ 자재투입
 ├─ 생산실적
 ├─ LOT 관계
 ├─ 품질검사
 ├─ 포장
 └─ 출하
```

## 17.2 LOT 관계 생성 원칙

LOT 관계는 다음 원본 이벤트에서 생성한다. 관계유형은 최소 12종을 지원한다.

| 원본 이벤트    | 관계 유형                                                  |
| --------- | ------------------------------------------------------ |
| 자재투입      | 투입됨 `CONSUMED_INTO`                                     |
| 생산실적      | 생산됨 `PRODUCED_FROM`                                     |
| 공정 인계     | 공정 인계됨 `TRANSFERRED_TO`                                 |
| LOT 분할    | 분할됨 `SPLIT_FROM`                                        |
| LOT 병합    | 병합됨 `MERGED_INTO`                                       |
| 재작업       | 재작업됨 `REWORKED_FROM`                                    |
| 포장        | 포장됨 `PACKED_INTO`                                       |
| 출하 LOT 구성 | 출하구성됨 `SHIPPED_AS`                                      |
| 라벨 재부여    | 라벨 재부여됨 `RELABELED_AS`                                  |
| 잔량 분리     | 잔량 분리됨 `REMAINDER_FROM`                                 |
| 외주 출고     | 외주 출고됨 `SENT_TO_SUBCONTRACTOR`                          |
| 외주 입고     | 외주 입고됨 `RETURNED_FROM_SUBCONTRACTOR`                    |

사용자가 근거 이벤트 없이 임의로 관계를 생성하는 것은 제한한다.

# 25. 핵심 무결성 규칙

## 25.1 작업지시

```text
한 작업지시는 하나의 routing_operation만 참조한다.
MES 미관리 routing_operation에는 일반 작업지시를 생성하지 않는다.
마감된 작업지시는 일반 사용자가 변경할 수 없다.
분할 자식 작업지시의 지시수량 합계는 원본 지시수량을 초과할 수 없다.
재작업 지시만 rework_source_*를 가질 수 있다.
```

---

## 25.2 자재투입

```text
material_consumption.input_qty > 0
material_consumption.lot.item_id = material_consumption.item_id
실제 투입량은 생산현장 가용수량을 초과할 수 없다.
필수 LOT 자재는 lot_id 없이 투입할 수 없다.
```

---

## 25.3 생산실적

```text
good_qty, defect_qty, hold_qty, scrap_qty, rework_qty >= 0
생산실적은 하나의 work_order에 속한다.
후속 공정 실적은 선행 공정 가용수량을 초과할 수 없다.
```

---

## 25.4 생산 LOT

```text
생산실적 LOT 배분수량 합계는 양품수량을 초과할 수 없다.
생산 LOT 최초수량은 연결된 유효 생산실적 배분수량과 일치해야 한다.
```

---

## 25.5 품질

```text
accepted_qty + rejected_qty + held_qty = inspected_qty
필수 검사항목 미입력 시 검사결과 확정 불가
불합격·보류재고는 일반 출고·투입·출하 불가
```

---

## 25.6 재고

```text
가용수량 = 현재수량 - 예약수량 - 피킹수량 - 사용제한수량
가용수량 이상 예약 불가
가용수량 이상 출고 불가
모든 재고변경은 inventory_transaction을 가져야 한다.
원장(inventory_transaction)은 수정·삭제하지 않고 역트랜잭션으로 정정한다.
음수재고는 품목 정책이 허용하는 경우에만 발생할 수 있다.
```

---

## 25.7 LOT 계보

```text
source_lot_id와 target_lot_id는 같을 수 없다.
LOT 관계는 순환할 수 없다.
분할된 LOT 수량 합계는 원본 분할수량과 일치해야 한다.
```

# 28. 정규화 검토

## 28.1 제1정규형

반복 컬럼을 사용하지 않는다.

잘못된 예:

```text
material_lot_1
material_lot_2
material_lot_3
```

적절한 구조:

```text
material_consumption
```

---

## 28.2 제2정규형

Line 테이블의 속성은 전체 키에 종속되도록 한다.

예:

* 입하 Header: 공급사, 차량, 입하일시
* 입하 Line: 품목, LOT, 수량

---

## 28.3 제3정규형

품목명·공급사명·창고명 등을 업무 트랜잭션마다 중복 저장하지 않는다.

다만 감사·증빙을 위해 당시 값을 보존해야 하는 경우 스냅샷 컬럼 또는 문서 출력 스냅샷을 별도로 둘 수 있다.

---

# 29. 다형 참조 사용 주의

다음 공통 테이블은 여러 업무대상을 참조한다.

* `approval_request`
* `attachment`
* `audit_event`
* `exception_case`
* `integration_message`
* `inspection_request`
* `document_issue_log`

논리적으로는 다음 구조를 가진다.

```text
target_type_code
target_id
```

장점:

* 공통 기능 구현이 단순하다.

단점:

* 일반 FK 제약조건을 직접 적용하기 어렵다.

물리 모델링 시 다음 중 하나를 선택한다.

1. 다형 참조 유지 및 애플리케이션 검증
2. 업무 영역별 연결 테이블 추가
3. 공통 `business_object` 식별자 체계 도입

핵심 품질·재고·생산 관계에는 다형 참조를 최소화하고 명시적 FK를 사용하는 것이 적절하다.

# 32. 논리 모델 최종 구조

```text
구매 P/O
→ 입하예정
→ 입하
→ 수입검사
→ 입고
→ 적치
→ 자재 LOT
→ 재고잔액
→ 생산출고 요청
→ 예약·피킹
→ 생산출고
→ 현장 인수
→ 자재투입
→ 생산실적
→ 생산 LOT
→ 공정 인계
→ 품질검사
→ 생산품 입고
→ 창고·사업부·외주 이동
→ 출하요청
→ 피킹·출하검사
→ 출하
→ 고객
```

LOT 추적 핵심 연결은 다음과 같다.

```text
공급사 LOT
→ 내부 자재 LOT
→ material_consumption
→ material_usage_allocation
→ production_result
→ production_result_lot_allocation
→ 생산 LOT
→ shipment_lot_allocation
→ 고객 출하
```

재고 핵심 연결은 다음과 같다.

```text
업무문서
→ inventory_transaction
→ inventory_transaction_line
→ inventory_balance
```

이 논리 모델을 기반으로 물리적 모델링에서는 PostgreSQL 기준 자료형, PK 생성방식, FK, 인덱스, 파티셔닝, 이력보관, 동시성 잠금 및 DDL을 구체화한다.
