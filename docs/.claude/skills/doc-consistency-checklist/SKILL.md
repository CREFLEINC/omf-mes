# 문서 정합성 검증·작성 공통 지식 베이스

omf-mes 기획 문서는 **깊게 상호 참조되는 지식 그래프**다. 한 결정이 여러 문서로 파급되고(예: "생산불량LOT 신설" → 개념데이터모델 + WF02 + 확정기록), 손으로 맞추면 놓치기 쉽다(실제로 생산LOT.불량수 필드 충돌이 정의를 직접 읽어야만 잡혔다). 이 문서는 그 파급을 놓치지 않고 정본에 정확히 쓰기 위한 방법을 담는다.

## 1. 문서 지형도 — 정본과 파급 방향

| 계층 | 문서 | 무엇의 정본인가 |
| --- | --- | --- |
| **의미 코어** | `research/2026-07-03-개념데이터모델-v2-요구사항통합.md` | 엔티티·필드·관계·카디널리티. 모든 데이터 구조 결정의 정본 |
| **워크플로우 정본** | `research/*-워크플로우-요구사항반영-0N-*.md` | 단계별(S1~S12) Trigger/Action/Rule/Exception. 프로세스·규칙 결정의 정본 |
| **도식 스펙** | `research/*-도식스펙-0N-*.md` | FigJam 도식의 소급 전사 + 미정의 마커·집계. 표기·시각 결정의 정본 (캔버스 자체는 figjam 하네스 소관) |
| **확정 근거** | `research/*-현장검증-QA-확정기록.md` · `*-설계결정서-*.md` · 날짜별 `*-확정기록.md` | 결정의 원천(회의록·문답). **원문 보존 — 새 결정이 덮어써도 안 고치고 상호 참조만** |

**파급 방향 (결정 성격 → 정본 → 하류):**
- 엔티티·필드·관계 변경 → **개념데이터모델**(정본) → 이를 참조하는 WF0N·도식스펙0N
- 프로세스·규칙 변경 → **WF0N**(정본) → 개념데이터모델(관련 엔티티 속성)·도식스펙0N
- 표기·시각 변경 → **도식스펙0N**(+ 캔버스는 figjam 하네스)
- 신규 결정 → 날짜별 **확정기록 신설** → 위 정본들이 이를 인용해 갱신

> 지형도는 스냅샷이다 — 문서가 늘면 각 문서 머리의 `근거 자료` 헤더로 상류를, repo 전역 grep으로 하류를 실측해 갱신한다.

## 2. 마커 범례

| 마커 | 뜻 |
| --- | --- |
| `✅ REQ-XX-nnnn` | 요구사항 명세서 근거 — `(현행)`=As-Is · `(요구)`=To-Be |
| `✓확정 YYYY-MM-DD QA #n` | CTO 문답 확정 |
| `✓설계확정 YYYY-MM-DD 결정 nn` | 내부 설계 결정서 확정 |
| `(기존 서술 폐기: …)` | 뒤집힌 서술의 흔적 — **필수. 되돌아가지 않게 남긴다** |
| `[가설]` | 내부 가설 — 검증 방법 병기 |
| `[확인필요]` · `(확인 필요)` | 미결 |
| `🟡`/`🟠`/`⚠` | Medium 가설 / Exception / 핵심 미결 |

## 3. 정합성 검증 5단계 (검증 담당자 핵심)

1. **정본 식별**: 결정 성격(엔티티/규칙/표기)으로 어느 문서가 정본인지 판단(§1 표). 데이터 구조면 개념데이터모델부터, 프로세스면 WF0N부터.
2. **상류 추적(근거)**: 대상 문서의 `근거 자료` 헤더 + 영향 라인의 마커를 읽는다. 신규 내용이 기존 `✓확정`과 모순되는가? **기존 확정을 뒤집으면 반드시 `(기존 서술 폐기: …)` 대상**임을 표면화한다 — 사용자가 되돌리는 줄 모르고 확정하면 사고다.
3. **하류 추적(파급)**: 영향 대상(엔티티명·필드·규칙·노드 ID)을 **repo 전역 grep**한다. 참조하는 모든 문서가 파급 대상이다. 하나라도 빠지면 문서 간 모순이 남는다.
4. **충돌 판정**: 각 파급 대상에서 신규 내용이 기존 서술과 모순되는지 `file:line`으로 명시한다. 정의를 요약이 아니라 원문으로 읽어야 잡힌다.
5. **추가 질문 표면화**: 결정이 남기는 하위 미결을 작성 **전에** 나열한다. 예: "생산불량LOT 신설 → 발번 트리거? 생산LOT과 관계? Lot Status 적용?" 이걸 미리 묻지 않으면 작성 도중 발견돼 되돌리게 된다.

## 4. 확정기록 패턴

- 신규 결정은 `research/YYYY-MM-DD-{주제}-확정기록.md`로 신설한다 — 구성: 배경(무엇이 충돌/미결이었나) · 확정 결정 사항 · 신규/변경 엔티티·규칙 · 파급 반영 대상 표 · 잔여 열린 지점.
- 이 확정기록이 정본이 되고, §1의 정본 문서들이 이를 **인용**(경로 병기)해 갱신된다.
- 회의록(QA 확정기록·설계결정서)은 **원문 보존**. 새 결정이 그 함의를 대체하면 상호 참조만 남기고 원문은 고치지 않는다.

## 5. 버전·변경 이력 규칙 (작성 담당자 준수)

- 문서 머리 blockquote의 **버전·날짜 표기 갱신** (v0.x 초안 / v1.0 최초 확정 / 변경 폭 따라 증가). 헤더 버전과 변경 이력 표의 최신 버전은 **반드시 일치**시킨다.
- 문서 끝 **변경 이력 표에 행 추가** (버전·날짜·변경 요지 — 근거 확정기록 경로 병기).
- **집계 수치 재계수**: 엔티티 총계·"메인 N개"·마커 수 등 숫자가 있으면 함께 갱신. 놓치면 본문과 집계가 어긋난다.
- 날짜는 `YYYY-MM-DD`. 문서 간 링크는 저장소 루트 기준 상대 경로.

## 6. 작성 지시서 포맷 (검증 → 작성 인계 정본)

검증 담당자가 CLEAR 판정 시 작성 담당자에게 넘기는 산출물. 작성 담당자는 이것을 **글자 그대로** 실행한다.

각 편집 항목:
- **대상 파일** (경로)
- **앵커**: 교체 대상 `old_string`을 원문 그대로 정확 인용 (유일하게 매칭되도록 충분히 길게)
- **신규 텍스트**: 넣을 `new_string` 전문
- **사용 마커**: 어느 날짜·출처의 `✓확정`/`(기존 서술 폐기)`를 붙일지
- **성격**: 신규 추가 / 서술 교체 / 폐기 표기

+ 문서별 **버전 bump** 지정 · **변경 이력 행** 문구 · **집계 재계수** 지점 · **파급 대상 전체 목록**(이 결정이 건드리는 모든 파일).

## 7. 절대 규칙

- **raw/ 는 읽기만 한다** — 생성·수정·삭제 금지(훅이 차단). 발췌·정리 결과물은 research/에 새로 쓴다.
- **planning/versions/ 스냅샷은 수정 금지**(훅이 차단). 확정은 `/snapshot`으로.
- 근거 없는 사실·수치는 쓰지 않는다 — `[가설]` 또는 `(확인 필요)`를 붙이거나, 확정기록에 근거를 먼저 만든다.
