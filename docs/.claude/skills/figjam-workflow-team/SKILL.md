# figjam-workflow-team — 도식 제작 팀 오케스트레이터

**실행 모드: 에이전트 팀** (설계자·작업자·검토자 3인 + 리더=본 세션). 검토자→작업자 결함 피드백 루프가 핵심이므로 팀 통신(SendMessage)을 쓴다.

**공통 지식 베이스**: `.claude/skills/figjam-workflow-diagram/SKILL.md` — 도식 문법·클론 킷·좌표 배치·함정·진행 상태 표. 리더와 세 에이전트 모두 이것을 1차 참조한다. fileKey `Sgy5IKD4aWuzpKtJAbMyWz`.

## Phase 0: 컨텍스트 확인 (실행 모드 판별)

1. **프리플라이트**: Figma 도구 로드(ToolSearch 1회 배치) → `get_figjam(nodeId:'0:1')`로 연결 확인. 실패 시 즉시 중단하고 사용자에게 알린다(데스크톱 앱·플러그인 연결은 사용자만 복구 가능).
2. **작업 페이지 확인**: 페이지가 여럿이면(v1/v2 등) 어느 페이지가 대상인지 확정한다. 애매하면 사용자에게 묻는다.
3. **기존 산출물 확인**: `_workspace/figjam-team/` 존재 여부.
   - 존재 + 부분 수정 요청 → **부분 재실행**: 해당 단계 에이전트만 재기동(예: 검토 결함 수정이면 drawer+reviewer만)
   - 존재 + 새 대상 → **새 실행**: 기존 run 폴더는 보존, 새 `{run}` 폴더 생성 (run = `{날짜}-{대상}`)
   - 미존재 → **초기 실행**
4. 대상 도메인의 스펙 문서 존재 여부 확인 — 없으면 설계자가 워크플로우 md에서 직접 추출해야 함을 지시서 요건에 반영.
5. **경로 선택** — 아래 표로 표준/경량을 판별한다.

## 경로 선택

| 조건 | 경로 |
| --- | --- |
| 변경 규모 = 노드·커넥터·라벨 합 **≤5** + 신규 섹션·밴드 없음 + 스펙 해석 판단 불요(수정 내용이 이미 확정·승인됨) | **경량 경로** (아래) |
| 그 외 — 신규 작화, 밴드 재작업, 메인/사이드 분할 판단, 스펙 해석 필요 | 표준 경로 (Phase 1~4) |

애매하면 표준 경로를 택한다 — 경량은 속도를 위해 설계 단계를 생략하므로, 스펙 해석이 끼는 순간 리더 창작 위험이 생긴다.

## 경량 경로 (소규모 수정: 리더 직접 + 검토자 1회)

> 도입 근거: 2026-07-13 파일럿 — 소규모 재배선(요소 6개)에 에이전트 3왕복(회당 ~10분)은 과잉. 단 검토자의 좌표 기반 겹침·정합 검증은 실효가 입증되어(관통 결함 2건 적발) 생략하지 않는다.

1. **미니 지시서**: 리더가 `_workspace/figjam-team/{run}/00_leader_minibrief_{대상}.md`를 쓴다 — ① 변경 목록(노드 ID·조치) ② 수정 후 기대 상태(검토자의 전수 대조 기준) ③ 근거 1줄. 이 파일이 없으면 검토자가 판정 기준을 잃는다.
2. **리더 직접 수정**: figma:figma-use·figma-use-figjam 로드 + 공통 지식 베이스 규칙(clone-not-draw·증분 빌드·선여백 금지) 그대로 적용, 자가 스크린샷 확인.
3. **검토자 1회**: workflow-reviewer 서브에이전트(`model: "opus"`, 포그라운드) — 미니 지시서 기준 3항목 검증, 보고는 표준과 동일(`03_review_*_r1.md`).
4. **FAIL 처리**: 리더가 결함만 수정 → 재검증(r2) 1회. **r2도 FAIL이면 규모 오판** — 표준 경로로 전환(designer부터).
5. **종료**: Phase 4와 동일(문서 정합·스크린샷 사용자 보고).

경량 경로에서도 불변인 것: 캔버스 단일 작화, 산출물은 파일이 정본, 검토의 독립성(리더가 수정자여도 판정은 검토자가 한다).

## Phase 1: 팀 생성·작업 할당

- TeamCreate로 3인 팀 구성(전원 `model: "opus"`). TaskCreate로 의존 관계를 건다:
  `T1 설계(designer)` ← `T2 메인 작화(drawer)` ← `T3 메인 검토(reviewer)` ← `T4 사이드 작화(drawer)` ← `T5 사이드 검토(reviewer)` ← `T6 문서 정합(리더)`
- 각 태스크에 입력 파일 경로와 산출 파일 경로를 명시한다(아래 데이터 흐름).

## Phase 2: 설계

- designer가 스펙을 읽고 지시서(`01_designer_brief_{대상}.md`)를 작성. 메인/사이드 분할이 애매하면 리더 경유로 사용자 확인.
- **리더 게이트**: 지시서를 직접 읽고 ① 사이드 코드 충돌 없음 ② 근거 표(§9) 채워짐 ③ 좌표·클론 소스 구체값 존재를 확인한 뒤 T2를 연다. 에이전트 완료 보고만 믿지 않는다.

## Phase 3: 작화 → 검토 루프 (섹션 단위 증분)

- **단일 작화 원칙**: 캔버스 쓰기는 한 번에 한 에이전트만. drawer가 메인을 완료(T2)하면 reviewer가 검토(T3), PASS 후에만 사이드(T4) 착수.
- 검토 FAIL → reviewer가 결함 목록을 drawer에 직접 전달(SendMessage) → drawer 정밀 수정 → 재검토. **최대 3회차**; 3회차에도 C 결함이 남으면 리더가 개입해 직접 수정하거나 사용자에게 보고.
- 설계 결함으로 판정된 항목은 designer에게 이관 → 지시서 개정(r+1) → 해당 부분만 재작화.
- **리더 직접 검증**: 각 PASS 후 리더가 get_figjam 노드 수·섹션 bounds를 표본 확인한다(에이전트 최종 메시지 잘림 대비 — 파일 보고가 정본).

## Phase 4: 종료·문서 정합 (리더 전담)

- 도식이 스펙과 달라졌으면 스펙 md(§1~§4)·QA 확정기록 §4(신규 미정의·[가설] 등재)·figjam-workflow-diagram 스킬의 진행 상태 표를 갱신한다. **repo 문서 갱신은 항상 리더 몫**(팀원은 캔버스만).
- 최종 스크린샷을 사용자에게 전달, 팀 정리(TeamDelete). `_workspace/` 중간 산출물은 보존(감사 추적).

## 데이터 흐름 (파일 기반 정본 + 메시지 보조)

```
_workspace/figjam-team/{run}/
├── 01_designer_brief_{대상}.md      designer → drawer·reviewer 입력
├── 02_drawer_report_{대상}.md       drawer → reviewer 입력 (노드 ID 맵)
└── 03_review_{대상}_r{n}.md         reviewer → drawer 피드백 / 리더 판정 근거
```

메시지(SendMessage)는 조율·질의용, 태스크는 진행 추적용, **산출물은 반드시 파일** — 최종 메시지 잘림이 있어도 파일이 남는다.

## 에러 핸들링

| 상황 | 처리 |
| --- | --- |
| Figma 연결 부재/도구 실패 반복 | 즉시 중단, 사용자에게 연결 복구 요청 (재시도 무의미) |
| use_figma 스크립트 에러 | 원자적 실패 — 원인 수정 후 1회 재시도, 재실패 시 리더 보고 |
| 팀원 응답 없음/통신 실패 | 리더가 해당 단계를 포그라운드 서브 에이전트(Agent 도구, `model:"opus"`)로 폴백 — 같은 에이전트 정의·같은 파일 프로토콜 사용 |
| 검토 3회차 C 결함 잔존 | 리더 직접 수정 또는 사용자 에스컬레이션 |
| 좌표 충돌(기존 섹션 겹침) | 섹션 bounds 재조회 후 designer가 좌표 재산정 |

## 테스트 시나리오

1. **정상 흐름**: "02 생산실행 사이드 D를 새 규약으로 재작화해줘" → Phase 0(연결·페이지 확인) → 설계(분할 판단·지시서) → 작화 → 검토 PASS → 문서 정합 → 스크린샷 보고.
2. **에러 흐름(검토 FAIL 루프)**: 작화 결과에 스티키-노드 겹침 + 조건 라벨 누락 → reviewer FAIL r1(결함 2건, 노드 ID 포함) → drawer 정밀 수정 → r2 PASS → 진행. 같은 결함 r2 잔존 시 리더 에스컬레이션 확인.
3. **에러 흐름(연결 부재)**: get_figjam 실패 → 팀 생성 없이 즉시 중단·사용자 알림.
