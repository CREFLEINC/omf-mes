ERPNext(frappe/erpnext) manufacturing·stock·subcontracting 모듈과 대조 검토 후
선별 채택한 7개 항목입니다.

| # | 항목 | 변경 |
| --- | --- | --- |
| E-1 | 적치 규칙 마스터 | 신규 `logistics.putaway_rule`(품목×창고×위치, 수용량·우선순위) + `putaway_task.applied_putaway_rule_id` 역참조 |
| E-2 | 반제품 계획 계층 연결 | `production_order.parent_production_order_id`(자기참조) + `bom_level` |
| E-3 | 작업지시 기본 로케이션 | `work_order.default_wip/fg/scrap_location_id` (기본값 제시·오입고 검증용) |
| E-4 | 운영정책 코드 시드 | `OPERATION_POLICY` 코드그룹 + 14종 시드 (ERPNext manufacturing_settings 대응 10 + 자체 4) |
| E-5 | 원장 잔액 스냅샷 | `inventory_transaction_line.from/to_qty_after_transaction` — 시점 조회·감사 대사 O(1)화 |

PostgreSQL 스키마는 테이블·함수·타입 등의 이름공간과 권한 경계를 구분할 수 있으므로 업무 영역 분리에 적합합니다. ([PostgreSQL][1])

### 식별자와 자료형

```text
PK            bigint generated always as identity
업무번호       varchar(100) + UNIQUE
수량           numeric(20,6)
비율           numeric(18,8)
실제 시각      timestamptz
업무일자       date
상세 변경값    jsonb
낙관적 잠금    version_no
```

금액·수량 계산에서 부동소수점 오차가 발생하지 않도록 생산·재고수량은 `numeric`으로 정의했습니다.

### 재고 원장과 현재 잔액 분리

```text
inventory_transaction
inventory_transaction_line
        ↓
inventory_balance
```

* `inventory_transaction`: 변경 불가능한 재고 원장
* `inventory_balance`: 현재 재고 조회 및 동시성 잠금 대상
* 모든 입고·출고·이동·투입·반납·출하는 재고 원장을 생성
* 재고조정도 기존 이력을 수정하지 않고 별도 조정 트랜잭션으로 처리

`inventory_balance.available_qty`는 다음 생성 컬럼으로 구성했습니다.

```sql
on_hand_qty
- reserved_qty
- picked_qty
- blocked_qty
```

PostgreSQL 생성 컬럼은 다른 컬럼에서 계산되는 값을 DB가 일관되게 유지하는 기능입니다. ([PostgreSQL][2])

### LOT와 재고 분리

```text
trace.lot
    1
    │
    N
inventory.inventory_balance
```

하나의 LOT가 다음처럼 여러 위치와 상태로 분리될 수 있습니다.

```text
LOT M001
├─ 자재창고 A01 / 합격 / 가용 300kg
├─ 자재창고 A02 / 합격 / 가용 200kg
├─ 생산현장 / 합격 / 현장재고 100kg
└─ 보류창고 / 보류 / 격리 20kg
```

```text
material_issue_request
→ picking_order
→ goods_issue
→ shopfloor_receipt
```

따라서 다음 수량이 구분됩니다.

### 생산실적과 생산 LOT 분리

```text

        N
        │
```

다음 두 경우를 모두 지원합니다.

* 여러 부분 생산실적을 하나의 생산 LOT에 누적
* 하나의 생산실적을 여러 박스·생산 LOT로 분할

```text
material_consumption
→ material_usage_allocation
→ production_result
→ production_result_lot_allocation
→ lot
```

LOT 계보는 `trace.lot_relation`에서 자기참조 다대다 관계로 관리합니다.

```text
source_lot_id
target_lot_id
relation_type_code
relation_qty
source_event_type_code
source_event_id
allocation_method_code
trace_accuracy_code
```

관계유형은 다음을 수용할 수 있습니다 (2-5 FR-LT-053의 12유형 기준으로 시드 통일).

```text
CONSUMED_INTO
PRODUCED_FROM
SPLIT_FROM
MERGED_INTO

PACKED_INTO
SUBCONTRACTED_INTO
SHIPPED_AS
```

`lot.parent_lot_id`는 표시용 비정규화이며 계보의 원천은 `lot_relation`입니다.
동일 이벤트 기준 중복 관계는 UNIQUE 제약으로 차단합니다.

### 대용량 데이터 파티셔닝

초기 DDL에서 다음 원장성 테이블을 범위 파티셔닝했습니다.

```text
inventory.inventory_transaction
    PARTITION BY RANGE (business_date)

audit.audit_event
    PARTITION BY RANGE (occurred_at)
```

PostgreSQL 선언적 파티셔닝은 Range·List·Hash 방식을 지원하며, 시간순으로 누적되는 원장과 감사이력에는 날짜 기준 Range 파티셔닝이 적합합니다. ([PostgreSQL][3])

현재는 누락 방지를 위해 기본 파티션을 포함했고, 운영 시에는 월별 파티션을 사전에 생성해야 합니다.

### 상태별 부분 인덱스

전체 이력보다 현재 처리대기 건을 자주 조회하는 테이블에는 부분 인덱스를 적용했습니다.

예:

```sql
CREATE INDEX ix_work_order_dispatch
ON production.work_order (
    status_code,
    planned_start_at,
    priority_no
)
WHERE status_code IN (
    'RELEASED',
    'WAITING',
    'IN_PROGRESS',
    'PAUSED',
    'ON_HOLD'
);
```

적용 대상:

* 실행 가능한 작업지시
* 진행 중 작업 세션
* 미완료 피킹
* 검사 대기 건
* 미종결 부적합
* 미처리 예외
* ERP 재전송 대상
* 미완료 적치작업 (v2)
* 해제되지 않은 LOT 보류 (v2)
* 분할·재작업·라인 배정 작업지시 (v2)

부분 인덱스는 조건에 맞는 일부 행만 인덱싱하는 PostgreSQL 기능입니다. ([PostgreSQL][4])

### 동시성 제어

재고 처리 흐름은 다음을 전제로 설계했습니다.

```text
1. idempotency_key 중복 확인
2. inventory_balance SELECT ... FOR UPDATE
3. 가용수량 재검증
4. 재고원장 Header·Line 생성
5. inventory_balance 변경
6. 업무문서 상태 변경
7. 감사이력 생성
8. ERP Outbox 생성
9. Commit
```

문서 변경은 `version_no`를 이용한 낙관적 잠금 방식으로 처리할 수 있습니다.

### 사업부·공장별 데이터 접근

DDL 하단에 RLS 적용 예시를 포함했습니다.

```sql
SET LOCAL app.business_unit_id = '10';
```

```sql
CREATE POLICY inventory_balance_bu_policy
ON inventory.inventory_balance
USING (
    business_unit_id
    = current_setting('app.business_unit_id', true)::bigint
);
```

PostgreSQL Row-Level Security는 사용자 또는 세션 조건에 따라 조회·수정 가능한 행을 제한할 수 있습니다. ([PostgreSQL][5])

## 2. PostgreSQL 제약조건으로 구현할 로직

|     번호 | 무결성 규칙                    | 권장 구현                                     |
| -----: | ------------------------- | ----------------------------------------- |
| DB-C01 | PK 중복 방지                  | `PRIMARY KEY`                             |
| DB-C02 | 업무번호 중복 방지                | `UNIQUE`                                  |
| DB-C03 | 참조 대상 존재 보장               | `FOREIGN KEY`                             |
| DB-C04 | 음수 수량 방지                  | `CHECK (qty >= 0)` — 단, `inventory_balance.on_hand_qty`는 signed 도메인 + 트리거로 품목 정책(`negative_stock_allowed`)에 따라 조건부 허용 (v2) |
| DB-C05 | 종료일이 시작일보다 빠르지 않음         | `CHECK`                                   |
| DB-C06 | 자기 LOT 관계 방지              | `CHECK (source_lot_id <> target_lot_id)`  |
| DB-C07 | 자기 공정·작업지시 의존관계 방지        | `CHECK`                                   |
| DB-C08 | 검사 판정수량 합계 일치             | `CHECK`                                   |
| DB-C09 | 피킹수량이 계획수량을 초과하지 않음       | `CHECK`                                   |
| DB-C10 | 인수수량이 출고수량을 초과하지 않음       | `CHECK`                                   |
| DB-C11 | 예약 해제·소비합계가 예약수량을 초과하지 않음 | `CHECK`                                   |
| DB-C12 | 가용재고 계산                   | Generated Column                          |
| DB-C13 | 동일 요청 중복 Posting 방지       | `UNIQUE(idempotency_key)`                 |
| DB-C14 | 동일 문서 Line 중복 방지          | 복합 `UNIQUE`                               |
| DB-C15 | 동일 재고 차원 중복행 방지           | 복합 Unique Index                           |
| DB-C16 | 필수 LOT 품목의 LOT 누락 방지      | 서비스 검증 + DB Trigger/제약 보조                 |
| DB-C17 | LOT 계보 순환 방지              | **구현 완료(v2)**: `trace.check_lot_relation_cycle()` — Recursive CTE 트리거 |
| DB-C18 | 생산실적 LOT 배분 초과 방지         | **구현 완료(v2)**: `production.check_result_lot_allocation()` — Deferred Constraint Trigger |
| DB-C19 | 자재사용 배분 초과 방지             | **구현 완료(v2)**: `production.check_material_usage_allocation()` — Deferred Constraint Trigger |
| DB-C20 | 역트랜잭션 원본 참조 보존            | **구현 완료(v2)**: `reversal_of_business_date` 추가로 복합 self FK 성립 + 쌍 CHECK |

일반적인 상태전이나 고객별 정책을 `CHECK` 제약에 과도하게 넣지는 않는 것이 좋습니다.

Posting 함수 내부 공통 처리 순서는 다음과 같이 통일하는 것이 좋습니다.

```text
멱등성 검증
→ 대상 재고행 정렬
→ SELECT FOR UPDATE
→ 최신 상태·수량 검증
→ 업무원장 생성 (잔액 스냅샷 기록 포함)
→ 재고잔액 변경
→ 문서 상태 변경
→ 감사이력·Outbox 생성
→ Commit
```

원장 Line의 `from/to_qty_after_transaction`(E-5)은 Posting 함수(DB-P 계열)가
재고잔액 변경과 **같은 트랜잭션에서** 기록할 책임을 진다. 이 스냅샷으로 시점 기준
재고 조회와 감사 대사를 원장 재합산 없이 수행한다.


## 7. 애플리케이션과 DB 양쪽에서 중복 검증할 항목

| 검증         | 애플리케이션         | DB                     |
| ---------- | -------------- | ---------------------- |
| 가용수량       | 사용자 입력 전 사전 확인 | Posting 시 행 잠금 후 최종 확인 |
| 품질상태       | 화면·피킹 시 확인     | 출고·투입·출하 확정 시 재확인      |
| LOT 순환     | 관계 생성 전 경로 표시  | Commit 시 최종 차단         |
| LOT 배분합계   | 잔여 배분량 표시      | 초과 Commit 차단           |
| 자재사용 배분합계  | 배분 계산·표시       | 실제 소비량 초과 차단           |
| 유효기간       | 후보 LOT 추천 시 확인 | 출하·투입 Posting 시 재확인    |
| 고객 지정 LOT  | 할당 시 안내        | 출하 확정 시 재확인            |
| 특채조건       | 승인과 대상 선택      | 사용·출하 시 유효조건 확인        |
| 중복요청       | 버튼 비활성화        | 멱등성 Unique 제약          |
| 후속 공정 가용수량 | 인계 가능량 표시      | 인계 Posting 시 잠금 후 재검증  |

중복 구현은 낭비가 아니라 목적이 다릅니다.

```text
애플리케이션 검증 = 빠른 안내와 좋은 사용자 경험
DB 검증 = 동시성 상황에서도 최종 무결성 보장
```

## 9. 명시적 범위 이연 (v2)

다음 항목은 요구사항 문서에서 우선순위가 낮게 분류되었거나 차기 확장으로
정의된 것으로, **누락이 아니라 의도적 이연**입니다.

| 항목 | 근거 | 비고 |
| --- | --- | --- |
| 대규모 리콜 사건관리 (회수수량·고객통지 추적) | 2-6 §11 P2 | 분석 스냅샷까지는 `trace.impact_analysis`로 커버 |
| 설비 가동/비가동 이력·OEE | 1-2 차기 확장 분류 | 작업 세션 기반 중지·재개는 `work_session_event`로 커버 |
| 도크 스케줄, 팔레트 개체 추적, 3PL API 연동 | 2-7 §9 P2 | 입하장 위치(`dock_location_id`)·취급단위까지는 v2 반영 |
| 정식 CAPA | 2-6 §7.4 2차 범위 | 최소 조치사항은 `nonconformance` 컬럼으로 반영 |
| 원가·평가 (재고 평가액, 가공비, 원가 배부) | MES-ERP 역할 분담 | **원가·평가는 ERP 소관** — MES 원장은 원가 계산의 원천(수량×시점×LOT)만 제공 (v3) |

또한 `serial_number`/`serial_component_relation`은 요구 근거가 명시적으로
확인되지 않았으나 `item.serial_control_type_code` 체계와 정합하므로 유지하며,
1차 구축 범위 포함 여부는 확인이 필요합니다.
