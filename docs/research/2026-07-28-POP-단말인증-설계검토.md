## §1. 배경 — 왜 지금 정리하는가

현행 API는 `@Public()`이 붙지 않은 **모든** 엔드포인트가 JWT를 요구한다(화이트리스트 가드, `src/auth/auth.guard.ts`). 지금까지 만든 것이 기준정보 CRUD뿐이라 문제가 되지 않았다 — 기준정보는 **관리 Desktop 소관**이고 계정 로그인이 전제이기 때문이다(결정 16 단말표: "마스터 CRUD·대시보드. **계정 로그인**. 온라인 전제").

문제는 **아직 만들지 않은 POP API**다. 같은 방식을 그대로 적용하면 현장 작업자에게 로그인을 시키게 되어 요구사항을 정면으로 위반한다.

> **REQ-PR-0023** — "생산 현장 단말기에서 작업자의 로그인 기능은 **작업성을 많이 떨어뜨리기 때문에 생략 필요**. 작업 시작 전에 **사번만 입력**"

따라서 POP은 "인증을 없앤다"가 아니라 **"인증 주체를 사람에서 단말로 옮긴다"**로 풀어야 한다. 본 문서는 그 설계를 정리한다.

## §2. 이미 확정된 것 (본 문서가 바꾸지 않는다)

### 2.1 인증·권한 이원화 원칙

WF02 S5 Boundary에 명문화된 확정 원칙이다:

> **인증·권한 이원화**: POP=사번 입력 경량 인증(실적 귀속용, **도용 리스크 수용**) / 권한 통제=**관리 화면**(메뉴·데이터) 중심 — REQ-PR-0023·REQ-PR-0015 병립 설계 원칙

| 폼팩터 | 인증 | 확정 근거 |
| --- | --- | --- |
| 관리 Desktop (React 웹, 사무 PC) | **계정 로그인**(JWT) | ✓설계확정 2026-07-09 결정 16 단말표 |
| POP (Electron 설치형, 산업용 패널 PC) | **사번 입력, 로그인 생략** | ✅ REQ-PR-0023 |
| 모바일 (Capacitor) | *미정* — §6-③ | (점검 입력=모바일은 ✓확정 2026-07-24 배지단말 #5) |

또한 하드웨어 스펙이 **"단말에 별도 인증 하드웨어 불요"**(✅ REQ-PR-0023)로 확정돼 있다 — NFC 리더·지문 등 인증 장치를 전제하지 않는다. §3의 단말 토큰은 **소프트웨어 토큰**이므로 이 확정과 정합한다.

### 2.2 물리 모델이 이미 전제하고 있는 구조

정본 물리 모델은 POP 트랜잭션이 **(작업자, 단말)** 쌍을 싣고 **app_user는 싣지 않는** 것을 이미 전제한다. 설계를 새로 정하는 게 아니라 **API 계층이 데이터 계층을 따라가야 하는** 상황이다.

| 테이블 | `worker_id` | `terminal_id` | `created_by`(app_user) |
| --- | --- | --- | --- |
| `production.production_result` | **NOT NULL** | nullable | nullable |
| `production.material_consumption` | **NOT NULL** | **NOT NULL** | nullable |
| `production.work_session` | (`work_session_worker`로 N:M) | **NOT NULL** | nullable |
| `audit.audit_event` | — | nullable | nullable |

→ 실적·소비의 **작업자 귀속은 필수**, **app_user는 선택**. `audit_event`는 `performed_by`(사람)와 `terminal_id`(단말)를 **나란히** 갖는다 — 감사 주체가 이원화될 것을 이미 예상한 스키마다.

### 2.3 단말×공정 권한 매트릭스가 이미 있다

`mdm.terminal_process`는 (단말, 공정)마다 8개 행위 플래그를 갖는다:

```
can_start_work · can_complete_work · can_input_material · can_input_result
can_input_inspection · can_print_label · can_cancel_input · can_return_material
```

**POP의 인가(authorization)는 역할·권한(RBAC)이 아니라 이 매트릭스다.** 관리 화면의 `MASTER_READ/WRITE/DEACTIVATE` 체계를 POP에 끌어올 필요가 없다.

## §3. [제안] 설계

### 3.1 원칙 — 3층 분리

| 층 | 질문 | 수단 | 위조 시 위험 |
| --- | --- | --- | --- |
| **인증(Authn)** | 이 요청이 우리가 설치한 단말에서 왔는가 | **단말 토큰** | 높음 → 암호학적으로 막는다 |
| **인가(Authz)** | 이 단말이 이 공정에서 이 행위를 해도 되는가 | **`terminal_process` 매트릭스** | 중간 → DB 조회로 막는다 |
| **귀속(Attribution)** | 누가 한 일로 기록할 것인가 | **사번(본문 파라미터)** | 낮음 → **수용**(WF02 S5 확정) |

핵심은 **사번을 인증에 쓰지 않는 것**이다. 사번은 귀속 정보일 뿐이며, 도용 리스크는 이미 확정 문서가 명시적으로 수용했다. 사번을 인증으로 승격시키면 REQ-PR-0023이 요구한 "로그인 생략"을 우회로 되살리는 셈이 된다.

### 3.2 단말 토큰

**발급**: 관리 화면에서 단말을 등록(`mdm.terminal`)할 때 1회 발급. Electron 설치형이라 토큰을 OS 자격증명 저장소(Windows DPAPI)에 둘 수 있다 — 브라우저 저장소 회수 문제가 없는 것이 결정 16에서 PWA를 폐기한 이유 중 하나였다.

**형태**: 사람 토큰과 **다른 클레임**을 쓴다. 같은 `sub` 구조를 재사용하면 가드가 둘을 구분하지 못한다.

```
사람 토큰: { sub: <app_user_id>, loginId }                    exp = 8시간
단말 토큰: { sub: <terminal_id>, kind: "terminal", plantId }  exp = 없음 또는 1년
```

**만료**: 사람 토큰의 8시간 만료를 그대로 쓰면 안 된다. 현장에서 토큰이 만료되면 작업이 멈추고, 그걸 푸는 방법이 결국 "누군가 로그인" 이므로 REQ-PR-0023으로 되돌아간다. 대신 **폐기(revocation)** 로 통제한다 — `terminal.is_active = false` 또는 `status_code` 전이 시 즉시 무효.

**폐기 확인 비용**: 매 요청마다 `terminal` 행을 조회하면 부하가 커진다. 현행 사람 토큰도 `resolvePrincipal`로 매번 DB를 친다.

> **구현 반영(2026-07-28)**: 초안은 짧은 TTL 캐시를 제안했으나 **캐시 없이 구현했다.** 분실 단말을 즉시 끊는 쪽이 지금 단계에서 더 중요하고, 캐시는 폐기 반영 지연이라는 대가가 분명하다. 부하가 실측으로 문제가 되면 그때 넣는다.

### 3.3 요청 형태

```http
POST /api/pop/production-results
Authorization: Bearer <단말 토큰>
X-Worker-No: 900028              ← 귀속. 인증 아님
Idempotency-Key: <UUID>          ← 오프라인 재전송 대비 (§3.5)

{ "workOrderNo": "...", "goodQty": 120, ... }
```

**사번 실물 형식 = 6자리 숫자**다. ERP 사원 마스터 `T_ERP_EMP_TIG_DOWN.EMP_CODE`(nvarchar(40), 786 rows)의 대표 레코드가 `"900028"`이고, 제품출하명세표(출문증) 실물의 신청자 사번도 `903677`이다 — 둘 다 `90****` 형태다. 현행 `worker_no`의 `CODE_PATTERN`(`^[A-Z0-9_]+$`) 검증을 그대로 통과하므로 **추가 조치가 필요 없다**. (물리 모델의 `app.code_t`는 `varchar(50) CHECK (VALUE <> '')`뿐이라 DB 차원 문자 제약은 애초에 없다.)

`X-Worker-No`를 헤더로 둘지 본문 필드로 둘지는 취향 문제지만, **헤더를 권한다** — 모든 POP 쓰기 요청에 공통으로 붙고, 가드/인터셉터에서 한 번에 꺼내 `worker_id`로 해석할 수 있다.

### 3.4 가드 설계

현행 `AuthGuard`를 건드리지 않고 **별도 가드를 추가**한다. 화이트리스트 구조(“`@Public()`이 없으면 막힌다”)는 안전망이므로 유지한다.

```
@Public()                    → 인증 없음 (health만)
(기본)                        → 사람 토큰 필수 + @RequirePermissions(...)
@TerminalAuth()              → 단말 토큰 필수 + @RequireCapability('can_input_result')
```

`@TerminalAuth()`가 붙은 엔드포인트는 사람 토큰을 **거부**해야 한다. 관리자 토큰으로 현장 실적을 올릴 수 있으면 `worker_id` 귀속이 무의미해진다.

`[제안]` 인가는 `@RequireCapability('can_input_result')` 형태로 선언하고, 가드가 `terminal_process`에서 (단말, 요청 대상 공정)을 찾아 해당 플래그를 확인한다. 공정은 대개 W/O나 라우팅 공정에서 파생되므로, 가드가 아니라 **서비스 계층에서 확인**해야 할 수도 있다 — §6-①.

> **구현 반영(2026-07-28)**: §6-① 제안대로 **서비스 계층 확인**으로 구현했다. `@RequireCapability()` 데코레이터는 만들지 않고 `TerminalAuthService.assertCapability(terminalId, processCode, capability)`를 서비스에서 호출한다. 가드는 단말 인증만 맡는다.

### 3.5 오프라인 정합

결정 17(오프라인 내성 — 최소 운영)과 QA #32(POP 로컬 버퍼링 + 복구 시 자동 동기화)를 만족해야 한다.

- **단말 토큰은 장기**라 오프라인 구간을 넘겨도 살아 있다. 사람 토큰(8시간)이었다면 복구 시점에 만료되어 outbox 전송이 통째로 401이 난다 — **이것이 단말 토큰을 쓰는 가장 실질적인 이유다.**
- **`idempotency_key`**: `production_result`·`material_consumption`·`inspection_result`·`inventory_transaction` 4개 테이블이 이미 UNIQUE 제약을 갖고 있다. 재전송 중복은 DB가 막고, 앱은 P2002를 200/209로 변환한다.
- **시각**: 오프라인 중 발생한 이벤트의 `occurred_at`은 단말 시각, 서버 수신 시각은 `created_at`으로 분리(결정 17 "시각 분리 메커니즘 유지").

### 3.6 조회 API — POP이 읽어야 하는 기준정보

POP은 품목·BOM·라우팅·검사기준을 읽어야 한다(W/O 선배포 캐시 포함). 현재 이들은 `MASTER_READ` 권한을 요구하는 관리 API뿐이다.

`[제안]` 관리 API를 단말에 개방하지 말고, **POP 전용 읽기 엔드포인트를 따로 둔다**:

- 관리 API는 편집 화면용이라 전체 필드·페이징·감사 컬럼을 노출한다. POP에 필요한 건 "이 W/O를 수행하는 데 필요한 기준정보 묶음"이다.
- 선배포 캐시는 **묶음 단위 스냅샷**이 자연스럽다 — 개별 엔티티를 N번 호출하는 것보다 `GET /api/pop/work-orders/:no/bundle` 한 번이 오프라인 준비에 맞다.
- 관리 API를 두 인증 방식에 동시에 여는 것보다 경계가 명확하다.

## §4. 대안 검토 — 채택하지 않은 것

| 대안 | 채택 안 하는 이유 |
| --- | --- |
| **POP 엔드포인트를 `@Public()`으로 개방** | 공장망이 신뢰 경계라는 가정에 의존한다. 실적·자재소비는 재고와 원가에 직결되는 쓰기이고, 단말 위조를 막을 수단이 사라진다. `audit_event.terminal_id`도 자기신고 값이 되어 감사 가치가 없다. |
| **사번을 인증 수단으로(사번=비밀번호 없는 로그인)** | 사번은 공개 정보다. 인증으로 승격하면 "인증됨"이라는 잘못된 신뢰가 생긴다. 확정 문서는 사번을 **귀속용**으로만 규정하고 도용 리스크를 수용했다 — 그 전제를 바꾸는 결정이 된다. |
| **공유 계정 1개(예: `pop@plant1`) 로그인** | 토큰 만료 시 현장에서 재로그인이 필요해 REQ-PR-0023으로 회귀한다. 단말 구분이 사라져 `terminal_process` 매트릭스를 쓸 수 없고, 분실 단말만 선택적으로 폐기할 수도 없다. |
| **mTLS(클라이언트 인증서)** | 보안은 가장 강하다. 다만 인증서 발급·갱신·폐기 운영이 필요하고, 상시 원격 채널이 없는 환경(결정서 §원격 운영 — 방문 기본)에서 갱신 부담이 크다. 단말 수가 늘거나 보안 요구가 올라가면 재검토할 값어치가 있다. |
| **IP 화이트리스트만** | 단말 이동·DHCP 변경에 취약하고, 같은 망 안의 다른 기기를 구분하지 못한다. 단말 토큰의 **보조** 수단으로는 유효하다. |

## §5. 파급 반영 대상

`REQ-PR-0023`·`사번 입력` 전역 grep으로 실측한 참조처 전체다. **본 설계가 확정되면** 아래를 갱신한다.

## §6. 사용자 확정이 필요한 지점

① ~~**공정 단위 인가를 어디서 하나**~~ → **해소(2026-07-28 구현)**: 서비스 계층 `assertCapability()`로 확인하고 가드는 단말 인증만 담당한다.

② **단말 토큰을 DB에 저장하나** — 폐기를 `terminal.is_active`로만 할지, 토큰 해시를 별도 컬럼/테이블에 두고 개별 폐기·재발급 이력을 남길지. 정본 물리 모델에 해당 컬럼이 없어 **스키마 변경이 필요한 결정**이다. **제안: 우선 `is_active` 기반으로 시작하고, 재발급 이력 요구가 생기면 확장.**

③ **모바일(Capacitor) 단말은 어느 쪽인가** — 결정 16은 모바일을 별도 폼팩터로 두지만 인증 방식이 명시되지 않았다. 다만 **점검 입력 매체 = 모바일**이 확정됐고(✓확정 2026-07-24 배지단말 #5), WF05 S2는 점검자 귀속을 **사번 기반**으로 서술한다(✅ REQ-PR-0023 전제, 단 "적용 가능성"으로 미확정). 이 둘을 합치면 **모바일도 단말 인증 + 사번 귀속** 쪽이 유력하다. **제안: POP과 동일 모델 적용.** 다만 모바일은 순회·핸드헬드라 분실 위험이 POP보다 높으므로 토큰 만료를 짧게(예: 30일) 두고 재발급 절차를 두는 편이 낫다.

④ **사번 검증 수준** — `worker.is_active`·`status_code='ACTIVE'`만 볼지, `worker_qualification`(공정 수행 자격)까지 볼지. 후자는 자격 없는 작업자의 실적 입력을 막지만, 자격 데이터가 정비되기 전에는 현장을 세울 수 있다. **제안: 초기에는 존재·재직 확인만, 자격 검증은 설정형(차단/경고/미적용)** — WF02 S5의 작업 통제 3단계 방식과 같은 패턴.

⑤ **REQ-PR-0015 미정의 영향** — "사용자 유형/권한/접근 범위 정의"가 고객 액션 대기 상태다(명세서 §미결 9). 관리 화면 권한 체계가 확정되면 현행 `MASTER_*` 3종 임시 체계를 손봐야 하며, 그때 POP 인가 경계도 함께 검토한다.
