## §5. 액션·상태

### §5-1. ★ 집계·조회 응답 설계 — **이 차수가 세울 것**

조회 화면은 앞 차수에도 있었으나(`W-01-09` 입하예정·`M-01-04` 위치 확인) **집계가 주 기능인 화면은 처음**이다. 규약 6가지를 세운다.

#### ① 요약은 **필터 전체**, 목록은 **페이지**

```
요약 카드  →  필터 조건 전체의 집계        (128건 전부)
목록       →  페이지네이션 (1–50)
```

**화면이 목록을 받아 세면 안 된다** — 50건만 받고 「전체 128」을 낼 수 없다. **응답이 요약과 목록을 나눠 담는다.**

#### ② 파생 값은 서버가 계산한다

`M-01-04` §5-4(GENERATED 컬럼은 화면이 다시 계산하지 않는다)의 확장이다. **DB에 GENERATED가 없어도** 달성률·지연 같은 파생은 **서버가 낸다.**

**왜** — 반올림·0 나눗셈·기준 시각이 화면마다 갈린다. 지시 0인 W/O의 달성률을 한 화면은 0%, 다른 화면은 `—`로 보이면 같은 데이터가 다르게 읽힌다.

#### ③ **기간 필터를 필수로 한다**

무제한 조회를 허용하면 **`production_result`가 누적된 뒤 화면이 멎는다.** 기본값을 **최근 1개월**로 두고 비울 수 없게 한다.

⚠ **`inventory.inventory_transaction`은 `business_date` RANGE 파티션**이다(실측). **파티션 키를 필터에 안 넣으면 전 파티션을 스캔**한다 — `W-01-07`이 이 제약을 직접 받는다.

#### ④ 정렬 키를 **제한**한다

「아무 열이나 정렬」을 열어 두면 인덱스 없는 열에서 전체 정렬이 돈다. **정렬 가능한 열을 스펙이 지정**한다.

| 정렬 가능 | 근거 |
| --- | --- |
| W/O 번호 · 계획 시각 · 상태 · 우선순위 | 단일 컬럼 |
| **달성률** | ⚠ **파생이라 정렬이 비싸다** — 허용하되 기간이 좁을 때만 |

#### ⑤ **기준 시각을 항상 보인다**

집계는 조회 시점의 스냅샷이다. C-6(오프라인 조회는 기준 시각 표시)의 **관리웹 판**이다 — 오프라인이 아니어도 **집계는 이미 과거**다.

```
기준 08-05 09:12   [ 새로고침 ]
```

#### ⑥ 자동 갱신을 두지 않는다

현장 대시보드가 아니라 **관리자 조회 화면**이다. 폴링을 두면 서버 부하가 사용자 수만큼 곱해진다. **명시적 새로고침**만 둔다.

⚠ **`W-CO-03`(알람 대시보드)은 다르다** — 그쪽은 실시간이 요건이다. **화면 성격에 따라 갈린다.**

→ **§C가 아닌 새 절이 필요하다** §9-1.

### §5-2. 달성률의 분모가 무엇인가

```
달성률 = 양품 / 지시수량 ?
        = 양품 / (양품+불량+손실) ?
```

**R80이 「마감 결과 3분류」를 **양품 기준**으로 정한다**(R14 「W/O 크기 = **양품 목표 수량**」). **분모는 지시 수량**이다.

⚠ **`W-02-05`(마감)와 같은 식을 써야 한다** — 조회에서 95%인데 마감에서 미달 판정이 다르게 나오면 신뢰를 잃는다. **서버가 한 곳에서 계산**하는 이유다(①②).

### §5-3. 「지연」 판정 — `planned_end_at`이 nullable이다

```
work_order.planned_end_at   timestamptz     ← nullable
```

`W-02-03` §8-3에서 「계획 시각을 필수로 할 것인가」를 미결로 남겼다. **여기서 그 파급이 보인다** — 시각이 없으면 **지연을 판정할 수 없다.**

| | 표시 |
| --- | --- |
| `planned_end_at` 있음 · 경과 · 미완료 | ⚠ **지연** |
| `planned_end_at` 없음 | **`—`** — 「지연 아님」이 아니라 **판정 불가** |

⚠ **판정 불가를 「정상」으로 보이면 안 된다.** 요약 카드의 「지연 9」가 실제로는 더 많을 수 있다 → §8-1.

### §5-4. 상태 체계는 결정 14 소관이다

**결정 14**가 「중단/취소/마감 구분 상태」를 확정했고(예외 E-13 **설계 종결**), 이 화면이 그 체계를 **처음 한눈에 보인다.**

**그런데 `work_order.status_code`가 `code_t` 맨몸**이라 값 집합이 데이터에 없다(#64 계열).

**화면 설계**: 요약 카드 6종(전체·대기·진행중·완료·마감·지연)을 **가정으로 두되**, 값 목록이 오면 조정한다. **지연은 상태가 아니라 파생**이므로 값 목록과 무관하다.

⚠ **「취소」가 카드에 없다** — 예외 E-4 ④가 「취소 상태 신설 **확정**」이라 했으므로 값이 오면 카드가 하나 는다 → §8-3.

### §5-5. 5컬럼을 3원으로 축약한다 — ⚠ #60이 여기서도 걸린다

```
production_result:  good_qty · defect_qty · hold_qty · scrap_qty · rework_qty   (5)
확정(QA #13):       양품 / 불량 / 손실                                          (3)
```

**#60**(작업실적 수량 구분 3원 ↔ 5컬럼)이 **차단** 등급으로 열려 있다(파일럿 `P-02-04`).

**이 화면은 조회라 차단이 아니다** — 어떻게 묶든 화면 골격이 같다. 다만 **묶는 규칙이 `P-02-04`와 같아야** 입력과 조회가 어긋나지 않는다.

**잠정 축약**(#60 회신 전):

| 3원 | 5컬럼 |
| --- | --- |
| 양품 | `good_qty` |
| 불량 | `defect_qty` + `rework_qty` ⚠ |
| 손실 | `scrap_qty` |
| *(미분류)* | `hold_qty` ⚠ **어디에도 안 들어간다** |

⚠ **`hold_qty`가 3원에 자리가 없다.** 합계가 안 맞을 수 있다 → §8-2. **화면은 3원 합계와 5컬럼 합계를 함께 보이지 않는다**(어긋남이 드러난다).

## §9. 이 장에서 나온 공유 계약 후보

1. **★ §L(조회·집계) 신설 — 6조항** — 조회 화면이 늘고 있는데 규약이 없다. ① **요약은 필터 전체 · 목록은 페이지**(응답이 나눠 담는다) ② **파생 값은 서버가 계산**(달성률·지연을 화면마다 다르게 내면 안 된다) ③ **기간 필터 필수**(파티션 테이블은 파티션 키 강제) ④ **정렬 키 제한** ⑤ **기준 시각 상시 표시**(C-6의 관리웹 판) ⑥ **자동 갱신 없음**(대시보드와 구분) (§5-1)
2. **같은 수치를 두 화면이 보이면 계산은 한 곳에서 한다** — 조회의 달성률과 마감의 3분류 판정이 다르면 신뢰를 잃는다. **파생 규칙의 소유 화면을 스펙이 지정**한다 (§5-2)
3. **「판정 불가」를 「정상」으로 보이지 않는다** — `planned_end_at`이 없으면 지연 판정이 불가한데, 빈칸으로 두면 정상으로 읽힌다. **A-7의 `(전체)` 표기와 같은 원리를 파생 값에도 적용**한다 (§5-3)
