## §5. 액션·상태

### §5-1. ★ A-7 11축 — 조회에서는 **「어느 축으로 묶나」**가 문제다

```
uq_inventory_balance_dim  (법인·사업부·공장·창고·위치·품목·COALESCE(lot)·품질상태·재고상태·소유·COALESCE(소유처))
```

**잔액 한 행이 11축의 조합이다.** `M-01-04`(모바일)는 LOT 하나를 스캔해 그 행들을 보였는데, 이 화면은 **수천 행을 묶어 보여야** 한다.

**보기 3종을 둔다**(§3):

| 보기 | `GROUP BY` | 쓰는 사람 |
| --- | --- | --- |
| **품목별** *(기본)* | 품목 | 「이 자재가 얼마나 있나」 |
| **LOT별** | 품목 + LOT | 「이 LOT이 어디 있나」 |
| **위치별** | 창고 + 위치 | **구 `W-01-08` 흡수분** — 「이 선반에 뭐가 있나」 |

⚠ **묶으면 나머지 축이 사라진다.** 품목별로 묶으면 품질상태·소유가 섞이는데, **섞인 것을 합치면 안 되는 경우**가 있다(자사 소유와 고객 지급품을 더하면 오독).

**규칙**: **소유(`ownership_type_code`)가 다르면 묶지 않는다.** 품질상태는 「가용/보류」 열로 이미 갈리므로 묶어도 된다.

→ **§L 신규 조항 후보** §9-1.

### §5-2. A-7 표기 규칙이 여기서도 걸린다

`M-01-04` §5-1에서 세운 것 그대로:

| 축 | NULL일 때 |
| --- | --- |
| `lot_id` | **`(LOT 무관)`** |
| `owner_partner_id` | **`(자사 소유)`** |

**LOT별 보기에서 `(LOT 무관)` 행이 섞인다** — 빈칸으로 두면 데이터 누락으로 읽힌다.

### §5-3. 결정 10 「캐시 없음」 — 관리웹이라 **문제가 안 된다**

`M-01-04` §5-6에서 **오프라인 캐시의 보류 표시**가 위험하다고 정리했다. **이 화면은 관리웹이라 오프라인이 없다**(C-5) — **항상 서버를 본다.**

⚠ **다만 §L ⑤(기준 시각 상시 표시)는 적용된다.** 조회 시점 스냅샷이므로 「08-05 09:12 기준」을 보인다. **집계는 오프라인이 아니어도 이미 과거다.**

⚠ **자동 갱신을 두지 않는다**(§L ⑥). 재고는 계속 움직이지만 **이 화면은 대시보드가 아니다.**

### §5-4. 수불 이력 조회 — **파티션 키를 강제한다**

```
inventory.inventory_transaction  ... PARTITION BY RANGE (business_date)
```

**§L ③의 「파티션 테이블은 파티션 키를 필터에 강제」가 여기서 처음 실제로 걸린다.**

| | |
| --- | --- |
| 기간 없이 조회 | ⛔ **전 파티션 스캔** — 운영에서 멎는다 |
| 화면 규칙 | **드로어의 「수불 이력 →」에 기간 입력을 붙인다.** 기본 최근 1개월 |

**LOT 하나의 이력이라 건수는 적지만 스캔 범위가 문제**다 — `business_date` 없이는 인덱스를 못 탄다.

### §5-5. 유효기간 관리 — 확정이 「관리한다」인데 화면이 무엇을 하나

**S6 태스크 3**: 「유효기간 관리」 · **예외 E-5 ②** 「유효기간 경과 — **처리 정책 잔여**」

**데이터는 있다**: `trace.lot.expiry_date` · `mdm.item.shelf_life_days` · `opened_shelf_life_hours`(개봉 후).

**정책이 없다.** 경과분을 어떻게 할지(자동 보류? 경고만?)가 미정이므로 **이 화면은 보이기만 한다.**

| 상태 | 표시 |
| --- | --- |
| 유효기한 경과 | ⚠ **경고 색 + 「경과」 표식** — 자동으로 보류하지 않는다 |
| 임박(30일 이내) | ⚠ 주의 표식 — **기준 일수 미정** §8-2 |

**A-9 ⓒ(표시만)** 등급이다. **차단·자동 전이를 하지 않는 이유를 화면이 밝힌다**(정책 미정).

### §5-6. 의심자재는 **여기서 등록하지 않는다**

**REQ-PR-0027**(의심 자재 등록 관리)이 S6 태스크 4에 있고 이 화면의 데이터에도 「의심자재」가 들어 있다.

**그런데 등록 화면은 `W-03-03`**(의심자재 등록 = Lot Status 생성 — `05` §5 S5)이다. **03 품질 소관**이다.

**이 화면은 결과를 보인다.** 등록 액션을 두면 **판정 권한이 두 화면으로 갈린다.**

```
[ 보류 상세 ]  ← 조회만
⛔ 의심자재 등록은 품질관리 > 의심자재 등록(W-03-03)에서 합니다
```

⚠ **§I-11이 여기서도 배경에 있다** — Lot Status 현재 상태 테이블이 없어 **`lot_hold` 미해제 행으로 유추**한다(`M-01-08` §5-2). 조회라 위험은 낮다.

## §9. 이 장에서 나온 공유 계약 후보

1. **§L 신규 조항 — 묶어 보일 때 「합치면 안 되는 축」을 계약이 지정한다** — `inventory_balance`는 11축인데 품목별로 묶으면 나머지가 사라진다. **소유(`ownership_type_code`)가 다르면 합치지 않는다** — 자사 재고와 고객 지급품을 더하면 오독이다. **집계 화면마다 「묶어도 되는 축/안 되는 축」을 스펙이 적는다** (§5-1)
2. **§L ③(기간 필터 필수)은 파티션 테이블에서 성능이 아니라 가능/불가능의 문제다** — `inventory_transaction`이 `business_date` RANGE 파티션이라 키 없이는 전 파티션 스캔이다. **파티션 키를 가진 테이블 목록을 계약이 갖고, 그 조회 화면은 필터를 강제**한다 (§5-4)
3. **조회 화면은 등록 액션을 갖지 않는다 — 판정 권한이 갈리기 때문** — 의심자재 등록은 `W-03-03`(03 품질) 소관이다. 편의로 등록 버튼을 두면 **같은 판정이 두 화면에서 일어난다.** 경로만 안내한다 (§5-6)
