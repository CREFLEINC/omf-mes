## §A. 데이터 제약 → UI 규칙

물리 모델의 제약을 화면이 어떻게 표현할지. **제약은 이미 정해져 있으므로 우리가 정하는 것은 표현 방식뿐이다.**

### A-1. 유일 제약 검사 시점 ✅ **✓확정 2026-08-02**

**규칙**: 코드 필드는 **blur 시 선검사 + 저장 시 서버 재검증**. 선검사만으로 확정하지 않는다(경합 때문).

**근거**: `uq_warehouse(plant_id, warehouse_code)` · `uq_location(warehouse_id, location_code)` · `trace.lot UNIQUE(plant_id, lot_no)` 등 유일키가 다수. — `W-06-07` §6

**문구**: 「같은 공장에 이미 있는 창고코드입니다」처럼 **유일키의 범위를 문구에 담는다**(단순 「중복입니다」 금지 — 어느 범위에서 중복인지 모르면 사용자가 고칠 수 없다).

> **결정 기록(2026-08-02 사용자 확정)**: 두 검사 중 하나만 두는 안을 검토한 뒤 **양쪽 다 유지**로 확정했다. 선검사만 두면 두 사람이 동시에 같은 코드를 넣을 때 뚫리고, 서버 검증만 두면 사용자가 폼을 다 채운 뒤에야 실패를 안다. 실질적으로 선택지가 없는 항목이다.
> **API 파급**: 중복 응답은 **어느 유일키 범위에서 중복인지**를 담아야 한다. 범위 없이 「중복」만 오면 화면이 위 문구를 만들 수 없다 — 횡단 규약에 반영한다.

### A-2. 조건부 필수·짝 제약의 표시 ✅

**규칙**: `CHECK` 제약을 **사용자 문구로 옮기고, 관련 필드를 함께 표시**한다.

| 제약 유형 | 예 | 표시 |
| --- | --- | --- |
| 조건부 필수 | `ck_external_warehouse_partner` — 외부창고면 거래처 필수 | 토글 ON 시 해당 필드에 필수 표시 전환 |
| 짝 제약 | `ck_location_capacity` — 수용량과 단위는 함께 | **두 필드에 동시** 인라인 오류 |
| 합계 제약 | `ck_inspection_result_qty` — 합격+불합격+보류 = 검사수량 | A-3 |

### A-3. 합계 제약의 UI 표현 ✅

**규칙**: `CHECK(a+b+c = total)` 류는 **실시간 합계·잔여를 표시**하고 **불일치 상태에서 확정 버튼을 비활성**한다.

**⚠ 자동 계산은 규칙이 확정된 뒤에만 얹는다.** 「합격만 넣으면 나머지 자동」은 **어느 칸을 자동으로 할지**가 정해져야 가능하다 — 지금은 미정(`W-01-01` §8-4).

### A-4. 감사 컬럼·`version_no`는 화면에 노출하지 않는다 ✅ **[2026-08-03 단서 추가]**

`created_at`·`created_by`·`updated_at`·`updated_by`·`version_no`는 시스템이 채운다. **필드표에 넣지 않고 폼에도 띄우지 않는다.** 단 `version_no`가 있으면 **B-1을 반드시 구현**한다.

> **확정(2026-08-03 사용자 확정)**: 이 조항은 **화면 표시 규칙**이다 — 전송은 막지 않는다. 원문이 「`version_no`가 있으면 B-1(낙관적 잠금)을 반드시 구현한다」를 함께 말하는데, **전송까지 금지하면 B-1이 성립할 수 없다.** **단서**: 낙관적 잠금 토큰은 **헤더로 전송**하되(`ETag` 응답 → `If-Match` 요청) **화면에 표시하지 않는다.** 금지되는 것은 필드표·폼·목록 열에 드러나는 것이지 전송 자체가 아니다.
> 현재 OpenAPI가 이미 그렇게 돼 있다(응답에는 `ETag` 헤더로 · 요청에는 `If-Match` 헤더로 전송하며, `version_no`를 본문 필드로 싣는 스키마는 없다) — **조항이 구현을 따라가는 정정**이다. *(실측 카운트는 API가 커지면서 낡으므로 계약에는 성질만 남긴다.)*

### A-5. 순서 컬럼의 재배치는 서버가 한 트랜잭션으로 한다 ✅ **[v0.4 신설 · 2026-08-03 정정]**

**규칙**: `UNIQUE` 제약이 걸린 순서 컬럼을 화면에서 맞바꾸면 **중간 상태가 반드시 제약을 위반**한다(10↔20을 바꾸려면 잠깐 중복이 생긴다). **화면은 최종 순서만 보내고, 서버가 일괄 갱신**한다.

**해당**(실측 2곳): `planning.routing_operation.operation_seq` · `quality.inspection_item_spec.sequence_no` — `W-06-01` §8-8

> ⚠ **3번째 후보 — `app.approval_route_step.step_no`** *(2026-08-04 확대 2차에서 발견)*. `UNIQUE(approval_route_id, step_no)`가 실재한다(실측). **결재선 단계 순서를 사용자가 바꾸는 화면이 생기면 A-5 대상**이다. 지금은 **결재선 정의 화면이 인벤토리 108건에 없어**(J-1 ⬜) 목록에 넣지 않고 후보로만 둔다. — `W-01-02` §9-A

> **⚠ 2026-08-03 정정 — 대상은 4곳이 아니라 2곳이다.** API 설계 과정에서 두 곳이 더 빠졌다는 것이 드러났다. ① `mdm.code_value.display_order`는 **유일 제약이 없다**(`integer NOT NULL DEFAULT 0` — 실측, 중복이 허용된다) — 중간 상태가 제약을 위반하지 않으므로 전체 치환의 이유가 성립하지 않는다(행마다 개별 갱신하면 된다). ② `planning.bom_component.sequence_no`는 **ERP 원본이라 MES가 재배치하지 않는다** — 편집 가능한 열은 확장 4열뿐이라 순번 자체가 이 API의 대상이 아니다(행 단위 PUT — `06-API-요구서.md` §3-6·§4-1이 확정). `ds-gap.md` **G-7**(행 순서 UI가 필요한 곳)과 혼동한 것이었다 — **UI가 필요한 곳과 서버 트랜잭션이 필요한 곳은 다르다.** G-7은 「사용자가 순서를 바꿀 수 있는 표」전부를 세고, A-5는 그중 「바꾸는 중간 상태가 DB 유일 제약을 위반하고 MES가 직접 재배치하는 것」만 센다. 두 집합이 겹치지만 같지 않다.

**조항 2건을 더한다(2026-08-03 · API 설계 과정에서 드러남)**

1. **전체 치환은 행 교체가 아니다** — 서버는 기존 행을 유지하며 순서만 갱신한다. `routing_operation` 참조가 넷이고 `production.work_order.routing_operation_id`는 `NOT NULL`이라 `DELETE`+`INSERT`로 구현하면 진행 중 작업지시가 무너진다.
2. **순서 표시는 서버 저장 키가 아니라 목록 내 위치로 매긴다.** 채번 방식(연번/간격)은 데이터 모델링 재량이며, 화면이 저장 키를 보여주지 않으면 채번이 바뀌어도 화면이 흔들리지 않는다.

### A-6. 「하나만 참」 부분 유일 인덱스는 전환도 서버가 한다 ✅ **[v0.4 신설]**

**규칙**: `CREATE UNIQUE INDEX ... WHERE <조건>` 형태는 **동시에 둘을 막을 뿐 자동 전환을 해 주지 않는다.** 화면이 「기존 해제 → 새것 설정」 2회 호출하면 **그 사이에 0개인 상태**가 생긴다. **단일 액션으로 노출하고 서버가 한 트랜잭션으로** 처리한다.

**해당**: `uq_bom_default ON planning.bom (parent_item_id) WHERE is_default` — `W-06-05` §9-3

### A-7. 부분 유일 인덱스(`COALESCE`)의 표기·오류 문구 ✅ **[v0.4 신설]**

**규칙**: `COALESCE(col, 0)`으로 NULL을 접어 유일 판정하는 인덱스에서 화면은

1. **빈 축을 `(전체)`로 표기**한다 — 「없음」이 아니라 「제한 없음」이라는 뜻이다. 빈칸으로 두면 오해한다
2. **중복 오류 문구에 접힘 규칙을 담는다**(A-1의 「유일키 범위를 문구에」를 이 형태로 확장)

**해당**(실측 9곳): `uq_user_data_scope` · `uq_item_external_code` · `uq_worker_qualification` · `uq_lot_external_identifier` · `uq_inventory_balance_dim` · `uq_putaway_rule` · `uq_shipment_lot_allocation` · `uq_operation_policy` · `uq_numbering_rule` — `W-CO-02` §9-2

### A-8. 수치 컬럼의 **저장 단위**를 계약이 못박는다 ✅ **[v0.4 신설]**

**규칙**: 비율·수량·퍼센트가 섞이는 컬럼은 **저장 단위와 표시 단위를 함께 명시**하고, 입력란에 단위를 표시한다.

| 컬럼 | 저장 | 표시 |
| --- | --- | --- |
| `bom_component.scrap_rate` | **비율 0~1**(`CHECK BETWEEN 0 AND 1`) | `%` — **100배 변환** |
| `routing_operation.standard_yield_rate` | **비율 0~1** | `%` |
| `inspection_plan_version.sampling_qty` | ⚠ **미정** — 확정 문구는 「샘플 비율(%)」인데 컬럼은 `qty_t`(수량) | §I-6 |
| `routing_operation.standard_cycle_time_sec` | **초** | 라벨에 단위 명시 |

**이유**: 화면이 `%`로 보이면서 저장을 비율로 하면 **100배 오입력이 조용히 통과**한다 — `W-06-05` §9-2 · `W-06-13` §9-2

### A-9. DB가 막지 않는 검증은 **등급을 나눠** 화면이 진다 ✅ **[v0.4 신설]**

**「DB 제약이 없다고 규칙이 없는 게 아니다」**(`M-01-02` §4-1). 확대 1차에서만 **10건 이상**이 나왔다. 화면이 지는 검증을 **세 등급**으로 나눈다.

| 등급 | 뜻 | 예 |
| --- | --- | --- |
| **ⓐ 차단** | 저장 불가 — 데이터 무결성 | 계층 순환 참조(`department`·`defect_code`) · 2계층 초과(결정 12) · 자기참조(CHECK 없는 테이블) |
| **ⓑ 경고** | 저장은 되나 확인 요구 — 운영 판단 | 목표값이 상·하한 밖 · 교정 만료 장비 지정 · 전사 고정 축 코드 추가 |
| **ⓒ 표시만** | 알려만 준다 | 이메일 형식 · 참조 건수 |

⚠ **등급을 화면마다 다르게 정하면 같은 성격의 오류가 화면에 따라 다르게 굴러간다** — `W-06-02` §9-1

**코드 필드 수정 — 확정 규칙**

- 저장된 코드는 **그 코드를 참조하는 레코드가 하나도 없을 때만** 수정할 수 있다
- 참조가 하나라도 있으면 **코드 입력란을 비활성**하고, 이름·속성 등 나머지 필드만 편집한다
- 비활성 사유를 함께 표시한다 — F-1·G-1과 같은 방식(「이 창고를 참조하는 자재 로트가 12건 있어 코드를 바꿀 수 없습니다」)
- 잘못 만든 코드는 **`is_active = false`로 내리고 새로 만든다**

> **결정 기록(2026-08-02 사용자 확정)**: 세 안을 검토했다. **(가)** 코드는 생성 후 수정 불가 — 참조와 부착 라벨은 안전하나 오타 하나를 못 고친다. **(나)** 수정 허용하되 라벨 재발행 대상을 함께 표시 — 요구사항 문구는 만족하나 이미 붙은 라벨을 회수·재부착하는 절차가 없다. **(다) 참조 건수 0일 때만 허용 — 확정.** 실수 직후에는 고칠 수 있고 운영 중에는 잠기므로, REQ-PR-0021 「전체 수정 가능」을 정면으로 어기지 않으면서 참조 무결성과 부착 라벨 문제를 둘 다 피한다.
> **감수하는 비용**: 화면이 참조 건수를 조회해야 하고, 사용자에게 「왜 어떤 때만 되는가」를 설명해야 한다. 그래서 사유 표시가 선택이 아니라 필수다.
> **API 파급**: 마스터 상세 조회 응답에 **참조 건수(또는 수정 가능 여부와 그 사유)** 가 포함돼야 한다. 화면이 별도 호출로 세면 화면마다 다르게 구현된다 — 횡단 규약에 반영한다.

「참조 0일 때만」은 **참조를 셀 수 있을 때만 성립**한다. 물리 모델에는 **셀 수 없는 참조가 두 형태** 있다(실측).

3. **파티션 테이블이므로 기간 조건을 필수**로 한다 — 기간 없는 조회는 전 파티션 스캔
4. **diff 표시 규약**: 바뀐 키만 강조 · 한쪽에만 있는 키는 추가/삭제 · **모르는 키도 원문 그대로**(파싱 실패로 감추지 않는다) · 값이 코드면 코드+표시명 병기

> ⚠ **「테이블이 있다」와 「쓸 수 있다」는 별개다.** `target_id`가 **FK가 아니고**(유형별로 다른 테이블), `before/after` **jsonb의 키 규약이 없다** — `W-06-11` §8-2 · §I-4.

### B-8. 트랜잭션의 경계 — **외부 호출은 밖, outbox 적재까지가 안** ✅ **[v0.5 신설]**

한 확정이 여러 엔티티를 움직일 때 **어디까지가 한 트랜잭션인가**를 정한다.

**규칙 1 — 업무 엔티티는 전부 안이다.** 부분 성공을 만들지 않는다.

`W-01-10` 입고 확정의 실측 예 — 확정 한 번이 다섯을 움직인다.

```
┌─ 한 트랜잭션 ────────────────────────────────────┐
│ ① goods_receipt + line        입고 전표          │
│ ② trace.lot.status_code       Hold → 가용        │
│ ③ inventory_transaction+line  수불원장           │
│ ④ inventory_balance           가용 수량          │
│ ⑤ integration_message         ERP 메시지 **적재** │
└──────────────────────────────────────────────────┘
                              ↓ 별도 워커
                        ERP 실제 전송
```

**규칙 2 — ★ 외부 시스템·장치 호출은 트랜잭션 밖이다.** ERP·프린터·OCR 같은 상대를 트랜잭션 안에서 부르면, 상대가 느릴 때 DB가 잡히고 **상대가 실패할 때 우리 업무까지 롤백된다.**

**outbox에 적재하는 것까지가 안이고 전송은 밖이다.** C-4가 정한 `integration_message`가 그 구조다(`available_at`·`locked_at`·`locked_by`·`retry_count`).

**규칙 3 — 「즉시」는 전송 시도의 즉시성이지 트랜잭션 포함이 아니다.** 확정 기록의 「건별 즉시」(✓확정 QA #1)를 동기 호출로 읽지 않는다. `available_at`을 현재로 두면 워커가 곧바로 집어간다.

**규칙 4 — 화면은 「무엇이 아직 안 됐는가」를 말한다.** 확정 직후 상대 시스템에 없을 수 있다. 「완료」라고만 하면 사용자가 상대를 보고 혼란스러워한다.

**규칙 5 — 경로마다 결과가 다르면 결과 안내도 달라진다.** 한도승인 건은 ERP 송신이 아예 없다(G/R 합격품 한정). 같은 화면이 같은 안내를 보이면 오해한다.

**규칙 6 — 외부 호출 실패는 업무 기록을 무효화하지 않는다.** 프린터가 죽어도 LOT은 생성되고, 재발행으로 푼다(K-1).

— `M-01-01` §5-4 · `W-01-03` §5-4 · `W-01-10` §5-4·§9 · `P-01-01` §5-2

### B-9. 선행 화면이 만드는 객체가 `NOT NULL`이면 **의존을 스펙이 명시한다** ✅ **[v0.6 신설]**

화면 A가 만든 것을 화면 B가 `NOT NULL`로 참조하면, **A 없이는 B가 성립하지 않는다.** 스펙이 이 의존을 적지 않으면 A가 빠졌을 때 B가 조용히 깨진다.

**판별** — 참조 컬럼의 nullability가 의존의 강도를 말한다.

| 참조 | 뜻 | 예 |
| --- | --- | --- |
| **nullable** | 선행 없이도 성립 — 기록만 약해진다 | `material_consumption.work_session_id` → `P-02-03`은 세션 없이도 투입 기록 |
| **`NOT NULL`** | **선행이 필수** — 없으면 진입 자체가 막힌다 | `work_session_event.work_session_id` → `P-02-10`은 세션 없이 불가 |

**규칙**: 스펙 §5에 **「이 화면이 무엇을 전제하는가」**를 적고, 전제가 미충족일 때의 화면 동작(차단·경고·대안 경로)을 §6에 적는다.

> ⚠ **실례** — `P-02-01`(작업 시작)이 **#67로 보류**되어 세션을 여는 화면이 3차에 없다. `P-02-03`은 nullable이라 돌지만 **`P-02-10`은 진입이 막힌다.** — `P-02-03` §8-5 · `P-02-10` §5-2

## §C. 오프라인·동기화 (POP · 모바일)

### C-1. 오프라인 입력 규약 ✅ **✓확정 2026-08-02**

**근거가 데이터 모델에 이미 박혀 있다** — `production_result`·`inspection_result` 양쪽에 `idempotency_key varchar(150) NOT NULL UNIQUE`.

**규칙**:

1. **`idempotency_key`는 클라이언트가 생성**해 outbox에 담는다. 재전송 시 서버가 중복을 흡수한다
2. **로컬 저장 후 즉시 성공 피드백** — 통신을 기다리지 않는다
3. **`occurred_at`(발생) 과 `recorded_at`(서버 수신)을 분리** — 오프라인 지연이 실적 시각을 왜곡하지 않는다
4. **연결 상태와 미동기 건수를 상시 표시** (결정 16 POP 요건)
5. 재전송은 같은 키로 — **사용자에게 중복 저장으로 보이지 않아야 한다**

> **결정 기록(2026-08-02 사용자 확정)**: 「전송 대기로 구분 표시하고 서버가 받으면 성공으로 바꾼다」 대안을 검토한 뒤 **즉시 성공 표시 + 미전송 건수 상시 노출**로 확정했다. 작업자가 통신을 기다리지 않는 것을 우선했다. 다만 **미전송 건수 표시가 이 결정의 전제**다 — 그것이 없으면 서버에 도달하지 않은 사실을 알 방법이 사라지므로, 헤더 표시는 선택 사항이 아니라 필수 요건이다.

### C-2. 오프라인 유일성 판정 ✅ **✓확정 2026-08-02**

**규칙**: `UNIQUE` 제약은 **서버만 확정 판정할 수 있다.**

- 로컬은 **큐 내 중복만** 선검사
- 서버가 거부하면 **해당 건만** 오류 목록으로 되돌린다
- **전체 롤백 금지** — 40건 스캔 중 1건 중복으로 39건을 버리면 현장이 마비된다

— `M-01-02` §5-3

> **결정 기록(2026-08-02 사용자 확정)**: 「한 건이라도 거부되면 묶음 전체를 취소」 대안을 검토한 뒤 **거부 건만 되돌리기**로 확정했다. 일부만 반영된 상태가 남아 확인이 필요해지는 비용보다, 스캔 작업을 처음부터 다시 하지 않는 이점을 택했다. **따라서 오류 목록 화면이 필수 요건이 된다** — 무엇이 되돌아왔는지 보이지 않으면 부분 반영 상태를 수습할 수 없다.

### C-3. 연속 작업의 완료 모델 ✅

**규칙**: 스캔·실적처럼 반복되는 작업은 **건별 저장 + 마지막 일괄 완료**. 건마다 화면을 전환하지 않는다.

— `W-01-04` §5-1 · `M-02-01` §5-1 · `M-02-02` §5-6

### C-6. 오프라인에서 **조회**는 캐시를 보이되 **판정에 쓰이는 값은 캐시하지 않는다** ✅ **[v0.7 신설]**

C-1~C-4가 **전부 입력에 대한 것**이라 조회 화면에 적용할 규칙이 없었다.

**규칙**

1. **캐시를 보이고 기준 시각을 함께 표시**한다 — 「08-05 09:12 기준」. 차단하면 창고 안쪽에서 작업이 멈춘다
2. ⛔ **차단·통제 판정에 쓰이는 값은 캐시하지 않는다.** 결정 10이 「출고·출하·Picking 차단 판정은 **캐시 없음**」을 확정했고, 조회 화면의 보류 **표시**도 사람이 그걸 보고 움직이므로 같은 대상이다
3. 캐시 금지 항목은 **값을 감추고 「확인 불가」로 바꾼다** — 빈칸으로 두면 「없음」으로 읽힌다

```
⚠ 보류 여부는 연결된 뒤에 확인하세요 (마지막 확인: 08-05 09:12)
```

4. **캐시가 아예 없으면**(첫 실행) 조회를 시도하지 않고 안내한다

⚠ **캐시해도 되는 것과 안 되는 것이 한 화면 안에서 갈린다.** — `M-01-04` §5-5·§5-6

### C-7. 저장 피드백은 **두 등급**이다 — 「즉시 성공」이 전부가 아니다 ✅ **[v0.7 신설 · C-1 규칙 2 보완]**

C-1 규칙 2는 「**로컬 저장 후 즉시 성공 피드백**」인데, **되돌릴 수 없는 실물 이동**에서는 위험하다.

| 등급 | 언제 | 표현 |
| :-: | --- | --- |
| **ⓐ 즉시 성공** | 기록성 작업 — 카운트·조회·이력 | `Toast` 성공 |
| **ⓑ 미확정 표식 유지** | **실물이 움직이는 작업** — 출고·적치·이동·인계 | `Chip`(warning) 「미확정」 · 서버 확정 시 해제 |

**왜** — 오프라인 출고는 **캐시 판정으로 통과시키고 서버가 최종 판정**한다(C-9). 거부가 오면 **실물이 이미 라인에 가 있다.** 즉시 성공으로 표시하면 작업자가 「끝났다」고 믿는다.

⚠ **ⓑ는 C-1의 결정 기록(「작업자가 통신을 기다리지 않는 것을 우선」)을 어기지 않는다** — 기다리게 하지 않되 **아직 확정이 아님을 보이는 것**이다.

— `M-01-08` §5-3

### C-8. 멱등키는 **`business_date`까지 클라이언트가 정한다** ✅ **[v0.7 신설]**

`idempotency_key`는 물리 모델에 **4곳뿐**(전수 실측): `inventory.inventory_transaction` · `production.material_consumption` · `production.production_result` · `quality.inspection_result`.

**재고를 움직이는 모든 화면이 `inventory_transaction`을 지나고, 그것만 유일 제약 범위가 다르다.**

```
inventory_transaction:  UNIQUE (idempotency_key, business_date)   ← 날짜가 키의 일부
나머지 셋:              UNIQUE (idempotency_key)                   ← 전역
```

**뚫리는 시나리오**

```
08-04 23:50  오프라인 저장 (키 K)
08-05 00:10  연결 복구 → 전송
             서버가 business_date 를 수신일로 잡으면 (K, 08-05) 로 저장 —
             (K, 08-04) 가 이미 있어도 둘 다 통과 = 이중 전기
```

**규칙**: 클라이언트가 `occurred_at`과 함께 **`business_date`(발생일)를 보낸다.** 서버는 수신 시각으로 다시 잡지 않는다. — `M-01-05` §5-4

### C-9. 오프라인 큐 전송에는 **낙관적 잠금 토큰을 싣지 않는다** ✅ **[v0.7 신설 · B-1 예외]**

A-4는 `version_no`가 있으면 B-1을 반드시 구현하라고 하는데, **큐에 담긴 건의 `version_no`는 이미 낡았고 충돌 화면을 볼 사용자가 없다.**

| | 온라인 | 오프라인 큐 |
| --- | --- | --- |
| `If-Match` | 조회 시 받은 `ETag` | **몇 시간 전 것** |
| 충돌 시 | 다시 불러오기(G-1) | ⚠ **작업자가 이미 자리를 떴다** |

**규칙**

1. 오프라인 큐 전송은 **`If-Match`를 싣지 않는다**
2. 중복은 **멱등키가 막는다**(C-1·C-8)
3. 상태 전이는 **서버가 판정**한다 — 이미 처리된 건이면 `400 STATE_LOCKED`
4. 거부는 **C-2대로 해당 건만** 오류 목록으로 되돌린다

— `M-01-05` §5-6

### C-10. 큐에 **순서 의존**이 있으면 묶음으로 거부한다 ✅ **[v0.7 신설 · C-2 보완]**

**결정 17 시나리오 2**가 확정이다: 「통신 두절 시 **입·출측 스캔 단일 단말 큐로 축퇴**」(✓확정 2026-07-24 #8). **§C에 조항이 없었다.**

**한 단말에 출고와 입고가 함께 담기면 C-2의 「건별 되돌리기」가 성립하지 않는다.**

```
출고 거부  →  그에 딸린 입고는 goods_issue_line_id 가 없어 반드시 실패
```

**규칙**

1. **선행–후행 관계가 있는 큐 항목은 묶음(batch)으로 표시**한다
2. **선행이 거부되면 딸린 후행도 함께 되돌린다** — C-2의 「전체 롤백 금지」는 **무관한 건끼리**에 적용되는 것이지 의존 관계를 무시하라는 뜻이 아니다
3. **전송 순서를 큐가 보장**한다 — 병렬 전송으로 역전시키지 않는다
4. **축퇴 중임을 화면이 알린다** — 「오프라인 — 출고분도 이 단말에서 처리합니다」

— `M-01-09` §5-1 · `M-01-10` §5-4

### C-11. 오프라인 화면은 **「무엇을 미리 받아 두어야 하는가」를 스펙이 명시한다** ✅ **[v0.7 신설]**

C-1은 **저장만** 다루고 선행 데이터를 다루지 않는다. **지시 목록·마스터·검증 규칙이 전부 서버에 있으면 오프라인에서 화면이 성립하지 않는다.**

**각 오프라인 화면의 §5 또는 §8에 적는다**:

| 갈래 | 예 |
| --- | --- |
| **작업 대상 목록** | 적치 지시(`putaway_task`) · 피킹 라인 · 실사 계획 라인 |
| **마스터** | 위치·품목·단위 |
| **검증 규칙** | `allow_mixed_*` · `capacity_qty` · 보류 목록(⚠ C-6 2번과 충돌 — **판정용은 캐시 금지**) |

⚠ **다른 단말이 만든 것은 못 본다.** 반쪽 이동(`M-01-10`)·미완 작업은 **오프라인에서 목록에 뜨지 않는다** — 그 사실을 스펙이 적는다.

— `M-01-05` §8-5 · `M-01-10` §8-3

### C-12. 발생 시각은 **단말 시계에 의존한다** — 오차 보정 규약을 둔다 ⬜ **[v0.7 신설 · 미결]**

C-1 규칙 3(`occurred_at` ≠ `recorded_at`)이 **데이터로 뒷받침된다**(실측):

```
inventory_count_line.counted_at   timestamptz NOT NULL      ← 발생
inventory_count_line.created_at   timestamptz NOT NULL      ← 서버 수신
                                  DEFAULT clock_timestamp()
```

**규칙**: 화면은 **발생 시각을 로컬 시각으로 채워** 큐에 담고, 서버가 받은 시각으로 덮어쓰지 않는다.

⬜ **미결** — PDA 시계가 틀어져 있으면 오프라인에서는 보정할 수단이 없다. **연결 시 서버 시각과의 차이를 어떻게 다루는지**가 정해지지 않았다. — `M-01-11` §5-4·§8-5

### C-13. 선행 데이터에는 **「받는 시점」**도 함께 적는다 ✅ **[v0.9 신설 · C-11 보완]**

C-11이 「무엇을 미리 받나」를 요구하는데, **받을 기회가 없는 구간**이 있다.

**실례** — `M-CO-01` 기기 등록

```
등록 완료  →  곧바로 오프라인 현장 진입  →  사번 확인 불가(작업자 목록 미수신)
```

**규칙**

1. 스펙에 **「언제 받나」**를 적는다 — 「등록 직후」·「앱 시작 시」·「W/O 선택 시」
2. **받기 전에는 다음 화면으로 넘기지 않는다** — 수신 진행을 끝까지 보인다
3. 받지 못한 채 오프라인이면 **화면이 그렇게 말한다** — 「연결된 상태에서 한 번 실행해야 합니다」

— `M-CO-01` §5-7 · `P-CO-01` §5-6

**보강 — C-6의 「판정값 ↔ 표시값」 판별 기준** **[v0.9]**

C-6이 「판정에 쓰이는 값은 캐시하지 않는다」고 했는데 **무엇이 판정값인지**를 정하지 않았다.

> **기준: 틀렸을 때 무엇이 일어나는가.**

| 값 | 캐시 | 틀리면 |
| --- | :-: | --- |
| 작업자 재직 여부 | ✅ 해도 된다 | 퇴사자 사번으로 기록 — **어차피 사후 확인 대상**(도용 리스크 수용) |
| 작업자 **자격 유효기간** | ⛔ 안 된다 | **무자격자가 검사한다** |
| Lot Status(보류·Hold) | ⛔ 안 된다 | **보류 자재가 나간다**(결정 10) |

— `P-CO-01` §5-6

## §D. 입력 방식

### D-1. 스캔은 폼팩터가 아니라 입력 방식이다 ✅

**웹 화면에도 스캔이 필요하다** — `W-01-01`(관리웹)이 자재 LOT을 스캔한다. 스캔 규약은 모바일 전용이 아니라 **입력 방식 규약**으로 세 셸 공통이다.

### D-2. 스캔 입력 규약 ✅ **✓확정 2026-08-02** *(전제 미검증 — 아래)*

| 항목 | 규칙 |
| --- | --- |
| 포커스 | **항상 스캔 필드에 고정.** 벗어나면 입력이 유실된다 |
| 제출 | 종료 문자 수신 시 자동 제출 |
| 입력 후 | 필드 클리어 → 다음 스캔 즉시 가능 |
| 오류 시 | **필드를 비우되 포커스 유지** + 오류음 |
| 결과 | 등록 목록에 누적 표시 |

⚠ **전제 검증 필요**: 이 규약은 **BLE 스캐너가 HID 키보드 모드**임을 전제한다. 기종이 SDK 연동 방식이면 다시 짜야 한다 — **기종 미정** §H-6.

> **결정 기록(2026-08-02 사용자 확정)**: **조건부 확정**이다. 위 규약을 그대로 적용해 스캔 화면 16건을 쓰되, **스캐너 기종이 확정되면 전제를 재검토**한다. 기종이 전용 연동 방식이면 「포커스 고정 → 종료 문자 자동 제출」이 성립하지 않아 규약을 다시 짜야 한다. 기종 확정을 기다리며 확산을 멈추지 않기로 한 것이며, 재작업 위험은 **스캔 유형 16건의 입력 처리 부분에 한정**된다(필드·검증·액션은 영향 없음).

### D-3. 직접 입력 대체 경로 의무 ✅

**모든 스캔 화면에 수동 입력을 둔다.** 스캐너 배터리 소진·손상·미연결은 현장에서 흔하다. 이것이 없으면 작업이 멈춘다.

### D-4. 숫자 키패드 ✅ **✓확정 2026-08-02**

**규칙**: POP 수량 입력은 **화면 내장 키패드**를 쓴다. OS 터치 키보드에 의존하지 않는다 — 키오스크 창에서 화면을 덮고 제어가 어렵다.

- 키 **64×64**, 간격 12 → 블록 216×292
- `C`(전체 지움) · `←`(한 자 지움) · 빠른 입력(`＋10`·`＋100`)
- 포커스된 수량 필드에 연동

> **결정 기록(2026-08-02 사용자 확정)**: 운영체제 터치 키보드에 맡기는 대안을 검토한 뒤 **화면 내장**으로 확정했다. POP은 전체 화면 키오스크로 실행되므로 운영체제 키보드가 화면을 덮고 닫기 제어가 어렵다. 실질적으로 선택지가 없는 항목이다.

### D-5. 귀속 정보는 **세션이 아니다** — 화면이 현재 귀속 대상을 상시 보인다 ✅ **[v0.9 신설]**

설계검토 §3.3 — **서버가 사번 세션을 갖지 않는다.** 단말이 「현재 작업자」를 들고 **매 쓰기 요청에 헤더로 싣는다.**

```http
Authorization: Bearer <단말 토큰>       ← 인증
X-Worker-No: 900028                     ← 귀속. 인증 아님
```

| 요청 | 사번 |
| --- | :-: |
| 읽기(기준정보·조회) | 불요 — 단말 토큰만 |
| **쓰기(실적·검사·이동)** | **필수** — 없으면 서버가 거부 |

**⛔ 그래서 「언제 지우나」가 화면 문제가 된다.** 사번이 남아 있으면 **다음 사람이 그 사번으로 기록된다.**

**규칙**

1. **현재 귀속 대상을 항상 크게 보인다** — 도용 리스크를 수용한 설계에서 **화면이 할 수 있는 유일한 방어**다
2. **교대는 사람이 명시적으로 누른다** — 유휴 시간으로 자동 해제하지 않는다(작업 중 화면을 떠나는 일이 흔하다)
3. **교대 시 미전송 큐가 있으면 알린다** — ⛔ **큐의 사번을 바꾸지 않는다**(B-3 이력 불변)

⬜ **근무 종료·유휴 시 처리 규약이 없다** — §I 아님(설계 결정). — `P-CO-01` §5-4 · `M-CO-01` §3-2

## §E. 폼팩터 규격·표시

### E-1. POP 화면 예산 ✅ *(실측 검증 완료)*

```
768  전체
-64  헤더
-88  액션바 (핵심 버튼 72 + 여백)
────
616  본문  → 패딩 16×2 제외 실질 584
```

**⚠ 슬랙이 0이다.** `64+616+88 = 768` 정확. 검증 목업에서 테두리 1px×2만으로 오버플로가 났다. **스크롤바·OS 표시줄·업데이트 배너가 하나라도 끼면 깨진다** — 실기 확인 항목.

**⚠ 제약은 세로 행 수가 아니라 가로 폭이다.** 실측에서 좌단은 465/584로 119px 남았으나, **34자리 LOT 행이 597/599px(여유 2px)** 였다. → E-2.

### E-2. 긴 식별자 표시 규칙 ✅ **✓확정 2026-08-02** *(실측에서 발견)*

**규칙**: 구분문자 없는 긴 코드는 **저장은 원문, 표시는 분절 그룹핑**한다.

```
저장  0001234500000012002607310001230007        (34자리·MLOT #16)
표시  000123450 · 000001200 · 260731 · 000123 · 0007
      제품코드9    수량9        날짜6    공급사6  번호4
```

**이유**: 34자리를 붙여 쓰면 작업자가 실물 라벨과 화면을 **눈으로 대조할 수 없다.** 열 폭 산정도 이 규칙을 전제로 다시 한다.

> **결정 기록(2026-08-02 사용자 확정)**: 원문 그대로 붙여 쓰는 대안을 검토한 뒤 **표시만 분절**로 확정했다. 실측에서 이 줄이 599픽셀 중 597픽셀을 써 여유가 2픽셀이었고(E-1), 붙여 쓰면 실물 라벨과 눈으로 대조가 불가능하다. **저장값은 손대지 않으므로** 데이터 영향이 없다.
> **⚠ 분절 자릿수는 자재 로트 번호 체계에 종속**된다 — 다른 번호 체계에 그대로 쓰지 말고 각 체계의 자리 구성을 확인해 정한다.

| **화면 수준** 문제 (저장 충돌·**상태 잠김**·권한 없음·통신 실패) | **배너**(`AlertBanner`) |

> **⚠ 「저장 충돌」과 「상태 잠김」은 배너 위치는 같으나 문구와 다음 행동이 다르다** *(2026-08-03 신설 — 기준정보 API 스펙에서 도출)*
>
> | | 무엇인가 | 사용자의 다음 행동 | 응답 |
> | --- | --- | --- | --- |
> | **저장 충돌** | 내가 보는 사이 남이 고쳤다 | **다시 불러오면 풀린다** | `409` + 충돌 원인(B-1) |
> | **상태 잠김** | 확정·폐기된 것이라 고칠 수 없다 | **다시 불러와도 안 풀린다.** 새 Rev를 발행하거나 포기한다 | `400` + `code: STATE_LOCKED` |
>
> 배너에 「새로고침」만 제시하면 상태 잠김에서는 눌러도 같은 화면이 돌아온다. **잠긴 경우에는 그 상태에서 가능한 행위**(새 Rev 발행 등)를 안내한다.

> **결정 기록(2026-08-02 사용자 확정)**: 「전부 상단 배너로 통일」 대안을 검토한 뒤 **범위에 따라 나누기**로 확정했다. 전부 배너로 몰면 어느 입력란이 잘못됐는지 사용자가 찾아야 한다.
> **POP 제약**: POP은 세로 여유가 119픽셀뿐이라(E-1) 인라인 문구가 예산을 잠식한다. **POP에서도 위치 규칙은 같게 두되**, 문구를 짧게 쓰고 F-1의 사유 표시와 마찬가지로 길어지면 요구 시 표시한다. 위치 규칙 자체를 폼팩터마다 다르게 하면 세 셸이 갈라진다.
> **API 파급**: 오류 응답이 **필드 단위 오류와 화면 수준 오류를 구분**해 내려줘야 한다. 구분 없이 문자열 하나만 오면 화면이 위 표를 적용할 수 없다 — 횡단 규약에 반영한다.

### G-2. 미확정 코드 목록의 표시 ✅ **✓확정 2026-08-02**

**규칙**: 회신 대기로 선택지가 비어 있는 필드는 **필드를 감추지 않고, 비활성 + 사유를 표시**한다.

```
종합 판정  [ 선택지 준비 중 ]  ⓘ 판정유형 목록은 고객 회신 대기 중입니다
```

**해당**: `overall_judgment_code`(회신 E-3) · `management_level_code`·`location_type_code`·`quality_zone_code`(공통코드 미정) 등.

**이유**: 감추면 나중에 화면 구조가 바뀌고, 임의값을 넣으면 잘못된 데이터가 쌓인다.

> **결정 기록(2026-08-02 사용자 확정)**: 「선택지가 없으면 필드를 감춘다」 대안을 검토한 뒤 **비활성 + 사유 표시**로 확정했다. F-1(권한 없는 기능)·B-4(참조가 있어 코드를 못 고침)와 **같은 원리**다 — 「할 수 없다」는 감추지 않고 이유와 함께 보인다. 한 화면 안에서 규칙이 갈리지 않게 하려는 것이기도 하다.

### G-3. 비활성 사유는 「왜」가 아니라 **「어떻게 풀 것인가」**를 담는다 ✅ **[v0.4 신설]**

잠금의 근거가 **넷으로 갈렸는데 사용자에게는 넷 다 「회색 컨트롤」로 보인다.** 해결 방법이 다르므로 문구가 경로를 담아야 한다.

| 잠긴 이유 | 문구가 안내할 경로 |
| --- | --- |
| ERP 수신본 | 「ERP에서 수정한 뒤 재동기화하세요」 (+ `W-06-10` 링크) |
| 상태 = 확정 | 「신규 Rev를 발행하세요」 (+ 발행 버튼) |
| 참조가 있음(B-4) | 「사용 중지하고 새로 만드세요」 (+ 참조 건수) |
| 권한 없음 | 「관리자에게 권한을 요청하세요」 |

— `W-06-01` §9-1 · `W-06-11` §9-1

### G-4. 「필수」·「비연계」는 **기본값이 아니라 구조로** 표현한다 ✅ **[v0.4 신설]**

확정이 「끌 수 없다」·「연계하지 않는다」일 때 화면이 이를 **기본값 on/off로 구현하면 확정이 무너진다**(누군가 켜거나 끌 수 있으므로).

| 확정 | 화면 표현 |
| --- | --- |
| **필수**(예: 생산 실적 송신 — QA #35) | **비활성 컨트롤 + 확정 번호를 담은 사유** |
| **비연계**(예: 검사 결과 — QA #4) | **목록에서 제외** — 꺼진 상태로도 보이지 않게 |

⚠ F-1·G-2의 「감추지 않는다」의 **예외**이며, 예외인 이유는 **선택지가 아니라 결정 사항**이기 때문이다. — `W-06-12` §9-1

### G-5. 사용자가 바꿀 수 없는 것에는 **확정 번호를 문구에 넣는다** ✅ **[v0.4 신설]**

「생산 실적 송신은 필수입니다」보다 **「생산 실적 송신은 필수입니다(2026-07-04 확정 QA #35)」**가 낫다. 현장·고객이 「왜 못 바꾸나」를 물을 때 **추적 가능한 근거가 화면에 있어야** 재확인 요청이 정상 경로로 간다. 대상: 필수·비연계·차단처럼 **바꿀 수 없는 것 전부**. — `W-06-12` §9-3

### G-6. 회신 대기 화면의 표준 형태 ✅ **[v0.4 신설 — G-2의 화면 수준 확장]**

G-2는 「필드 하나가 선택지를 못 채울 때」인데, **목록 전체가 대기**인 화면이 있다(`W-06-04` 판정유형 E-3 · `W-06-10` 알람 유형 E1 · `W-CO-02` 권한 매트릭스 E-9).

1. **확정분과 대기분을 한 목록에 함께 보이고 표식으로 구분**한다 — 대기분을 감추면 「없는 것」으로 오해한다
2. **회신 전 임시 등록을 막지 않되 「재검토 대상」으로 표시**한다
3. **화면 머리에 대기 사유와 회신 번호를 명시**한다(E-3·E1·E-9)

⚠ **대기 범위를 좁게 적지 않는다** — 회신 E-3의 문구는 「판정 유형 **전체 목록**」이라 확정 4종 외에 더 나올 수 있다. 화면은 목록 길이를 가정하지 않는다. — `W-06-04` §9-1

### G-7. 「전사 고정 축」 코드의 추가에는 경고를 붙인다 ✅ **[v0.4 신설]**

값 하나를 늘리면 **화면 밖 규칙**(전사 집계·보고서·사업부 간 비교·전이도·물류 통제)이 따라 바뀌는 코드가 있다. **차단은 하지 않고 A-9의 ⓑ 경고 등급**으로 다룬다.

**대상**: 불량 대분류(외관/치수/기능/이물/기타 — 결정 12) · 판정유형(결정 10) · 창고유형 · 손실사유 — `W-06-03` §9-3 · `W-06-04` §9-3

### G-8. 선택 목록의 유효성 판정은 **서버가 한다** ✅ **[v0.4 신설]**

유효기간(`effective_from`/`to`)과 `is_active`가 **함께 있는 코드**를 선택 목록에 넣을지 판정하는 규칙.

1. **판정은 서버**가 하고 화면은 받은 목록을 그대로 그린다 — 화면마다 다르게 구현되는 것을 막는다
2. **과거 데이터 표시는 예외** — 이미 저장된 값은 만료·비활성이어도 **그대로 보이고 「(사용 중지됨)」 표식**을 붙인다

— `W-06-06` §9-2

⚠ **선택지가 0개인 상태가 있다** — Lot Status의 `Hold`는 도식상 **발신 전이가 없다**. 빈 드롭다운을 보이지 말고 **「이 LOT은 더 전이할 수 없습니다 — 불량 처리는 생산실행에서 합니다」**로 안내한다. — `W-03-02` §5-5

### G-9. **모르는 값**과 **없는 값**을 같은 모양으로 그리지 않는다 ✅ **[v0.9 신설]**

## §J. 승인 워크플로우 **[v0.5 신설]**

> **왜 신설하나** — 확대 2차 도메인 01에서 `approval_request_id`를 가진 테이블이 **셋**(`inbound_receipt` 무발주 · `inbound_variance` 입하 오류 · 그리고 `W-01-02` 한도승인 대상)이고, 결재 4테이블이 완전한 형태로 실재한다. 화면마다 승인을 다시 발명하면 갈린다.

### J-1. 승인은 4테이블 한 벌이고, **정의와 실행이 분리**돼 있다 ✅

| 계층 | 테이블 | 성격 |
| --- | --- | --- |
| **정의** | `app.approval_route` | 마스터 형(`is_active` — B-4) · 유형·사업부·**값 구간**별 결재선 |
| | `app.approval_route_step` | 부여·회수 형(B-6) · 단계별 승인자 |
| **실행** | `app.approval_request` | 요청 1건 · `version_no` 有 |
| | `app.approval_step` | 단계별 결재 기록 · **기록 전용** |

**규칙**: 승인 화면은 **정의를 읽기만** 한다. 결재선 등록·수정은 별도 화면 소관이다.

⬜ **결재선 정의 화면이 인벤토리 108건에 없다**(실측). 공통(CO) 또는 06 도메인 후보.

### J-2. 「한도」는 `min_value` / `max_value`가 정한다 ✅

```
approval_route.min_value / max_value   numeric(20,6)
ck_approval_route_range: max >= min (둘 다 있을 때)
```

**값 구간에 따라 결재선이 달라진다.** 소량이면 1단계, 대량이면 2단계 — `business_unit_id`로 사업부별 차등도 된다.

**규칙**: 화면은 **적용된 구간을 보여준다.** 승인자가 「왜 내가 결재선에 있는가」를 알 수 있어야 한다.

⬜ **무엇의 값인지 미정** — 수량인지 금액인지 컬럼명이 말하지 않는다.

### J-3. 요청 시점에 승인자를 **사람으로 확정**한다 ✅

```
approval_step.approver_id   bigint NOT NULL
```

`route_step.approver_type_code`가 **USER · ROLE · DEPARTMENT** 세 방식이어도, **요청이 만들어질 때 실제 사람으로 전개**된다. 「그 역할의 누구나」가 아니다.

**규칙**: 승인 대기 큐는 **로그인 사용자가 `approver_id`인 것**만 보인다. 역할 기반 필터가 아니다.

> ### ⛔ **J-3 미해결 — #72 회신과 부딪친다** *(2026-08-05 확대 5차)*
>
> **#72 회신(사용자 확정)**: 「승인 주체는 **담당부서 관리자**」 · 「명확히 고정된 것이 아니라 **관리자의 권한 설정으로 처리**」
>
> 「권한 설정으로 처리한다」 = `approver_type_code`가 **`ROLE` 또는 `DEPARTMENT`**다. 그런데 `approval_step`은 **사람만 받는다.**
>
> ```
> approval_route_step.approver_type_code = 'DEPARTMENT' → 품질부
>     → 품질부에 관리자가 3명이면 approval_step.approver_id 에 누구를 넣나  ⛔
> ```
>
> **② 후보 전원에게 단계 생성은 불가**하다 — `uq_approval_step UNIQUE(approval_request_id, step_no)`가 같은 단계에 둘을 못 넣는다. **③ 대리 결재 컬럼도 없다.**
>
> **권고 — J-3을 다음으로 고쳐 쓴다**: 「**상신 시 규칙으로 한 사람을 골라 `approver_id`에 넣는다**」 + **부재 시 경로를 함께 정한다**(승인자 교체는 `approval_step`이 기록 전용이라 감사상 문제가 된다).
>
> **J-3을 세운 근거가 「데이터가 사람만 받는다」였고 업무 확정은 「역할로 처리한다」다. 둘 중 하나가 바뀌어야 한다.** — §I-28 · `W-01-06` §5-2 · `W-01-12` §5-3

### J-4. 사유는 필수다 ✅

```
approval_request.reason   text NOT NULL
```

**사유 없는 승인 요청이 데이터에 들어갈 수 없다.** 요청 화면이 반드시 받는다.

### J-5. 승인 화면은 **「승인하면 무엇이 일어나는가」**를 명시한다 ✅

특히 **일어나지 않는 것**을 적는다.

> `W-01-02` 실례 — 긴급 IQC 생략을 승인해도 **ERP G/R 전표는 나가지 않는다**(「합격품 한정」이 자동 제외). 이것을 모르고 누르면 승인자는 「입고 처리했다」고 오해하고 **사후에 회계가 어긋난다.**

**규칙**: 승인 버튼 위에 **결과 구획**을 둔다. 상태 전이·후속 연계·**제외되는 것**을 항목으로 적는다.

### J-6. 결재는 되돌릴 수 없다 ✅

`approval_step`이 기록 전용이다(감사 컬럼 `created_at`뿐 · `version_no` 없음).

**규칙**: 화면에 「수정」·「취소」를 두지 않는다. 번복은 **새 요청**이다. — B-3(이력 불변)의 승인 판.

— `W-01-02` §9 · `M-01-01` §5-5 · `M-01-06` §5-4 · `W-01-03` §5-3

### J-7. **상태 전이 화면**은 「이 전이가 무엇을 막고 무엇을 푸는지」를 확정 전에 보인다 ✅ **[v0.9 신설 · J-5의 전이 화면 판]**

J-5가 「승인하면 무엇이 일어나는가」를 요구했다. **전이 화면은 승인이 아니지만 파급이 더 크다.**

결정 10이 Lot Status를 **차단의 단일 지점**으로 만들었으므로, 버튼 하나가 **창고·출하 전체의 가부**를 바꾼다.

## §K. 출력물 발행·재발행 **[v0.5 신설]**

> **왜 신설하나** — `app.document_issue_log`가 라벨·인식표·QR·성적서를 **한 테이블로** 다루고, 두 제약이 재발행 규칙을 데이터로 강제한다. 라벨 화면이 도메인 01·02에 여럿(`P-01-01`·`P-01-02`·`P-02-05`·`P-02-07`·`P-02-09`)이라 규약이 먼저 서야 한다.

### K-1. 발행은 **회차로 쌓고** 이전 것을 지우지 않는다 ✅

```
uq_document_issue_log       UNIQUE (document_type_code, target_type_code, target_id, issue_seq)
issue_seq                   integer NOT NULL DEFAULT 1 CHECK (issue_seq > 0)   -- 1=최초, 2+=재발행
```

**규칙**: 재발행은 수정이 아니라 **새 기록**이다. 회차가 오르고 이전 회차는 남는다.

### K-2. ★ 재발행에는 **사유가 필수**다 ✅

```
ck_document_reissue_reason  CHECK (issue_seq = 1 OR reissue_reason_code IS NOT NULL)
```

**DB가 강제한다.** 화면이 사유를 받지 않으면 저장이 실패한다.

**왜** — 라벨이 여러 장 돌아다니면 같은 LOT이 두 곳에서 스캔된다. 재발행 이력이 있어야 추적된다.

> ⚠ **재발행이 정상 경로인 화면이 있다** *(v0.6 보완)*. `P-02-09`(포장 라벨·인식표 재출력)는 **포장 후 겉면에 붙일 것을 다시 찍는 것이 본래 목적**이라 `issue_seq`가 항상 2 이상이다.
>
> **사유 값 목록에 「정상 업무 흐름」(포장 등)이 있어야 한다.** 훼손·분실만 있으면 전부 훼손으로 기록되어 **재발행 통계가 무의미해진다.** — `P-02-09` §5-1

### K-3. 발행 기록에 **단말과 프린터**를 남긴다 ✅

```
terminal_id     FK -> mdm.terminal
printer_name    varchar(100)
```

「어디서 몇 번째로 찍었는가」가 추적의 단위다.

### K-4. 인쇄는 트랜잭션 밖이다 ✅

B-8 규칙 2의 적용. **프린터가 죽어도 LOT은 생성되고 기록은 남는다.** 인쇄 실패로 발번을 롤백하면 같은 자재에 발번을 다시 해야 하고, 그사이 다른 단말이 번호를 가져갈 수 있다.

**규칙**: 프린터 상태를 **화면 머리에 상시 표시**한다. 인쇄가 안 될 때 사용자가 가장 먼저 보는 곳이다.

### K-5. 라벨은 **서버가 그린다** ✅ *(결정 18)*

POP은 이미지를 받아 프린터로 보낼 뿐이다. 클라이언트가 레이아웃을 그리지 않으므로 **단말마다 라벨이 달라지지 않는다.**

### K-6. 물리적으로 유통되는 출력물은 **회차를 인쇄면에도** 넣는다 ✅

데이터에만 회차가 있으면 현장에서 몇 번째 라벨인지 구분할 수 없다.

⬜ **이전 라벨의 무효화 규칙이 없다** — 3회차를 찍어도 1·2회차가 물리적으로 남아 스캔된다. 회차 인쇄가 최소 대안이고, 스캔 시 회차 검증은 별도 결정.

— `P-01-01` §9

## §L. 조회·집계 **[v0.8 신설]**

> **왜 신설하나** — 조회 화면은 앞 차수에도 있었으나(`W-01-09`·`M-01-04`) **집계가 주 기능인 화면은 확대 5차가 처음**이다(`W-02-08`·`W-01-07`). 조회 화면은 인벤토리 108건 중 상당수이고, 규약 없이 만들면 **같은 수치가 화면마다 다르게 나온다.**

### L-1. 요약은 **필터 전체**, 목록은 **페이지** ✅

```
요약 카드  →  필터 조건 전체의 집계   (128건 전부)
목록       →  페이지네이션            (1–50)
```

**화면이 목록을 받아 세면 안 된다** — 50건만 받고 「전체 128」을 낼 수 없다. **응답이 요약과 목록을 나눠 담는다.**

⚠ **둘을 같은 트랜잭션에서 낸다.** 아니면 기준 시각을 나눠 표시해야 한다. — `W-02-08` §5-1 ①

### L-2. 파생 값은 **서버가 계산한다** ✅

`M-01-04` §5-4(GENERATED 컬럼을 화면이 다시 계산하지 않는다)의 확장. **DB에 GENERATED가 없어도** 달성률·지연 같은 파생은 서버가 낸다.

**왜** — 반올림·0 나눗셈·기준 시각이 화면마다 갈린다. 지시 0인 W/O의 달성률을 한 화면은 `0%`, 다른 화면은 `—`로 보이면 같은 데이터가 다르게 읽힌다.

⚠ **같은 수치를 두 화면이 보이면 계산은 한 곳에서 한다** — 조회(`W-02-08`)의 달성률과 마감(`W-02-05`)의 3분류 판정이 다르면 신뢰를 잃는다. **파생 규칙의 소유 화면을 스펙이 지정**한다. — `W-02-08` §5-1 ②·§5-2

### L-3. **기간 필터를 필수로 한다** — 파티션 테이블은 **파티션 키를 강제** ✅

무제한 조회를 허용하면 원장이 누적된 뒤 화면이 멎는다. 기본값을 **최근 1개월**로 두고 비울 수 없게 한다.

⚠ **파티션 테이블에서는 성능이 아니라 가능/불가능의 문제다.**

| 테이블 | 파티션 | 강제할 필터 |
| --- | --- | --- |
| `inventory.inventory_transaction` | `PARTITION BY RANGE (business_date)` | **`business_date` 범위** |
| `audit.audit_event` | 파티션(`audit_event_default` 실재) | 기간 |

**파티션 키 없이 조회하면 전 파티션을 스캔한다.** — `W-02-08` §5-1 ③ · `W-01-07` §5-4

### L-4. **정렬 키를 제한한다** ✅

「아무 열이나 정렬」을 열어 두면 인덱스 없는 열에서 전체 정렬이 돈다. **정렬 가능한 열을 스펙이 지정**한다.

⚠ **파생 값 정렬은 비싸다** — 허용하되 기간이 좁을 때만. — `W-02-08` §5-1 ④

### L-5. **기준 시각을 항상 보인다** ✅

집계는 조회 시점의 스냅샷이다. **C-6(오프라인 조회는 기준 시각 표시)의 관리웹 판**이다 — 오프라인이 아니어도 **집계는 이미 과거**다.

```
기준 08-05 09:12   [ 새로고침 ]
```

— `W-02-08` §5-1 ⑤ · `W-01-07` §5-3

### L-6. **자동 갱신을 두지 않는다** — 대시보드와 구분 ✅

관리자 조회 화면에 폴링을 두면 서버 부하가 사용자 수만큼 곱해진다. **명시적 새로고침**만 둔다.

⚠ **`W-CO-03`(알람 대시보드)은 다르다** — 그쪽은 실시간이 요건이다. **화면 성격에 따라 갈린다.** — `W-02-08` §5-1 ⑥

### L-7. **묶어도 되는 축 / 안 되는 축**을 스펙이 지정한다 ✅

`inventory_balance`는 유일축이 **11개**인데(A-7) 품목별로 묶으면 나머지가 사라진다.

| 축 | 묶어도 되나 |
| --- | :-: |
| 품질상태 | ✅ — 「가용/보류」 열로 이미 갈린다 |
| **소유(`ownership_type_code`)** | ⛔ **안 된다** — 자사 재고와 고객 지급품을 더하면 오독 |

**집계 화면마다 이 표를 §5에 적는다.** — `W-01-07` §5-1

### L-8. **「판정 불가」를 「정상」으로 보이지 않는다** ✅

`work_order.planned_end_at`이 nullable이라 **지연을 판정할 수 없는 건**이 생긴다. 빈칸으로 두면 「지연 아님」으로 읽힌다.

```
지연 판정 가능 · 경과   →  ⚠ 지연
지연 판정 가능 · 미경과 →  (빈칸)
planned_end_at 없음     →  —   ← 「판정 불가」이지 「정상」이 아니다
```

**A-7의 `(전체)` 표기와 같은 원리를 파생 값에도 적용**한다. 요약 카드의 「지연 9」가 실제로는 더 많을 수 있다는 사실이 화면에 드러나야 한다. — `W-02-08` §5-3

### L-9. **다계층 조회는 「한 화면」이지 「한 표」가 아니다** ✅ **[v0.9 신설 · L-1 확장]**

결정 01의 검사 3계층이 실례다. **층마다 건수의 자릿수가 다르다**(실측 추정):

```
의뢰      412 건
결과      450 건        (재검 포함)
측정치    135,000 건    (검사당 항목 10 × 샘플 30)
```

**측정치를 목록에 join하면 412행이 135,000행이 된다.**

**규칙**: **L-1을 층마다 따로 적용**한다.

| 층 | 화면 | 페이지 |
| --- | --- | --- |
| 상위 2층 | 한 표(하위를 들여쓰기) | ✅ 50건 |
| **가장 깊은 층** | **드로어에 요약만** | 전체는 **별도 페이지** |

— `W-03-05` §5-1

### L-10. **정책이 미정인 「의심스러운 데이터」**는 섞지도 지우지도 않는다 — 표시하고 **분리 보기**를 준다 ✅ **[v0.9 신설]**

실례 — 검교정 만료 장비로 측정한 결과. WF03 예외 **E-9 ①**이 「소급 무효화 여부 **[확인]**」로 미정이다.

| 선택 | 문제 |
| --- | --- |
| 그냥 섞는다 | ⛔ **잘못된 집계** |
| 자동 제외한다 | ⛔ **없는 정책을 화면이 만든다** |
| ✅ **경고 + 분리 보기** | 사람이 판단한다 |

```
⚠ 검교정 만료 장비로 측정된 8건이 포함돼 있습니다   [ 분리해 보기 ]
```

**`W-01-07` §5-5(유효기간 경과는 표시만)와 같은 형태**이고 **L-8의 집계 화면 판**이다. **A-9 ⓒ(표시만) 등급.**

⚠ **판별 데이터가 있는지 먼저 확인한다** — 이 건은 있었다(`inspection_measurement.inspection_equipment_id` + `mdm.equipment.calibration_due_date` + `measured_at`). 없으면 경고 자체가 불가능하다. — `W-03-05` §5-6

**보강 — 같은 낱말을 쓰는 두 화면이 다른 수를 보이면 양쪽에 정의를 적는다** **[v0.9 · L-2 보강]**

| 화면 | 낱말 | 정의 |
| --- | --- | --- |
| `W-03-05` | **불량률** | **검사 수량** 기준 |
| `W-02-08` | **수율** | **생산 수량** 기준 · **손실 분리**(QA #13 — 퍼징·시작불량은 불량이 아니다) |
