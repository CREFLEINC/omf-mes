## §A. 데이터 제약 → UI 규칙

물리 모델의 제약을 화면이 어떻게 표현할지. **제약은 이미 정해져 있으므로 우리가 정하는 것은 표현 방식뿐이다.**

### A-1. 유일 제약 검사 시점 ✅ **✓확정 2026-08-02**

**규칙**: 코드 필드는 **blur 시 선검사 + 저장 시 서버 재검증**. 선검사만으로 확정하지 않는다(경합 때문).

**근거**: `uq_warehouse(plant_id, warehouse_code)` · `uq_location(warehouse_id, location_code)` · `trace.lot UNIQUE(plant_id, lot_no)` 등 유일키가 다수. — `W-06-07` §6

**문구**: 「같은 공장에 이미 있는 창고코드입니다」처럼 **유일키의 범위를 문구에 담는다**(단순 「중복입니다」 금지 — 어느 범위에서 중복인지 모르면 사용자가 고칠 수 없다).

> **결정 기록(2026-08-02 사용자 확정)**: 두 검사 중 하나만 두는 안을 검토한 뒤 **양쪽 다 유지**로 확정했다. 선검사만 두면 두 사람이 동시에 같은 코드를 넣을 때 뚫리고, 서버 검증만 두면 사용자가 폼을 다 채운 뒤에야 실패를 안다. 실질적으로 선택지가 없는 항목이다.
> **API 파급**: 중복 응답은 **어느 유일키 범위에서 중복인지**를 담아야 한다. 범위 없이 「중복」만 오면 화면이 위 문구를 만들 수 없다 — 횡단 규약에 반영한다.

### A-2. 조건부 필수·짝 제약의 표시 ✅

**규칙**: `CHECK` 제약을 **사용자 문구로 옮기고, 관련 필드를 함께 표시**한다.

| 제약 유형 | 예 | 표시 |
| --- | --- | --- |
| 조건부 필수 | `ck_external_warehouse_partner` — 외부창고면 거래처 필수 | 토글 ON 시 해당 필드에 필수 표시 전환 |
| 짝 제약 | `ck_location_capacity` — 수용량과 단위는 함께 | **두 필드에 동시** 인라인 오류 |
| 합계 제약 | `ck_inspection_result_qty` — 합격+불합격+보류 = 검사수량 | A-3 |

### A-3. 합계 제약의 UI 표현 ✅

**규칙**: `CHECK(a+b+c = total)` 류는 **실시간 합계·잔여를 표시**하고 **불일치 상태에서 확정 버튼을 비활성**한다.

**⚠ 자동 계산은 규칙이 확정된 뒤에만 얹는다.** 「합격만 넣으면 나머지 자동」은 **어느 칸을 자동으로 할지**가 정해져야 가능하다 — 지금은 미정(`W-01-01` §8-4).

### A-4. 감사 컬럼·`version_no`는 화면에 노출하지 않는다 ✅ **[2026-08-03 단서 추가]**

`created_at`·`created_by`·`updated_at`·`updated_by`·`version_no`는 시스템이 채운다. **필드표에 넣지 않고 폼에도 띄우지 않는다.** 단 `version_no`가 있으면 **B-1을 반드시 구현**한다.

> **확정(2026-08-03 사용자 확정)**: 이 조항은 **화면 표시 규칙**이다 — 전송은 막지 않는다. 원문이 「`version_no`가 있으면 B-1(낙관적 잠금)을 반드시 구현한다」를 함께 말하는데, **전송까지 금지하면 B-1이 성립할 수 없다.** **단서**: 낙관적 잠금 토큰은 **헤더로 전송**하되(`ETag` 응답 → `If-Match` 요청) **화면에 표시하지 않는다.** 금지되는 것은 필드표·폼·목록 열에 드러나는 것이지 전송 자체가 아니다.
> 현재 OpenAPI가 이미 그렇게 돼 있다(응답에는 `ETag` 헤더로 · 요청에는 `If-Match` 헤더로 전송하며, `version_no`를 본문 필드로 싣는 스키마는 없다) — **조항이 구현을 따라가는 정정**이다. *(실측 카운트는 API가 커지면서 낡으므로 계약에는 성질만 남긴다.)*

### A-5. 순서 컬럼의 재배치는 서버가 한 트랜잭션으로 한다 ✅ **[v0.4 신설 · 2026-08-03 정정]**

**규칙**: `UNIQUE` 제약이 걸린 순서 컬럼을 화면에서 맞바꾸면 **중간 상태가 반드시 제약을 위반**한다(10↔20을 바꾸려면 잠깐 중복이 생긴다). **화면은 최종 순서만 보내고, 서버가 일괄 갱신**한다.

**해당**(실측 2곳): `planning.routing_operation.operation_seq` · `quality.inspection_item_spec.sequence_no` — `W-06-01` §8-8

> ⚠ **3번째 후보 — `app.approval_route_step.step_no`** *(2026-08-04 확대 2차에서 발견)*. `UNIQUE(approval_route_id, step_no)`가 실재한다(실측). **결재선 단계 순서를 사용자가 바꾸는 화면이 생기면 A-5 대상**이다. 지금은 **결재선 정의 화면이 인벤토리 108건에 없어**(J-1 ⬜) 목록에 넣지 않고 후보로만 둔다. — `W-01-02` §9-A

> **⚠ 2026-08-03 정정 — 대상은 4곳이 아니라 2곳이다.** API 설계 과정에서 두 곳이 더 빠졌다는 것이 드러났다. ① `mdm.code_value.display_order`는 **유일 제약이 없다**(`integer NOT NULL DEFAULT 0` — 실측, 중복이 허용된다) — 중간 상태가 제약을 위반하지 않으므로 전체 치환의 이유가 성립하지 않는다(행마다 개별 갱신하면 된다). ② `planning.bom_component.sequence_no`는 **ERP 원본이라 MES가 재배치하지 않는다** — 편집 가능한 열은 확장 4열뿐이라 순번 자체가 이 API의 대상이 아니다(행 단위 PUT — `06-API-요구서.md` §3-6·§4-1이 확정). `ds-gap.md` **G-7**(행 순서 UI가 필요한 곳)과 혼동한 것이었다 — **UI가 필요한 곳과 서버 트랜잭션이 필요한 곳은 다르다.** G-7은 「사용자가 순서를 바꿀 수 있는 표」전부를 세고, A-5는 그중 「바꾸는 중간 상태가 DB 유일 제약을 위반하고 MES가 직접 재배치하는 것」만 센다. 두 집합이 겹치지만 같지 않다.

**조항 2건을 더한다(2026-08-03 · API 설계 과정에서 드러남)**

1. **전체 치환은 행 교체가 아니다** — 서버는 기존 행을 유지하며 순서만 갱신한다. `routing_operation` 참조가 넷이고 `production.work_order.routing_operation_id`는 `NOT NULL`이라 `DELETE`+`INSERT`로 구현하면 진행 중 작업지시가 무너진다.
2. **순서 표시는 서버 저장 키가 아니라 목록 내 위치로 매긴다.** 채번 방식(연번/간격)은 데이터 모델링 재량이며, 화면이 저장 키를 보여주지 않으면 채번이 바뀌어도 화면이 흔들리지 않는다.

### A-6. 「하나만 참」 부분 유일 인덱스는 전환도 서버가 한다 ✅ **[v0.4 신설]**

**규칙**: `CREATE UNIQUE INDEX ... WHERE <조건>` 형태는 **동시에 둘을 막을 뿐 자동 전환을 해 주지 않는다.** 화면이 「기존 해제 → 새것 설정」 2회 호출하면 **그 사이에 0개인 상태**가 생긴다. **단일 액션으로 노출하고 서버가 한 트랜잭션으로** 처리한다.

**해당**: `uq_bom_default ON planning.bom (parent_item_id) WHERE is_default` — `W-06-05` §9-3

### A-7. 부분 유일 인덱스(`COALESCE`)의 표기·오류 문구 ✅ **[v0.4 신설]**

**규칙**: `COALESCE(col, 0)`으로 NULL을 접어 유일 판정하는 인덱스에서 화면은

1. **빈 축을 `(전체)`로 표기**한다 — 「없음」이 아니라 「제한 없음」이라는 뜻이다. 빈칸으로 두면 오해한다
2. **중복 오류 문구에 접힘 규칙을 담는다**(A-1의 「유일키 범위를 문구에」를 이 형태로 확장)

**해당**(실측 9곳): `uq_user_data_scope` · `uq_item_external_code` · `uq_worker_qualification` · `uq_lot_external_identifier` · `uq_inventory_balance_dim` · `uq_putaway_rule` · `uq_shipment_lot_allocation` · `uq_operation_policy` · `uq_numbering_rule` — `W-CO-02` §9-2

### A-8. 수치 컬럼의 **저장 단위**를 계약이 못박는다 ✅ **[v0.4 신설]**

**규칙**: 비율·수량·퍼센트가 섞이는 컬럼은 **저장 단위와 표시 단위를 함께 명시**하고, 입력란에 단위를 표시한다.

| 컬럼 | 저장 | 표시 |
| --- | --- | --- |
| `bom_component.scrap_rate` | **비율 0~1**(`CHECK BETWEEN 0 AND 1`) | `%` — **100배 변환** |

### A-9. DB가 막지 않는 검증은 **등급을 나눠** 화면이 진다 ✅ **[v0.4 신설]**

**「DB 제약이 없다고 규칙이 없는 게 아니다」**(`M-01-02` §4-1). 확대 1차에서만 **10건 이상**이 나왔다. 화면이 지는 검증을 **세 등급**으로 나눈다.

### A-10. 다형 참조는 **유형 코드 ↔ 대상 테이블 대응표**를 계약이 정한다 ✅ **[v0.5 신설]**

`{X}_type_code` + `{X}_id` 형태로 **여러 테이블 중 하나를 가리키는** 컬럼 쌍이 있다. **FK가 없다** — DB가 무결성을 보장하지 않는다.

**해당(실측 5곳)** — 확대 2차 도메인 01에서만 다섯이다.

| 테이블 | 컬럼 쌍 | 무엇을 가리키나 |
| --- | --- | --- |
| `app.approval_request` | `target_type_code` + `target_id` | 승인 대상 (LOT·입하·입하오류 …) |
| `audit.audit_event` | `target_type_code` + `target_id` | 변경 이력 대상 — **#68이 요청 중** |
| `logistics.goods_receipt` | `source_document_type_code` + `source_document_id` | 입고의 원천 문서 |
| `app.document_issue_log` | `target_type_code` + `target_id` | 발행 대상 (+ `lot_id` FK **병존**) |
| `trace.lot` | `source_type_code` + `source_id` | LOT의 원천 (입하·생산 …) |

**규칙**

1. **유형 코드와 대상 테이블의 대응표를 계약이 정한다.** 규약이 없으면 서버와 화면이 각자 해석해 갈린다
2. 화면은 **대응표에 없는 유형 코드를 만나면 원본 코드를 그대로 보이고 링크를 만들지 않는다** — G-2(미확정 코드)와 같은 처리
3. **다형 참조와 진짜 FK가 병존**하면 **둘이 같은 대상을 가리키는지 먼저 확인한다** — 같으면 FK 쪽을 쓰고, **다르면 `{X}_type_code`로 판정한다** ⚠ *(v0.6 보완)*
4. **한 화면이 여러 대상 유형을 다루면 대상마다 판정한다** — 일괄 규칙을 적용하면 잘못 기록된다 ⚠ *(v0.6 신설)*

> ⚠ **v0.6 보완의 근거** — `app.document_issue_log`가 `target_type_code`+`target_id`와 `lot_id` FK를 함께 갖는데 **화면에 따라 둘이 갈린다.**

> | 화면 | `target_id` | `lot_id` |
> | --- | --- | --- |
> | `P-01-01`·`P-02-07` 라벨 | LOT | **같은 값** |

| 규칙 | 내용 | 상태 |
| --- | --- | --- |
| 물리 삭제 금지 | `is_active = false`로만 처리. FK 참조가 걸려 있다 | ✅ |

| 변경 이력 | REQ-PR-0021 「변경 이력 필수」인데 **범용 이력 테이블이 확인되지 않았다** | ⬜ 데이터 확인 후 `[docs→데이터모델]` |

**코드 필드 수정 — 확정 규칙**

- 저장된 코드는 **그 코드를 참조하는 레코드가 하나도 없을 때만** 수정할 수 있다
- 참조가 하나라도 있으면 **코드 입력란을 비활성**하고, 이름·속성 등 나머지 필드만 편집한다
- 비활성 사유를 함께 표시한다 — F-1·G-1과 같은 방식(「이 창고를 참조하는 자재 로트가 12건 있어 코드를 바꿀 수 없습니다」)
- 잘못 만든 코드는 **`is_active = false`로 내리고 새로 만든다**

> **결정 기록(2026-08-02 사용자 확정)**: 세 안을 검토했다. **(가)** 코드는 생성 후 수정 불가 — 참조와 부착 라벨은 안전하나 오타 하나를 못 고친다. **(나)** 수정 허용하되 라벨 재발행 대상을 함께 표시 — 요구사항 문구는 만족하나 이미 붙은 라벨을 회수·재부착하는 절차가 없다. **(다) 참조 건수 0일 때만 허용 — 확정.** 실수 직후에는 고칠 수 있고 운영 중에는 잠기므로, REQ-PR-0021 「전체 수정 가능」을 정면으로 어기지 않으면서 참조 무결성과 부착 라벨 문제를 둘 다 피한다.
> **감수하는 비용**: 화면이 참조 건수를 조회해야 하고, 사용자에게 「왜 어떤 때만 되는가」를 설명해야 한다. 그래서 사유 표시가 선택이 아니라 필수다.
> **API 파급**: 마스터 상세 조회 응답에 **참조 건수(또는 수정 가능 여부와 그 사유)** 가 포함돼야 한다. 화면이 별도 호출로 세면 화면마다 다르게 구현된다 — 횡단 규약에 반영한다.

**⚠ 참조 건수를 셀 수 없는 대상이 있다 [v0.4 신설]**

「참조 0일 때만」은 **참조를 셀 수 있을 때만 성립**한다. 물리 모델에는 **셀 수 없는 참조가 두 형태** 있다(실측).

| 형태 | 예 | 규칙 |
| --- | --- | --- |
| **의도적 비-FK** | `created_by`·`updated_by`·`performed_by`(대량 적재 성능을 위해 **FK를 걸지 않았다** — SQL 210~211 주석) | 셀 수 없음 |

**규칙**: 마스터별로 **「참조 건수 산출 가능 여부」를 먼저 판정**하고, 불가면 **코드 수정을 무조건 잠근다**(참조 0을 확인할 수 없으므로). — `W-CO-02` §9-4 · `W-06-04` §9-2

### B-8. 트랜잭션의 경계 — **외부 호출은 밖, outbox 적재까지가 안** ✅ **[v0.5 신설]**

한 확정이 여러 엔티티를 움직일 때 **어디까지가 한 트랜잭션인가**를 정한다.

**규칙 1 — 업무 엔티티는 전부 안이다.** 부분 성공을 만들지 않는다.

`W-01-10` 입고 확정의 실측 예 — 확정 한 번이 다섯을 움직인다.

```
┌─ 한 트랜잭션 ────────────────────────────────────┐
│ ① goods_receipt + line        입고 전표          │
│ ② trace.lot.status_code       Hold → 가용        │
│ ③ inventory_transaction+line  수불원장           │
│ ④ inventory_balance           가용 수량          │
│ ⑤ integration_message         ERP 메시지 **적재** │
└──────────────────────────────────────────────────┘
                              ↓ 별도 워커
                        ERP 실제 전송
```

**규칙 2 — ★ 외부 시스템·장치 호출은 트랜잭션 밖이다.** ERP·프린터·OCR 같은 상대를 트랜잭션 안에서 부르면, 상대가 느릴 때 DB가 잡히고 **상대가 실패할 때 우리 업무까지 롤백된다.**

**outbox에 적재하는 것까지가 안이고 전송은 밖이다.** C-4가 정한 `integration_message`가 그 구조다(`available_at`·`locked_at`·`locked_by`·`retry_count`).

**규칙 3 — 「즉시」는 전송 시도의 즉시성이지 트랜잭션 포함이 아니다.** 확정 기록의 「건별 즉시」(✓확정 QA #1)를 동기 호출로 읽지 않는다. `available_at`을 현재로 두면 워커가 곧바로 집어간다.

**규칙 4 — 화면은 「무엇이 아직 안 됐는가」를 말한다.** 확정 직후 상대 시스템에 없을 수 있다. 「완료」라고만 하면 사용자가 상대를 보고 혼란스러워한다.

**규칙 5 — 경로마다 결과가 다르면 결과 안내도 달라진다.** 한도승인 건은 ERP 송신이 아예 없다(G/R 합격품 한정). 같은 화면이 같은 안내를 보이면 오해한다.

**규칙 6 — 외부 호출 실패는 업무 기록을 무효화하지 않는다.** 프린터가 죽어도 LOT은 생성되고, 재발행으로 푼다(K-1).

— `M-01-01` §5-4 · `W-01-03` §5-4 · `W-01-10` §5-4·§9 · `P-01-01` §5-2

### B-9. 선행 화면이 만드는 객체가 `NOT NULL`이면 **의존을 스펙이 명시한다** ✅ **[v0.6 신설]**

화면 A가 만든 것을 화면 B가 `NOT NULL`로 참조하면, **A 없이는 B가 성립하지 않는다.** 스펙이 이 의존을 적지 않으면 A가 빠졌을 때 B가 조용히 깨진다.

**판별** — 참조 컬럼의 nullability가 의존의 강도를 말한다.

| 참조 | 뜻 | 예 |
| --- | --- | --- |
| **nullable** | 선행 없이도 성립 — 기록만 약해진다 | `material_consumption.work_session_id` → `P-02-03`은 세션 없이도 투입 기록 |
| **`NOT NULL`** | **선행이 필수** — 없으면 진입 자체가 막힌다 | `work_session_event.work_session_id` → `P-02-10`은 세션 없이 불가 |

**규칙**: 스펙 §5에 **「이 화면이 무엇을 전제하는가」**를 적고, 전제가 미충족일 때의 화면 동작(차단·경고·대안 경로)을 §6에 적는다.

> ⚠ **실례** — `P-02-01`(작업 시작)이 **#67로 보류**되어 세션을 여는 화면이 3차에 없다. `P-02-03`은 nullable이라 돌지만 **`P-02-10`은 진입이 막힌다.** — `P-02-03` §8-5 · `P-02-10` §5-2

## §C. 오프라인·동기화 (POP · 모바일)

### C-1. 오프라인 입력 규약 ✅ **✓확정 2026-08-02**

**근거가 데이터 모델에 이미 박혀 있다** — `production_result`·`inspection_result` 양쪽에 `idempotency_key varchar(150) NOT NULL UNIQUE`.

**규칙**:

1. **`idempotency_key`는 클라이언트가 생성**해 outbox에 담는다. 재전송 시 서버가 중복을 흡수한다
2. **로컬 저장 후 즉시 성공 피드백** — 통신을 기다리지 않는다
3. **`occurred_at`(발생) 과 `recorded_at`(서버 수신)을 분리** — 오프라인 지연이 실적 시각을 왜곡하지 않는다
4. **연결 상태와 미동기 건수를 상시 표시** (결정 16 POP 요건)
5. 재전송은 같은 키로 — **사용자에게 중복 저장으로 보이지 않아야 한다**

> **결정 기록(2026-08-02 사용자 확정)**: 「전송 대기로 구분 표시하고 서버가 받으면 성공으로 바꾼다」 대안을 검토한 뒤 **즉시 성공 표시 + 미전송 건수 상시 노출**로 확정했다. 작업자가 통신을 기다리지 않는 것을 우선했다. 다만 **미전송 건수 표시가 이 결정의 전제**다 — 그것이 없으면 서버에 도달하지 않은 사실을 알 방법이 사라지므로, 헤더 표시는 선택 사항이 아니라 필수 요건이다.

### C-2. 오프라인 유일성 판정 ✅ **✓확정 2026-08-02**

**규칙**: `UNIQUE` 제약은 **서버만 확정 판정할 수 있다.**

- 로컬은 **큐 내 중복만** 선검사
- 서버가 거부하면 **해당 건만** 오류 목록으로 되돌린다
- **전체 롤백 금지** — 40건 스캔 중 1건 중복으로 39건을 버리면 현장이 마비된다

— `M-01-02` §5-3

> **결정 기록(2026-08-02 사용자 확정)**: 「한 건이라도 거부되면 묶음 전체를 취소」 대안을 검토한 뒤 **거부 건만 되돌리기**로 확정했다. 일부만 반영된 상태가 남아 확인이 필요해지는 비용보다, 스캔 작업을 처음부터 다시 하지 않는 이점을 택했다. **따라서 오류 목록 화면이 필수 요건이 된다** — 무엇이 되돌아왔는지 보이지 않으면 부분 반영 상태를 수습할 수 없다.

### C-3. 연속 작업의 완료 모델 ✅

**규칙**: 스캔·실적처럼 반복되는 작업은 **건별 저장 + 마지막 일괄 완료**. 건마다 화면을 전환하지 않는다.

### C-4. outbox 규약은 **서버 측에도 동형으로 있다 — 한 벌로 쓴다** ✅ **[v0.4 신설]**

C-1이 POP·모바일 오프라인을 위해 세운 것이 `integration.integration_message`에 **그대로 구현돼 있다**(실측).

| C-1 규약 | 서버 측 컬럼 |
| --- | --- |
| 클라이언트 생성 멱등 키 | `message_key varchar(150) NOT NULL UNIQUE` |
| 재전송은 같은 키로 | 동 — **재처리가 중복 전송이 아님을 화면이 문구로 보장** |
| 미동기 건수 상시 표시 | `status_code` 집계 → `StatCard` 요약 |
| — *(서버 고유)* | `available_at` 백오프 · `retry_count` · `locked_at`·`locked_by` 리스 |

**규칙**: **같은 개념을 두 이름으로 부르지 않는다.** 용어·상태 어휘·재시도 표현을 한 벌로 정의하고 세 셸과 서버 화면(`W-06-10`)이 같은 말을 쓴다. — `W-06-10` §9-1

## §E. 폼팩터 규격·표시

### E-1. POP 화면 예산 ✅ *(실측 검증 완료)*

```
768  전체
-64  헤더
-88  액션바 (핵심 버튼 72 + 여백)
────
616  본문  → 패딩 16×2 제외 실질 584
```

**⚠ 슬랙이 0이다.** `64+616+88 = 768` 정확. 검증 목업에서 테두리 1px×2만으로 오버플로가 났다. **스크롤바·OS 표시줄·업데이트 배너가 하나라도 끼면 깨진다** — 실기 확인 항목.

**⚠ 제약은 세로 행 수가 아니라 가로 폭이다.** 실측에서 좌단은 465/584로 119px 남았으나, **34자리 LOT 행이 597/599px(여유 2px)** 였다. → E-2.

### E-2. 긴 식별자 표시 규칙 ✅ **✓확정 2026-08-02** *(실측에서 발견)*

**규칙**: 구분문자 없는 긴 코드는 **저장은 원문, 표시는 분절 그룹핑**한다.

```
저장  0001234500000012002607310001230007        (34자리·MLOT #16)
표시  000123450 · 000001200 · 260731 · 000123 · 0007
      제품코드9    수량9        날짜6    공급사6  번호4
```

**이유**: 34자리를 붙여 쓰면 작업자가 실물 라벨과 화면을 **눈으로 대조할 수 없다.** 열 폭 산정도 이 규칙을 전제로 다시 한다.

> **결정 기록(2026-08-02 사용자 확정)**: 원문 그대로 붙여 쓰는 대안을 검토한 뒤 **표시만 분절**로 확정했다. 실측에서 이 줄이 599픽셀 중 597픽셀을 써 여유가 2픽셀이었고(E-1), 붙여 쓰면 실물 라벨과 눈으로 대조가 불가능하다. **저장값은 손대지 않으므로** 데이터 영향이 없다.
> **⚠ 분절 자릿수는 자재 로트 번호 체계에 종속**된다 — 다른 번호 체계에 그대로 쓰지 말고 각 체계의 자리 구성을 확인해 정한다.

### E-3. 터치 규격 — DS 갭 해소 전 임시 규약 ✅ **✓확정 2026-08-02**

**요구**(POP): 일반 56px↑ · 주요 64px↑ · 핵심 64~72px · 위험 72px↑ · 간격 8px↑(권장 12~16)

**임시 규약**: 해소 전까지 제품 측에서 높이를 지정한다. **DS에 밀도 프리셋이 생기면 즉시 그쪽으로 옮긴다** — 제품에 눌러 담고 방치하지 않는다.

> **결정 기록(2026-08-02 사용자 확정)**: 임시 규약을 **승인**했다. 제품 측 높이 지정으로 진행하고, DS에 밀도 프리셋이 생기면 그쪽으로 옮긴다.
> **DS 요청 시점 — 원칙대로 몰아서 낸다.** 확대 순서가 기준정보연계 우선으로 조정되면서 **1차 13화면이 전부 관리웹**이 되어 터치 규격이 걸리지 않는다. 따라서 예외로 선발행할 근거가 사라졌고, 대조를 더 쌓아 빈도 신호와 함께 내는 원칙(`uiux/CLAUDE.md` §디자인 시스템)을 따른다.

### G-2. 미확정 코드 목록의 표시 ✅ **✓확정 2026-08-02**


**해당**: `overall_judgment_code`(회신 E-3) · `management_level_code`·`location_type_code`·`quality_zone_code`(공통코드 미정) 등.

**이유**: 감추면 나중에 화면 구조가 바뀌고, 임의값을 넣으면 잘못된 데이터가 쌓인다.

> **결정 기록(2026-08-02 사용자 확정)**: 「선택지가 없으면 필드를 감춘다」 대안을 검토한 뒤 **비활성 + 사유 표시**로 확정했다. F-1(권한 없는 기능)·B-4(참조가 있어 코드를 못 고침)와 **같은 원리**다 — 「할 수 없다」는 감추지 않고 이유와 함께 보인다. 한 화면 안에서 규칙이 갈리지 않게 하려는 것이기도 하다.

## §J. 승인 워크플로우 **[v0.5 신설]**

> **왜 신설하나** — 확대 2차 도메인 01에서 `approval_request_id`를 가진 테이블이 **셋**(`inbound_receipt` 무발주 · `inbound_variance` 입하 오류 · 그리고 `W-01-02` 한도승인 대상)이고, 결재 4테이블이 완전한 형태로 실재한다. 화면마다 승인을 다시 발명하면 갈린다.

### J-1. 승인은 4테이블 한 벌이고, **정의와 실행이 분리**돼 있다 ✅

| 계층 | 테이블 | 성격 |
| --- | --- | --- |
| **정의** | `app.approval_route` | 마스터 형(`is_active` — B-4) · 유형·사업부·**값 구간**별 결재선 |
| | `app.approval_route_step` | 부여·회수 형(B-6) · 단계별 승인자 |
| **실행** | `app.approval_request` | 요청 1건 · `version_no` 有 |
| | `app.approval_step` | 단계별 결재 기록 · **기록 전용** |

**규칙**: 승인 화면은 **정의를 읽기만** 한다. 결재선 등록·수정은 별도 화면 소관이다.

⬜ **결재선 정의 화면이 인벤토리 108건에 없다**(실측). 공통(CO) 또는 06 도메인 후보.

### J-2. 「한도」는 `min_value` / `max_value`가 정한다 ✅

```
approval_route.min_value / max_value   numeric(20,6)
ck_approval_route_range: max >= min (둘 다 있을 때)
```

**값 구간에 따라 결재선이 달라진다.** 소량이면 1단계, 대량이면 2단계 — `business_unit_id`로 사업부별 차등도 된다.

**규칙**: 화면은 **적용된 구간을 보여준다.** 승인자가 「왜 내가 결재선에 있는가」를 알 수 있어야 한다.

⬜ **무엇의 값인지 미정** — 수량인지 금액인지 컬럼명이 말하지 않는다.

### J-3. 요청 시점에 승인자를 **사람으로 확정**한다 ✅

```
approval_step.approver_id   bigint NOT NULL
```

`route_step.approver_type_code`가 **USER · ROLE · DEPARTMENT** 세 방식이어도, **요청이 만들어질 때 실제 사람으로 전개**된다. 「그 역할의 누구나」가 아니다.

**규칙**: 승인 대기 큐는 **로그인 사용자가 `approver_id`인 것**만 보인다. 역할 기반 필터가 아니다.

### J-4. 사유는 필수다 ✅

```
approval_request.reason   text NOT NULL
```

**사유 없는 승인 요청이 데이터에 들어갈 수 없다.** 요청 화면이 반드시 받는다.

### J-5. 승인 화면은 **「승인하면 무엇이 일어나는가」**를 명시한다 ✅

특히 **일어나지 않는 것**을 적는다.

> `W-01-02` 실례 — 긴급 IQC 생략을 승인해도 **ERP G/R 전표는 나가지 않는다**(「합격품 한정」이 자동 제외). 이것을 모르고 누르면 승인자는 「입고 처리했다」고 오해하고 **사후에 회계가 어긋난다.**

**규칙**: 승인 버튼 위에 **결과 구획**을 둔다. 상태 전이·후속 연계·**제외되는 것**을 항목으로 적는다.

### J-6. 결재는 되돌릴 수 없다 ✅

`approval_step`이 기록 전용이다(감사 컬럼 `created_at`뿐 · `version_no` 없음).

**규칙**: 화면에 「수정」·「취소」를 두지 않는다. 번복은 **새 요청**이다. — B-3(이력 불변)의 승인 판.

— `W-01-02` §9 · `M-01-01` §5-5 · `M-01-06` §5-4 · `W-01-03` §5-3

## §K. 출력물 발행·재발행 **[v0.5 신설]**

> **왜 신설하나** — `app.document_issue_log`가 라벨·인식표·QR·성적서를 **한 테이블로** 다루고, 두 제약이 재발행 규칙을 데이터로 강제한다. 라벨 화면이 도메인 01·02에 여럿(`P-01-01`·`P-01-02`·`P-02-05`·`P-02-07`·`P-02-09`)이라 규약이 먼저 서야 한다.

### K-1. 발행은 **회차로 쌓고** 이전 것을 지우지 않는다 ✅

```
uq_document_issue_log       UNIQUE (document_type_code, target_type_code, target_id, issue_seq)
issue_seq                   integer NOT NULL DEFAULT 1 CHECK (issue_seq > 0)   -- 1=최초, 2+=재발행
```

**규칙**: 재발행은 수정이 아니라 **새 기록**이다. 회차가 오르고 이전 회차는 남는다.

### K-2. ★ 재발행에는 **사유가 필수**다 ✅

```
ck_document_reissue_reason  CHECK (issue_seq = 1 OR reissue_reason_code IS NOT NULL)
```

**DB가 강제한다.** 화면이 사유를 받지 않으면 저장이 실패한다.

**왜** — 라벨이 여러 장 돌아다니면 같은 LOT이 두 곳에서 스캔된다. 재발행 이력이 있어야 추적된다.

> ⚠ **재발행이 정상 경로인 화면이 있다** *(v0.6 보완)*. `P-02-09`(포장 라벨·인식표 재출력)는 **포장 후 겉면에 붙일 것을 다시 찍는 것이 본래 목적**이라 `issue_seq`가 항상 2 이상이다.
>
> **사유 값 목록에 「정상 업무 흐름」(포장 등)이 있어야 한다.** 훼손·분실만 있으면 전부 훼손으로 기록되어 **재발행 통계가 무의미해진다.** — `P-02-09` §5-1

### K-3. 발행 기록에 **단말과 프린터**를 남긴다 ✅

```
terminal_id     FK -> mdm.terminal
printer_name    varchar(100)
```

「어디서 몇 번째로 찍었는가」가 추적의 단위다.

### K-4. 인쇄는 트랜잭션 밖이다 ✅

B-8 규칙 2의 적용. **프린터가 죽어도 LOT은 생성되고 기록은 남는다.** 인쇄 실패로 발번을 롤백하면 같은 자재에 발번을 다시 해야 하고, 그사이 다른 단말이 번호를 가져갈 수 있다.

**규칙**: 프린터 상태를 **화면 머리에 상시 표시**한다. 인쇄가 안 될 때 사용자가 가장 먼저 보는 곳이다.

### K-5. 라벨은 **서버가 그린다** ✅ *(결정 18)*

POP은 이미지를 받아 프린터로 보낼 뿐이다. 클라이언트가 레이아웃을 그리지 않으므로 **단말마다 라벨이 달라지지 않는다.**

### K-6. 물리적으로 유통되는 출력물은 **회차를 인쇄면에도** 넣는다 ✅

데이터에만 회차가 있으면 현장에서 몇 번째 라벨인지 구분할 수 없다.

⬜ **이전 라벨의 무효화 규칙이 없다** — 3회차를 찍어도 1·2회차가 물리적으로 남아 스캔된다. 회차 인쇄가 최소 대안이고, 스캔 시 회차 검증은 별도 결정.

— `P-01-01` §9
