# 04 제품출하 API 스펙 — 설계

> 작성일: 2026-08-13 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 선행 트랙: 06 ✅ · 01 ✅ · 공통(승인·출력물) ✅ · 02 ✅ · 03 ✅
> **여섯 번째 계약 트랙 · 마지막에서 두 번째**(남는 것은 05 뿐이고 그것도 #67 대기)

## 1. 왜 04 가 다음인가

**가장 크고**(18장), **가장 많이 물려 있다**.

| | |
| --- | :-: |
| 04 도메인 화면 | **18** — 지금까지 중 최대 |
| ⭐ **04 가 풀어 주는 남의 미결** | **2** *(1단계 정정 — §2-1)* |
| ⭐ **04 가 처음으로 「받기만」 하지 않는다** | 03 계약을 **쓰는** 쪽이 된다 |

⭐ **03 이 「04 가 03 의 남은 하나를 푼다」고 예고했고 그대로다.**

## 2. ⭐⭐ 화면을 착수 전에 센다 — **18 이 아니라 16 이다**

⛔ **03 에서 배운 것을 그대로 적용한다** — 도메인 배지로 세지 않고 **앞 트랙 요구서의 「범위 밖」 절을 먼저 읽는다.**

```
생성기 dom == '04'                              18
⛔ 출력물 계약이 이미 덮은 것                   − 2   P-04-02 · P-04-04
                                                ────
                                    계약 대상    16
```

**근거** — 공통 출력물 요구서가 **자기 도출 화면 5장에 둘을 포함**한다:

```
| 도출 화면 | P-02-05 · P-02-07 · P-02-09 · P-04-02 · P-04-04 |
```

⚠ **02 가 P-02-05·07·09 를 뺀 것과 같은 규칙**이다 — 출력이 주 기능이면 출력물 계약이 센다.

⭐ **결번 2** — `W-04-09` · `M-04-02`.

### 2-1. ⛔ 그런데 **방향이 반대인 빚이 3건 있다**

**출력물 계약이 「04 소관」이라 적고 비워 둔 칸**이 셋이다.

> ⛔ **1단계 정정 — 셋이 아니라 하나다.** 아래는 착수 시점 서술이고, 실측하니 **둘은 01 계약에 이미 있었다.**

| 부르는 화면 | 비워 둔 칸 | 실측 |
| --- | --- | :-: |
| `P-02-09` 라벨 재출력 *(02 도메인)* | 「포장 구성이 정한다」 | ✅ **01 에 있다** — `GET /inventory/handling-units/{id}/contents` |
| `P-04-04` 재구성 신규 라벨 | 「대기 목록 조회」 | ✅ **01 에 있다** — `GET /inventory/handling-units?statusCode=` |
| ⭐ **`P-04-02`** 납품 포장 라벨 | 「**대상 선택** — 합격 건 목록」 | ⭐ **진짜 04 것** — `shipment_lot_allocation` |

⭐ **관문 ②의 변형이다** — 「04 가 내야 한다」고 적힌 것 중 **둘이 이미 있었다.** 03 트랙의 「신설 요구는 전건 이미 발행돼 있었다」와 같은 형태다.

⚠ **적기 전에 상대 계약을 열었어야 했다** — 출력물 요구서의 「04 소관」을 그대로 옮겨 적었다.

## 3. 계승하는 것 — 앞 다섯 트랙 그대로

| 무엇 | |
| --- | --- |
| **6단계 방법론** | 리소스 → URL·동작 → 오프라인 → OpenAPI → 검증 → 착수 통지 |
| **리소스 패턴 7종** | 가 마스터 / 나 부여·회수 / 다 버전 마스터 / 라 업무 문서 / 마 원장 / 바 파생 잔액 / 사 구간 |
| **URL 규약** | 복수 명사 · kebab-case · `:동사` 는 상태 전이에만 · **수정은 `PUT`**(PATCH 0) |
| **접두어는 공유하되 경로는 한 계약에만** | 03 이 실측으로 확인 |
| **두 계약이 한 테이블을 보면 소유는 쓰기를 가진 쪽** | 03 신설 |
| **생성기** | `build-04-openapi.py` — ⛔ **손으로 고치지 않는다** · ⭐ **공유 스칼라 오염 가드 필수**(03 Blocker) |
| **검사기 5종** | 구조 · 공개안전 · 커버리지 · 매핑 · ⭐ **인용(역방향 ②)** |

### 3-1. ⛔ 오프라인 `202` 를 쓰지 않는다

**2026-08-12 철회됐다**(공유계약 C-7 주석). 오프라인이면 HTTP 요청이 일어나지 않으므로 서버가 「접수했다」를 말할 수 없다. **`IfMatchVersionOptional` 만 단다.**

~~⚠ 04 는 POP 2 · 모바일 3 이라 오프라인 대상이 있다 — 03(1장)보다 넓다.~~

⛔ **3단계 정정 — 04 계약의 오프라인 대상은 0건이다.** 04 테이블을 쓰는 현장 화면은 `M-04-01` 하나뿐인데 **오프라인 진입 차단**이고, 오프라인을 허용하는 셋은 **전부 남의 테이블(01·02)**을 쓴다. ⚠ **「POP·모바일이 몇 장인가」로 세면 틀린다 — 어느 테이블에 쓰는가를 봐야 한다.**

### 3-2. ⭐ 03 이 남긴 두 가지를 반드시 가져온다

| 무엇 | 왜 |
| --- | --- |
| **공유 스칼라 오염 가드** | 03 에서 **19곳에 엉뚱한 설명이 샜다**. `build-02` 에는 아직 없다 — 04 는 처음부터 넣는다 |
| **역방향 ② 를 5단계 필수로** | 04 는 **01·02·03·06·공통 다섯 계약을 인용**한다. 지금까지 중 가장 많다 |

## 4. ⭐ 04 가 소유하는 것 — **10테이블**

`logistics` 32 중 04 것을 갈랐다.

| 무리 | 수 | 소관 |
| --- | :-: | --- |
| 구매·입하·입고·적치·출고·이동 | **21** | **01** — 계약 있다 |
| ⛔ `subcontract_*` | **4** | **범위 밖** — 화면 0건 · 「추후 구체화」 확정(01 §7) |
| ⭐ **판매·출하** | **7** | **04** — 이 트랙 |

```
04 소유 (logistics)   sales_order · sales_order_line
                      shipment_request · shipment_request_line
                      shipment · shipment_line · shipment_lot_allocation      7
04 소유 (quality)     nonconformance · nonconformance_lot
                      disposition_decision                                    3
                                                                            ───
                                                                             10
```

⭐ **뒤의 셋은 03 이 명시적으로 넘긴 것**이다 — 03 요구서 §1-2 「`nonconformance` · `nonconformance_lot` · `disposition_decision` → **04 제품출하** — `W-04-07` · `P-04-03`」.

**검산 — logistics 원소 유일**: 21 + 4 + 7 = **32** ✅

### 4-1. ⛔ `sorting_result` 는 만들지 않는다 — **관문 ②**

`sorting_result.disposition_decision_id` 가 **NOT NULL** 이라 04 가 `disposition_decision` 을 소유하면 딸려 오는 것처럼 보인다.

⛔ **#118 이 이미 확정했다 — 선별 실행은 1차 범위 밖이고 화면을 만들지 않는다.** 테이블은 두되 **경로를 만들지 않는다.**

⚠ **`W-04-07` 이 「선별」 값을 처분 유형 선택지에 둘지**는 5단계 적합성에서 본다(03 이 남긴 미결).

## 5. ⭐⭐ 04 는 **남의 계약을 가장 많이 쓴다**

16화면의 §2 데이터 면을 전수로 뽑아 갈랐다.

| 계약 | 04 가 쓰는 것 |
| :-: | --- |
| **01** | `goods_receipt` · `goods_issue` · `stock_transfer` · `putaway_task` · `inventory_balance` · `inventory_transaction` · `inventory_reservation` · `handling_unit` · `trace.lot` · `trace.lot_relation` |
| ⭐ **03** | **`inspection_request`**(`W-04-03` OQC) · **`lot_hold` 쓰기**(`W-04-07`·`10`·`11`) |
| **02** | `production_result` · `work_order`(`P-04-03` 재작업) |
| **공통** | `document_issue_log` · `approval_request` · `operation_policy` |
| **06** | `mdm.item` · `integration_message` |

### 5-1. ⭐ 03 이 만든 것이 여기서 쓰인다 — **예고가 맞았다**

| 03 이 만든 것 | 04 가 부르는 곳 |
| --- | --- |
| 검사 3계층 계약 | **`W-04-03`** OQC 출하검사 판정 |
| `/quality/lot-holds`(구간 형) | **`W-04-07`**·**`W-04-10`**·**`W-04-11`** |

⭐ **「두 계약이 한 테이블을 보면 소유는 쓰기를 가진 쪽」이 실제로 작동한다** — 04 는 보류를 **걸지 않고 읽거나 03 경로로 건다.**

### 5-2. ⛔ 그래서 **역방향 ②가 이 트랙에서 가장 중요하다**

**다섯 계약을 인용한다.** 02 가 「01 계약이 준다」고 적었다가 셋이 허공이었던 사고가 **여기서 다섯 배로 커질 수 있다.**

→ **5단계가 아니라 매 단계 끝에 돌린다.**
