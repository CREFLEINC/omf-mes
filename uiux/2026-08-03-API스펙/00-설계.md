## 1. 배경

### 1-1. 왜 지금인가

화면 상세 스펙 **확대 1차 13장**(기준정보 12 + `W-CO-02`)이 완료됐다. 각 장에 조회 조건·필드·액션·활성 조건·예외가 정의돼 있어 **API를 도출할 재료가 갖춰졌다.**

한편 저장소에 **전용 API 스펙 문서가 0건**이다(OpenAPI·Swagger·yaml 전 파일 검색 0). API가 적힌 곳은 셋뿐이다.

| --- | --- |

| `deliverables/02-SW설계사양서.md` | 계약 **규칙**만 — §3.2 인증 계층 · §3.3 「전 쓰기 API `Idempotency-Key` 필수」·실패 3분류 · NestJS + OpenAPI 생성 타입 FE/BE 공유 |
| `uiux/화면상세스펙-공통/공유계약.md` | 화면에서 도출한 **응답 규약** — 「API 파급」 5건 + v0.4 서버 동작 규정 3건 = **8건** |

### 1-2. 상류 계획과의 관계

**WBS §4.2 P0.4**가 이미 「**API 계약 v0 + 목업 서버**(도메인 6개 × 계약, 응답 구조 목업 데이터)」로 계획돼 있고, 전략은 **계약 우선(Contract-first)**이며 형식은 **OpenAPI**다. 계약 저장소의 소유는 **통합 Agent**이고 변경 승인권도 그쪽으로 단일화돼 있다.

다만 현재 백엔드 공식 진행은 **데이터 모델링까지**라 P0.4가 서 있지 않다. 그래서 **API는 화면 스펙에서 도출해 넘긴다**는 상태다.

**→ 이 산출물은 P0.4의 초안 입력이다.** 계약으로 확정·소유하는 것은 통합 Agent 몫이며, 우리는 **화면이 무엇을 요구하는지**를 근거와 함께 정리해 넘긴다.

> ⚠ WBS의 **일정(주차·마감)은 참조하지 않는다** — 일정은 사용자 소관이며 계획에서 제외한다. 참조한 것은 §4.2 작업 분해와 전략뿐이다.

### 3-2. 중복 금지 규칙 4건

이 프로젝트가 **§I 14건**(확정↔하류 불일치)을 만든 원인이 「같은 것이 여러 곳에 있고 서로 어긋난다」였다. 반복하지 않기 위한 규칙이다.

1. **필드 정의는 OpenAPI에만.** 요구서는 「이 화면은 창고 목록·상세·저장이 필요하다」까지만 쓰고 필드를 나열하지 않는다.
2. **OpenAPI 스키마는 물리 모델에서 옮긴 것.** 타입·필수·유일·CHECK를 자의로 바꾸지 않는다. **다르면 그건 결함이고 이슈로 낸다.**
3. **화면 스펙 §4는 그대로 둔다.** 거기 있는 것(라벨 한/베·편집 가능 여부·사용자에게 보일 검증 문구)은 API의 관심사가 아니다 — **서로 다른 것을 담으므로 중복이 아니다.**
4. **각 엔드포인트에 근거를 단다.** OpenAPI `description`에 `근거: W-06-07 §5-1 · 공유계약 B-4` 형태로 한 줄.

## 4. 설계

### 4-1. 리소스 목록

#### CRUD — 화면이 저장하는 것

| 군 | 리소스 | 근거 화면 |

※ **`W-06-07`은 확대 1차가 아니라 파일럿 산출물이나 포함한다** — 같은 06 도메인이고 스펙이 완성돼 있으며, 다른 화면들이 창고·위치를 참조한다. 빼면 도메인이 반쪽이 된다.

#### 조회 전용 — 관리 화면이 없는 것 8종

`uom` · `partner` · `plant` · `legal_entity` · `business_unit` · `production_line` · `process` · `equipment`

전부 확대 1차 화면의 **선택 목록**에 쓰인다(창고의 공장·사업부·거래처 / 품목의 기준단위 / 부서의 사업부 / 접근범위의 사업부·공장 / 검사 항목의 지정 검사장비 …). **관리 화면은 인벤토리 108건에 하나도 없다** — 실측.

**엔드포인트를 지어내지 않는다.** 요구서에 「이 화면은 API를 정의할 수 없다 — 이슈 해소 후」로 적고 OpenAPI에는 넣지 않는다.

### 4-2. URL·동작 규약

**네임스페이스는 물리 모델 스키마를 따른다** — `/mdm/*` · `/app/*` · `/planning/*` · `/quality/*` · `/integration/*` · `/audit/*`.

별도 `/lookup`을 두지 않는다. 조회 전용은 **같은 경로에 GET만** 두고, 나중에 관리 화면이 생기면 POST를 더한다. `/lookup`을 두면 「왜 이건 lookup이고 저건 아닌가」가 생기고, 화면이 생길 때 경로를 옮겨야 한다.

**명시적 오퍼레이션은 `:동사`로 쓴다.** PATCH에 여러 의미를 싣는 것보다 의도가 드러나고 OpenAPI에서 경로로 구분된다.

#### 세 종류 마스터가 URL 모양으로 구분된다

**(가) 마스터** — `version_no`·`is_active` 보유

```
GET    /mdm/warehouses                  목록(검색·필터·미사용 포함)
GET    /mdm/warehouses/{id}             상세 — 참조 건수·수정 가능 여부 포함(B-4)
POST   /mdm/warehouses                  등록
PUT    /mdm/warehouses/{id}             수정 — 낙관적 잠금(B-1)
POST   /mdm/warehouses/{id}:deactivate  사용 중지 — 물리 삭제 없음(B-4)
GET    /mdm/warehouses/{id}/history     변경 이력(B-5)
```

**(나) 부여·회수** — `created_at`·`created_by`만

```
GET    /app/users/{id}/roles            현재 부여분
PUT    /app/users/{id}/roles            전체 치환 — 한 트랜잭션
```

**개별 POST/DELETE가 아니라 전체 치환**이다. 체크박스 화면이 최종 상태만 보내면 되고 서버와 어긋날 여지가 없다. 대상: `user_role` · `user_data_scope` · `role_permission` · `worker_qualification` · `routing_operation_dependency` · `item_uom_conversion` · `item_external_code`.

**(다) 버전 마스터** — 헤더–버전–라인

> ⚠ **라인 전체 치환에 선후행(`routing_operation_dependency`)은 포함하지 않는다.** 선후행은 라인 행을 가리키는 별개 관계라 라인이 확정된 뒤에 걸어야 한다. 부여·회수 형태(가)로 **별도 엔드포인트**를 둔다 — `PUT /planning/routings/{id}/operation-dependencies`.

```
GET  /planning/routings?itemId=            품목의 Rev 목록
GET  /planning/routings/{id}               헤더+라인
POST /planning/routings/{id}:new-revision  최신 Rev 복사 → 작성중
PUT  /planning/routings/{id}               헤더 수정 (작성중만)
PUT  /planning/routings/{id}/operations    라인 전체 치환 — 순서 포함
POST /planning/routings/{id}:confirm       작성중 → 확정(B-2·B-7)
POST /planning/routings/{id}:obsolete      확정 → 폐기
```

같은 골격을 `inspection_plan`(검사기준)·`bom`(BOM)에 적용한다 — 세 마스터가 헤더–버전–라인 + 상태 + 유효기간으로 동형이다(공유계약 B-7).

#### 오퍼레이션 전체 목록

`:deactivate` 사용 중지 · `:new-revision` 신규 Rev · `:confirm`·`:obsolete` 상태 전이 · `:set-default` 「하나만 참」 전환(A-6) · `:retry` 연계 메시지 재처리

### 4-3. 순서를 가진 표 — A-5 처리

**문제**: 순서 컬럼에 유일 제약이 걸려 있으면 두 행을 맞바꿀 때 **중간 상태가 반드시 제약을 위반한다.** `10 사출 · 20 조립 · 30 검사`에서 조립↔검사를 바꾸려면 조립을 30으로도(검사가 이미 30) 검사를 20으로도(조립이 이미 20) 못 간다. 임시값 우회는 3회 호출이고 중간 실패 시 임시값이 남는다.

**해당 리소스 — 3곳** (실측)

| 컬럼 | 유일 제약 |
| --- | --- |
| `routing_operation.operation_seq` | `uq_routing_operation(routing_id, operation_seq)` |
| `bom_component.sequence_no` | `uq_bom_component(bom_id, sequence_no)` |
| `inspection_item_spec.sequence_no` | `uq_inspection_item_spec(inspection_plan_version_id, sequence_no)` |
| ~~`code_value.display_order`~~ | **유일 제약 없음** — `integer NOT NULL DEFAULT 0`. **대상 아님** |

> ⚠ `ds-gap` **G-7**(행 순서 재배치 UI)의 사용처 4곳과 **다르다.** G-7은 「순서를 바꾸는 화면 부품이 필요한 곳」이고 A-5는 「유일 제약 때문에 서버 트랜잭션이 필요한 곳」이다. `display_order`는 전자에만 해당한다. **공유계약 A-5 문구도 4곳 → 3곳으로 정정한다.**

**해법 — 라인 전체 치환**

화면이 최종 순서를 통째로 보내고 서버가 한 트랜잭션으로 반영한다. 중간 상태가 화면에 노출되지 않으므로 문제가 **구조적으로 사라진다.** 순서·추가·삭제·수정이 한 번에 끝나는 이점도 있다.

**⚠ 「전체 치환」의 의미를 못박는다 — 「행 교체」가 아니다**

`routing_operation`을 참조하는 곳이 **4군데**다(실측).

| 참조처 | 컬럼 | 위험 |
| --- | --- | --- |
| `routing_operation_dependency` | 선행·후행 2컬럼 | 선후행 그래프 소실 |
| `bom_component` | `routing_operation_id` | MES 등록 공정 연결 소실 |
| **`production.work_order`** | `routing_operation_id` **`NOT NULL`** | **진행 중 작업지시가 무너진다** |

**`DELETE` 후 `INSERT`로 구현하면 이 참조가 전부 깨진다.** 따라서 전체 치환은 **「최종 상태를 보내고 서버가 기존 행을 유지하며 순서만 갱신한다」**로 계약에 명시한다. 이를 적지 않으면 구현이 자연스럽게 `DELETE+INSERT`로 간다.

**순서 표시 — 목록 내 위치로 매긴다**

화면은 `operation_seq`를 그대로 보여주지 않고 **목록 내 위치로 1부터 연속** 표시한다(`1 사출 · 2 조립 · 3 검사`). 저장 키는 응답에 담되 표시하지 않는다. 그러면 **백엔드가 채번을 바꿔도 화면이 흔들리지 않는다.** 대상은 순서를 가진 표 3곳.

> 이에 따라 `W-06-01` §3·`W-06-02` §3 레이아웃의 `Seq` 열 표기를 「목록 내 위치」로 정정한다.

### 4-4. 공통 응답 규약 — 공유계약 8건을 구조로

**오류 (G-1 + A-1)** — `scope`로 필드↔화면을 가르고 유일 위반은 범위를 담는다

```json
{ "errors": [
  { "scope": "field", "field": "warehouseCode", "code": "UNIQUE_VIOLATION",
    "uniqueScope": ["plantId"], "message": "같은 공장에 이미 있는 창고코드입니다" },
  { "scope": "screen", "code": "PERMISSION_DENIED", "message": "..." } ] }
```

**충돌 409 (B-1)** — 원인 3종 구분. 지금 문구는 「다른 사용자가…」 하나뿐이라 뒤 둘에 사실과 다른 안내가 된다.

```json
{ "conflictCause": "user" | "erpSync" | "workerLease" }
```

**마스터 상세 (B-4)** — 참조 건수를 화면이 세지 않는다

```json
{ "editability": { "codeEditable": false, "reason": "REFERENCED", "referenceCount": 12 } }
```

셀 수 없는 대상(의도적 비-FK · 코드 문자열 참조)은 `referenceCount: null` · `reason: "NOT_COUNTABLE"` → 화면은 **무조건 잠금**.

**일괄 처리 (C-2)** — 전체 롤백 없음

```json
{ "succeeded": 39, "failed": [ { "index": 12, "key": "...", "errors": [ ... ] } ] }
```

**선택 목록 (G-8)** — 서버가 유효성을 판정한다. 기본은 유효한 것만, `?includeInactive=true`면 `isActive` 표식을 함께 내린다.

**멱등 (`02` §3.3)** — 전 쓰기에 `Idempotency-Key` 헤더 필수.

**저장 단위 (A-8)** — 비율은 **0~1 그대로** 전송. `%` 변환은 화면 책임이며 OpenAPI `description`에 명시한다. 대상: `bom_component.scrap_rate` · `routing_operation.standard_yield_rate`.

**수신본 표시 (B-4-1)** — **자리만 만들고 비운다.** `sourceType`을 정의하되 값은 `null`이고 `description`에 「판정 근거 컬럼 부재 — **#65**」를 단다.

### 4-5. 미착지 처리

**원칙: 스키마에 지어 넣지 않는다.** 물리 모델이 정본이므로 OpenAPI 스키마는 물리 모델과 1:1을 유지한다. 없는 필드를 넣으면 구현자가 「만들어야 할 것」으로 읽는다.

**대신 두 곳에 흔적을 남긴다** — OpenAPI 리소스 `description`에 한 줄, 요구서에 표.

| 미착지 | 막는 API | 이슈 |
| --- | --- | --- |
| 다국어(한/베) 명칭 | **전 마스터의 명칭 필드** | #64 |
| 품목 확장속성 4종 | 품목 확장 저장 | #64 |
| Routing 기본 Rev 플래그 | **`:set-default` 오퍼레이션이 성립하지 않음** | #64 |
| Routing 외주 공정 구분 | Routing 라인 — **요청 형태 확정**(`is_outsourced` boolean) | #64 |
| 검사정책 3속성 · 샘플 비율 형태 | 검사기준 버전 | #64 |
| 불량코드 N:M · 처분구분 | **공정 매핑 엔드포인트가 성립하지 않음** | #64 |
| 판정유형 통제 속성 | 전용 리소스 없이 `code_value`로만 | #64 |
| **수신본 식별 플래그** | **전 수신본 마스터의 편집 가능 여부 판정** | **#65** |
| I/F 정의·송신 항목 | `W-06-09`·`W-06-12` **엔드포인트 전무** | #66 |
| `audit_event` 사용 규약 | 변경 이력 응답을 사람이 읽게 만들 수 없음 | #68 |

**둘은 「필드가 빈다」가 아니라 「엔드포인트를 쓸 수 없다」**다 — `:set-default`(기본 Rev 플래그 없음)와 공정 매핑(N:M 테이블 없음). 요구서에 따로 표시한다.

## 5. 검증 — **UI 요구 충족이 축이다** *(2026-08-03 사용자 지시로 교체)*

> **⚠ 방향 전환.** 초안은 「물리 모델 ↔ OpenAPI 스키마 자동 대조」를 1번 축으로 뒀으나 **폐기한다.**
> 사용자 지시: 「**SQL과 OpenAPI를 직접 대조하는 검증은 필요없다. 지금 작업은 「UI」에 필요한 「API」가 모두 있는지, 그리고 「UI」에서 사용하기에 적절하게 만들어졌는지가 중요하다.**」
>
> 옳은 지적이다. **물리 모델 정합은 데이터모델 담당 소관**이고 우리가 발견한 불일치는 이미 이슈 #64~#70으로 넘겼다. 우리 트랙(UI/UX)이 책임질 것은 **화면이 이 API로 돌아가는가**이지 스키마가 DDL과 글자까지 같은가가 아니다.

### 5-1. 축 1 — 커버리지: UI가 필요로 하는 API가 다 있는가 *(기계 검산)*

화면 스펙에서 **UI 요구를 전건 추출**하고, 요구서 매핑표가 그것을 하나도 빠짐없이 소화했는지 대조한다.

| 추출 대상 | 화면 스펙 위치 | 무엇을 요구하는가 |
| --- | --- | --- |
| **액션** | §5-1 표 | 저장·등록·상태 전이·일괄 처리 → 쓰기 엔드포인트 |
| **선택 목록** | §4 필드표의 FK 열 | 코드·마스터 조회 → 읽기 엔드포인트 |
| **예외 처리** | §6 표 | 오류 응답이 그 상황을 표현할 수 있는가 |

**대조 규칙**: 추출 목록 − 매핑표에서 다룬 것 = **차집합이 0이어야 한다.** 「없음 + 이유」로 명시한 것은 다룬 것으로 친다(예: 라벨 이미지 생성 = 라벨 도메인 소관·범위 밖). **빈칸은 누락**이다.

### 5-2. 축 2 — 적합성: UI에서 쓰기에 적절한가 *(화면별 판단)*

화면 하나를 놓고 「**이 API로 이 화면을 그릴 수 있는가**」를 대조한다. 화면 10개 전건에 대해 다섯을 본다.

| # | 점검 | 무엇을 보나 |
| :-: | --- | --- |
| **1** | **진입 호출 수** | 화면을 처음 그리는 데 몇 번 부르나. 선택 목록이 많아 과하지 않은가 |
| **2** | **필요한 정보가 응답에 있나** | 참조 건수·수정 가능 여부(B-4) · 유효성 판정(G-8) · 충돌 원인(B-1) · 오류 범위(G-1) — 화면이 스스로 계산하게 두지 않았는가 |
| **3** | **안 쓰는 것을 담고 있지 않나** | 화면이 표시하지 않는 필드를 응답이 나르는가(과잉 전송·대외비 노출) |
| **4** | **예외를 표현할 수 있나** | §6의 조건부 필수·짝 제약·범위 위반·권한 없음이 **어느 오류 코드로** 오는가 |
| **5** | **상태 전이를 지원하나** | §5-2·§5-4의 화면 상태와 편집 잠금을 API가 뒷받침하는가 |

결과는 **요구서에 표로** 남긴다. 「적절하지 않다」가 나오면 그것이 API 설계 결함이고 고친다.

### 5-3. 부수 검증

| 검증 | 방법 |
| --- | --- |
| 공유계약 8건 반영 | 요구서 대조표 — 8건 × 어느 스키마·필드로 구현됐는가 |
| OpenAPI 문법 | `json.load` 로 유효성 확인 |

### 5-4. 매핑 선언은 남긴다 — 목적만 바뀐다

`x-source-table`·`x-source-column` 은 계속 단다. **검산 입력이 아니라 근거 추적용**이다 — 「이 필드가 물리 모델의 어느 컬럼에서 왔나」는 읽는 사람에게 값이 있고, 비용이 없다. **다만 강제하지 않는다.** 물리 모델에 대응물이 없는 것(공통 응답 스키마 등)은 달지 않는다.

## 7. 실행 순서 (개요)

상세 계획은 `writing-plans`로 별도 수립한다.

1. **골격** — OpenAPI 뼈대 + 공통 응답 스키마(§4-4 8건) + `verify-openapi.py`
2. **리소스** — 군별로 스키마·경로 작성. 검산을 통과시키며 진행
3. **요구서** — 화면 → API 매핑표 · 근거 · 미착지 표 · 규약 대조표
4. **HTML 생성 + 최종 검산**

**이 설계에서 파생된 정정 작업 2건**(산출물 작성과 별개로 반영해야 한다)

- **공유계약 A-5** — 대상을 4곳 → **3곳**으로 정정하고, 「전체 치환 = 기존 행 유지 + 순서 갱신」과 「순서 표시는 목록 내 위치」를 조항에 추가
- **`W-06-01` §3 · `W-06-02` §3** — 레이아웃의 `Seq` 열 표기를 「목록 내 위치」로 정정
