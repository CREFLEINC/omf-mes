# 설계팀 남은 작업 전체 정리 — 유형 · 고정/변동형 · 중요도

> 작성일: 2026-08-22 · 작성 주체: CREFLE OMF 팀 (UI/UX) · 기준 `main`(PR #189 반영 후 최신)
> 대상 = **설계팀이 지금 스스로 판단해 정할 수 있는(또는 정해야 하는) 잔여 결정**. 다른 팀(데이터 모델링·프론트 구현) 작업 대기 항목은 원칙적으로 뺐다 — 예외로 「이미 확정됐는데 화면 스펙 등 하류에 아직 안 옮겨진 것」은 방치하면 잘못된 구현이 나갈 수 있어 **§4 기타**에 남겼다.

## §0. 이 표를 읽는 법

**화면 ID** — 앞 글자가 프로그램, 가운데 두 자리가 도메인이다.

| 앞 글자 | 프로그램 | 가운데 두 자리 | 도메인 |
| :-: | --- | :-: | --- |
| `W-` | 관리웹(사무 PC, 브라우저) | `01` | 자재창고관리 |
| `P-` | POP(현장 키오스크, Electron) | `02` | 생산실행 |
| `M-` | 모바일(PDA, Capacitor 앱) | `03` | 품질관리 |
| | | `04` | 제품출하 |
| | | `05` | 설비툴관리 |
| | | `06` | 기준정보연계 |
| | | `CO` | 3개 프로그램 공통 화면 |

**분류 기준** — 사용자가 이번에 정한 정의를 그대로 적용했다.

| 축 | 값 | 뜻 |
| --- | --- | --- |
| 유형 | 정책 결정 | 업무 규칙·절차를 어떻게 정할지의 판단(값 하나가 아니라 「어떻게 할 것인가」) |
| | 예시 및 대표값 미결정 | 코드 값 목록·마스터 데이터의 구체적인 값(선택지)이 아직 안 정해짐 |
| | UIUX 설계 결정 | 화면 구성·상호작용·컴포넌트 선택 등 화면 설계 자체의 판단 |
| | 기타 | 위 셋에 안 들어가는 것 — 하우스키핑, 이미 확정됐으나 하류 전파만 안 된 것 등 |
| 고정/변동 | 변동형 | 시스템을 도입하는 고객사(운영 현장)마다 달라질 수 있는 값·정책 |
| | 고정형 | 시스템 정책으로 못박아도 되는 것 — 고객사가 시스템 방식을 따르면 되는 부분 |
| 중요도 | 낮음 | 지금 설계팀이 직접 정하고 개발해도, 나중에 실제 값으로 바뀌는 데 문제 없음 |
| | 보통 | 직접 정하고 개발해도 되지만, 나중에 바뀌면 **1일 이내** 작업 공수가 발생할 수 있음 |
| | 높음 | 지금 정해 버리면 **나중에 비즈니스 로직 자체가 바뀌는** 이슈가 생길 수 있음 — 직접 정하지 않는 편이 낫다 |

1차 추출 **144건** → 겹치는 것을 병합하고 분류를 재검증해 **100건**으로 정리했다. 제외 기준 = ① 최근 커밋(2026-08-19~08-22, 예: `2026-08-21-검사의뢰상태-확정` 등)으로 이미 해소된 것 ② 데이터 모델 팀에게 이미 통지가 나가 있고 설계팀이 더 판단할 게 없는 순수 컬럼·테이블 결손(단, 방치 위험이 있는 것은 §4 기타에 1건으로 요약해 남겼다).

⚠ **이 표 자체가 실측 스냅숏이다** — 다시 만들려면 위 자료원 다섯 개를 같은 방식으로 재수집해야 하고, 시간이 지나면 이슈 상태·미결 행 수가 달라진다. 재현 명령은 각 자료원 칸에 적힌 스크립트·경로다.

⛔ **실제로 빈틈이 하나 드러났다** — 문서 끝의 **「분류표가 놓친 자리」** 절을 함께 본다. 100건 집계만 보고 「전부 잡혔다」로 읽으면 안 된다.

## §2. 요약 — 3축 교차표

| 유형 | 고정·낮음 | 고정·보통 | 고정·높음 | 변동·낮음 | 변동·보통 | 변동·높음 | 합계 |
| --- | :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| 정책 결정 | 0 | 3 | 6 | 0 | 5 | 4 | **18** |
| 예시 및 대표값 미결정 | 3 | 6 | 7 | 12 | 18 | 6 | **52** |
| UIUX 설계 결정 | 3 | 5 | 3 | 0 | 1 | 1 | **13** |
| 기타 | 10 | 4 | 3 | 0 | 0 | 0 | **17** |
| **합계** | **16** | **18** | **19** | **12** | **24** | **11** | **100** |

⚠ **2026-08-23 정정** — `equipmentTypeCode`가 「변동·보통」에서 「변동·높음」으로 재평가됐다(`omf-mes#195`에서 화면 조회 필터로 쓰이는 게 실측 확인됨 — §5 47번 참고). 아래 수치는 정정을 반영한 값이다.

⭐ **가장 큰 덩어리는 「예시 및 대표값 미결정 · 변동형」**(코드 값 목록 대부분)이다 — 고객사 운영 관행에 따라 달라질 값이라 지금 임의로 정해도 나중에 실제 값으로 바뀌는 비용이 낮은 편이다.

⛔ **먼저 볼 것은 「중요도 높음」 30건**이다 — 지금 설계팀이 임의로 정하면 나중에 비즈니스 로직 자체를 다시 설계해야 할 위험이 있는 것들이다. 목록은 §3.

✅ **§5(예시 및 대표값 미결정) 중 29건은 이미 처리됐다** — 2026-08-22~23에 초기 시드가 만들어져 `uiux/2026-08-13-공통코드값목록-제안안/01-2차-제안안.md`로 제안되고 `omf-mes#198`로 데이터모델팀에 전달됐다(각 항목 카드의 「처리 현황」 줄 참고). 남은 건 이 29건을 뺀 23건 + 고정형 16건 + UIUX·정책·기타 전부다.

### §4-1. 고정형 (9건)

**1. '개발품' 판정 기준(품목 속성 vs 작업지시 유형) 확정**

- 무엇: ERP 실적 송신 시 '개발품 제외' 규칙의 판정 축이 문서마다 다르다 — 화면 인벤토리 W-06-05는 품목 속성(개발품 플래그)으로, 설계결정 14·개념모델 v2.0은 W/O 유형으로 서술한다. QA#35 '개발품 제외' 확정 자체가 주어 불명확한 채로 확정돼, §I 대장의 하류 전파 문제가 아니라 애초에 상류 확정이 두 갈래로 갈린 상태다. omf-mes#70으로 질의는 나가 있으나 2026-08-22 기준 회신 없음.
- 근거: omf-mes#70 · 공유계약.md §I-14
- 영향 화면: W-06-05, W-06-12
- 고정/변동: **고정형** — 개발품을 어느 축(품목 vs W/O)으로 판정할지는 MES 내부 데이터 구조·ERP 연계 로직 설계의 문제이며 고객사 운영 방식에 따라 달라질 사안이 아니다.
- 중요도: **높음** — 판정 축을 잘못 고르면 ERP 송신 제외 로직·품목 마스터·작업지시 마스터 양쪽의 데이터 구조가 갈려 나중에 비즈니스 로직 자체를 다시 설계해야 하는 큰 이슈로 번진다.

**2. 결정08 재검토 — '재고 행에 품질 상태 축을 두지 않는다'를 물리 모델이 뒤집었다**

- 무엇: 결정08(2026-07-06)은 재고 행에 가용/Hold 상태 축을 두지 않기로 확정했으나 물리 모델은 17일 뒤 inventory_balance.quality_status_code를 NOT NULL로 반대 설계했다. 재검토 결과 결정08의 우려(이원 관리로 정합 붕괴)는 성립하지 않고 오히려 하류가 맞다는 반론이 §I 대장에 이미 적혀 있어, 데이터모델이 아니라 설계결정서 본문을 다시 검토해야 한다. 관련해 도식스펙-01(한도승인≠합격품 서술)도 함께 정정이 필요하다고 omf-mes#115가 지적한다.
- 근거: 공유계약.md §I-45 · omf-mes#115
- 영향 화면: W-01-07, W-03-01, W-03-02 등 재고·품질 상태 조회 전 화면, 도식스펙-01
- 고정/변동: **고정형** — 재고 행이 품질 상태를 직접 보유할지 여부는 시스템 내부 데이터 아키텍처 결정으로 고객사 운영 방식에 따라 달라지는 값이 아니다.
- 중요도: **높음** — 이미 확정된 아키텍처 원칙을 뒤집는 재검토라, 설계팀이 지금 임의로 한쪽으로 밀어붙이면 나중에 정답이 다르게 확정될 경우 재고·품질 도메인 전반의 조회·집계 로직을 다시 갈아엎어야 한다.

## ⚠ 분류표가 놓친 자리 (2026-08-23 추가 · 앞 2건 종결 · 신규 표면화 1건)

⭐ **이 표는 실측 스냅숏이라 빈틈이 생길 수 있다**(§1 마지막 문단). 실제로 하나가 드러났으므로 지우지 않고 적어 둔다 — **놓친 것을 적어 두지 않으면 다음에 또 같은 방식으로 놓친다.**

| 무엇 | 왜 놓쳤나 | 결말 |
| --- | --- | --- |
| **세션 수준 중단 사유 `work_session.stop_reason_code`의 값 목록** | 같은 테이블 묶음의 **두 계층에 같은 성격의 칸**이 있는데(세션 `stop_reason_code` ↔ 사건 `reason_code`), 사건 쪽만 항목 46으로 잡히고 세션 쪽은 안 잡혔다. 자료원인 미확정 코드 계수기가 **한 자리를 세면 짝을 안 센다** | ✅ **종결(2026-08-23 사용자 확정)** — **쓰지 않기로 했다.** 요구 원천도 채울 화면도 없어 공유계약 **`A-21`**(자리가 있다고 채우지 않는다)로 **비우고 비우는 이유를 계약에 적었다**(`A-25` 해당 절 · `P-02-10` §8-1). 값 목록을 만들 일이 없어졌다 |
| ⭐ **`WORK_SESSION_EVENT_REASON`에 `QA #25`(CTO 확정)의 값 둘이 빠져 있었다** | 값을 제안할 때 **화면 목업만** 봤다. **미확정 코드 계수기는 계약(`enum` 부재)을 보고 값 제안은 화면 스펙을 보는데, 「CTO 확정 기록에 값이 적혀 있는 경우」를 두 경로 다 안 본다** | ✅ **정정(2026-08-23)** — 「긴급 오더 끼어들기·도구 고장」을 더해 **5 → 7값**. `omf-mes#198` 에 정정 통지 |

| ⭐ **작업 세션 상태(`work_session.status_code`)의 값 목록** | ⚠ **놓친 게 아니라 이번에 새로 드러났다** — 세션 모델 모순을 가르면서 이 칸이 「진행·중단·종료」를 담는다는 게 확정됐는데, **그 뜻을 담을 코드 문자열이 어디에도 없다.** 계약에도 설명이 없던 칸이라 미확정 코드 계수기(`enum` 부재로 뽑는다)에도 안 걸렸다 | ⬜ **미정 — 지금 만들지 않는다.** 뜻은 확정됐고 식별자는 아직이다(「뜻과 식별자는 다른 산출물」 · `G-32` v3.4). 계약의 `statusCode` 설명에 「코드 문자열은 아직 확정되지 않았다」로 표면화해 뒀다 · 작업 시작 화면(`P-02-01`) §8 미결 6 |

⛔ **둘째 줄이 더 무겁다.** 첫째는 「칸 하나를 안 셌다」지만, 둘째는 **값의 출처 한 갈래를 통째로 안 보고 있었다**는 뜻이다. **같은 방식으로 놓친 값이 다른 그룹에도 있을 수 있다** — 확정기록류(`2026-07-04-현장검증-QA-확정기록`·`2026-07-06-설계결정서-14건`·날짜별 확정기록)에 코드 후보가 적혀 있는 자리를 전수로 훑는 작업이 따로 필요하다.
