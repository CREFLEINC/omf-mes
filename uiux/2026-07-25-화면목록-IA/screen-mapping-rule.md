## 표기 안내 — 이 문서에 나오는 기호

읽다가 막히면 여기로 돌아오면 된다. **이 문서 안에서는 기호 대신 이름을 쓴다.** 아래 기호는 다른 문서(도식스펙·워크플로우)에서 넘어온 것이라 그대로 인용할 수밖에 없는 것들이다.

| 기호 | 뜻 | 예 |
| --- | --- | --- |
| `219:4511` 꼴 | **FigJam 캔버스 노드 번호.** 도형 하나를 가리키는 고유 번호다 | `946:6724` = 자재 LOT 번호 스캔 도형 |
| `01-S-A` 꼴 | **사이드 섹션.** `S`는 Side(곁가지). 메인 흐름에서 빠져나온 예외·분기 구간이다 | `01-S-A` = 입하 오류 처리 곁가지 |
| `A1`·`B7`·`M4`·`SC3` 꼴 | **도식 안 노드 이름표.** 도식스펙이 설명하려고 붙인 번호다. `SC3`처럼 `S`+사이드문자로 시작하면 그 사이드 안의 노드 | `M4` = 04 메인 네 번째 축 |
| `WF01 4단계` | **워크플로우 문서의 업무 단계.** 원문은 `S4`로 적혀 있으나 이 문서에서는 「4단계」로 풀어 쓴다 | WF01 4단계 = 입고(G/R) |
| `W-01-01` / `P-` / `M-` | **화면 번호.** 앞 글자가 프로그램 — W=관리웹, P=POP, M=모바일 | `M-01-01` = 모바일 입하 등록 |

## ⚠ 이 규칙의 위상 — 답을 내는 도구가 아니다

**규칙 적용 결과는 초안이고, 최종 확정은 사람이 한다** (사용자 결정 2026-07-28).

v1.0 초안을 검토한 결과, 나누는 조건뿐 아니라 **묶는 조건에도 주관이 개입하는 여지가 크다**는 판단이 나왔다. 「끊김 없는 연속 조작」이나 「앞 단계 결과가 곧 다음 입력」은 문장으로는 깔끔해도 실제 적용에서 사람마다 다르게 읽힌다. 규칙 문구를 아무리 다듬어도 이 여지는 없어지지 않는다.

그래서 규칙의 목적을 바꾼다.

- **하지 않는 것**: 753행의 화면 귀속을 규칙이 최종 결정한다
- **하는 것**: 규칙으로 **객관적으로 결정되는 것과 사람이 봐야 하는 것을 갈라낸다**

기계 처리의 가치는 정답을 맞히는 데 있지 않고, **사람이 검토할 대상을 753행에서 수십 행으로 줄이는 데** 있다. 그러려면 규칙이 **자기가 확신하지 못하는 지점을 스스로 표시**해야 한다. 조용히 결정해버리면 사람은 전부 다시 봐야 하고, 그러면 기계 처리를 한 의미가 없다.

### v1.3이 배운 것 — 보류의 대부분은 주관이 아니라 **기준 부재**였다

2026-07-29 4단계(사람 확정)를 끝내고 보니, 보류 89건 중 **47건(53%)이 다섯 개의 기준 하나로 한꺼번에 닫혔다.** 사람마다 다르게 읽힐 판단이라서 보류가 된 게 아니라, **규칙에 판정 기준이 아예 없어서** 밀린 것이었다.

그래서 v1.3은 그 다섯 기준을 규칙에 되먹인다. 주관성을 없애려는 시도가 아니다 — **주관인 줄 알았던 것 중 사실은 객관이었던 것을 골라내는 것**이다. 그 결과 §3-4의 주관 조건이 **넷에서 하나로 준다.**

| 기준 | 어디에 | 3단계에서 닫지 못했던 수 |
| --- | --- | ---: |
| 축 노드는 화면이 아니다 (`축상태` 신설) | §1 · §2 | 14 |
| 관리웹 절단 = 저장 엔티티 | §3-3 | 13 |
| 「작업 끊김」 조작적 정의 | §3-1 | 11 |
| 라벨 = 발행 시점 | §3-3 | 8 |
| 목록(Wallet) = 진입 경로 | §3-2 | 6 |

**남은 진짜 주관은 「결과가 입력으로」 하나다.** 이건 데이터 흐름 해석이라 업무를 아는 사람만 판정할 수 있고, v1.1의 진단(주관성은 역할 분담이지 해결 대상이 아니다)이 여기에는 그대로 유효하다.

## 0. 왜 필요한가

화면 목록 v1.0의 적대 검증에서 나온 **분해 기준 부재** 문제가 출발점이다(검증 보고서에서 「M8」로 적은 항목). 같은 문법 요소(Wallet=목록)를 04에서는 독립 화면으로 뽑고 05·06에서는 흡수해, **분해 기준이 도메인마다 달랐다.** 그 결과 「화면 112건이 WBS 추정보다 많으니 누락 없음」이라는 커버리지 근거가 성립하지 않게 됐다.

규칙 없이 화면을 하나씩 더하고 빼는 건 같은 문제를 반복하는 것이다. 먼저 기준을 정하고 전 도메인에 똑같이 적용한다.

## 1. 산출물 규약 — 모든 행은 처분을 받는다

노드 대장의 **모든 행**에 **처분**과 **확정도** 두 값을 부여한다. 빈칸을 허용하지 않는다.

**처분** — 다음 중 하나
- **화면 ID** (`W-01-01` 형식) — 이 노드가 그 화면에 속한다
- **`화면없음:<사유코드>`** — 화면이 아니다. 사유를 반드시 명시한다

**확정도** — 다음 중 하나 (§3-4에서 판정)
- **`확정`** — 객관 근거만으로 결정됐다. 사람 검토 불요
- **`보류`** — 주관 판단이 개입했다. **사람 확정 대상**
- **`근거`** — 왜 그렇게 판정했는지 한 줄. 보류는 **무엇이 갈리는지**를 반드시 적는다

빈칸을 금지하는 이유는 단순하다. **처분이 없는 행은 「검토했으나 화면이 아니다」와 「빠뜨렸다」를 구분할 수 없다.** 대장을 만든 목적 자체가 그 구분이다.

확정도를 함께 요구하는 이유도 같다. **확정과 보류를 구분하지 않으면 사람이 753행을 전부 다시 봐야 한다.** 기계 처리의 가치는 검토 대상을 줄이는 데 있다.

## 3. 행위 노드 → 화면 병합 규칙

### 3-1 · 나누는 조건 — 하나라도 해당하면 별도 화면

| 조건 이름 | 무엇을 보는가 | 판정 근거 |
| --- | --- | --- |
| **사용자 바뀜** | 이 일을 하는 사람이 달라지는가 | 대장의 인접 User 노드. 물류담당→품질담당이면 별개 |
| **단말 바뀜** | 쓰는 기기가 달라지는가 | **`placement-plan.md` 배지가 기계적 정답을 준다** |
| **작업 끊김** | 한자리에서 이어서 하지 못하는가 | **(v1.3 조작적 정의)** **실물 작업이 끼어 있고 전후가 다른 데이터를 다루면 분리. 같은 레코드를 이어서 완성하면 한 화면.** 아래 상술 |
| **따로 진입** | 앞 단계 없이 바로 들어올 수 있는가 | 관리웹 메뉴·모바일 홈 타일·POP 태스크 목록에서 직접 진입 |

**단말 바뀜**은 이미 정답이 있다. 배지 정본의 63배치는 적대 검증에서 인벤토리와 **충돌 0**으로 확인됐고, 2단말 스택 3건(`04-S-D`·`05-S-B`·`05-S-D`)이 정확히 화면 2개로 분해된 것도 이 기준이 작동한 결과다.

#### 「작업 끊김」의 조작적 정의 (v1.3 신설)

v1.2의 「**시간이 벌어진다**」는 잴 수 없어서 판정이 사람마다 갈렸다. 대신 **잴 수 있는 것**으로 바꾼다.

> **실물 작업이 끼어 있고 전후가 다른 데이터를 다루면 분리.**
> **같은 레코드를 이어서 완성하면 한 화면.**

「시간이 벌어지는가」는 관측이 필요하지만 「같은 레코드를 마저 채우는가」는 **도식과 개념모델로 판정**된다. 실물 작업의 개입만으로는 부족하다 — 그건 거의 모든 현장 흐름에 있다. **다루는 데이터가 갈리는지**가 실제 분기점이다.

| 사례 | 판정 | 근거 |
| --- | --- | --- |
| 05 보전지시 ↔ 보전실적 | **분리** | 지시는 *계획* 데이터, 실적은 *실적* 데이터. 사이에 `784:7966` 보전수행 물리 작업 실재 |
| 02 수리 투입 스캔 ↔ 반출 스캔 | **1화면** | **같은 수리이력 레코드**의 시작과 종료 |
| 01 반출 QR 스캔 ↔ 도착 스캔 | **1화면** | 같은 이동 레코드 |
| 04 반품입고 등록 ↔ 재고 재등록 | **분리** | 사이에 03 판정·재작업이 끼고 다루는 재고 상태가 다르다 |

4단계 적용 결과 **11건 전부 현행 인벤토리와 일치**했다. 현행이 감각적으로 옳게 잘랐다는 뜻이고, 이 정의는 그 감각에 이름을 붙인 것이다.

### 3-2 · 묶는 조건 — 전부 충족해야 한 화면

| 조건 이름 | 뜻 |
| --- | --- |
| **같은 사용자** | 처음부터 끝까지 한 사람이 한다 |
| **같은 단말** | 기기를 바꾸지 않는다 |
| **연속 조작** | 중간에 다른 사람이나 시간 경과가 끼지 않는다 |
| **결과가 입력으로** | 앞 단계에서 나온 것이 곧 다음 단계의 입력이 된다 |

예: `M-01-01 입하 등록`은 도식에서 「부착 여부 분기 → LOT 스캔 → P/O 후보 선별 → P/O 선택 → 거래명세서 촬영 → 품목·수량 확인 → 등록」 여러 노드지만, 창고 담당자가 PDA를 들고 한 자리에서 연속으로 하는 **한 작업**이라 한 화면이다. 여기서 노드마다 화면을 쪼개면 스캔할 때마다 화면을 넘나들어야 해서 「스캔 퍼스트」라는 모바일 IA 원칙과 정면으로 어긋난다.

#### 목록(Wallet) 노드 처리 — 진입 경로로 가른다 (v1.3 신설)

**적대 검증 M8의 직접 처방이다.** v1.2까지는 위 worked example이 Wallet 흡수를 *보여주기만* 하고 원칙을 적지 않아, 04는 독립 화면으로 뽑고 05·06은 흡수하는 불일치가 생겼다. 그래서 화면 수 집계가 커버리지 근거로 못 쓰이게 됐다.

> **독립 화면** — 메뉴나 홈 타일에서 **조회 목적으로 직접** 들어가는 목록
> **흡수** — 작업 흐름 한가운데서 **대상을 고르려고** 여는 목록

이 차이는 UI 구조가 아니라 **업무 진입 동선**이라 도식 문법으로는 보이지 않는다. Wallet은 대부분 바로 다음 행위의 입력 선택 단계라 「결과가 입력으로」가 성립하지만, 「출하 예정 조회」·「PM 도래 조회」는 목록 자체가 업무의 시작점이고 담당자가 하루에 몇 번씩 그것만 보러 들어온다.

| 노드 | 판정 |
| --- | --- |
| 04 `825:8404` 출하 예정 목록 · 05 `780:7866` PM 도래 목록 | **독립** |
| 04 `825:8417` 피킹 목록 · 05 `749:7637` 점검 항목 · 05 `784:8028` 예비품 목록 · 06 `717:7474` 송신 항목 목록 | **흡수** |

### 3-3 · 프로그램별 보정

세 프로그램의 IA 모델이 다르므로 **따로 진입**의 해석이 갈린다.

- **관리웹** — 메뉴 트리. **저장되는 엔티티가 다르면 다른 화면이다**(v1.3). 판정·전표·마스터는 원래 독립성이 높다.
- **POP** — 사번 인증 → W/O 태스크 모드. **메뉴가 아니다.** 태스크 흐름 안의 단계는 묶는 쪽이 기본이고, 별도 스테이션(창고 라벨 출력·설비 수집)만 독립 진입을 갖는다. **라벨 출력은 발행 시점으로 가른다**(v1.3).

#### 관리웹 절단 기준 — 저장 엔티티 (v1.3 신설)

v1.2의 「메뉴 항목이 되면 독립 화면이다」는 **순환 정의**였다 — 무엇이 메뉴 항목이 되는지를 알려주지 않는다. 그래서 관리웹 구간은 액터도 단말도 하나여서 객관 절단선이 **하나도 없었고**, 02 축1은 1화면부터 6화면까지, 03은 1~4화면이 다 성립했다.

> **저장되는 엔티티가 다르면 다른 화면.**

관리웹 메뉴 트리는 결국 **데이터 관리 단위**를 따른다. 사용자가 "무엇을 다루러 왔는가"가 메뉴 항목이 되지, 프로세스 단계가 메뉴가 되지는 않는다. 이 기준의 장점은 **도식이 아니라 개념모델을 근거로 삼는다**는 점이다 — 엔티티는 이미 정의돼 있으므로 판정이 재현 가능하다.

| 구간 | 판정 |
| --- | --- |
| 02 축1 | **4화면** — P/O 수신·W/O 전개·4M 배정·확정 배포가 각각 다른 엔티티. **조회일 뿐 저장하지 않는 노드는 내부 패널로 흡수**(`339:6639`·`330:6677`) |
| 03 판정 지점 | **2화면** — 의심자재 등록은 Lot Status를 *생성*, 판정·전이는 *변경* |
| 05 `793:8131` 캘린더설정 | **독립** — WorkCalendar는 마스터 엔티티 |
| 06 `676:7123` 운영마스터 | **분해** — 창고/Location과 예비품은 별개 엔티티 |

#### 라벨 출력 — 발행 시점으로 가른다 (v1.3 신설)

POP 보정의 「별도 스테이션(창고 라벨 출력·설비 수집)만 독립 진입」이라는 예외에 **생산·출하 라벨이 해당하는지가 규정돼 있지 않아** 8건이 보류였다.

> **발행 시점이 앞 작업과 다르면 분리, 같은 작업의 마무리면 흡수.**
> **「부착」은 화면 밖이다** — 라벨 노드 라벨이 「출력 및 부착」이어도 뒷부분은 물리 작업이므로 화면 범위는 **출력까지**로 자른다.

예: 04 `826:8462` A9 납품라벨은 **OQC 합격**이 트리거이고 `826:8488` A11 포장라벨은 **O1 일치 통과 후 사전발행**이라 발행 시점이 서로 다르다 → 분리. 반면 02 `492:7814`·`492:6693`은 둘 다 실적 등록 직후라 시점이 같다 → 병합 검토 대상.
- **모바일** — 스캔 퍼스트 홈 타일. 타일 하나가 하나의 작업 단위다. 타일 안의 스캔 연쇄는 묶는다.

### 3-4 · 확정도 판정 — 무엇이 객관이고 무엇이 주관인가

§3-1·§3-2의 조건은 **객관성이 서로 다르다.** 이걸 구분하지 않고 뭉뚱그린 것이 v1.0 초안의 결함이었다.

| 조건 | 판정 근거 | v1.2 | **v1.3** |
| --- | --- | --- | --- |
| **사용자 바뀜** | 대장의 인접 User 노드 — 있거나 없거나다 | 객관 | **객관** |
| **단말 바뀜** | `placement-plan.md` 배지 정본이 정답을 준다 | 객관 | **객관** |
| **작업 끊김** | **§3-1 조작적 정의 — 전후가 다른 데이터를 다루는가**(도식·개념모델로 판정) | 주관 | **객관** ⬆ |
| **따로 진입** | 목록은 **진입 경로**(§3-2), 관리웹은 **저장 엔티티**(§3-3), 라벨은 **발행 시점**(§3-3) | 혼합 | **객관** ⬆ |
| 같은 사용자 · 같은 단말 | 위 두 객관 조건의 이면 | 객관 | **객관** |
| **연속 조작** | 「작업 끊김」의 이면 — 같은 정의를 반대로 읽는다 | 주관 | **객관** ⬆ |
| 결과가 입력으로 | 데이터 흐름 해석 | 주관 | **주관** |

**v1.3에서 주관 조건은 「결과가 입력으로」 하나만 남는다.** 나머지 셋은 4단계에서 사람이 만든 판정 기준이 규칙에 들어오면서 객관으로 옮겨갔다. 이건 주관을 확정으로 위장한 것이 아니다 — **판정 근거가 도식·개념모델·배지 정본이라는 외부 정본에 있고, 다른 사람이 같은 근거로 같은 답에 도달할 수 있다.**

### 판정 원칙

- **사용자 바뀜·단말 바뀜만으로 갈린 경계 → `확정`.** 배지가 웹↔POP으로 바뀌는 지점, 물류담당↔품질담당이 바뀌는 지점은 사람이 다시 볼 필요가 없다.
- **작업 끊김·따로 진입·연속 조작·결과가 입력으로가 개입한 경계 → 무조건 `보류`.** 결과가 그럴듯해도 보류다. 판단이 들어갔으면 표시한다.
- **분류별 기본 처분(행위 외 7분류) → `확정`.** 유형에서 기계 파생이라 판단이 없다. 단 「확인 필수」가 붙은 `사람`·`게이트`는 흡수 대상이 실제로 반영됐는지 대조한 뒤 확정한다.
- **애매하면 보류.** 확정으로 잘못 넣으면 사람 눈을 영영 못 거치지만, 보류로 잘못 넣으면 검토 한 번 더 하고 끝난다. **비용이 비대칭이므로 보류 쪽으로 기운다.**

### 보류 행에 반드시 적을 것

「보류」만 적고 끝내면 사람이 처음부터 다시 판단해야 한다. **무엇이 갈리는지**를 적어야 검토가 빨라진다.

> 나쁜 예: `보류 — 판단 필요`
> 좋은 예: `보류 — 작업 끊김. 입하 등록(219:4521)과 LOT 등록(219:4571) 사이에 「수입 검사 대기」 축 상태(219:4512)가 끼어 세션이 끊기는지 애매. 끊긴다고 보면 2화면, 아니면 1화면`

## 4. 적용 순서

**1~3은 기계, 4가 사람이다.**

1. **기계 처분** — `행위` 외 7분류에 §2 기본 처분을 일괄 적용한다. 판단 없음 → 전부 `확정`.
2. **객관 경계 확정** — 행위 노드에 **단말 바뀜을 먼저 적용**해 배지 경계로 자르고, 이어 사용자 바뀜으로 자른다. 여기까지로 갈린 그룹은 `확정`.
3. **주관 경계 표시** — 남은 그룹 안에서 작업 끊김·따로 진입·연속 조작·결과가 입력으로를 적용하되, **결정하지 말고 후보와 갈리는 지점을 적어 `보류`로 남긴다.**
4. **사람 확정** — 보류 행만 검토해 최종 귀속을 정한다. **이 단계 산출이 정본이다.**
5. **대조·재검증** — 확정된 화면 집합을 현행 112건과 맞춘다. 차이가 누락·과잉이고, 적대 검증의 누락 15·과잉 7이 살아남는지 본다. 규칙으로 설명되는 건 지적이 아니라 규칙 적용 결과다.

### 성공 기준

3단계가 끝났을 때 **보류 비율이 얼마나 낮은가**가 이 규칙의 품질이다. 보류가 지나치게 많으면 규칙이 일을 안 한 것이고, 지나치게 적으면 주관을 확정으로 위장한 것이다.

**⚠ 반드시 행위 노드 기준으로 읽는다(v1.3).** 비행위 7분류는 §2 기계 파생이라 판단 없이 확정되므로 분모를 부풀린다. 초회 적용의 전체 보류율 11.8%는 **착시**였고 실질은 **행위 220건 중 약 36%**였다.

**초회 실측(2026-07-28~29)** — 3단계 보류 89(행위 기준 36%) → 4단계 사람 확정 후 **존치 5(0.7%)**. 보류 89 중 **47건(53%)이 다섯 기준 하나로 닫혔고**, 그 기준을 v1.3이 규칙에 되먹였다. 남은 존치 5건은 판단이 어려워서가 아니라 **외부 입력 대기**다(고객 회신 3·도식 수정 1·고객사 협의 1).

**v1.3 적용 시 기대치** — 같은 입력을 다시 돌리면 보류가 89 → 약 40으로 준다. 이 값이 다음 회차의 기준선이다.

## 5. 이 규칙이 답하지 못하는 것

정직하게 남긴다.

**주관성 자체는 더 이상 「해결할 문제」가 아니다.** v1.0은 규칙 문구를 다듬으면 주관이 사라질 것처럼 썼지만, 작업 끊김·연속 조작·결과가 입력으로는 업무 실태를 아는 사람만 판정할 수 있는 종류다. v1.1은 이를 없애려 하지 않고 **보류로 표시해 사람에게 넘기는 것**으로 처리한다. 규칙의 실패가 아니라 역할 분담이다.

남는 진짜 한계는 셋이다.

- **대시보드·조회 화면은 이 규칙 밖이다.** 이 규칙은 도식 노드에서 화면을 도출하므로, 도식 앵커가 없는 화면은 아예 대상이 아니다. 적대 검증이 지적한 대시보드 5건 난립(W-02-09·W-03-08·W-CO-05·W-05-14·W-04-09)이 여기 해당한다. **REQ·WF 단계를 근거로 하는 별도 도출 체계가 필요하다** — 이 규칙으로는 판정도 반박도 못 한다.
- **1화면의 노드 수 상한이 없다.** 하한(1노드 1화면 아님)은 §3-2에 있지만 상한은 없다. 실무상 한 화면이 10노드를 넘으면 재검토 신호로 보되, 이건 경험칙이지 규칙이 아니다.
- ~~**보류 비율의 적정선을 모른다.**~~ → **초회 실측으로 해소(v1.3)**. 3단계 행위 기준 36% → 4단계 후 존치 0.7%. v1.3 기준으로는 3단계 보류가 절반으로 줄 것으로 본다(§4 성공 기준).
- **입력(노드 대장)의 신뢰도는 이 규칙 밖이다(v1.3 신설).** 규칙은 대장을 참으로 놓고 돌아간다. 그런데 초회 적용에서 대장의 **「캔버스 미작화」 판정 2건이 모두 오판**이었다 — 04 `H7`(실물 `838:8635`)과 H6 「예」 분기(`840:8642`)가 **페이지 직속 커넥터**여서 섹션 자식 조회에 안 잡혔을 뿐 실재했다. 원인은 FigJam 커넥터를 섹션에 append하면 좌표가 재해석돼 불안정하므로 **페이지레벨+절대좌표 패턴**을 쓰기 때문이다. 이 오판 하나가 4단계에서 「도식 결함이라 판단 불가」라는 잘못된 존치를 낳았다.
  **→ 「캔버스에 없다」는 결론은 「내 조회 범위에 없다」와 구별되지 않는다. 부재를 주장할 때는 조회 범위를 함께 진술한다.**
