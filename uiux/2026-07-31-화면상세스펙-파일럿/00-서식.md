# 화면 상세 스펙 서식 (v0.1 초안)

> 작성일: 2026-07-31 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **미확정 — 파일럿 4장을 마친 뒤 v1.0으로 확정한다.** 이 서식이 나머지 105장의 틀이 되므로, 파일럿에서 안 맞는 것이 나오면 **화면이 아니라 서식을 고친다.**
> 위상: 화면 인벤토리 v1.3(109건)·IA 3종이 「어떤 화면이 있는가」를 정했고, 이 서식은 「그 화면이 무엇으로 이루어지는가」를 정한다.

## 1. 원칙 3가지

1. **스펙과 와이어프레임은 한 장이다.** 분리하면 필드를 두 번 정의하고 두 번 어긋난다.
2. **필드는 지어내지 않는다.** 물리 모델 컬럼에서 오거나, 없으면 `[미결]`로 남긴다. 「있으면 좋을 것 같은 필드」는 쓰지 않는다.
3. **모양은 정하지 않는다.** 색·타이포·간격은 `@crefle/web-ui` 토큰이 이미 정했다. 우리가 정하는 것은 **무엇을 어떤 컴포넌트로 어떻게 배치하는가**까지다.

## 2. 입력은 4면이다

| 면 | 원본 | 무엇을 가져오나 |
| --- | --- | --- |
| **프로세스** | `deliverables/05` | 단계(S/사이드) · 행위자 · 단말 · 태스크 순서 · 예외 |
| **화면·IA** | `deliverables/04` · 인벤토리 v1.3 | 화면 ID·명·유형·행위자·주요 데이터·근거·신뢰도 · IA 위치 |
| **요구** | `deliverables/01` | REQ 원문 요지 · 확정/재정의 · 잔여 미결 |
| **데이터** | `docs/research/2026-07-23-데이터모델링/mes_postgresql_physical_model.sql` | 테이블·컬럼·타입·NOT NULL·UNIQUE·FK·CHECK |

⚠ 4면이 서로 어긋나면 **고치지 말고 §8 미결에 기록**한다. 정본 수정은 각 소관에서 한다(데이터모델은 읽기 전용 — `[docs→데이터모델]` 이슈).

## 3. 한 장의 구성 — 8블록

| # | 블록 | 내용 |
| --- | --- | --- |
| §1 | **식별** | 화면 ID · 명 · 프로그램 · 도메인 · 유형 · 행위자 · 신뢰도 |
| §2 | **근거 4면** | 위 표대로. 각 항목에 원본 경로·절 번호 병기 |
| §3 | **레이아웃** | 영역 분할과 배치. 충실도 기준은 §4 |
| §4 | **필드** | 라벨(한/베) · 출처 컬럼 · 타입 · 필수 · 유일 · 기본값 · 검증 · 편집 가능 여부 |
| §5 | **액션·상태** | 버튼과 활성 조건 · 화면 상태(초기/조회/편집/저장중/오류) |
| §6 | **예외·오프라인** | 실패·충돌·권한 없음·미동기. POP·모바일만 오프라인 항목 |
| §7 | **DS 매핑** | 사용 컴포넌트 · 갭이면 a·b·c·d 판정 |
| §8 | **미결** | 확인 필요 · 4면 불일치 · 회신 대기 |

## 4. 충실도 기준 — 폼팩터마다 다르다

| 폼팩터 | 규격 | 레이아웃 표기 |
| --- | --- | --- |
| 관리웹 | 데스크톱 브라우저 | **구조 기술로 충분** — 영역 분할·배치 순서·컬럼 구성을 글과 표로 |
| 모바일 | 360×720dp (Android 13 · 1080×2160 @xxhdpi) | 구조 기술 + 스크롤 단위 표시 |
| **POP** | **1024×768** · 터치 타겟 일반 56px↑ · 주요 64px↑ · 핵심 64~72px · 위험 72px↑ · 간격 8px↑(권장 12~16) | **실측 그리드 필수** — 헤더·액션바 제하면 본문 약 632px(≈56px 행 9~10행). **들어갈 것과 뺄 것을 치수로 판정해야 하므로 시각 도구로 그린다** |

**POP은 배치 자체가 설계 결정**이다. 「관리웹 화면을 축소해 얹기」는 성립하지 않으며 **한 화면 = 한 태스크**를 강제한다.

와이어프레임 이미지는 **`omf-mes`(비공개)에만** 둔다 — 공개 저장소 반출 금지 항목(`uiux/CLAUDE.md` §공개 저장소 반출 경계).

## 5. §4 필드표 규칙

| 열 | 규칙 |
| --- | --- |
| 라벨(한/베) | 베트남어 미정이면 `(미정)`. i18n 키 네이밍은 공유 계약에서 확정 |
| 출처 컬럼 | `스키마.테이블.컬럼`. 물리 모델에 없으면 **`[미결]`** — 지어내지 않는다 |
| 타입 | 물리 모델 도메인 그대로. `app.code_t`=varchar(50) · `app.name_t`=varchar(200) · `app.qty_t`=numeric(20,6)≥0 |
| 필수 | `NOT NULL` 여부. **조건부 필수는 CHECK 제약을 근거로 명시** |
| 유일 | UNIQUE 제약. **중복 검사 시점(blur/제출)을 함께 정한다** |
| 검증 | CHECK·FK·도메인 제약을 **사용자에게 보일 문구로** 옮긴다 |
| 편집 | 신규/수정 시 편집 가능 여부. ERP 수신본은 읽기 전용+확장 속성만(REQ-PR-0021 확정) |

**감사 컬럼(`created_at`·`created_by`·`updated_at`·`updated_by`)과 `version_no`는 필드표에 넣지 않는다** — 시스템이 채운다. 다만 `version_no`가 있으면 §5에 **낙관적 잠금 충돌 처리**를 반드시 쓴다.

## 6. §7 DS 매핑 규칙

갭은 네 갈래(`omf-mes-client/CLAUDE.md`·DS `docs/component-requests.md`):

| 유형 | 뜻 | 처리 |
| --- | --- | --- |
| **a** | 그대로 있다 | 컴포넌트명·주요 prop만 적는다 |
| **b** | 컴포넌트는 있으나 변형·prop이 없다 | DS 이슈 후보 — `ds-gap.md`에 등재 |
| **c** | 기존 컴포넌트의 **조합** | 제품이 소유. 이슈 없음. 조합 구성만 적는다 |
| **d** | 진짜 새 원시 요소 | `ds-candidates/` 후보. **세 번째 사용처**에서 DS 승격 |

⚠ **c가 가장 많다.** 조합물을 DS로 올리려는 것이 디자인 시스템이 망가지는 가장 흔한 경로다. 「없다」고 적기 전에 조합으로 되는지 먼저 본다.

갭은 화면별로 적되 **이슈는 전 화면 매핑을 마친 뒤 몰아서** 낸다 — 빈도 신호가 티어·우선순위를 정하기 때문이다.

## 7. 파일·표기

- 파일명 `<화면ID>-<화면명>.md` (예: `W-06-07-창고Location마스터.md`)
- 마커는 docs 관례를 따른다 — `✅REQ-XX-nnnn` · `✓확정 YYYY-MM-DD QA #n` · `✓설계확정 결정 nn` · `[가설]` · `(확인 필요)`
- 원본과 어긋나면 원본이 이긴다. 채택한 쪽을 «(정합주: …)»로 밝힌다
