## §5. 액션·상태

### §5-1. ★ 같은 레코드를 두 화면이 다루는데 오프라인 정책이 반대다

```
W-01-04  (관리웹)  ⛔ 오프라인 금지   ← 결정 08
M-01-11  (모바일)  ✅ 오프라인 허용   ← C-1
        ↑ 둘 다 inventory_count / _line 을 다룬다
```

**§C 어디에도 「어느 화면이 오프라인을 허용하는가」의 목록이 없다.** C-1~C-4는 「오프라인이면 이렇게 한다」만 정하고 **누가 오프라인인지는 정하지 않는다.**

4차에서 세 갈래가 다 나왔다:

| 정책 | 화면 | 근거 |
| --- | --- | --- |
| **오프라인 허용** | `M-01-04`·`05`·`07`·`08`·`09`·`10`·`11` | C-1 |
| ⛔ **오프라인 금지** | **`W-01-04`** | 결정 08 |
| ⛔ **온라인 전용** | `M-02-01`·`M-02-02` | ✓확정 2026-07-24 #2·#3 |

⚠ **「금지」와 「온라인 전용」이 같은 말인가**가 정리되어 있지 않다. 배지 정본은 웹에 「오프라인 금지」, 02 모바일에 「온라인 전용」이라고 서로 다르게 적었다.

**해석**: 같은 뜻이고 **표현만 갈렸다**. 다만 이유가 다르다 —

| | 이유 |
| --- | --- |
| `W-01-04` 오프라인 금지 | **관리웹은 애초에 오프라인을 만들지 않는다**(셸 성격) |
| `M-02-01`·`M-02-02` 온라인 전용 | **모바일인데 예외로 금지**(업무 성격 — 실시간 인계) |

**후자가 계약이 다뤄야 할 것이다** — 전자는 셸 규격이라 화면마다 적을 일이 없다.

→ **§C 신규 조항 후보** §9-1.

### §5-2. 블라인드는 개시 시에만 정한다

```
blind_count  boolean NOT NULL DEFAULT false
```

**실사가 시작된 뒤 바꾸면 안 된다** — 일부 라인은 장부를 보고 세고 일부는 안 보고 센 상태가 되어 결과의 성격이 섞인다.

**DB가 막지 않는다**(그냥 boolean 컬럼). **화면이 진다**(A-9 ⓐ 차단):

| 상태 | 블라인드 |
| --- | :-: |
| 개시 전(계획) | ✅ 편집 |
| **진행 중** | ⛔ **잠김** — G-3대로 사유 + 경로 표시 |
| 완료·마감 | ⛔ 잠김 |

```
진행 중에는 바꿀 수 없습니다. 새 실사를 개시하세요.
```

⚠ **`M-01-11` §5-1의 「서버가 `system_qty`를 안 내려보낸다」와 짝이다** — 이 화면이 블라인드를 켜면 모바일 API 응답이 달라진다.

### §5-3. 웹에서 실물 수량을 고칠 수 있나

프로세스는 카운트를 **모바일 소관**으로 두었다(219:5551). 인벤토리도 「조정은 관리웹 `W-01-04`」라고 **역할을 갈랐다.**

**그런데 현장에서 실수가 나오면 어디서 고치나.**

| 안 | 동작 |
| :-: | --- |
| **① 웹 편집 불가** | 모바일에서 다시 센다 — 역할 분리가 깨끗하다 |
| **② 웹 편집 가능** *(권고)* | 재실사가 어려운 경우(먼 창고·야간)를 위해 · **누가 고쳤는지 남긴다** |

**②를 권고**하되 **`counted_by`를 바꾸지 않는다** — 실제로 센 사람은 그대로 두고 **수정 이력은 `audit.audit_event`**에 남긴다.

⚠ **`audit_event` 사용 규약이 없다**(§I-5 · #68). 규약이 없으면 「누가 고쳤나」를 되짚을 수 없다 → §8-2.

### §5-4. 「차이 없음」과 「미실사」를 화면이 갈라야 한다

`M-01-11` §5-2에서 정리한 대로 **미실사 라인은 전송되지 않는다.** 이 화면이 그 수신측이다.

| 라인 상태 | 판정 근거 |
| --- | --- |
| **카운트됨 · 차이 없음** | `counted_at` 있음 · `variance_qty = 0` |
| **카운트됨 · 차이 있음** | `counted_at` 있음 · `variance_qty ≠ 0` |
| **미실사** | ⚠ **행이 없거나 `counted_at`이 계획값** |

⚠ **`counted_at`이 `NOT NULL`이라 계획 라인에도 무언가 들어 있다.** 계획 생성 시 무엇을 넣는지가 미정이다 — 계획일? `clock_timestamp()`? **그 값으로 미실사를 판정하면 위태롭다.**

**화면 규칙**: 미실사 판정을 **`counted_by IS NULL`**로 한다(nullable이고 사람이 세야만 채워진다). 다만 **이것도 규약이지 제약이 아니다** → §8-1.

**프로세스의 「[차이 없음] 실사 결과 등록」 분기는 미실사가 0일 때만 성립**한다. 82건이 미실사인 채로 「차이 없음」이라 하면 안 된다.

```
실사 마감 활성 조건:  미실사 라인 = 0
```

### §5-5. 조정은 이 화면 밖이다 — 그러나 경계가 얇다

**v1.2 범위 축소**로 조정 등록(219:5554)이 `W-01-12`로 갔다. 근거는 「독립 메뉴: **ERP 조정 전표 + 승인 마커 (U-D1)**」 — 결재선과 전표 종류가 달라 화면을 가른 것이다(`W-01-05`·`W-01-06` 분리와 같은 기준).

**이 화면은 「조정 등록 →」 링크만 둔다.**

⚠ **그런데 조정 없이 마감할 수 있는가**가 정해지지 않았다. 차이가 6건 있는데 조정을 안 하고 마감하면 **장부와 실물이 다른 채로 실사가 끝난다.**

| 안 | |
| :-: | --- |
| **① 차이가 있으면 마감 불가** *(권고)* | 조정을 강제한다 — 결정 08의 「수불 원장=정본」과 맞는다 |
| ② 마감 가능 · 차이는 남김 | 미조정 실사가 쌓인다 |

**①로 설계**하고 **(U-D1) 승인 권한이 정해지면 재검토**한다 → §8-3.

### §5-6. 집계·조회 성능 — 5차 주제가 여기서 먼저 걸린다

창고 하나의 실사 라인은 **수백~수천 건**이다. `variance_qty`가 GENERATED STORED라 정렬·필터는 인덱스로 가능하나, **요약 4칸(계획/카운트/미실사/차이)은 집계 쿼리**다.

**규칙**: 요약은 **서버가 계산해 내려보낸다.** 화면이 전체 라인을 받아 세지 않는다 — 페이지네이션과 어긋난다.

→ 5차(`W-02-08`·`W-01-07`)의 「집계·조회 응답 설계」와 **같은 요구**다. §9-3.

## §9. 이 장에서 나온 공유 계약 후보

1. **★ §C가 「어느 화면이 오프라인인가」를 정하지 않는다** — 4차에서 세 정책이 다 나왔다(허용 7 · 금지 1 · 온라인 전용 2). **셸 성격상 오프라인이 없는 것**(관리웹)과 **모바일인데 업무상 금지한 것**(`M-02-01`·`M-02-02`)은 다르다. **후자를 계약이 목록으로 갖고 이유를 함께 적는다** (§5-1)
2. **같은 레코드를 두 셸이 다루면 편집 권한을 화면이 아니라 **컬럼 단위**로 가른다** — `counted_qty`는 모바일이 쓰고 `variance_reason_code`는 웹이 쓴다. 화면 단위로 「이 화면은 조회 전용」이라 하면 실무가 막힌다 (§5-3)
3. **요약·집계는 서버가 계산해 내려보낸다** — 화면이 전체 라인을 받아 세면 페이지네이션과 어긋난다. 5차의 조회 화면 주제가 4차에서 먼저 나왔다 (§5-6)
