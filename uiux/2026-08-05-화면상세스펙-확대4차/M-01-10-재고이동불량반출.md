### §3-1. 스캔 둘 사이에 **시간이 있다**

`M-01-05`(위치→LOT)의 두 스캔은 **연속**이지만, 이 화면의 ①반출과 ②도착 사이에는 **작업자가 물건을 들고 이동하는 시간**이 있다. 몇 분에서 수십 분이다.

**화면이 그 사이 유지되어야 한다** — 앱이 백그라운드로 가거나 화면이 꺼져도 ①의 결과가 살아 있어야 한다. **§5-4의 오프라인 문제가 여기서 나온다.**

## §5. 액션·상태

### §5-1. ⛔ 창고 안에서의 이동을 담을 헤더가 없다

```
CONSTRAINT ck_stock_transfer_warehouses
    CHECK (from_warehouse_id <> to_warehouse_id)
```

**프로세스 S8의 제목은 「재고이동 (창고·Location·파렛트 간)」**이다. 세 축 중 **창고 간만 이 테이블이 받는다.**

| 이동 | `stock_transfer` |
| --- | :-: |
| 자재창고 → 불량창고 | ✅ |
| 자재창고 → 생산창고 | ✅ (다만 그건 `goods_issue` 경로) |
| **A-01-03 → B-02-01**(같은 창고) | ⛔ **불가** |
| **파렛트 재편성**(같은 위치) | ⛔ **불가** |

**⚠ 이것이 `M-01-07`(임시 적치)의 복귀 경로를 막는다.** 01-S-D의 복귀는 「[정위치 이동] → 01-S-G」인데, **임시 위치도 정위치도 같은 자재창고 안**이다.

**수불 원장은 받아 준다:**

```
inventory_transaction_line:
    from_warehouse_id, from_location_id, to_warehouse_id, to_location_id
    CHECK ((from_location_id IS NOT NULL) OR (to_location_id IS NOT NULL))
```

**창고가 같아도 위치만 다르면 통과한다.** 즉 **이동 자체는 기록되나 「이동 건」이라는 업무 문서가 없다.**

**A-11 적용 — 물러난 수준**:

| 확정 | 물러난 수준 |
| --- | --- |
| 이동 = `stock_transfer` 헤더 + 라인 | **창고 간만** 헤더를 만든다 |
| 창고 내 위치 이동 | **`inventory_transaction` 직접 기록** — 헤더 없음 |
| 이동 이력 조회 | ⚠ **두 곳을 봐야 한다** |

**화면 설계**: 유형에 따라 **저장 경로가 갈린다.** 화면 구성은 같다(①반출 → ②도착).

```
창고가 다르면   → stock_transfer + line  (+ 수불 2건)
창고가 같으면   → inventory_transaction  (수불 1건 · from/to 위치)
```

→ **§I 신규 후보** §9-1 · **`[docs→데이터모델]` 이슈**.

### §5-2. 파렛트는 이동 그룹핑이지 재고 잠금 단위가 아니다

✓확정 QA #16: 「**파렛트=이동 그룹핑**(재고 잠금 단위 아님)·확인=**자재별** 출고 QR 스캔」

```
inventory.handling_unit           파렛트 자체
inventory.handling_unit_content   그 안의 품목 × LOT × 수량
inventory_transaction_line.handling_unit_id   (late FK 실재)
```

**확정이 정확히 데이터에 있다.** `handling_unit`은 `warehouse_id`·`location_id`를 갖되 **재고 잔액을 갖지 않는다** — 잔액은 `inventory_balance`가 위치·LOT 축으로 관리한다. 그룹핑일 뿐이라는 확정이 그대로다.

**화면 규칙**: 파렛트 단위를 선택해도 **확인 스캔은 자재별**이다(확정 문구). 파렛트 QR 한 번으로 끝내지 않는다.

| 단위 | ① 반출 | ② 도착 |
| --- | --- | --- |
| **자재별** | LOT QR ×N | 위치 QR ×1 |
| **파렛트** | 파렛트 QR ×1 → **내용 자재별 확인 스캔 ×N** | 위치 QR ×1 |

⚠ **「상황별 혼용(설정형)」** — 어느 단위를 쓸지 설정으로 정한다. `app.operation_policy`가 그런 파라미터를 담는 자리다(실측). 정책 코드 값은 미정 §8-2.

### §5-3. Hold LOT 이동 — (U-C1) 허용 정책 미정

프로세스: 「이동 대상 선택(219:5523 — **[Hold LOT 이동 시] → (U-C1)**)」 · 예외 E-7 ③ 「차단 판정 위치=Lot Status 조회 **확정**(결정 10)·**허용 정책 자체는 잔여** ⚠」

**어디서 판정하는지는 정해졌고 무엇을 할지는 안 정해졌다.**

| | 상태 |
| --- | --- |
| 판정 위치 | ✅ 결정 10 — 단일 지점. ⚠ 다만 **그 테이블이 없다**(`M-01-08` §5-2 · §I-11) |
| 허용 여부 | ⬜ **미정** |

**화면은 「경고 + 진행 가능」으로 시작**한다. 근거: **결정 14가 「홀드품 이동=재고이동 트랜잭션 **별개 기록**」을 확정**했다(WF02 S11 R77) — 이동 자체는 일어난다는 뜻이다.

⚠ **차단이 아니라 경고인 이유를 화면에 적는다**(G-5 — 확정 번호를 문구에):

```
보류 중인 LOT입니다. 이동은 별개로 기록됩니다 (✓설계확정 결정 14)
```

### §5-4. 반쪽만 저장된 이동 — 오프라인의 새 형태

`M-01-08`은 「출고」 한 번이면 끝나는데, 이 화면은 **①과 ② 사이에 시간이 있다**(§3-1).

| 시나리오 | 결과 |
| --- | --- |
| ① 반출 저장 → 오프라인 → ② 도착 저장 | ✅ 큐에 둘 다 — 순서 유지 필요(`M-01-09` §5-1) |
| ① 반출 저장 → **작업자가 그만둠** | ⚠ **`shipped_qty > 0, received_qty = 0`인 행이 남는다** |
| ① 반출 저장 → 앱 종료 → 재실행 | ⚠ **미완 이동을 화면이 되살려야 한다** |

**`ck_stock_transfer_qty CHECK (shipped ≤ requested AND received ≤ shipped)`** 는 **반쪽 상태를 허용**한다(`received_qty = 0`). DB가 막지 않으므로 **화면이 미완 목록을 보여야** 한다.

**규칙**: 화면 진입 시 **미완 이동(반출됨·미도착)을 먼저 보인다.** 없으면 새 이동으로 시작한다.

⚠ **그 목록을 오프라인에서 어떻게 얻나** — 로컬 큐에 있는 것은 보이나, **다른 단말이 반출한 건은 못 본다.** §8-3.

### §5-5. 불량 반출은 이동 뒤에 03으로 넘어간다

프로세스: 「[불량 반출 시] 불량창고 적치(219:5519) → **판정 → 03 전이도**(219:5520)」

**이 화면은 불량창고까지만** 한다. 재작업/폐기 판정은 03 소관이고 화면은 `W-01-06`(폐기 품의)·`W-03-*`이다.

⚠ **불량 사유를 이 화면이 받나** — REQ-OA-0007은 「언제·어떤 부품·몇 개」만 요구한다. **왜인지는 `quality.defect_record`**(`defect_code_id NOT NULL`)가 갖는데, **자재 불량은 `defect_record`의 대상이 아닐 수 있다** — 그 테이블은 `work_order_id NOT NULL`이라 **생산 불량 전용**이다.

**자재 불량 반출의 사유를 담을 자리가 없다.** `M-01-07`의 적치 사유와 같은 형태다 → §8-4.

## §9. 이 장에서 나온 공유 계약 후보

1. **⛔ 업무 문서 헤더가 받지 못하는 이동이 있다** — `stock_transfer`는 창고 간만 받고(`CHECK from <> to`) 창고 내 위치 이동은 `inventory_transaction` 직접 기록으로 물러난다. **같은 업무가 두 경로로 저장되면 조회 화면이 두 곳을 봐야 한다** — 스펙이 그 사실을 명시한다 (§5-1)
2. **두 스캔 사이에 시간이 있는 화면은 「반쪽 상태」를 화면이 되살려야 한다** — DB가 `received_qty = 0`을 허용하므로 미완이 남는다. **진입 시 미완 목록을 먼저 보이는 것이 이 유형의 표준 형태** (§5-4)
3. **「사유를 기록한다」가 확정인데 컬럼이 없는 곳이 늘고 있다** — `putaway_task`(적치 사유 · `M-01-07`)에 이어 `stock_transfer`(불량 반출·분실 사유). **`reason_code`를 가진 테이블과 없는 테이블의 경계가 업무 기준이 아니다** — 묶어서 이슈로 낸다 (§5-5)
