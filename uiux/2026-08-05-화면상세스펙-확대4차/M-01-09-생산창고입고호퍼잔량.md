## §5. 액션·상태

### §5-1. ★ 결정 17 시나리오 2 — 오프라인이 **화면 구성을 바꾼다**

> **✓확정 2026-07-24 #8 · 결정 17 시나리오 2**: 「정상 시 출고(01-S-E 모바일)·입고(01-S-F 모바일) **별개 단말** → 통신 두절 시 **입·출측 스캔 단일 단말 큐로 축퇴** · 복구 시 일괄 동기화」

**C-1~C-4 어디에도 이 조항이 없다.** §C는 「한 화면이 오프라인에서 어떻게 저장하는가」만 다루고, **「두 화면이 한 단말로 합쳐진다」**는 상황을 다루지 않는다.

| 상태 | `M-01-08` 출고 | `M-01-09` 입고(이 화면) |
| --- | --- | --- |
| **온라인** | 창고 단말 | 라인 단말 |
| **오프라인** | ⟵ **한 단말** ⟶ | |

**화면이 져야 하는 것 셋**:

1. **오프라인 진입 시 두 화면이 한 홈에 모인다** — 「출고 → 인계 → 입고」를 한 사람이 연속 수행
2. **큐 순서가 보장되어야 한다** — 입고가 출고보다 먼저 서버에 닿으면 `goods_issue_line_id`가 없어 거부된다. **C-2의 「건별 되돌리기」가 여기서는 위험**하다
3. **복구 시 일괄 동기화** — 두 화면 분량이 한 큐에 섞여 있다

⚠ **2번이 심각하다.** C-2는 「거부 건만 되돌린다·전체 롤백 금지」인데, **출고가 거부되면 그에 딸린 입고는 반드시 함께 거부되어야 한다.** 건별 독립이 아니다.

→ **§C 신규 조항 후보** §9-1.

### §5-2. `CHECK (received_qty <= issued_qty)` — 초과 수령을 DB가 막는다

예외 E-11 ①은 「라인 입고 검증 실패(**수량·품목 상이**): 차단? 반송? [확인]」을 남겼는데, **수량 초과는 이미 막혀 있다.**

```
ck_shopfloor_receipt_qty  CHECK (issued_qty >= 0 AND received_qty >= 0
                                AND received_qty <= issued_qty)
```

| 상황 | 처리 |
| --- | --- |
| **부족 수령**(500 출고 → 480 수령) | ✅ 허용 · `variance_qty = 20` · 사유 입력 |
| **초과 수령**(500 출고 → 520 수령) | ⛔ **DB가 막는다** — 화면도 차단 |
| **품목 상이** | ⚠ 스캔이 출고 라인과 매칭되지 않음 → 등록 불가 |

**「모델이 화면 설계보다 앞선」 두 번째 사례**(`M-01-08` §5-4 LOT 미지정에 이어). 예외 E-11 ①의 「차단? 반송?」 중 **초과는 차단으로 이미 정해져 있다.**

⚠ **실물이 더 왔을 때 무엇을 하나** — 초과분을 담을 자리가 없으니 **출고 쪽을 정정**해야 한다. 그 화면이 없다 → §8-1.

### §5-3. ⛔ 호퍼를 지정할 수 없다 — 설비—Location 매핑이 0건

**결정 08이 못박았다**: 「호퍼=**Location 모델링(설비—Location 매핑)**」.

**실측 결과**:

```
mdm.equipment   (18열)  → location_id 없음
mdm.location    (17열)  → equipment_id 없음
mdm.production_line     → location_id 없음
어느 방향으로도 매핑 컬럼이 없다
```

`mdm.location`은 `warehouse_id`·`parent_location_id`·`location_type_code`를 갖지만 **설비와 이어지지 않는다.**

**A-11 적용 — 물러난 수준**:

| 확정 | 물러난 수준 |
| --- | --- |
| 호퍼 = 설비에 매핑된 Location | **Location 코드로만 지정**(설비 연결 없음) |
| 「1호기 호퍼」 선택 | **「L1-HOP-01」 코드 선택** — 어느 설비인지 화면이 모른다 |
| 설비 기준 잔량 집계 | ⛔ **불가** |

화면은 **`location_type_code`가 호퍼인 위치 목록을 그대로 보이는 것**으로 시작한다. 값 목록이 미정이라 **G-2 비활성 + 사유 표시**가 현재 상태다.

→ **§I 신규 후보** §9-2 · **`[docs→데이터모델]` 이슈**.

### §5-4. 잔량 입력은 조정 트랜잭션이다 — 실사 헤더 없이도 된다

결정 08: 「실측 입력=**실사 계열 조정 트랜잭션**으로 수불 원장 기록」.

```
inventory_adjustment.inventory_count_id   bigint     ← nullable (실측)
                                                       REFERENCES inventory_count
```

**nullable이라 실사 헤더 없이 조정만 만들 수 있다.** 호퍼 잔량은 실사 계획에서 나오는 것이 아니라 **입고 시점에 발생**하므로 이 형태가 맞다.

```
① inventory_adjustment (reason_code = 호퍼 실측)
② inventory_transaction + line  (from = 호퍼 Location · 차이만큼)
③ inventory_balance 갱신은 서버 전기
```

⚠ **`inventory_adjustment.approval_request_id`가 있다**(late FK 실재). 호퍼 실측에 승인이 필요한가 — `W-01-04`의 (U-D1)과 같은 미결이다. §8-4.

### §5-5. `work_order_id NOT NULL` — 라인 수령이 W/O에 묶인다

```
shopfloor_receipt.work_order_id   bigint NOT NULL
```

출고요청이 W/O에서 나오므로 자연스럽다(`material_issue_request.work_order_id NOT NULL`). **다만 「추가 자재 출고 요청」(수동·긴급 W/O 대응)도 W/O를 갖는다**(✓확정 2026-07-14 #4·#5) — 성립한다.

⚠ **한 출고 전표가 여러 W/O 라인을 담으면** 수령 전표를 나눠야 한다. `goods_issue`는 `source_document_type_code`+`source_document_id`(다형)이라 **여러 요청을 묶을 수 있는데** `shopfloor_receipt`는 W/O 하나다. §8-2.

## §9. 이 장에서 나온 공유 계약 후보

1. **★ 오프라인에서 두 화면이 한 단말로 합쳐지는 경우를 §C가 다루지 않는다** — 결정 17 시나리오 2가 확정인데 조항이 없다. **큐 순서 의존이 있으면 C-2의 「건별 되돌리기」가 성립하지 않는다** — 선행 건이 거부되면 딸린 건도 함께 거부해야 한다. **큐에 묶음 개념이 필요하다** (§5-1)
2. **⛔ 결정 08의 「호퍼=설비 매핑 Location」이 성립하지 않는다** — 설비·위치 어느 방향으로도 매핑 컬럼이 없다(실측). **A-11에 따라 물러난 수준(Location 코드로만 지정 · 설비 기준 집계 불가)을 명시** (§5-3)
3. **DB가 이미 막고 있는 예외는 설계하지 않는다** — 예외 E-11 ①의 「초과 수령 차단? 반송?」이 `CHECK`로 이미 정해져 있었다. `M-01-08`의 LOT 미지정에 이은 두 번째. **예외 카탈로그를 볼 때 물리 모델을 먼저 대조한다** (§5-2)
