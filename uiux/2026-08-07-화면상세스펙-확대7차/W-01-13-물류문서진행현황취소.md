## §5. 액션·상태

### §5-1. ⭐ 취소는 **3단 관문**이다

FR-IM-076~078이 세 문서에 대해 같은 말을 한다 — **「후속이 없으면 취소할 수 있다」**.

```
FR-IM-076  후속 입고·검사 이력이 없는 입하 건은 취소할 수 있어야 한다
FR-IM-077  입고재고가 이동·출고·투입되지 않은 경우 입고를 취소할 수 있어야 한다
FR-IM-078  아직 인수하지 않았거나 사용하지 않은 출고 건은 취소할 수 있어야 한다
```

| # | 관문 | 판정 | 실패하면 |
| :-: | --- | --- | --- |
| **①** | **후속이 있는가** | 하류 문서·투입 기록 조회(§5-3) | ⛔ **취소 불가** — 「먼저 이것들을 역순으로 취소하세요」 + **목록 제시** |
| **②** | **전기됐는가** | `status_code` | 전기 전 = 상태만 전이 · 전기 후 = **원장 역트랜잭션 필요**(§5-4) |
| **③** | **승인** | `W-CO-09` | ⛔ **승인 전에는 실행되지 않는다**(사용자 확정 2026-08-07 — 「승인 모두 필요」) |

⚠ **①은 화면이 보이고 서버가 다시 판정한다.** 승인을 기다리는 사이에 후속이 생길 수 있다 — §5-4.

### §5-2. 범위 — **출하 취소는 이 화면이 받지 않는다**

| FR | 대상 | 소관 |
| --- | --- | :-: |
| FR-IM-076 입하취소 | `inbound_receipt` | ✅ **이 화면** |
| FR-IM-077 입고취소 | `goods_receipt` | ✅ **이 화면** |
| FR-IM-078 출고취소 | `goods_issue` | ✅ **이 화면** |
| **FR-IM-079 출하취소** | `shipment` | ⛔ **04 도메인** — 「ERP·운송·고객납품 상태에 따라」가 조건이고 **실제 반출됐으면 반품 절차**로 간다. 성격이 다르다 |

**진행현황(FR-IM-086)은 10문서를 요구하는데 이 화면은 6종을 덮는다.**

| 문서 | 테이블 | 이 화면 |
| --- | --- | :-: |
| P/O · 입하 · 입고 · 출고요청 · 피킹 · 이동요청 | `purchase_order`·`inbound_receipt`·`goods_receipt`·`material_issue_request`·`picking_order`·`stock_transfer` | ✅ |
| 생산품 입고 | `shopfloor_receipt` | ⚠ **02 도메인** |
| 외주출고·입고 | `subcontract_issue`·`subcontract_receipt` | ⛔ **상태 컬럼이 없다**(§5-6) |
| 출하요청 · 출하 | `shipment_request`·`shipment` | ⚠ **04 도메인** |

**A-11로 물러난다** — 화면은 **덮는 6종만 유형 선택지에 두고**, 나머지는 「이 화면에서 보지 않습니다 · 어디서 보는지」를 적는다. 선택지에서 그냥 빼면 요구가 채워졌는지 알 수 없게 된다.

### §5-3. 「후속이 있는가」를 무엇으로 아는가 — **원천 참조를 거꾸로 읽는다**

하류 문서가 상류를 가리키는 컬럼이 실재한다.

```
goods_receipt.source_document_type_code + source_document_id      입하 → 입고
goods_issue.source_document_type_code   + source_document_id      출고요청 → 출고
picking_order.source_document_type_code + source_document_id
inventory_transaction.source_document_type_code + source_document_id   전표 → 원장
```

**즉 「이 문서를 원천으로 삼는 행이 있는가」로 판정한다.**

⚠ **다시 다형 참조다.** `source_document_type_code`의 값이 어느 테이블을 가리키는지 규약이 없다 — **#68의 네 번째 사용처**다. 유형↔테이블 표를 화면이 갖지 않고 **계약이 판정 결과를 내려 준다**(§9-1).

**투입은 다르다** — FR-IM-077의 「투입되지 않은」은 `production.material_consumption`을 봐야 하고, 그것은 원천 문서가 아니라 **LOT**를 가리킨다. 그래서 후속 판정이 두 갈래다:

| 갈래 | 무엇을 보나 |
| --- | --- |
| **문서 하류** | `source_document_*`로 거꾸로 조회 |
| **재고 사용** | 그 입고가 만든 LOT·수량이 **이동·출고·투입**에 쓰였는가 → 원장 |

### §5-4. ⭐ 취소 흐름 — **승인은 문을 열 뿐, 실행은 다시 누른다**

`W-CO-09` §5-7이 정한 규칙을 그대로 따른다. **취소만 예외로 두지 않는다.**

```
① [취소 요청]   문서 상태 → 취소요청 · approval_request 생성(사유 필수)
       ↓
② W-CO-09       승인자가 승인 / 반려
       ↓
③ [취소 실행]   ⚠ 후속 유무를 다시 판정 → 통과하면 역처리
       ↓
   전기 전이면 상태 전이만 · 전기 후면 원장 역트랜잭션
```

**③을 자동화하지 않는 이유는 두 가지고, 두 번째가 결정적이다.**

1. `W-01-06`(폐기 품의)·01 계약의 「`:post`는 승인 전이면 400」과 **같은 패턴**이다 — 승인자가 화면마다 다른 결과를 기대하게 만들지 않는다
2. ⭐ **승인을 기다리는 사이에 후속이 생길 수 있다.** 승인 즉시 자동 취소하면 **①의 판정을 다시 할 자리가 없다** — 그 사이에 출고된 400 EA가 원장에서 사라진다

⚠ **③에서 다시 막히면 승인은 이미 났다.** 화면은 「승인은 유효하지만 지금은 실행할 수 없습니다 — 출고 GI-…-0455가 새로 생겼습니다」를 보이고, **새 요청을 다시 올리게 하지 않는다**(승인은 되돌릴 수 없다 — J-6).

### §5-5. ⛔ FR-IM-080이 요구하는 7가지 — **넷은 승인이 담고, 하나가 빈다**

FR-IM-080은 정정 시 **「기존 이력을 삭제하거나 덮어쓰지 않고」** 7가지를 보존하라고 한다.

| # | 보존 항목 | 어디에 담기나 | 판정 |
| :-: | --- | --- | :-: |
| 1 | 정정 전 값 | 원 `inventory_transaction`(+ line) — **그대로 남는다** | ✅ |
| 2 | 정정 후 값 | 역트랜잭션 `reversal_of_transaction_id` | ✅ |
| 3 | **정정사유** | **`approval_request.reason`** NOT NULL | ✅ |
| 4 | 요청자 | **`approval_request.requested_by`** | ✅ |
| 5 | **승인자** | **`approval_step.approver_id` + `decision_at`** | ✅ |
| 6 | 정정일시 | 역트랜잭션 `occurred_at`·`recorded_at` | ✅ |
| 7 | 관련 재고·LOT 영향 | `inventory_transaction_line`(item·lot·qty·from/to) | ✅ |
| — | **문서 자신의 취소 흔적** | ⛔ **`status_code` 뿐** — 언제·누가가 없다 | ⛔ |

> ⭐ **취소를 승인 대상으로 만든 것이 3·4·5를 자동으로 채웠다.** 사용자가 말한 「실무자가 취소 → 관리자가 승인 요청 목록에서 승인/반려/의견」 흐름이 **FR-IM-080의 절반을 데이터 변경 없이 충족**한다.

**빈 자리 하나** — 전기되지 않은 문서를 취소하면 원장에 아무것도 안 생기므로 **역트랜잭션이 없고**, 문서에는 `status_code`만 바뀐다. **누가 언제 취소했는지가 어디에도 안 남는다.**

**A-11로 물러난다** — 화면은 **취소 이력을 `approval_request`로 보인다**(취소 요청이 곧 이력이다). 그러나 **승인이 필요 없는 취소는 이 화면에 두지 않는다** — 두면 흔적 없는 취소가 생긴다. → §8-1 · §9-2.

### §5-6. ⛔ 외주 2문서는 상태를 보일 수 없다

```
logistics.subcontract_issue     status_code ⛔ 없음 · version_no ⛔ 없음
logistics.subcontract_receipt   status_code ⛔ 없음 · version_no ⛔ 없음
```

FR-IM-086이 「외주출고·입고」를 진행현황 대상으로 요구하는데 **상태 컬럼 자체가 없다.** 다른 10문서는 전부 있다.

**유형 선택지에 두되 비활성 + 사유**(G-2·G-10) — 「상태를 저장하는 자리가 아직 없습니다」. → §8-2 이슈.

| 대상 화면에서 보기 | 문서 유형에 대응 화면이 있을 때 |

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **다형 원천 참조의 「후속이 있는가」는 계약이 판정해 내려 준다 — 화면이 유형↔테이블 표를 갖지 않는다** — `source_document_type_code`가 **#68의 네 번째 사용처**다. 화면이 「입고 → 출고·이동·투입」 관계표를 하드코딩하면 문서 유형이 늘 때마다 취소 판정이 조용히 틀린다. `W-CO-09` §9-1과 **같은 요청의 다른 축**이다 (§5-3)
2. ⭐ **흔적을 남길 컬럼이 없는 행위는 승인을 필수로 만들어 승인 기록이 이력을 대신하게 한다** — 문서 12테이블에 `cancel*` 컬럼이 0건이라 취소의 누가·언제·왜가 어디에도 안 남는데, **취소를 승인 대상으로 만들면 `approval_request`(사유·요청자·일시) + `approval_step`(승인자·의견)이 FR-IM-080의 7항목 중 4개를 채운다.** 역으로 **승인 없는 취소를 두면 흔적 없는 취소가 생기므로 두지 않는다** (§5-5)
3. ⭐ **승인은 문을 열 뿐이고, 실행 시점에 전제를 다시 판정한다** — `W-CO-09` §9-3이 「승인 ≠ 실행」을 세웠다면, 이 장은 **왜 그래야 하는지의 결정적 사례**를 준다: 승인을 기다리는 사이에 후속이 생기면 자동 실행은 그것을 못 본다. **③에서 막히면 새 요청을 다시 올리게 하지 않는다** — 승인은 유효하고 전제만 어긋난 것이다 (§5-4)
4. **되돌리는 화면은 「무엇이 막고 있는지」를 목록 단계에서 보인다** — 상세를 열어야 취소 가능 여부를 알면 실무자가 목록에서 대상을 고르지 못한다. **후속 건수를 목록 열로 둔다.** G-3(비활성 사유는 「어떻게 풀 것인가」)을 **목록 수준으로 끌어올린 형태** (§3·§6)
