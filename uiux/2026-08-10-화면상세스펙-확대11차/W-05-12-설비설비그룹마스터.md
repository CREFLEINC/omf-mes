## §3. 「설비그룹이 없다」는 틀렸다 — A-13 4단을 돌린 결과

공유계약 **A-13**은 「없다」고 적기 전에 ① 한 층 아래 ② 다른 파일 ③ 다른 스키마 ④ **다른 이름**을 보라고 정한다. 넷째에서 걸렸다.

| 단 | 확인한 것 | 결과 |
| :-: | --- | :-: |
| ① 한 층 아래 | `mdm.equipment` 안에 그룹 컬럼이 있나 | 없음 (`equipment_type_code`·`production_line_id` 만 있음) |
| ② 다른 파일 | 물리 모델이 여러 파일인가 | 단일 파일 |
| ③ 다른 스키마 | `mdm` 밖에 있나 | 없음 |
| ④ **다른 이름** | **`mdm.production_line` 이 그것이다** | ⭐ **걸렸다** |

### §3-1. 형태가 같다

```
개념모델 §1 「설비그룹」          물리모델 mdm.production_line (SQL 164)
─────────────────────────       ──────────────────────────────────────
설비그룹코드 (키)          ↔     line_code   + UNIQUE (plant_id, line_code)
그룹명                    ↔     line_name
상위그룹                  ↔     parent_line_id  (자기참조 FK)
설비그룹-설비 1:N          ↔     equipment.production_line_id  (SQL 463)
                          +     line_type_code = LINE | WORK_AREA
```

**상류와 하류가 같은 결론에 이름만 다르게 도달했다.**

- **상류(결정 03)**: 「라인 개념 필요 시 **별도 라인 마스터 대신 설비그룹 유형에 '라인' 추가로 흡수**」
- **하류(H-4)**: 라인 마스터를 만들고 **작업구역을 `line_type_code` 로 흡수**했다

둘 다 **「계층형 테이블 하나 + 유형 코드」**다. 담는 그릇이 같고 부르는 이름이 다르다.

### §3-2. 그래서 화면은 새 테이블을 요구하지 않는다

**이 화면이 다루는 「설비 그룹」의 저장처 = `mdm.production_line`.** `line_type_code` 가 그 층이 무엇인지 말한다(라인 · 작업구역 · 그 밖의 분류축).

⚠ **필요한 것은 테이블이 아니라 값 목록 하나**다 — `line_type_code` 에 분류축을 추가할 것인지. 이는 공통코드이므로 **웹-공통코드조직작업자-마스터(`W-06-06`)** 소관이다(§8-3).

### §3-3. ⭐ 같은 상황을 다룬 앞 장과 이 장이 다른 점

**웹-예비품-마스터(`W-06-08`, 2026-08-03)**도 「데이터 면이 비어 있다」를 만났고, 그때는 **§4를 「신설 요청 명세」로 남기고 이슈로 넘겼다.** 지금은 다르다.

| | `W-06-08` (2026-08-03) | **이 장 (2026-08-10)** |
| --- | --- | --- |
| 근거 | 물리 모델이 정본 | **원칙 1) — 데이터 모델이 UI/UX 결정을 따라온다** |
| 없는 항목을 어떻게 | **요청**으로 적고 대기 | **정의**하고 넘긴다 |
| 넘기는 시점 | 즉시 이슈 | **17장을 다 쓴 뒤**(DR-001 §5-2) |

**§4-C(점검·보전 항목·주기)가 그 차이가 드러나는 자리다.** 「지어내지 않는다」(서식 원칙 2)는 여전히 지킨다 — **근거 없이 필드를 늘리지 않되, 근거가 있으면 모델에 자리가 없어도 정의한다.**

### §3-4. 「설비 위치」도 새 컬럼이 아니다

REQ-PR-0036 이 요구한 「알람발생 설비 위치 표시」는 **DR-004 확정으로 계층 텍스트가 됐다.** 계층 텍스트의 재료가 이미 다 있다.

```
공장(mdm.plant) > 상위 그룹(production_line) > 하위 그룹(production_line) > 설비(equipment)
```

⛔ **설비 마스터에 좌표·평면 위치 필드를 두지 않는다.** DR-004 가 「알람발생 설비 위치 표시에서 평면 배치 불필요」로 확정했다.

⚠ **`mdm.location` 을 쓸 수 없다** — `warehouse_id NOT NULL`(SQL 335)이라 **창고에 소속된 위치**만 담는다. 설비는 창고에 있지 않다.

#### C-2. 부여 — 어느 설비가 어느 항목을 언제 도는가

공유계약 **B-6**(마스터 테이블과 부여 테이블을 구분한다)을 적용한다. 부여가 갖는 것:

| **주기** — 유형(일/주/월) + 간격 + 기준일 | WF05 S1 Action 「점검/보전 항목·**주기** 정의」 · S2 Trigger 「점검 **주기 도래**(일상=Daily, 정기=Monthly)」 | 실측 |

⭐ **해석 규칙은 새로 만들지 않는다 — 결정 03 이 이미 정한 것을 그대로 쓴다.**

> **결정 03(WorkCalendar)**: 「해석 규칙: **설비 → 소속 설비그룹 → 공장** 순으로 **가장 가까운** 캘린더 적용」

점검 항목 부여도 같은 규칙을 쓴다 — **설비에 부여가 있으면 그것, 없으면 소속 그룹의 것, 둘 다 없으면 점검 대상 아님.**

**왜 같은 규칙을 쓰는가**: 같은 화면군에서 **캘린더는 「설비→그룹→공장」, 점검 항목은 다른 순서**로 돌면 설비담당이 두 규칙을 외워야 한다. 한 규칙이면 「가장 가까운 것이 이긴다」 한 문장으로 끝난다. → §9-2

⚠ **공장 층은 두지 않는다.** 캘린더는 공장 기본 1건이 필수지만(가동일은 공장 전체가 공유한다), **점검 항목은 설비 종류마다 다르므로 공장 단위 기본값이 성립하지 않는다.** 2층(설비 → 그룹)으로 둔다.

## §5. 액션·상태

### §5-1. 액션

| 액션 | 활성 조건 |
| --- | --- |
| 그룹 추가 · 설비 추가 | 편집 권한 |
| 저장 / 취소 | 변경분 존재 · 필수 충족 |
| **사용 중지** | `is_active=true` · **물리 삭제 버튼을 두지 않는다**(B-4) |
| 점검 항목 부여 편집 | 그룹 또는 설비 선택 상태 |
| 변경 이력 | 항상 — `audit.audit_event`(`target_type_code`+`target_id`, B-5) · 기간 필수(파티션) |
| 계층 텍스트 확인 | 설비 선택 시 §5-3 |

⛔ **엑셀 업로드를 두지 않는다.** 다른 마스터(검사기준·예비품·툴)와 다른 판단이며 근거가 있다 — **WF05 S1 Medium 이 설비(기계) 대장의 매체를 🟡 미검증으로 남겼다**(「엑셀 설비대장+종이 사양서 **추정**, **매체 미검증**」). 마이그레이션 원천이 무엇인지 모르는 상태에서 업로드 양식을 만들면 두 번 만든다. 툴(`W-05-13`)은 「엑셀 관리·ERP 미사용」이 **확정**(REQ-PR-0003 현행)이라 반대다. → §8-6

### §5-2. ⭐ 운용 상태를 2값으로 정한다 — A-14 적용

`status_code` 는 `NOT NULL` 인데 값 목록이 없다. 늘리기 쉬운 자리다 — 「가동중 / 정지 / 고장 / 보전중 / 비가동 / 폐기」로 벌어질 수 있다.

공유계약 **A-14**가 이것을 막는다.

> **A-14**: 같은 상태에 이르는 길이 여럿이면 **상태 값을 늘리지 말고 조건을 따로 관리**한다. **값 목록이 자꾸 늘면 조건을 값에 밀어 넣고 있는지 의심한다.**

**확정** — 마스터가 갖는 것은 **자산 수명주기 축**뿐이다.

| 값 | 뜻 | 근거 |
| --- | --- | --- |
| **운용** | 자산으로 살아 있다 | WF05 S1 Result 「**상태**: 자산 '가동(운용)'」 |
| **폐기** | 자산 처분됨 | WF05 S9 Result 「**상태변화**: 자산 '운용→폐기'」 |

**「지금 쓸 수 있는가」는 마스터에 적지 않는다. 판정한다.**

```
사용 가능 = is_active
          AND status_code = 운용
          AND (검교정 대상이면 → 검교정 유효기간 내)
          AND 열린 고장·보전 건이 없다
```

**왜 이렇게 하는가** — 「고장」·「보전중」·「비가동」은 **트랜잭션이 만드는 조건**이고 각각 주인이 있다.

| 조건 | 만드는 곳 |
| --- | --- |
| 고장 | 모바일-설비고장-현장보고(`M-05-02`) → 웹-설비고장-상세처리(`W-05-04`) |
| 보전중 | 웹-보전지시-발행(`W-05-05`) → 웹-보전실적-예비품출고등록(`W-05-06`) |
| 비가동 | POP-비가동실적-입력(`P-05-02`) → 웹-비가동집계-조회(`W-05-08`) |
| 검교정 만료 | 웹-계측기검교정이력-등록(`W-05-10`) |

⛔ **이 넷을 마스터 상태로 올리면 네 화면이 같은 컬럼 하나를 두고 경합한다** — 공유계약 **B-13**(한 컬럼을 여러 경로가 바꾸면 「누가 정하고 누가 반영하는가」를 가른다)이 정면으로 걸린다. **상태를 2값으로 묶으면 경합 자체가 생기지 않는다.**

⚠ **이 판단은 이 화면 하나의 것이 아니다** — 툴 마스터(`W-05-13`)·계측기(`W-05-11`)에 같은 형태가 있다. → §9-1

### §5-3. 계층 텍스트를 이 화면이 보인다

DR-004 확정으로 설비 위치 = 계층 텍스트다. **그 텍스트가 맞게 나오는지 확인하는 자리가 여기**다 — 통합 대시보드(`W-CO-05`)가 그리는 문자열의 재료를 만드는 곳이기 때문이다.

```
설비 선택 시 상단에 표시
   호치민공장 > 프레스라인 A > 1구역 > 프레스 1호기
```

⚠ **소속 그룹이 비어 있으면 공장까지만 나온다.** 그 상태를 감추지 않는다 — 공유계약 **G-9**(모르는 값과 없는 값을 같은 모양으로 그리지 않는다)에 따라 **「소속 그룹 없음」을 명시**한다. 알람 화면에서 위치가 「호치민공장」으로만 나오면 찾아갈 수 없으므로, **여기서 비어 있음이 보여야 채운다.** → G-12(통제의 근거가 되는 마스터는 「비어 있음」을 함께 보인다)와 같은 취지.

### §5-4. 화면 상태

`초기(EmptyState)` → `조회` → `편집` → `저장 중` → `성공(Toast)` / `실패(인라인·배너)` / `충돌(B-1)`

**낙관적 잠금**: `production_line`·`equipment` 둘 다 `version_no` 실재 → **B-1 적용**. 저장 충돌과 상태 잠김은 배너 위치가 같고 문구·다음 행동이 다르다(G-1).

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐ 자산 마스터의 상태는 **수명주기 축만** 갖는다 — 「지금 쓸 수 있는가」는 파생 판정이다

A-14(상태와 조건을 분리한다)의 **자산 마스터 판**이다. §5-2 가 실증했다.

**규칙안**

1. 설비·툴·계측기 같은 **자산 마스터의 `status_code` 는 「운용 / 폐기」 2값**으로 둔다
2. 「고장」·「보전중」·「비가동」·「검교정 만료」는 **트랜잭션이 만드는 조건**이며 **마스터에 쓰지 않는다**
3. **「지금 쓸 수 있는가」는 화면·서버가 판정**한다 — 판정식을 계약이 갖는다
4. 판정 결과를 보일 때는 **어느 조건 때문에 못 쓰는지**를 함께 보인다(G-3 — 「어떻게 풀 것인가」)

**왜 계약인가**: 이 규칙이 없으면 **네 화면이 같은 컬럼을 두고 경합**한다(B-13). 그리고 **세 마스터(설비·툴·계측기)에 같은 형태가 있다** — 한 곳에서 정하지 않으면 셋이 갈라진다.

### 9-2. **계층 해석 규칙은 도메인 안에서 하나만 쓴다**

결정 03 이 캘린더에 대해 「설비 → 소속 설비그룹 → 공장 순으로 **가장 가까운** 것을 적용」을 확정했다. **점검 항목 부여도 같은 규칙을 쓴다**(§4-C-2).

**규칙안**: 한 도메인 안에서 **계층을 거슬러 올라가며 값을 찾는 규칙이 둘 이상 생기면 합친다.** 층의 개수는 대상마다 다를 수 있으나(캘린더 3층 · 점검 항목 2층) **「가장 가까운 것이 이긴다」는 한 문장을 공유**한다.

**왜 계약인가**: 사용자가 규칙을 외우는 비용이 규칙 수에 비례한다. 그리고 **구현이 같은 탐색 함수를 재사용**할 수 있다.

### 9-3. 「없다」의 4단 뒤에 **5단째가 붙는다** — 「그러면 우리가 정의한다」

A-13 은 「없다」고 적기 전에 4단을 확인하게 한다. **2026-08-10 원칙 전환으로 5단째가 생겼다.**

```
① 한 층 아래  ② 다른 파일  ③ 다른 스키마  ④ 다른 이름
                                              ↓ 네 단 다 없으면
                                    ⑤ 원칙 1) — 화면이 정의하고 모델이 따라온다
```

⚠ **⑤가 ①~④를 건너뛰는 면허가 아니다.** 이 장이 그 증거다 — **④에서 걸려 테이블 신설이 불필요**해졌고(§3), ⑤로 간 것은 점검 항목 하나뿐이다(§4-C). **먼저 찾고, 없을 때만 정의한다.**

그리고 **⑤로 갈 때도 서식 원칙 2(「있으면 좋을 것 같은 필드는 쓰지 않는다」)는 그대로**다 — §4-C 가 **항목마다 근거와 강도를 붙인** 이유다.
