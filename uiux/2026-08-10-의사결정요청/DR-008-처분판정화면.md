# 의사결정 요청서 **DR-008** — 처분 판정(재작업/폐기/정상)을 **어느 화면이 저장하는가**

| 항목 | 값 |
| --- | --- |
| 요청일 | 2026-08-13 |
| 요청 주체 | CREFLE OMF 팀 (UI/UX) |
| 결정 주체 | 팀 리더 |
| 상태 | ⏳ **회신 대기** |
| 막고 있는 것 | ⛔ **화면 3장의 착수 통지** — `W-04-10`·`W-04-11`·`P-04-03` |

---

## 1. 무엇을 결정해야 하는가

**부적합 판정 의뢰가 올라왔을 때, 「재작업할지·폐기할지·정상으로 되돌릴지」를 정하는 화면이 어디인가**입니다.

```
W-04-07  부적합 등록 · 판정 의뢰
             ↓
        ???  판정 · 처분 결정          ← 이 화면이 없습니다
             ↓
   ┌─────────┼─────────┐
W-04-10   W-04-11   P-04-03
폐기 품의  재고 재등록  재작업 실적     ← 셋 다 「처분 = ○○」이 진입 조건
```

## 2. 왜 지금 결정해야 하는가

### 2-1. ⛔⛔ **03 과 04 가 서로에게 미뤘습니다**

계약을 쓰면서 실측으로 드러났습니다.

| 어디 | 원문 |
| --- | --- |
| **03 품질 요구서** §1-2 | `nonconformance` · `nonconformance_lot` · **`disposition_decision`** → 「**04 제품출하** — `W-04-07`·`P-04-03`」 |
| **`W-04-07`** §5-1 | 「이 화면은 **판정하지 않는다** — 04 는 **의뢰만** 한다」<br>「처분 결정을 만드는 것은 **03** 이고 이 화면은 **읽기만** 한다」 |

⭐ **03 은 「04 것」이라 했고, 04 화면은 「03 이 만든다」고 합니다.**

### 2-2. 「소유는 쓰기를 가진 쪽」으로 풀려니 **쓰는 쪽이 없습니다**

**화면 116장의 액션 표를 전수로 뽑아 확인했습니다.**

| 화면 | 도메인 | 처분을 저장하나 |
| --- | :-: | --- |
| `W-03-02` Lot Status 판정·전이 | 03 | ⛔ 7액션이 전부 **Lot Status 전이**다 |
| `W-04-07` 재작업/폐기 판정 의뢰 | 04 | ⛔ 「부적합 등록」·「판정 의뢰」뿐 — **「판정」은 ⛔ 두지 않는다** |
| `W-04-10`·`W-04-11`·`P-04-03` | 04 | ⛔ **처분을 읽어 진입한다**(쓰지 않는다) |
| `P-02-13` PQC 제품 검사 | 02 | ⛔ 처분 선택이 **잠정**이라 저장하지 않는다(03 계약 확정) |

⛔ **인벤토리 전체에 0건입니다.**

### 2-3. ⚠ 확정이 있는데 **착지하지 않았습니다**

**`F04` 정합 확정(2026-07-07)** 이 이렇게 정했습니다.

> 재작업/폐기 **판정**은 전 도메인에서 **03 소관** 통일

**그런데 03 도메인 5화면에 그 화면이 없습니다.**

| 03 화면 | 무엇 |
| --- | --- |
| `W-03-01` · `W-03-05` | 조회 |
| `W-03-02` | Lot Status 전이 |
| `W-03-03` | 의심자재 등록 |
| `W-03-09` | 특채·한도승인 승인 |

⭐ **「03 소관」이라는 확정은 있는데 그 화면이 만들어지지 않았습니다.**

### 2-4. 스펙이 이미 알고 넘겼습니다

`W-04-07` §5-1 이 그대로 적었습니다.

> ⚠ **B-13 이 여기 걸린다** — 처분 결정을 만드는 것은 03 이고 이 화면은 읽기만 한다.
> **누가 정하고 누가 반영하는가를 계약이 갈라야 한다.**

⭐ **계약 단계가 왔고, 답이 「아무도 안 만든다」였습니다.**

### 2-5. 데이터는 준비돼 있습니다

```
quality.disposition_decision          (SQL 1992)
    nonconformance_id      NOT NULL   ← 부적합이 선행한다
    disposition_type_code  NOT NULL   ← 재작업 · 폐기 · 정상 · 선별
    decision_qty           NOT NULL   ← 부분 처분이 된다
    reason                 text NOT NULL   ⭐ 사람이 쓴다
    decided_by             NOT NULL   ⭐ 사람이 정한다
    decided_at             NOT NULL
    approval_request_id               ← 승인이 붙을 수 있다(nullable)
```

⭐ **`decided_by`·`reason` 이 NOT NULL 이라 「사람이 화면에서 정한다」가 데이터에 박혀 있습니다.** 자동 판정이 아닙니다.

⚠ **`M-01-13` 때와 같은 형태입니다** — 「이 `NOT NULL` 을 누가 채우나」를 사람으로 답해 보니 **앞단계 화면이 빠져 있었습니다**(공유계약 **A-24**).

## 3. 결정 항목 — **안 넷**

### 3-A · ⭐ **03 에 처분 판정 화면을 신설한다** *(권고)*

부적합 판정 의뢰 목록을 받아 처분을 정하는 화면을 **03 품질**에 하나 만듭니다.

| ✅ | ⛔ |
| --- | --- |
| **`F04` 확정을 그대로 따른다** — 「판정은 03 소관 통일」 | **화면이 하나 는다** — 116 → 117 |
| ⭐ **전 도메인의 불량이 한 화면으로 모인다** — 02 수리·04 반품·01 자재가 같은 기준으로 판정된다 | 03 트랙을 다시 연다(스펙 1장 + 계약 경로 1~2) |
| **데이터가 그대로 맞는다** — 신설 0(`disposition_decision` 실재) | |
| ⭐ **세 화면이 곧바로 풀린다** | |

### 3-B · **`W-04-07` 에 판정 기능을 넣는다**

의뢰 화면이 판정까지 합니다.

| ✅ | ⛔ |
| --- | --- |
| 화면이 늘지 않는다 | ⛔⛔ **`F04` 확정과 어긋난다** — 「03 소관 통일」을 04 가 가져온다 |
| 의뢰 → 판정이 한 자리라 빠르다 | ⛔ **02·01 에서 온 불량은 어디서 판정하나** — 04 화면이 남의 도메인 불량을 판정하게 된다 |
| 세 화면이 곧바로 풀린다 | ⚠ **`W-04-07` 이 「판정하지 않는다」를 상단에 상시 안내**하도록 설계돼 있다 — 그 설계를 뒤집는다 |

### 3-C · **`W-03-02`(Lot Status 판정·전이)를 확장한다**

기존 03 화면에 처분 축을 더합니다.

| ✅ | ⛔ |
| --- | --- |
| 화면이 늘지 않는다 | ⛔⛔ **축이 다르다** — Lot Status(정상·불량·검사 대기·폐기)와 처분(재작업·폐기·정상·선별)은 **다른 결정**이다 |
| 03 안에 있어 `F04` 와 맞는다 | ⚠ **`W-03-01` §5-3 이 경고한 것과 같은 형태** — 「같은 낱말을 두 축에 쓰지 않는다」. 한 화면에 두 축을 넣으면 **어느 것을 고르는지 흐려진다** |

### 3-D · **1차 범위 밖으로 확정한다**

처분 판정을 1차에서 하지 않고, 세 화면도 함께 미룹니다.

| ✅ | ⛔ |
| --- | --- |
| 지금 아무것도 안 만들어도 된다 | ⛔⛔ **고객 요구를 어긴다** — ✅**REQ-PR-0025** 「재작업 가능 불량 vs 폐기 불량 **구분** — 판정은 불량창고 입고 후」 |
| | ⛔ **화면 셋이 함께 빠진다** — `W-04-10`·`W-04-11`·`P-04-03` |
| | ⛔ 이미 만든 `W-04-07`(의뢰)이 **받는 쪽 없이 남는다** |

## 4. 실측으로 확인한 것

| 무엇 | 결과 |
| --- | :-: |
| 처분을 저장하는 화면 | **0건** (116화면 액션 전수) |
| `disposition_decision` 을 **읽는** 화면 | **4** — `W-04-07`·`W-04-10`·`W-04-11`·`P-04-03` |
| 처분 유형 갈래 | **4** — 재작업 · 폐기 · 정상 · **선별**(⛔ #118 로 1차 범위 밖) |
| 데이터 신설 필요 | ⛔ **0** — 테이블·컬럼이 이미 있다 |

## 5. 권고 — **3-A(03 에 신설)**

**두 가지를 먼저 봤습니다.**

| 물음 | 답 |
| --- | --- |
| **용도가 하나인가** | ⛔ **아니다** — 처분은 **네 갈래**로 갈리고 각각 **다른 화면**으로 이어진다. 갈래를 정하는 자리가 따로 있는 것이 자연스럽다 |
| **고객 약속인가** | ✅ **그렇다** — **REQ-PR-0025** 가 「재작업/폐기 **구분**」을 요구한다. 3-D 는 이 약속을 어긴다 |

**그래서 3-D 는 권고에서 뺍니다.** 남은 셋 중 **3-A** 를 권고하는 이유는 하나입니다 —

⭐ **불량은 04 에서만 오지 않습니다.** 02 수리·01 자재·04 반품이 전부 부적합을 만들고, **판정 기준이 하나여야 한다는 것이 `F04` 확정의 취지**입니다. 3-B 는 04 가 남의 도메인 불량을 판정하게 됩니다.

⚠ **3-B 가 더 싸다는 것은 사실입니다** — 화면이 안 늘고 의뢰→판정이 한 자리입니다. **속도를 우선한다면 3-B 도 합리적**이고, 그때는 `F04` 확정을 함께 고쳐야 합니다.

## 6. 무엇을 막고 있나 — **화면 3장의 착수 통지**

| 화면 | 진입 조건 | 지금 |
| --- | --- | :-: |
| `W-04-10` 제품 폐기 품의 | 처분 = **폐기** | ⏳ 목록이 빈다 |
| `W-04-11` 재고 재등록 | 처분 = **정상** | ⏳ |
| `P-04-03` 재작업 실적 등록 | 처분 = **재작업** | ⏳ |

⚠ **계약은 이미 나갔습니다** — `GET /quality/disposition-decisions` 로 **읽기만** 냈고, `x-internal-note` 에 「만드는 화면이 없다」와 막히는 세 화면을 적었습니다. **계약이 우회하지 않았습니다.**

⭐ **결정이 오면 세 화면이 함께 풀립니다.** 3-A 라면 **화면 1장 신설 + 03 계약에 경로 1~2개**가 따라옵니다(데이터 신설 0).
