# 의사결정 요청서 **DR-005** — 공지·전달을 어디까지 만드는가

| 항목 | 내용 |
| --- | --- |
| 번호 | **DR-005** |
| 작성일 | 2026-08-10 |
| 요청 대상 | 팀 리더 |
| 막고 있는 화면 | **1장** — 웹-공지전달-게시조회(`W-CO-04`) |
| 실제 파급 | ⚠ **POP 22화면 전체** — 팝업 강제 표시를 만들면 모든 현장 화면에 걸린다 |
| 관련 이슈 | **#87** §5(공지 엔티티 부재) · 공유계약 **§I-30** |
| 상태 | ⏳ **결정 대기** |

---

## 1. 무엇을 결정해야 하는가

**관리자가 작성해서 사람들에게 보이는 글을 어디까지 만들 것인가.**

⚠ **「단일 엔티티로 한다」는 이미 확정돼 있습니다.** 남은 것은 **기능 범위**입니다.

| # | 결정 항목 | 선택지 |
| :-: | --- | --- |
| **5-A** | **현장 단말 강제 팝업을 1차에 만드는가** | 만든다 / 뒤로 미룬다 |
| **5-B** | **「읽었다」 확인을 받는가** | 받는다 / 받지 않는다 |
| **5-C** | **대상 범위를 어디까지 쓰는가** | 5종 전부 / 전사만 / 그 사이 |

---

## 2. 왜 결정해야 하는가

### 2-1. 구조는 확정됐고 **범위가 확정되지 않았습니다**

2026-07-06 설계결정 2번이 이렇게 확정했습니다.

> **「공지/전달(Notice)」 단일 엔티티.**
> 속성 — 제목 · 본문 · 게시 기간 · 작성자 + **대상 범위**(전사 / 사업부 / 설비그룹 / 작업조 / 작업지시) + **표시 방식**(현장 단말 강제 팝업 여부 · **확인 요구 여부**) + **수신자별 확인 이력**
> 기존 3개의 대응 — 공지사항 = 전사·팝업 없음 / 전달사항 = 작업지시 범위·확인 요구 / 현장 팝업 = 설비그룹·팝업 강제. **값의 차이일 뿐 구조 차이가 아니다.**

⭐ **무엇을 만들지는 정해졌고, 그중 무엇을 1차에 켤지가 안 정해졌습니다.**

### 2-2. 알림과의 경계도 이미 확정돼 있습니다

| | 알림(Notification) | **공지·전달(Notice)** |
| --- | --- | --- |
| 누가 만드나 | **시스템이 자동** — 불량 발생·계획 변경 등 | **사람이 작성** |
| 본질 | **발송**(채널·재시도) | **게시·확인** |
| 화면 | 웹-알림센터 · 웹-알람수신자-설정 (DR-003) | **웹-공지전달-게시조회** |

⭐ **자동인가 수동인가**가 분리 기준입니다. **DR-003 에서 정한 것과 겹치지 않습니다.**

### 2-3. 저장할 곳이 없습니다

**`notice` 전 파일 검색 0건**입니다.

⚠ **그 결과가 이미 다른 화면에 나타났습니다** — 웹-작업지시-확정배포 화면(`W-02-04`)이 「전달사항 확인 여부를 담을 컬럼이 작업지시에 없다」를 미결로 적었는데, **원인은 공지 엔티티 자체가 없는 것**이었습니다.

⛔ **예외 상황 하나를 추적할 수 없습니다** — 「**전달사항을 확인하지 않은 채 작업을 시작**」이 예외 목록에 있는데, 확인 이력이 없으면 **그런 일이 있었는지조차 모릅니다.**

### 2-4. ⚠ 화면은 1장인데 **파급은 POP 22화면**입니다

**강제 팝업은 화면이 아니라 셸 동작입니다.**

```
작업자가 POP 을 켠다 → ⚠ 확인하지 않은 공지가 있으면 팝업이 뜬다
                     → 「확인」을 눌러야 작업 화면으로 간다
```

**이것을 만들면 POP 22화면 전부가 「진입 전에 팝업이 뜰 수 있다」는 전제를 갖습니다.** 공유 계약에 조항이 필요합니다.

## 3. 결정 항목별 상세

### 3-A. 현장 단말 강제 팝업

| 안 | 무엇 | 파급 |
| :-: | --- | --- |
| **가 · 만든다** | POP 진입 시 미확인 공지를 팝업으로 띄우고 **확인해야 넘어간다** | POP 22화면 공통 전제 · 공유 계약 조항 신설 · **셸 레벨 구현** |
| **나 · 미룬다** | 웹에서만 게시·열람한다. 현장은 **관리자가 구두로** 전달 | 화면 1장으로 끝난다 |

⚠ **원래 요구가 무엇이었는지** — 설계결정 2번이 흡수한 3개 중 하나가 **「관리자 → 작업자 팝업 전달」**입니다. **현장 팝업은 원래 있던 요구**이지 우리가 만든 것이 아닙니다.

⛔ **다만 「강제」의 부작용이 있습니다** — 매번 팝업이 뜨면 작업자는 **읽지 않고 누릅니다.** 공유 계약이 이미 같은 문제를 다룬 적이 있습니다(경고 피로 — 「UI 마찰로 검토를 강제하면 오히려 안 읽는다」).

### 3-B. 「읽었다」 확인

| 안 | 무엇 | 필요한 것 |
| :-: | --- | --- |
| **가 · 받는다** | 공지마다 「확인 요구」를 켤 수 있고, 켜면 **누가 언제 확인했는지** 남는다 | 수신자별 확인 이력 |
| **나 · 안 받는다** | 게시만 하고 읽었는지는 모른다 | 공지 본문만 |

⚠ **예외 추적이 여기 걸립니다** — 「전달사항 미확인 채 작업 시작」을 잡으려면 **확인 이력이 있어야** 합니다.

### 3-C. 대상 범위

**확정된 5종** — 전사 / 사업부 / 설비그룹 / 작업조 / 작업지시

⚠ **화면 인벤토리는 이미 좁혀 두었습니다.**

> **범위 축소**(2026-07-29) — **전사 공지 전용**으로 좁힌다. 작업지시 전달사항은 **웹-작업지시-확정배포 화면 안의 구획으로 복귀**(엔티티는 단일 유지)

| 안 | 무엇 |
| :-: | --- |
| **가 · 5종 전부** | 웹-공지전달 화면에서 모든 범위를 지정한다 |
| **나 · 전사 + 작업지시** | 전사는 공지 화면에서, 작업지시 전달사항은 **작업지시 화면 안에서** — 인벤토리가 이미 그렇게 정리했다 |
| **다 · 전사만** | 나머지는 1차에 안 쓴다 |

⚠ **설비그룹 범위는 05 도메인에 걸립니다**(DR-001 로 착수 확정). **작업조는 회사 기준정보로 확정**됐습니다(#54).

## 4. 결정되면 어디에 영향을 주는가

| 결정 | 영향 |
| --- | --- |
| **5-A 가**(팝업) | **공유 계약 조항 신설** — 「POP 진입 시 미확인 공지 차단」. POP 22화면 §3 에 전제 한 줄이 붙는다 |
| **5-A 나** | 화면 1장으로 끝난다. **원래 요구 하나가 1차에서 빠진다** |
| **5-B 가**(확인) | 확인 이력 저장 + 웹 화면에 **「누가 확인했나」 구획**이 생긴다 |
| **5-C 나** | 웹-작업지시-확정배포 화면에 **전달사항 구획**이 붙는다(이미 그 화면이 미결로 적어 둔 것이 풀린다) |

### 4-1. 이미 쓴 화면

| 화면 | 무엇이 걸리나 |
| --- | --- |
| **웹-작업지시-확정배포**(`W-02-04`) | 「전달사항 확인 여부를 담을 곳이 없다」 미결이 **5-B·5-C 로 풀린다** |
| **POP 22화면 전부** | 5-A 가 「만든다」면 진입 전제가 하나 는다 |

## 5. 권고안

### 5-A. **가 — 만든다. 다만 「강제」가 아니라 「먼저 보인다」로**

**이유 셋입니다.**

1. **원래 요구입니다.** 「관리자 → 작업자 팝업 전달」이 설계결정 2번이 흡수한 3개 중 하나입니다. 빼면 요구 하나가 사라집니다.
2. **현장은 웹을 안 봅니다.** 작업자는 POP 앞에 서 있고 관리웹에 들어가지 않습니다. **현장에 닿는 경로가 팝업뿐**입니다.
3. **경고 피로는 「강제」의 문제이지 「표시」의 문제가 아닙니다.**

⭐ **그래서 이렇게 권고합니다** — 미확인 공지가 있으면 **진입 시 한 번 보이되, 확인 없이도 닫고 작업할 수 있게** 합니다. 대신 **「확인하지 않았다」가 이력에 남습니다.**

> **공유 계약이 이미 같은 판단을 했습니다** — 「관리자가 확인하지 않는 것은 관리자의 책임으로 정책에 두고, 기능은 확인하는 절차를 두는 것으로 충분하다」. **같은 기준을 작업자에게도 적용합니다.**

⚠ **예외 하나** — 「확인 요구」를 켠 공지는 **닫을 수 없게** 합니다. 안전·품질 사고처럼 반드시 읽어야 하는 것이 있습니다. **작성자가 그 공지에만 켭니다.**

### 5-B. **가 — 확인을 받는다**

**이유 둘입니다.**

1. **예외 추적이 이것 없이는 불가능합니다.** 「전달사항 미확인 채 작업 시작」이 예외 목록에 있는데, 확인 이력이 없으면 **그 예외가 존재하지 않는 것처럼** 됩니다.
2. **알림과 구조가 같습니다** — DR-003 의 알림도 「수신자별 읽음」이 필요합니다. **한 번에 같은 모양으로 설계**하면 두 번 만들지 않습니다.

### 5-C. **나 — 전사 + 작업지시**

**이유 둘입니다.**

1. **인벤토리가 이미 그렇게 정리했습니다**(2026-07-29). 전사 공지는 공지 화면이, 작업지시 전달사항은 작업지시 화면이 맡습니다. **되돌릴 근거가 없습니다.**
2. **설비그룹·작업조 범위는 쓸 화면이 아직 없습니다.** 05 도메인은 이제 착수하고(DR-001), 작업조 마스터 화면도 신설 검토 단계입니다. **필요해지면 범위 값을 하나 켜면 됩니다** — 구조가 단일 엔티티라 확장이 쌉니다.

| # | 질문 | 권고 |
| :-: | --- | --- |
| **5-A** | 현장 단말 팝업을 1차에 만드는가 | ✅ **만든다** — 단 기본은 「먼저 보인다」이고, **확인 요구를 켠 공지만 닫기 차단** |
| **5-B** | 「읽었다」 확인을 받는가 | ✅ **받는다** — 수신자별 확인 이력 |
| **5-C** | 대상 범위를 어디까지 | ✅ **전사 + 작업지시** — 나머지 3종은 값만 남기고 안 쓴다 |

**답해 주시면 그것이 정본이 됩니다.**

⚠ **5-A 는 POP 22화면에 전제를 하나 더합니다.** 「현장에서 공지를 보게 할 필요가 없다」고 판단하시면 **나로 가겠습니다** — 그때는 화면 1장으로 끝납니다.
