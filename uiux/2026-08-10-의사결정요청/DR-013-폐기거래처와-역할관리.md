## 1. Q1 — `partner_role` 이 **이미 있었다**

초안은 `mdm.partner` 에 `partner_type_code` 를 **신설**하려 했다. 실측하니 **역할 테이블이 이미 설계돼 있었다.**

```sql
CREATE TABLE mdm.partner_role (
    partner_role_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    partner_id       bigint NOT NULL REFERENCES mdm.partner(partner_id),
    role_type_code   app.code_t NOT NULL,
    CONSTRAINT uq_partner_role UNIQUE (partner_id, role_type_code)
);
```

⭐ **`(partner_id, role_type_code)` 유일 = 한 거래처가 여러 역할을 갖는 N:M 이다.** 공급사이면서 폐기업체가 성립한다.

⚠ **스펙·계약이 이 테이블을 한 번도 안 썼다(0건).** 이 저장소가 반복해 온 **A-13**(「없다」를 검색 없이 적는다)의 반대 형태다 — **있는데 못 봤다.**

| ⛔ 안 (가) `partner.partner_type_code` 신설 | ✅ 안 (나) `partner_role` 사용 |
| --- | --- |
| 컬럼 신설 1 — **#147 에 세 번째 스키마 변경**이 붙는다 | ⭐ **컬럼 신설 0** |
| 한 거래처 = **한 유형** | 여러 역할 — **공급사이면서 폐기업체** 성립 |
| ⛔ **기존 `partner_role` 과 축이 겹친다** | 설계 의도대로 쓴다 |

### 1-1. 남는 것 — `role_type_code` **값 목록**

⛔ **값 목록이 없다**(CHECK 0 · 시드 0). **공급사 · 고객 · 외주처 · 폐기처리 …** 를 정해야 한다.

⭐ **스키마 문제가 아니라 값 문제라 `#145`(공통코드 값 목록) 소관이다.** 업무 코드 44종에 **`roleTypeCode` 를 더한다** — 2차 제안안 대상.

## 2. Q2 — 거래처 본체는 **ERP 가 준다**

| 실측 | |
| --- | --- |
| **ERP 연계 스펙** | 「수신 = 품목·BOM·공통코드·조직·사용자·**거래처(공급사) 승격**」 — 🔹2026-07-08 확정 |
| **06 화면 12개** | ⛔ 거래처 마스터 **0건**(`W-06-01`~`12`) |
| **06 계약** | `GET /mdm/partners` — **읽기뿐** |
| ⭐ 계약이 이미 적어 뒀다 | 「선택 목록용. **관리 화면이 인벤토리에 없다**」 |

⛔ **「폐기업체를 MES 거래처 마스터에 등록한다」는 성립하지 않는다** — 등록 화면도 쓰기 경로도 없고, 거래처는 ERP 수신 마스터다.

### 2-1. ✅ 확정 — **본체는 ERP · 역할은 MES**

```
ERP  →  거래처 본체(코드·명·국가·ERP 코드)      수신 · MES 는 읽기만
MES  →  거래처 역할(partner_role)               ⭐ MES 가 편집한다
```

⭐ **ERP 가 안 주는 것을 MES 가 덧붙이는 형태**이고, `partner_role` 이 정확히 그 모양이다.

### 2-2. ⭐⭐ 선례가 **같은 화면에 있다** — `W-06-06` 「작업자」 탭

`W-06-06`(공통코드·조직·작업자 마스터) §3 이 이렇게 적고 있다.

> 세 축은 편집 주체·빈도·소유가 모두 다르다 — 코드는 표준화 TFT가 초기에, 조직은 인사 변동 시, **작업자는 ERP 수신 후 확장 속성만.**

⭐ **「ERP 가 본체를 주고 MES 가 확장 속성만 편집한다」가 이미 이 화면의 설계 원리다.** 거래처 역할을 **네 번째 탭**으로 얹으면 완전히 같은 모양이다.

| 무엇 | 결과 |
| --- | --- |
| **화면 신설** | ⛔ **0** — `W-06-06` 에 「거래처 역할」 탭 추가(**범위 확대**) |
| **인벤토리** | **117 유지** |
| **06 계약** | `partner_role` 읽기·쓰기 경로 신설 · `/mdm/partners` 에 역할 필터 |

## 3. Q3 — 「자체 폐기」는 **체크박스**로 말한다

`destination_type_code` 를 nullable 로 두면 **「아직 안 골랐다」와 「자체 폐기라 없다」가 같은 모양**이 된다.

```
《폐기 처리》
  ☐ 자체 폐기(외부 업체 없음)
  폐기 거래처  [ 선택 ▾ ]   ← 체크하면 비활성 · 값 비움
```

| ✅ | |
| --- | --- |
| **컬럼이 안 는다** — 화면 UX 로만 가른다 | 체크 = 도착지 짝을 비운다 · 미체크 = 거래처 필수 |
| **미입력과 구분된다** | 체크 없이 비우면 저장이 막힌다 |
| 공유계약 **G-1** 과 맞물린다 | 「없음」을 값으로 두지 않는다 |

## 4. 물리 모델에 요청하는 것 — **둘** (`#147`)

```sql
mdm.warehouse
  + is_defect boolean NOT NULL DEFAULT false          ← DR-012 3-C

logistics.goods_issue
  ~ destination_type_code  NOT NULL → NULL 허용        ← 이 확정
  ~ destination_id         NOT NULL → NULL 허용
  + CHECK (둘 다 NULL 이거나 둘 다 NOT NULL)            ← A-10 다형 짝
```

⭐ **`partner_role` 은 요청에 안 들어간다** — 테이블이 이미 있다. 필요한 것은 **값 목록**(`#145`)뿐이다.

## 5. ⛔ ERP 회계 계정은 하지 않는다 — **DR-009 유지**

> **DR-009** — 폐기 계정도 MES 밖이다. MES 는 「무엇을 몇 개 폐기했다」까지만 기록하고 **회계 계정**은 ERP 가 전표를 만들 때 정한다.

⭐ **폐기 거래처를 기록하는 것과 회계 계정을 고르는 것은 다르다.**

| | MES | ERP |
| --- | :-: | :-: |
| 무엇을 몇 개 폐기했나 | ✅ | |
| ⭐ **누가 가져갔나**(폐기 거래처) | ✅ | |
| **회계 계정**(폐기손실 계정 등) | ⛔ | ✅ |

⚠ **초판의 자기지적이 과했다** — 「폐기 거래처를 기록하는 것이 DR-009 와 어긋난다」고 적었는데, DR-009 확정문의 주어는 **회계 계정**이다. **거래처 기록은 계정이 아니다.** 그때 실제 결함은 「**요구 0건 · 화면 0건 · 등록할 자리 없음**」이었고 DR-009 는 방증이었다. → §7

## 7. ⭐ 이 건에서 배운 것 — **권고가 두 번 흔들렸다**

| 판 | 무엇 | 왜 틀렸나 |
| :-: | --- | --- |
| 초판 | `DISPOSAL_SITE` **권고** | ⛔ 요구·화면·등록처를 안 세고 「테이블이 있으니 값을 만든다」 |
| 2판 | **철회**(nullable 만) | ⛔ 자기지적이 과했다 — DR-009 의 주어는 **회계 계정**인데 「어긋난다」로 단정 |
| ✅ **확정** | **둘 다** — 거래처 기록 **+** nullable | 폐기 업체가 있으면 적고, 자체 폐기면 비운다 |

⛔⛔ **틀린 방향이 양쪽이었다** — 처음엔 **과하게 넣으려** 했고, 고칠 때는 **과하게 빼려** 했다. **둘 다 실측 전에 판단했다.**

⭐ **관문을 「확정 대조」가 아니라 「사용처 확인」으로 둔다** — 이번 건은 「누가 이 값을 넣나 · 넣을 화면과 요구가 있나」로 잡혔을 것이고, 확정 대조로는 애매하게 통과했을 수 있다(DR-009 는 계정 얘기였으므로).
