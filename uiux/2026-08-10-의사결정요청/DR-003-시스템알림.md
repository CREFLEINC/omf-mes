# 의사결정 요청서 **DR-003** — 시스템 알림을 어떻게 만들고 어디로 보내는가

| 항목 | 내용 |
| --- | --- |
| 번호 | **DR-003** |
| 작성일 | 2026-08-10 |
| 요청 대상 | 팀 리더 |
| 막고 있는 화면 | **2장** — 웹-알림센터(`W-CO-03`) · 웹-통합대시보드(`W-CO-05`) |
| 실제 파급 | ⚠ **알림을 만드는 화면 여럿** — 생산·재고·품질의 예외 흐름이 이것을 부른다 |
| 관련 이슈 | **#90** §1(알림 엔티티 부재) · **회신 E1**(알람 유형 값 목록) |

## 1. 무엇을 결정해야 하는가

**MES가 「이런 일이 생겼습니다」를 사람에게 알리는 방법.**

결정할 항목은 **셋**입니다.

| # | 결정 항목 | 선택지 |
| :-: | --- | --- |
| **3-A** | **알림을 어디로 보내는가** | 시스템 안에서만 / 외부 메신저까지 |
| **3-B** | **누가 받을지를 어떻게 정하는가** | 사람이 구독한다 / 역할로 정해 둔다 |
| **3-C** | **알림 유형 목록을 지금 정하는가** | 우리가 정한다 / 고객사 회신을 기다린다 |

## 2. 왜 결정해야 하는가

### 2-1. ⛔⛔ 확정 두 개가 **정면으로 부딪칩니다**

**이것이 이 요청서의 핵심입니다.**

| 날짜 | 확정 | 내용 |
| --- | --- | --- |
| **2026-07-04** | 현장검증 문답 24번 | 알람 매체 = **대시보드 + 카카오톡·Zalo 선택형** |
| **2026-07-10** | 운영 전제 C11 (기술책임자 확정) | 인터넷 = 설치·유지보수 때만 일시 보장, **운영 중 비보장.** → **「상시 원격 채널 · 클라우드 백업 · 외부 인공지능 서비스 전면 배제」** |

**카카오톡·Zalo 는 인터넷을 탑니다.** C11 이 「상시 원격 채널을 전면 배제한다」고 했으므로 **7월 4일 확정이 7월 10일 확정에 의해 무효가 됩니다.**

⛔ **그런데 그 무효화가 어느 문서에도 기록되지 않았습니다.** 문답 24번은 지금도 「카카오톡 또는 Zalo 선택 사용」으로 살아 있고, 설계결정서 2번은 그것을 **전제로 인용**하고 있습니다.

⚠ **이 요청서가 그 충돌을 처음 드러냅니다.** 지금 정하지 않으면 **알림센터 화면에 「외부 메신저 설정」 구획을 그릴지 말지**를 판단할 수 없습니다.

### 2-2. 알림을 저장할 곳이 없습니다

**`notification` 전 파일 검색 0건**입니다.

가장 가까운 것은 외부 시스템 연계용 발신함(`integration.integration_message`)인데, **그것은 다른 시스템에 보내는 전문**이지 사람에게 보내는 알림이 아닙니다.

### 2-3. ⭐ 이 화면 하나가 **전사 알람의 수렴처**입니다

2026-07-29 대시보드 정리에서 **알람 기능 5건이 화면 5개에서 삭제되고 전부 알림센터로 모였습니다.**

| 원래 있던 곳 | 지금 |
| --- | --- |
| 웹-생산현황-비가동알람 대시보드 | → **알림센터** |
| 웹-품질대시보드-불량발생알람 | → **알림센터** |
| 웹-설비툴-대시보드 | → 통합 대시보드로 병합 |
| 그 외 2건 | → 알림센터 |

**알림센터가 안 서면 그 5건이 전부 갈 곳을 잃습니다.**

### 2-4. 이미 쓴 화면들이 알림을 부르고 있습니다

| 화면 | 무엇을 알리려 하나 |
| --- | --- |
| **웹-생산계획-확정**(`W-02-06`) | 계획 확정·변경을 관계자에게 |
| **웹-알람유형-설정**(`W-06-10`) | 알람 유형 자체를 설정하는 화면 — **값 목록이 비어 있다** |
| **모바일-재고이동-스캔**(`M-01-05`) | 예외 발생 시 담당 관리자에게 |
| **웹-작업지시-진행현황**(`W-02-08`) | 지연·중단을 |

**요구사항 REQ-OA-0009**(관리자 개입이 필요한 예외는 담당 관리자에게 알람 통지)가 **도메인 01·02 예외 흐름 여러 곳에서 참조**됩니다. 지금까지 쓴 스펙에서 「알림 트리거 미정」으로 남긴 것이 여럿인데, **트리거 이전에 저장할 곳이 없습니다.**

⚠ **요구사항 원문 제목 자체가 「예외 상황 관리자 알람 — 매체 미확정·Zalo 검토」**입니다. **매체 미확정이 요구사항 단계부터 표시돼 있었습니다.**

## 3. 결정 항목별 상세

### 3-A. 알림을 어디로 보내는가

#### 안 가 · 시스템 안에서만 (사내망 완결)

```
사건 발생 → 알림 생성 → 알림센터에 쌓임 → 사용자가 웹에서 본다
                     → 화면 상단 배지에 미읽음 수 표시
```

| | |
| --- | --- |
| **닿는 사람** | **관리웹을 켜 놓고 있는 사람만.** 자리를 비우면 못 본다 |
| **필요한 것** | 알림 저장 + 수신자별 읽음 표시 |
| **C11 준수** | ✅ 인터넷을 타지 않는다 |

#### 안 나 · 외부 메신저까지 (카카오톡·Zalo)

```
사건 발생 → 알림 생성 → 알림센터
                     → 외부 메신저 발송  ← ⛔ 인터넷 필요
```

| | |
| --- | --- |
| **닿는 사람** | 자리를 비워도 휴대폰으로 받는다 |
| **필요한 것** | 위 + **외부 발송 설정·발송 이력·실패 재시도** + 메신저 사업자 계정 |
| **C11 준수** | ⛔ **위반.** 「상시 원격 채널 전면 배제」와 부딪친다 |
| **추가 문제** | 인터넷이 끊기면 **알림이 조용히 사라진다.** 발송 실패를 사람이 알 수 없다 |

#### 안 다 · 시스템 안에서 하되 **외부 발송 자리를 비워 둔다**

```
사건 발생 → 알림 생성 → 알림센터  (1차 범위)
                     ⋯ 외부 발송은 나중에 붙일 수 있게 구조만 남긴다
```

| | |
| --- | --- |
| **1차에 만드는 것** | 안 가와 동일 |
| **남겨 두는 것** | 알림에 「어느 채널로 보냈는가」를 적을 자리. 지금은 **사내 채널 하나만** 쓴다 |
| **C11 준수** | ✅ 지금은 인터넷을 타지 않는다 |

### 3-B. 누가 받을지를 어떻게 정하는가

| 안 | 방식 | 장점 | 단점 |
| :-: | --- | --- | --- |
| **가 · 구독** | 사용자가 **「나는 이 유형을 받겠다」**를 스스로 켠다 | 각자 필요한 것만 본다 | ⛔ **아무도 구독 안 하면 아무도 못 받는다.** 중요한 알림이 조용히 사라진다 |
| **나 · 역할 지정** | 알림 유형마다 **「이 역할이 받는다」**를 관리자가 정해 둔다 | 담당자가 바뀌어도 역할이 그대로면 계속 간다 | 개인이 끌 수 없다 |
| **다 · 둘 다** | 역할로 기본을 정하고 **개인이 추가로 켤 수 있다** | 기본이 보장되고 확장도 된다 | 화면과 설정이 는다 |

⚠ **요구사항 REQ-OA-0009 가 「담당 관리자에게 통지」라고 적습니다** — 「구독한 사람에게」가 아닙니다. **역할·담당 기반으로 읽힙니다.**

### 3-C. 알림 유형 목록을 지금 정하는가

**지금 상태** — 알람 이벤트 유형 목록이 **고객사 회신 대기(E1)**입니다. 그래서 웹-알람유형-설정 화면(`W-06-10`)이 **값 목록이 빈 채로** 물러나 있습니다.

⭐ **회신 E-3(판정유형)에서 겪은 것과 같은 형태입니다.** 그때도 「값 목록」을 물었는데 고객사가 답할 수 없었고, **우리가 정하고 고객사가 확인하는 형태로 바꿔** 종결했습니다.

**지금 이미 알 수 있는 것** — 화면들이 부르는 알림이 이만큼 있습니다.

| 무엇이 생겼을 때 | 어느 화면이 부르나 |
| --- | --- |
| 관리자 개입이 필요한 **예외**가 생겼다 | 모바일·POP 현장 화면 여럿 (REQ-OA-0009) |
| **결재가 내 차례**로 왔다 | 웹-결재함 · 승인이 붙은 화면 전부 |
| 생산 계획이 **확정·변경**됐다 | 웹-생산계획-확정 |
| 설비가 **멈췄다**(비가동·고장) | 모바일-설비고장-현장보고 · POP-비가동실적-입력 |
| 품질 **불량이 발생**했다 | 검사 판정 3형 |
| 재고가 **기준을 벗어났다** | 웹-재고현황 계열 |
| 예방보전 **시기가 도래**했다 | 웹-툴보전오더-생성 |

## 4. 결정되면 어디에 영향을 주는가

### 4-1. 화면

| 결정 | 영향 |
| --- | --- |
| **3-A 안 가·다** | 웹-알림센터에 **외부 발송 설정 구획을 그리지 않는다** |
| **3-A 안 나** | 위 구획 + **발송 실패 목록**이 필요하다. 화면이 1장 더 늘 수 있다 |
| **3-B 안 가** | 웹-알림센터에 **구독 설정 구획**이 생긴다 |
| **3-B 안 나** | 구독 구획 없음. 대신 **웹-알람유형-설정**에 「이 유형은 어느 역할이 받는가」 축이 생긴다 |
| **3-C 우리가 정함** | **웹-알람유형-설정의 값 목록이 채워진다** — 지금 빈 채로 물러나 있다 |

### 4-2. 이미 쓴 화면

| 화면 | 무엇이 걸리나 |
| --- | --- |
| **웹-알람유형-설정**(`W-06-10`) | 3-B·3-C 가 **이 화면의 편집 대상을 정한다** |
| **웹-생산계획-확정** 등 알림을 부르는 화면 | 「알림 트리거 미정」으로 물러나 있던 것이 **풀린다** |

### 4-3. 데이터 모델

**알림 저장 + 수신자별 읽음 표시**가 필요합니다. 3-B 에 따라 「누가 받는가」를 정하는 자리가 달라집니다.

⚠ **공지·전달(`W-CO-04`, DR-005 대상)과 구조가 같습니다** — 둘 다 「보낸 것 하나 : 받은 사람 여럿, 각자 읽음 표시」입니다. **DR-005 와 함께 설계하는 것이 낫습니다.**

## 5. 권고안

### 5-A. **안 다 — 시스템 안에서 하되 외부 발송 자리를 비워 둔다**

**이유 셋입니다.**

1. **C11 이 나중 확정이고 더 강합니다.** 7월 10일 기술책임자 확정이 「상시 원격 채널 전면 배제」라고 명시했고, 7월 4일 알람 매체 확정은 그 전입니다. **나중 확정이 이깁니다.**
2. **인터넷이 끊기면 알림이 조용히 사라집니다.** 운영 중 인터넷 비보장인데 외부 메신저를 정상 경로에 두면, **가장 알림이 필요한 순간(네트워크 장애)에 가장 확실히 실패**합니다.
3. **나중에 붙일 수 있게 남겨 둡니다.** 고객사가 「그래도 카카오톡으로 받고 싶다」고 하면 **채널 축 하나를 추가**하면 됩니다. 처음부터 만들면 쓰지도 않는 발송 실패 처리를 유지해야 합니다.

⚠ **이것은 「고객사 요구를 거절한다」가 아닙니다.** 문답 24번의 「선택형」을 그대로 살리되 **1차에는 사내 채널 하나만 켠다**는 뜻입니다. 그리고 **충돌 사실을 고객사에 알려야 합니다** → §6.

### 5-B. **안 나 — 역할로 정해 둔다**

**이유 둘입니다.**

1. **요구사항이 「담당 관리자에게 통지」라고 적습니다.** 구독이면 「구독한 사람에게」가 되어 요구와 달라집니다.
2. **구독은 조용히 실패합니다.** 아무도 구독하지 않은 유형은 **아무에게도 안 갑니다.** 예외 알림이 그렇게 사라지면 REQ-OA-0009 가 무의미해집니다.

⚠ **개인 구독은 나중에 더할 수 있습니다** — 역할 기본이 있으면 개인 추가는 위에 얹는 것이라 안전합니다. 반대는 위험합니다.

### 5-C. **우리가 정한다 — 7종으로 시작**

§3-C 표에 적은 7가지가 **화면들이 실제로 부르는 것**입니다. 이것을 초기 값 목록으로 삼고, **운영 중 관리자가 추가할 수 있게** 합니다(웹-알람유형-설정 화면이 그 자리입니다).

⭐ **판정유형 때와 같은 방식입니다** — 우리가 정하고 고객사가 확인합니다. 회신 E1 을 기다리지 않습니다.

## 6. ⚠ 이 결정이 고객사에 알려야 하는 것을 만듭니다

**5-A 를 택하면 7월 4일 확정 하나가 실질적으로 바뀝니다.**

| 무엇 | 어떻게 |
| --- | --- |
| 문답 24번 「카카오톡·Zalo 선택 사용」 | **1차 범위에서 쓰지 않는다**로 정정 |
| 「Zalo 기업 API 기술 검토 = CREFLE가 함」 | **보류** — 1차에 쓰지 않으므로 검토 시점을 늦춘다 |

⚠ **이것은 우리가 조용히 뺄 수 있는 것이 아닙니다.** 고객사가 「휴대폰으로 알람을 받는다」고 기대하고 있을 수 있습니다. **결정하시면 정정 통지를 준비하겠습니다.**
