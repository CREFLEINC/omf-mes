## ✅ 확정 (2026-08-13) — **3-C · `is_defect` 불리언으로 뺀다**

**「불량인가」는 창고 유형이 아니라 별도 축이다.** `is_external` 과 같은 모양으로 둔다.

```sql
-- 선례 (SQL 305 · 315)
is_external  boolean NOT NULL DEFAULT false,
CONSTRAINT ck_external_warehouse_partner
    CHECK (NOT is_external OR partner_id IS NOT NULL)

-- 신설 요청
is_defect    boolean NOT NULL DEFAULT false
```

| 무엇 | 결과 |
| --- | --- |
| **창고 유형 5종** | ⭐ **안 건드린다** — 자재·제품·반제품·상품·생산 그대로 |
| ⭐ **선행 조건 소멸** | 3-A 였다면 「**5종의 출처가 상류에 있는가**」를 먼저 확인해야 했다. 3-C 는 5종을 안 건드리므로 **그 확인이 불필요하다** |
| **축** | ✅ **안 섞인다** — 「자재창고이면서 불량」이 표현된다 |
| ⛔ **소관 이동** | **컬럼 신설이라 데이터모델 소관**이다 — `#64` 계열로 올린다(assignee 필수) |
| **화면** | `W-01-06` §3 의 창고 선택이 **`is_defect = true` 로 걸러진다** |
| **값 목록** | ⭐ `warehouseTypeCode` 가 **1차 대상에서 빠진다** — 불량과 무관해졌다 |

### ⚠ 남는 것 — **한 불량창고가 자재·제품을 함께 받으면 유형이 무엇인가**

3-C 가 축 섞임은 풀었으나 **이것은 안 푼다.** `W-01-06`(자재 폐기)과 `W-04-10`(제품 폐기)이 **같은 「불량창고」를 말하는데**, 그 창고의 `warehouse_type_code` 는 여전히 5종 중 하나여야 한다.

| 갈래 | |
| --- | --- |
| (a) | 품목 종류별로 불량창고를 나눈다 — 자재 불량창고(유형=자재) · 제품 불량창고(유형=제품) |
| (b) | 하나를 두고 유형을 대표값으로 둔다 — **유형이 그 창고를 설명하지 못한다** |

✅ **2026-08-13 결정 — (a) 나눈다.** 자재 불량창고(유형=자재) · 제품 불량창고(유형=제품)로 갈라 두고 둘 다 `is_defect=true` 를 켠다.

| 근거 | |
| --- | --- |
| **확정과 충돌 없음** | QA #15 의 「불량창고 반품입고 **통일**」은 **반품 3유형의 처리 경로 통일**이지 창고를 합친다는 뜻이 아니다 |
| ⭐ **행위자가 이미 갈렸다** | 자재 축 = **물류담당**(`W-01-06`·`W-01-05`·`M-01-10`) / 제품 축 = **완제품창고담당**(`W-04-06`·`W-04-11`) |
| **정상 창고 선례** | 자재창고(141회) ↔ 완제품창고(31회)가 이미 갈려 있다 — 불량창고만 합치는 것이 어긋난다 |

⭐ **`is_defect` 를 대체하지 않고 보완한다** — 나눠도 자재창고와 자재 불량창고는 **유형이 같아** 구분되지 않는다.

⭐ **확장에 강하다** — 반제품·상품 불량창고가 필요해지면 **값 추가 없이** `is_defect` 만 켠다.

## 1. 무엇을 결정해야 하는가

**`warehouse_type_code`(창고 유형)의 값 집합에 「불량」을 넣는가**입니다.

```
지금 스펙   창고유형 = 자재 · 제품 · 반제품 · 상품 · 생산      5종
실제 업무   불량창고가 스펙 전체에 92회 등장한다
              ⛔ 그 다섯 안에 「불량」이 없다
```

## 2. 왜 지금 나왔는가

### 2-1. `W-01-06` 이 불량창고로 거른다

DR-010 확정으로 `W-01-06` §3 이 **2단**이 됐고, 1단이 이렇습니다.

```
1단 · 입고 전표   창고 [불량창고▾]  기간 [        ]  [조회]
```

⛔ **이 드롭다운이 무엇으로 채워지는지가 정해져 있지 않습니다.** 창고 유형으로 거른다면 「불량」이라는 유형 값이 있어야 합니다.

### 2-2. ⭐ 불량창고는 **창고다** — 그건 확정돼 있습니다

「구역인가 창고인가」를 실측으로 갈랐습니다.

| 근거 | 무엇을 말하나 |
| --- | --- |
| ✓확정 **QA #15** | 「불량창고 **우선 입고**」 — `warehouse_id` 를 갖는다 |
| `M-01-10` 재고이동·불량반출 | `destination_location_id` **NOT NULL** — **불량창고의 위치**가 있다 |
| WF01 **S8** | 「재고이동(창고·Location·파렛트 간) + **불량창고 반출**」 — 창고 간 이동이다 |
| ✅REQ-PR-0025 | 「판정은 **불량창고 입고 후**」 |

⭐ **`quality_zone_code`(Location 의 품질구역)가 아닙니다.** 그것은 Location 속성이고 값 목록도 따로 미정입니다. **불량창고는 창고 인스턴스입니다.**

→ **그래서 남는 질문은 하나** — **그 창고의 유형이 무엇인가.**

### 2-3. ⛔⛔ 진짜 문제 — **5종이 이미 두 축을 섞고 있습니다**

| 값 | 무엇으로 분류하나 |
| --- | --- |
| 자재 · 제품 · 반제품 · 상품 | **무엇을 보관하는가** (품목 종류) |
| 생산 | **무엇에 쓰는가** (용도) |

⛔ **「불량」을 넣으면 세 번째 축(품질 상태)이 들어옵니다.**

⚠ **그리고 불량창고는 자재 불량도 제품 불량도 받습니다.**

```
W-01-06   자재 폐기      불량창고 입고분
W-04-10   제품 폐기      같은 축
```

⭐ **품목 종류로 분류하는 축에서는 「불량창고」가 자재도 제품도 아니게 됩니다.**

### 2-4. ⚠ 스펙이 이미 「미확인」이라 적었습니다

`W-06-07` §8-3:

> 창고유형 5종(자재·제품·반제품·상품·생산)이 `warehouse_type_code` 공통코드 값과 **1:1인지 미확인** — 확인 필요

⭐ **5종이 어디서 온 것인지도 계약·화면에는 근거가 없습니다.** §4-A 표에 적혀 있을 뿐입니다.

### 2-5. 외부창고는 이미 갈려 있습니다 — **선례**

```
is_external  boolean                        ← 유형이 아니라 별도 축
partner_id   조건부 필수(ck_external_warehouse_partner)
```

⭐ **「외부인가」를 유형 값으로 넣지 않고 불리언으로 뺐습니다.** 같은 방식이 「불량인가」에도 쓰일 수 있습니다 → 안 C.

## 3. 결정 항목 — **안 넷**

### 3-A · ⭐ **유형 값에 `DEFECT`(불량)를 더한다** *(권고)*

5종 → **6종**.

| ✅ | ⛔ |
| --- | --- |
| ⭐ **화면이 곧바로 선다** — `W-01-06` 이 유형으로 거른다 | ⛔ **축이 셋으로 섞인다**(품목 종류 · 용도 · 품질) |
| 값 하나만 더하면 된다 — **구조 변경 0** | ⚠ 자재 불량과 제품 불량을 **한 유형이 받는다** |
| 「생산」이 이미 용도 축이라 **선례가 있다** | |

### 3-B · **품목 종류와 무관하게 「불량」을 유형으로 두고 나머지도 용도 축으로 재편한다**

자재·제품·반제품·상품을 빼고 **용도 축**(일반·생산·불량·출하…)으로 통일합니다.

| ✅ | ⛔ |
| --- | --- |
| ⭐ **축이 하나가 된다** — 가장 깨끗하다 | ⛔⛔ **5종을 뒤집는다** — 어디서 왔는지 모르는 값을 폐기하게 된다 |
| 「무엇을 보관하나」는 **재고가 이미 안다**(품목별 잔액) | ⚠ 상류(개념·논리 모델)에 5종의 출처가 있으면 충돌한다 |

### 3-C · **`is_defect` 불리언으로 뺀다** — 외부창고와 같은 방식

| ✅ | ⛔ |
| --- | --- |
| ⭐ **선례가 있다** — `is_external` 이 정확히 이 모양 | ⛔ **물리 모델에 컬럼 신설**이 필요하다 — #64 계열이 된다 |
| 축이 안 섞인다 — 「자재창고이면서 불량」이 표현된다 | ⚠ 값 목록 문제가 **구조 문제로 바뀐다**(소관 이동) |

### 3-D · **불량창고를 유형으로 구분하지 않는다** — 인스턴스 이름으로만 둔다

| ✅ | ⛔ |
| --- | --- |
| 아무것도 안 해도 된다 | ⛔ **`W-01-06` 이 창고를 이름으로 골라야 한다** — 사업장이 늘면 깨진다 |
| | ⛔ **✅REQ-PR-0025 「불량창고 입고 후 판단」을 시스템이 판별 못 한다** |

## 4. 실측

| 무엇 | 결과 |
| --- | :-: |
| 스펙 전체의 「불량창고」 | **92회** |
| 창고 유형 5종에 「불량」 | ⛔ **없다** |
| 불량창고가 `warehouse_id` 를 갖는가 | ✅ **그렇다**(QA #15 · `M-01-10`) |
| `warehouse_type_code` 에 걸린 CHECK 제약 | ⛔ **0건** |
| 공통코드 시드에 `WAREHOUSE_TYPE` 그룹 | ⛔ **없다**(시드된 그룹은 `OPERATION_POLICY`·`INVENTORY_STATUS` **둘뿐**) |
| 5종의 출처 | ⚠ **`W-06-07` §4-A 표에만 있다** — 상류 근거 미확인 |

## 5. 권고 — **3-A**, 단 조건이 있습니다

**두 가지를 먼저 봤습니다.**

| 물음 | 답 |
| --- | --- |
| **용도가 하나인가** | ✅ **그렇다** — 불량창고를 판별해야 하는 화면이 `W-01-06`·`W-04-10`·`M-01-10` 로 **여럿이고 전부 같은 뜻**이다 |
| **고객 약속인가** | ✅ **그렇다** — ✅**REQ-PR-0025** 가 「판정은 **불량창고 입고 후**」라 못박았다. 시스템이 「불량창고인가」를 알아야 한다 |

⭐ **3-A 를 권고합니다** — 값 하나를 더하는 것이 가장 싸고, **「생산」이 이미 용도 축이라 축이 섞이는 것은 새로 생기는 문제가 아닙니다.**

⚠ **조건** — 5종의 출처를 먼저 확인해야 합니다. **상류(개념·논리 모델)에 5종이 확정으로 박혀 있다면** 값을 더하는 것도 상류 변경이라 `[uiux→docs]` 로 가야 합니다. **`W-06-07` §8-3 이 「1:1인지 미확인」이라 한 것이 이 뜻입니다.**

⭐ **3-C 가 설계로는 가장 깨끗합니다**(축이 안 섞인다 · 선례 있음). **다만 컬럼 신설이라 값 문제가 구조 문제로 바뀌고 소관이 데이터모델로 넘어갑니다.** 속도를 우선하면 3-A, 구조를 우선하면 3-C 입니다.

## 6. 무엇을 막고 있나 — **막지 않되 화면이 임시로 섭니다**

| | |
| --- | --- |
| **지금** | `W-01-06` 이 「창고 [불량창고▾]」로 그려져 있고 **선택지 출처가 비어 있다**(G-2) |
| **프론트** | 값이 오면 `code-options.ts` 한 파일로 반영된다(client #34) |

✅ **함께 걸렸던 폐기 출고 도착지도 풀렸습니다** — 「폐기 전용 Location」이 아니라 **컬럼을 nullable 로** 바꾸는 것으로 정해져(2026-08-13) **창고 유형 축과 분리됐습니다.** → 1차 제안안 §6
