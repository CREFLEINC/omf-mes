# 의사결정 요청서 **DR-011** — 공통코드 **값 목록**을 누가 언제 정하는가

| 항목 | 값 |
| --- | --- |
| 요청일 | 2026-08-13 |
| 요청 주체 | CREFLE OMF 팀 (UI/UX) · **프론트 우선 상향 재요청 접수**(client #34) |
| 결정 주체 | 팀 리더 |
| 상태 | ⏳ **회신 대기** |
| 막고 있는 것 | ⚠ **막지 않습니다** — 다만 **화면 하나당 자리표시가 아홉**이고 전 화면으로 번집니다 |

---

## 1. 무엇을 결정해야 하는가

**「입고 유형」·「출고 유형」·「사유」 같은 코드에 **어떤 값이 들어가는지**를 누가 언제 정하는가**입니다.

```
계약        issueTypeCode  app.code_t     ← 자리는 있다
화면        [ 선택지 준비 중 ▾ ]           ← 무엇을 넣을지 모른다
```

## 2. 왜 지금 나왔는가

### 2-1. ⛔ 프론트가 세어 보니 **한 화면에 아홉**입니다

`W-01-06` 하나를 구현하며 보고가 올라왔습니다(client #34).

> **미확정 코드가 아홉**(이슈는 둘) — `code-options.ts` 한 곳 + 전환 감지기. **질문: 확정 범위가 아홉을 덮는가? 우선 상향 재요청.**

**실측으로 확인했습니다 — 정확히 아홉입니다.**

| 코드 | 어디 |
| --- | :-: |
| `receiptTypeCode` · `sourceDocumentTypeCode` · `reasonCode` | 01 입고 |
| `inventoryStatusCode` · `qualityStatusCode` | 01 입고 라인 |
| `issueTypeCode` · `destinationTypeCode` | 01 출고 |
| `warehouseTypeCode` · `managementLevelCode` | 06 창고 |

⚠ **착수 통지 §4 는 두 건만 적었습니다** — 스펙 §8 을 번역했는데 **스펙 §8 이 계약이 요구하는 코드를 전부 세지 않았습니다.**

### 2-2. ⛔⛔ 우리가 이미 물었고 **답이 없었습니다**

`#64` 코멘트(확대 4차)에 이렇게 적혀 있습니다.

> 값 목록 요청 2건이 추가로 확인돼 여기 덧붙입니다. **컬럼 신설이 아니라 값 집합 정의**라 별도 이슈로 내지 않았습니다 — 이 이슈가 「확정이 하류에 착지하지 않은 것」의 우산이라 함께 두는 것이 맞다고 봤습니다. **별도 관리가 나으면 말씀 주세요.**

⭐ **그 물음에 답이 오지 않은 채 값 목록이 계속 쌓였습니다.**

### 2-3. `#64` 는 값 목록 이슈가 아닙니다

| | |
| --- | --- |
| **`#64` 제목** | 「확정 사항의 **물리 모델** 미착지 8건 — 다국어 명칭·품목 확장속성·Rev 플래그…」 |
| **담당** | `wooju-shin`(데이터모델) |
| **성격** | **컬럼·구조 부재** |

⛔ **값 목록은 컬럼 문제가 아니라 업무 문제**입니다. 데이터모델 담당이 정할 사안이 아닙니다.

⚠ **그런데 스펙 전체가 「값 목록 미확정 → `W-06-06` · #64」로 보내고 있습니다** — 실측 5곳.

### 2-4. 지금 어떻게 굴러가고 있나

```
화면    G-2 적용 — 「선택지 준비 중」 비활성 또는 자리표시
계약    enum 을 못박지 않고 x-internal-note 로 남김
프론트  code-options.ts 한 곳 + 값이 오면 자동 반영되는 전환 감지기
```

⭐ **셋 다 「오면 받는다」로 준비돼 있습니다.** 막히지 않습니다 — **다만 안 오면 끝까지 자리표시입니다.**

### 2-5. ⭐ 해소된 선례가 있습니다 — **E-3**

`판정 유형 값 목록`(회신 E-3)이 이렇게 풀렸습니다.

```
uiux/2026-08-07-E3-판정유형-제안안/
   E3-판정유형-상태목록-제안안.md      ← 우리가 안을 만들고
   LOT상태-확정기록.md                 ← 팀 리더가 확정
```

⭐ **고객 회신을 기다리지 않고 우리가 제안안을 만들어 확정받았습니다.** 그 결과 **화면 19장이 한 번에 풀렸습니다.**

## 3. 결정 항목 — **안 셋**

### 3-A · ⭐ **E-3 방식으로 우리가 제안안을 만든다** *(권고)*

전 화면의 미확정 코드를 모아 **값 제안안**을 만들고 확정받습니다.

| ✅ | ⛔ |
| --- | --- |
| ⭐ **선례가 있고 통했다** — E-3 가 19화면을 한 번에 풀었다 | ⚠ **우리 작업이 는다** — 전 화면 코드 수집 + 안 작성 |
| **고객 회신을 안 기다린다** — 대부분은 업무 상식으로 정해진다 | ⚠ 고객 실무와 다를 수 있다 — **확정 후 바뀌면 값만 고친다**(구조 무영향) |
| 프론트의 자리표시가 **한 번에 걷힌다** | |

### 3-B · **값 목록 전용 이슈를 만들고 `#64` 에서 뗀다**

`[uiux→docs]` 또는 공통코드 전용 이슈를 새로 냅니다.

| ✅ | ⛔ |
| --- | --- |
| 소관이 맞아진다 — 데이터모델 담당에서 뗀다 | ⛔ **이슈만 옮긴다고 값이 정해지지 않는다** |
| 추적이 명확해진다 | ⚠ **누가 정하는가**가 여전히 안 정해진다 |

### 3-C · **지금대로 둔다 — 값이 올 때까지 자리표시**

| ✅ | ⛔ |
| --- | --- |
| 아무것도 안 해도 된다 | ⛔ **전 화면이 자리표시로 완성된다** — 화면 하나에 아홉이면 116화면이면… |
| 구조는 안 흔들린다(G-2 가 이미 덮는다) | ⛔ **인수 시점에 한꺼번에 터진다** |

## 4. 실측

| 무엇 | 결과 |
| --- | :-: |
| `W-01-06` 흐름의 `*Code` 필드 | **13** |
| 그중 **값 목록 없음** | ⛔ **9** *(프론트 보고와 일치)* |
| 착수 통지 §4 가 적은 것 | **2** |
| `#64` 의 성격 | 물리 모델 컬럼 부재 — **값 목록 아님** |
| 스펙이 값 목록을 보내는 곳 | `W-06-06` 5 · 회신 E-3/E-4/E-9 4 · `#64` |
| 해소 선례 | ✅ **E-3**(우리 제안 → 팀 리더 확정 → **19화면 해소**) |

## 5. 권고 — **3-A + 3-B 함께**

**두 가지를 먼저 봤습니다.**

| 물음 | 답 |
| --- | --- |
| **용도가 하나인가** | ⛔ **아니다** — 아홉이 **전 도메인에 걸친다.** 화면마다 따로 정하면 같은 코드가 갈린다 |
| **고객 약속인가** | ⚠ **일부만** — `E-4`(폐기 계정)처럼 **고객이 정해야 하는 것**과 「입고 유형」처럼 **업무 상식으로 정해지는 것**이 섞여 있다 |

⭐ **그래서 먼저 갈라야 합니다** — 우리가 정할 수 있는 것과 고객이 정해야 하는 것.

**E-3 가 그 방식으로 통했습니다.** 제안안을 만들면 대부분은 「이걸로 갑시다」로 끝나고, **정말 고객이 정해야 하는 것만 회신 대기로 남습니다.**

⚠ **3-B 만 하면 값이 안 정해집니다** — 이슈를 옮기는 것과 값을 정하는 것은 다릅니다. **함께 해야 합니다.**

## 6. 무엇을 막고 있나 — **막지 않되 번집니다**

```
지금    W-01-06 하나에 자리표시 9
        프론트가 code-options.ts + 전환 감지기로 준비해 둠
```

⭐ **프론트가 잘 준비했습니다** — 값이 오면 **한 파일만 고치면** 반영됩니다.

⛔ **다만 화면이 늘수록 자리표시가 늘고**, 인수 시점에 「선택지 준비 중」이 화면마다 남습니다.
