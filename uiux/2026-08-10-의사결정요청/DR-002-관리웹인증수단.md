## ✅ 확정 (2026-08-10)

**세 항목 모두 권고안대로 확정됐다. 이 문서가 정본이다.**

| # | 확정 내용 |

| **2-A** | **MES가 직접 아이디·비밀번호를 갖는다.** 사용자가 자기 비밀번호를 보유한다. 사내 계정 체계에 위임하지 않는다 |
| **2-B** | **비밀번호 정책은 최소** — ① 복원 불가 형태로 저장 ② 로그인 실패 누적 시 잠금 ③ 관리자가 초기화해 준다. **만료 주기·문자 조합 규칙·직전 비밀번호 재사용 금지는 두지 않는다** |
| **2-C** | **권한 범위에 법인 축을 두지 않는다.** 사업부·공장 두 축을 그대로 쓴다 |

### 이 확정이 낳는 것

| 무엇 | 어디에 |
| --- | --- |
| **화면 1장 신설** — 웹-비밀번호-변경 | 화면 인벤토리 **113 → 114** |
| 웹-계정-로그인 설계 착수 | 아이디·비밀번호 입력 · 실패 잠금 안내 |
| **웹-사용자권한-매트릭스의 「비밀번호 초기화」 액션 유지** | 이미 쓴 화면 — 안 나였다면 뺐을 액션이 **살아남았다** |
| 사용자 계정에 **비밀번호·실패 횟수·마지막 로그인 시각** 필요 | 화면 작성 후 데이터 모델에 넘긴다 |
| 권한 매트릭스에 **「범위는 사업부·공장 단위」 명시** | 운영자가 법인 단위를 기대하지 않게 한다 |

### ⚠ 확정하지 **않은** 것 — 두지 않기로 한 셋

**뺀 것을 명시한다.** 나중에 「왜 없나」가 나오면 이 줄을 근거로 쓴다.

| 뺀 것 | 이유 |
| --- | --- |
| 비밀번호 **만료 주기** | 매일 쓰지 않는 사무 사용자가 **업무 시점에 막힌다** |
| 문자 **조합 규칙** | 1차 범위를 좁히는 방침(결재선 사람만 · 값 구간 미사용 · 대리 결재 없음)과 같은 기준 |
| 직전 비밀번호 **재사용 금지** | 비밀번호 이력 저장이 필요해진다 |

⭐ **실패 잠금과 복원 불가 저장은 최소에 포함된다** — 보안을 낮춘 것이 아니라 **운영 마찰을 만드는 셋만** 뺐다.

## 1. 무엇을 결정해야 하는가

**사무실에서 관리웹을 쓰는 사람이 「나는 나다」를 무엇으로 증명하는가.**

결정할 항목은 **셋**입니다.

| # | 결정 항목 | 선택지 |
| :-: | --- | --- |
| **2-A** | **인증 방식** | MES가 직접 아이디·비밀번호를 갖는다 / 사내 계정 체계에 위임한다 |
| **2-B** | **비밀번호 정책의 범위** | 최소만 둔다 / 만료·복잡도·이력까지 둔다 |
| **2-C** | **권한에 「법인」 축을 두는가** | 둔다 / 두지 않는다 |

⚠ **2-C 는 인증이 아니라 인가입니다.** 같은 이슈(#69)에 묶여 있고 같은 화면군에 걸려 함께 냅니다.

## 2. 왜 결정해야 하는가

### 2-1. 지금 로그인 화면을 그릴 수 없습니다

사용자 계정 테이블(`app.app_user`)의 실측입니다.

| 있는 것 | 없는 것 |
| --- | --- |
| `login_id` (유일) · `user_name` · `email` · `department_id` · `status_code` · `is_active` | **비밀번호** · **마지막 로그인 시각** · **로그인 실패 횟수** · **비밀번호 변경 시각** |

**아이디는 있고 비밀번호가 없습니다.** 로그인 화면에 입력란 두 개를 그리는데 **한 칸이 저장될 곳이 없습니다.**

### 2-2. ⭐ 세 프로그램 중 관리웹만 인증 수단이 없습니다

공유 계약 F-2 가 인증·기능구성·귀속 **세 축**을 분리해 두었습니다. 그 표의 실측 상태입니다.

| 프로그램 | 「나는 나다」를 무엇으로 증명하나 | 상태 |
| --- | --- | :-: |
| **POP**(현장 터치 단말) | **단말 토큰** — 우리가 설치한 단말에서 온 요청인가 | ✅ 설계 완료 |
| **모바일**(휴대 단말) | **단말 토큰** — 동일 | ✅ 설계 완료 |
| **관리웹**(사무 PC) | **계정 토큰** — 이 사람에게서 온 요청인가 | ⛔ **수단이 없다** |

⭐ **POP 의 사번 입력은 인증이 아닙니다.** 이미 쓴 화면(POP-사번경량인증, `P-CO-01`)이 스스로 밝힙니다 — **「이 화면은 인증이 아니라 귀속이다. 인증은 셸이 단말 토큰으로 이미 통과했다.」** 사번은 「누가 한 일로 기록할 것인가」에만 답합니다.

⚠ **그래서 현장에는 인증 경계가 하나(단말) 있고, 사무에는 아직 없습니다.**

### 2-3. 화면 1장이지만 **관리웹 72장이 이것을 전제**합니다

이미 쓴 관리웹 화면들이 「로그인한 사용자」를 전제로 설계돼 있습니다.

| 무엇을 전제하나 | 어느 화면 |
| --- | --- |
| **누가 결재하는가** | 웹-결재함 · 웹-특채한도승인-처리 · 웹-폐기품의 등 승인 화면 전부 |
| **누가 발행했는가** | 출력물을 만드는 화면 전부 |
| **누가 확정했는가** | 검사 판정 3형 · 출하 확정 |
| **무엇을 볼 수 있는가** | 권한 매트릭스(`W-CO-02`) · 데이터 범위 |

**인증 수단이 늦게 정해지면 이 전제들이 흔들립니다.** 그래서 화면 수가 1장인데도 순서를 앞에 두었습니다.

### 2-4. 운영 환경이 선택지를 좁힙니다

| 확정 사실 | 무엇을 뜻하나 |
| --- | --- |
| **온프레미스 설치형** — 고객사 서버에 설치 | 외부 인증 서비스에 의존할 수 없다 |
| **운영 중 인터넷 비보장** | 인터넷을 타는 인증은 **끊기면 아무도 못 들어온다** |
| 서버 웜 스탠바이 2대 + 네트워크 저장장치 | 사내망 안에서 완결돼야 한다 |

⛔ **외부 계정(구글·마이크로소프트 등)은 후보에서 제외됩니다.** 인터넷이 끊기면 공장이 멈춥니다.

## 3. 결정 항목별 상세

### 3-A. 인증 방식 — 두 갈래

#### 안 가 · MES가 직접 아이디·비밀번호를 갖는다

```
사용자 → [아이디 / 비밀번호] → MES 서버가 대조 → 통과
```

| | |
| --- | --- |
| **필요한 것** | 사용자 계정에 **비밀번호 저장 칸**(복원 불가 형태) · 실패 횟수 · 마지막 로그인 시각 |
| **필요한 화면** | 로그인 · 비밀번호 변경 · **비밀번호 초기화**(관리자가 해 주는 것) |
| **장점** | 사내 계정 체계가 없어도 **바로 쓸 수 있다.** 인터넷·외부 시스템에 의존하지 않는다 |
| **단점** | 비밀번호를 **우리가 책임진다.** 분실·유출·정책을 전부 MES가 다룬다 |

#### 안 나 · 사내 계정 체계에 위임한다

```
사용자 → 사내 계정 서버가 대조 → 통과 사실만 MES가 받음
```

| | |
| --- | --- |
| **필요한 것** | 고객사에 **사내 계정 서버가 실재해야 한다**(사내 디렉터리 서비스 등) |
| **필요한 화면** | 로그인 1장(아이디·비밀번호를 받아 **넘기기만** 한다) |
| **장점** | 비밀번호를 **우리가 갖지 않는다.** 퇴사자 차단이 사내 체계에서 한 번에 된다 |
| **단점** | ⛔ **고객사에 그 체계가 있는지 확인되지 않았습니다.** 없으면 이 안은 성립하지 않는다 |

⚠ **확인된 사실이 없습니다** — 고객사의 사내 계정 체계 유무는 지금까지 어느 문서에도 나오지 않았습니다(전수 검색). **없다고 단정하지도, 있다고 가정하지도 않았습니다.**

### 3-B. 비밀번호 정책의 범위

안 가를 택할 때만 해당합니다.

| 안 | 무엇을 두나 | 화면 영향 |
| :-: | --- | --- |
| **최소** | 저장(복원 불가) · 실패 횟수로 잠금 · 관리자 초기화 | 로그인 1 + 비밀번호 변경 1 |
| **표준** | 위 + **만료 주기** · 복잡도 규칙 · **직전 비밀번호 재사용 금지** | 위 + **최초 로그인 시 강제 변경** 흐름 · 만료 임박 알림 |

⚠ **표준을 택하면 화면이 늘어납니다** — 만료된 사용자가 로그인하면 **비밀번호 변경 화면으로 강제 이동**하는 흐름이 생기고, 그것은 로그인 화면의 분기 하나가 아니라 **별도 상태**입니다.

### 3-C. 권한의 「법인」 축

**지금 상태의 실측입니다.**

```
app.user_data_scope
    business_unit_id   ← 사업부 단위로 볼 수 있는 범위
    plant_id           ← 공장 단위로 볼 수 있는 범위
    (법인 없음)
```

조직 계층은 **법인 → 사업부 → 공장 → 부서** 넷이 다 실재합니다. **그런데 권한 범위는 사업부·공장 둘로만 줍니다.**

⛔ **무엇이 문제인가** — 「이 사람은 A법인 것만 본다」를 주려면 **A법인에 속한 사업부를 전부 나열**해야 합니다. 나중에 A법인에 사업부가 하나 추가되면 **그 사람에게 자동으로 열리지 않습니다.** 반대로 **누군가 그 사업부를 나열해 주지 않으면 못 봅니다.**

⚠ **다법인 운영이 실제로 있는지가 관건입니다.** 법인 테이블이 있다고 해서 고객사가 여러 법인을 쓰는 것은 아닙니다.

| 안 | 뜻 |
| :-: | --- |
| **가** | **법인 축을 둔다** — 사용자 범위에 법인을 추가한다 |
| **나** | **두지 않는다** — 단일 법인 운영이라 필요 없다 |

## 4. 결정되면 어디에 영향을 주는가

### 4-1. 화면

| 결정 | 영향 |
| --- | --- |
| **2-A 안 가** | 웹-계정-로그인 1장 + **비밀번호 변경 1장이 새로 생긴다**(인벤토리 113 → 114) |
| **2-A 안 나** | 웹-계정-로그인 1장. **비밀번호 변경 화면은 만들지 않는다**(사내 체계가 한다) |
| **2-B 표준** | 위 + **최초·만료 시 강제 변경 흐름**이 로그인 화면의 별도 상태로 붙는다 |
| **2-C 가** | 웹-권한매트릭스(`W-CO-02`)에 **법인 선택 축이 하나 는다** |

⚠ **이미 쓴 화면 하나가 걸립니다** — **웹-사용자권한-매트릭스**(`W-CO-02`)가 「비밀번호 초기화」 액션을 이미 갖고 있습니다. **안 나를 택하면 그 액션을 뺍니다.**

### 4-2. 데이터 모델

| 결정 | 무엇이 필요해지나 |
| --- | --- |
| **2-A 안 가** | 사용자 계정에 비밀번호 저장 칸 · 실패 횟수 · 마지막 로그인 시각 · 변경 시각 |
| **2-A 안 나** | **추가 없음** — 사내 계정 식별자만 있으면 되고 `login_id` 가 그 역할을 한다 |
| **2-B 표준** | 위 + **직전 비밀번호 이력** |
| **2-C 가** | 사용자 데이터 범위에 법인 축 |

### 4-3. 세 프로그램의 인증 구조

**결정과 무관하게 이 구조는 유지됩니다.**

| 프로그램 | 인증 | 귀속 |
| --- | --- | --- |
| POP · 모바일 | 단말 토큰 | 사번 |
| 관리웹 | **이 결정** | 계정 자신 |

⚠ **사번을 인증으로 승격시키지 않습니다** — 공유 계약 F-2 가 못박은 것입니다. 사번에 비밀번호를 붙이면 「현장에서 로그인을 생략한다」는 요구를 우회로 되살리는 것입니다.

## 5. 권고안

### 5-A. **안 가 — MES가 직접 아이디·비밀번호를 갖는다**

**이유 셋입니다.**

1. **안 나가 성립하는지 확인되지 않았습니다.** 고객사에 사내 계정 서버가 있는지가 어느 문서에도 없습니다. **없으면 안 나는 아예 불가능**하고, 그때 다시 결정하면 **로그인 화면과 계정 관련 설계를 되돌립니다.**
2. **온프레미스·인터넷 비보장 환경에 안전한 쪽입니다.** MES 서버 안에서 완결되므로 외부 의존이 0입니다.
3. **나중에 안 나로 옮길 수 있습니다.** 반대는 어렵습니다 — 사내 체계에 위임했다가 되돌리려면 **모든 사용자의 비밀번호를 새로 만들어야** 합니다.

⚠ **다만 이것은 「사내 계정 체계가 없다」는 판단이 아닙니다.** 있으면 나중에 추가 연동으로 붙일 수 있게 **아이디를 사내 계정과 같은 값으로 쓰도록** 설계하겠습니다.

### 5-B. **최소 — 저장·잠금·관리자 초기화까지만**

**이유 둘입니다.**

1. **만료 주기는 현장 운영과 부딪칩니다.** 사무직이라도 MES 를 매일 쓰지 않는 사용자가 있고, 만료되면 **업무 시점에 막힙니다.** 그때 관리자를 찾아야 합니다.
2. **1차 범위를 좁히는 것이 이 프로젝트의 일관된 방침**이었습니다 — 결재선은 사람만, 값 구간 미사용, 대리 결재 없음. 같은 기준을 적용합니다.

⚠ **보안을 낮추자는 것이 아닙니다.** 실패 잠금과 복원 불가 저장은 **최소에 포함**됩니다. 뺀 것은 **만료 주기·복잡도 규칙·재사용 금지** 셋입니다.

### 5-C. **두지 않는다 — 법인 축 없음**

**이유 둘입니다.**

1. **다법인 운영이 확인되지 않았습니다.** 법인 테이블이 있는 것은 조직 계층을 그렸기 때문이고, **고객사가 실제로 여러 법인을 운영한다는 근거가 없습니다.**
2. **필요해지면 그때 추가하는 것이 싸다.** 사용자 범위에 축을 하나 더하는 일이고, 이미 있는 사업부·공장 범위를 버리지 않습니다.

⚠ **다만 화면은 물러나 표시합니다** — 권한 매트릭스 화면에 **「범위는 사업부·공장 단위로 준다」**를 명시해, 운영자가 법인 단위를 기대하지 않게 합니다.

## 6. ⚠ 이 결정으로 풀리지 않는 것

**하나 남습니다.** 정직하게 적습니다.

| 무엇 | 왜 남나 |
| --- | --- |
| **기능 권한 값 목록** — 「이 사람에게 어느 기능을 열 것인가」의 값 | 공유 계약이 **회신 E-9 대기**로 두었습니다. 인증(누구인가)과 인가(무엇을 할 수 있는가)는 다른 축이라 **이 결정이 그것까지 풀지 않습니다** |

**웹-계정-로그인 화면은 이 결정만으로 쓸 수 있습니다.** 권한 값 목록은 **웹-사용자권한-매트릭스** 화면의 문제이고 그 화면은 이미 쓰여 있습니다(값 목록이 빈 채로 물러나 있습니다).
