# 공통코드 그룹을 「이름」으로 가리킨다 — 구현팀 질의 omf-mes#179

> 작성일: 2026-08-21 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 계약 패치: `deliverables/openapi/patch-179-code-group-by-name.py` · 조항 신설: 공유계약 **`G-32`**
> 병합 요청: **`omf-mes#181`** · 데이터 모델 통지: **`omf-mes#182`**
> 앞선 작업: `uiux/2026-08-21-검사자-서버파생/`(#173) · `uiux/2026-08-21-귀속헤더/`(#178) — 같은 화면(`W-01-01`)에서 이어진 셋째 건

## 무엇

**화면이 공통코드 그룹을 「이름」으로 부를 수 있게 했고, 검사 판정 두 그룹을 확정했다.**

| 대상 | 바뀐 것 |
| --- | --- |
| `GET /mdm/code-values` | **`codeGroupCode`(문자열) 질의 신설** · `codeGroupId` **필수 → 선택** · **400 선언**(둘 중 정확히 하나) |
| `overallJudgmentCode` **4곳** | 그룹 코드·값 명시 · ⛔ **틀린 예시값 `"IQC"`(수입검사) 3곳 정정** |
| `judgmentCode` **2곳** | 그룹 코드·값 명시 — **종합 판정과 다른 그룹** |
| 공유계약 | **`G-32` 신설** — 조항 152 → **153** · 판 v3.1 → **v3.2** · `G-2` 에 단서 |
| 화면 스펙 **3장** | `W-01-01`·`W-04-03`·`P-02-13` — 낡은 「회신 대기·미확정」 표기 정정 + 받는 법 명시 |
| 요구서 **3장** | §5 미착지 14 절반 해소 · §3 매핑 · 변경 이력 |

⛔ **건드리지 않은 것** — 경로 · 새 스키마 · 쓰기 본문. `enum` 도 넣지 않았다(G-2·G-6 대로 늘 수 있게 둔다).

## 어떻게

### 무엇이 막혔나 — **값은 있는데 부를 수가 없었다**

계약이 종합 판정 값을 공통코드로 넘겨 두었는데(값 목록을 못박지 않는다 — G-2·G-6), **화면이 그 그룹을 가리킬 방법이 없었다.**

```
GET /mdm/code-values?codeGroupId={정수}   ← 정수이고 «필수»
GET /mdm/code-groups?q=...                ← 검색뿐. 정확히 집을 수 없다
```

`codeGroupId` 는 **채번된 값**이라 화면이 알 수 없고, 하드코딩하면 **개발·검증·운영이 서로 다른 정수를 갖는다.**

⭐ **값 셋은 이미 확정돼 있었다** — `합격`·`불합격`·`보류`(2026-08-07 회신 E-3 종결). **값이 정해진 것과 그 값을 부를 수 있는 것은 다른 문제**이고, 그 사이에서 구현이 멈췄다.

⚠ **실패 방식이 나쁘다** — 오류가 나지 않고 **목록만 빈다.** 화면은 「값이 아직 없나 보다」로 보이고, 선택칸이 비면 **확정 자체를 못 하는 화면**이 된다.

### ⭐ 구현팀이 잘한 것 — **이름을 지어내지 않았다**

`INSPECTION_JUDGMENT` 같은 이름을 만들어 넣지 않고 물어왔다. **지어냈으면 화면이 늘 빈 목록을 받고 확정이 영영 비활성**인데, 오류가 없어 원인을 찾기 어려웠을 것이다.

### 뿌리 — **이미 적어 둔 미착지였다**

`deliverables/06-API-요구서.md` §5 **미착지 14**(공통코드 그룹·값 목록 미정)가 같은 것을 적어 두었다. **#179 는 그것이 실제로 구현을 막은 첫 사례**다.

⭐ **그 항목이 두 겹이라는 것이 이번에 드러났다.**

| | 상태 |
| --- | --- |
| **① 「어떻게」 가리키나** — 정수를 화면이 모른다 | ✅ **해소** — 전 그룹에 적용된다 |
| **② 「어느」 그룹인가** — 이름이 안 정해졌다 | ⬜ **그룹마다 남는다** — 이번에 둘 확정 |

남은 것 — 창고유형·관리수준·Location유형·품질구역·보관조건·상태코드.

### 실측 — 판정 필드는 **둘**이었다

```
기준: 계약 7벌에서 이름에 「judgment」가 든 속성을 전수로 뽑았다.
```

| 필드 | 어디 | 곳 |
| --- | --- | :-: |
| `overallJudgmentCode` | 검사 **결과** — `InspectionResult`·`Create`·`Update`·`Confirm` | 4 |
| `judgmentCode` | 검사 **측정치** — `InspectionMeasurement`·`Input` | 2 |
| `judgmentMethodCode` | 설비 점검 항목(기준정보) — **다른 것**(판정 «방법») | 4 |

⚠ **#179 는 종합 판정만 물었지만 측정치 판정도 같은 자리에서 막힌다.** 그쪽은 설명조차 없는 맨몸(`{"type":"string","example":"값"}`)이었다.

## 왜

### ⭐ A안을 택했다 — 값 조회가 **이름을 받는다**

| 안 | 판정 |
| :-: | --- |
| **A** | ✅ **택함** — `code-values` 가 `codeGroupCode` 를 받는다. **한 걸음** |
| B | ⛔ `code-groups` 에 정확 일치 질의를 더한다 → **두 걸음**이 된다. 코드값 쓰는 화면이 계속 느는데 **걸음이 하나 늘면 실패 지점도 하나 는다**. 그 조회가 실패하면 각 화면의 **주 기능**이 막힌다 |
| C | ⛔ 검색(`q`)으로 고른다 → **여러 건 중 어느 것인지 화면이 판정**하게 된다. 부분 일치로 엉뚱한 그룹을 집을 수 있다 |

구현팀 권고와 같고, **그 근거가 우리 실측과 맞았다.**

⚠ **`codeGroupId` 를 없애지는 않았다** — 관리 화면(`W-06-06`)은 그룹을 목록에서 골라 이미 정수를 손에 쥐고 있다. 선택으로 내려 **둘 다 살렸다.**

⚠ **응용 프로그램 인터페이스 규약으로는 「둘 중 정확히 하나」를 표현할 수 없다.** 설명문에 규칙을 적고 **400 을 선언**했다 — 규칙이 계약에 **보이게** 한다.

### ⭐ 값과 이름을 **지어내지 않았다** — 물리 모델이 이미 부르고 있었다

```
ck_inspection_result_qty:  accepted_qty + rejected_qty + held_qty = inspected_qty
                           ↓            ↓              ↓
                           ACCEPTED     REJECTED       HELD
```

⭐ **이 합계 제약이 「왜 정확히 셋인가」의 구조적 근거이기도 하다.** 값 이름을 따로 지으면 같은 개념에 **어휘가 두 벌** 생긴다.

**그룹 이름 규칙** — 기존 선례(`INSPECTION_REQUEST_STATUS` ← `inspection_request.status_code` · #170)에서 뽑았다.

> 컬럼 이름에서 `_code` 를 뺀 것을 대문자로. 그것만으로 「무엇의 값인지」 모르면 테이블 이름을 앞에 붙인다.

| 컬럼 | 그룹 |
| --- | --- |
| `warehouse_type_code` | `WAREHOUSE_TYPE`(자기 완결) |
| `inspection_request.status_code` | `INSPECTION_REQUEST_STATUS`(`STATUS` 만으로는 모호 — **기존 선례와 일치**) |
| `inspection_result.overall_judgment_code` | `INSPECTION_RESULT_OVERALL_JUDGMENT` |

⚠ **길다고 줄이지 않았다.** 판정 컬럼이 둘이라 `INSPECTION_JUDGMENT` 로는 **어느 쪽인지 모르고**, 화면이 엉뚱한 그룹을 불러 **틀린 선택지를 보인다.** 식별자는 길어도 값이 안 든다.

### ⛔ 자기 정정 — 「스펙에 값이 없다」가 틀렸다

측정치 판정을 처음에는 **미정으로 두고 별건으로 넘기려 했다.** 검사 결과 §4-C 에 필드표가 없어 「적혀 있지 않다」고 판단했다. **틀렸다** — `P-02-13` 이 §5·§6 에 적어 두었다.

```
「항목 판정(합격/불합격)」                                   §5-9
「정상/불량 단순 선택 + 자유 입력」                           §5(검사기준 없을 때)
「측정값이 규격 밖 → ⚠ 자동 불합격 «아님» — 사람이 판정」      §6
「검사 확정 = 합계 일치 AND «전 항목 판정» AND 종합 판정 선택」  §5-9
```

⇒ **항목 판정에는 「보류」가 없다.** 보류는 검사 **결과** 수준의 개념이고(`held_qty`), 항목은 규격에 드는지 아닌지 둘뿐이다.

⚠ **한 문서의 한 절만 보고 「없다」고 하지 않는다**(uiux-design §2-1). 같은 화면의 다른 절이 답을 갖고 있었다.

### ⛔ 그래서 그룹을 **둘로 갈랐다**

| 그룹 | 값 |
| --- | --- |
| `INSPECTION_RESULT_OVERALL_JUDGMENT` | `ACCEPTED`·`REJECTED`·`HELD` |
| `INSPECTION_MEASUREMENT_JUDGMENT` | `ACCEPTED`·`REJECTED` |

**합치면 항목 선택칸에 「보류」가 떠서 화면이 스펙과 어긋난 값을 받는다.** 「비슷하니 하나로」가 값 목록에서는 결함이 된다 — `B-28`(같은 이름 다른 형태)과 같은 원리라 `G-32` 에 함께 적었다.
