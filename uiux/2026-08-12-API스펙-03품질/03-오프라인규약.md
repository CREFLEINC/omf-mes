# 03 품질 — 3단계 오프라인 규약

> 작성일: 2026-08-12 · 선행: `02-URL동작규약.md`
> **오프라인 대상 화면 1 / 7** — `P-02-13` 뿐이다

## 1. 범위 — **한 화면만 걸린다**

| 화면 | 프로그램 | 오프라인 |
| --- | :-: | :-: |
| `W-03-01`·`02`·`03`·`05`·`09` · `W-01-01` | 관리웹 | ⛔ **해당 없음 — C-5** |
| **`P-02-13`** PQC 제품 검사 | **POP** | ✅ **대상** |

⚠ **02 는 20장 중 다수가 POP·모바일이라 오프라인이 본론이었다.** 03 은 **6/7 이 관리웹**이라 C-5 로 닫힌다.

⭐ **그래서 이 단계가 짧은 것이 정상이다** — 「없어야 정상인 것」(A-13 ④)이다.

## 2. 저장 측이 **이미 준비돼 있다**

실측 — `quality.inspection_result`:

```
idempotency_key   varchar(150) NOT NULL UNIQUE    (1856)   ← C-8 저장 측
version_no        integer NOT NULL DEFAULT 1               ← B-1
```

⭐ **02 가 찾은 것과 같은 형태다**(`material_consumption`·`production_result`). **헤더로 받아 그 자리에 저장한다.**

### 2-1. ⭐ `business_date` 문제가 **없다**

```
inventory_transaction   UNIQUE (idempotency_key, business_date)   ← 복합 · C-8 날짜 경계 처리 필요
inspection_result       UNIQUE (idempotency_key)                  ← ⭐ 전역
```

**전역 UNIQUE 라 날짜 경계를 계약이 다룰 일이 없다.** `P-02-13` §5-7 이 이미 짚었다.

### 2-2. ⚠ 측정치에는 잠금이 없다

`inspection_measurement` 에 **`version_no` 가 없다**(실측). 3계층 중 가장 깊은 층이 기록 전용이다.
→ **토큰은 `inspection_result` 로 대표한다.** 측정치는 결과 저장에 함께 실린다(1단계 §6).

## 3. ⛔⛔ 그런데 **큐가 두 오퍼레이션을 이어 부를 수 없다**

**2단계가 임시 저장과 확정을 두 오퍼레이션으로 갈랐다**(§8). **온라인에서는 성립하는데 오프라인에서 깨진다.**

```
온라인    POST /quality/inspection-results        → 201 { inspectionResultId: 4821 }
          POST …/4821:confirm                     → 200

오프라인  POST /quality/inspection-results        → 202 큐 접수  ⛔ id 가 없다
          POST …/{???}:confirm                    → ⛔ 부를 수 없다
```

⭐ **`:confirm` 은 서버가 만든 `{inspectionResultId}` 를 URL 에 요구하는데, 큐에 담긴 요청은 그 값을 아직 모른다.**

⚠ **이것은 03 에서 처음 나오는 형태다** — 02 의 오프라인 대상 12건은 **전부 단발 POST** 였고(투입·실적·세션), **앞선 요청의 응답을 URL 에 쓰는 것이 없었다.**

### 3-1. 어떻게 푸나 — 셋을 놓고 골랐다

| 안 | 판정 |
| :-: | --- |
| **가.** 클라이언트가 id 를 만든다 | ⛔ **저장소 관행에 어긋난다** — 전 테이블이 `GENERATED ALWAYS AS IDENTITY` 다 |
| **나.** 큐가 응답을 기다렸다 이어 부른다 | ⛔ **큐의 뜻이 없어진다** — 오프라인이면 응답이 없다 |
| ⭐ **다.** **임시 저장을 큐에 담지 않는다** | ✅ **채택** |

### 3-2. ⭐ 채택안 — **임시 저장은 단말에 남고, 확정만 큐에 담긴다**

```
오프라인 임시 저장   →  ⛔ 서버로 보내지 않는다. POP 로컬에만 둔다
오프라인 검사 확정   →  POST /quality/inspection-results   본문 statusCode = 확정
                        → 202 큐 접수 (C-7)
```

**근거**: **작성 중인 것을 서버가 알 필요가 없다.** 임시 저장은 「이 단말에서 하던 일을 잃지 않는다」이지 「남이 본다」가 아니다.

| 오퍼레이션 | 온라인 | 오프라인 |
| --- | :-: | :-: |
| `POST /quality/inspection-results` `statusCode=작성중` | ✅ | ⛔ **보내지 않는다** |
| `PUT …/{id}` | ✅ | ⛔ 동 |
| `POST /quality/inspection-results` `statusCode=확정` | ✅ | ⭐ **큐 대상** |
| `POST …/{id}:confirm` | ✅ | ⛔ **관리웹·온라인 전용** — 이미 저장된 작성중 건을 올린다 |

⭐ **`:confirm` 을 없애지 않는다** — `W-01-01`(관리웹)이 「임시 저장 → 나중에 확정」을 실제로 쓴다. **오프라인 경로만 한 번에 보낸다.**

### 3-3. ⚠ 그래서 확정 경로가 **둘이다** — 계약이 그것을 말한다

```
POST /quality/inspection-results        statusCode=확정   ⭐ 한 번에 (오프라인·POP 즉시 확정)
POST /quality/inspection-results/{id}:confirm             작성중인 것을 올린다 (관리웹)
```

⛔ **둘 다 A-3 을 강제한다** — `accepted + rejected + held = inspected` 가 아니면 **400**.
⛔ **둘 다 Lot Status 를 전이시킨다** — 부수 효과가 같아야 한다.
⭐ **멱등키가 둘을 잇는다** — 같은 키로 재전송하면 **어느 쪽으로 와도 한 건**이다.

→ **`x-internal-note` 에 「두 경로가 같은 결과를 낸다」를 적는다.** 4단계.

## 4. 계약 표현 — 앞 트랙 그대로

| 무엇 | 형태 |
| --- | --- |
| 멱등키 | **`IdempotencyKey`**(header · **required** · uuid) — 전 쓰기 |
| 잠금(관리웹) | **`IfMatchVersion`**(**required**) |
| 잠금(오프라인 경로) | ⭐ **`IfMatchVersionOptional`** — 큐는 토큰을 싣지 않는다(**C-9**) |
| 즉시 처리 | **201** |
| 큐 접수 | ⭐ **202** — 「아직 서버가 모른다」(**C-7**) |

### 4-1. `IfMatchVersionOptional` 을 **어디에 붙이나** — 한 곳뿐

| 오퍼레이션 | 잠금 |
| --- | :-: |
| ⭐ `POST /quality/inspection-results` | **`IfMatchVersionOptional`** — 오프라인 대상 |
| `PUT /quality/inspection-results/{id}` | `IfMatchVersion` (required) |
| `POST …/{id}:confirm` | `IfMatchVersion` (required) |
| `POST /quality/lot-holds` · `…:release` | `IfMatchVersion` (required) — **관리웹 전용** |

⚠ **`lot-holds` 는 오프라인이 아니다** — `W-03-02`·`W-03-03` 이 관리웹이고, **결정 10 「판정 참조는 캐시하지 않는다」**(C-6)와도 정합이다.

### 4-2. ⭐ `lot_hold` 의 토큰은 `lot.version_no` 다

`lot_hold` 에 `version_no` 가 없다(1단계 §3-3). **B-8 로 `lot.status_code` 와 한 트랜잭션**이므로 **`lot` 의 토큰을 쓴다**.

⚠ **`W-03-03` 은 다중 LOT 이다** — **토큰이 여럿**이고 **하나라도 어긋나면 전체 거부**한다(§6 예외). → 본문에 `lots: [{lotId, version}]` 형태로 받는다. **헤더 `If-Match` 로는 표현할 수 없다.**

⭐ **헤더 잠금이 성립하지 않는 첫 오퍼레이션이다.** `IfMatchVersion` 을 붙이지 않고 **본문에 토큰을 싣는다** — `x-internal-note` 에 사유를 적는다.

## 5. `P-02-13` 이 오프라인에서 **못 하는 것**

⛔ **드러내고 우회하지 않는다.**

| 무엇 | 왜 |
| --- | --- |
| **Lot Status 즉시 반영** | 확정이 큐에 있으면 LOT 상태가 아직 안 바뀐다 → **C-7 미확정 표식** |
| **`can_input_inspection` 최신 판정** | `mdm.terminal_process` 는 **06 계약**이고 선배포분으로 판정한다 |
| **검사 기준 최신 버전** | `inspection_plan_version` 은 **06 계약** · 선배포분 — ⚠ **검사 시점 버전이 고정**되므로(W-01-01 §4-A) **문제가 되지 않는다** |

⭐ **세 번째는 「없어야 정상」이다** — 기준 버전이 검사 시점에 고정되는 설계라 오프라인이 오히려 자연스럽다.

## 6. 남긴 것 — 4단계로

| # | 무엇 |
| :-: | --- |
| 1 | `ConflictResponse.code` 에 **2값 추가** — `DUPLICATE_HOLD` · `HOLD_QTY_EXCEEDED`(1단계 §3-2) |
| 2 | 확정 경로 둘의 **부수 효과 동일성**을 `x-internal-note` 로 |
| 3 | 다중 LOT **본문 토큰** 형태 |
| 4 | `reinspection_reason_code` 값 목록 — 공통코드(운영 중 추가 가능) |
