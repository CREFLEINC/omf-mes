# 공통코드 값 목록 — **1차 제안안**

> 작성일: 2026-08-13 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 근거: **DR-011 확정 3-A**(E-3 방식으로 우리가 제안안을 만든다) · 이슈 **`omf-mes#145`**
> 결정 주체: **팀 리더**

---

## 0. 요약 — 네 줄

1. **1차 9종으로 잡았던 것이 실측하니 셋으로 갈렸다** — 진짜 제안 대상은 **6종**이고, **2종은 값이 이미 있었으며**(계약이 「없다」고 잘못 적었다), **1종은 별도 결정이 필요하다**.
2. ⛔ **계약이 「확정된 값 목록이 아직 없다」고 적은 곳이 62곳인데, 최소 2계열은 값이 있었다.** 열어 보지 않고 적었다.
3. ⛔⛔ **`reasonCode` 는 코드 하나가 아니라 자리 15개다.** 23회 쓰이는데 입고 사유 ≠ 출고 사유 ≠ WO 중단 사유다. **「코드 이름」 단위로 정하면 틀린다.**
4. ⭐ **폐기 출고의 도착지는 값과 컬럼을 함께 손대야 했다** — 폐기 업체가 있으면 `DISPOSAL_SITE` 로 적고, **자체 폐기면 비운다**(컬럼 nullable). 역할 구분은 **이미 있는 `mdm.partner_role`** 을 쓴다 — 컬럼 신설 0(§6 · DR-013).

## 1. 무엇을 제안하는가

계약 6종에서 **값 목록이 없는 업무 코드가 44종**이다. 그중 **`W-01-06` 하나가 곧바로 막고 있는 9종**을 1차로 잡았다.

> **⚠ 수치의 정본은 `deliverables/openapi/count-undecided-codes.py` 다.** 초판이 「79종 → 51종」이라 적었는데 **기준을 안 남겨 재현되지 않았다.** 되짚을 수 없는 수치는 결정 근거가 못 되므로 스크립트로 못박고 아래 수치를 그 출력으로 바꿨다.

```
*Code 프로퍼티 이름              112
  enum 없음                      105
    ├ x-source-column 없음        32   대상 아님 (쿼리 파라미터·파생 — 저장되지 않는다)
    └ 실제 컬럼에 착지            73
        ├ 인스턴스 식별           22   대상 아님 (itemCode·warehouseCode — 마스터 데이터다)
        ├ 표준값                   4   대상 아님 (countryCode·timezoneCode·uomCode …)
        ├ 상태값                   3   상태 기계와 함께 정한다
        └ ⭐ 업무 코드             44   ← 정해야 할 것
```

**E-3 선례를 따른다** — 고객 회신을 기다리지 않고 우리가 안을 만들어 팀 리더 확정을 받는다. E-3 는 그 방식으로 **화면 19장을 한 번에 풀었다.**

## 2. ⛔ 실측 — 「값이 없다」가 사실이 아니었다

계약 6종에서 **「확정된 값 목록이 아직 없다 — 서버가 내려주는 선택지를 그대로 쓴다(G-2)」** 문구를 전수로 셌다.

```
그 문구가 붙은 필드        62곳
그중 값이 실재한 것        ⛔ 최소 6곳 (2계열)
```

| 코드 | 어디에 값이 있었나 |
| --- | --- |
| **`inventoryStatusCode`** | ⭐ **물리 모델 시드에 4값** — `AVAILABLE`·`IN_TRANSIT`·`ON_HOLD`·`BLOCKED` (공통코드 그룹 `INVENTORY_STATUS` · **[E-7] 근거**) |
| **`qualityStatusCode`** | ⭐ **회신 E-3 으로 4값 확정** — 정상 · 불량 · 검사 대기 · 폐기 |

⚠ **E-3 는 2026-08-07 에 확정됐고 01 계약도 같은 날 작성됐다.** 확정이 나온 날 쓴 계약이 그 확정을 안 실었다.

⭐ **이미 고쳤다** — `patch-01-status-code-values.py`(멱등). `inventoryStatusCode` 는 enum 으로 못박았고, `qualityStatusCode` 는 **값 집합은 확정이나 코드 문자열이 미정**이라 서술만 고쳤다.

### 2-0. ⛔ 더 나쁜 것이 있었다 — **아무 말도 안 한 곳 넷**

1차 패치가 컬럼 이름을 **정확히 두 개**로만 매칭해 **전이 컬럼 넷을 빠뜨렸다**(리뷰에서 잡혔다).

```
InventoryTransactionLine.fromInventoryStatusCode   from_inventory_status_code
                        .toInventoryStatusCode     to_inventory_status_code
                        .fromQualityStatusCode     from_quality_status_code
                        .toQualityStatusCode       to_quality_status_code
```

⛔ **넷은 description 이 아예 없었다.** 「값이 없다」고 **잘못 적힌 것보다 나쁘다** — 잘못 적힌 것은 의심이라도 받는다.

⚠ **E-3 근거가 정확히 이 넷을 가리키고 있었다** — 「`from_quality_status_code` → `to_quality_status_code` = **품질 상태 전이 = 재고 이동 트랜잭션**」. **인용해 놓고 대상에서 뺐다.**

⭐ **접미사 매칭으로 고쳤다**(`*inventory_status_code`·`*quality_status_code`) — 이제 **10곳**을 덮고 `from_`/`to_` 에 「전이 전/후」를 붙인다.

### 2-1. ⚠ 이 발견이 뜻하는 것

**나머지 56곳도 같은 의심을 받아야 한다.** 04 트랙이 정정 3회를 「**남의 것을 열어 보지 않고 옮겨 적었다**」로 정리했는데, **같은 형태가 계약 자신 안에도 있었다.**

⛔ 다만 **전수 재검은 1차 범위 밖**이다 — 44종을 3차에 나눠 볼 때 각 차수의 **첫 단계로 「값이 이미 있는가」를 먼저 본다.**

### 3-1. ⛔ `warehouseTypeCode` 를 1차에서 뺀 이유

`W-06-07` §4-A 가 이미 이렇게 적고 있다.

> 창고유형 — 공통코드 **자재·제품·반제품·상품·생산 5종** «§8-3»

그런데 같은 문서 §8-3 이 「**그 5종이 공통코드 값과 1:1인지 미확인**」이라 했고, **더 큰 문제가 있다.**

```
스펙 전체의 「불량창고」 출현        92회
그 5종 안에 「불량」                ⛔ 없다
```

⛔ **`W-01-06` 이 「창고 [불량창고▾]」로 조회하는데 유형 값에 불량이 없다.** 「불량창고」가 **유형**인지 **창고 인스턴스 이름**인지 **Location 의 품질구역(`quality_zone_code`)**인지가 갈리지 않았다 — 셋 다 후보다. **값이 아니라 축을 정하는 문제라 요청서로 뗀다.**

⭐ **외부창고는 유형이 아니다** — `is_external` 불리언 + 거래처 조건부 필수(`ck_external_warehouse_partner`)로 이미 갈려 있다. 값 후보에서 뺀다.

## 5. 제안 — **6종**

> **표기 규약** — 코드 문자열은 시드 선례(`AVAILABLE`·`IN_TRANSIT`)를 따라 **영문 대문자 SNAKE** 로 쓴다. 화면에 보이는 것은 `code_name`(한국어)이고 코드는 안 보인다.
> **⚠ `[추정]` 표시** — 근거가 화면 스펙에 직접 없고 업무 상식으로 세운 것. 확정 때 특히 봐 주십시오.

### 5-1. `receiptTypeCode` — 입고 유형

| 코드 | 이름 | 근거 |
| --- | --- | --- |
| `MATERIAL` | 자재입고 | 01 입하 → 입고 주경로. 원천 = 구매발주 |
| `PRODUCT` | 제품입고 | ⭐ `M-04-04` 「**제품입고 고정**」 · 원천 = 생산 |
| `RETURN` | 반품입고 | ⭐ `W-04-06` 「**반품 입고 고정**」 — 고객 반품·클레임 |
| `TRANSFER` | 창고간이동 입고 | **[추정]** — `IN_TRANSIT` 시드가 창고 간 이동 구간을 전제한다([E-7]) |

⛔ **외주입고는 넣지 않는다** — 「외주 구분」이 **물리 모델에 아직 없다**(#64 미착지 8건 중 하나). **구조가 선 뒤에 값을 얹는다.**

### 5-2. `sourceDocumentTypeCode` — 원천 문서 유형

⚠ **이것은 다형 참조(A-10)의 판별자다** — 값이 틀리면 `source_document_id` 가 엉뚱한 테이블을 가리킨다. **가장 조심해야 할 하나.**

| 코드 | 이름 | 가리키는 것 |
| --- | --- | --- |
| `PURCHASE_ORDER` | 구매발주 | 입하·자재입고의 원천 |
| `WORK_ORDER` | 작업지시 | 생산 투입 출고의 원천 |
| `MATERIAL_ISSUE_REQUEST` | 자재출고요청 | `W-02-10` 추가 자재 요청 |
| `PRODUCTION` | 생산 | 제품입고의 원천 |
| `SHIPMENT_ORDER` | 출하지시 | 04 출하 작업지시 |
| `INVENTORY_ADJUSTMENT` | 재고조정 | ⭐ A-10 — 「재고조정 값이 있어야 잇는다」로 스펙이 명시 |
| `MAINTENANCE_ORDER` | 보전지시 | ⏳ **05 설비툴 트랙 미착수** — 값만 미리 세운다 |
| `NONE` | 없음 | ⛔ **`W-04-06` §5-3 「출하 또는 **없음**」인데 컬럼이 `NOT NULL`** 이라 값이 필요하다 |

⛔ **`NONE` 은 냄새가 난다** — 「없음」을 값으로 두는 것은 `NOT NULL` 을 우회하는 것이다. **대안은 컬럼을 nullable 로 바꾸는 것**이고 그건 물리 모델 변경이라 #64 계열이다. **팀 리더 판단이 필요하다.**

### 5-3. `issueTypeCode` — 출고 유형

| 코드 | 이름 | 근거 |
| --- | --- | --- |
| `PRODUCTION` | 생산투입 | 「생산 투입용」 |
| `SUPPLIER_RETURN` | 공급사반품 | ⭐ `W-01-05` — QA #15 「전용 트랜잭션 불요」로 확정 |
| `SCRAP` | 폐기 | ⭐ `W-01-06`·`W-04-10` |
| `OTHER` | 기타출고 | ✅REQ-PR-0028 「기타 출고로 처리」 |
| `SHIPMENT` | 출하 | **[추정]** — 제품 출하가 `shipment` 축이라 별개일 수 있다 ⚠ §5-3-1 |

#### 5-3-1. ⚠ 갈림 — 폐기는 **유형**인가 **기타출고의 사유**인가

`W-01-06` 스펙이 「**기타출고(폐기) 고정**」이라 적었다. 두 가지로 읽힌다.

| 읽기 | 뜻 |
| :-: | --- |
| (a) | `issueTypeCode = OTHER` · `reasonCode = 폐기` — **유형은 기타출고 하나** |
| ⭐ (b) | `issueTypeCode = SCRAP` — **폐기가 독립 유형** |

⭐ **(b)를 권고한다.** 설계 메모가 「별도 폐기 헤더를 만들기보다 **출고 유형을 확장**」이라 했고, 폐기는 **승인 게이트가 붙는 유일한 출고**라 유형으로 갈라야 화면·권한이 깔끔하다.

### 5-4. `destinationTypeCode` — 도착지 유형 ⚠ **부분**

⚠ **A-10 다형이고 `destination_id` 와 짝이며 둘 다 `NOT NULL`** 이다.

| 코드 | 이름 | 가리키는 것 | 근거 |
| --- | --- | --- | --- |
| `LOCATION` | 위치 | `mdm.location` | 창고 내 이동·적치 |
| `PARTNER` | 거래처 | `mdm.partner` | ⭐ `W-01-05` §5-3 「**값 집합에 「공급사」가 있어야** 한다」 |
| `PROCESS` | 공정·라인 | 라인 | 생산 투입 |
| `WORK_ORDER` | 작업지시 | `WO` | **[추정]** — 스펙이 「위치? 라인? W/O?」로 셋을 병렬로 물었다 |
| ⭐ `DISPOSAL_SITE` | 폐기 거래처 | `mdm.partner` | ✅ **확정**(DR-013) — 역할은 `partner_role` 로 가른다 · §6 |

✅ **폐기 도착지가 채워졌다** — 값을 더하고 **동시에 컬럼을 nullable 로** 바꾼다(자체 폐기) → §6.

### 5-5. `managementLevelCode` — 창고 관리 수준

⭐ **이것은 근거가 가장 단단하다** — 논리 모델링 §262 가 「**창고 · 구역 · 랙 · 셀 관리수준**」이라 명시했고, `W-06-07` §5-3 이 「관리수준이 위치 입력을 가른다」로 화면 규칙까지 걸어 뒀다.

| 코드 | 이름 | 위치 입력 |
| --- | --- | --- |
| `WAREHOUSE` | 창고 | 위치를 안 받는다 |
| `ZONE` | 구역 | 구역까지 |
| `RACK` | 랙 | 랙까지 |
| `CELL` | 셀 | 셀까지 |

⚠ **순서가 의미를 갖는다**(계층 깊이). `display_order` 를 10·20·30·40 으로 두어 **깊이 비교가 되게** 한다.

### 5-6. `reasonCode` — **입고 자리 하나만**

물리 모델 주석이 「반품입고 등 사유」다. **정상 입고는 사유가 없다**(nullable).

| 코드 | 이름 |
| --- | --- |
| `CUSTOMER_RETURN` | 고객 반품 |
| `CLAIM` | 클레임 |
| `SUPPLIER_REPLACEMENT` | 공급사 대체 입고 ⭐ `goods_issue.replacement_expected` 와 짝 |
| `REWORK_RETURN` | 재작업 후 재입고 |

⚠ **이 넷은 근거가 약하다** — 화면이 사유를 **자유 선택**으로만 그렸고 목록을 적은 곳이 없다. **현업 확인 우선순위 1번.**

## 6. ✅ **폐기 출고의 도착지** — 확정 (2026-08-13 · DR-013)

```sql
logistics.goods_issue
    destination_type_code  app.code_t NOT NULL   ← 비울 수 없었다
    destination_id         bigint     NOT NULL
```

**폐기는 어디로 가는가?** 같은 질문이 **두 경로로** 올라왔다 — 프론트 구현 질문(DR-009 §5)과 이 제안안 §5-4.

### ✅ 확정 — **거래처를 기록하되 비울 수 있게 한다**

```
폐기 업체가 있으면   destination_type_code = DISPOSAL_SITE
                    destination_id        → mdm.partner
자체 폐기면          둘 다 NULL           ← 「자체 폐기」 체크박스
```

| 무엇 | 결과 |
| --- | --- |
| ⭐ **값 추가** | `DISPOSAL_SITE`(폐기 거래처) — A-10 대응표: → `mdm.partner` |
| ⭐ **컬럼 완화** | `destination_type_code`·`destination_id` **NULL 허용** + **짝 제약**(둘 다 NULL 이거나 둘 다 NOT NULL) |
| **역할 구분** | ⭐ **`mdm.partner_role`** 에 `role_type_code=폐기처리` — **컬럼 신설 0**(테이블이 이미 있다) |
| **등록 주체** | 거래처 본체는 **ERP 수신** · 역할은 **MES**(`W-06-06` 탭 추가) |
| **화면** | 「자체 폐기」 체크박스 + 폐기 거래처 선택 — `W-01-06`·`W-04-10` |
| ⛔ **하지 않는 것** | **ERP 회계 계정** — DR-009 유지 |
| **소관** | 모델 컬럼 완화 = **`#147`**(통지) · `roleTypeCode` 값 목록 = **`#145`** |
| ⭐ **01 계약** | ✅ **이미 완화했다** — 모델을 기다리지 않는다. **모델이 계약을 따라온다**(2026-08-10 확정 작업 방식) |

⭐ **「무엇을 몇 개 폐기했나」에 「누가 가져갔나」가 더해지고, 회계는 여전히 ERP 다.**

### ⚠ 이 절이 세 판을 거쳤다 — 양쪽으로 틀렸다

| 판 | 무엇 | 왜 틀렸나 |
| :-: | --- | --- |
| 초판 | `DISPOSAL_SITE` **권고** | ⛔ **요구·화면·등록처를 안 셌다** — 「테이블이 있으니 값을 만든다」 |
| 2판 | **철회**(nullable 만) | ⛔ **자기지적이 과했다** — DR-009 확정문의 주어는 **회계 계정**인데 「어긋난다」로 단정했다 |
| ✅ 확정 | **둘 다** | 업체가 있으면 적고, 자체 폐기면 비운다 |

⛔⛔ **처음엔 과하게 넣으려 했고 고칠 때는 과하게 빼려 했다 — 둘 다 실측 전에 판단했다.**

⭐ **결정적이었던 실측은 「사용처」였다** — 폐기 업체가 요구·워크플로우에 **0건**, 폐기 출고 화면의 도착지 입력이 **0건**, 거래처 등록 화면이 **0건**. **확정 대조가 아니라 사용처 확인이 이 건을 갈랐다.**

### ⛔ 택하지 않은 것

| 안 | 왜 |
| :-: | --- |
| `mdm.partner` 에 `partner_type_code` 신설 | ⛔ **`partner_role` 과 축이 겹친다** — 한 거래처가 여러 역할을 갖는 구조가 이미 있다 |
| MES 에 거래처 마스터 화면 신설 | ⛔ 거래처는 **ERP 수신 마스터**다. 본체를 MES 가 만들면 두 곳에서 생긴다 |
| 폐기 전용 Location(`LOCATION`) | ⛔ **재고가 그 위치에 영원히 쌓인다** — 나간 물건인데 위치를 갖는다 |
| `DISPOSAL` + 자기 창고 | ⛔ **거짓을 적는다** — 나간 물건의 도착지가 출발 창고다 |
| nullable 만 두고 거래처는 안 적는다 | ⚠ 자체 폐기는 풀리지만 **「누가 가져갔나」를 못 남긴다** — 폐기물 수거 추적이 안 된다 |

## 7. 값이 착지하는 곳 — **시드 데이터이지 스키마가 아니다**

```
mdm.code_group   (group_code, group_name, description)
mdm.code_value   (code_group_id, code, code_name, display_order,
                  effective_from, effective_to, is_active)
```

⭐ **등록부가 이미 있다.** 값을 정하는 것은 **시드 행을 넣는 일**이지 컬럼을 만드는 일이 아니다 — **`#64`(물리 모델)와 `#145`(값)를 가른 근거가 이것이다.**

**지금 시드된 그룹은 둘뿐이다.**

| 그룹 | 값 | 근거 |
| --- | :-: | --- |
| `OPERATION_POLICY` | 14 | ERPNext manufacturing_settings 벤치마킹 + 자체 요구 |
| `INVENTORY_STATUS` | 4 | [E-7] |

### 7-1. ⚠ 함께 보고할 것 — **등록부로 들어오는 FK 가 0건이다**

```
app.code_t 컬럼            200개
그중 code_value 참조 FK    ⛔ 0개
```

⚠ **이것을 결함이라 단정하지 않는다** — 코드 컬럼 200개에 FK 를 다 거는 것은 흔히 피하는 설계이고, 선택지는 `W-06-06`(공통코드 마스터)이 내려 주고 **강제는 애플리케이션 층**에서 하면 된다.

⛔ **다만 명시돼 있지 않다.** 「값 목록을 정해도 DB 는 아무 문자열이나 받는다」가 설계 의도인지 누락인지 적힌 곳이 없다. **DB 강제를 원하면 별도 결정**이고 그건 **`#64` 계열**이다.

## 8. 확정되면 무엇이 풀리는가

| 무엇 | 얼마나 |
| --- | --- |
| ⭐ **`W-01-06` 의 자리표시** | **9 → 2** (남는 것 = `warehouseTypeCode`·폐기 도착지) |
| 프론트 `code-options.ts` | ⭐ **한 파일만 고치면 반영된다**(전환 감지기 보유 · client #34) |
| 계약 서술 | ⭐ **26곳** — 이미 반영한 상태 2계열 **10**(전이 4 포함) + 1차 제안 5종이 덮는 **16** |
| 착수 통지 | ⛔ **늘지 않는다** — 값은 통지 차단 사유가 아니었다(G-2 가 덮는다) |

> **세는 기준** — 「프로퍼티 출현 횟수」다(스키마마다 따로 센다). 이름 단위가 아니다.
> ⚠ 초판은 「62곳 중 최소 20곳」이라 적었는데 **실측 근거가 없었다.** 위 수치는 계약 6종을 다시 세어 낸 것이고, 「없다」 문구가 남은 곳은 **56**이다.

## 9-1. ⛔⛔ 권고가 **양쪽으로** 흔들렸다 — 관문을 하나 더 둔다

`DISPOSAL_SITE` 를 두고 **두 번 틀렸다.** 방향이 반대였다.

| 판 | 무엇 | 왜 틀렸나 |
| :-: | --- | --- |
| 초판 | **값 추가 권고** | ⛔ **요구·화면·등록처를 안 셌다** — 「테이블이 있으니 값을 만든다」 |
| 2판 | **전면 철회** | ⛔ **자기지적이 과했다** — DR-009 확정문의 주어는 **회계 계정**인데 「어긋난다」로 단정했다 |
| ✅ 확정 | **값 + nullable 둘 다** | 업체가 있으면 적고, 자체 폐기면 비운다(DR-013) |

⛔⛔ **처음엔 과하게 넣으려 했고, 고칠 때는 과하게 빼려 했다.** 두 번 다 **실측 전에 판단**했다.

### 뒤집힌 권고 넷

| 차수 | 권고 | 사용자가 옳았던 이유 |
| :-: | --- | --- |
| 1 | Zalo | 용도가 하나가 아니었다 |
| 2 | 평면 배치 | 고객 약속이 아니었다 |
| 3 | 재생재 | 고객 약속이었다 |
| **4** | **`DISPOSAL_SITE`** | ⛔ **사용처를 안 세고 값을 만들려 했다** |

⛔ **기존 관문 둘로는 안 잡힌다.** 넷째는 「용도가 하나인가」 ✅ · 「고객 약속인가」 ⚠ 를 **통과했다.**

### ⭐ 세 번째 관문 — **「누가 이 값을 넣나」**

**값·필드·경로를 만들자고 하기 전에 사용처를 센다.**

```
① 이 값을 넣는 화면이 있나          폐기 업체 → 화면 0건
② 요구·워크플로우가 부르나          폐기 업체 → 문서 0건
③ 담을 마스터·등록 화면이 있나       거래처 등록 화면 0건 (ERP 수신 마스터)
```

⚠ **「이미 확정한 것과 어긋나나」로 두지 않는다** — 이번 건은 확정 대조로는 **애매하게 통과했을 것**이다(DR-009 는 회계 계정 얘기였고 거래처 기록은 계정이 아니다). **사용처 확인이 갈랐다.**

⭐ **셋 다 grep 으로 센다** — 「없다/있다」를 검색 없이 적지 않는다는 **A-13** 의 값 판이다. 검사기가 절의 유무까지는 볼 수 있으나 **사용처 판단은 사람이 본다.**

## 9. 이 제안의 약점

| # | 무엇 |
| :-: | --- |
| 1 | ⛔ **`reasonCode`(입고) 4값은 근거가 약하다** — 화면이 목록을 적은 곳이 없다. **현업 확인 1순위** |
| 2 | ⚠ **`[추정]` 4건** — `TRANSFER` 입고 · `SHIPMENT` 출고 · `WORK_ORDER` 도착지 · 폐기가 독립 유형인가(§5-3-1) |
| 3 | ⛔ **`NONE`(원천 없음)은 `NOT NULL` 우회다** — 값으로 풀 문제가 아닐 수 있다 |
| 4 | ⚠ **1차가 44종 중 6종이다** — 나머지 38종 + `reasonCode` 14자리가 남는다 |
| 5 | ⚠ **62곳 전수 재검을 안 했다** — 2계열에서 값이 나왔으니 더 있을 수 있다. 2·3차 첫 단계로 돌린다 |
