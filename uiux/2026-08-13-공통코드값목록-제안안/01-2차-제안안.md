## §0. 이 문서의 성격

⭐ **E-3 선례를 따른다** — 팀 리더·고객 확정을 기다리지 않고 설계팀이 먼저 값을 제안한다. 근거: 이 28건은 전부 「값에 화면·서버 동작이 걸리지 않는다」(G-31 기준)로 이미 실측 검증됐다 — 목록 조회 API의 필터 파라미터로 쓰이지 않고, 화면 폼 구성·계산식·승인 분기를 바꾸지 않는다.

⛔ **이것은 회신 대기가 아니라 작업 통지다.** 계약은 이미 enum을 두지 않고 열어 뒀고, 화면은 이 값이 없어도 정상 동작한다(공유계약 G-2 — 비활성 + 사유). **아래 값은 시작값일 뿐이다** — B-4-3에 따라 고객이 운영 중 `W-06-06` 공통코드 마스터 화면에서 언제든 추가·삭제·변경한다.

| 무엇 | 값 |
| --- | :-: |
| 코드 그룹 — **마스터안전형**(§2) | **28개**(1차 29개 → 병합 확정 1건으로 28개) |
| 코드값 | **128개** |
| 그중 화면 스펙에 이미 있던 값(그대로 옮김) | **69개** |
| 그중 업무 상식으로 새로 제안한 값 | **57개** |
| 그중 ⭐ **CTO 확정 기록(`QA #25`)의 한글을 코드로 옮긴 값** | **2개** *(2026-08-23 추가)* |
| 코드 그룹 — **시스템 소유**(§2-B, 2026-08-23 추가) | **1개** · 값 **5개** |
| 그중 코드 문자열이 그대로 있던 값 | **1개** |

⚠ **아래 세 줄(CTO 확정 기록 2 · 시스템 소유 1+4)은 아래 수치 기준으로 세지 않았다** — 출처 문서 종류가 달라(현장검증 확정기록 · 계약 설계 문서 · 화면 스펙 §5-4) §2의 69/57 집계에 섞지 않고 따로 센다. 근거는 각 그룹의 「값 출처」 줄과 §2-B 의 출처 표.

⛔ **`QA #25` 2개가 왜 뒤늦게 붙었나** — v1.2까지 화면 목업만 보고 세었기 때문이다. **미확정 코드 계수기는 계약(`enum` 부재)을 보고, 값 제안은 화면 스펙을 보는데, 「CTO 확정 기록에 값이 적혀 있는 경우」를 두 경로 다 안 본다.** 같은 방식으로 놓친 값이 더 있을 수 있다.

⚠ **수치 기준** — 「스펙에 이미 있음」은 화면 상세 스펙의 §3 레이아웃 목업·§4 필드표·§8 미결에 코드값이 문자 그대로 나열돼 있던 것만 센다. 재현: 각 그룹 절의 「근거」 줄에 적힌 화면·문단을 대조하면 된다.

## §1. ✅ 병합 후보 8곳 — 물리 모델·화면 스펙 대조로 전건 확정(2026-08-23)

**「확인 없이 합치지 않는다」 원칙대로, 실제로 물리 모델(`mes_postgresql_physical_model.sql`)의 CREATE TABLE 원문과 계약·화면 스펙을 대조해 판정했다.** 추측 없음 — 8곳 전부 근거를 확보했다.

| # | 후보 | 판정 | 근거 |
| :-: | --- | :-: | --- |
| 1 | ⭐⭐ `WORK_ORDER_HOLD_REASON` ↔ `WORK_SESSION_EVENT_REASON` | **병합 확정** | `work_session_event.reason_code` **하나뿐인 컬럼**에 두 진입점(POP 홀드·세션 이벤트)이 함께 쓴다(물리 모델 실측). 화면 스펙(`P-02-10` §9)이 스스로 「화면마다 다르게 쓰면 집계가 어긋난다」고 이미 적어 뒀다 — 값도 완전히 동일했다. `WORK_SESSION_EVENT_REASON`(물리 컬럼 기준 명명)으로 통일, `WORK_ORDER_HOLD_REASON`은 폐기 |
| 2 | `WORK_SESSION_EVENT_REASON` ↔ `CONTROL_OVERRIDE_REASON` | 별도 유지 | `ControlOverride`도 같은 컬럼에 쓰지만(계약 실측), `event_type_code`가 이미 「중단·재개·통제 우회」를 별개 값으로 구분해 값 집합 자체가 다르다(우회=단일 사유). ✅ **후속 과제 종결(2026-08-23)** — `event_type_code`(판별자 — 한 칸에 어느 값 목록을 쓸지 가르는 코드)가 어느 사유 그룹을 적용할지 정하는 대응표를 **공유계약 `A-25` 신설**로 실었다. 판별자 값 목록 `WORK_SESSION_EVENT_TYPE` **5값**(`START`·`STOP`·`RESUME`·`END`·`CONTROL_OVERRIDE`)도 함께 확정 — `STOP`→이 그룹(필수) · `CONTROL_OVERRIDE`→`CONTROL_OVERRIDE_REASON`(필수) · `RESUME`·`END`→비움 |
| 3 | `INBOUND_VARIANCE_REASON` ↔ `VARIANCE_REASON` | 별도 유지 | 물리 모델 실측 — 네 테이블(`inbound_variance`·`shopfloor_receipt_line`·`inventory_count_line`·`inventory_adjustment`) 전부 다른 컬럼이고 FK 사슬도 없다. 「파손」류 어휘 겹침은 두 목록 다 물류 사고를 다루는 자연스러운 결과일 뿐 |
| 4 | `INVENTORY_ADJUSTMENT_REASON`(「운반 파손」) ↔ `VARIANCE_REASON`(「운반 중 파손」) | 별도 유지 | 마찬가지로 물리 컬럼·FK 사슬이 다르다. 문구 중복은 그룹 병합이 아니라 라벨 통일 정도로 충분(값 자체는 안 건드림) |
| 5 | `PICKING_TYPE` ↔ `RESERVATION_TYPE` | 별도 유지 | `picking_order.picking_type_code` ↔ `inventory_reservation.reservation_type_code` — 물리적으로 다른 테이블. 유일한 연결(`picking_line.inventory_reservation_id`)은 개별 예약 건 참조용이지 값 목록 공유가 아니다 |
| 6 | `LOT_HOLD_REASON` ↔ 불량코드 대분류(`quality.defect_code`, 결정 12) | 별도 유지 | `lot_hold.reason_code`는 FK가 아닌 맨몸 문자열이라 `defect_code`(2계층 전용 마스터, 자기참조 FK 구조)를 참조하지 않는다. **직접 선례 발견** — `W-06-03` §(결정 12)가 「손실 사유는 별도 코드 그룹 — 불량코드 체계에 섞지 않음(3원 집계와 정합)」을 이미 확정해 뒀다 |
| 7 | `INSPECTION_ITEM_SPEC_METHOD` ↔ `EQUIPMENT_INSPECTION_JUDGMENT_METHOD`(확정 `#185`·`#186`) | 별도 유지 | 물리적으로 다른 테이블(`quality.inspection_item_spec` vs 설비 쪽 신설 예정 `EquipmentInspectionItem`). 계약 자신이 「모양이 닮았으나 다른 자원 — 소유·대상·쓰임이 다르다」로 이미 구분해 뒀고, 설비 점검·품질 검사를 값 집합이 다르면 가르는 전례(`EQUIPMENT_INSPECTION_TYPE`↔`QUALITY_INSPECTION_TYPE`)가 있다 |
| 8 | `PROCESS_TYPE`의 「외주」 값 ↔ `routing_operation.is_outsourced` | **값 제거 확정** | `is_outsourced`는 물리 모델에 아직 없지만 `W-06-01` §4-B-1에서 **이미 사용자 확정**(2026-08-03)된 라인별 실행 플래그다 — 「이 공정 종류가 외주냐」(마스터 속성)와 「이번 라우팅에서 외주로 돌리느냐」(라인별 플래그)는 다른 축인데, `PROCESS_TYPE.OUTSOURCING`을 남기면 구현팀이 어느 필드를 써야 할지 헷갈리는 함정이 된다 — **`OUTSOURCING` 값을 뺐다** |

**요약** — 8곳 중 실제 병합은 **1건**(#1), 값 제거는 **1건**(#8), 나머지 **6건은 별도 유지가 근거로 확정**됐다. 병합·근거불충분 상태로 남은 것은 없다.

- 근거: M-01-06-입하오류등록.md §3(레이아웃) · §4-A(reason_code)
- 값 출처: M-01-06 §3 목업은 사유 드롭다운 자리를 비워 두고 "⚠ 값 목록 미확정"으로만 표시해 화면 스펙에는 구체값이 없다. OpenAPI InboundVariance/InboundVarianceCreate.reasonCode의 example 「DAMAGED」만 유일한 기존 단서라 채택하고, 나머지는 입하 검수 업무상식(라벨·포장·오배송 계열)으로 보완했다.

| `MISLABELED` | 라벨 오류 | 20 | 제안 |
| `SUPPLIER_MISSHIP` | 공급사 오배송 | 30 | 제안 |

**3. `INVENTORY_ADJUSTMENT_REASON` — 재고조정 사유**

**4. `PUTAWAY_TASK_TEMPORARY_REASON` — 임시 위치 적재 사유**

- 무엇: logistics.putaway_task 관련 임시 적치 사유. M-01-07 작성 시점(2026-08-05)에는 물리 컬럼이 없어 remarks 자유텍스트로 물러났으나(§5-1, §I 신규 후보), 이후 OpenAPI PutawayTaskCompleteTemporary.reasonCode(nullable — 사유 코드와 비고 중 적어도 하나는 필요)로 반영되어 §8 #1 취지가 사실상 해소된 상태다.
- 근거: M-01-07-임시위치적재.md §3(레이아웃) · §5-1 · §5-5
- 값 출처: M-01-07 §3 레이아웃 목업의 적치 사유 라디오 그룹에 「정위치 포화」·「검사 대기」·「위치 미지정」·「기타」 네 값이 이미 그려져 있다("⚠ 값 목록 미확정"이라 확정 표시는 아니지만 후보 자체는 목업에 실재). OpenAPI PutawayTaskCompleteTemporary.reasonCode의 example 「NO_SPACE」는 이 중 「정위치 포화」에 대응한다.

## §2-B. 부록 — **시스템 소유** 그룹 1건 `WORK_SESSION_EVENT_TYPE` (2026-08-23 추가)

⚠ **이 그룹은 §2의 28건과 성격이 다르다.** §2는 「고객이 값을 더하고 지워도 화면이 그대로 도는」 마스터안전형이지만, 이 그룹은 **값에 화면·서버 동작이 걸려 있어** 고객 편집 대상이 아니다(가르는 기준 = 공유계약 `G-31`). 그런데도 여기 함께 적는 이유는 **같은 두 표(`mdm.code_group`·`mdm.code_value`)에 들어가야 하고, 같은 전달 경로를 타기 때문**이다.

**29. `WORK_SESSION_EVENT_TYPE` — 작업세션 사건 유형** ⛔ **시스템 소유 · 고객 편집 불가**

- 무엇: `production.work_session_event.event_type_code` — 작업세션에 무슨 사건이 일어났는가. **이 값이 형제 칸(`reason_code`)에 어느 사유 목록을 적용할지까지 가른다** — 대응표는 공유계약 `A-25`가 갖는다.
- 근거: 작업 중단 등록 화면(`P-02-10`) §5-4 · 02 생산실행 `03-오프라인규약.md` §7 · 물리 모델 884~893
- 값 출처: 앞 셋은 `P-02-10` §5-4 표가 한글로 이미 열거해 둔 것을 코드 문자열로 옮겼고(`stop_reason_code`·`:end` 등 **이미 쓰이는 어휘에 맞춤**), `CONTROL_OVERRIDE`는 **02 생산실행 계약 설계 3단계가 이미 적어 둔 문자열을 그대로** 가져왔다 — 넷 다 지어내지 않았다

| 코드 | 뜻 | 순서 | 출처 |
| --- | --- | :-: | :-: |
| `START` | 시작 | 10 | **한글→코드** |
| `STOP` | 중단 | 20 | **한글→코드** |
| `RESUME` | 재개 | 30 | **한글→코드** |
| `END` | 종료 | 40 | **한글→코드** |
| `CONTROL_OVERRIDE` | 통제 우회 | 50 | **코드 실재** |

⭐ **`START` 는 2026-08-23 추가다** — 처음엔 넷이었는데 **논리 모델 §9.7 이 `work_session_event` 를 「작업 **시작**·중지·재개·종료 이력」으로 정의**했고 `P-02-10` §3 목업도 「`08:00 세션 시작`」을 그리는데, `END` 만 값으로 넣고 `START` 를 빠뜨려 **비대칭**이었다. ⚠ `work_session.started_at` 이 있어 시작 시각은 그 칸으로도 그릴 수 있지만, 그러면 이력 화면이 **두 표를 합쳐** 그려야 한다.

⚠ **출처 표기가 §2와 다르다 — 이 그룹은 §0의 계수 기준으로 셀 수 없다.** §0 기준은 「**화면 상세 스펙의 §3·§4·§8**에 **코드값이 문자 그대로** 나열돼 있던 것」인데, 이 넷은 어느 쪽도 그 조건을 그대로 만족하지 않는다.

| 표기 | 뜻 | 이 그룹의 사정 |
| --- | --- | --- |
| **코드 실재** | 우리 산출물에 **코드 문자열 그대로** 있었다 | `CONTROL_OVERRIDE` 1개 — 다만 출처가 화면 상세 스펙이 아니라 **계약 설계 문서**(`03-오프라인규약.md` §7)다 |
| **한글→코드** | 뜻은 확정돼 있었고 **식별자를 이번에 지었다** | `STOP`·`RESUME`·`END` 3개 — `P-02-10` **§5-4**(§3·§4·§8 아님)에 「중단·재개·종료」라는 **한글**로 있었다 |

⭐ **이 구분은 공유계약 `G-32`가 이미 조항으로 세워 뒀다** — 「**뜻이 확정된 뒤에도 「코드 문자열」은 따로 정해야 한다 … 뜻과 식별자는 다른 산출물이다**」(v3.4, 구현팀 결함 신고 `omf-mes#175`·`#176`). 식별자를 새로 지은 것은 **성과이지 감출 일이 아니다** — 지어낸 방식(이미 쓰이는 어휘 `stop_reason_code`·액션 `:end`에 맞춤)을 위 「값 출처」 줄에 적어 뒀다.

⛔ **고객이 여섯째 값을 넣으면 화면이 무엇을 해야 할지 아무도 모른다** — 유형에 따라 세션 상태가 갈리고, 사유를 묻는지가 갈리며, 묻는다면 어느 목록을 띄울지가 갈린다. 마스터 화면(`W-06-06` 공통코드 탭)에서 **이 그룹만은 읽기 전용으로 두거나, 최소한 값 추가를 막아야 한다** — 처리 방법은 데이터 모델·구현 소관으로 넘긴다.

## §3. 반영 방법

SQL은 별도 전달(`[uiux→데이터모델]` 이슈) — `mdm.code_group` + `mdm.code_value` INSERT. 형식은 기존 시드 선례(`omf-mes#182`)와 동일하다. `omf-mes#198`(1차 전달, 29그룹)에 이번 §1 판정 결과를 정정 코멘트로 남겼다.

⭐ **§2-B의 시스템 소유 그룹도 같은 이슈에 이어 붙인다** — 다만 **「고객 편집 불가」임을 값과 함께 전달**한다. 값만 보내고 성격을 안 보내면 마스터 화면에 그대로 열려 버린다.
