## §5. 액션·상태

### §5-1. ⭐ 이 화면이 **사후 경로 전부**를 받는다

`W-04-12`(출하 확정·취소)가 **「확정 후 취소는 원칙적으로 불가」**로 닫혔다(2026-08-07 사용자 확정). 그래서 **확정된 출하에 문제가 생기면 갈 곳이 여기 하나**다.

```
출하 처리(미확정)  →  [ 취소 가능 ]  →  확정  →  ⛔ 취소 불가
                                                   ↓
                                            W-04-06 반품 입고
```

**FR-IM-079 가 이미 그렇게 적었다** — 「실제 고객에게 반출된 경우 출하취소가 아니라 **고객 반품 절차**를 사용해야 한다」. **2단 확정이 그 경계를 「반출 여부」에서 「확정 여부」로 옮겼을 뿐**이고, 반품 절차가 받는다는 것은 그대로다.

### §5-2. ⛔ 「원천 구분」을 담을 컬럼이 **없다**

QA #15 가 **「클레임 = 불량창고 반품입고로 통일 + 원천 구분 속성」**을 확정했다. **속성이 데이터에 없다.**

| 원천 | 뜻 |
| --- | --- |
| **내부** | 우리가 발견 — 출하 후 자체 점검에서 |
| **외부 클레임** | 고객이 제기 |

| 후보 | 실측 |
| --- | :-: |
| `goods_receipt.reason_code` | ⚠ 있으나 **반품 사유**(품질 불량·수량 오류)이지 **원천**이 아니다 |
| 전용 컬럼 | ⛔ **없다** |

**A-11 로 물러난다** — **`reason_code` 값 목록에 원천을 접어 넣는다**(「외부 클레임-품질 불량」 형태). 두 축을 한 코드로 합치면 **조합이 곱해져 값이 늘지만**, 컬럼이 없는 것보다는 **집계가 된다.**

⚠ **`remarks` 자유 텍스트로 두면 집계가 안 된다** — 「클레임이 몇 건인가」를 셀 수 없다. → §8-1.

### §5-3. 원 출하를 **못 찾는 경우가 정상이다**

```
goods_receipt.source_document_type_code + source_document_id   NOT NULL
goods_receipt_line.original_shipment_lot_allocation_id          nullable
```

⭐ **헤더는 원천이 필수인데 라인의 원 출하 배분은 선택이다.** 즉 **「반품인 것은 확실한데 어느 출하인지 모르는」 경우**를 데이터가 받는다.

| 상황 | 처리 |
| --- | --- |
| 원 출하를 찾았다 | `original_shipment_lot_allocation_id` 를 채운다 — **genealogy 가 이어진다** |
| **못 찾았다** | 비운다. 헤더 원천은 **반품 요청 문서**나 **클레임 접수**를 가리킨다 |

⚠ **고객이 오래된 물건을 보내면 못 찾는다** — LOT 라벨이 훼손됐거나 여러 출하가 섞였을 때다. **막지 않는다.**

### §5-4. ⭐ 원 LOT 을 그대로 쓴다 — 새 LOT 을 만들지 않는다

`W-04-11`(재고 재등록) §5-1 이 세운 것과 **같은 판단**이다.

```
⛔ 새 LOT 발번        →  「이 물건이 한 번 나갔다 돌아왔다」는 사실이 끊긴다
✅ 원 LOT + 상태 전이  →  genealogy 가 이어진다
```

**`trace.lot_relation` 을 쓰지 않는다** — 같은 LOT 이라 관계가 아니다. 관계가 생기는 것은 **선별로 갈릴 때**다(`W-04-07` §5-4).

### §5-5. 반품은 **Hold 로 들어온다** — 판정 전이다

QA #15 가 「**불량창고 우선 입고 → 재작업/폐기 판정 → 재고 재등록 → 출하 재진입**」으로 확정했다.

```
quality_status_code = Hold 고정
```

**결정 10**(Lot Status = 차단의 단일 지점)이 여기서도 작동한다 — **판정 전에는 출하·피킹이 막힌다.**

⚠ **`M-04-04`(제품 입고)와 반대다** — 거기는 「들어오는 것은 막지 않는다」였는데, **여기는 들어올 때부터 막힌 상태**다. 갈림은 **「의심할 이유가 있는가」**다.

### §5-6. J-7 로 결과를 보인다

```
✅ 불량창고 재고가 120 EA 늘어납니다
✅ Lot Status 는 Hold 로 들어옵니다 — 출하·피킹이 막힙니다
ⓘ 재작업/폐기 판정은 W-04-07 에서 합니다
```

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **되돌리기를 막은 화면은 사후 경로가 어디인지를 가리켜야 한다** — `W-04-12` 가 「확정 후 취소 불가」로 닫히면서 **그 뒤의 모든 사고가 이 화면으로 온다.** 확정 화면이 「반품 절차로 진행하세요」를 안내하고, 반품 화면이 **원 출하를 찾아 잇는 경로**를 갖는 것이 짝이다. B-14 의 **뒷면** (§5-1)
2. **확정된 업무 축을 담을 컬럼이 없으면 기존 코드에 접어 넣되 「접었다」를 적는다** — 원천 구분(내부/외부)을 `reason_code` 에 합치면 **값이 곱해지지만 집계는 된다.** `remarks` 자유 텍스트로 두면 **「클레임이 몇 건인가」를 셀 수 없다.** A-11 의 선택지 판 — **물러날 때도 집계 가능성을 우선한다** (§5-2)
3. **「의심할 이유가 있는가」가 입고 차단의 기준이다** — `M-04-04`(제품 입고)는 「들어오는 것은 막지 않는다」였는데 **반품은 들어올 때부터 Hold** 다. 같은 입고인데 갈리는 근거가 **의심 여부**이고, 결정 10 의 차단 지점을 어디에 둘지가 그것으로 정해진다 (§5-5)
