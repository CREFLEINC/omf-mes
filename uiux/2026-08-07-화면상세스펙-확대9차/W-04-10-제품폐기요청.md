# W-04-10 · 제품 폐기 요청

> 작성일: 2026-08-07 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **확대 9차 4/6** — ⭐ **`W-01-06`(자재 폐기 품의)의 대칭**이고, **골격을 그대로 쓴다.** 다른 것은 대상이 제품이라는 것과 **처분 결정에서 온다**는 것뿐이다.
> ⚠ **신뢰도 미정** — 04-S-C **SC6 폐기 stub**(도식 범위 외) · **회신 E-4**(폐기 계정) 대기.

> ⛔⛔ **2026-08-13 확정 — MES 는 품의서를 기안하지 않는다**(DR-009).
>
> 「MES 에서는 품의서를 기안하지 않는 것이 원칙이다. 외부에서 승인 받는 품의서는 MES 에 가져오지 않으며,
> MES 에서 실제 품의서 승인을 득했는지 관심갖지 않는다. **사용자에게 맡긴다.**
> 그럼 MES 에서는 **작업자가 요청하고 승인하는 방식**으로 정리한다.」
>
> **이 화면에 미치는 것** — 「품의 발의」 → **「폐기 요청」** · 「품의 상신」 → **「승인 요청」** ·
> ⛔ **폐기 계정 필드 삭제**(MES 밖 · **회신 E-4 종결**) · 외부 품의서 번호·첨부·승인 확인 게이트 **두지 않는다**.
> ⭐ **2026-08-13 DR-013** — 회계 계정은 안 적되 **「누가 가져갔나」는 적는다.** 《③》에 **자체 폐기 체크 + 폐기 거래처 선택**이 붙는다(§5-6).
> ⭐ **골격은 그대로다** — 요청 → 승인 → 기타출고 3단과 「승인 완료 후에만 출고」 잠금은
> **MES 내부 승인 기준**으로 그대로 선다. 아래 본문의 「품의」는 이 기준으로 읽는다.

## §5. 액션·상태

### §5-1. ⭐ 승인 계약이 완성돼 있다 — **`W-01-06` 이 겪은 미결이 없다**

`W-01-06`(2026-08-05)은 **§J 2차 검증 화면**이었고 **⛔ J-2·J-3 이 미결**이었다. 그 둘이 **2026-08-07 에 닫혔다.**

| | `W-01-06` 작성 시점 | **지금** |
| --- | --- | --- |
| J-3 승인자 확정 | ⛔ 회신과 충돌 | ✅ **1차 결재선은 `USER` 만** |
| J-2 값 구간 | ⬜ 수량인가 금액인가 | ✅ **1차엔 쓰지 않는다**(값 성격 = 수량) |
| 결재선 정의 화면 | ⬜ 인벤토리에 없다 | ✅ **`W-06-15`** |
| 승인 실행 계약 | ⛔ 미착지 | ✅ **`app-공통.json`** — 경로 9 |

**이 화면은 완성된 계약 위에 선다.** `W-01-06` 의 §5 를 그대로 따르고 **미결만 다르다.**

### §5-2. 대상은 **처분 = 폐기** 로 판정된 것만이다

`W-04-07` → 03 판정 → `disposition_decision.disposition_type_code = 폐기`.

**REQ-PR-0025 가 「판정은 입고 후」**를 확정했으므로 **판정 없이 폐기 품의를 올릴 수 없다.**

```
⚠ 판정 없이 폐기할 수 없습니다 — W-04-07 에서 의뢰하세요
```

⭐ **`W-01-06`(자재)과 갈리는 지점이다** — 자재 폐기는 「불량창고 입고분」이면 되는데, **제품 폐기는 처분 결정이 선행**이다. **고객에게 나갔던 물건**이라 근거가 더 필요하다.

### §5-3. ⛔ 품의 참조 컬럼이 없다 — **`W-01-06` §8-1 과 같은 건**

```
logistics.goods_issue   reason_code ✅  replacement_expected ✅  remarks ✅
                        품의 참조 ⛔     폐기 계정 ⛔
```

설계 메모가 「**사유·품의 참조·계정 속성 통합**」을 말했는데 **사유만 착지**했다.

**A-10 다형 참조로 잇는다** — `approval_request.target_type_code` + `target_id` 가 **기타출고 전표**를 가리키면, 전표에서 품의를 찾을 때 **`GET /app/approval-requests?targetTypeCode=&targetId=`** 로 역조회한다(승인 계약 §3-2 가 그 경로를 갖는다).

⚠ **`W-01-06` 과 완전히 같은 문제이므로 이슈를 새로 내지 않는다** — **#87 에 이미 올라가 있다**(품의 참조·계정).

### §5-4. J-8 을 적용한다 — **승인은 자물쇠를 풀 뿐**

```
⚠ 승인 없이 출고할 수 없습니다
ⓘ 승인은 자물쇠를 풀 뿐입니다 — 출고는 여기서 다시 누릅니다
```

01 계약이 이미 그렇게 썼다 — `POST /logistics/goods-issues/{id}:post` 는 **승인 전이면 400**. **승인 ≠ 전기**다.

### §5-5. 사유는 **처분 사유를 인용**한다 — A-12

`disposition_decision.reason` 이 **NOT NULL** 이라 판정 시점에 이미 쓰였다. **품의 사유를 처음부터 쓰게 하지 않고 그것을 기본값으로 채운다.**

```
사유  [ 재작업 불가 — 변형 손상 (처분 사유 자동 인용) ]
```

⭐ **결재함(`W-CO-09`)에서 이 문장이 목록 요약을 겸한다** — `approval_request` 에 업무 값이 `reason` 하나뿐이기 때문이다(A-12 보강). **인용해 두면 승인자가 판정 근거를 바로 본다.**

⚠ **편집은 허용한다** — 판정 사유와 폐기 품의 사유가 다를 수 있다(예: 「재작업 불가」 판정 + 「보관 비용」 폐기 사유).

### §5-6. 액션

| 액션 | 활성 조건 |
| --- | --- |
| 대상 선택 | **처분 = 폐기** 인 것만(§5-2) |
| 사유 입력 | ✅ **필수** — 처분 사유가 기본값(§5-5) |
| 폐기 **계정** 선택 | ⛔ **두지 않는다** — 회계는 MES 밖(DR-009 · **E-4 종결**) |

| 품의 취소 | ⛔ **두지 않는다** — 상신 철회 경로가 승인 계약에 없다(01 요구서 §5-3) |

1. ⭐ **선행 화면이 필수 자유 텍스트를 이미 받았으면 뒤 화면이 그것을 인용해 채운다** — `disposition_decision.reason` 이 NOT NULL 이라 판정 시점에 이미 쓰였는데, 품의 사유를 **빈칸으로 다시 받으면** 사람이 대충 쓴다. **인용을 기본값으로 두고 편집을 허용**하면 결재함 목록의 정보량이 올라간다(A-12 보강 — 사유가 요약을 겸한다) (§5-5)
2. **같은 결손이 두 화면에 걸리면 이슈를 새로 내지 않는다** — 품의 참조·계정 컬럼 부재가 `W-01-06`·`W-04-10` 둘 다에 걸리는데 **#87 에 이미 있다.** 관문 ②(이미 판정이 있는가)의 적용례이고, **두 번째 사용처를 코멘트로 더하는 것**이 논의를 한 곳에 모은다 (§5-3)
3. **신뢰도 「미정」은 도식 보강으로 재판정될 수 있다** — `W-04-07` 이 #44 해소로 **추정 → 확정**이 됐다. `W-04-10` 의 SC6 stub 도 같은 형태다. **미정을 영구 미정으로 두지 말고 「무엇이 오면 재판정하는가」를 적어 둔다** (§8-4)
