# 화면 상세 스펙 차수 배치표 — 도메인 01·02

> 작성일: 2026-08-03 (v1.0) · 작성 주체: CREFLE OMF 팀
> **대상**: 도메인 01 자재창고관리(24) + 02 생산실행(24) = **48화면**
> **왜 재정렬하는가**: 확대 2차로 잡아 두었던 14화면을 사전 점검하니 **실질 착수 가능이 5화면**이었다. `W-CO-03`·`04`·`05`·`08`은 물리 모델에 테이블이 **0건**이라 쓸 근거가 없었다. 화면 번호 순으로 집으면 이 일이 반복된다.
> **정본 관계**: 화면 목록의 정본은 `screen-inventory-ia.md` v1.5다. 이 문서는 **순서**만 정한다.

## 0. 요약

**48화면 전건이 착수 가능하다.** 물리 모델 근거가 아예 없는 화면은 **0건**이다 — 기준정보 도메인과 다르다.

```
물리 모델 충실도    충분 42 · 부분 6 · 없음 0
차단 이슈           6화면 (#60·#61·#62·#64·#67·#68)
차수                4개 (2차~5차) · 차수당 10~14화면
```

도메인 01·02는 **테이블이 가장 두꺼운 영역**이다 — logistics 32 · production 14 · inventory 10 · planning 8 · trace 7 = **71테이블**(전체 129의 55%). 기준정보(mdm 24)보다 근거가 탄탄하다.

> **이 사실 자체가 「정본을 뒤집을 것인가」에 대한 1차 신호다.** 기준정보에서 모델 미반영이 16건 나왔는데, 01·02는 성긴 훑기에서 6건뿐이다. 상세 스펙을 쓰며 늘겠지만, **모델이 화면 현실과 크게 어긋난 상태로는 보이지 않는다.**

## 1. 세 축

### 축 1 — 물리 모델 충실도

「이 화면이 설 테이블이 있는가」를 **성기게** 본다. 필드 단위 대조는 상세 스펙에서 하므로 여기서는 핵심 엔티티의 유무만 본다.

| 등급 | 뜻 | 건수 |
| :-: | --- | :-: |
| **충분** | 핵심 엔티티가 전부 실재한다 | **42** |
| **부분** | 일부가 없다 — 쓸 수는 있으나 §8 미결이 붙는다 | **6** |
| **없음** | 핵심 엔티티가 없다 — 지금 쓸 수 없다 | **0** |

**2차 대조에서 9화면이 「부분」 → 「충분」으로 올라갔다.** 화면의 데이터 용어와 테이블 이름이 달라 1차 훑기에서 놓친 것이다.

| 화면 용어 | 실제 근거 | 걸린 화면 |
| --- | --- | --- |
| 인식표 · LOT라벨 · 출고QR | **`app.document_issue_log`** — `document_type_code`(LABEL 등) · `issue_seq`(1=최초, 2+=재발행) · `reissue_reason_code` | `P-01-02` `P-02-05` `P-02-07` `P-02-09` |
| 의심자재 | **`trace.lot_hold`** — `reason_code` · `release_condition` · `status_code` | `W-01-01` `W-01-07` |
| 자원배정(4M) | **`production.work_session`**(`equipment_id`·`mold_id`) + `work_session_worker` | `W-02-03` |
| 거래명세서 | **`app.attachment`** — 촬영본 자체. ⚠ OCR 파싱 **결과**의 매핑은 미결 | `M-01-01` |
| 비가동기록 | **`production.work_session_event`** — `event_type_code`·`reason_code`·`occurred_at` | `P-02-13` |

> **교훈**: 「테이블이 없다」고 판단하기 전에 **이름이 다른 곳에 있는지** 본다. 라벨 발행 이력이 `app` 스키마에 있을 줄은 화면 용어만 보고는 알 수 없다. 기준정보에서 `MatrixGrid`를 갭으로 잘못 본 것과 같은 실수다.

## 3. 「지을 수 있는 스펙」 판정 기준

개발팀이 **「이 화면은 지금 지어도 되는가」를 스스로 판단**하는 잣대다. 화면 상세 스펙 §8(미결)의 각 항목에 등급을 붙인다.

| 등급 | 뜻 | 개발팀은 |
| :-: | --- | --- |
| **차단** | 이것이 정해지지 않으면 **화면의 골격이 바뀐다** — 필드가 생기거나 없어지고, 흐름이 갈린다 | **짓지 않는다** |
| **조정** | 골격은 서지만 **동작·문구·기본값이 바뀔 수 있다** | **지어도 된다.** 해당 부분을 격리해 둔다 |
| **표시** | 화면에 어떻게 보일지만 남았다 | **지어도 된다** |

**스펙 §8에 「차단」이 0건이면 그 화면은 개발 가능**하다. 스펙 머리에 이 판정을 요약해 적는다.

### 등급 판정의 예

| 미결 | 등급 | 왜 |
| --- | :-: | --- |
| 검사자와 확정자를 분리할 것인가(#62) | **차단** | 분리하면 화면이 둘로 갈리고 권한 축이 생긴다 |
| 작업실적 수량 구분 3원 ↔ 5컬럼(#60) | **차단** | 입력란의 개수가 달라진다 |
| 「개발품」의 기준(#70) | **조정** | 송신 대상 판정 로직만 바뀐다 — 화면 골격은 같다 |
| 재발행 사유를 필수로 할 것인가 | **조정** | 필드는 있고 필수 여부만 남았다 |
| 비활성 사유를 항상 펼칠지 요구 시 볼지 | **표시** | G-1이 이미 권고를 담고 있다 |

> ⚠ **이 기준은 스펙을 쓰는 쪽이 정한다.** 개발팀이 「조정」을 「차단」으로 읽고 멈추거나 그 반대가 되면 안 되므로, **각 §8 항목에 등급과 한 줄 이유를 함께 적는다.**

## 4. 이 재정렬이 발견한 것

### 물리 모델에 없는 개념 5건 — 이슈 후보

성긴 훑기에서 드러난 것이라 상세 스펙 단계에서 더 나올 수 있다. **지금 이슈로 내지 않고 해당 차수 착수 시점에 확정해 발행한다** — 성기게 본 것을 근거로 이슈를 내면 정확하지 않다.

| # | 개념 | 화면 | 상태 |
