## 0. 요약 — 세 줄

1. **E-3는 「값 목록」 질문으로 물었지만 실은 「무엇의 값인가」 질문이다.** 그래서 고객사가 답할 수 없었다.
2. **물리 모델은 이미 답을 갖고 있다** — 품질 상태는 **재고 잔량의 차원**이고(`uq_inventory_balance_dim` 실측), 값은 **4개**면 충분하다.
3. **한도승인·특채·폐기는 상태 값이 아니라 전용 테이블이다.** 셋 다 물리 모델에 자기 테이블이 실재하고, 끝나면 4개 값 중 하나로 수렴한다. 도식이 이 셋에 **전이 화살표를 하나도 못 그린 것**(실측 `attachedConnectors`=0)이 그 신호였다.

## 1. E-3가 실제로 묻고 있는 것

### 1.1 질문 원문

> **E3** — 의심 자재 **판정 유형 목록**(한도승인·특채·폐기 등 — 현장에 요청함, 회신 대기)
> 회신 회수 → **판정유형 코드 · 후속 처리(출고 가능 여부) 매핑**
> — 질문지 v2 §E3

⭐ **질문이 둘이다.** 「목록」과 「출고 가능 여부」. 그동안 우리는 앞의 것만 대기로 잡고 있었다.

### 1.2 왜 한 달 넘게 안 풀렸나

고객사에 「판정 유형이 뭐가 있습니까」라고 물으면 답할 수 없다. **고객사에 기존 MES가 없기 때문이다**(QA §1). 답하려면 먼저 **「판정 유형이 무엇을 결정하는 것인가」**가 정해져야 하는데, 그것이 우리 설계 소관이다.

| 우리가 물은 것 | 고객사가 답할 수 있는 것 |
| --- | --- |
| ⛔ 「Lot Status 값을 뭐로 할까요」 | 답할 수 없다 — 시스템 개념이다 |
| ✅ 「불합격인 자재를 조건부로 쓰는 일이 있습니까」 | 답할 수 있다 — **업무 사실**이다 |

**제안안의 목적은 질문을 뒤 칸으로 바꾸는 것이다.**

## 2. 실측 — 상태 3축은 어디에 착지했나

결정 10이 확정한 「상태 3축 분리」의 하류 착지처를 전수 확인했다.

| 축 (결정 10) | 결정 10의 정의 | 물리 모델 착지처 | 상태 |
| --- | --- | --- | :-: |
| ① **수명주기** | 사전발행/활성/소진/종료 | `trace.lot.status_code` (DEFAULT `'ACTIVE'`) | ✅ 있다 |
| ② **품질 판정** | 보류/Release/한도승인/특채/폐기 | **`inventory.inventory_balance.quality_status_code`** (NOT NULL) | ⚠ **있는데 자리가 다르다** |
| ③ **작업 홀드** | C2 작업홀드이력 | `trace.lot_hold` (+ W/O 계열 별개) | ✅ 있다 |

### 2.1 ⭐ 품질 판정 축은 **재고의 차원**이었다

```
CREATE UNIQUE INDEX uq_inventory_balance_dim
ON inventory.inventory_balance (
    legal_entity_id, business_unit_id, plant_id,
    warehouse_id, location_id, item_id,
    COALESCE(lot_id, 0),
    quality_status_code,        ← 차원에 들어 있다
    inventory_status_code, …
```

**같은 LOT이 같은 위치에 있어도 품질 상태가 다르면 재고 행이 갈린다.** 즉 물리 모델은 「LOT 하나 = 상태 하나」가 **아니다**.

관련 컬럼이 전부 정합한다:

| 컬럼 | 뜻 |
| --- | --- |
| `inventory_balance.blocked_qty` | **「사용제한수량」**(논리 모델 3-2 §1328) — ⚠ **품질 축과 별개다**(§6.1) |
| `inventory_balance.available_qty` | `on_hand − reserved − picked − blocked` **GENERATED** — ⚠ 식에 **`quality_status_code` 가 없다** |
| `inventory_transaction_line.from_quality_status_code` → `to_quality_status_code` | **품질 상태 전이 = 재고 이동 트랜잭션** |
| `inventory_transaction_line.from_qty_after_transaction` | 전이 직후 잔량 **스냅샷** |
| `trace.lot_hold.hold_qty` | `NULL` = 전량 보류 → **부분 보류가 설계 전제다** |
| `quality.concession.approved_qty` · `consumed_qty` | 특채가 **수량 단위**다 |
| `quality.nonconformance_lot.quality_status_before_code` / `_after_code` | 부적합 등록 시 전후 상태 |

### 2.2 ⭐⭐ 「변경이력이 없다」고 적은 것이 있었다 — A-13 네 번째

`W-06-04` §확인필요 2번이 이렇게 적었다:

> 결정 10이 확정한 「Lot Status변경이력(1:N) 신설」이 물리 모델에 없다 — `trace` 스키마 7테이블 중 해당 없음 · `previous_status`·`from_status`·`to_status` 컬럼 **전 파일 0건**(실측)

**틀렸다.** `inventory_transaction_line.from_quality_status_code` / `to_quality_status_code` 가 있다. 게다가 잔량 스냅샷·트랜잭션 사유·행위자·일시까지 붙어 결정 10이 요구한 것보다 많다.

| 왜 못 찾았나 | 교훈 |
| --- | --- |
| 검색어가 `from_status` 였고 실제는 `from_quality_status_code` | **이름을 좁게 잡았다** |
| `trace` 스키마만 봤고 실제는 `inventory` 스키마 | **스키마를 좁게 잡았다** |

→ **A-13 강화**: 「없다」고 적기 전에 ① 한 층 아래 ② 다른 파일 ③ **다른 스키마** ④ **다른 이름**을 본다. 지금까지 네 번 다 「없다」 쪽으로 틀렸다.

## 3. ⛔ 상류↔하류 충돌 2건

물리 모델(2026-07-23)이 결정 08·10(2026-07-06)을 따르지 않았다. **17일 간격이고, 하류가 더 나중이다.**

### 3.1 충돌 ① — 재고가 품질 상태를 보유한다

| | |
| --- | --- |
| **결정 08** | 「**재고 행에 가용/Hold 상태 축을 두지 않는다.** 품질 판정은 Lot Status(C4)가 정본이고 출고·출하 시점에 참조로 판정한다. **재고가 상태를 복제 보유하면 이원 관리로 정합이 깨진다**」 |
| **물리 모델** | `inventory_balance.quality_status_code` **NOT NULL** + `blocked_qty` + `available_qty` GENERATED(blocked 차감) |

⚠ **다만 결정 08의 우려는 성립하지 않는다** — 결정 08이 걱정한 것은 **복제**(같은 사실이 두 곳)인데, `trace.lot` 에는 품질 판정 컬럼이 **없다**. 즉 **일원인데 위치가 다르다.** 결정 08의 원칙(「단일 지점」)은 지켜졌고 **위치 지정만 어긋났다**.

### 3.2 충돌 ② — 「LOT당 현재 1행」이 성립하지 않는다

| | |
| --- | --- |
| **결정 10** | 「품질 판정의 정본=Lot Status(C4), **LOT당 현재 1행**」 |
| **물리 모델** | `quality_status_code` 가 유니크 차원 → **LOT당 N행** |

⭐ **물리 모델 쪽이 맞다.** 결정 10 모델로는 표현할 수 없는 것이 넷이다:

| 표현 못 하는 것 | 근거 |
| --- | --- |
| **부분 보류** — 100개 중 30개만 Hold | `lot_hold.hold_qty` NULL=전량 → **부분이 기본 전제** |
| **부분 특채** — 100개 중 30개만 조건부 사용 | `concession.approved_qty` · `consumed_qty` 가 **수량** |
| **분산 LOT의 상태 분기** — 자재창고 분은 Release, 생산창고 분은 의심 발생으로 Hold | 결정 08 **자신의 전제** — 「동일 LOT이 자재창고·생산창고·호퍼에 분산 실재」(REQ-PR-0034, QA #5) |
| **전이 수량 이력** | `inventory_transaction_line` 이 수량과 함께 기록 |

⚠ **결정 08이 자기 전제로 「LOT 분산 실재」를 적어 두고, 결정 10에서 「LOT당 1행」을 확정했다.** 두 결정이 세트로 묶여 있는데 서로 어긋난다.

## 4. 제안 — 값은 **4개**다

### 4.1 값 목록

**Lot Status(= 재고 품질 상태) 값 = 4개.** 03 도식이 이미 확정한 것 그대로다.

| # | 코드(안) | 표시명 | 뜻 | 출고 가능 | 도식 노드 |
| :-: | --- | --- | --- | :-: | --- |
| 1 | `RELEASE` | Release | 쓸 수 있다 | ✅ | 585:6760 |
| 2 | `PENDING` | 보류 | 판정 대기 — 의심 자재 포함 | ❌ | 584:6759 |
| 3 | `HOLD` | Hold | 불합격 — 못 쓴다 | ❌ | 585:6763 |
| 4 | `PQC_REQUIRED` | PQC 검사 필요 | 합격판정개수 초과 → 전수 재검 대기 | ❌ | 632:6932 |

> 코드 문자열은 **제안**이다. `mdm.code_group` 명명 규약에 맞춰 조정될 수 있다.

### 4.2 ⭐ 한도승인·특채·폐기는 값이 아니다

**셋 다 물리 모델에 전용 테이블이 실재한다.** 상태 코드 한 칸으로는 담기지 않는 정보를 갖고 있다.

| 후보 | 전용 테이블 | 코드 한 칸으로 **담을 수 없는** 정보 |
| --- | --- | --- |
| **특채** | `quality.concession` | `approved_qty`·`consumed_qty`(소진 추적) · `valid_from`/`valid_to`(기간) · `allowed_work_order_id`·`allowed_process_id`·`allowed_customer_id`(**허용 범위 3축**) · `approval_request_id` |
| **폐기** | `quality.disposition_decision` | `disposition_type_code`·`decision_qty`·`reason`(NOT NULL)·`decided_by`/`decided_at`·`approval_request_id`<br>⭐⭐ **그리고 이 테이블에는 `lot_id` 가 아예 없다** — `nonconformance_id` **NOT NULL** 이다 |
| **한도승인** | `app.approval_request` (+ `W-01-02`) | 결재선·단계별 승인자·의견·시각 |

⭐⭐ **결정적 논거.** 결정 10은 이렇게 적었다:

> 「**한도승인·특채의 출하 허용 범위 규칙**(E3 목록 확정 후)도 여기 한 곳에만 걸면 된다」

그 **「출하 허용 범위」가 이미 `concession` 에 컬럼으로 있다** — `allowed_work_order_id` · `allowed_process_id` · `allowed_customer_id` · `approved_qty` · `valid_to`.

**특채를 상태 값으로 만들면 이 다섯 컬럼이 갈 곳을 잃는다.** 「W/O 3번 · 5공정 · 고객 A에만 · 100개까지 · 8월 말까지」를 `code_t` 문자열 하나로 쓸 수 없다.

### 4.2.1 ⭐⭐ 폐기는 **LOT 을 가리키지도 않는다**

```
CREATE TABLE quality.disposition_decision (
    nonconformance_id  bigint NOT NULL REFERENCES quality.nonconformance(...)
    ...                         ← lot_id 컬럼이 없다 (전문 실측)
```

**폐기 판정의 대상은 LOT 이 아니라 부적합 건이다.** LOT 과의 연결은 `nonconformance` → `nonconformance_lot`(`quality_status_before_code`/`_after_code` 보유)을 **경유**한다.

⭐ **상태 값이 될 수 없는 가장 분명한 근거다** — 「LOT 의 상태」라면 LOT 을 가리켜야 하는데 **가리키는 컬럼 자체가 없다.** `W-04-10`(제품폐기품의)도 이 경로를 그대로 쓴다(「`W-04-07` → 03 판정 → `disposition_decision.disposition_type_code = 폐기`」 §5).

### 4.3 ⭐ 도식이 이미 신호를 보냈다

03 도식 §1.1 실측:

| 상태 | 배선 |
| --- | --- |
| 보류 · Release · Hold · PQC 검사 필요 | 수신·발신 커넥터 **16개** |
| **한도승인 · 특채 · 폐기** | **`attachedConnectors` = 0** |

작화 담당이 **일부러 안 그린 게 아니라 그릴 수 없었다.** 상태라면 「무엇에서 들어오고 무엇으로 나가는가」가 있어야 하는데, 셋 다 **들어오는 곳이 상태가 아니라 승인 절차**이고 **나가는 곳이 확정 4 중 하나**다.

## 5. 그러면 셋은 어디에 있나 — 실제 경로

```
                  검사 판정
                     │
      ┌──────────────┼──────────────┬─────────────────┐
      ▼              ▼              ▼                 ▼
   Release         보류           Hold          PQC 검사 필요
      ▲              │              │                 │
      │              │              │                 ├─ 전수 재검 양품 ─▶ Release
      │              │              │                 └─ 재검 불량분 ──▶ 02-S-I
      │              │              │
      │         재판정 합격          │
      ├──────────────┘              │
      │                             │
      │      ┌──── 특채 승인 ────────┤   quality.concession
      ├──────┤     (범위·수량·기간)   │   → 승인분 수량만 Release 로 이동
      │      └───────────────────────┘
      │
      │      ┌──── 한도승인 ─────────┐   app.approval_request
      └──────┤   (IQC 생략·W-01-02)  │   → 검사 없이 Release 로 입고
             └───────────────────────┘

           Hold ──▶ 부적합 등록 ──── 폐기 판정 ────▶ 재고에서 출고(goods_issue)
              quality.nonconformance   disposition_decision    LOT 상태가 아니라 재고 소멸
              (+ nonconformance_lot)   ⚠ lot_id 없음 · nonconformance_id NOT NULL
```

⚠ **폐기는 부적합 등록을 반드시 경유한다**(§4.2.1) — 위 흐름도의 다른 갈래와 달리 **한 단계가 더 있다.**

| 후보 | 무엇인가 | LOT/재고는 어떻게 되나 |
| --- | --- | --- |
| **한도승인** | 검사를 **생략하고** 쓰기로 한 **승인 행위** (`W-01-02`) | 검사 없이 → **Release** |
| **특채** | 불합격인데 **조건부로** 쓰기로 한 **승인 행위** | 승인 **수량만** Hold → **Release** (`concession` 이 범위를 건다) |
| **폐기** | 못 쓰기로 한 **처분 판정** | **Hold 유지** → 폐기 출고로 **재고에서 나간다** |

⭐ 셋 다 **「어떤 상태인가」가 아니라 「어떻게 그 상태가 되었나」**다. 그건 상태 값이 아니라 **이력·근거**이고, `inventory_transaction` 이 그 자리다.

## 6. E3의 두 번째 질문 — 출고 가능 여부 매핑

`W-06-04` §4-B 가 「전부 미착지」로 남겨 둔 통제 속성이다. **4개로 줄이면 표가 닫힌다.**

| 상태 | 출고(생산 투입) | 출하(고객) | Picking 대상 | **출고 조회 대상** |
| --- | :-: | :-: | :-: | :-: |
| `RELEASE` | ✅ | ✅ | ✅ | ✅ |
| `PENDING` | ❌ | ❌ | ❌ | ❌ |
| `HOLD` | ❌ | ❌ | ❌ | ❌ |
| `PQC_REQUIRED` | ❌ | ❌ | ❌ | ❌ |

⭐ **통제 축이 사실상 1개다** — 「`RELEASE` 인가 아닌가」. 나머지 셋은 차단이 같다.

### 6.1 ⚠ 차단은 **차원 필터**이지 `blocked_qty` 가 아니다

`quality_status_code` 가 유니크 차원이므로(§2.1) **차단은 「그 행을 조회 대상에서 뺀다」로 이뤄진다.**

```sql
-- 출고 가능 재고
WHERE quality_status_code = 'RELEASE'
```

⛔ **`blocked_qty` 로 차단되는 것이 아니다.** 둘은 **별개 축**이다:

| | `quality_status_code` | `blocked_qty` |
| --- | --- | --- |
| 단위 | **재고 행 전체**(차원) | **행 안의 일부 수량** |
| 이름 | 품질 판정 | **「사용제한수량」**(논리 모델 3-2 §1328) |
| `available_qty` 와의 관계 | **식에 없다** | `on_hand − reserved − picked − **blocked**` 에 들어간다 |

즉 `HOLD` 행에도 `available_qty` 는 **양수로 남는다**(그 행의 `on_hand_qty` 만큼). 그 행을 **아예 안 보는 것**이 차단이다.

⚠ **구현 시 주의** — 「Hold 면 `available_qty` 가 0 이겠지」로 짜면 **재고가 새어 나간다.** 조회 조건에 상태 필터를 반드시 건다.

> `blocked_qty` 가 무엇을 위한 축인지는 이 제안안이 다루지 않는다(실사 중 잠금·예약 대기 등으로 보이나 **확인하지 않았다**). §10-5 와 함께 남긴다.

⚠ **그래서 `W-06-04`(판정유형 코드 마스터)의 존재 이유가 약해진다.** 통제 속성이 상태별로 다르지 않으면 이 화면은 `W-06-06` 공통코드 편집기의 복제다(`W-06-04` §3 이 스스로 제기한 질문). **본 제안이 채택되면 `W-06-04` 폐지 검토가 따라온다.**

특채의 허용 범위는 **상태가 아니라 `concession` 행이 건다**:

| 검사 지점 | 무엇을 보나 |
| --- | --- |
| 출고·Picking | `inventory_balance.quality_status_code = 'RELEASE'` |
| 특채분 사용 | + `concession` 의 `allowed_work_order_id`·`allowed_process_id`·`valid_to`·`approved_qty − consumed_qty > 0` |
| 출하 | + `concession.allowed_customer_id` |

## 8. 고객사에 물을 것 — 질문을 바꾼다

**「값 목록을 정해 주세요」를 「업무에 이런 일이 있습니까」로 바꾼다.** 셋 다 예/아니오로 답할 수 있고, 답이 무엇이든 상태 값 4개는 바뀌지 않는다.

| # | 질문 | 왜 묻나 | 답이 「예」면 | 답이 「아니오」면 |
| :-: | --- | --- | --- | --- |
| **Q1** | 검사 불합격인 자재·제품을 **조건부로 사용하기로 결정**하는 일이 있습니까? (수량·기간·용도를 한정해서) | 특채(`concession`) 사용 여부 | `concession` + `W-01-02` 계열 승인 화면 필요 | 해당 테이블·화면 **미사용**. 상태 4개는 그대로 |
| **Q2** | 검사를 **생략하고** 먼저 투입해야 하는 긴급 상황이 있습니까? | 한도승인(`W-01-02`) 사용 여부 | 승인 결재선 정의 필요 | `W-01-02` **미사용** |
| **Q3** | Q1·Q2의 **승인 권한은 누구입니까?** (직책·직급 수준으로) | 결재선 설계 입력 | 결재선 정의(`W-06-15`)에 반영 | — |

⚠ **Q1·Q2에 「아니오」가 나와도 설계는 안 무너진다** — 테이블과 화면을 안 쓸 뿐이다. **이것이 안 A의 큰 이점이다.** 안 B였다면 「특채 안 씁니다」가 상태 값 목록을 바꿔 전이도를 다시 그려야 한다.

## 10. 이 제안의 약점

정직하게 적는다.

| # | 약점 | 완화 |
| :-: | --- | --- |
| 1 | **결정 08·10을 정정해야 한다** — 확정 기록을 뒤집는 것은 가볍지 않다 | 뒤집는 것은 **위치 지정과 카디널리티**이고, 두 결정의 **원칙**(단일 지점·이원 보유 금지·3축 분리)은 그대로 산다. 게다가 하류가 이미 다르게 구현했다 |
| 2 | **고객사가 「한도승인·특채를 상태로 보고 싶다」고 할 수 있다** — 현장 용어로는 그게 자연스럽다 | 화면 **표시**는 「특채(수량 100 / 잔여 40)」로 보여 줄 수 있다. **저장 구조와 표시가 다른 것은 정상**이다. §8 Q1이 그 요구를 잡는다 |
| 3 | **`W-06-04` 존재 이유가 약해진다** — 화면 하나가 사라질 수 있다 | 폐지가 아니라 **폐지 검토**다. `W-06-13`(→`W-06-02` 통합) 선례가 있다. 인벤토리 재계수는 별건으로 다룬다 |
| 4 | **`quality_status_code` 값 목록이 물리 모델에 정의돼 있지 않다** — `app.code_t` 맨몸이라 DB가 4개로 강제하지 않는다 | 그래서 이 제안안이 필요하다. 확정 후 `mdm.code_group` 에 등록하고 **OpenAPI enum 으로 강제**한다 |
| 5 | **`inventory_status_code` 와의 관계를 이 제안이 다루지 않았다** — 같은 유니크 차원에 나란히 있다 | 별건. 품질 축(②)과 다른 축으로 보이나 **확인하지 않았다**. 단정하지 않고 남긴다 |
