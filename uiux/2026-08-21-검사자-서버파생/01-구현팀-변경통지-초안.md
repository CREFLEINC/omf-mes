## 무엇이 바뀌었나

**검사 결과 저장 요청에서 검사자·단말 칸을 뺐습니다. 서버가 채웁니다.**

| 스키마 | 바뀐 것 |
| --- | --- |
| `InspectionResultCreate` | `inspectorId`(**필수였음**) 제거 · `terminalId` 제거 |
| `InspectionResultUpdate` | `inspectorId` 제거 |

⛔ **응답 `InspectionResult` 는 그대로입니다** — `inspectorId`·`terminalId` 를 **읽어서 화면에 보이는 것**은 변함이 없습니다. 바뀐 것은 **보내는 쪽**뿐입니다.

**왜** — 검사자는 **로그인한 주체에서 서버가 정하는 값**이라 화면이 만들 수 없습니다. 로그인 사용자 번호와 작업자 번호는 서로 다른 체계이고 둘을 잇는 연결이 비어 있을 수 있어서, 화면이 세션 값을 그대로 실으면 **품질 감사 기록에 엉뚱한 사람이 검사자로 남습니다.** 값이 그럴듯한 정수라 아무도 눈치채지 못합니다. 단말도 같습니다 — 요청을 인증한 것이 단말이므로 서버가 이미 압니다.

## 코드에 무엇을 해야 하나

**1. 저장 요청 본문에서 두 칸을 지웁니다.**

```
POST /quality/inspection-results
PUT  /quality/inspection-results/{inspectionResultId}

  ⛔ inspectorId  보내지 않습니다
  ⛔ terminalId   보내지 않습니다
```

보내면 계약에 없는 칸이라 타입이 맞지 않습니다.

**2. 세션에서 검사자를 만들어 내려던 코드가 있으면 지웁니다.** 세션의 사용자 번호를 `inspectorId` 로 쓰거나, 작업자 목록을 받아 로그인 사용자와 맞춰 보려던 처리가 대상입니다. **둘 다 필요 없어졌습니다.**

**3. 저장 실패 하나를 새로 다뤄 주세요.** 로그인 계정에 작업자 정보가 연결돼 있지 않으면 **서버가 저장을 거부**합니다. 그때는 이런 성격의 안내를 보이면 됩니다.

```
이 계정에 작업자 정보가 연결돼 있지 않습니다 — 기준정보 담당자에게 문의하세요
```

⚠ **재시도 버튼을 두지 마세요.** 기준정보를 고쳐야 풀리는 것이라 다시 눌러도 같은 결과입니다. 정확한 오류 코드와 응답 형태는 확정되는 대로 따로 알리겠습니다.
