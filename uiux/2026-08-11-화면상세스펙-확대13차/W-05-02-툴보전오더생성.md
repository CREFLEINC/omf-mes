## §3. ⭐ 「겸용 설정형」의 절반이 저장처가 없다

QA #11 이 PM 트리거를 **「타발수 + 날짜 주기 **겸용 설정형**」**으로 확정했다. **두 축의 재료가 다르다.**

| 축 | 재료 | 실재 |
| --- | --- | :-: |
| **타발수** | `guaranteed_shot_count`(적정타수) · `current_shot_count`(누계) | ✅ **둘 다 실재**(SQL 477~) |
| **날짜 주기** | 주기(일/월) · **마지막 PM 일자**(BaseDate) | ⛔ **없다** |
| **겸용 설정** | 어느 축을 쓰는가 · 둘 다면 **어느 쪽이 먼저** | ⛔ **없다** |

### §3-1. 확정 — 툴 마스터에 **주기 축 3개**를 더한다

11차 `W-05-13` 이 툴 마스터에 「유형 코드 1개」를 더했다. **여기서 3개가 더 필요하다.**

| 항목 | 왜 |
| --- | --- |
| **PM 주기 유형** — 타발수 / 날짜 / 둘 다 / 안 함 | QA #11 「**겸용 설정형**」의 「설정」이 이것이다 |
| **PM 날짜 주기**(간격 + 단위) | 날짜 축의 재료 |
| **마지막 PM 일자** | BaseDate — ⛔ **읽기 전용**(`W-05-03` 이 정한다 · B-13) |

⚠ **「어느 쪽이 먼저」는 값이 아니라 규칙이다** — 둘 다면 **먼저 도달한 쪽**이 트리거다. **A-14** 적용 — 설정 값을 늘리지 않고 판정 규칙으로 둔다.

```
PM 도래 = (타발수 축 사용 AND 누계 ≥ 적정타수)
       OR (날짜 축 사용 AND 오늘 ≥ 마지막 PM 일자 + 주기)
```

### §3-2. ⭐ 이것은 **A-15 가 막는 컬럼이 아니다**

「PM 도래 여부」를 컬럼에 넣고 싶어진다. **A-15**(달력이 만드는 변화를 컬럼에 넣지 않는다)가 막는다 — 판별 질문에 **「예」**다(아무도 아무것도 안 해도 날짜가 지나면 도래한다).

⭐ **그런데 「마지막 PM 일자」는 저장한다** — 판별 질문에 **「아니오」**다(PM 실적이 만든다). **A-17 ②**(재료가 바뀌면 과거가 소급으로 달라지는가)도 아니다 — 그냥 **사실 기록**이다.

| | 저장 | 근거 |
| --- | :-: | --- |
| 마지막 PM 일자 | ✅ | 사실 기록 — 실적이 만든다 |
| PM 주기 · 유형 | ✅ | 설정 값 |
| **PM 도래 여부** | ⛔ | **A-15** — 달력이 만든다 |
| **다음 PM 예정일** | ⛔ | **파생**(마지막 + 주기) · L-2 서버 계산 |

### §5-1. 목록은 **적체 화면**이다 — L-12

**기본값 = 「PM 도래 전건」 · 정렬 = 초과율 높은 순.**

| L-12 요구 | 이 화면 |
| --- | --- |
| 기본 조회 = 미처리 전건 | **PM 도래 전건**(오더 미발행) |
| 기본 정렬 = 경과일 긴 순 | ⭐ **초과율 높은 순** — 경과일보다 **초과율이 위험 크기**다 |
| 요약 = 경과 구간별 건수 | **「초과 3건 · 임박(90%↑) 5건 · 미등록 2건」** |

⚠ **「미등록 2건」을 요약에 넣는 것이 G-15 다** — 적정타수·주기가 비어 판정이 안 서는 툴이 **숨지 않는다**.

### §5-2. ⭐ 트리거 축과 누계를 **스냅샷으로 저장한다** — A-17 ②

오더를 만든 시점의 **누계타발수**와 **어느 축이 도달했는지**를 저장한다.

**A-17 ②** 판별 — 「**재료가 나중에 바뀌면 과거 값이 소급으로 달라지는가**」에 **「예」**다.

```
오더 발행 시   누계 512,400 · 적정 500,000 → 타발수 축 초과 2.5%
그 뒤          PM 실적이 누계를 리셋한다 (W-05-03)
               → 나중에 조회하면 「왜 이 오더가 발행됐는지」를 알 수 없다
```

⭐ **11차 `W-05-13` 의 「누계는 실적이 정한다」(B-13)와 12차 B-18(증분 가산)이 이 문제를 만든다** — 누계가 계속 움직이므로 **발행 근거를 얼려야 한다.**

### §5-3. ⭐⭐ 12차가 이월한 카디널리티 — **여기서 안 걸린다**

12차 `P-05-01` §8-3 이 「작업실적 : 툴사용실적 = N:1 이 모호하다 · **확정은 `W-05-02` 에서 — 거기서 실제로 걸린다**」로 넘겼다.

**확인 결과 — 이 화면은 카디널리티를 몰라도 성립한다.**

| 이 화면이 쓰는 것 | 어디서 |
| --- | --- |
| **누계타발수** | `mdm.mold.current_shot_count` — ⭐ **이미 합산된 값** |
| 적정타수 | `guaranteed_shot_count` |

⛔ **툴 사용실적 개별 행을 세지 않는다.** 12차가 **증분 가산(B-18)**으로 정해서 **누계가 마스터에 이미 있고**, 이 화면은 그 값만 본다.

⭐ **그래서 카디널리티가 실제로 걸리는 곳은 여기가 아니다** — **개별 실적 행을 세는 화면**, 즉 **`W-05-08`(비가동·가동 집계, 4단계)** 이거나 **툴 사용 이력 조회**다. 12차의 지목이 한 칸 어긋났다. → §7-2

⚠ **12차를 탓할 것이 아니다** — 12차 시점에는 「누계를 누가 갖는가」가 이 화면과 무관하다고 볼 근거가 없었다. **B-18 이 그 뒤에 확정되면서 답이 바뀌었다.**

### §5-4. 한 오더 = 한 툴

`W-05-05` §6-2 와 같은 판단이다 — **툴 2건을 고르면 오더 2건이 발행**된다. ③에 그 사실을 적는다.

⚠ **설비 보전 지시와 다른 점** — 설비는 **트리거 여러 개를 한 지시로 묶을 수 있다**(같은 설비면). 툴은 **트리거가 툴 자신의 상태**라 묶을 것이 없다.

### §5-5. 마커 M4 — **회신 대기가 아니다**

도식 마커 **M4**(「알람유형대기」)가 「적정타수 초과·고장 이벤트가 알람 상황 유형에 포함되는지 **고객 회신 대기**(E1)」로 남아 있다.

⭐ **DR-003 확정이 이것을 바꿨다** — 「이벤트 목록은 **코드 상수**(사용자 편집 불가)」이고 **우리가 정한다.**

| 이 화면 | `W-CO-11`(알람 수신자 설정) |
| --- | --- |
| PM 도래를 **목록으로 보인다** | 「적정타수 초과」 이벤트의 **수신자를 정한다** |

⚠ **이 화면이 알람을 발송하지 않는다** — 도래 판정은 조회 시점의 파생이고, **알람은 서버 배치가 낸다.** → §7-1

### §7-3. 이 장에서 나온 공유 계약 후보

#### ⭐ **판정 근거가 계속 움직이면 판정 시점의 값을 스냅샷으로 남긴다**

§5-2 가 그 사례다 — PM 오더를 만든 근거(누계타발수)가 **실적으로 계속 바뀌고 리셋까지 된다.**

**규칙안**: 어떤 문서를 **발행·확정**할 때 그 근거가 **뒤에 바뀌는 값**이면 **발행 시점의 값을 문서에 함께 저장**한다.

| 문서 | 얼려야 할 근거 |
| --- | --- |
| 툴 보전오더(이 화면) | 도래 시 누계타발수 · 트리거 축 |
| 보전 지시(`W-05-05`) | 트리거가 된 점검 이력·고장 |
| 특채 승인 | 승인 시점의 재고·판정 |

⭐ **A-17 ②의 실행형**이다 — A-17 은 「저장할지」를 정하고, 이것은 「**언제 얼리는지**」를 정한다.

#### **두 축을 겸용하는 판정은 「먼저 도달한 쪽」으로 두고 설정 값을 늘리지 않는다**

§3-1 이 그 사례다. **A-14 의 겸용 판**이다.

**규칙안**: 판정 축이 둘 이상이면 ① **각 축의 사용 여부만 설정**하고 ② **우선순위를 값으로 두지 않는다** — 「먼저 도달한 쪽」 같은 **규칙 하나**로 정한다 ③ 화면은 **어느 축이 도달했는지 보인다**.

⛔ **우선순위를 설정 값으로 두면** 「날짜 우선인데 타발수가 초과했다」 같은 **설명 못 할 조합**이 생긴다.
