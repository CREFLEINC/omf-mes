## §3. ⛔⛔ DR-001 1-B 의 근거 하나가 **절반만 맞았다**

DR-001 6-B(권고 근거 2번)가 이렇게 적었다.

> **이미 있는 것을 씁니다.** 자재 출고 경로(**출고 요청 → 출고 → 수불 기록**)가 완성돼 있고 API 계약도 있습니다. 예비품 전용 출고를 새로 만들면 같은 일을 두 번 만듭니다.

**실측으로 단계별로 확인했다.**

| 단계 | 테이블 | 재사용 | 막는 것 |
| --- | --- | :-: | --- |
| 출고 **요청** | `logistics.material_issue_request`(SQL 1377) | ⛔ **불가** | `work_order_id` **NOT NULL** → `production.work_order` — **보전은 W/O 가 없다**<br>`destination_location_id` **NOT NULL** → `mdm.location` — **설비가 아니라 창고 로케이션** |
| 요청 **라인** | `material_issue_request_line`(1393) | ⛔ **불가** | `item_id` **NOT NULL** → `mdm.item` — **예비품은 별도 마스터**(QA #7) |
| **출고 헤더** | `logistics.goods_issue`(1448) | ⭐ **가능** | `source_document_type_code` + `source_document_id` **다형** → **보전 지시를 원천으로**<br>`destination_type_code` + `destination_id` **다형** → ⭐ **설비를 도착지로** |
| 출고 **라인** | `goods_issue_line`(1469) | ⛔ **불가** | `item_id` **NOT NULL** → `mdm.item`<br>`lot_id` **NOT NULL** → `trace.lot` — ⚠ **예비품에 LOT 을 발번한다는 근거가 없다** |

### §3-1. 그래서 확정은 성립하되 범위가 좁다

⭐ **DR-001 1-B 의 실질은 「보전 실적이 출고 건을 참조만 하고 재고를 자동으로 깎지 않는다」이고 그것은 그대로 성립한다.** 틀린 것은 **「경로가 통째로 완성돼 있다」**는 근거 쪽이다.

| DR-001 이 기대한 것 | 실제 |
| --- | --- |
| 출고 요청 → 출고 → 수불, 세 단계 재사용 | ⭐ **출고 헤더의 다형 참조만 재사용** |
| 예비품 전용 출고를 새로 안 만든다 | **라인은 새로 만들어야 한다** |

⛔ **이것을 조용히 넘기지 않는다** — DR-001 은 **확정 문서**이고 그 근거가 부분적으로 틀렸다. **#67 회신에 함께 적는다**(§8-1).

### §3-2. 확정 — **헤더 재사용 · 라인 신설**

```
logistics.goods_issue          ← 그대로 쓴다
  source_document_type_code = MAINTENANCE_ORDER
  source_document_id        = 보전 지시 ID
  destination_type_code     = EQUIPMENT
  destination_id            = 설비 ID
  source_warehouse_id       = 예비품 창고

  └ goods_issue_spare_line   ← [신설]  (기존 goods_issue_line 과 형제)
      spare_part_id  → 예비품 마스터
      issue_qty · uom_id
```

**왜 기존 라인에 `item_id`·`lot_id` 를 nullable 로 풀지 않는가**

| 이유 | |
| --- | --- |
| **기존 제약이 약해진다** | 자재 출고 40만 건이 그 `NOT NULL` 에 기대고 있다 |
| **LOT 이 없는 것이 정상** | 예비품에 LOT 을 발번할 근거가 없다 — 자재 LOT 은 **입하에서 34자리로** 만들어진다 |
| **A-10 대응표가 갈린다** | 한 테이블이 품목과 예비품을 섞으면 조회하는 쪽이 매번 유형을 봐야 한다 |

⭐ **12차 `M-05-02` §9-3 의 「소유 클러스터가 다르면 한 테이블에 담지 않는다」와 같은 형태**다 — 여기는 **참조 대상이 다르다**(품목 ↔ 예비품).

### §3-3. DR-001 파생 확인 항목 1 에 답한다

DR-001 이 「**예비품이 일반 재고와 같은 창고 체계에 있는가** — 별도 부품 창고를 쓰면 창고 유형이 하나 는다」를 파생 확인으로 남겼다.

⭐ **`goods_issue.source_warehouse_id NOT NULL → mdm.warehouse`** 이므로 **예비품 창고도 `mdm.warehouse` 의 한 행**이다.

| | |
| --- | --- |
| 필요한 것 | **`warehouse_type_code` 값 하나**(예비품 창고) |
| 소관 | **`W-06-06`** 공통코드 |
| 창고 마스터 화면 | **`W-06-14`** — 이미 작성됨. **변경 없다**(값만 늘면 된다) |

✅ **「창고 유형이 하나 는다」가 맞았고, 그 이상은 없다.**

### §5-1. ⛔ 재고를 이 화면이 깎지 않는다 — DR-001 1-B 의 실질

| 이 화면 | 물류(01 도메인) |
| --- | --- |
| **출고 건을 참조**한다 · 사용 수량을 적는다 | **출고를 만든다** · 재고를 깎는다 |

⚠ **③ 구획에 그 사실을 상시 문구로 둔다** — 「출고 건을 참조만 합니다 — 재고는 이 화면이 깎지 않습니다」. 없으면 등록자가 **여기서 재고가 빠진다고 믿는다.**

⭐ **`[출고 요청 만들기 → 물류]` 는 링크다** — 이 화면이 요청을 만들지 않는다(§3-1 이 요청 경로를 못 쓴다고 확인했으므로, **예비품 출고 요청 자체를 어떻게 낼지는 물류 쪽 미결**이다). → §8-2

### §5-2. 지시 없는 실적 — **고장을 직접 참조한다**

`W-05-04` §5-4 가 「긴급 고장은 지시를 강제하지 않는다」로 정했고 `W-05-05` §3-2 가 「지시 없는 실적은 허용한다」로 이었다.

```
지시 있음   실적 → 보전 지시 → (트리거) → 고장·점검·PM
지시 없음   실적 → 고장 기록                     ← 직접
```

⚠ **둘 중 하나는 반드시 있다**(A-2 짝 제약) — 아무것도 안 가리키는 보전 실적은 **왜 했는지 알 수 없다.**

### §5-3. ⛔ 설비 상태를 바꾸지 않는다 — B-16

WF05 S5 Result 가 「**상태변화: 설비 '보전 중→가동'**」이라 적었다. **11차 B-16 이 그것을 막았다** — 자산 마스터의 상태는 **운용/폐기 2값**이고 「보전 중」은 **트랜잭션이 만드는 조건**이다.

| 상류가 말한 것 | 우리가 정한 것 |
| --- | --- |
| 보전 완료 시 설비 상태를 '가동'으로 | ⛔ **바꾸지 않는다** — **「열린 보전 건이 없다」가 되면 자동으로 사용 가능 판정이 선다**(B-16 판정식) |

⭐ **④ 마감 구획에 그 사실을 적는다** — 「설비 상태는 바뀌지 않습니다 — 「운용/폐기」 2값입니다」. **11차 판단이 3단계 화면에서 실제로 지켜지는지가 여기서 확인된다.**

### §5-4. 수행 구간 — G-16

**12차 G-16**(「진행 중」을 상태 컬럼으로 두지 않는다 · 자동 종료 금지)이 그대로 걸린다. 수행 종료가 비면 진행 중이고, **경과 시간은 저장하지 않는다.**

⚠ **비가동과 다른 점** — 비가동은 **자동 종료를 절대 안 한다**(OEE 를 조용히 틀리게 만든다). 보전 수행 구간은 **집계 지표가 아니라 기록**이라 위험이 낮다. **그래도 자동 종료는 두지 않는다** — 규칙을 화면마다 다르게 하면 갈린다.

### §5-5. 외주 보전 — **담당자를 비우고 이름을 적는다**

WF05 S5 Exception ④ 가 「**외주 보전**(자체 불가) → MES 는 **사용기록만**, 계약·발주 = 범위 밖」으로 확정했다. `W-05-05` §8-3 이 「`app.app_user` FK 라 외주 인력을 담을 수 없다」를 남겼다.

**확정 — 잠정안을 그대로 간다.**

| | |
| --- | --- |
| `외주 여부` 체크 | 켜면 **수행자 FK 를 비활성**(A-2 조건부) |
| `외주처` | **자유 텍스트** — ⚠ `mdm.partner` FK 를 쓰지 않는다 |

⛔ **`mdm.partner` 를 쓰지 않는 이유** — 협력사 마스터는 **구매·외주가공 대상**이고, **보전 업체는 등록돼 있지 않을 가능성이 높다.** 등록을 강제하면 **보전 실적을 못 적는다.** 외주가 잦아지면 그때 축을 더한다(§8-3).

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐⭐ **「이미 있는 것을 쓴다」는 단계별로 확인한다**

DR-001 1-B 가 「자재 출고 경로(**출고 요청 → 출고 → 수불 기록**)가 완성돼 있다」를 근거로 들었고, **셋 중 하나만 맞았다.**

**규칙안** — 기존 경로 재사용을 근거로 결정할 때

1. **경로를 단계로 쪼개 각각 확인**한다 — 「경로가 있다」는 **단계마다 성립 여부가 다르다**
2. **막는 것은 대개 `NOT NULL` FK 다** — 그 경로가 전제하는 대상(`work_order`·`item`·`lot`)이 우리 것과 다른가
3. **헤더가 다형이면 재사용되고 라인이 FK 면 안 된다** — 이번이 정확히 그 형태다

```
goods_issue        source_document_type_code + destination_type_code   ← 다형 → 재사용 ✅
goods_issue_line   item_id NOT NULL + lot_id NOT NULL                  ← FK   → 불가 ⛔
```

⚠ **A-13(「없다」고 적기 전에 4단)의 반대 방향**이다 — A-13 은 **없다고 단정하는 것**을 막고, 이 규칙은 **있다고 단정하는 것**을 막는다.

### 9-2. **확정의 결론이 맞아도 근거가 틀렸으면 적는다**

DR-001 1-B 의 **결론**(참조만·자동 차감 없음)은 성립하는데 **근거 하나**가 틀렸다.

**규칙안**: 확정을 실행하다 근거의 오류를 발견하면

1. **결론이 여전히 성립하는지 먼저 판정**한다
2. 성립하면 **결론을 유지**하고 **근거만 정정 기록**한다 — 확정을 흔들지 않는다
3. ⛔ **조용히 넘기지 않는다** — 같은 근거로 다음 결정을 내릴 수 있다

⚠ **DR-001 1-B 는 「나」안을 기각하고 「다」안을 택한 근거 셋 중 하나였다.** 다른 둘(확정 문답과 안 부딪침 · `W-06-08` 이 살아난다)은 그대로 맞으므로 **결론이 흔들리지 않는다.**
