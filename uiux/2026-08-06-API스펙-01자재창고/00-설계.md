# 01 자재창고 도메인 API 스펙 — 설계

> 작성일: 2026-08-06 (v0.1) · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **선행 트랙**: 기준정보 도메인(`uiux/2026-08-03-API스펙/` · PR #71 병합). **그 산출물 구조와 검증 축을 그대로 계승**하고, **다른 점만 이 문서가 정한다.**

---

## 1. 왜 지금인가

**화면 스펙은 65/108인데 계약은 기준정보 도메인 하나뿐이다.**

```
deliverables/openapi/    파일 1개  —  mdm-기준정보.json (경로 73)
                         /mdm 31 · /quality 16 · /planning 12 · /app 9 · /integration 4 · /audit 1
                         ⛔ /logistics · /inventory · /trace  →  0건
```

**52화면이 여기서 막혀 있다.** 프론트는 계약이 없으면 만들 수 없다 — 목 서버가 mock 할 것이 없고, 엔드포인트를 지어내면 나중에 전부 버린다(`deliverables/07` §1이 3화면을 뺀 사유와 같다).

### 1-1. 모델이 없어서가 아니다

| | |
| --- | --- |
| 01~04 도메인 테이블 | **78개 전부 실재**(logistics 32 · production 14 · quality 15 · inventory 10 · trace 7) |
| 화면 스펙 §8 차단 미결 | **전 화면 0건**(2차~6차 49장이 전부 「차단 0건 — 지금 지어도 된다」) |

**우리가 안 썼을 뿐이다.**

### 1-2. 7차(04 제품출하 11장)보다 이것이 먼저다

| | 지금 하면 | 안 하면 |
| --- | --- | --- |
| **01 API 스펙** | 화면 21장이 발행 가능해진다 | 스펙만 쌓이고 프론트는 7화면 뒤로 논다 |
| 7차 화면 스펙 | 스펙 65 → 76 | 발행 가능 화면은 **그대로 7** |

⚠ **01이 02보다 먼저인 이유** — `omf-mes-client` 에 앱이 **`web` 하나뿐**이다(`apps/web` · `packages/{api-client,domain,i18n,ui}`). **POP·모바일 셸이 아직 없다.** 01은 관리웹이 12장(`W-01-01`~`12`)이고 02는 POP이 절반이다.

## 2. 계승하는 것 — 기준정보 트랙에서 그대로

**다시 정하지 않는다.** 아래는 `uiux/2026-08-03-API스펙/00-설계.md`가 이미 확정한 것이고 이 트랙도 따른다.

| 항목 | 내용 |
| --- | --- |
| **산출물 한 쌍** | 요구서(`.md`) = **왜·어디서** / OpenAPI(`.json`) = **무엇** |
| **중복 금지** | 요구서에 **필드표를 쓰지 않는다.** 같은 것을 두 곳에 쓴 것이 §I 불일치의 원인이었다 |
| **검증 축 둘** | ① **커버리지**(UI가 필요로 하는 API가 다 있는가) ② **적합성**(UI에서 쓰기에 적절한가). ⛔ **SQL↔OpenAPI 직접 대조는 하지 않는다** — 데이터모델 담당 소관 |
| **`example` 필수** | 목 도구가 스키마만 보면 `"string"`·`0`이 나와 화면 검증이 안 된다. 화면 스펙의 예시 값을 넣는다 |
| **오류 2계열** | 409(재시도하면 풀린다) ↔ 400(고쳐야 풀린다)를 섞지 않는다 |
| **미착지 처리** | 없는 것을 스키마에 지어 넣지 않고 **무엇이 막히는지**를 요구서에 적는다 |
| ⚠ **`description` 은 공개된다** | client 의 `gen:api` 가 JSDoc 으로 옮겨 **공개 저장소에 커밋**한다. 내부 서술은 `x-internal-note` · 커밋 전 `deliverables/openapi/check-public-safe.py` |

## 3. ⭐ 계약이 모델보다 앞서도 된다 — **2026-08-06 사용자 확정**

기준정보 트랙은 **물리 모델에서 타입·제약을 그대로 가져왔다.** 그래서 품질이 좋았지만, 그것이 **전제 조건은 아니었다.**

| 원칙 | |
| --- | --- |
| **모델이 있으면 모델을 우선한다** | 01은 테이블이 다 있으므로 **대부분 이쪽**이다 |
| **없으면 화면 요구로 쓴다** | 단 **「모델 미확정 — 조정 대상」을 표시**한다 |
| **조정이 필요하면 합의** | **계약을 먼저 끝까지 쓰고 조정 필요분을 묶어서 한 번에** 이슈로. 건건이 물으면 트랙이 멈춘다 |

> 근거 — 우리 검증 축이 이미 **「UI 요구 충족」**이고, §I 대장 34건이 **「하류가 확정을 못 따라간다」**는 기록이다. **물리 모델이 정본이 아니라는 것을 우리가 이미 세고 있다.**

**무엇을 정하고 무엇을 비우나:**

| 화면이 정한다 | 모델이 정한다 |
| --- | --- |
| 리소스·경로·오퍼레이션 | 저장 타입·길이·정밀도 |
| 보여줄 필드 / 받을 입력 | `NOT NULL`(저장상 필수) |
| **업무상** 필수 여부 | 유일 제약의 실제 범위 |
| 오류 상황·상태코드 | `CHECK` 제약의 정확한 식 |
| 페이지네이션·정렬·필터 축 | 인덱스·파티션 |

⚠ 담당자(`wooju-shin`) 원칙 통지는 **사용자가 직접** 한다 — 이 트랙에서 이슈를 내지 않는다.

## 4. ⭐ 이 트랙의 핵심 발견 — **리소스 패턴 3종이 01을 덮지 못한다**

기준정보의 세 패턴은 **마스터 데이터**를 위한 것이다. 01은 **업무 문서**다.

### 4-1. 실측 — 01 범위 30테이블의 형태

```
is_active 를 가진 것        putaway_rule  1개뿐
status_code + version_no    27개  ← 지배적
idempotency_key             inventory_transaction  1개뿐
헤더-라인 구조              10쌍
```

| 기준정보 패턴 | 판별 | 01에 몇 개 |
| --- | --- | :-: |
| **가. 마스터 형** | `is_active` + `version_no` | **1** (`putaway_rule`) |
| **나. 부여·회수 형** | `created_at`·`created_by`만 | 6 (`inbound_variance`·`lot_relation`·`handling_unit_content` 등) |
| **다. 버전 마스터 형** | 헤더–버전–라인 + 유효기간 | **0** |

**27개가 어디에도 안 들어간다.**

### 4-2. 신설 — **라. 업무 문서 형**

```
헤더(+라인)  ·  status_code 로 생애주기  ·  version_no  ·  is_active 없음
```

**`is_active` 가 없다는 것이 결정적이다.** 마스터 형의 `:deactivate`(끄기)가 성립하지 않는다 — 업무 문서는 **끄는 것이 아니라 상태를 옮긴다.**

| | 마스터 형 | **업무 문서 형** |
| --- | --- | --- |
| 지우기 | 물리 삭제 없음 · `:deactivate` | 물리 삭제 없음 · **`:cancel`**(취소 상태로 전이) |
| 상태 | `is_active` boolean | **`status_code`** — 작성중 → 확정 → 완료 / 취소 |
| 액션 | CRUD + `:deactivate` | CRUD + **상태 전이 액션 N개** |
| 낙관적 잠금 | 있다 | 있다 |

⚠ **상태 전이 액션의 이름과 개수는 문서마다 다르다.** `:confirm`·`:cancel`·`:post`·`:close`·`:approve` … **화면 스펙 §5의 버튼에서 도출**하고, 임의로 통일하지 않는다.

⚠ **`status_code` 값 목록이 전부 미확정이다**(맨 `code_t`). 공유계약 **G-2**(미확정 코드 목록의 표시)를 계약에도 적용해 **enum 을 못박지 않고 `x-internal-note` 로 남긴다.**

### 4-3. 신설 — **마. 원장 형** (`inventory.inventory_transaction`)

**성격이 완전히 다르다.** 하나뿐이지만 **01의 심장**이다 — 재고를 움직이는 모든 화면이 지난다.

```
PARTITION BY RANGE (business_date)          ← 조회에 기간 필수 (공유계약 L-3)
UNIQUE (idempotency_key, business_date)     ← 멱등 (C-8 — business_date 까지 클라이언트가 정한다)
reversal_of_transaction_id + business_date  ← 취소는 삭제가 아니라 역처리 행
PRIMARY KEY (id, business_date)             ← 복합 키
version_no 없음                              ← append-only. 낙관적 잠금 대상이 아니다
```

| 규칙 | |
| --- | --- |
| **쓰기** | 화면이 직접 전기하지 않는다. **업무 문서의 상태 전이가 만든다**(전표 확정 → 원장 기록) |
| **취소** | `DELETE`·`PUT` 없음. **역처리 행을 추가**한다 |
| **조회** | `business_date` 범위 **필수** — 없으면 전 파티션 스캔 |
| **멱등키** | 오프라인 큐가 재전송해도 중복되지 않는다. **`business_date` 가 키에 포함**되므로 날짜 경계 처리를 계약이 명시한다(C-8) |

### 4-4. 신설 — **바. 파생 잔액 형** (`inventory.inventory_balance`)

```
available_qty  numeric GENERATED STORED     ← 화면이 계산하지 않는다 (L-2)
version_no 있음 · status_code 없음
uq_inventory_balance_dim  11축              ← 공유계약 A-7
```

**읽기 전용이다.** 잔액을 직접 쓰는 경로를 두지 않는다 — 원장이 움직이면 서버가 파생한다.

⚠ **11축 유일 인덱스가 조회 API 설계를 지배한다** — 「어느 축으로 묶어 보이나」가 곧 쿼리 파라미터다(공유계약 **L-7** 「묶으면 안 되는 축」).

### 4-5. 정리 — **패턴 6종**

| # | 패턴 | 01 개수 | 출처 |
| :-: | --- | :-: | --- |
| 가 | 마스터 형 | 1 | 기준정보 계승 |
| 나 | 부여·회수 형 | 6 | 기준정보 계승 |
| 다 | 버전 마스터 형 | 0 | 기준정보 계승(01에는 없다) |
| **라** | **업무 문서 형** | **27** | **이 트랙 신설** |
| **마** | **원장 형** | **1** | **이 트랙 신설** |
| **바** | **파생 잔액 형** | **1** | **이 트랙 신설** |

**착수 통지의 「리소스 패턴」 드롭다운은 4종**(마스터/버전 마스터/조회/입력)이라 **1:1이 아니다.** 업무 문서 형·원장 형은 **「입력 형」**, 파생 잔액 형은 **「조회 형」**으로 옮긴다 — 하네스 `references/field-sources.md` §1-2에 이 대응을 추가한다.

## 7. 착수 전 확인 대상

| # | 항목 | 상태 |
| :-: | --- | --- |
| 1 | **상태 전이 액션의 이름 규약** | ▶ **진행하며 정한다** — 화면 §5 버튼에서 도출 |
| 2 | ~~**원장 쓰기 경로를 노출할 것인가**~~ | ✅ **해소 (2026-08-06)** — **#88 회신: 「`inventory_adjustment` 도 라인을 만든다」.** 재고조정도 다른 전표와 같다(문서 확정 → 원장). **예외 경로 불요** |
| 3 | **오프라인 큐의 계약 표현** | ▶ **진행하며 정한다** — §C 12조항을 OpenAPI 형태로 옮기는 일이다 |
| 4 | ~~**`putaway_rule` 관리 화면이 없다**~~ | ✅ **해소 (2026-08-06 사용자 확정)** — **`W-06-14` 적치 규칙 마스터 신설**(인벤토리 v1.6 · 화면 108→109). `W-06-07`에서 이어지는 화면 |

### 7-1. 4번이 이 트랙보다 먼저 드러난 이유

`M-01-05`(적치·입고 완료)의 **권장 위치 규칙이 「경고」에서 「차단」으로 바뀌면서**(2026-08-06 사용자 확정) 파급이 올라갔다.

| | 경고였을 때 | **차단인 지금** |
| --- | --- | --- |
| `putaway_rule` 이 비면 | 경고가 안 뜰 뿐 — 무해 | ⛔ **차단 기준 자체가 없다** |

**규칙 없는 품목은 「확인 후 통과」로 정했다** — 막으면 미등록 품목이 적치를 못 해 현장이 선다. 대신 **적치 위치는 반드시 남긴다**(`ck_putaway_completed`가 이미 강제).

⚠ **창고 단위 위치 관리 ON/OFF 는 새 컬럼이 필요 없다** — `mdm.warehouse.management_level_code`(「창고·구역·랙·셀 관리수준」)가 이미 그 축이고 `W-06-07` 이 편집한다. **값 목록만 미정**(#64)이고, 그 값이 **차단 판정의 근거**가 되어 무게가 올라갔다.

### 7-2. 이 트랙이 새로 안게 된 것

**`W-06-14` 는 06 도메인이라 이 트랙(01)의 대상이 아니다.** 다만 **계약은 이미 있다** — `putaway_rule` 은 마스터 형이고 기준정보 OpenAPI 가 덮는 범위다. ⚠ **실측 확인 필요** — 현재 `mdm-기준정보.json` 에 `/logistics/putaway-rules` 경로가 **없다**(73경로 전수 확인). **기준정보 계약에 추가할지 01 계약에 넣을지**를 §6 실행 순서 2단계에서 정한다.
