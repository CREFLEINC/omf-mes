## 3. ⭐ 화면 버튼을 다시 세니 2단계 규약이 **세 곳 뒤집혔다**

2단계는 테이블과 프로세스를 보고 동사를 정했다. 3단계는 **화면 §5의 버튼을 한 줄씩** 대조했고, 「화면이 두 버튼이면 두 오퍼레이션, 한 버튼이면 하나」(2단계 §2-2) 규칙이 **자기 자신을 세 번 정정했다.**

### 3-1. `:depart` 를 두지 않는다

| | 2단계 | **3단계** |
| --- | --- | --- |
| 반출 | `POST /stock-transfers` 생성 → `:depart` | **`POST /stock-transfers` 하나** |

`M-01-10` §5-6의 버튼은 **「① 반출 스캔」 하나**다. 생성과 반출을 나누면 **오프라인 큐에 「생성됐으나 반출 전」 상태가 남는다** — 그 상태를 볼 화면이 없다. `:arrive`는 「② 도착 스캔」이 따로 있으므로 남는다.

### 3-2. ⭐⭐ **`:cancel` 을 쓰는 화면이 01에 하나도 없다**

2단계가 업무 문서 형의 「끄기」로 `:cancel` 을 정의했다. 3단계에서 23장의 「취소」 버튼을 전수 확인했다.

| 화면 | 「취소」의 뜻 |
| --- | --- |
| `W-01-03` | **화면 이탈** — 「아직 아무것도 저장되지 않았다」(§5-1) |
| `M-01-06` | **화면 이탈** — `M-01-01`로 복귀 |
| `W-01-11` | **화면 이탈** — `W-01-03`으로 복귀 |

**전부 저장 전 복귀다.** 문서를 취소 상태로 옮기는 액션은 **0건**이다.

> **⛔ 그래서 전기된 전표를 되돌릴 방법이 계약에 없다.** 2단계 §3-2는 「원장의 취소도 전표의 `:cancel` 이 만든다」고 했는데, 그 `:cancel` 이 어느 화면에도 없다. 현재 설계에서 되돌리는 유일한 경로는 **실사 → 조정**이다.
>
> 지어내지 않았다. **화면이 없는 오퍼레이션을 만들면 프론트가 부를 데가 없고, 나중에 진짜 화면이 생기면 버린다**(`00-설계.md` §2 미착지 처리). 4단계 요구서에 **미착지**로 올린다.

### 3-3. 예약에 쓰기 경로를 두지 않는다

1단계는 `inventory_reservation` 을 「조회 · 예약/해제」로 적었으나, `M-01-08` §5-5가 **「화면은 이 이동을 직접 쓰지 않고 서버 전기에 맡긴다」**고 못박았다. **조회만** 만들었다.

### 3-4. `:temporary` → `:complete-temporary`

`:complete` 와 **짝이라는 것이 이름에 드러나야** 한다. `M-01-07`의 「적치 완료(임시)」는 정상 적치의 변종이지 별개 행위가 아니다.

## 4. 한 버튼을 한 오퍼레이션으로 옮긴 자리

| 화면 | 버튼 | 계약 |
| --- | --- | --- |
| `W-01-10` | 「입고 처리」 **하나** | `POST /logistics/goods-receipts` **하나** — `:confirm`·`:post` 로 쪼개지 않았다 |
| `M-01-09` | 「입고 확정」 **하나** | `POST /logistics/shopfloor-receipts` **하나** |
| `M-01-08` · `W-01-05` | 「출고 확정」·「반품 처리」 **하나** | `POST /logistics/goods-issues` + **`postImmediately: true`** |
| `W-01-06` | 「품의 상신」→「승인」→「기타출고 처리」 **셋** | `POST` + `:request-approval` + `:post` |
| `W-01-12` | 「조정 상신」→「승인」→「전기」 **셋** | `POST` + `:request-approval` + `:post` |

### 4-1. ⚠ `postImmediately` 를 둔 이유

**한 리소스(`goods_issue`)를 세 화면이 서로 다른 버튼 구조로 쓴다.** 두 화면은 한 버튼, 한 화면은 셋이다.

| 안 | 판정 |
| :-: | --- |
| 경로를 셋으로 나눈다 | ⛔ 2단계 §2-3이 이미 「나누면 조회가 세 곳을 봐야 한다」고 기각 |
| 늘 `POST` 후 `:post` 두 번 호출 | ⛔ **오프라인 큐에 중간 상태가 남는다**(C-1) · 한 버튼인데 두 번 부른다 |
| **`postImmediately` 필드** | ✅ **채택** — 화면의 버튼 구조를 계약이 그대로 표현한다 |

`W-01-03` 초과 분리의 `mode`(`BOTH`·`NORMAL_ONLY`·`EXCESS_ONLY`)도 같은 형태다 — **세 갈래가 모두 화면의 버튼**이다(§5-1).

## 5. 오프라인을 계약에 실장한 곳 — **10 오퍼레이션**

2단계 §5가 정한 3항목(멱등키 헤더 필수 · `businessDate` 본문 · `If-Match` optional)을 **모바일 화면이 부르는 오퍼레이션에만** 적용했다.

```
POST /logistics/inbound-receipts                                   M-01-01
POST /logistics/putaway-tasks/{id}:complete                        M-01-05
POST /logistics/putaway-tasks/{id}:complete-temporary              M-01-07
POST /logistics/picking-orders/{id}/lines/{id}:pick                M-01-08
POST /logistics/goods-issues                                       M-01-08
POST /logistics/shopfloor-receipts                                 M-01-09
POST /logistics/stock-transfers                                    M-01-10
POST /logistics/stock-transfers/{id}:arrive                        M-01-10
PUT  /inventory/counts/{id}/lines                                  M-01-11
POST /trace/lots                                                   M-01-02
```

**관리웹 전용 쓰기는 `If-Match` 를 required 로 유지**했다(`IfMatchVersion` ↔ `IfMatchVersionOptional` 두 파라미터). C-9의 완화는 **오프라인 대상에만** 적용한다는 2단계 단서를 계약이 구조로 표현한다.

⚠ `occurredAt`(단말 시계)과 `recordedAt`(서버 수신)을 원장 응답에서 **분리해 내린다.** C-12(시계 오차 보정)는 아직 없다 — `occurredAt` 을 그대로 신뢰하는 것이 현재 계약이다.

## 6. 화면이 세지 않게 서버가 세는 것

「화면이 별도 호출로 세면 화면마다 다르게 구현된다」는 기준정보의 `Editability`(B-4)와 같은 원리를 **네 곳**에 적용했다.

| 필드 | 어디에 | 없으면 |
| --- | --- | --- |
| `InventoryCountSummary` 4칸 | 실사 상세 | 화면이 전 라인을 받아 센다 — 페이지네이션과 어긋난다(`W-01-04` §5-6) |
| `PickingLine.held` · `holdReasonCode` | 피킹 상세 | 라인마다 `lot_hold` 를 따로 조회한다(`M-01-08` §5-8) |
| `InventoryBalance.heldLotCount` | 재고 조회 | 같은 문제 |
| `PutawayTask.warehouseManagementLevelCode` | 적치 지시 | 위치 스캔 유무를 화면이 창고를 따로 조회해 판정한다(`M-01-05` §5-3) |
| `GoodsReceipt.erpMessageQueued` | 입고 상세 | 「전송됐다」와 「적재됐다」를 화면이 구분 못 한다(`W-01-10` §5-4) |

## 7. ⛔ 이 단계에서 드러난 것 — **`W-01-01` 은 계약이 없다**

1단계 §1-2가 **지금 착수 가능 7장**으로 `W-01-01`을 넣었다. **틀렸다.**

```
W-01-01 IQC 수입검사·판정 이 쓰는 것
   quality.inspection_request · inspection_result · inspection_measurement
                                    ↓
   mdm-기준정보.json 의 /quality 16경로  =  inspection_plan · plan_version · item_spec
                                            defect_code · cause_code
                                    ↓
                              ⛔ 전부 마스터다. 검사 실행 계약이 없다
```

**테이블은 있다**(`quality.*` 15개). 계약이 없을 뿐이다 — 01과 정확히 같은 상황이고, **`quality` 스키마라 03 품질 도메인 소관**이다(`lot_hold` 쓰기를 03으로 보낸 것과 같은 규칙 · `00-설계.md` §5-3).

| | 1단계 | **3단계** |
| --- | :-: | :-: |
| 지금 착수 가능 | 7장 | **6장** |

**`W-01-03` · `W-01-04` · `W-01-05` · `W-01-07` · `W-01-09` · `W-01-10`.**

| 리소스 | 무엇이 없나 | 어떻게 썼나 |
| --- | --- | --- |
