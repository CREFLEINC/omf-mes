## 1. 확정 — 5값

| 코드 | 표시명 | 뜻 |
| --- | --- | --- |
| **`REQUESTED`** | **대기** | 의뢰가 만들어졌고 **아직 아무도 손대지 않았다** |
| **`IN_PROGRESS`** | **진행** | 검사가 시작됐다 — **임시 저장이 있다** |
| **`COMPLETED`** | **완료** | 판정이 **확정**됐다 |
| **`SKIPPED`** | **생략** | 검사를 **하지 않기로 승인**되어 종결됐다 |
| **`CANCELLED`** | **취소** | 의뢰가 **무효**가 됐다 |

### 1.1 전이 — 그리고 **누가** 전이시키나

```
                          ┌────────────────────────────┐
                          │        재검사 회차 추가      │
                          ▼                            │
  (서버 생성) ──▶ REQUESTED ──▶ IN_PROGRESS ──▶ COMPLETED
                     │   첫 임시저장     판정 확정
                     │              │
                     ├──────────────┼──▶ SKIPPED     한도승인 · 샘플링 미대상
                     └──────────────┴──▶ CANCELLED   입하취소 · 검사 취소
```

| 전이 | 계기 | 누가 |
| --- | --- | --- |
| → `REQUESTED` | 입하(IQC) · 생산 실적(PQC) · 출하(OQC) 시점 | **서버** — 화면이 만들지 않는다 |
| → `IN_PROGRESS` | 첫 임시 저장 `POST /quality/inspection-results` `statusCode=작성중` | **서버(파생)** |
| → `COMPLETED` | `POST /quality/inspection-results/{inspectionResultId}:confirm` | 서버 |
| `COMPLETED` → `IN_PROGRESS` | 재검사 회차 추가 `POST /quality/inspection-results` `previousResultId` | 서버(파생) |
| → `SKIPPED` | `W-01-02` 긴급 IQC 생략 **한도승인**이 승인됨 | 서버(파생) |
| → `CANCELLED` | `W-01-13` 입고 취소(FR-IM-076) 등 원 거래 역처리 | 서버(파생) |

⭐ **새 경로가 0이다.** 다섯 전이 전부 **이미 있는 액션의 부수 효과**다. 03 품질 계약에 오퍼레이션을 더하지 않는다.

### 1.2 ⛔ 「검사 시작」 버튼을 두지 않는다

`FR-QM-050`(품질이력)이 **「검사 시작」을 이벤트로 열거**하지만, `W-01-01` §3 레이아웃에 **시작 버튼이 없다**(실측). 별도 액션을 신설하면 **화면에 없는 것을 계약이 요구**하게 된다.

⭐ **첫 임시 저장이 곧 검사 시작이다.** 품질 이력에는 그 순간 「검사 시작」으로 기록한다.

### 1.3 `pendingOnly` 의 정의를 값으로 못박는다

#170 으로 신설한 질의의 뜻이 이제 값으로 표현된다 — **서버 구현이 이것을 기준으로 삼는다.**

```
pendingOnly=true  ⇔  status_code ∈ { REQUESTED, IN_PROGRESS }
```

## 2. 왜 이 다섯인가 — 근거

| 값 | 근거 |
| --- | --- |
| `REQUESTED` | `FR-QM-050` 「검사대상 생성」·「검사 요청」 · `W-01-01` §3 좌측 큐가 **「대기」로 그린다** · client#85 「검사 의뢰는 **서버가 입고 시점에 만든다**」 |
| `IN_PROGRESS` | `FR-QM-050` 「검사 시작」·「임시저장」 · `W-01-01` §3 큐가 **「진행」으로 그린다** · §5-2 「**입력과 확정이 2단계다**」 |
| `COMPLETED` | `FR-QM-050` 「검사 확정」 · `FR-QM-008` 「**미완료** 검사」의 반대 축 · `W-01-01` §5-2 |
| `SKIPPED` | `W-01-01` §2·§5 「**생략 경로 2종**」(샘플링 미대상 → Release / 긴급승인 → 한도승인) · E3 제안안 §5 흐름도 「(IQC 생략·`W-01-02`) → **검사 없이 Release 로 입고**」 |
| `CANCELLED` | `FR-QM-050` 「**검사 취소**」 · `FR-IM-076` 입하취소(`W-01-13`) — 원 거래가 사라지면 그 의뢰도 설 수 없다 |

### 2.1 ⭐ `SKIPPED` 와 `CANCELLED` 를 합치지 않는다

**둘 다 「결과 없이 끝났다」지만 뜻이 정반대다.**

| | `SKIPPED` 생략 | `CANCELLED` 취소 |
| --- | --- | --- |
| 무슨 일이 있었나 | **검사를 안 하기로 «승인»했다** | **의뢰 자체가 «무효»가 됐다** |
| LOT 은 | **Release 로 입고된다** — 쓴다 | 원 거래와 함께 사라지거나 되돌아간다 |
| 정상 종결인가 | ✅ 예외적이지만 **정상 종결** | ⛔ 없던 일 |

합치면 **「검사 없이 통과시킨 건」과 「없던 일이 된 건」이 같아 보인다.** 품질 감사에서 「검사를 몇 건 생략했나」를 셀 수 없게 된다 — 생략은 **세어야 하는 수치**다.

### 2.2 ⭐ `대기` 를 「검사 대기」라 쓰지 않는다 — 축이 다르다

**LOT 상태 4값에 이미 `검사 대기` 가 있다**(2026-08-07 확정). 같은 문자열을 두 축에 쓰면 **#166 이 겪은 「같은 이름 다른 형태」가 재발한다.**

| 축 | 값 |
| --- | --- |
| **LOT 품질 상태** (`lot.status_code`) | 정상 · 불량 · **검사 대기** · 폐기 |
| **검사 의뢰 진행** (`inspection_request.status_code`) | **대기** · 진행 · 완료 · 생략 · 취소 |

⚠ **둘은 같이 움직이지 않는다** — 의뢰가 `COMPLETED` 여도 LOT 이 `불량`일 수 있고, 의뢰가 `SKIPPED` 여도 LOT 은 `정상`이다.

## 3. 표기 — **영문 코드 + 한글 표시명**

### 3.1 실측이 정했다 — enum 76개 중 한글은 **1개**

계약 7벌 전체를 세었다(`검사기`: 아래 재현 명령).

```
enum 총 76개 · 한글값 포함 1개
    quality-03품질.json  statusCode  ['작성중', '확정']
```

⭐ **한글 enum 은 관례가 아니라 «예외»다.** 나머지 75개가 전부 영문 대문자 스네이크이고, `mdm.code_value` 시드도 **`code`(영문) + `code_name`(한글)** 구조다(`INVENTORY_STATUS` → `AVAILABLE`/`가용`).

재현:

```
cd deliverables/openapi && python3 - <<'PY'
import json,glob,re
ko=re.compile(r'[가-힣]'); tot=kor=0
for f in sorted(glob.glob('*.json')):
    def walk(o):
        global tot,kor
        if isinstance(o,dict):
            if isinstance(o.get('enum'),list):
                tot+=1
                if any(isinstance(v,str) and ko.search(v) for v in o['enum']): kor+=1
            for v in o.values(): walk(v)
        elif isinstance(o,list):
            for v in o: walk(v)
    walk(json.load(open(f)))
print(tot,kor)
PY
```

### 3.2 ⚠ 그 예외를 **지금 고치지 않는다**

`inspection_result.statusCode` 의 `["작성중","확정"]` 은 **이미 구현팀이 코드를 만든 값**이다(계약의 `x-internal-note` 가 client#102·2026-08-12 를 인용한다). 지금 영문으로 바꾸면 **⛔ 이미 만든 것이 틀린다.**

⭐ **한 화면에서 두 축의 표기가 갈리는 것은 사실이다** — 의뢰는 `REQUESTED`, 결과는 `작성중`. #170 회신에서 **먼저 밝혀** 두 번째 질의를 막는다.

**후속 판단 사항**(이 확정의 범위 밖) — 결과 축을 영문으로 맞출지는 **별도 ⛔ 통지와 함께** 판단한다. 값 두 개짜리 변경에 이미 만든 코드를 깨뜨릴 값어치가 있는지가 쟁점이다.

### 3.3 철자

`CANCELLED` — **L 두 개**. 계약 실측 관례다(`CANCELLED` 3건 · `CANCEL_IN_PROGRESS` 4건 · `CANCELED` 0건).

### 3.4 기존 값과 의미 충돌 없음

| 값 | 계약 내 기존 사용 | 충돌 |
| --- | --- | :-: |
| `REQUESTED` | `logistics` 전표 `statusCode` **예시**(값 목록 미확정) | 없음 — 다른 표 |
| `IN_PROGRESS` | `app` 예시 · `logistics` 예시 | 없음 |
| `CANCELLED` | `logistics` 예시 | 없음 |
| `PENDING` | `app` **`printOutcome`**(인쇄 결과) | **⛔ 그래서 `REQUESTED` 를 골랐다** |

## 4. ⛔ enum 으로 못박지 않는다

**확정했지만 계약에 `enum` 을 넣지 않는다.** 값 목록은 **공통코드가 갖고 늘 수 있다**(공유계약 **G-2**·**G-6**).

⭐ **선례가 정확히 같다** — 판정 3값(`합격`·`불합격`·`보류`)도 2026-08-07 에 확정됐지만 계약은 이렇게 적혀 있다:

> `overallJudgmentCode` — 「합격·불합격·보류 3값. ⛔ **enum 으로 못박지 않는다** — 값 목록은 공통코드가 갖고 늘 수 있다(공유계약 G-2·G-6)」

따라서 계약에는 **설명 + `example`** 로만 싣는다. 화면도 값을 고정하지 않고 `GET /mdm/code-values` 로 표시명을 채운다.

## 5. 데이터 모델에 필요한 것 — **작업 통지 · 우리 차단 없음**

`mdm.code_group` / `code_value` 에 시드가 필요하다. **규칙 1** 대로 이것은 **남의 작업이고 우리를 막지 않는다** — 계약과 화면은 이 문서로 이미 선다.

```sql
INSERT INTO mdm.code_group (group_code, group_name, description) VALUES
('INSPECTION_REQUEST_STATUS', '검사 의뢰 상태',
 'quality.inspection_request.status_code 목록. 확정 2026-08-21 · omf-mes#170');

-- code / code_name / display_order
('REQUESTED',   '대기', 10)
('IN_PROGRESS', '진행', 20)
('COMPLETED',   '완료', 30)
('SKIPPED',     '생략', 40)
('CANCELLED',   '취소', 50)
```

⚠ **물리 모델은 이 확정을 앞설 수 없다**(사용자 확정 2026-08-18). `status_code` 는 `app.code_t`(varchar 50) 맨몸이라 타입은 이미 담을 수 있고, 시드가 늦어도 **계약은 이 문서대로 선다**.
