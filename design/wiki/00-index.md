## ⭐ 이 문서를 읽기 전에 — 규칙 하나

> ### **숫자는 여기 있는 것을 믿지 말고 «명령» 을 돌린다.**

이 저장소에서 **손으로 쓴 수치는 예외 없이 낡았고, 스크립트가 정본인 자리는 하나도 안 갈렸다.** 그래서 아래 표의 규모 칸에는 **숫자와 실측일과 세는 명령이 함께** 있다. 셋이 다 있으면 **낡아도 낡은 것이 보인다.**

```
python3 design/schema/generators/verify-counts.py     ← 이 문서의 숫자가 아직 맞는지 본다
```

## ⭐ 길 찾기 — **화면 하나에서 시작한다**

개발은 대개 **화면 하나**를 맡아 시작한다. 그 화면의 모든 것을 한 줄로 잇는 표가 있다.

> ### 👉 [**화면 진도표**](handover/화면-진도표.md) — 화면 ↔ 상세 스펙 경로 ↔ 요구서 ↔ 계약 ↔ 착수 통지

⛔ **이것이 없으면 나머지가 아무리 정확해도 안 읽힌다.** 화면 상세 스펙 118장은 이제
`screens/{01~06,공통}/` 도메인 폴더에 정리돼 있지만, 통합 정보구조 문서는 여전히
**화면 번호만 적고 파일 경로를 안 적는다.**

| 찾는 것 | 보는 곳 |
| --- | --- |
| **「이 화면의 상세 스펙이 어느 파일이지?」** | **화면 진도표** 또는 `screens/<도메인>/` |
| 「이 말이 무슨 뜻이지?」 | **00 용어 사전** |
| 「만들 때 지킬 규약이 뭐지?」 | **Ⅲ → 공유계약 §A~§L** |
| 「이 화면 액션이 어느 경로에 대응하지?」 | **Ⅴ → 요구서 §3** |
| 「필드·타입·필수·값 목록」 | **Ⅴ → `api-contracts/openapi/*.json`**(Tier 0, 컷오버 완료) |
| 「이 결정의 원문이 어디 있지?」 | **Ⅲ → 결정 대장** |
| 「남은 미결이 뭐지?」 | **99 인계 대장** |
| 「이 요구사항이 어디까지 확정됐지?」 | Ⅰ §3·§4 → §8 추적성 |
| 「이 단계에서 누가 어느 단말로 뭘 하지?」 | Ⅳ → 도메인 워크플로우 해당 도메인 |
| 「단말·수량·금액」 | Ⅱ → HW 구성안 ⛔ **미확정 — 고객 회신 대기** |

⛔ **한 칸이 여러 표를 가리키는 자리의 대응표 검사(구 `verify-polymorphic-mapping.py`)는
은퇴했다** — 물리 모델 소관이 백엔드팀으로 넘어가며 이 저장소 안에는 참조할 원본이 없다
(`schema/data-model-boundary.md` 참조).

## ⚠ 읽을 때 주의 셋

1. **예외 `E-n` ≠ 회신 `E-n`** — 업무 흐름 예외 번호와 고객 회신 대기 코드가 같은 표기로 병존한다. 이 위키에서는 「예외 E-n」·「회신 E-n」으로 갈라 적었다.
2. **«(정합주: …)»** — 원본끼리 어긋난 지점에서 **최신 확정을 채택했음**을 밝히는 각주다.
3. ⛔ **「회신 대기」와 「작업 통지」는 다르다** — 데이터 모델 요청은 **우리를 막지 않는다.** 답이 없어도 계약은 화면대로 선다. 고객 회신만 「회신 대기」다.
