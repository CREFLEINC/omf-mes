⭐ **막힌 것은 아니었다** «(구표기 보존)» — 그때 본 대체 경로는 이것이었다.

```
GET /logistics/goods-receipts   params: receiptTypeCode · warehouseId · statusCode · receiptDateFrom/To · q · page · size
```

`receiptTypeCode=RETURN` + `warehouseId` 로 반품 입고를 목록할 수 있다. ⚠ **다만 「부적합을 아직 안 만든 건만」을 서버에서 거를 축이 없다.**

⭐ **그러나 그 경로로 가지 않았다.** ⛔ 「부적합을 아직 안 만든 건만」을 서버에서 거를 축이 없는 것이 문제인데, 그 축을 `/logistics/goods-receipts`(01)에 달면 **물류 계약이 `quality.nonconformance` 를 알아야 한다** — 도메인 경계를 넘는 첫 사례가 된다. 게다가 **원천이 둘**이라(반품 입고는 01, OQC 불합격은 03) 어느 한쪽에 달아도 나머지가 남는다.

✅ **해소 2026-09-03(사용자 확정) — `GET /quality/disposition-candidates` 를 04 에 신설했다.**

```
GET /quality/disposition-candidates
  sourceCode(PRODUCT|RETURN) · withoutNonconformanceOnly · warehouseId · itemId · lotId
  receivedFrom/To · q · page · size
  → items[DispositionCandidate]  (LOT 단위 · nonconformanceId 가 null 이면 「미등록」)
```

`receivedAt`은 입고 전표의 입고일이 아니라 두 원천 공통의 **불량창고 거래 참고일**이다. 수량이 가장
큰 불량창고·단위 잔액 그룹을 고르고, 수량이 같으면 `warehouseId`가 작은 그룹을 고른 뒤 그 그룹의 마지막
거래 시각을 날짜로 표시한다. 기간은 양끝을 포함하고 날짜를 알 수 없는 행을 지우지 않는다. 기본 정렬은
원시 마지막 거래 시각 내림차순이며 그 시각까지 같으면 `lotId` 내림차순이다. 응답은 날짜만 노출하므로
같은 날짜 안의 시각 순서는 응답만으로 판별할 수 없고, null을 별도로 마지막에 배치하지 않는다.
`withoutNonconformanceOnly=true`는 열린
부적합이 없는 LOT를 뜻한다. 응답의 부적합 세 필드는 개시 시각 내림차순, 식별자 내림차순으로 고른
가장 최근 건이며, 열린 건이 없으면 최근 종결분을 싣는다.

**판정 셋과 근거** — ① **대상 단위 = LOT**(`NonconformanceCreate.lots[]` minItems 1 · `W-04-07` §3 목업의 행도 LOT). 상세 머리의 입고번호·거래처는 반품 전표 정보이고, 거래 참고일은 두 원천 공통의 불량창고 잔액 정보다 ② **원천 = 둘**(반품 + OQC) — §3-3 이 이미 「불합격 처분 의뢰 → 화면 이동 `W-04-07`」을 적었고 계약도 `sourceCode=PRODUCT`·`inspectionResultId` 로 그 진입을 받는데 **화면 스펙만 빠뜨리고 있었다** ③ **축은 04 에 둔다** — `nonconformance` 는 04 소유다(§1-1).

⭐ **`REQ-PR-0025` 가 말하는 진입 조건은 「부적합이 있는가」가 아니라 「불량창고에 입고됐는가」**다(「판정은 **불량창고 입고 후**」 · 프로세스 05 S11 도 「[판정 대기 시] 불량창고 입고 → 판정」). 선례도 둘 있다 — `withoutMaintenanceOrder`(`W-05-05` §7 「이미 지시가 있는 트리거는 목록에서 제외한다」)와 `followUpPending`(⭐ **그 축의 근거가 `W-04-07` §5-5 다** — 같은 04 형제 화면 셋의 같은 문제를 이렇게 풀었다).

⇒ **§6 의 착수 판정은 재확인 조건이 풀렸다.**
