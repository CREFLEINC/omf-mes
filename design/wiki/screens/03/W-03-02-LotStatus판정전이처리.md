# W-03-02 · Lot Status 판정·전이 처리

> 작성일: 2026-08-06 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 결정 10의 **「차단 판정 단일 지점」**을 실제로 조작하는 화면. ⭐ **B-3(이력 불변)을 지킬 수 없는 첫 화면**이다(§5-2).

## §0. 요약

- **개요**: 관리웹에서 품질담당이 보류 LOT의 재판정(Release/Hold 전이)과 Release LOT의 재Hold(클레임·리콜·재판정) 전이를 처리하는 화면. 좌측 대상 LOT 목록(상태·기간 필터) + 우측 선택 LOT의 현재 상태 카드와 전이 폼 2단 레이아웃이다.
- **데이터**: `trace.lot.status_code`(전이 대상)·`trace.lot_hold`(보류·해제 이력)·`inventory.inventory_balance.blocked_qty`를 다루며, 결정 10에 따라 출고·출하·피킹 차단을 결정하는 단일 판정 지점이다.
- **핵심 액션**: 대상 LOT 선택 → 전이 대상(서버가 갈 수 있는 곳만 제공) 선택 → 수량(전량/일부) 지정 → 사유 입력(필수) → 전이 확정(낙관적 잠금 토큰 동봉). 이 화면이 처리하는 전이는 재판정 합격(C7)·재판정 불합격(C8)·클레임·리콜·재판정(C9) 3건뿐이다.

## §4. 필드

### §4-A. 전이 대상 `trace.lot` (편집 — `status_code` 한 컬럼)

| 라벨(한/베) | 출처 컬럼 | 필수 | 편집 | 검증·비고 |
| --- | --- | :-: | :-: | --- |
| LOT 번호 | `lot_no` | — | ⛔ | 표시만 |
| **Lot Status** | **`status_code`** | ✅ | ✅ | ⛔ **전이 규칙이 DB에 없다** §5-5 |

**감사 컬럼·`version_no` 제외**(A-4). **`version_no`가 있으므로 B-1 낙관적 잠금 적용** — 이 화면은 **반드시** 적용해야 한다(§6).

### §4-B. 보류 건 `trace.lot_hold` (편집 — 해제 시)

| 라벨 | 출처 컬럼 | 필수 | 비고 |
| --- | --- | :-: | --- |
| 보류 수량 | `hold_qty` | — | **NULL = 전량** · `ck_lot_hold_qty_uom` 짝 제약(**A-2**) |
| 등록 사유 | `reason_code` | ✅ | 등록 시 입력됨 — 이 화면은 표시만 |
| 해제 조건 | `release_condition` | — | text |
| **해제자·해제 시각** | `released_by` · `released_at` | ✅ | `ck_lot_hold_release`(해제 ≥ 등록) |
| **해제 사유** | `releaseReasonCode` | `code_t` | ✅ 값 목록 `LOT_HOLD_RELEASE_REASON` §5-4 |
| 보류 건 상태 | `status_code` | ✅ | ⚠ **`lot.status_code`와 다른 축**(`W-03-01` §5-3) |

⛔ **`version_no`가 없다** — 기록 전용 구조라 **낙관적 잠금이 불가**하다. `lot`의 토큰으로 대표한다(`W-CO-06` §5-3과 같은 형태).

⭐ **원천은 `GET /quality/lot-holds?lotId=…&open=true` 재조회다** — 후보 목록(`GET /quality/lot-statuses`)의 요약 필드로 카드를 재정의하지 않는다(계약 변경 없음, 이미 있는 경로 재사용). **열린 보류가 여러 건이면 하나를 임의로 고르지 않고 전부 나열한다** — 시스템이 하나만 골라 보이면 화면에 안 뜬 다른 보류가 실제로는 안 풀린 채 숨는다. 근거: W-03-03 §5-5(중복 보류 허용) · omf-mes#225.

## §5. 액션·상태

### §5-1. 이 화면이 하는 전이는 **3건뿐**이다

전이 16건 중 상태 전이 9건의 소재를 갈랐다.

| 전이 | 라벨 | 어느 화면 |
| :-: | --- | --- |
| C4 ⊕ → Release | `합격` | **검사 판정 화면** — `W-01-01`(IQC) · `P-02-13`(PQC) · `W-04-03`(OQC) |
| C5 ⊕ → 보류 | `보류` | 동 |
| C6 ⊕ → Hold | `불합격` | 동 |
| C14 ⊕ → PQC 검사 필요 | `합격판정개수 초과` | 검사 판정 화면의 **서버 부수 효과** — 화면 액션 아님(계약 `:confirm` 설명) |
| **C7 보류 → Release** | `재판정 합격` | ✅ **이 화면** |
| **C8 보류 → Hold** | `재판정 불합격` | ✅ **이 화면** |
| **C9 Release → Hold** | `클레임·리콜·재판정` | ✅ **이 화면** |
| C10 의심자재등록 → 보류 | (트리거) | **`W-03-03`** |
| **C15**(구 「PQC 검사 필요 → Release」) | `전수 재검 양품` | ⚠ **미정** §8-3 — ⭐ E-3 종결(2026-08-07)로 「PQC 검사 필요」가 「검사 대기」에 통합돼(`W-06-04` §4 · 공유계약 v1.5) **좌표상 C7 과 같은 전이가 됐다.** 남은 물음은 「어느 «행위»가 그것을 하나」다 |
| C16 PQC 검사 필요 → 02-S-I | (경계 위임) | 화면 아님 — 02 도메인 |

**⊕(판정 허브)에서 나가는 4갈래는 이 화면이 하지 않는다.** 검사 결과를 낸 화면이 그 자리에서 상태를 정한다 — 판정과 전이를 갈라 놓으면 **검사자가 판정한 것과 다른 상태**가 될 수 있다.

**⚠ C15가 비어 있다.** 「전수 재검 양품」은 **검사 행위**(P-02-13)로 볼 수도, **재판정 전이**(이 화면)로 볼 수도 있다. 도식은 `화면없음:전이`로 뒀다. → §8-3.

### §5-2. ⭐ **B-3(이력 불변)을 지킬 수 없다**

B-3은 「이력 테이블은 갱신·삭제하지 않는다」다. **이 화면은 그것을 지킬 수단이 없다.**

```
UPDATE trace.lot SET status_code = 'RELEASE' WHERE lot_id = ...
                     ↑ 이전 값 '보류' 는 사라진다
```

**변경이력 테이블이 없으므로**(§I-11) **덮어쓰기가 유일한 저장 수단**이다.

**남는 것과 사라지는 것**:

| 전이 | 무엇이 남나 |
| :-: | --- |
| **C7** 보류 → Release | `lot_hold.released_by`·`released_at` ✅ · **왜 합격인지는 `remarks`로** ⚠ |
| **C8** 보류 → Hold | `released_at`만 ✅ — **Hold로 갔다는 사실이 안 남는다** ⛔ |
| **C9** Release → Hold | ⛔ **아무것도 안 남는다** — `lot_hold` INSERT로 담는다면? §5-6 |

> **결정 10이 이 화면을 만든 이유가 「감사」인데, 그 감사가 성립하지 않는다.** 「한도승인·특채는 **승인 행위 자체가 감사 대상**」이라 했다.

**A-11(구판 물러남 — 반영·통지 재검토 대상)** — 화면은 **전이할 때 `lot_hold`에 남길 수 있는 것을 최대한 남기고**, 남지 않는 전이(C9)는 **§8에 명시**한다. 있는 척 그리지 않는다.

→ **§I-11 보강** §9-1.

### §5-3. ⭐ **이 전이가 무엇을 막고 무엇을 푸는지** 화면이 먼저 말한다

결정 10: 「출고·출하·Picking **차단 판정은 이 단일 지점**」 · WF03 S5: 「**Release분만 출고/출하 가능**」.

**버튼 하나가 창고·출하의 가부를 바꾼다.** J-5(승인 화면은 「승인하면 무엇이 일어나는가」를 명시한다)의 **전이 화면 판**이다.

| 전이 | 무엇이 일어나나 | 표시 |
| :-: | --- | --- |
| → **Release** | **출고·출하·피킹이 풀린다** | ✅ 대상 수량·위치를 함께 보인다 |
| → **Hold** | **출고·출하·피킹이 막힌다** | ⛔ ⚠ **진행 중인 피킹이 있으면 함께 알린다** §6 |
| → 보류 | 막힌다(Hold와 같음) · **해제 조건이 붙는다** | `W-03-03` 소관 |

⚠ **되돌림 비용을 함께 적는다.** Release로 풀었다가 다시 막으려면 **C9 전이를 또 해야** 하고, 그 사이에 출고가 나가면 **되돌릴 수 없다**.

→ **§J 신규 조항 후보** §9-2.

### §5-4. ✅ 해제 사유를 코드로 되살렸다 — 등록·해제 대칭(2026-08-30)

```
trace.lot_hold
    reason_code          code_t NOT NULL   ← 등록 사유
    release_condition    text              ← 해제 「조건」(등록 시 적는 것)
    released_by/at                          ← 누가·언제 풀었나
    release_reason_code  code_t            ← 되살림 — 해제 사유
    remarks               text             ← 부가 비고
```

**`releaseReasonCode`로 C7(재판정 합격)과 C8(재판정 불합격)이 왜 갈렸는지를 가른다.** 등록·해제 비대칭이 해소됐다(「기록하라는데 자리가 없다」 7번째 — omf-mes#87 해소).

집계가 가능해졌다 — 「재판정으로 풀린 건이 몇 건인가」를 이 값으로 센다. 저장 컬럼은 데이터 모델 담당에게 통지한다, 기다리지 않는다.

### §5-5. 전이 규칙이 데이터에 없다 — **서버가 진다**

`lot.status_code`는 맨 `code_t`다. **「보류에서 Release로 갈 수 있는가」를 DB가 모른다.**

도식이 규칙을 갖고 있다(§1.3 상태별 수렴):

```
보류    수신 C5·C10   /  발신 C7·C8·C11
Release 수신 C4·C7·C15 / 발신 C9
Hold    수신 C6·C8·C9  /  발신 (없음)
PQC     수신 C14      /  발신 C15·C16
```

**⚠ Hold는 발신이 없다** — 도식상 Hold에서 나가는 전이가 **하나도 없다.** 「불합격 처리된 LOT은 Lot Status에서 더 움직이지 않는다」가 현재 설계다(불량은 02-S-I·S6으로 위임).

**G-8(선택 목록의 유효성 판정은 서버가 한다)** 적용:

| | |
| --- | --- |
| 화면 | 현재 상태에서 **갈 수 있는 곳만** 선택지로 받는다 |
| ⛔ 화면이 표를 갖지 않는다 | 전이 규칙이 바뀌면 화면 3벌(웹·POP·모바일)을 고쳐야 한다 |
| 서버 | 전이 가부를 판정하고, **거부 시 이유를 문구로** 준다(G-3) |

⚠ **Hold를 고른 LOT에는 선택지가 0개다.** 「이 LOT은 더 전이할 수 없습니다 — 불량 처리는 생산실행에서 합니다」로 안내한다(빈 드롭다운을 보이지 않는다).

### §5-6. 「보류」와 「Hold」가 다른 상태인데 **테이블은 하나**다

도식 §1.1은 둘을 **별개 상태 박스**로 갖는다 — `S-보류`(584:6759) · `S-HOLD`(585:6763).

```
trace.lot_hold  「LOT 보류: 특정 LOT(전량 또는 일부 수량) 사용 중지와 해제 이력」
```

**테이블 이름은 `hold`, 주석은 「보류」다.** 어느 쪽인지 판별되지 않는다.

| 해석 | 결과 |
| --- | --- |
| `lot_hold` = **보류(판정 보류)** 전용 | **C9(Release → Hold)를 담을 곳이 없다** |
| `lot_hold` = **사용 중지 전반**(보류 + Hold) | C9도 INSERT로 담긴다. **다만 `lot.status_code`로 둘을 갈라야** 한다 |

**후자를 채택한다** — 주석이 「사용 중지와 해제 이력」이라 넓게 읽힌다. **그러면 `lot_hold` 행 하나만 보고 「보류인지 Hold인지」를 알 수 없고, `lot.status_code`를 함께 봐야 한다.**

⚠ **`M-01-08` §5-2가 「미해제 `lot_hold` 행으로 Lot Status를 유추」했던 것이 여기서 위험해진다** — 그 유추로는 **보류와 Hold를 구분하지 못한다.** 둘 다 「막힘」이라 피킹 차단에는 문제가 없지만, **사유·해제 조건의 뜻이 다르다.**

→ **용어 사전 등재 후보** §9-4. **사전이 정확히 이런 것을 위해 있다.**

✅ **종결(2026-08-25 · omf-mes#227) — 후자(사용 중지 전반) 채택이 맞았고, `lot.status_code`로 가르는 값도 못박았다.** `targetLotStatusCode`(계약)가 전이별 도착값을 낸다 — 재판정 합격(C7)=`NORMAL` · 불합격(C8)=`DEFECTIVE` · 클레임·리콜 재Hold(C9)=`DEFECTIVE` · **의심자재 등록(C10)=`INSPECTION_PENDING`**. 「보류」는 `lot.status_code`의 값이 아니라 `lot_hold.status_code`(보류 «문서» 자체의 진행 상태)에서만 쓰는 말이다.

### §5-7. 부분 전이 — 수량이 갈리면 **LOT이 갈려야 하나**

`lot_hold.hold_qty`가 부분 보류를 허용한다(NULL = 전량).

**부분 해제를 어떻게 하나**:

| 안 | 문제 |
| :-: | --- |
| `hold_qty`를 줄인다 | ⛔ **B-3 위반** — 원래 얼마를 보류했는지 사라진다 |
| 새 `lot_hold` 행 | ⚠ 같은 LOT에 미해제 행이 여럿 — **합계를 화면이 계산**해야 한다 |
| **LOT 분할** | `trace.lot_relation`(`relation_type_code`)로 표현 가능하나 **업무가 커진다** |

**두 번째로 시작한다** — 원 행은 해제하고, 남은 수량으로 **새 보류 행**을 만든다. B-3을 지키면서 합계로 현재 보류량을 낸다.

⚠ **`inventory_balance.blocked_qty`와의 정합이 남는다.** 재고 잔액에도 보류 수량이 있어 **두 곳이 어긋날 수 있다.** 어느 쪽이 정본인지 규약이 없다 → §8-5.

## §9. 이 장에서 나온 공유 계약 후보

1. ⛔ **B-3(이력 불변)을 지킬 수 없는 화면은 그 사실을 상시 안내로 둔다** — 변경이력이 없어 `status_code` 덮어쓰기가 유일한 저장 수단이고, **C9(Release → Hold)는 아무 흔적도 남지 않는다.** 이런 화면은 **성공 토스트에 경고를 붙이지 않는다**(매번 붙으면 무시된다) — **화면 상단 상시 안내**로 둔다 (§5-2 · §6)
2. **상태 전이 화면은 「이 전이가 무엇을 막고 무엇을 푸는지」를 확정 전에 보인다** — 결정 10이 Lot Status를 **차단의 단일 지점**으로 만들어, 버튼 하나가 창고·출하의 가부를 바꾼다. **J-5(승인 화면은 「승인하면 무엇이 일어나는가」를 명시)의 전이 화면 판**이고, **되돌림 비용**(이미 나간 출고는 회수되지 않는다)을 함께 적는다 (§5-3)
3. ⚠ **이 교훈은 폐기됐다(2026-08-30)** — 「컬럼이 없어서 비대칭이다」는 원칙 위반이었다. `releaseReasonCode` 신설로 등록·해제 대칭을 되살렸다 (§5-4)
4. **한글 용어와 영문 컬럼이 1:1이 아니면 용어 사전에 올린다** — 도식은 `보류`와 `Hold`를 **별개 상태**로 갖는데 테이블은 `trace.lot_hold` 하나다. **행 하나만 보고 어느 쪽인지 알 수 없어 `lot.status_code`를 함께 봐야 한다.** `M-01-08`이 물러났던 「미해제 행으로 유추」가 이 지점에서 정확도를 잃는다. **사전이 이런 것을 위해 있다** (§5-6)
