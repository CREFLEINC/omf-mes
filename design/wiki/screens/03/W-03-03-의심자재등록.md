# W-03-03 · 의심자재 등록

> 작성일: 2026-08-06 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 결정 10이 「**전이 트리거**」라 부른 것을 화면으로 만든다. ⭐ **여기서 쓴 문장이 나중에 `W-03-02`의 판정 근거가 된다**(§5-4).

## §0. 요약

- **개요**: 품질담당이 관리웹에서 LOT(들)에 판정 보류를 거는 화면. `trace.lot_hold` 신규 등록과 `trace.lot.status_code` 갱신을 한 트랜잭션으로 처리하는 전이 트리거 화면이다(결정 10).
- **주요 데이터**: `trace.lot_hold`(신규) · `trace.lot`(읽기+상태 갱신) · `inventory.inventory_balance.blocked_qty`(화면은 직접 쓰지 않음).
- **핵심 액션**: 대상 LOT 조회·다중 선택 → 보류 범위(전량/일부)·사유·해제 조건 입력 → 보류 등록(B-8 트랜잭션, `lot.version_no` 낙관적 잠금 동봉).

## §4. 필드

### §4-A. 보류 `trace.lot_hold` (신규)

| 라벨(한/베) | 출처 컬럼 | 타입 | 필수 | 편집 | 검증·비고 |
| --- | --- | --- | :-: | :-: | --- |
| 대상 LOT | `lot_id` | bigint FK | ✅ | 신규만 | **①에서 고른다** |
| **보류 수량** | `hold_qty` | `qty_t` | — | ✅ | **NULL = 전량 보류** · **`ck_lot_hold_qty_uom`** §5-2 |
| 단위 | `uom_id` | bigint FK | 조건부 | ✅ | ⛔ **`hold_qty`와 짝** — 하나만 넣으면 CHECK 위반 |
| **사유** | `reason_code` | `code_t` | ✅ **NOT NULL** | ✅ | `INCOMING_INSPECTION_WAIT`(수입검사 대기) · `FOREIGN_MATTER_SUSPECTED`(이물 혼입 의심) · `DIMENSION_ABNORMAL`(치수 이상) · `APPEARANCE_ABNORMAL`(외관 이상) · `CLAIM_RECALL`(클레임·리콜) · `OTHER`(기타) **6값** — 값 목록은 `GET /mdm/code-values?codeGroupCode=LOT_HOLD_REASON` 로 받는다(공유계약 `G-32` · 코드 사전 `CD-LOT-HOLD-REASON` · `omf-mes#198`). ⭐ **고객이 늘린다 — 위 여섯은 초기 시드다**(`registry`). ⚠ 채번 식별자(`codeGroupId`)를 하드코딩하지 않는다 |
| **해제 조건** | `release_condition` | text | — | ✅ | ⚠ **화면이 필수로 만든다** §5-4 |
| 보류 건 상태 | `status_code` | `code_t` | ✅ | ⛔ | **서버가 「보류 중」으로 넣는다** |
| 등록자·등록 시각 | `held_by` · `held_at` | bigint FK · timestamptz | ✅ | ⛔ | `app_user` — **관리웹이라 계정 인증**(F-2) |
| 비고 | `remarks` | text | — | ✅ | |

**해제 컬럼**(`released_by`·`released_at`)은 **이 화면이 쓰지 않는다** — `W-03-02` 소관.

⛔ **`version_no`가 없다** — 기록 전용. 이 화면은 INSERT만 하므로 B-1이 걸리지 않는다. **다만 대상 LOT의 `lot.version_no`는 필요하다**(§5-1).

### §4-B. 대상 LOT `trace.lot` (읽기 + `status_code` 갱신)

| 라벨 | 출처 컬럼 | 비고 |
| --- | --- | --- |
| LOT 번호 · 품목 · 보유 수량 | `lot_no` · `item_id` · `initial_qty` | 표시 |
| **Lot Status** | `status_code` | **이 화면이 `INSPECTION_PENDING`(검사 대기)으로 바꾼다** — B-8 한 트랜잭션(§5-1). ⚠ **「보류」는 이 축의 값이 아니다** — `lot.status_code`는 4값(`NORMAL`·`DEFECTIVE`·`INSPECTION_PENDING`·`SCRAPPED`)뿐이고 「보류(Hold)」는 `lot_hold.status_code`(§4-A) 가 별도로 갖는다(공유계약 §I-32 · omf-mes#227). |

⚠ **「자재 종류」는 입력 필드가 아니다.** REQ-PR-0027 원문이 「수량·**자재 종류** 등 입력」이라 했으나, **LOT을 고르면 품목이 따라온다**(`lot.item_id`). 따로 받으면 어긋날 수 있다.

## §5. 액션·상태

### §5-1. B-8 — **두 테이블이 한 트랜잭션이다**

결정 10: 「의심자재등록 = 판정 보류를 만드는 **트랜잭션** … Lot Status = **결과 상태**(상태 이중 보유 없음)」

```
BEGIN
  INSERT trace.lot_hold  (lot_id, hold_qty, reason_code, release_condition, held_by, held_at, status_code)
  UPDATE trace.lot SET status_code = 'INSPECTION_PENDING' WHERE lot_id = ... AND version_no = <토큰>
COMMIT
```

**둘 중 하나만 되면 안 된다** — `lot_hold`만 들어가면 **재고가 안 막히고**, `lot.status_code`만 바뀌면 **왜 막혔는지가 없다.**

**B-8 적용**(트랜잭션 경계 — 외부 호출은 밖):

| 안 | 밖 |
| --- | --- |
| `lot_hold` INSERT · `lot.status_code` UPDATE | ⚠ **알림 발송**(불량 발생 알람 — `W-CO-03`·SNS · QA #24) |

⚠ **`inventory_balance.blocked_qty`는 어느 쪽인가**가 미정이다(§5-6).

**B-1 토큰**: `lot.version_no`를 동봉한다. **여러 LOT을 고르면 토큰도 여럿**이고, **하나라도 어긋나면 전체를 거부**한다(§6).

### §5-2. A-2 — 짝 제약을 화면이 구조로 표현한다

```
CONSTRAINT ck_lot_hold_qty_uom CHECK ((hold_qty IS NULL) = (uom_id IS NULL))
```

**수량과 단위는 함께 있거나 함께 없다.** 「전량 보류」는 **둘 다 NULL**이다.

**A-2(조건부 필수·짝 제약의 표시)**를 라디오 구조로 낸다:

```
범위   (•) 전량           ← hold_qty = NULL · uom_id = NULL
       ( ) 일부 수량  [  500  ] [ EA ▾ ]   ← 둘 다 채운다
```

**단위를 따로 비울 수 없게** 만든다 — 수량 입력이 열리면 단위도 함께 열리고, 단위 기본값은 **LOT의 `uom_id`**로 채운다.

⚠ **「전량」과 「보유 수량 전부를 숫자로 입력」은 다르다.** 전자는 NULL이라 **이후 입고분까지 막히고**, 후자는 그 수량만 막힌다. **화면이 이 차이를 문구로 밝힌다**:

```
(•) 전량   ⓘ 지금 수량뿐 아니라 이 LOT 전체가 막힙니다
```

### §5-3. 여러 LOT 일괄 등록 — **전량만 허용한다**

클레임·리콜은 LOT 하나로 끝나지 않는다. 목록에서 **여러 건을 고를 수 있게** 한다.

**⛔ 그런데 수량은 LOT마다 다르다.** 「일부 500」을 5개 LOT에 똑같이 적용하면 의미가 없다.

| 선택 | 범위 |
| --- | --- |
| 1건 | 전량 · **일부 수량 가능** |
| **2건 이상** | **전량만** — 수량 입력을 잠근다 |

⚠ **`trace.impact_analysis`가 있는데 쓰지 않는다.** 리콜 시 영향 LOT을 분석해 스냅샷을 남기는 테이블(`affected_lot_count`·`result_summary jsonb`)이 실재하지만, **분석 결과로 보류를 거는 경로가 없다**(FK도 없다). 지금은 **사람이 목록에서 고른다.** → §8-4.

### §5-4. ⭐ 해제 조건은 **나중에 판정 근거가 된다** — 화면이 형식을 유도한다

```
release_condition  text        ← 자유 문장
```

**`W-03-02`가 「풀어도 되는가」를 판단할 때 보는 것이 이 문장이다.** 지금 대충 적으면 **나중에 다른 사람이 판단할 수 없다.**

**G-3(비활성 사유는 「왜」가 아니라 「어떻게 풀 것인가」)의 입력 쪽 판**이다 — 그쪽은 화면이 문구를 쓰고, 여기서는 **사람이 쓴다.**

**화면이 형식을 유도한다**(강제하지 않는다 — text라 검증할 수 없다):

```
해제 조건 *
┌────────────────────────────────────────────┐
│ 재검사 3점 전항목 합격 시 해제              │
└────────────────────────────────────────────┘
ⓘ 누가 · 무엇을 확인하면 풀리는지 적어 주세요
   예) IQC 재검사 합격 시 / 공급사 회신 도착 후 품질담당 확인 시
```

**⚠ DB는 nullable인데 화면이 필수로 만든다.** A-9 ⓑ(화면이 막는다) 등급이다. **근거**: 이 문장이 없으면 보류가 **영구히 안 풀린다** — 아무도 조건을 모르므로 아무도 못 푼다.

→ **§A 신규 조항 후보** §9-2.

### §5-5. ⛔ 중복 보류를 막는 제약이 없다 — **화면이 진다**

`trace.lot_hold`에 **UNIQUE 제약이 없다.** 같은 LOT에 미해제 보류가 **여러 건** 들어갈 수 있다.

**부분 보류가 있으므로 그것이 맞다** — 「이물 500」과 「치수 300」이 따로 걸릴 수 있다.

**⛔ 그러나 전량 보류가 이미 있으면 다르다.**

| 기존 | 새 등록 | 판정 |
| --- | --- | --- |
| 전량 보류(미해제) | 아무거나 | ⛔ **막는다** — 이미 전부 막혀 있다 |
| 부분 500(미해제) | 부분 300 | ✅ 허용 — 합계 800 |
| 부분 500(미해제) | 부분 3,800 | ⛔ **보유 4,000 초과** |
| 해제된 보류만 있음 | 아무거나 | ✅ 허용 |

**A-9 ⓑ 등급** — DB가 막지 않으므로 **서버가 판정하고 화면이 문구를 보인다**(화면이 계산하지 않는다).

⚠ **동시 등록 경합이 남는다.** 두 사람이 같은 LOT에 동시에 걸면 합계가 넘을 수 있다. **`lot.version_no` 토큰이 그것을 막는다**(§5-1) — 한 트랜잭션 안에서 `lot`을 갱신하므로 뒤엣것이 충돌한다.

### §5-6. `blocked_qty` 정합 — **이 화면은 건드리지 않는다**

`inventory.inventory_balance.blocked_qty`가 보류 수량을 갖고 있고, `available_qty`는 **GENERATED STORED**다(`W-01-07` §4-A).

**이 화면이 `blocked_qty`를 직접 쓰면 두 곳이 정본을 다툰다.**

**규칙**: **쓰지 않는다.** `lot_hold`가 정본이고 잔액은 **서버가 파생**한다(L-2 — 파생은 서버 계산).

⚠ **파생 시점이 규약이 없다** — 트랜잭션 안에서 즉시인지, 배치인지. 즉시가 아니면 **등록 직후 화면에서 「막혔다」와 재고 조회의 「가용」이 어긋난다.** → §8-3.

### §5-7. LOT이 없는 의심 자재는 담을 수 없다

REQ-PR-0027이 「의심 자재(**반제품**·판정 보류)」라 했다. 반제품도 LOT을 갖는다(`lot_type_code`).

**⛔ 그런데 「이 선반의 물건이 의심스럽다」는 담을 수 없다.** `lot_hold.lot_id`가 **NOT NULL**이다.

| 상황 | 담기나 |
| --- | :-: |
| LOT이 붙은 자재·반제품·제품 | ✅ |
| **LOT 표식이 떨어진 물건** | ⛔ |
| **위치 단위 보류**(「A-01 구역 전체」) | ⛔ |

**현장에서 실제로 일어나는 일**이지만 **지금 설계에 자리가 없다.** 화면은 **LOT을 먼저 특정하라고 안내**한다. ⚠ 이것은 **설계 자신의 결손**이지 모델 결손이 아니다 — 되살리기 잔여로 §8 에 남긴다.

⚠ 「없어야 정상인가 없어서 문제인가」를 아직 가르지 못했다 — **위치 단위 보류가 업무상 필요한지 확인이 먼저다.** → §8-5.

## §9. 이 장에서 나온 공유 계약 후보

1. **「트리거 화면」은 트랜잭션과 결과 상태를 한 트랜잭션으로 쓴다** — 결정 10이 「상태 이중 보유 없음」이라 했으므로 `lot_hold` INSERT와 `lot.status_code` UPDATE는 **갈라질 수 없다.** 하나만 되면 **재고가 안 막히거나 이유가 없다.** B-8의 「안/밖」에 이 형태를 예시로 넣고, **파생 잔액(`blocked_qty`)은 서버가 계산하되 시점을 계약이 정한다**(L-2 보강) (§5-1 · §5-6)
2. **나중에 남이 읽고 판단할 자유 텍스트는 화면이 필수로 만들고 형식을 유도한다** — `release_condition`은 DB에서 nullable인데 **비면 보류가 영구히 안 풀린다**(아무도 조건을 모르므로). **A-9 ⓑ 등급으로 화면이 막고**, 「누가·무엇을 확인하면 풀리는지」를 예시로 유도한다. G-3(비활성 사유는 「어떻게 풀 것인가」)의 **입력 쪽 판**이다 (§5-4)
3. **부분 수량을 받는 테이블에 UNIQUE가 없으면 「전량 행의 존재」가 사실상의 유일 제약이다** — `lot_hold`는 중복을 막지 않는데 **그게 맞다**(부분 보류가 여럿일 수 있다). 다만 **전량 보류(`hold_qty` IS NULL) 행이 있으면 더 걸 수 없고**, 부분끼리는 **합계가 보유를 넘지 않아야** 한다. **서버가 판정하고 화면은 문구만 보인다** (§5-5)
4. **일괄 처리에서 「수량」과 「건수」는 함께 열리지 않는다** — 여러 LOT을 한 번에 보류할 때 수량 입력은 의미를 잃는다(LOT마다 다르다). **2건 이상이면 전량만** 허용한다. 일괄 액션을 가진 전 화면에 적용된다 (§5-3)
