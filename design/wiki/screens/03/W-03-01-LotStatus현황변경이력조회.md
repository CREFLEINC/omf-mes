# W-03-01 · Lot Status 현황·변경이력 조회

> 작성일: 2026-08-06 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ⭐ **§I-11을 정면으로 만나는 첫 화면.** 01·02에서는 대장에만 있던 결손이 **여기서는 화면 주제 자체**다.

## §0. 요약

- **개요**: 관리웹에서 품질담당·물류담당(+품질책임자의 감사 조회)이 LOT의 현재 Lot Status를 「LOT으로 찾기」로 조회하고, 「이력으로 찾기」로 변경이력을 검색하는 화면. N6(현재 1행)과 N7(변경이력 1:N)을 한 화면에 통합했고, 구 `W-03-04`(변경이력 조회)를 흡수했다.
- **주요 데이터**: LOT 현재 상태 `trace.lot.status_code`(현재 1값만 저장) · 변경이력 `GET /trace/lot-status-events`(전용 이력 — 2026-08-30 신설, 전이 9종 전건). 저장 테이블은 데이터 모델 담당에게 통지 — 기다리지 않는다.
- **핵심 액션**: LOT 조회(상태·품목·창고 필터) · 이력 조회(기간 필수 + 판정유형·행위자) · LOT 선택 → 드로어에서 보류 이력 확인 → 「판정·전이 처리 →」로 `W-03-02` 이동.

## §5. 액션·상태

### §5-1. ✅ 요건 ①을 되살렸다 — **전용 이력으로 전이 9건 전건을 담는다**(2026-08-30)

도식이 요구하는 것은 명확하다:

```
공통 범례 (595:6841)   「모든 전이 = 변경이력 기록 → N6·N7」
결정 10                「현재 1행 + 변경이력 1:N」
전이 16개 중 상태 전이 = C4·C5·C6·C7·C8·C9·C10·C14·C15  (9건)
```

**실측: `trace` 7테이블에 변경이력이 없다.** `previous_status`·`status_history`·`_log` 류 검색 **0건**.

**전이 9건 중 무엇이 남는지 대조했다.**

| 전이 | 라벨 | `lot_hold`에 남나 |
| :-: | --- | :-: |
| C5 ⊕ → 보류 | `보류` | ✅ INSERT |
| C10 의심자재등록 → 보류 | (트리거) | ✅ INSERT — `W-03-03` |
| C7 보류 → Release | `재판정 합격` | ⚠ **해제 시각만** — 「합격이라서」가 안 남는다 |
| C8 보류 → Hold | `재판정 불합격` | ⚠ **해제로만 보인다** — Hold로 갔다는 사실이 안 남는다 |
| C4 ⊕ → Release | `합격` | ⛔ **안 남는다** |
| C6 ⊕ → Hold | `불합격` | ⛔ **안 남는다** |
| C9 Release → Hold | `클레임·리콜·재판정` | ⛔ **안 남는다** |
| C14 ⊕ → PQC 검사 필요 | `합격판정개수 초과` | ⛔ **안 남는다** |
| C15 PQC 검사 필요 → Release | `전수 재검 양품` | ⛔ **안 남는다** |

**되살렸다** — `GET /trace/lot-status-events`가 9건 전건을 `transitionCode`(C4~C15)로 담는다. 결정 10이 요구한 대로 「한도승인·특채는 승인 행위 자체가 감사 대상」을 충족한다.

화면은 확정대로 온전히 그린다(A-11) — 저장 테이블은 데이터 모델 담당에게 통지한다, 기다리지 않는다.

### §5-2. ⭐ §I-11과 §I-5는 **같은 문제의 두 얼굴**이다

이력을 담을 후보가 하나 더 있다 — **`audit.audit_event`**.

```
occurred_at        timestamptz NOT NULL       ← 요건 ①의 「기간」
target_type_code   code_t                     ← 'LOT'
target_id          bigint                     ← ⚠ 비-FK (§I-5)
event_type_code    code_t                     ← 'STATUS_CHANGE'
before_value       jsonb                      ← 이전 상태
after_value        jsonb                      ← ⚠ 「판정유형」이 여기 들어간다
performed_by       bigint                     ← 요건 ①의 「행위자」
reason             text                       ← 전이 사유
) PARTITION BY RANGE (occurred_at)
```

**요건 ①의 세 축(기간·판정유형·행위자)이 전부 있다.** 컬럼은 이미 맞는다.

**⛔ 그런데 쓸 수 없다** — §I-5가 정확히 이것을 막고 있다:

| 막는 것 | 이 화면에 무엇이 일어나나 |
| --- | --- |
| `target_id`가 **비-FK** | LOT이 삭제·병합돼도 이력이 고아로 남는다. 조인 무결성 없음 |
| `before/after` **jsonb 키 규약 없음** | **판정유형으로 검색할 수 없다** — 키 이름을 모르면 질의를 못 짠다 |
| **아직 아무도 쓰지 않는다** | 설계검토 §6-②가 확인 — 「이 저장소에서 아직 아무도 쓰지 않아, 여기서 시작하면 **이벤트 코드 체계와 기록 범위를 먼저 정해야** 해 범위가 번진다」 |

> ⚠ **정정(2026-08-30)** — §I-11은 전용 테이블 신설로 되살려 §I-5(`audit_event` 규약)와 더는 묶이지 않는다. `audit_event` 규약 정비는 별건으로 진행한다.
>
> 지금까지 **#64**(확정 미착지 8건 — 11번 포함)와 **#68**(`audit_event` 규약)로 **다른 이슈**에 들어가 있었다. 그런데 **먼저 정해야 하는 것은 「Lot Status 이력을 어디에 담는가」 하나**다:

| 안 | 결과 |
| :-: | --- |
| **A. 전용 테이블**(`trace.lot_status_history`) | **결정 10의 문언 그대로**(「1:N 신설」) · 판정유형이 컬럼이라 인덱스·검색이 곧바로 성립 · `audit_event`와 무관하게 진행 가능 |
| **B. `audit_event` 규약** | 테이블 신설 없음 · **그러나 jsonb 키 규약·이벤트 코드 체계를 먼저 정해야 하고 그 범위가 전 마스터로 번진다** · 판정유형 인덱스가 어렵다 |

**A를 권고한다** — 결정 10이 이미 「신설」이라 못박았고, B는 **이 화면 하나를 위해 전사 감사 규약을 먼저 세우는 순서**가 된다.

→ **§I-11 갱신 · 이슈 코멘트** §9-1. **#64와 #68 양쪽에 「선후 관계」를 적는다.**

### §5-3. `lot.status_code`와 `lot_hold.status_code`는 **다른 축**이다

이름이 같아 섞기 쉽다.

| | `trace.lot.status_code` | `trace.lot_hold.status_code` |
| --- | --- | --- |
| 무엇 | **Lot Status**(품질 판정) — 정상 / 불량 / 검사 대기 / 폐기 | **보류 건의 진행 상태** — 보류 중 / 해제됨 |
| 개수 | LOT당 1 | LOT당 **N**(해제된 것 + 진행 중) |

**결정 10의 상태 3축 분리**(①수명주기=LOT 속성 ②품질 판정=Lot Status ③작업 홀드=작업홀드이력)에 **넷째로 끼어드는 것이 아니다** — `lot_hold.status_code`는 **보류라는 업무 문서의 상태**다.

**규칙**: 화면은 **「상태」라는 낱말을 두 곳에 쓰지 않는다.**

```
현재 상태   검사 대기        ← lot.status_code
보류 건     진행 중 (1건)   ← lot_hold.status_code
```

⚠ **`M-01-08` §5-2가 「`lot_hold` 미해제 행으로 Lot Status를 유추한다」고 물러났던 것**과 이어진다. 그 유추가 성립하려면 **둘의 관계가 규약으로 고정**돼야 한다 — 지금은 화면마다 다르게 유추할 수 있다.

→ **§I 신규 후보** §9-2.

### §5-4. 미확정 3상태는 **셀 수도 없다**

도식 §1.1이 명시한다 — 한도승인·특채·폐기는 **별표 표기 + 배선 0**. 실측 `attachedConnectors`=0.

~~**요약 카드에 이 셋을 넣을 수 없다.**~~ ✅ **해소 2026-08-07** — **✅ 회신 E-3 종결(2026-08-07)** — LOT 상태 4값(`정상`·`불량`·`검사 대기`·`폐기`) 확정. 요약 카드는 **4값 전건**을 센다. 한도승인·특채는 **값이 아니라 조건**이므로 카드가 아니라 상세에서 승인 기록으로 보인다.

```
│  ⓘ 대기   │      ← 「0」이 아니다. 0이면 「없다」로 읽힌다
└───────────┘
   (구 문구 폐기 — 4값 확정으로 대기 안내 불요)
```

⚠ **「0」으로 쓰지 않는다.** G-4(「필수」·「비연계」는 기본값이 아니라 구조로 표현한다)와 같은 이유다 — **모르는 것과 없는 것을 같은 모양으로 그리면 안 된다.**

### §5-5. 요건 ② 권한 분리 — **감사 조회는 범위를 제한할 수 있어야 한다**

인벤토리가 「감사 조회는 품질책임자 범위로 제한할 수 있어야 한다(`W-CO-02`의 `user_data_scope` 활용)」를 통합 조건으로 달았다.

**`app.user_data_scope`는 실재한다** — `business_unit_id` · `plant_id` · `ck_user_data_scope_target`(둘 중 하나는 NOT NULL).

| 축 | 성립 |
| --- | :-: |
| 사업부·공장 범위 제한 | ✅ **성립한다** |
| **법인 범위** | ⛔ **§I-4** — `legal_entity_id` 없음 |
| **「이력 검색 모드만 품질책임자」** | ⚠ **기능 권한**(`role_permission.permission_code`)이라 다른 축 — **값 목록이 회신 E-9 대기**(F-3) |

**F-2 두 축이 여기서 함께 걸린다** — 데이터 범위는 `user_data_scope`, 기능 권한은 `role_permission`이다. **섞지 않는다.**

**지금 할 수 있는 것**: 데이터 범위 제한은 **적용한다**. 「이력 검색 탭 자체를 감춘다」는 **권한 값 목록 확정 후**로 미룬다(G-2 — 화면은 만들되 비활성).

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **「이력이 없다」와 「감사 규약이 없다」가 한 문제일 때는 선후를 먼저 정한다** — §I-11(Lot Status 변경이력 1:N 신설)과 §I-5(`audit_event` 사용 규약)가 **다른 이슈(#64·#68)에 나뉘어 있는데 따로 풀 수 없다.** 먼저 답할 것은 **「전용 테이블인가 `audit_event`인가」** 하나다. 결정 10이 「신설」이라 못박았으므로 **전용 테이블을 권고**한다 — `audit_event`로 가면 **이 화면 하나를 위해 전사 감사 규약을 먼저 세우는 순서**가 된다 (§5-2)
2. **같은 이름의 `status_code`가 여러 층에 있으면 계약이 층을 지정한다** — `trace.lot.status_code`(Lot Status · LOT당 1)와 `trace.lot_hold.status_code`(보류 건의 진행 상태 · LOT당 N)는 **다른 축**인데 이름이 같다. `M-01-08`이 「미해제 `lot_hold` 행으로 Lot Status를 유추」한다고 물러났는데, **그 유추가 성립하려면 관계가 규약으로 고정**돼야 한다. 화면은 「상태」라는 낱말을 두 곳에 쓰지 않는다 (§5-3)
3. **모르는 값과 없는 값을 같은 모양으로 그리지 않는다** — 미확정 3상태를 「0」으로 쓰면 「그런 LOT이 없다」로 읽힌다. **「ⓘ 대기」로 쓴다.** G-4(「필수」·「비연계」는 구조로)의 조회 화면 판이고, **L-8(판정 불가 ≠ 정상)의 요약 카드 적용**이다 (§5-4)
4. ⚠ **이 교훈은 폐기됐다(2026-08-30)** — 전용 이력 신설로 9건 전건을 되살려 「무엇이 안 보이는지」를 적을 필요 자체가 없어졌다(§3 · §5-1)
