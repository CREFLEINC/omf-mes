# `W-03-10` 처분 판정 처리(재작업/폐기/정상)

> ⭐ **DR-008 확정 3-A 로 신설된 화면**(2026-08-13). 인벤토리 **116 → 117**.
>
> **왜 없었나** — `F04` 정합 확정(2026-07-07)이 「재작업/폐기 **판정**은 전 도메인에서 **03 소관** 통일」이라 했는데 **03 의 다섯 화면에 그 화면이 만들어지지 않았다.** 03 요구서는 `disposition_decision` 을 「04 것」이라 넘겼고, `W-04-07` 은 「03 이 만든다 · 04 는 의뢰만」이라 적었다 — **서로에게 미뤘다.**
>
> 04 계약 트랙 1단계에서 **116화면 액션을 전수로 뽑아** 처분을 저장하는 화면이 **0건**임을 확인했다.

## §0. 요약

- **개요**: 관리웹에서 품질담당·품질책임자가 부적합의 처분(재작업/폐기/정상)을 승인 없이 판정·저장하는 화면이다(2026-09-08 사용자 확정).
- **주요 데이터**: `quality.nonconformance`·`quality.nonconformance_lot`(부적합·대상 LOT, 읽기) · `quality.disposition_decision`(처분 판정 — `decision_qty`·`reason`·`decided_by` 모두 NOT NULL, 신설 0). 판정 저장과 `trace.lot.status_code` 전이는 한 트랜잭션이다(공유계약 B-8).
- **핵심 액션**: 판정 대기 목록 조회 → 부적합 선택 → 처분·남은 수량 이하 수량·사유 입력 → 판정 저장·확정. 처분 판정의 승인 상신·승인·반려는 없다. 폐기 실행 단계 승인은 별개로 유지한다.

### §2-1. ⭐ 데이터가 「사람이 화면에서 정한다」를 말하고 있었다

```sql
quality.disposition_decision
    nonconformance_id      NOT NULL   ← 부적합이 선행한다
    disposition_type_code  NOT NULL   ← 재작업 · 폐기 · 정상
    decision_qty           NOT NULL CHECK (> 0)   ⭐ 부분 처분이 된다
    uom_id                 NOT NULL
    reason                 text NOT NULL          ⭐ 사람이 쓴다
    decided_by             NOT NULL → app.app_user  ⭐ 사람이 정한다
    decided_at             NOT NULL
    approval_request_id                            ← 과거 참조 호환용. 신규 처분 판정의 승인 요청 없음
```

⭐ **처분 판정은 사람이 사유를 적고 판정자를 남기는 업무다** — `DR-008` 확정 3-A 가 이 화면을 신설한 이유가 그것이다. 자동 판정이 아니다. ⚠ **물리 제약(`decided_by`·`reason` 의 `NOT NULL`)이 그 업무와 일치하는 것은 방증이지 근거가 아니다**(`schema/data-model-boundary.md` — 모델의 제약으로 화면의 필수를 정하지 않는다). ⭐ **다만 발견 경로로는 유용했다** — `M-01-13` 때와 같은 형태로, 「이 칸을 누가 채우나」를 사람으로 답해 보니 **앞단계 화면이 빠져 있었다**(공유계약 **A-24**).

⭐ **②의 「남은 수량」이 이 화면의 핵심이다** — 부적합 하나를 **수량으로 갈라** 일부는 재작업, 일부는 폐기로 정할 수 있다(`decision_qty`). 남은 수량이 0 이 되면 판정이 끝난다.

⛔ 다만 현재 서버의 LOT 전이는 판정 수량을 LOT별로 배분하지 않는다. 판정 한 건을 저장할 때마다
연결된 **모든 LOT에** 그 판정 유형의 상태 전이를 시도하고, 출발 상태가 맞지 않는 LOT는 건너뛸 수
있다. 여러 번 부분 판정하면 마지막 판정의 상태가 앞선 판정 상태를 덮을 수 있다. 화면은 저장 전에 대상 LOT 전건과 전이 예정 상태를 확인시키고 이
한계를 숨기지 않는다. 수량별·LOT별 상태 보존과 전건 원자 전이는 §8-10의 미지원 요구로 남긴다.

| 사유 / *(미정)* | `disposition_decision.reason` | `text` | ✅ | **화면이 필수로 만든다** — 남이 읽고 판단할 자유 텍스트다(공유계약 **A-12**). 공백만 불가 |

⛔ **`decided_by`·`decided_at` 은 화면에 없다** — 서버가 인증 주체와 수신 시각으로 채운다(공유계약 **B-6**).

`qualityStatusBeforeCode`·`qualityStatusAfterCode`는 각각 **부적합 등록 전·등록 후 스냅샷**이다.
현재 구현은 두 값 모두 등록 당시 LOT 상태를 저장하며 처분 판정 뒤 갱신하지 않는다. 따라서
`qualityStatusAfterCode`를 「판정 후」로 표시하지 않는다. 판정 결과는 판정 이력과 현재 LOT 상태를
각각 보여 주며, 둘이 수량별로 대응한다고 추정하지 않는다.

저장 직전 확인에는 처분·수량·단위·사유와 대상 LOT 전건, **전건에 시도할 현재 전이와 건너뛸 수
있는 불일치 LOT**를 표시한다. `SCRAP`(폐기)이면 `SCRAPPED`(폐기)에서 나오는 전이가 없어 되돌릴 수 없음을 별도 경고한다. 이 확인은
현재 서버의 전체 LOT 전이를 사용자에게 드러내는 안전장치이지 수량별 상태 보존을 구현하지 않는다.

### §5-2. ⭐ 판정 저장과 Lot Status 전이는 **한 트랜잭션**이다

```
disposition_decision INSERT
        +
trace.lot.status_code UPDATE      ← 재작업 → 검사 대기 / 폐기 → 폐기 / 정상 → 정상
```

**공유계약 B-8**(§5-2)**.** 처분만 남고 LOT 이 안 바뀌면 **다음 화면이 잘못된 대상을 집는다** — `W-04-11`(재등록)이 아직 불량인 LOT 을 정상으로 본다.

LOT 상태 이력에는 `C17`(처분 재작업), `C18`(처분 폐기), `C19`(처분 정상)가 남는다. 원천 유형은
`DISPOSITION_DECISION`(처분 판정), 원천 식별자는 저장된 처분 판정 ID다. 화면이 별도 이력 API나 전이를 만들지 않는다.

### §5-4. ⛔ 이 화면은 **부적합을 만들지 않는다**

부적합 등록·판정 의뢰는 **`W-04-07`**(04)이 한다. **소유가 갈린다** — 공유계약 **B-13**.

| 테이블 | 쓰는 화면 | 계약 |
| --- | --- | --- |
| `nonconformance` · `_lot` | `W-04-07` (04) | **제품출하** |
| ⭐ `disposition_decision` | **`W-03-10`** (03) | **품질** |

⭐ **2026-09-01 정정** — 부적합을 만드는 화면은 **`W-04-07` 하나**다(요구서 §3-6 · 2026-08-29 확정). `W-04-06` 반품 입고는 입고 전표만 만들고 부적합은 만들지 않는다. **원천 축이 사라지는 것은 아니다** — 반품으로 들어온 LOT 에 대해 `W-04-07` 이 만든 건이 `RETURN` 이고, 그 판정은 **서버가 입고 유형으로 파생**한다(`omf-mes#303`).

**정정(2026-08-30)** — 04 제품과 04 반품이 **같은 경로·같은 스키마**로 들어와 서로 가를 근거가 없던 것은 `nonconformance`에 원천 열이 없었기 때문이다. `sourceCode`(`PRODUCT`/`RETURN`)를 명시 축으로 신설해 되살린다. 02 수리·01 자재는 애초에 이 경로로 안 들어오므로(§5-4 정정) 이 축의 대상이 아니다 — 별개 사실이다.

⇒ ⭐ **① 에 원천 필터(제품/반품)를 둔다.** ⭐ **저장 컬럼이 아니다** — 서버 파생이라 데이터 모델 대기 사항이 없다.

### §5-5. ⭐ 잔량은 **보이되 막지 않는다** — 화면과 서버의 몫이 다르다

| 무엇 | 누가 | 근거 |
| --- | :-: | --- |
| 남은 수량을 **낸다** | **서버** | `GET …/disposition-decisions` 응답의 `summary.remainingQty`. 화면이 대상 합에서 결정 합을 빼지 않는다(**L-2**) |
| 남은 수량을 **보인다** | 화면 | ② 구획 Chip |
| 초과 입력을 **알린다** | 화면 | ⚠ 경고 — 「남은 수량은 저장할 때 서버가 확정합니다」 |
| 초과를 **거절한다** | **서버** | ⛔ **409** `DISPOSITION_QTY_EXCEEDED` + `remainingQty` (§6) |

⛔ **저장 단추를 잔량으로 잠그지 않는다.** 잔량은 **읽은 시점의 값**이라 두 사람이 같은 부적합을
동시에 판정하면 둘 다 화면을 통과하고 서버에서 하나가 떨어진다. **`W-03-03` §5-5 가 「부분 보류
합계 초과」로 이미 겪은 것과 같은 모양**이고, 공유계약 **A-9** 가 이런 합계 검증을 **ⓑ 경고**
(저장은 되나 확인 요구)로 등급 지었다 — ⓐ 차단이 아니다.

⭐ **잔량 필드가 내려온 뒤에도 이 규칙은 그대로다.** 서버가 값을 준다는 것과 화면이 판정한다는 것은
다르다.

⭐ **동시 판정을 실제로 잡는 것은 저장 충돌 토큰이다.** 판정 저장은 `If-Match` 를 **필수로** 받고,
그 값은 **부적합 상세**(`GET /quality/nonconformances/{nonconformanceId}`)의 `ETag` 를 그대로 담는다
— 잠그는 대상이 처분 결정 한 건이 아니라 **부적합**이기 때문이다(잔량이 부적합 단위로 정해진다).
⚠ 그러려면 판정 저장이 `nonconformance.version_no` 를 올려야 한다 — **§8 미결 8**.

⚠ **`status_code` 로는 판정 진행을 못 가른다.**

| 화면이 보이려는 것 | 잔량으로 본 조건 | `status_code` |
| --- | --- | --- |
| **미판정** | 결정 0건 | **판정 대기** |
| **⚠ 일부 판정** | 결정 1건 이상 · 잔량 > 0 | **판정 대기** ← 같다 |
| 완료 | 잔량 0 | 판정 완료 |

그래서 §4-A 의 「판정 진행」은 `status_code` 가 아니라 **`disposition_progress_code`** 파생을 쓴다.
