# M-04-03 · 포장 재구성 스캔

> 작성일: 2026-08-07 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)

> ✅ **결정 13 「이벤트 헤더–라인 계보」를 되살렸다**(2026-08-30) — `HandlingUnitRepackEvent`(+Line) 신설.

## §0. 요약

- **개요**: 완제품창고담당이 모바일(PDA)에서 원 포장을 스캔해 재구성 유형(합병·분할·재구성)을 고르고 새 구성을 편집하는 스캔형 화면이다. 04 에서 유일한 2단말 스택으로, 발번·라벨 인쇄는 이 화면이 아니라 POP(`P-04-04`)에서 한다.
- **주요 데이터**: 포장 단위(`inventory.handling_unit` — `handling_unit_no`·`parent_handling_unit_id` 자기참조·`status_code`), 내용물(`inventory.handling_unit_content` — `item_id`·`lot_id`·`qty`, `uq(HU, 품목, LOT)`). 재구성은 LOT 을 가르지 않으므로 `trace.lot_relation` 이 생기지 않는다. 재구성 이벤트는 `HandlingUnitRepackEvent`(+Line)로 되살렸다(2026-08-30).
- **핵심 액션**: 원 포장 스캔 → 재구성 유형 선택(합병/분할/재구성) → 새 구성 편집(숫자 키패드, 수량 합 = 원 수량 합 검증) → 재구성 확정. 확정 후 POP 대기 목록에 오르며, 발번·라벨 인쇄·재출력 선택은 `P-04-04`에서 수행한다. 재구성 이력은 저장·조회된다(`GET .../repack-events`).

## §4. 필드

### §4-A. 포장 단위 `inventory.handling_unit`

| 라벨(한/베) | 출처 컬럼 | 비고 |
| --- | --- | --- |
| 포장 번호 | `handling_unit_no` | UNIQUE · ⭐ **분할 잔량은 원 번호 유지**(결정 13) |
| 유형 | `handling_unit_type_code` | 카톤 · 팔레트 |
| 상위 포장 | `parent_handling_unit_id` | 자기참조 · `ck` 는 자기 자신만 막는다 |
| 상태 | `status_code` | ⛔ **공통코드 그룹을 세우지 않는다**(2026-09-02 판정) — 이 리소스는 «전표»가 아니라 «물건»(팔레트·박스 같은 담는 그릇)이라 상태를 «올릴» 전표 진행 축이 없다. 화면은 서버가 내려주는 값을 **표시만** 하고 값으로 분기하지 않는다 |

## §5. 액션·상태

### §5-1. ⭐ 2단말 스택 — **04 에서 유일하다**

```
M-04-03 (모바일)          P-04-04 (POP)
원 포장 스캔 · 구성 편집  →  신규 발번 · 새 라벨 인쇄
```

**한 업무가 두 셸에 걸쳐 있다.** 통합 IA §7-4 가 「**셸 간 레코드 공유 설계가 필요하다**」를 파생 확인 사항으로 남겼다.

**화면 규칙** — 모바일이 **확정하면 POP 대기 목록에 올라간다.** 모바일에서 인쇄하지 않는다(프린터가 POP 스테이션에 있다 — 결정 18).

⚠ **중간 상태가 생긴다** — 「구성은 바꿨는데 라벨은 아직」. 그 상태를 **어디에 저장하나**가 §5-2 의 문제와 같은 뿌리다.

### §5-2. ✅ 재구성 이벤트를 되살렸다(2026-08-30)

**결정 13 확정**(2026-07-06 CTO · 절충안 채택):

> **이벤트 헤더–라인 계보** · 신규 생성분 = 신규 발번 + 새 라벨 · **분할 잔량 = 원 단위 유지** · **수량 변경은 이벤트 한정 + 이력** · 라벨 재출력 = 사용자 선택

`PUT .../contents`가 `HandlingUnitRepackEvent`(헤더) + `Line`(수량 변경 전/후)을 함께 기록한다.

| 결정 13 요구 | 되살린 상태 |
| --- | --- |
| **누가 언제 왜 재구성했는가** | ✅ `performedBy`·`occurredAt`·`repackTypeCode` |
| **수량 변경 이력** | ✅ `qtyBefore`/`qtyAfter` |
| **모바일 → POP 중간 상태** | 이벤트가 남아 추적 가능(§5-1) |

저장 테이블은 데이터 모델 담당에게 통지한다, 기다리지 않는다. `lot_relation.source_event_id`가 가리킬 대상은 여전히 없다 — 재구성은 LOT을 가르지 않으므로(§4-C 주) 이 이벤트가 그 관계에 걸리지 않는다.

**중간 상태는 `handling_unit.status_code`(「라벨 발행 대기」)로 표시하고, 재구성 자체는 이벤트로 남는다.**

### §5-3. ⭐ 재구성은 **LOT 을 가르지 않는다** — 포장만 바뀐다

```
handling_unit_content   handling_unit_id · item_id · lot_id · qty
```

**LOT 은 그대로이고 어느 포장에 들었는지만 바뀐다.** 그래서 **`trace.lot_relation` 이 생기지 않는다.**

| 행위 | LOT | 관계 |
| --- | :-: | :-: |
| **재구성**(이 화면) | 그대로 | ⛔ 없다 |
| 선별(`sorting_result`) | **갈린다** — `good_lot_id`·`defect_lot_id` | ✅ 생긴다 |
| 생산(투입 → 산출) | 새로 생긴다 | ✅ 생긴다 |

⭐ **`P-04-03` §5-4 가 세운 것과 같은 형태** — **모델의 컬럼이 「LOT 이 갈리는가」를 이미 말한다.**

### §5-4. 분할 잔량은 **원 번호를 유지한다** — 결정 13 절충안

```
CTN-2026-0091 (180)  →  분할  →  새 포장 (80) + CTN-2026-0091 (100)
                                    ↑ 신규 발번      ↑ 원 번호 유지
```

**둘 다 새로 발번하는 안**과 **잔량이 원 번호를 쓰는 안** 중 **후자가 채택**됐다(절충안).

**화면이 그것을 명시한다** — 「분할 잔량은 원 포장 번호를 그대로 씁니다」. 안 적으면 **작업자가 잔량 라벨도 새로 뽑으려 한다.**

⚠ **그래서 라벨 재출력이 사용자 선택이다**(결정 13) — 잔량 라벨은 **원래 것이 아직 유효**하다. 다만 **수량이 바뀌었으므로** 라벨에 수량이 찍혀 있으면 다시 뽑아야 한다 → `P-04-04` 가 선택하게 한다.

### §5-5. 합병에서 **같은 LOT 이 만나면 합친다**

`P-04-01` §5-3 과 같은 규칙이다 — `uq_handling_unit_content` 가 같은 LOT 두 행을 막는다.

```
CTN-A: FG-…-0311  80     +   CTN-B: FG-…-0311  60
                    ↓ 합병
CTN-C: FG-…-0311  140  (한 행)
```

⚠ **합쳤다고 말한다** — 조용히 합치면 **어느 포장에서 얼마가 왔는지**를 못 본다. `HandlingUnitRepackEventLine`의 `roleCode=SOURCE` 행들이 그 출처를 남긴다(§5-2).

### §5-6. 오프라인 — **판정값을 쓰지 않으므로 허용**

**C-14** 판정 기준을 적용한다.

| | |
| --- | --- |
| Lot Status 판정 | ⛔ **쓰지 않는다** — 포장 구성만 바꾼다 |
| 결론 | ✅ **오프라인 허용** — `M-04-04`(제품 입고)와 같은 갈래 |

⚠ **다만 POP 으로 넘기는 것이 온라인을 요구한다** — 오프라인에서 확정하면 **POP 대기 목록에 안 올라간다.** 동기화 후에 올라간다는 것을 화면이 적는다(C-7 미확정 표식).

## §9. 이 장에서 나온 공유 계약 후보

1. ⚠ **이 교훈은 폐기됐다(2026-08-30)** — 「테이블이 없으면 이력을 그리지 않는다」는 원칙 위반이었다. `HandlingUnitRepackEvent`(+Line) 신설로 결정 13을 되살렸다 (§5-2)
2. **2단말 스택은 중간 상태를 어디에 두는지를 스펙이 정한다** — 모바일이 확정하고 POP 이 발행하는데, **그 사이 상태를 담을 곳**이 정해지지 않으면 두 화면이 서로를 못 찾는다. 이벤트 테이블이 없어 **`status_code` 값으로 물러났고**, 그 사실을 양쪽 스펙에 적는다 (§5-1)
3. **오프라인 허용 화면이라도 「다음 단말로 넘기는 것」은 온라인을 요구한다** — C-14 로 판정하면 이 화면은 오프라인 허용인데, **POP 대기 목록에 올리는 것**은 동기화 뒤다. **「저장은 됐지만 다음 단계로 안 넘어갔다」**를 화면이 말해야 작업자가 POP 앞에서 헤매지 않는다 (§5-6)
