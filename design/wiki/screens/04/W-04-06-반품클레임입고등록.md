> 작성일: 2026-08-07 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ⭐ **나간 물건이 돌아오는 유일한 입구**다. `W-04-12`(출하 확정)가 「확정 후 취소 불가」로 닫히면서 **이 화면이 사후 경로 전부**를 받는다.

## §0. 요약

- **개요**: 관리웹 입력형 화면(신뢰도 **확정**). 완제품창고담당이 반품·클레임 입고를 등록한다 — 출하 확정 화면(`W-04-12`)이 「확정 후 취소 불가」로 닫히면서 확정된 출하에 문제가 생기면 갈 곳이 이 화면 하나뿐이다.
- **주요 데이터**: `logistics.goods_receipt`+`goods_receipt_line`(생성 — `original_shipment_lot_allocation_id` late FK 로 원 출하 LOT 을 가리킨다) · `trace.lot`·`lot_relation`(읽기 — 원 LOT 을 그대로 쓴다) · `quality.nonconformance`(이 화면은 만들지 않는다 — `W-04-07` 소관 · B-13).

## §5. 액션·상태

### §5-1. ⭐ 이 화면이 **사후 경로 전부**를 받는다

`W-04-12`(출하 확정·취소)가 **「확정 후 취소는 원칙적으로 불가」**로 닫혔다(2026-08-07 사용자 확정). 그래서 **확정된 출하에 문제가 생기면 갈 곳이 여기 하나**다.

```
출하 처리(미확정)  →  [ 취소 가능 ]  →  확정  →  ⛔ 취소 불가
                                                   ↓
                                            W-04-06 반품 입고
```

**FR-IM-079 가 이미 그렇게 적었다** — 「실제 고객에게 반출된 경우 출하취소가 아니라 **고객 반품 절차**를 사용해야 한다」. **2단 확정이 그 경계를 「반출 여부」에서 「확정 여부」로 옮겼을 뿐**이고, 반품 절차가 받는다는 것은 그대로다.

### §5-2. ✅ 원천은 이 화면에서 **고정**이다 — 가를 것이 없다

⛔ **이전 판의 「원천 구분(내부/외부 클레임)을 담을 컬럼이 없다」는 확정 원문을 잘못 읽은 것이었다**(사용자 정정 2026-08-31).

**업무 사실** — **출하가 완료된 뒤 되돌아오는 입고는 전부 고객사 클레임이다.** 이 화면에 들어오는 건에 「내부」 갈래가 없다.

QA #15 원문은 이렇다.

> 클레임 입고 = 불량창고 반품입고로 통일. 단 **내부 품질검사 판정 입고분**과 구분 필요 → 불량창고 입고에 원천 구분(내부 판정 vs 외부 클레임) 속성 신설

여기서 「내부 품질검사 판정 입고분」은 **공정 검사에서 불합격 받아 불량창고로 들어오는 것**이지 반품 입고가 아니다. QA #15 가 가르라 한 것은 **불량창고에 들어오는 서로 다른 두 경로**이지 이 화면 «안»에서 가르는 것이 아니었다.

**그 구분은 이미 계약에 서 있다.**

| 어디 | 축 | 값 |
| --- | --- | --- |
| `DefectRecord.sourceCode` | 불량 기록의 원천 (결정 09) | 현장 · PQC · OQC · 수리 · **클레임** |
| `Nonconformance.sourceCode` | 부적합의 원천 | 제품 부적합 등록 · **반품 입고** — ⭐ **서버 파생** — 이 화면도 `W-04-07` 도 보내지 않는다 |

⭐ **이 화면은 부적합을 만들지 않는다**(§5-7 · 요구서 §3-6). 이 화면이 넣은 입고 전표를 **뒤에 `W-04-07` 이 부적합으로 올릴 때**, 그 원천은 입고 유형(`RETURN`)에서 **서버가 파생**한다 — 어느 화면도 원천을 묻지 않는다.

**그래서 `reason_code` 는 순수한 반품 사유만 받는다** — 원천을 접어 넣지 않는다. 값이 곱해지지 않으므로 **사유는 고객 설정 마스터로 그대로 넘어간다**(G-31 · `omf-mes#145`).

⭐ **「클레임이 몇 건인가」는 이 화면을 세면 된다** — 이 화면이 만드는 건이 곧 클레임이다. 사유별로 나눠 세는 것은 `reason_code` 가 받는다.

### §5-3. 원 출하를 **못 찾는 경우가 정상이다**

```
GoodsReceiptCreate.sourceDocumentTypeCode + sourceDocumentId   선택 (비울 수 있다)
GoodsReceiptLine.originalShipmentLotAllocationId               선택   ✅ 계약 반영 완료(2026-09-01)
```

⛔ **서버가 `lotId` 만으로는 못 잇는다** — **한 LOT 이 여러 출하에 나뉘어 나가기 때문**이다(143행). 어느 «배분»인지는 등록 시점에만 알 수 있다.

⭐ **원천 문서를 통째로 비울 수 있다**(✓확정 2026-08-31 사용자 · 계약 반영 완료). 「반품인 것은 확실한데 어느 출하인지 모르는」 경우를 계약이 받는다.

⛔ **「없음(NONE)」을 값으로 두지 않았다** — 가리킬 대상이 없는 값을 다형 참조 판별자에 섞으면 그 칸이 어느 표를 가리키는지 판별할 수 없게 된다(A-10). 📨 저장 컬럼의 `NOT NULL` 해제는 데이터 모델 담당 통지 사항이고 우리를 막지 않는다.

| 상황 | 처리 |
| --- | --- |
| 원 출하를 찾았다 | `original_shipment_lot_allocation_id` 를 채운다 — **genealogy 가 이어진다** |
| **못 찾았다** | 비운다. 헤더 원천도 **가리킬 문서가 없으면 함께 비운다**(2026-08-31 확정) |

⚠ **고객이 오래된 물건을 보내면 못 찾는다** — LOT 라벨이 훼손됐거나 여러 출하가 섞였을 때다. **막지 않는다.**

### §5-4. ⭐ 원 LOT 을 그대로 쓴다 — 새 LOT 을 만들지 않는다

`W-04-11`(재고 재등록) §5-1 이 세운 것과 **같은 판단**이다.

```
⛔ 새 LOT 발번        →  「이 물건이 한 번 나갔다 돌아왔다」는 사실이 끊긴다
✅ 원 LOT + 상태 전이  →  genealogy 가 이어진다
```

**`trace.lot_relation` 을 쓰지 않는다** — 같은 LOT 이라 관계가 아니다. 관계가 생기는 것은 **선별로 갈릴 때**다(`W-04-07` §5-4).

### §5-5. 반품은 **Hold 로 들어온다** — 판정 전이다

QA #15 가 「**불량창고 우선 입고 → 재작업/폐기 판정 → 재고 재등록 → 출하 재진입**」으로 확정했다.

```
quality_status_code = Hold 고정
```

**결정 10**(Lot Status = 차단의 단일 지점)이 여기서도 작동한다 — **판정 전에는 출하·피킹이 막힌다.**

⚠ **`M-04-04`(제품 입고)와 반대다** — 거기는 「들어오는 것은 막지 않는다」였는데, **여기는 들어올 때부터 막힌 상태**다. 갈림은 **「의심할 이유가 있는가」**다.

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **되돌리기를 막은 화면은 사후 경로가 어디인지를 가리켜야 한다** — `W-04-12` 가 「확정 후 취소 불가」로 닫히면서 **그 뒤의 모든 사고가 이 화면으로 온다.** 확정 화면이 「반품 절차로 진행하세요」를 안내하고, 반품 화면이 **원 출하를 찾아 잇는 경로**를 갖는 것이 짝이다. B-14 의 **뒷면** (§5-1)
2. ⛔ **「자리가 없다」를 적기 전에 확정 원문의 «주어»를 본다** — 이 화면은 QA #15 의 「내부 판정과 구분 필요」를 자기 화면 안의 축으로 읽고 3주 동안 라디오 버튼 하나를 그려 두었다. 원문이 가른 것은 **불량창고에 들어오는 서로 다른 두 경로**였고, 그 축은 이미 계약에 있었다(`DefectRecord.sourceCode` 5종). 확정문의 주어를 잘못 잡으면 **없는 결손을 만들어 낸다** (§5-2)
3. **「의심할 이유가 있는가」가 입고 차단의 기준이다** — `M-04-04`(제품 입고)는 「들어오는 것은 막지 않는다」였는데 **반품은 들어올 때부터 Hold** 다. 같은 입고인데 갈리는 근거가 **의심 여부**이고, 결정 10 의 차단 지점을 어디에 둘지가 그것으로 정해진다 (§5-5)
