# W-04-02 · 출하 예정 목록

## §0. 요약

- **개요**: 관리웹에서 물류 출하담당이 출하작업지시를 출하일 축으로 모아 조회하는 목록 화면(신뢰도 확정 — WF04 S3). **조회만** 한다 — 편성은 `W-04-01`, 피킹은 `M-04-01`, 확정은 `W-04-04`가 맡는다. 공유계약 §L(조회·집계) 10조항 중 8개가 걸린다.
- **주요 데이터**: `logistics.shipment_request`(출하일)·`shipment_request_line`(요청/배정/출하 3수량)·`logistics.shipment`(상태·적재·출하 시각). 인벤토리 근거가 요구하는 시간대 슬롯 필터는 저장 형태가 미결정이라 제공하지 않는다(고객 운영 방식 확인 대기 — 물리 모델 문제 아님).
- **핵심 액션**: 출하일 범위(필수) 입력 후 조회 → 요약은 필터 전체·목록은 페이지 기준으로 각각 표시 → 지정된 열만 정렬 → 행 클릭으로 편성(`W-04-01`) 또는 출하 확정(`W-04-04`, 피킹·검사 완료 건만) 이동. 자동 갱신 없음 — 수동 새로고침만.

> 작성일: 2026-08-07 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **§L 조회·집계의 6번째 적용.** 출하작업지시를 날짜 축으로 모아 「오늘 무엇이 나가는가」를 본다.

### §5-2. ⏳ 시간대 슬롯 필터 — **저장 형태 결정 대기**

인벤토리 근거가 「**M2 Wallet 시간대 슬롯 필터**」를 명시한다. **저장 형태가 아직 결정되지 않았다**(`W-04-01` §5-3과 같은 건 — 고객 운영 방식에 달렸다. 물리 모델 문제가 아니다).

**A-11로 물러난다** — 필터에서 **빼고 사유를 적는다.**

```
ⓘ 시간대 필터는 저장 자리가 없어 제공하지 않습니다
```

⚠ **비활성 컨트롤로도 두지 않는다.** 필터는 「고르면 걸러진다」는 약속인데, 저장 자체가 없으면 **나중에 컬럼이 생겨도 과거 데이터에는 값이 없다.** 있는 척하면 운영자가 「필터가 고장났다」고 본다.

### §5-3. 「진행」과 「검사」는 파생이다 — **계약이 정의한다**

두 열 다 여러 테이블을 가로지른다.

| 열 | 무엇을 보나 |
| --- | --- |
| **진행** | 라인 3수량 + `shipment.status_code` + 피킹 진행 |
| **검사** | `shipping_inspection_required` + `quality.inspection_result` — ✅ `ShipmentRequest.shippingInspectionStatusCode`로 계약 반영(03 품질 조인은 서버 몫 · omf-mes#232 · #235) |

**화면이 규칙을 갖지 않는다** — 「배정 0이면 미편성, 배정 < 요청이면 미배정…」 같은 판정을 프런트가 하면 **`W-04-01`·`W-04-04`와 갈린다.**

**규칙**: **계약이 진행 상태 코드를 내려 준다.** `W-01-13`의 후속 판정, `W-CO-09`의 내 차례 판정과 **같은 형태**다.

### §5-4. ⭐ **다섯 모양**으로 그린다 — L-8 확장 (2026-08-25 · omf-mes#235)

03 품질의 판정(`overallJudgmentCode`)이 **합격·불합격·보류 3값**이라(`quality-03품질.json`
`INSPECTION_RESULT_OVERALL_JUDGMENT`), 「대상 아님」·「아직 안 함」 둘만으로는 불합격과 보류를
구분할 수 없었다. `ShipmentRequest.shippingInspectionStatusCode` 를 5값으로 확장한다.

```
shipping_inspection_required = false             →  「—」        NOT_REQUIRED (대상 아님)
= true, 라인 전체 결과 없음                       →  「● 대기」   PENDING      (아직 안 함)
= true, 라인 전체 합격                            →  「✅ 합격」  PASSED       (했음 · 통과)
= true, 불합격 라인 존재                          →  「⛔ 불합격」 REJECTED     (했음 · 차단)
= true, 보류 라인 존재(불합격 없음)                →  「⚠ 보류」   HELD         (했음 · 보류)
```

**행 하나에 라인이 여럿이면 서버가 「가장 나쁜 것이 이긴다」 순서로 접어 하나로 낸다**:
`REJECTED > HELD > PENDING > PASSED > NOT_REQUIRED`.

**다섯을 셋으로 뭉치면 출하 확정에서 막힌다** — `W-04-04`가 「불합격 없이 합격이어야 한다」로
차단하는데, 목록이 불합격·보류를 「대기」로 뭉치면 **왜 막히는지 목록에서 알 수 없다.**

⚠ **이 필드를 이미 `PASSED` 셋만 알고 소비 중인 코드**는 `REJECTED`·`HELD`를 몰라도 당장은
`PENDING`과 같은 표시(회색·「● 대기」 계열)로 두면 안전하다 — 다만 그렇게 두면 이 절이 막으려는
바로 그 문제(왜 막히는지 모름)가 재현되므로, 다음 착수 때 세 색을 마저 구분해 그린다.

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **여러 화면이 같은 「진행 상태」를 보이면 계약이 그 코드를 내려 준다** — 배정·피킹·검사·출하를 조합한 판정을 프런트가 하면 `W-04-01`·`W-04-02`·`W-04-04`가 **같은 건을 다르게 부른다.** `W-01-13`의 후속 판정·`W-CO-09`의 내 차례 판정과 **같은 형태의 세 번째 사용처** (§5-3)
2. **저장 자리가 없는 축은 필터에서 아예 뺀다 — 비활성으로도 두지 않는다** — 필터는 「고르면 걸러진다」는 약속이고, 저장이 없으면 **나중에 컬럼이 생겨도 과거 데이터에 값이 없다.** 비활성 컨트롤은 「곧 된다」로 읽혀 더 나쁘다. A-11이 「입력란을 두지 않는다」였다면 이것은 **조회 쪽 판** (§5-2)
3. **「대상 아님」·「아직 안 함」·「했음」을 세 모양으로 그린다** — L-8이 「판정 불가를 정상으로 보이지 않는다」였는데, **대상이 아닌 것까지 셋으로 갈려야** 하류 화면의 차단 사유를 목록에서 읽을 수 있다 (§5-4, 2026-08-25 다섯 모양으로 확장 — 아래 4)
4. ⭐ **「했음」이 하나가 아니면 다섯이다** — 3이 예고한 확장의 실제 사례. 「했음」이 유효기간을 가지면 넷이랬는데, 「했음」 자체가 **여러 값**(합격·불합격·보류)을 가질 수도 있다는 것이 이번에 드러났다. 판정을 내는 하류 계약(03 품질)의 값 개수가 상류(04) 화면의 모양 개수를 결정한다 — 화면을 먼저 정하고 계약을 끼워 맞추지 않는다 (§5-4 · omf-mes#235)
