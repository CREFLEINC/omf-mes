# W-04-03 · OQC 출하검사 판정

> 작성일: 2026-08-07 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **검사 3형(IQC·PQC·OQC) 중 마지막**이고, 앞의 둘과 다른 점이 하나 있다 — **검사성적서가 고객에게 나간다.**
> ⭐ **`confirmed_at` 이 nullable 이다** — 이슈 **#62**(검사자와 확정자를 분리할 것인가)의 답이 **데이터에 이미 있다**(§5-4).

## §0. 요약

- **개요**: 관리웹에서 품질담당이 OQC(출하검사) 대상 검사 의뢰를 선택해 합격·불합격·보류 수량과 종합 판정을 입력·저장하는 화면. 좌측 검사 대상 목록(상태·기간 필터) + 우측 선택된 검사의 대상 정보·판정 입력 2단 레이아웃이다.
- **주요 데이터**: 검사 의뢰(`quality.inspection_request` — `target_type_code`+`target_id` 다형)·검사 결과(`quality.inspection_result` — 합격·불합격·보류 합계가 검사 수량과 같아야 하는 CHECK 제약, 회차·멱등키 UNIQUE, `confirmed_at` nullable)를 다루며, 판정에 따라 Lot Status(Release/Hold)가 전이된다. 검사성적서(CoA/CoC)는 `app.document_issue_log`에 담길 예정이나 발행 계약은 아직 없다.
- **핵심 액션**: 검사 선택 → 합격·불합격·보류 수량 입력(합계가 검사 수량과 실시간으로 맞는지 확인) → 종합 판정 선택 → 판정 저장(Lot Status 전이 경고 확인) 또는 재검사(회차를 추가하고 사유 입력, 이전 판정은 수정하지 않음). 검사성적서 발행 버튼은 계약 미착지로 비활성 상태다.

## §5. 액션·상태

### §5-1. ⭐ 수량 셋의 합을 **DB가 강제한다** — 화면이 먼저 맞춘다

```sql
ck_inspection_result_qty  CHECK (accepted_qty + rejected_qty + held_qty = inspected_qty)
```

**IQC(`W-01-01`)·PQC(`P-02-13`)에도 같은 제약이 있다** — 검사 3형이 공통 골격을 쓴다.

**화면 규칙** — 세 칸을 따로 받되 **합계를 실시간으로 보이고**, 어긋나면 저장을 막는다.

```
합계 500 = 검사 수량 ✅        ← 맞을 때
합계 480 ≠ 검사 수량 500 ⛔    ← 20 이 어디에도 안 들어갔다
```

⚠ **「나머지 자동 채움」을 두지 않는다.** 합격만 입력하면 나머지를 불합격으로 채우는 편의가 있을 수 있는데, **보류와 불합격은 후속이 다르다**(불합격 → 재작업 의뢰 / 보류 → 판정 대기). 자동으로 정하면 **엉뚱한 후속이 돈다.**

### §5-2. ⭐ 판정이 **Lot Status 를 바꾼다** — J-7을 적용한다

결정 10이 Lot Status 를 차단의 단일 지점으로 만들었고, **OQC 합격이 출하를 여는 열쇠**다.

**J-7(상태 전이 화면은 무엇을 막고 무엇을 푸는지 확정 전에 보인다)를 그대로 적용한다.**

```
⚠ 판정하면 Lot Status 가 바뀝니다
   합격 480 EA  →  Release — 출하·피킹이 풀립니다
   불합격 20 EA →  Hold    — 재작업 의뢰가 필요합니다
   ⚠ 이 LOT 을 쓰는 진행 중 피킹 1건이 함께 막힙니다
```

**규칙 넷**(J-7) — ① 대상 규모를 숫자로 ② 다른 화면에 미치는 영향 ③ 되돌림 비용 ④ 푸는 경로.

⚠ **되돌림 비용** — 이미 피킹된 분은 이 전이로 회수되지 않는다. 그 문장을 함께 적는다.

### §5-3. 재검사는 **회차로 쌓는다** — 덮어쓰지 않는다

```
inspection_round            integer NOT NULL DEFAULT 1
uq_inspection_round         UNIQUE (inspection_request_id, inspection_round)
previous_result_id          bigint REFERENCES inspection_result
reinspection_reason_code    app.code_t
```

**§K-1(발행은 회차로 쌓고 이전 것을 지우지 않는다)의 검사 판**이다. B-3(이력 불변)이 **구조로 강제**된다.

| | |
| --- | --- |
| 1차 판정 | `inspection_round = 1` |
| **재검사** | `round = 2` · `previous_result_id` = 1차 · **사유 필수** |
| 화면 | **회차 목록을 함께 보인다** — 1차가 왜 뒤집혔는지가 판단 근거다 |

⚠ **재검사 사유 코드 값 목록이 미정이다** — `W-06-06` 소관. `K-2`가 「재발행 사유」에서 겪은 것과 같은 형태다.

### §5-4. ⭐ **`confirmed_at` 이 nullable 이다** — 이슈 #62의 답이 데이터에 있다

**#62**(검사 결과 확정 권한 — 검사자와 확정자를 분리할 것인가)가 회신 대기 중이다. **실측하니 모델이 이미 분리를 받는다.**

```
inspector_id   bigint NOT NULL      ← 검사한 사람
inspected_at   timestamptz NOT NULL ← 검사한 시각
confirmed_at   timestamptz          ← nullable — 확정한 시각이 따로 있다
```

| 운영 | 데이터 |
| --- | --- |
| 검사 = 확정 (한 사람) | 저장 시 `confirmed_at` 을 함께 채운다 |
| **검사 ≠ 확정 (두 단계)** | `confirmed_at` 을 비워 두고 **확정자가 나중에 채운다** |

⚠ **그런데 `confirmed_by` 컬럼이 없다** — 언제 확정했는지는 남는데 **누가 확정했는지는 안 남는다.**

⭐ **그리고 이것도 비대칭이다** — `confirmed_by` 는 **다른 두 테이블에 실재한다**(`planning.production_plan` · `logistics.subcontract_reconciliation`, 실측). 「확정한 사람을 남긴다」는 이 모델의 관행이고 **`inspection_result` 에만 빠져 있다.** `M-04-04` §5-4(제품 입고 수량 차이)와 같은 형태로 **비대칭 자체가 결손의 근거**다.

**업무 확정대로 둔다** — 1차는 **검사 = 확정 한 단계**로 운용하고 저장 시 `confirmed_at` 을 함께 채운다. 근거는 **`#62` 확정(「분리하지 않는다」 · 1차)**이지 컬럼 유무가 아니다. ⚠ **구판 A-11 인용을 정정한다** — v4.6 이 「물러난 수준을 명시한다」를 「확정대로 반영하고 모델 결손은 통지한다」로 바꿨다. 데이터 모델은 설계 결정을 앞설 수 없다. 분리를 열면 그때 `confirmed_by` 를 계약에 세우고 컬럼은 통지한다. → §8-1.

> ⭐ **회신 대기 항목이 데이터에 반쯤 준비돼 있었다.** 「분리할 것인가」를 묻기 전에 **모델이 무엇까지 받는지**를 함께 보내면 회신이 구체적으로 온다.

### §5-5. ⛔ 검사성적서(CoA/CoC) 발행이 **미착지**다

인벤토리 근거가 「**검사성적서(CoA/CoC)**」를 데이터로 명시한다. **어디에 담기는지는 실측으로 나왔다.**

```
app.document_issue_log.document_type_code   -- LABEL | COA | TRACE_REPORT 등
```

⭐ **`COA` 가 주석에 값으로 예고돼 있다** — 별도 테이블이 필요하지 않고 **§K 출력물 경로를 그대로 탄다.**

**그런데 계약이 없다.** `app.document_issue_log` 는 01 트랙이 지목한 **횡단 계약 3종 중 둘째**이고, 아직 `app-공통.json` 에 들어오지 않았다.

**A-11로 물러난다** — 발행 버튼을 **비활성 + 사유**로 둔다.

```
⛔ 검사성적서 발행은 아직 불가합니다 — 출력물 발행 계약이 준비되면 열립니다
```

⚠ **CoC 는 값이 예고돼 있지 않다**(주석은 `COA` 만). CoA(성적서)와 CoC(적합증명서)가 다른 문서라면 **값이 하나 더 필요하다** → §8-3.

### §5-6. 「검사 대상」은 **`W-04-01` 이 정한다**

```
shipment_request_line.shipping_inspection_required   boolean NOT NULL DEFAULT false
```

라인마다 켜고 끄는 값이고 **편성 화면이 정한다.** 이 화면은 **켜진 것만** 목록에 받는다.

⚠ **L-8을 적용한다** — 「대상 아님」과 「대상인데 아직 안 함」을 다르게 그린다(`W-04-02` §5-4와 같은 규칙).

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **회신 대기 항목은 「모델이 무엇까지 받는지」를 함께 물어야 답이 구체적으로 온다** — #62(검사자와 확정자 분리)가 회신 대기인데, 실측하니 **`confirmed_at` 이 nullable 로 이미 분리를 받고 `confirmed_by` 만 없다.** 「분리할 것인가」만 물으면 답이 와도 **컬럼 신설이 뒤늦게 드러난다.** 회신 요청에 **데이터 준비 상태를 함께 적는다** (§5-4)
2. **합계 제약이 있는 입력에서 「나머지 자동 채움」을 두지 않는다** — 합격만 넣으면 나머지를 불합격으로 채우는 편의가 자연스러워 보이지만, **보류와 불합격은 후속이 다르다**(재작업 의뢰 ↔ 판정 대기). 자동으로 정하면 **엉뚱한 후속이 돈다.** A-9(DB 미강제 검증 등급)의 반대 방향 — **DB 가 강제하는 것을 화면이 대신 채우지 않는다** (§5-1)
3. **번복이 「수정」이 아니라 「회차 추가」인 구조는 화면도 그렇게 그린다** — `uq_inspection_round` + `previous_result_id` 가 이력 불변을 구조로 강제한다. 화면에 「수정」을 두면 **DB 가 거부하는 동작을 사용자에게 제안**하는 것이다. J-6(결재는 되돌릴 수 없다)·K-1(발행은 회차로 쌓는다)과 **같은 형태의 세 번째** (§5-3)
