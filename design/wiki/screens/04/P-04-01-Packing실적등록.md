# P-04-01 · 출하 실적 등록

> **POP 공통 개정(2026-09-08)**: 글꼴·버튼·입력·선택·키패드·목록 행과 터치 영역은 관리웹 기본 밀도(E-3)를 사용한다. 본문의 구 56~72px 수치와 확대 터치 판정은 변경 이력이며 구현 기준이 아니다. 모든 선택형 목록은 선택값 + [선택] 버튼과 로컬 검색·목록 스크롤·[페이지 위]·[페이지 아래] 팝업(G-34)을 사용한다. 성공 피드백은 G-1의 POP 공통 규칙을 따른다. 로컬 기록·서버 반영·인쇄 결과를 구분하고 C-7 미확정 표식은 유지한다.

> 개정일: 2026-09-08 · 현장 테스트 확정 반영
> 기존 `P-04-02 납품·포장 라벨 출력`을 이 화면에 통합한다.

## §0. 요약

- **개요**: 납품라벨/출하 대상과 생산 LOT을 대조해 포장 단위를 구성하고 포장 실적을 확정하는 POP 화면이다. 포장 확정 후 포장 라벨을 자동 출력하며, OQC 합격 또는 OQC 비대상 제품은 납품 라벨도 자동 출력한다.
- **재출력**: 포장·납품 라벨의 기존 재출력 기능을 같은 화면에 유지한다. 대상과 사유를 선택한 뒤 수동 실행하고 발행 회차를 남긴다.
- **OQC**: `shippingInspectionRequired=true`이면 OQC 합격 전 납품 라벨을 발행하지 않는다. `false`이면 OQC 절차를 생략하고 포장 확정 직후 납품 라벨을 자동 출력한다.

## §2. 레이아웃·밀도

글꼴, 버튼, 입력, 선택 트리거, 목록 행과 터치 영역은 **관리웹 기본 크기**를 사용한다(공유계약 E-3). 긴 LOT·라벨 번호는 원문을 저장하고 구성 단위로 분절 표시한다(E-2).

```text
┌ 출하 실적 등록 ─ 출하작업지시 번호 · 거래처 · 작업자 · 연결상태 · 화면 이동 · 사용자 전환 ┐
│ 출하 대상 [현재 선택값] [선택]                                                            │
│ 출하 대상 확인 ─ 생산 LOT 스캔 ─ 배분 매칭 판정                                           │
│ 포장 구성: 유형 [값] [선택] · 상위 포장 [값] [선택] · 내용물/수량 목록                    │
│ OQC 상태: 비대상 / 대기 / 합격 / 불합격                                                   │
│ 라벨 상태: 포장 라벨 · 납품 라벨 · 최근 인쇄 결과                                         │
│ [재출력 대상 선택] [재출력 사유 선택] [재출력]          [포장 확정]                       │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

헤더의 **출하작업지시 번호**와 **거래처**는 출하 LOT 배분 응답이 내려 주는 값이다
(`ShipmentLotAllocation.shipmentRequestNo` · `customerName` — 서버가 출하작업지시를 거슬러 풀어
준다 · 공유계약 L-2). 두 값은 계약의 `required` 목록에 없어 **비어 올 수 있다** — 비면 그 자리를
「—」로 그리고 나머지 헤더 항목은 그대로 둔다.

선택형 필드는 모두 **선택값 + [선택] 버튼**으로 표시하고 공유계약 G-34의 목록 팝업을 사용한다. 팝업 검색은 현재 화면에 로드된 항목만 로컬에서 거르며 API 검색으로 전환하지 않는다.

## §3. 포장 등록

공통 헤더의 **[화면 이동]**은 G-34를 따른다. 셸의 활성 POP 라우트 등록부에서 통합·폐지 화면을 제외한 후보 전체를 목록 팝업으로 표시한다. 후보 안 로컬 검색·스크롤·페이지 이동을 제공하고 선택 즉시 이동하며 미저장 입력 확인 팝업은 띄우지 않는다. 등록 검증·준비 전에는 업무 이동을 열지 않고, 등록 후 화면 이동이 실제 업무의 공정별 기능 구성·인증·서버 검증을 우회하지 않는다.

**물류 기능 구성 정합 결정(2026-09-10, 요청 #536)**: 이 화면의 포장·출하 입력은 생산 실적이 아니라 물류 업무이므로 F-1의 `canInputResult` 적용에서 제외한다. 과거 폐지 확정의 전파가 아니라 이번 자율 설계 정합 결정이다. 인증·사번 귀속·출하 배분·수량·OQC(출하 검사)·서버 403 검증은 유지한다. 공정 0행을 물류 업무 금지로 보거나 임의 생산 공정을 선택하지 않는다.

### §3-1. 매칭 스캔

1. 출하번호를 스캔하거나 출하 목록에서 대상을 선택해 `shipmentId`를 정하고, 그 출하의 미포장 배분에서 품목을 확정한다. 출하번호 스캔은 정확 일치 `shipmentNo`로 조회한다. 목록 팝업은 현재 영업일의 피킹 완료 출하를 페이지로 읽고, 팝업 검색은 현재 표시된 항목만 로컬에서 거른다. 납품 라벨은 포장 확정 뒤 발행되므로 최초 포장의 선행 입력으로 요구하지 않는다. 이미 납품 라벨이 발행된 건의 재진입·재출력은 납품 라벨 스캔도 허용한다.
2. 생산 LOT을 스캔한다.
3. 서버가 출하 배분(`shipment_lot_allocation`)과 대조한다.
4. 일치한 **미포장 배분**만 포장 내용물에 추가한다. 같은 `shipmentLotAllocationId`를 다시 스캔하면 중복 추가하거나 수량을 늘리지 않고 이미 선택됐음을 안내한다. 같은 LOT이라도 `shipmentLotAllocationId`가 다른 미포장 배분이면 각 배분의 전량을 선택하고 표시 수량만 합산한다. `handlingUnitId`가 이미 채워진 배분은 재선택을 차단한다.

불일치, 배분에 없는 LOT, 배분 수량 초과는 포장 확정을 차단한다. 스캔 실패 시 직접 입력 경로를 제공한다. **현재 지원 단위는 출하 LOT 배분 한 건의 전량 포장이다.** 배분 한 건의 일부 수량만 포장하는 중간 상태는 지원하지 않는다. 하나의 LOT을 여러 배분으로 이미 나누어 놓은 경우에는 필요한 배분 건만 선택해 포장할 수 있다.

### §3-2. 포장 단위 구성

- `POST /inventory/handling-units`로 빈 포장 단위를 만든다.
- 유형과 선택 가능한 상위 포장은 선택 팝업으로 고른다.
- 내용물 1건 이상을 구성한 뒤 `POST /inventory/handling-units/{handlingUnitId}:pack`으로 확정하고, 선택한 배분의 전량을 그 포장 단위에 연결한다.
- 생성 후 확정 전 취소 요구는 보존하지만 `DELETE /inventory/handling-units/{handlingUnitId}`는 현재 서버에 구현되지 않았다. 화면은 취소 성공으로 표시하지 않고 미지원 안내를 보이며, 생성된 빈 포장 단위가 남을 수 있음을 알린다. 구현 전에는 호출하지 않는다.
- 확정 후 해체 기능은 이 화면에 두지 않는다.

## §4. 포장 확정 후 자동 출력

```text
[포장 확정]
  → 포장 실적 확정 성공
  → 포장 라벨 자동 발행·인쇄
  → OQC 판정
      ├─ 검사 비대상 → 납품 라벨 자동 발행·인쇄
      ├─ 합격       → 납품 라벨 자동 발행·인쇄
      └─ 대기/불합격 → 납품 라벨 발행 안 함, 상태와 해제 조건 표시
```

포장 라벨은 `PACKING_LABEL`, 납품 라벨은 `DELIVERY_LABEL`로 `POST /app/document-issues`를 호출한다. 발행 후 렌디션을 받아 인쇄하고 `POST /app/document-issues/{documentIssueLogId}:report-print`로 결과를 보고한다.

포장 실적 확정과 두 라벨 발행은 각각 상태를 가진다. 포장 확정이 성공한 뒤 라벨 출력이 실패해도 포장 실적을 다시 만들지 않는다. 같은 화면 재진입 시 발행 요약을 조회해 누락된 라벨만 이어서 출력한다.

### §4-1. OQC 대기 후 납품 라벨

OQC가 필요한 제품이 포장 시점에 미합격이면 포장 라벨만 자동 출력한다. 목표 계약은 출하 배분 응답의 `shippingInspectionStatusCode`로 비대상·대기·합격·불합격/보류를 구분하고, 같은 응답의 `oqcPassed`를 납품 라벨 발행 조건으로 쓰는 것이다. 두 값은 배분이 매달린 출하작업지시 라인이 피킹한 `LOT`(로트) 집합을 공통 후보로 삼는다. `LOT`(로트) 대상 OQC는 `lotId`가 있으면 이를, 없으면 `targetId`를 해당 집합과 대조한다. 출하작업지시 대상 OQC의 `lotId`가 있으면 그 `LOT`(로트)을 피킹한 라인에만, 없으면 같은 지시의 모든 검사 대상 라인에 적용한다. 확정된 결과 중 의뢰별 최신 회차만 세고, 매칭 결과가 하나도 없을 때만 대기이며 하나 이상이면 불합격 > 보류 > 합격 순으로 판정한다. 이는 피킹한 모든 LOT에 결과가 하나씩 있어야 합격이라는 뜻이 아니다. 검사 비대상은 상태를 합격으로 꾸미지 않고 `NOT_REQUIRED`(검사 비대상)로 표시하되 라벨 발행 게이트 `oqcPassed`는 `true`다.

현재 배분 조회는 `oqcPassed`만 반환하고 `shippingInspectionStatusCode`는 반환하지 않는다. 따라서 `oqcPassed=true`만으로 검사 비대상과 합격을 구별할 수 없어, 보완 전에는 이 화면에서 둘을 합격/비대상으로 추정해 표시하지 않고 납품 라벨 활성 조건으로만 쓴다. 세부 상태 표시만 미지원으로 안내하며 `omf-mes#599`에 남긴다. 현재도 `oqcPassed=true`이고 미발행이면 포장 확정 직후 자동 발행하거나 재진입 시 [납품 라벨 출력]을 활성화한다. 이미 발행됐다면 신규 출력이 아니라 재출력 흐름을 사용한다.

| 포장 취소 | **현재 비활성** — 서버 DELETE 미구현 | 미지원 안내. 빈 포장 단위를 삭제했다고 표시하지 않음 |
| 납품 라벨 출력 | OQC 합격/비대상 · 미발행 | 지연된 최초 발행 |
| 재출력 | 대상·사유 선택 · OQC 게이트 충족 | 선택 라벨 수동 재출력 |

## §7. 예외

| 상황 | 처리 |
| --- | --- |
| 출하 대상 ↔ LOT 불일치 | 차단하고 기대 품목을 표시 |
| 배분에 없는 LOT | 차단하고 다시 스캔 유도 |
| 배분 일부 수량만 포장 시도 | ⛔ 현재 미지원 안내 — 전량 포장할 배분 건을 선택한다 |
| 같은 배분 재스캔 | 중복 추가·수량 증가 없이 「이미 선택한 배분입니다」 안내 |
| 같은 LOT의 다른 미포장 배분 | 배분 ID별 전량을 각각 선택하고 표시 수량 합산 |
| 이미 포장에 연결된 배분 | ⛔ 재선택 차단 — 기존 포장 단위 표시 |
| 확정 전 빈 포장 취소 | ⛔ 현재 서버 미지원. 「현재 내용물 0」만으로 이력 없음이라 판단하지 않는다. 향후에는 미확정·현재 내용물 0·재포장 이력 0을 모두 확인하고 하나라도 어긋나면 409 |
| OQC 필요·미합격 | 포장 라벨만 출력, 납품 라벨은 숨기지 않고 대기 상태/조건 표시 |
| OQC 비대상 | 검사 절차 없이 납품 라벨 자동 출력 |
| 자동 출력 실패 | 포장 확정 상태 유지, 실패한 라벨만 재시도 |
| 프린터 미연결 | 발행/포장 성공 여부를 분리 표시하고 인쇄 복구 제공 |
| 포장 확정 `user` 409 | 입력을 보존하고 취급 단위 상세·내용물을 재조회한다. `PACKED`이면 현재 확정 상태만 알리고 재확정하지 않는다. 원요청 성공이나 라벨 출력 성공을 추정하지 않고 발행 이력을 별도 조회한다. `OPEN`이어도 낡은 ETag로 단정하지 않으며, 서버 내용물과 보존 입력의 차이를 보여 주고 사용자가 명시적으로 재확정해야 한다. 재확정은 재조회한 최신 ETag를 `If-Match`로 보낸다. 다시 409면 재조회·사용자 확인을 반복하며 자동 재전송하지 않는다. 본문이 같으면 원래 멱등키, 수정하면 새 논리 요청의 새 키를 사용한다. 멱등키 유지와 헤더 토큰 갱신은 별개다. `message` 문구를 기계 파싱하지 않는다 |
| 같은 요청 처리 중 | 이 포장 확정 요청의 멱등 처리에서 `conflictCause=workerLease`가 왔으면 「처리 중입니다」를 표시하고 입력을 보존한다. 잠시 뒤 같은 요청·같은 멱등키로 재전송하며 새 포장을 만들거나 새 키로 우회하지 않는다 |
| 사용자 전환 | 현재 사번만 삭제, 저장·오프라인 큐 기록은 유지 |

## §8. API 매핑

| 목적 | 계약 |
| --- | --- |
| 최초 출하번호 스캔 | 현재는 `GET /logistics/shipments?pickedOnly=true&q={스캔번호}&shipDateFrom=&shipDateTo=&page=&size=`의 **전 페이지**에서 응답 `shipmentNo`가 스캔값과 정확히 같은 행만 선택 → `GET /logistics/shipment-lot-allocations?shipmentId=&unpackedOnly=true`. 부분검색 첫 행을 고르지 않는다. 정확 일치가 없으면 현재 기간·피킹완료 조건 안에 없다는 뜻만 안내하고 기간 확장·필터 확인을 제공한다. 같은 번호가 복수면 자동 선택하지 않고 후보를 보여 준다 |
| 최초 출하 목록 선택 | `GET /logistics/shipments?pickedOnly=true&shipDateFrom={businessDate}&shipDateTo={businessDate}&page=&size=` — 팝업 검색은 수신한 현재 표시 목록만 로컬 필터 → 선택 후 배분 조회 |
| 기존 납품 라벨 재진입 | `GET /logistics/shipment-lot-allocations?q=` |
| 출하 배분/LOT 매칭 | `GET /logistics/shipment-lot-allocations?shipmentId=&lotQ=` |
| 포장 단위 생성/조회 | `POST /inventory/handling-units` · `GET /inventory/handling-units/{handlingUnitId}` |
| 포장 확정/취소 | 확정은 `POST /inventory/handling-units/{handlingUnitId}:pack`. 취소 DELETE는 계약 요구만 있고 현재 서버 미구현이라 호출하지 않음 (`omf-mes#562`) |
| 라벨 발행 | `POST /app/document-issues` (`PACKING_LABEL`·`DELIVERY_LABEL`) |
| 발행 요약/이력 | `GET /app/document-issues/summary` · `GET /app/document-issues` |
| 렌더링/인쇄 보고 | `GET /app/document-issues/{documentIssueLogId}/rendition` · `POST …:report-print` |

## §9. 명시적 비범위

- 포장 라벨·납품 라벨을 별도 화면으로 이동시키지 않는다.
- OQC 대상 제품의 납품 라벨을 합격 전에 발행하지 않는다.
- OQC 비대상 제품에 검사 완료를 요구하지 않는다.
- 재출력은 자동 실행하지 않으며 대상·사유 선택을 생략하지 않는다.
- 저장하지 않은 입력에 대한 화면 이동 확인 팝업은 만들지 않는다.
- 배분 한 건을 여러 포장에 나누는 부분 포장은 지원하지 않는다. 중간 표나 배분 분할 API를 임의로 만들지 않는다.
- 확정 전 빈 포장 취소 요구는 `omf-mes#562`에 남긴다. 향후 삭제 경로는 미확정·현재 내용물 0뿐 아니라 재포장 이력 0도 확인한다. 확정 후 해체·일반 재편성은 이 범위가 아니다.
