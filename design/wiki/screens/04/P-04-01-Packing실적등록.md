# P-04-01 · Packing(P&P) 실적 등록

> 작성일: 2026-08-07 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ⭐ **매칭 스캔 화면이다.** 두 개를 스캔해 **같은 것인지 확인**하는 형태는 04에서 처음이다(`P-02-03` 오투입 검증의 대칭).
> **POP 1024×768** — E-1 세로 예산 검산 · E-2 긴 식별자 분절 적용.

## §0. 요약

- **개요**: POP(1024×768 터치+스캔)에서 물류 출하담당이 납품라벨과 생산LOT을 순서대로 스캔하면 서버가 「스캔한 둘이 서로 맞는가」를 판정하고, 포장 단위(카톤·팔레트 등)를 만들어 내용물을 배분하는 포장 실적 등록 화면. 라벨 출력은 `P-04-02`가 맡는다.
- **데이터**: 포장 단위(`inventory.handling_unit` — `parent_handling_unit_id` 자기참조로 계층 구성)와 포장 내용물(`inventory.handling_unit_content` — 포장·품목·LOT당 1행 유일)을 다루며, 출하 배분(`logistics.shipment_lot_allocation.handling_unit_id`, nullable)과 연결된다.
- **핵심 액션**: 납품라벨 스캔 → 생산LOT 스캔(서버가 배분과 대조해 매칭 판정) → 품목·LOT·수량 담기(같은 LOT 재스캔 시 수량을 합산) → 상위 포장 선택(선택 사항) → 포장 확정.

### §3-1. 세로 예산 검산 — **E-1 슬랙 0**

```
헤더        64
본문       616   ← ① 88 + ② 88 + ③ 320 + ④ 88 = 584 + 패딩 16×2 = 616  ✅
액션바      88   ← 핵심 버튼 72 + 여백 16
──────────────
합계       768   슬랙 0
```

⚠ **③ 포장 구성이 320px 로 가장 크고 유일한 조정 여지다.** 행이 6줄을 넘으면 **③ 안에서 스크롤**한다 — 화면 전체를 스크롤하면 액션바가 밀려 E-1이 깨진다.

### §3-2. 가로 제약 — **E-2 를 적용한다**

파일럿 실측에서 **34자리 LOT 행이 597/599px(여유 2px)** 였다. 이 화면은 **LOT 열이 표 안에 들어가므로 더 좁다.**

**E-2 그대로 분절 표시한다** — 저장은 원문, 표시는 그룹핑. **붙여 쓰면 실물 라벨과 눈으로 대조가 불가능하다.**

### §3-3. 「예상 포장 수」를 1차에서 표시하지 않는다 — **기준이 마스터에 없다**

초판 목업이 「포장 2 / **예상 3**」을 그렸으나 **예상 포장 수를 낼 기준이 어디에도 없다.**
계약 7벌 전수에서 「포장당 수량」에 해당하는 속성은 **0건**이고, 있는 것은 보관 위치·적치
규칙의 용량(`mdm.location.capacity_qty` · `mdm.putaway_rule.capacity_qty`)뿐이다.
품목 마스터의 `default_production_lot_size` 는 **생산LOT 기본크기**이지 포장 단위가 아니다.

⇒ **서버 파생(L-2)도 지금은 세울 수 없다.** 기준이 서면 그때 L-2 로 내린다.
⭐ **같은 구획의 나머지 둘은 남긴다** — 「미포장 N」은 `Σ(allocatedQty − packedQty)`(서버가
파생 · `packedQty` 필수), 「포장 N」은 이 출하 배분들의 비어 있지 않은 `handlingUnitId` 의
서로 다른 개수다(`shipmentId` 로 묶는다 — §5-1 참조).
⚠ **「/ 예상 N」을 임시값으로 채우지 않는다** — 채우면 현장이 그 수를 목표로 삼는다.

## §5. 액션·상태

### §5-1. ⭐ 매칭 스캔 — **두 개를 대조한다**

`P-02-03`(자재 투입 오투입 검증)이 「스캔한 것이 지시와 맞는가」였다면, 이것은 **「스캔한 둘이 서로 맞는가」**다.

```
① 납품라벨 스캔  →  이 라벨이 어느 출하·어느 품목인지가 정해진다
② 생산LOT 스캔   →  그 LOT 이 ① 의 출하에 배분된 것인가
```

⭐ **① 스캔 응답이 「어느 출하·어느 품목」을 «값으로» 준다** — `shipmentId`·`itemId`·
`itemCode`·`warehouseId` 네 축이 `ShipmentLotAllocation` 에 실려 온다(2026-09-01 신설 ·
`omf-mes#330` A). ⛔ **화면이 그 값을 얻으려 출하를 다시 조회하지 않는다** — 초판 계약은
`shipmentId` 를 질의 축으로만 두어 「거를 수는 있는데 받을 수는 없는」 순환이 있었다.
⭐ **불일치 문구의 「FG-1002」는 `itemCode` 다** — 화면이 코드→이름 대응표를 갖지 않는다
(표시 문자열까지 계약이 내려 준다 · A-10 보강).

| 판정 | 화면 |
| --- | --- |
| 맞다 | ✅ 「매칭 — 이 납품라벨의 LOT 이 맞습니다」 |
| **다르다** | ⛔ **차단** — 「이 납품라벨은 FG-1002 용입니다」 + 다시 스캔 |
| 배분에 없는 LOT | ⛔ 「이 출하에 배분되지 않은 LOT 입니다」 |

⚠ **매칭 판정을 화면이 하지 않는다** — 배분(`shipment_lot_allocation`)을 서버가 보고 판정한다. 프런트가 목록을 받아 비교하면 **오프라인·캐시 상태에서 틀린다.**

### §5-2. 포장 단위는 **계층이다** — 박스 안에 박스

```
handling_unit.parent_handling_unit_id   자기참조
ck_handling_unit_parent                 자기 자신은 불가
```

| 층 | 예 |
| --- | --- |
| 최하위 | 카톤 — 내용물(품목·LOT·수량)을 직접 갖는다 |
| 상위 | 팔레트 — **카톤들을 담는다** |

**화면 규칙** — 이 화면은 **한 번에 한 포장**을 만들고, **상위 포장은 선택으로 지정**한다. 팔레트를 먼저 만들고 카톤을 담는 순서도, 카톤을 만들며 팔레트를 고르는 순서도 둘 다 된다.

⚠ **순환 참조는 `ck` 가 자기 자신만 막는다** — A → B → A 는 DB 가 막지 않는다. **화면이 상위 후보에서 자기 하위를 제외**한다. ⭐ 단 이 화면에는 걸리지 않는다 — §5-2-1.

⚠ **G-1(계층 목록·편집)이 걸린다** — 상위 포장 선택이 **2단 이내면 갭 불성립**이다(`W-06-07` §8-5 판정과 같은 기준). 팔레트–카톤 2단이면 `Select` 들여쓰기로 성립한다 → §8-4.

#### §5-2-1. 상위 포장 후보를 어디서 받는가 — **이 출하 창고로 좁힌다**

```
GET /inventory/handling-units?warehouseId={배분 응답의 warehouseId}&statusCode={포장 가능}
```

⭐ **새 질의 축을 만들지 않았다** — `warehouseId`·`statusCode` 는 01 계약에 이미 있다.
모자랐던 것은 축이 아니라 **그 축에 넣을 값**이었고, 그것을 배분 응답이 이제 준다(§5-1).

⛔ **「부모가 없는 것만」으로 좁히지 않는다.** 두 가지 이유다 —
① **계층 깊이가 확정이 아니다**(§8 미결 4). 「부모가 있으면 후보가 아니다」는 2단 전제를
   깔고 있는데 그 전제가 아직 안 섰다. 상류 확정(QA #16 · 2026-07-04 D15 종결)은 오히려
   「파렛트=이동 그룹핑, 재고·포장 계층 아님」 쪽이다 — 확정을 앞질러 화면을 굳히지 않는다.
② **이 화면에서는 순환이 구조적으로 불가능하다.** 매번 «새» 취급 단위를 만들고 그 상위를
   고르므로 **자기 하위가 존재할 수 없다.** 위 §5-2 의 「화면이 상위 후보에서 자기 하위를
   제외한다」가 실제로 걸리는 곳은 기존 포장을 다시 엮는 `M-04-03`(포장 재구성)이다.

⚠ **후보가 0건이어도 정상이다** — 이 화면은 빈 포장을 못 만들므로(§5-6 「내용물 ≥ 1」)
팔레트는 다른 화면이 만든다. 후보가 없으면 「상위 포장 (없음)」으로 확정한다.

### §5-3. ⭐ 같은 LOT 을 두 번 담을 수 없다 — **합쳐서 넣는다**

```
uq_handling_unit_content   UNIQUE (handling_unit_id, item_id, lot_id)
```

같은 포장에 같은 LOT 을 **두 행으로 못 넣는다.** 현실에서는 「120 넣고 나중에 60 더 넣기」가 자연스러운데 **데이터는 180 한 행**을 요구한다.

**화면이 합친다** — 이미 있는 LOT 을 다시 스캔하면 **수량을 더한다.**

```
FG-…-0311  120  →  같은 LOT 재스캔 60  →  180 (한 행)
```

⚠ **더한 것인지 새로 넣은 것인지 화면이 말한다** — 「기존 120 에 60 을 더해 180 이 됩니다」. 조용히 합치면 **중복 스캔을 못 알아챈다.**

### §5-4. ⛔ 「고객 바코드」의 마스터가 보류 상태다

인벤토리 근거가 「고객 바코드」를 명시한다. **고객 바코드 체계 마스터는 v1.3에서 [가설] 단계로 보류**됐다(인벤토리 v1.3 잔여).

| 있는 것 | 없는 것 |
| --- | --- |
| `mdm.item_external_code` — 품목의 외부 코드 | **고객별 바코드 체계 규칙**(자릿수·구성) |

**형식 검증을 하지 않는다** — 납품라벨의 바코드는 **`P-04-02` 가 발행한 값을 그대로 읽는다.** 근거는 **고객 바코드 규칙이 업무에서 정해지지 않았다**는 것이지(「이 고객은 13자리 EAN」 같은 규칙이 없다) 컬럼 유무가 아니다. ⚠ **구판 A-11 인용을 정정한다** — v4.6 이 「물러난 수준을 명시한다」를 「확정대로 반영하고 모델 결손은 통지한다」로 바꿨다. 데이터 모델은 설계 결정을 앞설 수 없다.

⚠ **형식 검증을 안 하면 오스캔이 통과한다** — 그래서 §5-1의 **매칭 판정이 유일한 방어선**이다. 라벨 값 자체는 안 믿고 **그것이 가리키는 배분**을 본다.

### §5-5. 단말 기능 구성 — **F-1 이 이 화면을 여는가**

```
mdm.terminal_process   8플래그   can_input_material · can_input_result · … · can_return_material
```

⛔ **포장에 맞는 플래그가 없다**(§I 등재 · 이슈 **#77**). `can_input_result`(실적 입력)로 물러날 수 있으나 **의미가 다르다.**

**확정대로 둔다** — **`can_input_result` 로 게이팅**한다. ✅ **`omf-mes-server#40` 회신(2026-08-31)이 「신설하지 않는다」로 확정**했고, 기존 8플래그 재사용도 하지 않는다(공유계약 F-1). 즉 이것은 물러난 상태가 아니라 **확정된 형태**다. ⚠ **구판 A-11 인용을 정정한다** — v4.6 이 「물러난 수준을 명시한다」를 「확정대로 반영하고 모델 결손은 통지한다」로 바꿨다. 데이터 모델은 설계 결정을 앞설 수 없다.

⚠ **#77 회신이 「플래그를 추가할 일이 아니다」로 올 수도 있다** — 2026-07-28 설계검토가 모바일에 대해 그렇게 판정한 선례가 있다(`W-CO-06` §5-1). 그러면 **게이팅 자체를 두지 않는다.**

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **매칭 판정은 서버가 한다 — 라벨 값 자체를 믿지 않는다** — 고객 바코드 체계 마스터가 없어 **형식 검증을 할 수 없으므로**, 방어선은 「라벨이 가리키는 배분이 실제로 있는가」 하나뿐이다. 프런트가 배분 목록을 받아 비교하면 캐시 상태에서 틀린다. **A-10 보강(계약이 판정 결과를 내려 준다)의 스캔 판** (§5-1·§5-4)
2. **유일 제약이 「합치라」고 말하는 곳에서는 화면이 합치되 합쳤다고 말한다** — `uq_handling_unit_content` 가 같은 LOT 두 행을 막으므로 재스캔은 수량을 더해야 한다. **조용히 합치면 중복 스캔을 못 알아챈다** — 「기존 120 에 60 을 더해 180」을 보인다. A-1(유일키 범위를 문구에 담는다)의 **입력 판** (§5-3)
3. **POP 화면은 어느 구획이 스크롤하는지를 스펙이 지정한다** — E-1 슬랙이 0이라 **화면 전체를 스크롤하면 액션바가 밀려 예산이 깨진다.** 「행이 넘치면 어디가 스크롤하는가」를 §3에 못박지 않으면 구현이 화면 스크롤을 택한다 (§3-1)
