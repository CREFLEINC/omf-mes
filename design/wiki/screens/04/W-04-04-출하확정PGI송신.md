# W-04-04 · 출하 처리(상차·실물 출고)

## §0. 요약

- **개요**: 관리웹에서 물류 출하담당이 상차 정보를 입력하고 실물 출고를 처리해 **미확정 상태의 출하**를 생성하는 화면. 도메인 04(제품출하)에서 genealogy가 종결되는 지점이며, v0.2부터는 **확정·ERP PGI 송신을 `W-04-12`(신설)로 분리**해 이 화면은 재고 차감과 미확정 출하 생성까지만 담당한다.
- **주요 데이터**: `logistics.shipment`(16열 — 차량번호·운전자·봉인번호·운송문서·상차담당·운송사 등 운송정보 + `erp_delivery_no`), `shipment_line`(`shipped_qty`·`goods_issue_line_id` nullable), `shipment_lot_allocation`(LOT×수량 — genealogy 종결점).
- **핵심 액션**: 확정 대기 목록에서 대상 선택 → 상차 정보 입력 → 서버가 판정하는 관문 3종(피킹 완료·검사 완료·Release) 통과 확인 → **출하 처리** 한 번으로 ① 재고 차감 ② 미확정 출하 생성이 한 트랜잭션으로 일어난다. 확정과 ERP 송신은 이 화면이 아니라 `W-04-12`에서 별도로 한다.

> 작성일: 2026-08-07 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ⭐ **genealogy 가 여기서 종결된다.**
> ⛔⛔ **v0.2 범위 축소(2026-08-07 사용자 확정) — ERP PGI 송신이 이 화면에서 빠졌다.** 출하를 **미확정 상태로** 만들고, **확정과 ERP 송신은 `W-04-12`**(신설)가 한다. 근거는 §5-1.

## §5. 액션·상태

### §5-1. ⭐⭐ **v0.2 정정 — 이 화면은 ERP 를 부르지 않는다**

> **초판은 재고 차감·출하 확정·ERP 송신 적재를 한 트랜잭션에 두었다.** 2026-08-07 **출하 2단 확정 도입**으로 **뒤의 둘이 `W-04-12` 로 갔다.**

```
이 화면 (출하 처리)
  ① 재고 차감        inventory_transaction (전기)
  ② 미확정 출하 생성   status_code = 미확정 · shipped_at
  ────────────────────────────────────────────  한 트랜잭션
W-04-12 (출하 확정)
  ③ 확정             status_code = 확정 · confirmed_at
  ④ ERP 송신 적재     integration_message (outbox)
  ────────────────────────────────────────────  한 트랜잭션
  ⑤ 실제 ERP 호출     ← 밖 · 비동기
```

**여전히 B-8 이다** — 각 트랜잭션 안에 업무 엔티티만 있고 외부 호출은 밖이다.

⭐ **바뀐 것은 「어디까지가 되돌릴 수 있는 구간인가」다.**

| | 초판 | **v0.2** |
| --- | --- | --- |
| 되돌릴 수 있는 구간 | ⛔ **없다** — 확정 즉시 ERP 로 간다 | ✅ **미확정 구간 전체** |
| 취소하면 ERP 는 | 역전표를 보내야 하고 **거부할 수 있다** | ✅ **아무것도 모른다** |
| 취소 판정 축 | ERP · 운송 · 고객납품 **3개** | ✅ **확정 여부 1개** |

**이 화면의 몫은 ①②까지다.** 실물이 나갔으므로 **재고는 여기서 차감한다** — 미확정이라고 장부에 남겨 두면 실물과 어긋난다.

### §5-2. ⭐ J-7을 「결과 구획」으로 그린다 — **일어나지 않는 것까지**

J-5·J-7이 요구하는 것을 **확정 버튼 바로 위**에 둔다.

```
✅ 재고가 300 EA 줄어듭니다
✅ 제품 LOT 2건의 출하 기록이 만들어집니다 — genealogy 가 여기서 끝납니다
ⓘ 상태는 「미확정」입니다 — ERP 에는 아직 가지 않습니다
ⓘ 최종 확정은 출하 확정·취소 화면에서 관리자가 합니다
✅ 확정 전까지는 취소할 수 있습니다
```

⭐ **v0.2 에서 마지막 줄이 「없다」에서 「있다」로 바뀌었다.** 초판은 「출하 취소 화면이 아직 없습니다」를 경고로 적었는데, **2단 확정을 도입해 되돌릴 구간 자체를 만들었다.**

⚠ **`shipment_line.goods_issue_line_id` 가 nullable 이다** — 출하가 출고 전표를 반드시 만드는지 아닌지가 데이터로 열려 있다. **1차는 만든다**(재고 차감의 근거가 필요하다) → §8-2.

### §5-3. ⛔ **v0.2 — ERP 송신은 이 화면의 일이 아니다**

> 아래는 초판 기록이고 **내용은 `W-04-12` 로 그대로 옮겨 간다.** 확정 성공을 「전송됨」이라 쓰지 않는다는 규칙(K-7 계열)은 그쪽에서 유효하다.

```
integration_message
    message_key   varchar(150) NOT NULL UNIQUE   ← 중복 송신을 DB 가 막는다
    retry_count   integer NOT NULL DEFAULT 0
    available_at  timestamptz                    ← 재시도 지연
    locked_at · locked_by                        ← 워커 리스
```

| 이 화면 | 다른 화면 |
| --- | --- |
| **적재**(outbox 한 행) | **송신 현황·재처리**는 `W-06-10` |

**규칙**: 확정 성공 토스트에 **「전송됨」이라 쓰지 않는다.**

```
✅ 출하가 확정됐습니다 — ERP 전표는 대기열에 실렸습니다
   전송 결과는 연계 현황 화면에서 확인합니다
```

⚠ **`erp_delivery_no` 는 송신 성공 후에 채워진다** — 확정 직후에는 비어 있는 것이 정상이다. **G-9를 적용해** 「없음」이 아니라 **「전송 대기」**로 보인다.

⚠ **`conflictCause` 에 `erpSync` 가 있다**(공유계약 B-1 확장) — ERP 배치가 같은 행을 건드리면 409가 온다. 재로드하면 풀린다.

### §5-4. 확정 전 관문 — **셋을 서버가 판정한다**

| 관문 | 근거 |
| --- | --- |
| **피킹 완료** | 라인 전체가 `pickedQty` = `allocatedQty`(`ShipmentRequestLine.pickedQty`) |
| **검사 완료** | `shipping_inspection_required` 인 라인은 **합격**이어야 한다 |
| **Release** | 배분된 LOT 이 전부 Release — 결정 10 |

**화면이 이 판정을 하지 않는다** — `W-04-02`의 「진행」 열과 **같은 원천**을 쓴다(§9-1 계약 후보). 프런트가 세 조건을 각자 조합하면 **목록과 상세가 다른 답을 낸다.**

⚠ **막힌 이유를 목록에서 보인다** — 「검사대기 ⛔」·「피킹중 ⛔」. G-3(비활성 사유는 「어떻게 풀 것인가」)를 **목록 수준으로** 올린 형태다(`W-01-13` §9-4와 같은 규칙).

### §5-5. ⚠ 운전자 이름이 **실명 자유 텍스트**다

```
driver_name   varchar(100)   ← 마스터 FK 가 아니다
```

**운송사는 FK 인데 운전자는 텍스트다.** 매번 손으로 적고 오타가 남는다.

**A-11로 물러난다** — 그대로 받되 **최근 입력값을 제안**한다(같은 운송사의 직전 운전자). 마스터를 만들지 않는다 — 운전자는 자주 바뀌고 우리가 관리할 대상이 아니다.

⚠ **⛔ 공개 저장소 반출 경계** — 이 값은 **담당자 실명**이라 착수 통지·이슈에 예시로도 쓰지 않는다. 합성값을 쓴다.

### §5-6. 오프라인 금지 — **C-5의 「온라인 전용」**

| 근거 | |
| --- | --- |
| ERP 송신 적재 | outbox 라 큐잉이 가능해 보이지만 |
| **Release 판정** | C-6 — 판정값은 캐시하지 않는다 |
| **재고 차감** | 원장 전기라 동시성 판정이 필요하다 |

**셋 다 온라인을 요구한다.** 관리웹이라 애초에 오프라인 대상이 아니지만(C-5), **그 근거를 적어 둔다** — 나중에 「모바일에서도 확정하자」가 나오면 이 목록이 답이다.

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **outbox 적재를 「전송됨」으로 말하지 않는다** — B-8이 「외부 호출은 트랜잭션 밖」이라 정했으므로 **확정 성공과 ERP 반영은 다른 사건**이다. 성공 토스트에 「전송됨」이라 쓰면 운영자가 ERP 를 확인하지 않고, **실패가 며칠 뒤에 발견된다.** 「대기열에 실렸습니다 + 결과는 연계 현황에서」가 정확하다. C-7(저장 피드백 2등급)의 **연계 판** (§5-3)
2. **송신 결과가 채우는 필드는 「없음」이 아니라 「대기」로 보인다** — `erp_delivery_no` 가 확정 직후 비어 있는 것은 **정상**인데, 빈칸으로 두면 「실패했나」로 읽힌다. G-9(모르는 값과 없는 값을 다르게)에 **「아직 안 온 값」**을 더한다 (§5-3)
3. **오프라인 금지의 근거를 화면이 적어 둔다** — 관리웹이라 C-5로 자동 제외되지만, **왜 안 되는지**(판정값 캐시 금지 · 원장 동시성 · outbox)를 남기지 않으면 나중에 「모바일에서도 확정하자」가 나왔을 때 처음부터 따진다. **C-5에 「금지 근거를 적는다」를 더한다** (§5-6)
