# P-04-02 · 납품·포장 라벨 출력

## §0. 요약

- **개요**: POP(Electron 키오스크) 화면. 물류 출하담당이 납품라벨·포장라벨을 발행·재출력한다. 포장라벨은 포장 즉시, 납품라벨은 OQC 합격 후에만 발행되어 발행 시점이 갈리지만 한 화면에서 종류를 먼저 골라 처리한다. 라벨 이미지는 서버가 그린다.
- **주요 데이터**: `app.document_issue_log`(문서유형·대상유형+대상 다형 참조·회차 `issue_seq`·재발행 사유·발행자·단말·프린터), `inventory.handling_unit`, `logistics.shipment_lot_allocation`.
- **핵심 액션**: 라벨 종류 선택 → 대상 선택(납품라벨은 합격 건만) → 재발행이면 사유 선택 → 프린터 선택 → 미리보기 → 발행·인쇄(현재는 계약 미착지로 비활성).

> **§K 출력물 6조항 전건이 걸리는 화면**이고, 04에서 **발행 시점이 둘로 갈리는 유일한 자리**다(사전 발행 ↔ 합격 트리거).

## §5. 액션·상태

### §5-1. ⭐ 발행 시점이 둘로 갈린다 — **그래서 화면이 하나다**

인벤토리 근거가 「발행 시점 상이 → 분리」라 적었는데, **분리된 것은 `P-04-01`(포장 실적)과 이 화면**이고 **라벨 두 종류는 한 화면에 있다.**

| 라벨 | 발행 시점 | 왜 |
| --- | --- | --- |
| **포장라벨** | **포장하면 바로** | 물리적으로 붙여야 다음 공정이 식별한다 |
| **납품라벨** | ⛔ **OQC 합격 후에만** | 고객에게 나가는 것이라 불합격품에 붙으면 안 된다 |

**화면 규칙** — 종류를 먼저 고르고, **납품라벨을 고르면 대상 목록이 「합격」만 활성**된다.

```
CTN-…-0093  ● 검사 대기   ⛔ 발행 불가
```

⚠ **G-3 적용** — 「왜」가 아니라 **「어떻게 풀 것인가」**를 담는다: 「OQC 판정이 나면 발행할 수 있습니다」.

### §5-2. ⛔ 납품라벨과 포장라벨을 가를 값이 **주석에 없다**

```
document_type_code   -- LABEL | COA | TRACE_REPORT 등
```

**`LABEL` 하나뿐이다.** 그런데 이 화면은 **두 종류를 다르게 다룬다**(발행 시점·대상·트리거).

**두 갈래가 있다.**

| 안 | 방법 |
| --- | --- |
| ① 유형 값을 나눈다 | `DELIVERY_LABEL` · `PACKING_LABEL` |
| ② `target_type_code` 로 가른다 | 포장 단위면 포장라벨, 출하 배분이면 납품라벨 |

**②로 물러난다** — 값 목록이 미정이라 ①을 우리가 정할 수 없고, **대상 유형이 이미 갈려 있어** ②가 성립한다. ⚠ 다만 `uq_document_issue_log` 가 `(문서유형, 대상유형, 대상, 회차)` 라 **②로도 유일성이 성립한다**(대상유형이 키에 들어 있다) → §8-1.

### §5-3. 다형 참조와 `lot_id` 가 **병존한다** — A-10 v0.6 보완

`app.document_issue_log` 는 A-10 이 **v0.6 보완의 근거로 든 바로 그 테이블**이다.

| 화면 | `target_id` | `lot_id` |
| --- | --- | --- |
| `P-01-01`·`P-02-07` 라벨 | LOT | **같은 값** |
| `P-02-05` 인식표 | 개체(serial) | **소속 LOT — 다른 값** |
| **이 화면 · 포장라벨** | **포장 단위** | ⚠ **여러 LOT 이 들어 있다** |
| **이 화면 · 납품라벨** | **출하 배분** | 그 배분의 LOT |

⛔ **포장라벨은 `lot_id` 를 하나로 정할 수 없다** — 한 포장에 여러 LOT 이 들어간다(`handling_unit_content` 가 여러 행).

**포장라벨은 `lot_id` 를 비운다** — 한 포장에 여러 LOT 이 담기므로 한 칸으로 가리킬 수 없다. 추적은 `target_id`(포장 단위) → `handling_unit_content` 로 간다. **비운 이유를 §8에 적는다.** ⚠ **구판 A-11 인용을 정정한다** — v4.6 이 「물러난 수준을 명시한다」를 「확정대로 반영하고 모델 결손은 통지한다」로 바꿨다. 데이터 모델은 설계 결정을 앞설 수 없다.

### §5-4. ⭐ 재발행 사유를 **DB 가 강제한다** — K-2가 제약으로 서 있다

```sql
ck_document_reissue_reason  CHECK (issue_seq = 1 OR reissue_reason_code IS NOT NULL)
```

**공유계약 조항이 규약이 아니라 제약인 드문 경우다.** 화면이 안 받으면 저장 자체가 실패한다.

**K-1·K-6 도 함께 적용한다.**

```
ⓘ 재발행하면 회차 2 로 쌓이고 이전 기록은 지워지지 않습니다
   인쇄면에도 「재발행 2」가 찍힙니다
```

⚠ **K-6(회차를 인쇄면에도)이 중요하다** — 물리적으로 유통되는 라벨이라 **현장에 1회차와 2회차가 함께 굴러다닌다.** 인쇄면에 없으면 어느 것이 최신인지 알 수 없다.

⚠ **재발행 사유 값 목록이 미정이다** — `W-06-06` 소관. **3차가 「정상 업무 흐름」을, 01 트랙이 「인쇄 실패」를 후보로 올렸다**(#145 코멘트).

### §5-5. 인쇄는 **트랜잭션 밖**이다 — K-4

```
① 발행 기록 저장   document_issue_log INSERT     ← 트랜잭션 안
─────────────────────────────────────────────
② 서버 렌더링      라벨 이미지 생성              ← 밖
③ 물리 인쇄        프린터로 전송                 ← 밖
```

**K-5(라벨은 서버가 그린다 · 결정 18) 때문에 ②가 서버 호출이고, B-8이 「외부 호출은 트랜잭션 밖」이라 했다.**

**화면이 알아야 하는 것** — **①이 성공했는데 ③이 실패할 수 있다.**

| 상황 | 처리 |
| --- | --- |
| ① 실패 | 발행되지 않았다 — 다시 시도 |
| **③ 실패**(프린터 오류) | **기록은 남았다** — 다시 인쇄하면 **회차 2**가 되고 **사유 = 「인쇄 실패」** |

⚠ **그래서 「인쇄 실패」가 재발행 사유 값으로 필요하다** — 없으면 사용자가 다른 사유를 골라 기록이 오염된다.

### §5-6. ⛔ 계약이 미착지다 — **발행을 비활성한다**

`app.document_issue_log` 계약이 `app-공통.json` 에 아직 없다(01 트랙이 지목한 **횡단 3종 중 둘째**).

**A-11로 물러난다** — 화면 골격은 다 그리고 **발행 버튼만 비활성 + 사유**.

```
⚠ 출력물 발행 계약이 준비되면 열립니다
```

⚠ **`W-04-03`(OQC 검사성적서)도 같은 계약을 기다린다** — 두 화면이 한 계약에 묶여 있다.

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **기록은 남고 인쇄만 실패하는 경우를 재발행 사유가 받아야 한다** — K-4가 「인쇄는 트랜잭션 밖」이라 정했으므로 **①(기록) 성공 + ③(인쇄) 실패**가 정상적으로 생긴다. 그때 다시 인쇄하면 **회차 2 + 사유**가 되는데, **「인쇄 실패」 값이 없으면 사용자가 다른 사유를 골라 기록이 오염된다.** 조항이 만든 상태에는 그 상태를 표현할 값이 함께 있어야 한다 (§5-5)
2. **다형 참조와 병존하는 FK 는 「하나로 정할 수 없는」 경우가 있다** — A-10 v0.6 보완이 「둘이 같은 대상인지 먼저 확인한다」였는데, **포장라벨은 한 포장에 여러 LOT 이라 `lot_id` 를 정할 수 없다.** 「같다/다르다」가 아니라 **「정할 수 없다」가 세 번째 갈래**다 — 비우고 다형 쪽으로 추적한다 (§5-3)
3. **POP 에서 조건부 구획은 접었다 펼친다 — 늘 띄우면 예산을 잠식한다** — E-1 슬랙이 0이라 재출력 구획 184px 를 상시 두면 **목록이 3줄로 줄어든다.** 「이 구획은 언제 펼치는가」를 §3에 못박는다 (§3-1)
