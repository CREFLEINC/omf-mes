# P-02-11 · 러닝체인지 부품 교체 등록

## §0. 요약

- **개요**: POP에서 작업자가 설비를 멈추지 않고(설비 무중단) 같은 세션 안에서 신규 부품 LOT을 스캔해 교체를 등록하는 화면이다. **생산 당일 교체 시점 지정 = 신규 부품 등록**만 다루며, 계획 분할 시점 지정은 관리자가 웹에서 지정하면 시스템이 자동 실행한다(화면 없음).
- **주요 데이터**: `production.material_consumption`(31열 — 교체 전용 컬럼 **`replaced_consumption_id`**·**`change_reason_code`**, 기존 투입과 같은 테이블), `trace.lot`(19열), `mdm.mold`, `production.work_session`.
- **핵심 액션**: 신규 부품 LOT 스캔 → 교체 대상·사유 선택 → **교체 등록**(`replaced_consumption_id`로 이전 투입을 남긴 채 잇는다 — 지우지 않는다). 게이팅은 `P-02-03`과 같은 `can_input_material` 플래그를 쓴다.

> 작성일: 2026-08-04 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 이 장에서 **「W/O 무분할·생산LOT만 분할」**을 다룬다. 확정 규칙이 데이터에 자리를 못 찾았던 사례였으나, `Lot.bomSnapshot` 신설로 2026-08-30 되살렸다(§5-3).

## §5. 액션·상태

### §5-1. 단말 게이팅 — `can_input_material`

교체도 자재 투입이므로 `P-02-03`과 **같은 플래그**를 쓴다. 별도 플래그가 필요하지 않다.

> `P-02-08`(포장)·`P-02-10`(중단)의 미매핑과 대조된다 — **교체는 투입의 한 형태**라 기존 플래그가 맞는다.

### §5-2. 교체는 지우지 않고 잇는다

```
replaced_consumption_id   →  이전 투입을 가리킨다
corrects_consumption_id   →  정정을 가리킨다 (다른 개념)
```

**둘이 다르다.**

| 컬럼 | 뜻 |
| --- | --- |
| `corrects_consumption_id` | **잘못 기록한 것을 고친다** — 원래 투입이 없었던 셈 |
| **`replaced_consumption_id`** | **실제로 교체했다** — 이전 투입도 실재했다 |

러닝체인지는 **후자**다. 이전 부품도 실제로 쓰였고 그 시점까지의 제품에 들어갔다. 화면은 이전 투입을 **남긴 채** 새 투입을 잇는다 — B-3(이력 불변).

### §5-3. ✅ R42의 「생산LOT만 BOM 스냅샷별 분할」을 되살렸다 (2026-08-30)

**R42** — 「W/O **무분할** · **생산LOT만 BOM 스냅샷별 분할**」 · **R43** — 「투입 Validation = **해당 LOT BOM 기준**」

**W/O 쪽은 이미 있었다.**

```
work_order.operation_settings_snapshot   jsonb   ← W-02-04 §5-2
```

**생산LOT 쪽도 계약에 생겼다.** `Lot.bomSnapshot`(01 계약, jsonb) — 서버가 선발행(`W-02-04`) 시점에 자동으로 채운다. 화면·클라이언트가 값을 만들어 보내지 않는다(`LotCreate`에는 없다).

| R42가 요구하는 것 | 데이터 |
| --- | --- |
| 생산LOT마다 BOM 스냅샷이 다르다 | ✅ `Lot.bomSnapshot`(계약에 신설) |
| 투입 Validation을 **해당 LOT의 BOM**으로 한다(R43) | ✅ LOT이 자기 BOM 스냅샷을 갖는다 — `P-02-03` 오투입 판정이 이 값을 본다 |

**`lot.parent_lot_id`로 분할은 그대로 표현하고**, 이제 「이 LOT은 BOM-A로, 저 LOT은 BOM-B로 만들었다」도 `bomSnapshot`이 담는다.

**화면은 교체를 기록한다**(`replaced_consumption_id`) — 그리고 **R43의 「해당 LOT BOM 기준 Validation」도 확정대로 선다.** `P-02-03`의 오투입 판정은 `Lot.bomSnapshot`이 있으면 그 값을 보고, 없으면(자재·제품 LOT처럼 `bomSnapshot`이 null인 경우) W/O BOM으로 물러난다.

> ✅ **되살렸다(2026-08-30)** — 계약이 `Lot.bomSnapshot`을 신설해 확정대로 그렸다. 저장 컬럼(`trace.lot`)은 데이터 모델 담당에게 통지 — 기다리지 않는다. §8-2 종결.

### §5-4. 「같은 세션」이 전제다

프로세스가 **「작업자·POP **같은 세션**」**이라 못박는다(4단계 확정 ⑥). 즉 **작업을 멈추지 않고**(설비 무중단) 세션 안에서 교체한다.

`material_consumption.work_session_id`에 현재 세션이 붙는다. **세션이 없으면 교체 기록이 세션 밖에 남는다** — `P-02-10` §5-2와 같은 문제이나 nullable이라 성립은 한다.

### §5-5. 계획 분할은 이 화면이 아니다

02-S-B 태스크 ①은 **「관리자가 웹에서 계획 분할 시점 지정 → 시스템 자동 실행(화면 없음)」**이다.

**이 화면은 태스크 ②(생산 당일 교체)만** 다룬다. 계획 분할 지정 화면이 관리웹에 있어야 하는데 **인벤토리에 없다** — §8-3.

> ⚠ 잔여로 남은 것 — 「분할 지정 타이밍 = **편성 시점 + 진행 중 W/O 양쪽 지원 필요**」(매핑02 보류결정 ⑥). 진행 중 W/O를 나누려면 화면이 필요하다.

## §9. 이 장에서 나온 공유 계약 후보

1. **「정정」과 「교체」를 구분한다** — `corrects_*`는 없었던 일로 만들고 `replaced_*`는 실재했던 것을 잇는다. 화면이 둘을 섞으면 이력이 왜곡된다 (§5-2)
2. ~~확정 규칙이 데이터에 자리가 없으면 화면은 물러난 수준을 명시한다~~ — 이 화면이 A-11 신설의 계기였다(구판 v0.6). **A-11은 2026-08-30 v4.6으로 재판정됐다** — 「물러난 수준을 명시한다」가 아니라 「데이터 모델 상태와 무관하게 확정대로 그대로 반영하고, 모델 결손은 통지만 하고 기다리지 않는다」가 정본이다. 이 화면 자신도 §5-3에서 그 재판정대로 되살렸다(§5-3)
