# P-02-12 · 긴급 W/O 현장 투입·실적

## §0. 요약

- **개요**: 긴급 W/O(P/O 비귀속·발행자 직접 전개)의 현장 실행 전 구간을 다루는 POP 진입 화면이다. **정상 경로 화면을 그대로 재사용**하고 긴급 플래그만 유지한다(4단계 확정) — 투입·실적용 화면을 별도로 만들지 않는다. ⛔ 다만 확정(02-S-D 「P/O 비귀속」)과 물리 모델(`work_order.production_plan_id` NOT NULL → `production_plan.production_order_id` NOT NULL 체인)이 정면 충돌해 **긴급 W/O 자체가 지금 데이터로 만들어지지 않는다**(§5-2, 데이터 모델 판단 대기 `#76`). 이 불일치가 화면 골격을 바꾸지는 않아 차단 등급은 아니다.
- **주요 데이터**: `production.work_order`(35열 — `production_plan_id` NOT NULL·`work_order_type_code`), `planning.production_plan`(`production_order_id` NOT NULL) · 투입·실적은 `P-02-03`·`P-02-04`와 **같은 테이블**(`material_consumption`·`production_result`)을 공유하며 별도 테이블이 없다.
- **핵심 액션**: 긴급 W/O 목록에서 항목 선택 → **정상 화면(자재 투입 `P-02-03`, 실적 입력 `P-02-04`)으로 이동**하며 긴급 플래그를 유지한다. 긴급 W/O 발행 자체는 관리웹(`W-02-07`) 소관이라 이 화면이 만들지 않는다.

### §4-B. 투입·실적

`P-02-03`(투입)·`P-02-04`(실적, 앵커)와 **같은 테이블**을 쓴다. 긴급이라고 별도 테이블이 없다.

## §5. 액션·상태

### §5-1. 이 화면은 진입점이다

**4단계 확정** — 「현장 실행 전 구간 = **정상 경로 화면 재사용 + 긴급 플래그**」

긴급이라고 투입·실적 화면을 따로 만들지 않는다. 이 화면은

1. **긴급 W/O 목록**을 보이고
2. 선택 시 **정상 화면으로 보내되 긴급 플래그를 유지**한다

**긴급 W/O 발행 자체는 관리웹**(`W-02-07`)이다 — 프로세스가 「발행자 직접 전개」라 하고, 인벤토리에 `W-02-07`(긴급 W/O 발행)이 실재한다.

### §5-2. ⛔ 확정과 데이터가 정면으로 부딪힌다

**확정** — 02-S-D 태스크 ① 「긴급 W/O 발행(**P/O 비귀속** · 발행자 직접 전개 · 별도 승인 없음)」

**데이터** — 실측

```
production.work_order
    production_plan_id   bigint NOT NULL  REFERENCES planning.production_plan

planning.production_plan
    production_order_id  bigint NOT NULL  ← P/O
    bom_id               bigint NOT NULL
    routing_id           bigint NOT NULL
```

**W/O → 생산계획 → P/O 체인이 전부 `NOT NULL`이다.** 즉 **P/O 없이는 W/O를 만들 수 없다.**

| 확정이 요구하는 것 | 데이터 |
| --- | --- |
| 긴급 W/O는 **P/O 비귀속** | ⛔ `production_plan_id` NOT NULL → `production_order_id` NOT NULL |
| 발행자가 **직접 전개** | ⛔ 생산계획(`bom_id`·`routing_id` NOT NULL)이 선행돼야 한다 |

**세 가지로 읽을 수 있다.**

| 해석 | 뜻 | 대가 |
| --- | --- | --- |
| **가. 더미 P/O·계획을 만든다** | 긴급용 P/O를 자동 생성해 체인을 채운다 | ERP 정본 원칙(R07 「P/O = ERP 발행·MES 수정 불가」)과 충돌 |
| **나. 컬럼을 nullable로** | `production_plan_id`를 nullable로 바꾼다 | 데이터 모델 변경 필요 |
| **다. 긴급 전용 계획** | MES가 만드는 「긴급 생산계획」을 허용 | `production_order_id`가 여전히 NOT NULL이라 P/O가 필요 |

**셋 다 데이터 모델 담당의 판단이 필요하다.** 화면이 정할 수 있는 것이 아니다.

> ⚠ **이것이 이 차수 세 번째 확정↔모델 불일치이고, 성격이 가장 무겁다** — 앞의 둘(`W-02-04` 선발행 · `P-02-11` LOT BOM 스냅샷)은 **표현이 어색한 것**이었으나 이것은 **아예 만들 수 없는 것**이다.

### §5-3. 통제 우회 — 데이터에 근거가 없다

**✓확정 QA #9** — 「작업 통제 = 차단/경고/미적용 **3단계 정책 설정형** + **긴급 W/O 우회 허용**」

**우회를 표현할 컬럼이 없다.** `work_order`에 「통제 우회」 플래그가 없고, 통제 정책 자체(3단계)를 담을 테이블도 확인되지 않는다.

`work_order_type_code = 긴급`으로 **서버가 판단**하는 것으로 설계한다 — 유형이 긴급이면 점검 게이트를 건너뛴다.

> ⚠ 다만 **점검 게이트 자체가 `P-02-01`·`P-02-02`이고 #67로 보류**됐다. **우회할 대상이 지금 없다** — 이 화면의 「통제 우회」는 실질적으로 무의미하다. §8-3.

### §5-4. 자재 부족 시 — 수동 출고 요청

02-S-D 태스크 ② — 「부족 시 **「추가 자재 출고 요청」 수동 + 사유**(대응 화면 = `W-02-10` **[추정]** · 도식 미작화)」

**정상 경로는 자동**(R29 「W/O 생성 완료 → 출고요청 자동 발행」)인데 **긴급은 수동**이다. `W-02-04` §5-5의 ④가 「긴급 W/O 제외」인 이유다.

화면은 **부족을 감지하면 `W-02-10`을 안내**한다. 다만 `W-02-10`은 신뢰도 **추정**이고 5차 대상이다.

## §9. 이 장에서 나온 공유 계약 후보

1. **「예외 경로」가 정규 체인의 `NOT NULL`에 걸리면 화면이 아니라 데이터가 답해야 한다** — 긴급·무발주 같은 우회 경로는 정규 참조를 채울 수 없다. 화면이 더미 데이터로 우회하면 정본이 오염된다 (§5-2)
2. **우회 규칙은 우회 대상이 있을 때만 의미가 있다** — 「긴급은 점검을 우회한다」가 점검 화면 부재 시 공허하다. 규칙의 전제를 스펙이 확인한다 (§5-3)
