# M-02-02 · 수리 왕복 투입·반출 스캔

> 작성일: 2026-08-05 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **처분 유형 중 「선별」만 실행 결과 테이블을 갖고 「재작업·수리」는 없다.**

## §0. 요약

- **개요**: 모바일(360×720dp · 스캐너 일체형 PDA) 스캔형 화면. 작업자가 수리 공정의 투입 스캔과 반출 스캔을 한 화면에서 처리한다(확정) — 같은 수리이력 레코드의 시작·종료. ⛔ 온라인 전용이며, **수리이력을 담을 실행 기록 테이블이 없어** 저장 자리 자체가 없다(등급은 차단이 아니라 조정).
- **주요 데이터**: 생산불량LOT·수리이력(⛔ 담을 테이블 없음) · 구조적 최근접 `quality.sorting_result`(17열 — `started_at`/`ended_at` 짝) · `quality.disposition_decision` · `quality.defect_record`(기록 전용, 읽기) · `production.work_order`(`rework_source_*` 3열).
- **핵심 액션**: 탭 전환(투입/반출) → 불량 LOT 스캔(포커스 고정) → 수리 수량 입력 → **투입 등록**/**반출 등록**(⚠ 저장 자리 부재로 비활성 + 사유 표시).

## §5. 액션·상태

### §5-1. ⛔ 수리 실행 기록 테이블이 없다 — 처분 유형 중 「선별」만 있다

**02-S-I 태스크 5가 「수리이력 기록」**이고 인벤토리도 주요 데이터에 **「수리이력」**을 명시하는데, 물리 모델 129테이블에 대응이 없다(실측 — `repair`·`수리` 검색 0건).

**구조적으로 가장 닮은 것을 찾았다.**

```
quality.disposition_decision        처분 결정 (disposition_type_code)
   └─ quality.sorting_result        「선별」의 실행 결과   ← 실재
   └─ (재작업의 실행 결과)                                 ← ⛔ 없다
```

`sorting_result`가 **정확히 이 화면이 필요로 하는 모양**이다:

| `sorting_result` | 이 화면이 필요한 것 |
| --- | --- |
| `started_at` timestamptz **NOT NULL** | **투입 시각** |
| `ended_at` timestamptz (nullable) | **반출 시각** — 반쪽 상태 허용 |
| `worker_id` NOT NULL | 작업자 |
| `status_code` | 진행/완료 |
| `good_qty`·`defect_qty`·`hold_qty` | 수리 성공/실패/보류 |
| `good_lot_id`·`defect_lot_id` | **재투입 LOT** |
| `disposition_decision_id` NOT NULL | 처분 결정 연결 |

**「선별」은 실행 결과를 갖는데 「재작업·수리」는 갖지 않는다.** 처분 유형이 대칭이 아니다.

**A-11 적용 — 물러난 수준**:

| 확정 | 물러난 수준 |
| --- | --- |
| 수리이력 기록(투입·반출 왕복) | ⛔ **저장 불가** |
| 재투입 참조 필드 추적 | ⛔ **불가** |
| 왕복 소요 시간 집계 | ⛔ **불가** |
| 수리 대상 식별 | ✅ `defect_record`로 가능 |

→ **§I 신규 후보** §9-1 · **`[docs→데이터모델]` 이슈**.

### §5-2. 결정 09 규칙 ⓒ가 실행될 수 없다

> **✓설계확정 결정 09 규칙 ⓒ**: 「재판정 = **원 불량 레코드 갱신** + 수리이력 연결 · **신규 레코드 금지**」

```
quality.defect_record:
    created_at  timestamptz NOT NULL DEFAULT clock_timestamp()
    created_by  bigint
    (updated_at 없음 · version_no 없음)
```

**갱신 컬럼이 없다.** 기록 전용 테이블에 「원 레코드 갱신」을 지시한 것이다.

⚠ **UPDATE 자체가 막히는 것은 아니다** — 감사 컬럼이 없을 뿐 SQL은 통과한다. **그러나 B-1 낙관적 잠금을 걸 수 없고**(`version_no` 없음) **언제 누가 고쳤는지 남지 않는다.**

**A-11 물러난 수준**: 「신규 레코드 금지」는 지키되 **갱신 이력은 `audit.audit_event` 의존**이다 — 그 사용 규약이 없다(§I-5 · #68).

### §5-3. 왕복이 1화면인데 **반쪽 상태를 저장할 곳이 없다**

`M-01-10`(반출↔도착)·`M-02-01`(인계↔수령)과 같은 형태인데 **저장 테이블이 없어 문제가 더 크다.**

```
① 수리 투입 스캔  ──→  (수리 작업 · 실물 · 시간 경과)  ──→  ② 수리 반출 스캔
```

**②에서 ①을 찾을 수 없으면 왕복이 성립하지 않는다.** 화면이 「투입 대기 목록」을 보여야 하는데 **그 목록의 원천이 없다.**

**임시 설계**(테이블이 생길 때까지):

| 안 | 동작 | 대가 |
| :-: | --- | --- |
| **① 화면 비활성** | 「수리 이력 저장 자리가 없습니다」 | 02-S-I가 통째로 멈춘다 |
| **② 로컬 목록만** *(권고 아님)* | 단말이 투입 목록을 갖는다 | 단말이 바뀌면 사라진다 · **온라인 전용과 모순** |
| **③ `defect_record` + `remarks`** | 투입 사실을 원 불량에 메모 | 왕복 시각·수량이 안 남는다 |

**어느 것도 충분하지 않다.** 이 화면은 **테이블이 생겨야 제대로 선다** — 다만 **화면 골격(투입/반출 탭 · 스캔 · 수량 · 목록)은 테이블이 어떤 모양이든 같다.**

⚠ **그래서 등급은 「차단」이 아니라 「조정」이다.** `P-02-12`(#76)에서 정리한 기준 그대로 — **「데이터가 안 만들어지면 보여줄 게 없다」와 「화면 골격이 바뀐다」는 다르다.**

### §5-4. R75 — 재투입은 원 LOT과 무관하다

> **R75**: 「수리 재투입 = **I/O 검사 과정부터 생산 추적 재시작**」(REQ-OA-0004)
> **✓확정 2026-07-15**: 「재투입 성공분 = **재투입 시점 진행 중 생산LOT에 등록**(**원 LOT 무관**) · 생산불량LOT **재투입 참조 필드**로 추적」

**수리된 물건은 원래 LOT으로 돌아가지 않는다.** 그때 돌고 있는 LOT에 합류한다.

| | 원 LOT | 재투입 후 |
| --- | --- | --- |
| 물리적 물건 | PLOT-…0031의 불량 40개 | 그대로 |
| **기록상 소속** | — | **PLOT-…0047**(그때 진행 중) |
| 추적 | | **재투입 참조 필드**로 원 불량과 연결 |

⚠ **「재투입 참조 필드」가 없다**(§5-1). `production_result.rework_qty`(실측)는 **수량만** 세고 어느 불량에서 왔는지 모른다.

**이 화면은 반출까지** 하고, 재투입 등록은 **`P-02-03`(자재 투입 스캔)** 또는 `P-02-04`(작업실적)가 맡는다 — 프로세스의 복귀가 「메인 PQC 분기 재진입」이라 그쪽이다. ⚠ **다만 「포인터-only·실제 커넥터 없음」**이라 연결이 도식에 없다 → §8-2.

### §5-5. `defect_record.work_order_id NOT NULL` — 자재 불량은 대상이 아니다

`M-01-10` §5-5에서 나온 것과 같은 제약이다. **이 화면의 대상은 「생산불량LOT」**(인벤토리 주요 데이터)이라 문제되지 않는다 — 02 도메인 화면이므로 W/O가 항상 있다.

⚠ **다만 03 재검 불량분이 진입 원천에 포함**된다(02-S-I 진입 조건 — 「노트 I-1 원천 필드로 포괄」). 재검이 IQC(자재)면 W/O가 없다.

**권고**: 이 화면은 **생산 불량만** 받는다. 자재 불량 수리는 범위 밖으로 둔다 → §8-3.

> **「부분」의 뜻**: `M-01-09`(호퍼)는 **한 구획만** 근거가 없었지만, 이 화면은 **저장 대상 전체**가 없다. 화면 골격(탭·스캔·수량·목록)이 테이블 모양과 무관해 차단은 아니나, **실제 동작이 가장 늦어질 화면**이다.

## §9. 이 장에서 나온 공유 계약 후보

1. **⛔ 처분 유형이 대칭이 아니다 — 「선별」만 실행 결과 테이블을 갖는다** — `disposition_decision` 아래 `sorting_result`는 있고 재작업·수리는 없다. **요청할 때 「무엇과 같은 모양으로」를 함께 적으면** 데이터모델 담당이 판단하기 쉽다 (§5-1)
2. **「원 레코드를 갱신한다」는 확정은 그 테이블이 갱신 가능한지 확인해야 성립한다** — `defect_record`는 `created_at`만 가진 기록 전용인데 결정 09 ⓒ가 갱신을 지시한다. **A-11의 물러난 수준에 「이력이 남지 않는다」를 명시** (§5-2)
3. **저장 자리가 통째로 없는 화면도 골격은 확정할 수 있다** — 「데이터가 없으면 보여줄 게 없다」와 「화면 골격이 바뀐다」는 다르다(#76 판정 기준). **다만 「실제 동작 시점이 가장 늦다」를 스펙이 명시**해 개발 순서에 반영되게 한다 (§5-3)
