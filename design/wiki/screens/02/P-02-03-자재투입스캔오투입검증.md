# P-02-03 · 자재 투입 스캔·오투입 검증

## §0. 요약

- **개요**: POP(1024×768 터치+QR 스캔)에서 작업자·현장반장이 라인 자재 수령을 확인하고 자재LOT·금형을 스캔해 투입을 확정하는 스캔형 화면이다. 단말 게이팅(`can_input_material`)의 첫 사용이자 계보(genealogy, 자재LOT→생산LOT)가 시작되는 지점이다.
- **주요 데이터**: `production.material_consumption`(투입 기록 — `bom_component_id`·`actual_use_process_id`·`idempotency_key`) · `logistics.shopfloor_receipt_line`(라인 수령) · `trace.lot_relation`(계보 — `trace_accuracy_code`) · `production.work_session`(세션) · `mdm.terminal_process`(단말 게이팅).
- **핵심 액션**: 라인 수령 검증 확인 → 자재LOT·금형 QR 스캔 → 오투입(BOM 불일치) 판정 — NG면 자재LOT 스캔부터 루프백 → 투입 확정(계보 생성).

> 작성일: 2026-08-04 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ★ **단말 게이팅(`can_input_material`)의 첫 사용**이자 **계보(genealogy)가 시작되는 지점**. 이 장에서 **오투입 판정**과 **추적 정확도**를 다룬다.

## §5. 액션·상태

### §5-1. ★ 단말 게이팅 — `can_input_material`

```
mdm.terminal_process.can_input_material   boolean NOT NULL DEFAULT false
                                          UNIQUE (terminal_id, process_id)
```

**이 단말이 이 공정에서 자재를 투입할 수 있는가**가 데이터로 정해져 있다. **기본값이 `false`**이므로 명시적 허용이 필요하다.

화면은 진입 시 확인하고, 없으면 **「투입 확정」을 비활성**하고 사유를 보인다(F-1 · G-3).

> ⭐ **`can_input_material`을 쓰는 화면은 `P-02-03`·`P-02-11` 2화면이다**(공유계약 F-1 실증표).
> 실증 화면 목록과 플래그별 현황의 정본은 **F-1 실증표 하나**이며 이 절은 그것을 가리킨다 —
> 세는 값을 화면마다 복제하면 F-1 범위가 바뀔 때 화면마다 어긋난다.
> «(정합주: 2026-08-27 — 구 각주는 「`P-01-01`(`can_print_label`)에 이은 2번째 실증」이라
> 적었으나, `omf-mes#245`가 창고 POP을 F-1 적용 범위 밖으로 판정해 `P-01-01`의 게이팅 서술을
> 폐기하면서 그 선행항이 사라졌다. 함께 적혀 있던 「8플래그 중 6종」도 어느 시점 기준으로도
> 재현되지 않아 수치를 고치는 대신 문장을 폐기했다 — `omf-mes#246`)»

### §5-2. R37 — Release분만 투입할 수 있다

```
trace.lot.status_code = Release   →  투입 가능
                      = Hold      →  ⛔ 차단
                      = 한도승인   →  ⚠ §8-3
```

**스캔한 LOT의 상태를 서버가 판정한다.** 화면이 자체 판단하지 않는다.

`W-01-01`(IQC)·`W-01-10`(입고 확정)이 만든 상태가 여기서 소비된다 — **도메인 01의 판정이 도메인 02의 게이트가 된다.**

> ⭐ **2026-08-07 해소** — 「한도승인 자재를 투입할 수 있는가」는 **투입할 수 있다**. **한도승인품의 LOT 상태는 `정상`이다**(검사 기준에 못 미치지만 협의로 정상품으로 받기로 승인된 것). 투입 차단은 `불량`·`검사 대기`·`폐기` 셋에만 건다. → `design/raw/process/uiux/2026-08-07-E3-판정유형-제안안/LOT상태-확정기록.md` §2

### §5-3. ★ R39 오투입 판정 — 세 갈래로 갈린다

**✓확정 2026-07-14 문답 #5·#6** — 「오투입 판정 기준 = **BOM 품목 정합** · **출고 귀속 무관** · **교차 투입 허용**」

| 축 | 판정 | 데이터 |
| --- | --- | --- |
| **BOM 품목 정합** | 이 W/O의 BOM에 있는 품목인가 | `bom_component_id`가 **채워지면 정합** |
| **출고 귀속** | 이 W/O에 출고된 것인가 | ⚠ **무관** — `shopfloor_receipt_line_id`가 비어도 투입된다 |
| **교차 투입** | 다른 공정용 자재를 쓰는가 | ⚠ **허용** — `actual_use_process_id`가 그것을 기록한다 |

**즉 막는 것은 하나뿐이다** — BOM에 없는 품목. 나머지 둘은 **기록하되 막지 않는다.**

⭐ 그러므로 이 화면은 `M-01-09` 수령 라인의 **소비자가 아니다** — 의존은 **공유계약 B-9 의 nullable**(선행 없이도 성립 · 기록만 약해진다)이지 C-14·C-18 이 말하는 판정값 소비가 아니다. 전제 미충족 시의 화면 동작은 §6 두 행(「출고 귀속 없는 자재 → ✅ 통과 + 표시」 · 「라인 수령 미달 → ⚠ 경고」)이 이미 B-9 규칙을 충족한다.

```
BOM에 없음        →  ⛔ NG · 자재LOT 스캔부터 루프백 (태스크 ④)
BOM에 있음        →  ✅ 통과
  + 출고 귀속 없음  →  기록만 (shopfloor_receipt_line_id = NULL)
  + 다른 공정 자재  →  기록만 (actual_use_process_id 기록)
```

화면은 **통과한 것 중 「기록만 되는 것」을 표시한다** — 나중에 계보를 추적할 때 이 구분이 필요하다.

### §5-4. ★ `trace_accuracy_code` — 계보의 정확도를 데이터가 구분한다

`lot_relation`에 **추적 정확도** 컬럼이 있다. 이것이 §5-3과 맞물린다.

교차 투입·출고 무관 투입을 허용하면 **「이 생산LOT에 어느 자재LOT이 얼마나 들어갔는가」가 정확하지 않을 수 있다.** 여러 LOT을 섞어 쓰거나 호퍼를 경유하면 배분이 추정이 된다.

**`allocation_method_code`(배분 방법)와 함께 「이 계보가 얼마나 정확한가」를 기록한다.** 화면은 투입 방식에 따라 이 값을 정한다 — 1:1 스캔이면 정확, 호퍼 경유·혼합이면 근사.

> ⚠ **정합주(2026-08-27 · `omf-mes#246` 요청 밖 확인)** — 위 「화면이 정한다」는 **지금 실행할 수
> 없다.** 계약 일곱 파일 어디에도 `trace.lot_relation`에 대응하는 스키마가 없고
> `MaterialConsumptionCreate`에도 `traceAccuracyCode`·`allocationMethodCode`가 없다(재현:
> `grep -rn "traceAccuracyCode\|allocationMethodCode" design/wiki/api-contracts/openapi/` → 0건).
> **화면은 이 값을 보내지 않는다.** §8 미결 #2·#4가 값 목록을 확정할 때까지 정확도 판정은
> 서버가 갖는다 — 이 화면이 지원하는 1:1 스캔은 서버가 투입 형태만 보고 정할 수 있다.
> 값 목록이 확정되면 「화면이 정한다」로 되돌릴지 그때 판단한다.

> ⚠ **값 목록이 미확정**이라 어떤 등급이 있는지 모른다. 화면은 **1:1 스캔만 우선 지원**하고 나머지는 미결로 둔다. §8-4.

### §5-5. 세션 — `work_session_id`가 nullable이다

```
production.work_session
    session_no      integer NOT NULL CHECK > 0
    terminal_id     bigint NOT NULL          ← 세션이 단말에 묶인다
    shift_id        bigint NOT NULL
    started_at      NOT NULL / ended_at      nullable
    stop_reason_code
```

**세션은 「한 단말에서 한 교대 동안 이 W/O를 돌린 구간」**이다. `material_consumption.work_session_id`가 nullable이므로 **세션 없이도 투입이 기록될 수 있다** — 긴급 투입·사후 입력이 그 경우다.

화면은 **세션이 열려 있으면 붙이고, 없으면 연다.** 세션을 여는 것이 `can_start_work`인지는 `P-02-01`(#67로 보류) 소관이라 **이 화면은 열린 세션에 붙는 것만** 다룬다 — §8-5.

### §5-6. 입력 단위와 저장 단위가 다를 수 있다

```
input_qty  + uom_id           ← 저장 (기준단위)
entered_qty + entered_uom_id  ← 사용자가 실제로 친 것
```

작업자가 「2 BOX」라 치면 `entered_qty=2, entered_uom_id=BOX`로 남고, `input_qty`는 환산된 기준단위 값이 된다.

**환산은 서버가 한다** — `mdm.item_uom_conversion`이 정본이다. 화면은 두 값을 모두 보여 작업자가 확인할 수 있게 한다(공유계약 A-8 저장 단위).

### §5-7. 오프라인 — 이 화면이 POP 폴백의 첫 사례

예외 **E-14** 「네트워크 두절 — **폴백 확정**」. 데이터가 그것을 받쳐 준다.

```
idempotency_key         NOT NULL UNIQUE   ← 재전송해도 중복 안 됨 (C-2)
occurred_at ≠ recorded_at                 ← 발생과 기록 시각 분리
late_entry_reason_code                    ← 사후 입력 사유
```

**오프라인에서 스캔하고 복구 시 전송하면** `occurred_at`은 스캔 시각, `recorded_at`은 전송 시각이 된다. 화면은 **미동기 건수를 상시 표시**한다(C-1).

> ⚠ **POP 오프라인은 「W/O 선배포 생산」 한정**(결정 17)이다. 이 화면은 그 시나리오 안에 있으므로 폴백이 정당하다.

### §5-8. 이 화면이 보내지 않는 세 칸

1. **무엇을 안 보내나** — 투입 유형 · 작업자 · 단말. 셋 다 스펙이 「자동」이라 적었던 칸이다(§4-B).
2. **왜** — 작업자·단말은 서버가 인증에서 이미 안다. 같은 것을 두 경로가 말하면 어긋날 자리만 생긴다(`omf-mes#173` 2026-08-21 확정 — 검사 결과 저장에서 같은 두 칸을 뺐다).
3. **투입 유형은 이유가 다르다** — 서버가 인증에서 풀 수 있는 값이 아니다. 값 목록이 아직 축을 정합화하지 못해서 안 보낸다. 확정되면 이 절을 고친다.
4. ⛔ **화면이 상수를 박지 않는다** — 이력 불변(B-3)이라 투입은 정정이 아니라 새 기록으로만 고칠 수 있어, 승인된 적 없는 값이 원장에 남으면 되돌릴 수 없다. 개발팀이 스스로 이 판단을 했고 그것이 옳았음을 이 절이 확인한다.
5. **그래서 「투입 확정」 버튼의 비활성 사유가 사라진다** — 세 칸이 필수에서 빠지면 화면이 채울 수 없는 필수는 남지 않는다. 쓰기 배선을 만들어도 된다.

> ⚠ §5-4 정합주(`#246` 산출)와 겹치지 않는다 — 그쪽은 계보 정확도(`trace_accuracy_code`) 얘기이고, 이 절은 투입 유형·작업자·단말 셋을 다룬다.

⭐ 스캔 한 건이 곧 한 호출이다(공유계약 **C-3** 건별 저장 + 마지막 일괄 완료). **[투입 확정]** 은 그날 목록을 닫는 완료 동작이지 저장을 모아 보내는 버튼이 아니다 — 그래서 §6 의 「BOM 에 없음 → 자재LOT 스캔부터 루프백」이 스캔 자리에서 성립한다.

## §9. 이 장에서 나온 공유 계약 후보

1. **상류 도메인의 판정이 하류 도메인의 게이트가 된다** — `lot.status_code`(도메인 01의 IQC 판정)가 투입 가능 여부를 정한다. 화면이 자체 판단하지 않고 서버가 상태를 본다 (§5-2)
2. **「막는 것」과 「기록만 하는 것」을 화면이 구분해 보인다** — 오투입 판정에서 BOM 불일치는 막고, 출고 무관·교차 투입은 통과시키되 표시한다. 통과 = 정상이 아니다 (§5-3)
3. **계보의 정확도를 데이터가 구분하면 화면이 그 값을 정한다** — `trace_accuracy_code`. 1:1 스캔과 혼합 배분은 추적 신뢰도가 다르고, 그것을 나중에 알 수 있어야 한다 (§5-4)
4. **입력 단위와 저장 단위가 다르면 둘 다 보인다** — `entered_qty`/`entered_uom_id`가 별도 컬럼인 이유다. 환산은 서버가 하고 화면은 확인시킨다 (§5-6 · A-8 확장)
5. **오프라인 기록은 발생 시각과 기록 시각을 분리한다** — `occurred_at` ≠ `recorded_at`. 복구 시 전송된 것을 「지금 일어난 일」로 기록하면 실적 시각이 통째로 틀린다 (§5-7 · C-1 확장)
