# P-02-09 · 포장 라벨·인식표 재출력·부착

> **POP 공통 개정(2026-09-08)**: 글꼴·버튼·입력·선택·키패드·목록 행과 터치 영역은 관리웹 기본 밀도(E-3)를 사용한다. 본문의 구 56~72px 수치와 확대 터치 판정은 변경 이력이며 구현 기준이 아니다. 모든 선택형 목록은 선택값 + [선택] 버튼과 로컬 검색·목록 스크롤·[페이지 위]·[페이지 아래] 팝업(G-34)을 사용한다. 성공 피드백은 G-1의 POP 공통 규칙을 따른다. 로컬 기록·서버 반영·인쇄 결과를 구분하고 C-7 미확정 표식은 유지한다.

## §0. 요약

- **개요**: 포장 후 겉면에 다시 붙일 LOT 라벨·인식표를 재출력하는 POP 화면이다. 포장 작업자가 쓰며, 다른 라벨 화면(`P-01-01`·`P-02-04`)은 최초 발행이 정상 경로인데 이 화면만 **재발행이 정상 경로인 유일한 화면**이다.
- **주요 데이터**: 발행 기록(`app.document_issue_log`) — 재출력이 정상 경로지만 실제 발행 이력으로 회차와 사유를 판정한다. 포장 단위(`inventory.handling_unit`) 내용물이 LOT 단위 포장이면 LOT 라벨(`trace.lot`), 제품 단위 포장이면 인식표(`trace.serial_number`)로 재출력 대상이 갈린다.
- **핵심 액션**: 포장 단위 확인 → 같은 문서종류의 대상 선택(혼적 시 다건 가능·최대 1000) → 기존 발행 이력이 있는 대상이면 재출력 사유 선택 → **재출력**(필요 공정 전체의 `canPrintLabel` 필요).

## §3. 레이아웃 (POP — 1024×768)

공통 헤더의 **[화면 이동]**은 G-34를 따른다. 셸의 활성 POP 라우트 등록부에서 통합·폐지 화면을 제외한 후보 전체를 목록 팝업으로 표시한다. 후보 안 로컬 검색·스크롤·페이지 이동을 제공하고 선택 즉시 이동하며 미저장 입력 확인 팝업은 띄우지 않는다. 등록 검증·준비 전에는 업무 이동을 열지 않고, 등록 후 화면 이동이 실제 업무의 공정별 기능 구성·인증·서버 검증을 우회하지 않는다.

```
┌ 1024 ────────────────────────────────────────────────────────────────────┐
│ 재출력   HU-2026-0804-0007 · 박스           프린터 LP-02 ●  단말 POP-P1 ●│
├──────────────────────────────┬───────────────────────────────────────────┤
│ 《포장 단위》                │ 《재출력 대상》                           │
│  내용물                      │   [ ] LOT 라벨      LOT-…0031             │
│   LOT-…0031  ABC-123 100 EA │        발행 이력  1회 (08-04 14:20)       │
│   LOT-…0032  ABC-123  50 EA │                                           │
│  ⚠ 혼적(LOT 2건)             │   [ ] LOT 라벨      LOT-…0032             │
│                              │        발행 이력  1회                     │
│                              │                                           │
│                              │   [ ] 인식표        SN-…0201 ~ 0300      │
│                              │        발행 이력  1회                     │
│                              │   ─────────────────────────────           │
│                              │   재출력 사유  [ ▾               ]        │
│                              │   ⚠ 기존 발행 대상은 사유가 필요합니다     │
│                              │                                           │
│                              │           [   재출력   ]                  │
└──────────────────────────────┴───────────────────────────────────────────┘
```

**머리줄이 받는 것이고 좌단 구획은 내용물이다.** 포장 번호·유형은 진입 인자라 머리줄에만 둔다 —
공유계약 `E-1`·`E-4` 가 「공통 헤더와 주 액션은 화면 안에 고정한다」로 머리줄의 상시 표시를 보장하고,
`K-4` 가 프린터 상태를 「화면 머리에 상시 표시」로 요구한다. 좌단 《포장 단위》 구획이 답하는 물음은
「이 포장에 무엇이 들었나」이고, 그 내용물이 우단 《재출력 대상》을 고르는 근거다(§5-2).
«(정합주: 2026-09-10 — 구판 도면은 좌단 구획 첫 줄에 `HU-…0007  박스` 를 다시 실어 머리줄과 같은
값이 두 자리에 있었다. `P-02-13` §9-4 가 이 화면을 「좌단이 《포장 단위》 **내용물**」로 인용한다)»

⭐ **스크롤은 구획 안에서 한다**(`E-4`). 좌단 《포장 단위》 내용물 목록과 우단 《재출력 대상》
목록은 각각 자기 구획 안에서 스크롤하고, 화면 전체는 스크롤하지 않는다. 머리줄과 [재출력]
버튼은 화면 안에 고정한다(`E-1`). ⚠ 우단은 한 번에 최대 1000건까지 고를 수 있어(§6) 넘치는
것이 정상이다.

**발행 이력 회차를 대상마다 보인다.** 몇 번째 재출력인지가 §K-1의 핵심이다.

## §5. 액션·상태

### §5-1. ★ 재발행이 정상 경로인 유일한 화면

다른 라벨 화면(`P-01-01`·`P-02-04`)은 **최초 발행이 정상**이고 재발행이 예외다. 이 화면은 반대다 — **포장 후 겉면에 붙일 것을 다시 찍는 것이 본래 목적**이다.

다만 실제 이력이 없는 대상은 최초 발행(issueSeq=1)이며 사유를 남기지 않는다. 기존 이력이 있어 회차 2 이상인 대상에만 재발행 사유가 필수다. 기존 #516의 대상별 실제 이력 판정을 따른다.

> ✅ **「포장」이 재발행 사유 값에 있다.** 훼손·분실과 성격이 다른 정상 업무 흐름이고, `PACKAGING`(포장) 이 시드에 실려 있다 — 코드 사전 `CD-REISSUE-REASON` = `DAMAGED`(훼손) · `LOST`(분실) · `PRINT_FAILURE`(인쇄 실패) · `PACKAGING`(포장) · `QUANTITY_CHANGE`(재구성으로 수량 변경) **5값**(2026-09-03 등재). 값 목록은 `GET /mdm/code-values?codeGroupCode=REISSUE_REASON` 로 받는다(`G-32`). ⭐ **고객이 늘린다 — 위 값은 초기 시드다**(`G-31`). §8 미결 2. «(정합주: 2026-09-10 — 구표기는 「⚠ 「포장」이 재발행 사유 값에 **있어야 한다**」였다)»

### §5-2. 무엇을 재출력할지는 포장 구성이 정한다

| 포장 방식 | 재출력 대상 | 매수 |
| --- | --- | --- |
| **LOT 단위 포장** | **LOT 라벨** | 포장에 든 LOT 수만큼 |
| **제품 단위 포장** | **인식표** | 포장에 든 개체 수만큼 |

**`P-02-08`이 만든 `handling_unit_content`가 근거다.** 화면은 내용물을 읽어 대상 후보를 만든다.

선택 후보별 실제 발행 문서종류를 포함해 `GET /app/document-issues/summary`를 조회한다. LOT은 `PACKING_LABEL`(포장 라벨)/`LOT`(로트), 개체는 `IDENTIFICATION_TAG`(인식표)/`SERIAL_NUMBER`(개체) 조합이다. 문서종류·대상유형별로 기존 다건 `targetIds`를 묶고 한 요청의 1~1000 한도를 지킨다. 조합별로 조회하더라도 최종 선택 전체의 필요 공정을 모두 만족해야 한다.

> ⚠ **개체(인식표) 대상은 데이터로 좁힐 수 없다** — `handling_unit_content`에 개체 참조가 없다(`P-02-08` §5-2). 「이 박스에 든 개체가 어느 것인가」를 LOT + 수량으로만 알 수 있어 **범위 추정**이 된다. §8-3.

### §5-3. 다형 참조가 대상마다 갈린다

구 `P-02-07`에서 발견해 현재 `P-02-04`로 통합된 다형 참조 갈림이 여기서 실제로 문제가 된다.

```
LOT 라벨 재출력   target_type = LOT     · target_id = lot_id  · lot_id 같음
인식표 재출력     target_type = 개체     · target_id = serial  · lot_id 다름(소속)
```

**같은 화면이 두 대상 유형을 다룬다.** A-10 규칙 3(FK 우선)을 그대로 적용하면 인식표 재출력이 LOT 라벨로 잘못 기록된다 — **`target_type_code`로 먼저 판정해야 한다.**

`requiredProcessIds`는 생산 LOT **자체를 실제 발행한 W/O**의 공정이며 개체는 `SerialNumber.lotId`의 소속 생산 LOT을 거친다. 현재 기본 라우팅·투입 자재 생산 이력·계보 조상의 공정을 재귀 수집하지 않는다. 실제 발행 원천이 결손·모순이거나 유일하게 정해지지 않으면 null이다. 정수 ID는 정밀도 손실 없이 오름차순·중복 제거되어 오며, 같은 단말의 각 공정 `canPrintLabel=true`를 **전부** 요구한다. 첫 행·다른 공정 OR 합산은 없다.

이 화면의 LOT 대상은 생산 LOT이며 포장 단위 자체로 바꾸지 않는다. `PACKING_LABEL`(포장 라벨)/`HANDLING_UNIT`(취급 단위)은 물류 화면의 별도 유효 조합으로 `[]`다. 자재 LOT의 생산 문서 요청·잘못된 조합은 `[]`로 우회하지 않고 null/발행 422로 처리한다.

## §6. 예외

한 번의 발행 선택은 같은 documentTypeCode·최대 1000개 대상이다. 요약 읽기는 조합별/페이지별로 나눌 수 있지만 혼합 문서종류·1000개 초과 선택을 묵시적으로 여러 POST로 분할하지 않고 선택 조정 안내를 제공한다. 다른 문서종류는 사용자가 별도 발행 단위로 실행한다. 전체 AND와 원자성은 실제 한 POST의 모든 targets에 적용하며 서로 다른 POST를 하나의 원자적 작업으로 보장하지 않는다.

summary는 원천 읽기이지 권한 증명이 아니다. 서버는 인증 단말·실제 문서·대상으로 필요 공정을 재계산한다. 선택 대상 하나라도 불허/불명이면 한 요청의 발행 기록 전체를 만들지 않는다. 같은 공정의 단말 행 없음/false는 403, 부적합 대상·원천은 422다. 조회를 나누어도 화면의 최종 선택 전체를 AND로 검증하고 공정별 부분 발행을 하지 않는다. 인증·사번·프린터·재발행 사유·회차·멱등·물리 인쇄 경계는 유지한다.

문서종류 생략 조회의 null은 기존 건수 표시용이며 신규 생산 발행 활성에 쓰지 않는다. null이어도 이력/건수와 삭제 대상 `TYPE#id` 표시는 유지한다. `issueCount=0`은 미발행이라는 뜻이지 공정 불명이라는 뜻이 아니다.

발행 기록 생성과 인쇄 완료를 구분한다. 서버는 대상별 회차를 잠금 안에서 부여하고 한 발행 요청의 기록을 모두 생성하거나 모두 실패시킨다. 같은 요청 키 재전송은 해당 단계의 기존 결과를 재생한다. 재출력 실패를 새 개체 발번으로 복구하지 않는다(발행 통보 · `omf-mes#516`).

발행 이력의 목록·전체 건수·대상 표시명은 같은 조회 스냅샷에서 읽는다. 이를 대상 표시명의 발행 당시 영구 보존으로 해석하지 않는다. 삭제된 대상은 `TYPE#id` 형태로 표시하고 대상 이동을 제공하지 않으며, 과거 비활성 재발행 사유도 이력에서 숨기지 않는다. 과거 사유 표시와 신규 입력의 활성 사유 선택은 구분한다.

프린터는 명시적으로 매핑된 목록만 표시하며 기본 프린터는 최대 1개다. 요청의 `terminalId`를 우선하고 생략 시 인증 단말을 사용하며 둘 다 없으면 빈 목록이다. 상태는 저장된 값을 표시하고 과거 null은 `OFFLINE`(오프라인)으로 보인다. 화면이 상태를 추론하거나 실시간 폴링이 된 것으로 표시하지 않는다.

렌디션·물리 인쇄는 현재 기술적 미지원 범위다. 출력 요구는 유지하지만 발행 API 성공을 「인쇄 완료」로 안내하지 않으며 실제 인쇄 결과와 구분한다.

| 상황 | 처리 |
| --- | --- |
| 필요 공정 중 같은 단말 행 없음 또는 `canPrintLabel=false` | 선택 전체 재출력 **비활성** + 사유 (F-1) |
| 필요 공정 null·미조회 또는 부적합 문서/대상 | 재출력 비활성·원천/대상 확인 안내, 이력/건수는 유지 |
| 기존 발행 이력이 있는 대상의 재출력 사유 미선택 | 비활성 — 재발행 대상에만 사유 필수 |
| 대상 미선택 | 비활성 |
| 최초 발행 이력 없음 | ⚠ **재출력이 아니라 최초 발행이다** — `issue_seq=1`로 처리하고 사유를 받지 않는다 |
| 프린터 오프라인 | 기록은 남고 인쇄만 실패 — K-4 |
| 혼적 포장 | 대상이 여럿 — 전부 선택 가능하나 모든 대상의 실제 공정 허용을 AND 검증 |
| 오프라인 | 기존 정책상 이용 가능한 같은 문서/대상의 확정 원천·동일 단말 기능 구성 캐시가 있을 때만 새 발행 큐 생성. 미조회/null/다른 대상 캐시로 대체 금지 |

대상·문서종류를 변경하면 이전 허용 상태를 초기화한다. 기존 미전송 기록은 보존하고 복구 시 서버가 재검증한다. 403/422를 부분성공으로 숨기지 않는다.

## §9. 이 장에서 나온 공유 계약 후보

1. **재발행이 정상 경로인 화면이 있다** — 「예외적 재출력」과 「업무상 재출력」을 사유 값이 구분해야 한다. 전부 「훼손」으로 기록되면 재발행 통계가 무의미해진다 (§5-1 · **K-2 보완**)
2. **한 화면이 여러 대상 유형을 다루면 다형 참조 판정을 대상마다 한다** — FK 우선 규칙(A-10 규칙 3)을 일괄 적용하면 잘못 기록된다 (§5-3 · **A-10 보완**)
