# P-02-04 · 작업실적 등록 (LOT·제품 선택)

## §0. 요약

- **개요**: POP(Electron 키오스크) 작업실적 등록 화면. 작업자·현장반장이 W/O 진행 중 대상 LOT·제품을 선택하고 **양품수량만** 입력한다(R50 — 불량은 이 화면에서 받지 않는다). 저장 후 잔여수량이 남으면 제품 선택으로 되돌아가고, 0이 되면 LOT 완료로 넘어간다.
- **주요 데이터**: 작업실적(`production.production_result` — 양품수량·타발수·비고·발생/기록 시각·멱등 키), 생산LOT 배부(`production.production_result_lot_allocation`).
- **핵심 액션**: LOT/제품 변경 → 숫자 키패드로 양품수량 입력 → **저장**(`can_input_result` 플래그 + 잔여수량 검증 통과 시 활성) → 잔여수량 재계산에 따라 연속 입력 또는 LOT 완료 안내.

> 작성일: 2026-07-31 · 서식: `00-화면스펙서식.md` v0.1 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 유형 「입력」(39건) 대표 · 폼팩터 **POP**. 이 장에서 **1024×768 실측 그리드**와 **터치 규격 갭**을 처음 판정한다.

## §3. 레이아웃 — **1024×768 실측 그리드**

### §3-1. 세로 예산

```
768  전체
 -64  헤더 (W/O·품목·사번·연결 상태)
 -88  액션바 (핵심 버튼 72 + 상하 여백 8+8)
────
 616  본문 가용
```

### §3-2. 배치 — 좌우 2단 (입력 / 키패드)

```
1024 × 768
┌ 헤더 64 ───────────────────────────────────────────────────────┐
│ W/O-2026-0731-004 · 품목 ABC-123 · 900xxx · ● 온라인          │
├──────────────────────────────────┬─────────────────────────────┤
│ 좌 616 × 616                     │ 우 392 × 616                │
│                                  │                             │
│  대상 LOT   LOT-...-0007  [변경] │   ┌ 숫자 키패드 ─────────┐  │
│                             64px │   │  7    8    9         │  │
│  제품       ABC-123       [변경] │   │  4    5    6         │  │
│                             64px │   │  1    2    3         │  │
│  ──────────────────────────────  │   │  C    0    ←         │  │
│                                  │   └──────────────────────┘  │
│  ▣ 양품수량  [       120 ] EA    │     키 64×64 · 간격 12       │
│                             72px │     블록 216 × 292          │
│                                  │                             │
│                             64px │                             │
│    비고      [          ]   64px │                             │
│                                  │                             │
│  잔여수량  380 / 500       64px  │                             │
├──────────────────────────────────┴─────────────────────────────┤
│ 액션바 88    [ 취소 72 ]                      [ 저장 72 ]      │
└────────────────────────────────────────────────────────────────┘
```

**세로 검산(좌단)**: 64+64+72+64+64 = 328 + 간격 12×4 = 48 → **376 / 616** — 여유 240px. 통과.

### §3-3. ✅ 실측 검증 (2026-07-31) — **산술 결론이 부분적으로 틀렸다**

**방법**: `@crefle/web-ui`의 실제 토큰(`styles/index.css` — foundation 51 + web 76)과 **실제 폰트**(Spoqa Han Sans Neo)를 그대로 불러와 1024×768 프레임을 브라우저에 렌더하고 치수를 측정했다. DS 컴포넌트는 CSS Modules(해시 클래스)라 직접 쓸 수 없어 **토큰 값으로 치수만 재현**했다 — 실물 컴포넌트 렌더는 아니다.
재현물: `P-02-04-레이아웃검증.html` · 캡처: `P-02-04-레이아웃검증-1024x768.png`

| 항목 | 산술 예상 | 실측 | 판정 |
| --- | --- | --- | --- |
| 프레임 | 1024×768 | 1024×768 | ✅ |
| 본문 가용 | 616 | 616 (패딩 제외 **584**) | ✅ |
| 좌단 내용 | 452 | **465** (행 393 + 간격 72) | ✅ **여유 119px** |
| 34자리 LOT 행 | (미검토) | **597 / 599px — 여유 2px** | ⚠ |

#### ⚠ 뒤집힌 것 — 제약은 세로가 아니라 **가로**였다

- **「입력 필드 3개 상한」은 보수적이었다.** 좌단에 119px가 남아 **1~2행을 더 넣을 수 있다.** 산술에서 패딩(32px)을 예산에 포함하지 않아 실제보다 빡빡하게 봤다.
- **진짜 병목은 34자리 자재 LOT 번호다.** 라벨 104 + LOT **369** + 변경 버튼 68 + 패딩 32 + 간격 24 = **597 / 599px.** 라벨이 한 글자 길어지거나 폰트가 1pt 커지면 **즉시 넘친다.**
- 따라서 POP 화면 설계 규칙은 **「행 수 상한」이 아니라 「긴 식별자를 담는 열 폭 확보」**로 바꿔야 한다.

#### ⚠ 세로 예산에 슬랙이 0이다

`64 + 616 + 88 = 768`로 **정확히** 맞는다. 검증 목업에서 프레임 테두리 1px×2만으로 곧바로 2px 오버플로가 났다. Electron 키오스크 전체화면에는 브라우저 크롬이 없지만, **스크롤바·OS 표시줄·업데이트 배너가 하나라도 끼면 즉시 깨진다.** 실기 확인(트랙 H) 시 반드시 확인할 항목.

#### ⚠ 34자리 무구분 숫자는 육안 대조가 사실상 불가능하다

`0001234500000012002607310001230007` — 구분문자 없이 34자리라 작업자가 실물 라벨과 화면을 **눈으로 맞출 수 없다.** 저장은 구분문자 없이(MLOT #16) 하되 **화면 표시는 분절 단위로 그룹핑**해야 한다(예: `000123450 · 000001200 · 260731 · 000123 · 0007`). 표시 규칙이 정해지면 열 폭도 다시 계산해야 한다 → §9-6.

#### 검증이 여전히 못 본 것

토큰·폰트·치수는 실제이나 **실물 DS 컴포넌트 렌더가 아니고**, 장갑 조작감·공장 조명·작업 거리 판독성은 **실기(트랙 H · N100 1세트)** 몫이다.

### §3-4. 이 배치가 강제하는 것

- ~~**입력 필드는 3개가 상한**이다. 필드를 하나 더 늘리면 빠듯해진다 → 「한 화면 = 한 태스크」가 산술로 증명된다.~~ → **§3-3 실측으로 정정**: 세로는 119px 여유가 있어 1~2행 더 들어간다. **상한을 정하는 것은 행 수가 아니라 긴 식별자의 가로 폭**이다.
- **숫자 키패드를 화면 안에 고정**한다. Windows 터치 키보드에 의존하지 않는다 — 키오스크 전용 창(결정 16)에서 OS 키보드가 화면을 덮으면 입력 필드가 가려지고 제어가 어렵다.
- 양품수량이 **핵심 입력이라 72px**, 나머지는 64px.
- ⚠ **정본이 「양품만 입력」(R50)이라 이 배치가 성립한다.** 수량 5종을 다 입력받으면 좌단이 넘친다 — §8-1 참조.

## §5. 액션·상태

### §5-1. 액션

| 액션 | 크기 | 활성 조건 |
| --- | --- | --- |
| 변경(LOT / 제품) | 64px | 항상 |
| 키패드 숫자·`C`·`←` | 64×64 | 수량 필드 포커스 시 |
| `＋10` · `＋100` | 64px | 동상 |
| **저장** | **72px** | 양품수량 > 0 **AND** `can_input_result` 플래그 **AND** 잔여수량 검증 통과 |
| 취소 | 72px · **저장과 격리** | 입력 있음 |

⚠ **`mdm.terminal_process.can_input_result`가 이 화면의 저장 활성 조건이다.** 단말×공정 조합에 플래그가 없으면 저장 불가 — 사유를 표시한다(「이 단말은 이 공정의 실적 입력 권한이 없습니다」). 관리 화면은 `W-CO-06` 단말기-공정 매핑 설정.

### §5-2. 저장 후 분기 (S7 태스크 ⑥)

```
저장 → 잔여수량 재계산
        ├─ > 0 → 제품 선택으로 회귀 (연속 입력)
        └─ = 0 → LOT 완료 처리 안내 → P-02-06 (S10)
```

### §5-3. ⚠ 오프라인 — `idempotency_key`가 핵심

`production_result`에 **`idempotency_key varchar(150) NOT NULL UNIQUE`** 가 있다. 이는 **클라이언트가 생성해 outbox에 담고, 재전송 시 서버가 중복을 흡수**하는 설계다(결정 16 공유물 `outbox 모듈`·결정 17 시나리오 1 W/O 선배포).

화면 요구:
1. 저장 시 **로컬 SQLite에 먼저 기록**하고 즉시 성공 피드백 — 통신을 기다리지 않는다
2. 헤더에 **연결 상태와 미동기 건수 상시 표시**(결정 16 POP 「오프라인/미동기 상시 표시」)
3. `occurred_at`은 **입력 시점**, `recorded_at`은 서버 수신 시점 — 오프라인 지연이 실적 시각을 왜곡하지 않는다
4. 재전송은 같은 `idempotency_key`로 — **사용자에게 중복 저장으로 보이지 않아야 한다**

> 이 규약은 POP·모바일의 모든 입력 화면에 동일하다 → **공유 계약 후보**.

## §7. DS 매핑

### §7-1. 터치 타겟 — **버튼은 해소, 입력류는 잔여 1건**

터치 규격 조항(E-3)이 2026-08-28 개정되며 등급과 부품의 대응이 확정됐다. ⛔ **등급표를 여기 옮겨 적지 않는다** — 정본은 조항이고, 이 절은 그 조항이 이 화면에 어떻게 걸리는지만 적는다.

| 이 화면이 요구하는 것 | 어느 부품인가 | 지금 낼 수 있나 |
| --- | --- | :-: |
| 저장 **72px** · 취소 **72px**(§5-2) | 버튼류 `Button` | ✅ `size="2xl"`(72픽셀) |
| 변경 · `＋10` · `＋100` · 키패드 키 **64px** | 버튼류 `Button` | ✅ `size="2xl"` — 64와 72 사이에 단이 없어 `2xl` 로 올린다(E-3 적용 규칙 2) |
| **양품수량 72px** — 핵심 입력(§3-1) | 입력류 `TextField` | ⛔ **`xl` 60픽셀이 최대다** |
| 비고 **64px** | 입력류 `TextField` | ⛔ 동상 |

⛔ **입력류 잔여 갭의 근거가 바로 이 화면이다.** 고정 커밋 `8c4a775` 는 `2xl` 을 버튼류(`Button`·`IconButton`)에만 주고 입력류(`TextField`·`Select`·`SearchInput`)를 **명시적으로 제외**했다. 우리가 낸 요청은 그 셋을 「액션 영역에는 안 선다」는 근거로 디자인 시스템 판단에 넘겼는데, **이 화면이 액션 영역이 아닌 본문에서 양품수량을 핵심 등급 72픽셀로 요구한다.** 그 근거가 이 한 화면을 놓쳤다. 표지 `omf-mes#284`.

- **유형** — 버튼은 `a`(부품이 그대로 덮는다) · 양품수량·비고 입력은 `a + b`(부품은 있고 크기 변형이 없다)
- **소관** — 잔여 갭은 디자인 시스템 쪽에 있다. 제외 이유도 그 고정 커밋의 메시지에 적혀 있다 — 선택 부품은 트리거·옵션 행·팝업 셋을 함께 올려야 하고 팝업 배치 문제와 얽힌다

**파급 — POP 22건이다.** ⚠ 「POP·모바일 41건」 «(구표기 보존)» 은 2026-07-31 에 자재 LOT 스캔·등록 화면(M-01-02) §7-2 가 이미 「POP 22건」으로 정정한 낡은 수치였다(모바일은 터치 규격이 아직 미확정이라 재판정 대상이다).

### §7-2. 갭 — 숫자 키패드 (d 유형 후보)

화면 내장 숫자 키패드가 DS에 없다. `Button` 12개 조합으로 만들 수 있으므로 **`c`(조합)로 볼 수도 있으나**, 포커스 연동·입력 버퍼·`C`/`←` 동작이 함께 와야 쓸모가 있어 **상태를 가진 단일 요소**에 가깝다.

- **잠정 판정 `d`** — `ds-candidates/`에 제품 로컬 구현
- **세 곳 규칙**: POP 입력 화면 대부분이 수량을 받으므로 사용처는 쉽게 3곳을 넘는다(`P-02-04`·`P-02-06`·`P-01-02` 등). 전 화면 매핑 후 확정

## §9. 이 장에서 나온 공유 계약 후보

1. **오프라인 입력 규약** — 클라이언트 `idempotency_key` 생성 · 로컬 선기록 후 즉시 피드백 · `occurred_at`/`recorded_at` 분리 · 연결 상태·미동기 건수 상시 표시. **POP·모바일 전 입력 화면 공통** (§5-3)
2. **단말 권한 게이팅** — `terminal_process` 8플래그를 액션 활성 조건으로 쓰는 방식. 플래그별 대응 화면·버튼 매핑표 필요 (§5-1)
3. ~~**터치 밀도 프리셋** — DS 갭 해소 전까지의 제품 측 임시 규약~~ → ✅ **폐기(2026-08-28)** — 그 규약은 버튼에 한해 폐기됐고, 디자인 시스템이 `xl`(60픽셀)·`2xl`(72픽셀)을 직접 들였다. 남은 것은 입력류 잔여 갭 하나이고, 그것은 화면 전체 밀도를 올리는 문제가 아니라 부품 하나의 크기 문제다 (§7-1 · `omf-mes#284`)
4. **숫자 키패드 동작 규약** — 포커스 연동·버퍼·`C`/`←`·빠른 입력 버튼 (§7-2)
