# P-02-04 · 생산 실적 등록

> **POP 공통 개정(2026-09-08)**: 글꼴·버튼·입력·선택·키패드·목록 행과 터치 영역은 관리웹 기본 밀도(E-3)를 사용한다. 본문의 구 56~72px 수치와 확대 터치 판정은 변경 이력이며 구현 기준이 아니다. 모든 선택형 목록은 선택값 + [선택] 버튼과 로컬 검색·목록 스크롤·[페이지 위]·[페이지 아래] 팝업(G-34)을 사용한다. 성공 피드백은 G-1의 POP 공통 규칙을 따른다. 로컬 기록·서버 반영·인쇄 결과를 구분하고 C-7 미확정 표식은 유지한다.

> 개정일: 2026-09-08 · 현장 테스트 확정 반영
> 기존 `P-02-05` 인식표 발행, `P-02-06` 생산LOT 완료, `P-02-07` LOT 라벨 출력을 이 화면에 통합한다.

## §0. 요약

- **개요**: 진행 중 W/O의 생산 LOT을 순서대로 보여 주고, 최종 생산수량을 확인·수정한 뒤 생산 LOT 라벨을 출력한다. **라벨 출력 시점에 생산 실적을 저장**하고, 부착한 라벨을 스캔하면 해당 LOT을 자동 마감한 뒤 다음 LOT으로 전환한다.
- **중간 실적**: LOT 진행 중 별도 실적 등록 단계는 두지 않는다. 중간 실적 등록은 인식표 발행·등록이 전부이며, 인식표 대상이 아닌 제품에는 관련 영역을 숨긴다.
- **구분**: 이 화면의 LOT 마감은 **LOT 생산 등록 확정**이다. W/O 마감이 아니며, 미달 사유·잔량 이월/소멸과 미사용 선발행 번호 폐번은 관리웹 `W-02-05`의 W/O 마감에서 처리한다.
- **오프라인**: 생산 실적 저장은 기존 오프라인 큐 규약을 유지한다. 라벨 발행·물리 인쇄·스캔 완료의 단계별 상태를 화면에 분리해 보여 준다.

### §2-1. POP 밀도

글꼴, 버튼, 입력, 선택 트리거, 숫자 키패드와 터치 영역은 모두 **관리웹 기본 크기**를 사용한다(공유계약 E-3). 통합 전 화면에 적힌 56~72픽셀 POP 전용 확대 규격은 적용하지 않는다.

### §2-2. 마감된 LOT 목록 팝업

[마감된 LOT 목록 보기]를 누르면 현재 W/O에서 마감된 생산 LOT 번호를 순서대로 표시한다. 이 팝업은 **단순 확인용**이며 선택·재개·정정 기능을 제공하지 않는다. 목록 내부 스크롤과 [페이지 위]·[페이지 아래]를 제공한다.

## §3. 핵심 흐름

공통 헤더의 **[화면 이동]**은 G-34를 따른다. 셸의 활성 POP 라우트 등록부에서 통합·폐지 화면을 제외한 후보 전체를 목록 팝업으로 표시한다. 후보 안 로컬 검색·스크롤·페이지 이동을 제공하고 선택 즉시 이동하며 미저장 입력 확인 팝업은 띄우지 않는다. 등록 검증·준비 전에는 업무 이동을 열지 않고, 등록 후 화면 이동이 실제 업무의 공정별 기능 구성·인증·서버 검증을 우회하지 않는다.

```text
현재 LOT 표시
  → 실제 생산수량 확인/수정
  → [생산 LOT 출력]
      1) 생산 실적 저장
      2) 생산 LOT 라벨 발행·렌더링·인쇄
  → 작업자가 라벨 부착
  → 부착한 LOT 번호 스캔
  → 현재 LOT 일치 확인
  → LOT 자동 마감
  → 다음 LOT 번호로 화면 전환
```

### §3-1. 출력 시 생산 실적 저장

생산 실적의 선택 W/O 공정 판정은 유지한다. 이미 존재하는 LOT/개체의 발행·재출력은 실제 문서종류를 포함한 `GET /app/document-issues/summary`의 `requiredProcessIds`로 대상 자체의 발행 W/O 공정을 확인한다. 선택 W/O와 대상의 실제 귀속이 같아야 하며 다른 W/O 대상에 현재 W/O의 허용을 빌려 주지 않는다. 필요한 공정 전체가 같은 단말에서 허용되어야 한다(공유계약 F-1).

공정별 기능 구성은 선택 `WorkOrder.processId`와 셸의 자기 단말 공정 목록에서 정확히 같은 `processId` 행으로 판정한다. 생산 실적·라벨은 그 행의 `canInputResult`·`canPrintLabel`을 사용한다. 설비 공정·첫 매핑·다른 행 OR 합산으로 대신하지 않는다. W/O 변경 시 이전 허용 상태를 초기화하며 행 없음/false는 해당 쓰기 비활성+사유·서버 403이다. 서버도 실제 대상 W/O로 재판정한다.

[생산 LOT 출력] 클릭은 별도 [실적 저장] 버튼을 대체한다.

1. 실제 생산수량과 `can_input_result`를 검증한다.
2. `POST /production/production-results`로 생산 실적을 저장한다. `goodQty`는 실제 생산수량이고 `lotAllocations=[{lotId: 현재 LOT, allocatedQty: 실제 생산수량}]`를 함께 보내 **해당 LOT의 최종 실적**으로 귀속한다. 작업자·단말은 각각 `X-Worker-No`와 단말 토큰에서 서버가 파생한다.
3. 같은 사용자 동작 안에서 `POST /app/document-issues`(`documentTypeCode=PRODUCTION_LOT_LABEL`)로 발행 기록을 만든다.
4. 렌디션을 받아 물리 인쇄하고 결과를 `POST /app/document-issues/{documentIssueLogId}:report-print`로 보고한다.

생산 실적 저장과 출력물 발행은 서로 다른 트랜잭션이다. 실적 저장 후 출력이 실패하면 현재 LOT을 유지하고 **출력 재시도** 상태를 보여 준다. 재시도는 같은 생산 실적을 다시 만들지 않으며, 이미 발행 기록이 있으면 재출력 사유를 받아 새 회차로 남긴다.

### §3-2. 인식표 중간 실적

아직 생성되지 않은 개체의 발번은 기존 선택 `WorkOrder.processId` 판정을 사용한다. 발번 전 summary를 요구하는 순환을 만들지 않는다. 생성 후 개체 발행은 `IDENTIFICATION_TAG`(인식표)/`SERIAL_NUMBER`(개체) 조합의 실제 대상 원천으로 판정한다. 생산 실적·개체 발번·LOT 마감과 발행의 기존 트랜잭션은 서로 합치지 않는다.

인식표 발번·발행의 라벨 플래그 `canPrintLabel`도 선택 `WorkOrder.processId`의 동일 단말 매핑 행을 사용한다. 별도 공정 입력·요청 필드를 추가하지 않는다.
- 인식표 대상 여부는 품목/작업 조건에서 서버가 내려 준 값을 사용한다 — `GET /trace/lots` 응답의 `identificationTagRequired`다(2026-09-09 신설).
- 생산 LOT의 값이 null 또는 미제공이면 대상 여부를 아직 모르는 상태다. false로 간주해 영역을 숨기거나 개체 수 검증을 생략하여 최종 생산 LOT 출력·마감을 진행하지 않는다. 기존 목록·입력을 보존하고 원천 확인 사유를 표시한다. 구체적인 품목/작업 조건 판정 원천은 #369에서 추적하며 `serialControlTypeCode`로 대신하지 않는다.
- 대상이면 [인식표 라벨 출력]과 출력한 인식표 목록을 표시한다.
- 인식표는 `trace.serial_number` 개체 생성 후 `POST /app/document-issues`(`IDENTIFICATION_TAG`)로 발행한다.
- 이 단계에서는 `production_result`를 만들지 않는다. 생성된 개체 수가 LOT 중간 실적이며, `POST /trace/serial-numbers`는 아직 저장되지 않은 양품 누계를 선행조건으로 요구하지 않는다.
- 인식표는 **단위 정보를 갖지 않는다 — 개체 하나가 무조건 1개**다. 그래서 발번 수량을 LOT 실적 배분 수량에서 환산해 구하지 않으며, 단위 환산도 소수도 발생하지 않는다.
- 실적 수량의 단위는 **품목 기준단위 하나**이고 LOT 마다 다르게 설정하지 않는다. 생산 실적은 단위를 헤더에 하나만 싣고 배분 행은 단위를 갖지 않는다.
- 인식표 대상 품목은 생산 LOT 출력 전에 실제 생산수량과 이 LOT의 개체 수가 같아야 한다. 적으면 부족분 인식표를 추가 발행하고, 많으면 실제 생산수량을 이미 생성된 개체 수보다 작게 낮출 수 없다. 이 검증으로 최종 `goodQty`와 중간 개체를 중복 합산하지 않는다.
- 기존 발행분은 `GET /app/document-issues/summary`와 상세 목록으로 구분하고, 재출력은 대상과 사유를 선택해 수동 실행한다.
- 대상이 아니면 인식표 관련 영역과 여백을 모두 숨긴다.

### §3-2-a. 인식표 발번·발행 재시도의 경계

새 개체 상태는 `REGISTERED`(등록됨)이며 과거 개체의 상태 원문은 유지한다. 서버는 전역 `SN-{YYYYMMDD}-{SEQ4}` 규칙으로 한 요청의 연속 번호 구간을 예약하고 개체 N행을 모두 생성하거나 모두 실패시킨다. 번호 예약 후 실패하면 결번이 생길 수 있어 무결번을 약속하지 않는다(통보 104·106 · `omf-mes#516`).

발번과 발행은 **서로 다른 요청 키**로 실행한다. 발번 성공 응답의 개체 목록과 해당 단계 키를 보존한 뒤 발행한다. 발행만 실패하면 같은 개체로 발행 단계만 재시도하고 새로 발번하지 않는다. 발번 응답을 잃었으면 같은 발번 요청·키로 결과를 재생한다. LOT 개체 조회의 첫 페이지만으로 해당 발번 배치를 복원하지 않는다(통보 107).

발번 시 사번 존재와 단말의 라벨 출력 권한을 검증한다. 사번·단말 정보가 중복 방지 지문에 포함돼도 발번 개체의 영구 귀속 기록을 보장하는 것은 아니다. 인증 계정의 생성 기록과 발번 사번·단말의 사후 복원을 혼동하지 않는다.

**현재 기술적 미지원**: 렌디션 생성·물리 인쇄 완료는 발행 API 성공만으로 보장되지 않는다. 이 통보는 출력 요구사항을 삭제하지 않으며, 물리 인쇄 성공을 확인하기 전에는 아래 LOT 스캔 마감 단계로 넘어가지 않는다.

### §3-3. LOT 스캔 마감

마감의 `canCompleteWork`는 해당 LOT의 선택 W/O `processId`에 정확히 대응하는 단말 행에서 읽는다. 이전 W/O의 마감 허용 상태를 물려받지 않는다.

생산 LOT 라벨의 물리 인쇄 성공 후 `can_complete_work=true`일 때 스캔 대기 상태로 전환한다. 스캔 값이 현재 LOT과 일치하면 `POST /trace/lots/{lotId}:complete`를 호출하고, 성공 시 다음 미마감 LOT으로 전환한다. 다른 LOT을 스캔하면 마감하지 않고 현재 LOT 번호를 다시 안내한다.

LOT 마감 후에는 생산 실적 수량을 이 화면에서 직접 수정하지 않는다. 정정은 관리웹 `W-02-05`의 정정 흐름을 사용한다.

### §3-4. 「수량 유효」의 뜻

§4의 활성 조건 「수량 유효」는 다음 셋을 모두 만족하는 것이다.

1. 실제 생산수량이 **0보다 크다**.
2. 인식표 대상 품목이면 **정수**이고 이 LOT의 개체 수와 **같다**.
3. 인식표 대상 품목이면 **이미 생성된 개체 수보다 작지 않다**.

⛔ **「잔여 이내」는 조건이 아니다** — 계획 수량을 넘는 입력을 막지 않는다(§3-5).

### §3-5. 초과 생산 — 막지 않고, 저장 직전에 한 번 확인한다

계획 수량은 상한이 아니다. 실제 생산수량이 이 LOT의 계획 수량을 넘어도 **차단하지 않는다**.

[생산 LOT 출력]을 누르면 실적 저장·라벨 발행·물리 인쇄가 잇따라 일어나고, 저장된 생산 실적은
이 화면에서 고칠 수 없다(정정은 관리웹 `W-02-05`의 정정 흐름이 원본을 두고 정정 기록을 덧붙인다).
그래서 **저장 직전 한 번**이 파급을 말할 수 있는 유일한 자리다(공유계약 G-19).

- 초과일 때 확인 창에 넷을 함께 보인다 — **계획 수량 · 이미 배분된 양품 · 이번 입력값 · 초과분**.
  이미 배분된 양품은 `GET /trace/lots`의 `withProgress=true` 응답 `progress.goodQty`이고, 초과분은
  `이번 입력값 − (계획 수량 − 이미 배분된 양품)`이다.
- 확인하면 그대로 저장한다. 취소하면 수량 입력 상태로 돌아간다.
- 초과가 아니고 판정도 설 때는 확인 창을 띄우지 않는다 — 하루에 수십 번 지나는 지점이다.
- ⛔ 화면은 「초과 달성」 같은 **판정 이름을 스스로 붙이지 않는다**. 마감 3분류 판정은 서버가 내리고
  (`progress.completionJudgmentCode`) 「정상」의 폭은 아직 서버 정책이 정하지 않았다(공유계약 L-2).
  저장 전에 화면이 말하는 것은 판정 이름이 아니라 **수치 사실**이다.

**잔여를 판정할 수 없을 때** — 진행 정보 응답에 `progress`가 없거나 계획 수량을 받지 못하면 초과
여부가 서지 않는다. 이때도 **저장을 막지 않는다**(공유계약 G-15). 확인 창을 띄워 「이 LOT의 진척을
받지 못해 초과 여부를 판정하지 못했습니다」를 밝히고 진행 여부를 묻는다. ⛔ 잔여와 초과분을 `0`으로
그리지 않는다 — 「다 만들었다」로 읽힌다(공유계약 G-9).

**계획 수량에 못 미친 채 마감할 때** — 스캔 마감은 이 LOT에 배분된 양품 합계가 계획 수량보다 적으면
미달 사유를 함께 보낸다(`POST /trace/lots/{lotId}:complete`의 `completionVarianceReasonCode` —
미달일 때만 조건부 필수이고 정상·초과이면 보내지 않는다). 사유 선택지는
`GET /mdm/code-values?codeGroupCode=WORK_ORDER_COMPLETION_VARIANCE_REASON`으로 받는다(공유계약 G-32).
⚠ 이 사유는 LOT별로 보존되지 않고 원천 W/O의 사유 한 칸을 덮어써 마지막 기록만 남는다 — 계약이
그렇게 못박았다. W/O 단위 미달 사유·잔량 이월/소멸은 그대로 관리웹 `W-02-05` 소관이다(§0·§7).

## §5. 상태·예외

| 상황 | 처리 |
| --- | --- |
| 생산할 LOT 없음 | 완료 안내. W/O 마감 버튼은 제공하지 않음 |
| 실제 생산수량 변경 | 출력 전 허용. 해당 LOT의 최종 수량으로 저장 |
| 인식표 수와 실제 생산수량 불일치 | 인식표 대상 품목은 LOT 출력 차단. 부족분은 추가 발행하고 이미 발행한 개체 수보다 실제 생산수량을 작게 낮추지 않음 |
| 실제 생산수량이 이 LOT의 계획 수량을 넘음 | 차단하지 않는다. 저장 직전 확인 창에 계획 수량·이미 배분된 양품·입력값·초과분을 보이고, 확인하면 그대로 저장한다(§3-5) |
| 이 LOT의 진척을 받지 못함 | 초과 여부를 「판정 불가」로 밝히고 저장을 막지 않는다. 잔여·초과분을 `0`으로 그리지 않는다(§3-5) |
| 배분 양품이 이 LOT의 계획 수량에 못 미침 | 마감 전에 미달 사유를 고르게 한다. 고르지 않으면 마감을 보내지 않는다(§3-5) |
| W/O 지시수량 미달 | POP에서 사유·잔량 처리를 요구하지 않음. 관리웹 W/O 마감 소관 |
| 실적 저장 성공·발행 실패 | 같은 LOT 유지, 출력 재시도 제공, 실적 중복 저장 금지 |
| 발행 성공·인쇄 실패 | 기존 발행 건 렌디션 재인쇄. 새 실적·새 LOT 생성 금지 |
| 다른 LOT 스캔 | 차단하고 현재 LOT 번호 표시 |
| 중복 스캔 | 이미 마감된 LOT임을 알리고 다음 LOT 상태 유지 |
| 오프라인 | 실적은 동일 멱등 키로 큐 적재. 서버 판정이 필요한 마감은 연결 복구 후 수행하며 출력/마감 상태를 혼합하지 않음 |
| 사용자 전환 | 현재 사번만 삭제. 저장·큐 기록의 작업자 사번 유지 |

## §7. 명시적 비범위

- 별도 [실적 저장] 버튼과 LOT 중간 실적 반복 등록은 만들지 않는다.
- 인식표 외 중간 실적 종류를 추가하지 않는다.
- LOT 마감을 W/O 마감으로 부르지 않는다.
- W/O 미달 사유, 잔량 이월·소멸, 미사용 선발행 LOT 번호 폐번은 `W-02-05`에 유지한다.
- 인식표 비대상 품목에 비활성 버튼이나 빈 목록을 보여 주지 않는다.
- 초과분에 대한 생산 LOT 추가 발번은 이 화면이 하지 않는다. ⚠ 그 발번을 어느 화면이 하는지와 승인
  주체(자동인지 관리자 확인인지)는 아직 정해지지 않았다(2026-07-29 생산LOT 발번·폐번 확정기록의
  「미확인」 항). 정해지기 전까지 이 화면은 초과 사실을 실적으로 남기는 데까지만 한다.

## §8. 확정 정책

라벨 발행의 실제 대상 원천은 공유계약 F-1을 따른다. 원천 null·부적합은 새 발행 허용으로 보지 않으며 기존 이력·미전송 기록은 보존한다. 오프라인 새 발행은 같은 문서/대상의 기존 이용 가능한 확정 원천·단말 매핑 캐시가 있을 때만 허용하고 문서/대상 변경 시 재판정한다. 서버는 복구 시 전체 공정·대상을 재검증한다. 기존 물리 인쇄 지원 범위는 바꾸지 않는다.

- 생산 수량 3원은 공유계약 L-10에 따라 **양품=`goodQty`, 불량=`defectQty + holdQty + reworkQty`, 손실=`scrapQty`**로 표시한다.
- 이 화면은 R50에 따라 양품만 입력하므로 `goodQty`에 실제 생산수량을 저장하고, 불량·보류·재작업·폐기 수량은 이 화면에서 새로 입력하거나 합산하지 않는다.
- 인식표 대상 품목의 수량은 개체 수와 같아 **정수**다(2026-09-09 확정). **버림·반올림 규칙은 두지 않는다** — 소수가 발생하는 경우 자체가 없다.
