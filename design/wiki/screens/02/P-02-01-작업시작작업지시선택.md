# P-02-01 · 작업 시작 (작업지시 선택)

## §0. 요약

- **개요**: POP(Electron 키오스크 · 1024×768 터치) 화면. 현장 오퍼레이터가 사번을 입력하고 이 설비에 배포된 작업지시(W/O) 중 하나를 선택해 작업을 시작하거나, 중단된 W/O를 재개한다. 단말 게이팅(`can_start_work`)과 작업 전 점검 통제(`P-02-02`의 판정)를 통과해야 세션이 열린다 — 이 화면은 점검 결과를 「보이고」, 판정·차단은 `P-02-02`가 한다.
- **주요 데이터**: `production.work_order`(작업지시 — `status_code`·`work_order_type_code`·`priority_no`·`planned_equipment_id`·`planned_mold_id`·`operation_settings_snapshot`) · `production.work_session`(작업 세션 — `session_no`·`started_at`·`terminal_id`·`status_code`) · `mdm.terminal_process.can_start_work`(단말 게이팅).
- **핵심 액션**: 사번 입력 → 작업지시 선택(이 설비 배포분 / 전체 보기) → 작업 전 점검 통제 결과 확인 → **작업 시작**(새 세션 개설, `START` 사건 동시 생성) 또는 **재개**(중단된 W/O — 같은 세션에 `RESUME` 사건 적재, 새 세션 아님).

> 작성일: 2026-08-11 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> DR-001 §7 **5단계**의 첫 번째. **DR-001 이 마지막으로 미룬 두 장**이다 — 「**점검 기록의 형태가 정해진 뒤**에야 「무엇을 보고 막을지」를 쓸 수 있다」(§7 주). **그 형태를 확정**해 조건이 충족됐다.
> ⚠ **05 화면이 아니다** — 02 생산실행 소속인데 **설비 점검 데이터에 의존**해 DR-001 범위에 들어왔다.

## §3. ⭐ 이 화면이 **테이블 신설을 요구하지 않는다**

05 의 17장 중 **테이블 신설을 요구하지 않은 것이 3장**이었다. **이 화면이 넷째**이고, 이유가 다르다 — **02 생산실행은 물리 모델의 선언 Scope 안**이라 애초에 갖춰져 있다.

| 필요한 것 | 실재 |
| --- | :-: |
| 작업지시 목록·상태 | `work_order.status_code` ✅ |
| **긴급 구분** | ⭐ **`work_order_type_code`**(기본 `'NORMAL'`) ✅ — QA #9 우회 판정의 근거 |
| 우선순위 | `priority_no`(기본 100) ✅ |
| 계획 설비·금형 | `planned_equipment_id`·`planned_mold_id` ✅ |
| **작업 세션 시작** | `work_session.session_no`·`started_at`·`terminal_id` ✅ |
| **단말이 시작할 수 있는가** | ⭐ **`terminal_process.can_start_work`** ✅ |

⭐ **`operation_settings_snapshot jsonb` 가 있다** — 주석이 「**기준정보 in-place 변경이 기존 지시에 소급되지 않도록 고정**」이다. **A-18**(판정 근거가 움직이면 스냅샷)이 **하류에 이미 있던 선례**다.

### §5-1. ⭐ **F-1 이 정확히 걸리는 첫 자리** — `can_start_work`

공유계약 **F-1**(`terminal_process` 8플래그를 액션 활성 조건으로 쓴다)이 v0.9 에서 「**생산·품질 단말 한정**」으로 범위 정정됐다. **이 화면이 그 한정의 정중앙**이다.

```
[ 작업 시작 ]  활성 조건
   terminal_process (이 단말 × 이 W/O 의 공정) . can_start_work = true
```

⚠ **05 액션을 `can_input_result` 에 「잠정 포섭」**했던 것과 다르다 — **여기는 전용 플래그가 있다.**

| 없으면 | 처리 |
| --- | --- |
| 이 단말×공정 행이 없다 | ⛔ **시작 불가** + 「이 단말은 이 공정의 작업을 시작할 수 없습니다」(**G-3** — 「단말 설정에서 권한을 부여하세요」 + `W-CO-06` 안내) |
| 행은 있고 `can_start_work=false` | 동상 |

### §5-2. ⭐⭐ 작업 전 점검 통제 — **이 화면은 「보이고」 `P-02-02` 가 「막는다」**

**F-5**(게이트를 만드는 화면과 집행하는 화면을 나눈다)를 그대로 쓴다.

| 화면 | 책임 |
| --- | --- |
| **`M-05-01`** 점검 입력 | **근거를 만든다** |
| **`P-02-02`** 작업 전 점검 통제 | ⭐ **판정하고 막는다** |
| **이 화면** | **판정 결과를 보이고** 통과 시 세션을 연다 |

⭐ **③ 구획에 결과를 한 줄로 보인다** — 「✅ 작업 전 점검 08-11 07:12 · 사번 3391 · 합격」.

⛔ **이 화면이 판정 규칙을 다시 쓰지 않는다** — F-5 규칙 3(근거 화면은 집행 문구를 쓰지 않는다)의 역방향이다. **판정은 `P-02-02` 가 하고 결과 문자열을 받는다.**

### §5-4. 중단된 W/O 는 **「재개」이지 새 시작이 아니다**

**결정 14** 가 「**재시작은 상태가 아니라 중단→진행 전이 이벤트**」로 확정했고, `uq_work_session (work_order_id, session_no)` 가 **세션이 여러 번 열림**을 전제한다.

⛔ **정정(2026-08-23) — 「재개하면 새 세션」은 틀렸다.** v0.1 이 아래처럼 적었으나 **실측 다섯 곳이 반대**였다.

> ~~`WO-2026-0405` `session_no 1` 08:00\~09:40 (중단) / `session_no 2` ← **재개하면 새 세션**~~

**재개는 같은 세션 안의 사건이다.** 중단해도 세션은 **열려 있고**(`ended_at` 이 비어 있다) `status_code` 만 「중단」으로 바뀐다. 근거·판정 전문은 공유계약 **`G-16` 보완**(구간을 «닫는» 사건과 구간 «안의» 사건을 가른다) — 요약하면 ① 계약의 **작업 «세션»에 `:resume` 액션이 없다**(세션 층에서 재개를 표현할 길은 사건 적재뿐) ② 논리 모델 §9.7 이 사건 표를 「시작·중지·**재개**·종료 이력」으로 정의했다 ③ `status_code` 가 「중단」을 담는다 ④ `P-02-10` §3 목업이 **한 세션에** 시작→중단→재개를 그린다 ⑤ **아래 §8 미결 2 자신이** 「`ended_at` 과 `status_code` 를 둘 다 쓴다」고 적었다.

⛔ **v0.2 가 이 근거를 「계약에 `:resume` 액션이 없다」로 적었는데 사실이 아니었다**(2026-08-27
정정 · `omf-mes#247`). **W/O 층에는 `POST /production/work-orders/{workOrderId}:resume` 가
실재하고**, 요구서 §3-10 이 이 화면의 [재개] 를 바로 그것에 매핑해 두고 있었다. 결론(재개 =
같은 세션의 사건)은 나머지 근거 넷으로 그대로 서지만, **근거가 틀려서 정정이 요구서와 그 두
오퍼레이션에 닿지 못했다** — 12일 어긋나 있던 것을 고치면서 다시 4일을 어긋나게 뒀다.
⭐ **이 화면의 [재개] 는 `POST /production/work-sessions/{workSessionId}/events`
(`eventTypeCode=RESUME`)로 확정한다**(§5-5 · 계약 정정).

⚠ **결정 14 인용이 결론을 받쳐 주지 않았다** — 그 문장은 **작업지시 상태 그래프**에 대한 것이고, 「전이 이벤트」는 **같은 것의 상태가 바뀐다**는 뜻이라 오히려 반대쪽이다.

```
WO-2026-0405   session_no 1  08:00~17:00   ← 세션은 하나
                 08:00  START
                 09:40  STOP   (사유: 설비 고장)
                 11:20  RESUME
                 17:00  END    ← :end 로 닫는다
```

| 버튼 | 언제 | 무엇 |
| --- | --- | --- |
| **작업 시작** | 상태 = **배포** | 새 세션을 연다 — `session_no = 직전 + 1`(그 작업지시의 첫 세션이면 `1`) · ⭐ **`START` 사건도 같은 트랜잭션으로 만들어진다** — 화면이 따로 보내지 않는다 |

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐ **판정하는 화면은 오프라인을 금지하고, 만드는 화면은 허용한다** — C-14 ↔ C-15 의 짝

**C-15**(내가 만든 것이 남의 판정 근거면 오프라인 허용 + 미전송 경고)를 세웠다. **그 반대쪽이 이 화면**이다.

```
M-05-01 점검 입력   만든다  →  오프라인 ✅ 허용 (C-15)
P-02-01 작업 시작   읽는다  →  오프라인 ⛔ 금지 (C-14)
```

**규칙안**: 한 데이터의 **생산자와 소비자가 다른 화면**일 때 오프라인 정책이 **반대**가 되는 것이 정상이다.

| | 생산자 | 소비자 |
| --- | :-: | :-: |
| 오프라인 | ✅ 허용 | ⛔ 금지 |
| 왜 | 막으면 현장이 종이로 돌아간다 | **틀린 판정으로 통과시킨다** |
| 화면이 말할 것 | 「**미전송 N건 — 작업 통제에 반영되지 않습니다**」 | 「**연결이 끊겨 시작할 수 없습니다**」 |

⚠ **두 문구가 짝이어야 한다** — 점검자는 「반영 안 됨」을 보고, 작업자는 「시작 못 함」을 본다. **같은 원인의 두 얼굴이다.**

### 9-2. **연결이 끊겼을 때 회색 버튼만 두지 않는다**

**G-3**(비활성 사유는 「왜」가 아니라 「어떻게 풀 것인가」)의 **오프라인 판**이다.

**규칙안**: 오프라인을 금지하는 화면은

1. **왜 못 하는지** — 「연결이 끊겼습니다」
2. **무엇을 하면 되는지** — 「복구되면 자동으로 불러옵니다」 · 대안 경로가 있으면 안내
3. ⛔ **회색 버튼만 두지 않는다** — 작업자는 **단말이 고장 난 줄 안다**
