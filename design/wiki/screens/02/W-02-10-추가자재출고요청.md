# W-02-10 · 추가 자재 출고 요청(수동)

## §0. 요약

- **개요**: 관리웹에서 생산관리자·현장반장이 긴급 W/O 등으로 부족한 자재를 **무절차 창고 반출 없이 정식 출고 절차로 경유**시키기 위해 발행하는 수동 요청 화면. 요청 발행까지만 다루며 피킹·출고 자체는 `M-01-08`이 담당한다.
- **주요 데이터**: 자재출고요청(`logistics.material_issue_request` — W/O·도착위치 FK, 사유는 코드형 컬럼이 확정됐으나 아직 없음), 요청 라인(`logistics.material_issue_request_line` — BOM소요·기출고·부족·요청수량, BOM 밖 품목도 허용), `planning.bom_component`.
- **핵심 액션**: W/O 선택 → 도착 위치·필요 시각 지정 → 「BOM 소요량 불러오기」로 라인 채움(「+ 품목 추가」로 BOM 밖 품목도 가능) → 사유 선택(값 목록 확정 — `MATERIAL_ISSUE_REQUEST_REASON`, G-31 마스터)·비고 입력 → **요청 발행**(라인 1건 이상 AND 사유 또는 비고 입력).

> **확정이 「사유 필드(코드형)를 신설한다」고 명시했다.** 계약에 `reasonCode`(코드형, 값 목록 `MATERIAL_ISSUE_REQUEST_REASON`)로 되살렸다(2026-08-30) — 저장 컬럼은 데이터 모델 담당에게 통지, 기다리지 않는다.

## §5. 액션·상태

### §5-1. ✅ 확정이 **컬럼 형태까지 지정한 것을 되살렸다**(2026-08-30)

**✓확정 2026-07-14 #4·#5·#7·#8**

> 「출고요청 **사유 필드(코드형 — '긴급 W/O 대응' 포함) 신설**」

계약에 `reasonCode`(코드형)로 정의했다 — 값 목록 `MATERIAL_ISSUE_REQUEST_REASON`에 「긴급 W/O 대응」을 포함한다. **사유별 집계가 이 기능의 존재 이유였다**(무절차 반출을 정식 경유로 돌리고 그 빈도를 본다) — 이제 가능하다. 저장 컬럼은 데이터 모델 담당에게 통지한다, 기다리지 않는다.

→ **#84에 병합 요청**한다(같은 성격 · 같은 담당) — §8-1.

### §5-2. 「긴급 W/O 참조 연결 없음」이 확정이다 — 화면이 만들지 않는다

**✓확정 2026-07-14**: 「**긴급 W/O 참조 연결 없음**(실투입 추적 = genealogy 커버)」

**그런데 `material_issue_request.work_order_id`가 NOT NULL이다.** W/O를 반드시 가리킨다.

**모순이 아니다** — 확정이 말한 「참조 연결」은 **「이 요청이 어느 긴급 W/O 때문에 생겼는지를 잇는 별도 필드」**이고, `work_order_id`는 **「이 자재를 어느 W/O에 쓸 것인가」**다.

| | 뜻 |
| --- | --- |
| `work_order_id` (실재) | **투입 대상** W/O |
| 「긴급 W/O 참조」 (만들지 않음) | **발생 원인** W/O |

**긴급 W/O 대응이면 둘이 같다.** 다르게 쓸 일은 「A의 부족분을 B의 여분으로 메운다」인데, **그것은 genealogy(실투입 추적)가 커버한다**는 것이 확정의 논지다.

**화면 규칙**: 원인 W/O를 묻지 않는다. **사유 코드가 그 역할**을 한다(그래서 §5-1이 더 아프다).

### §5-3. BOM 밖 품목도 요청할 수 있다 — 모델이 앞섬

```
material_issue_request_line.bom_component_id   bigint     ← nullable
```

**nullable이라 BOM에 없는 품목도 라인에 담긴다.**

프로세스는 「BOM 품목 정합 조건으로 교차 투입」이라 하여 **BOM 안쪽만** 상정하는 듯한데, **데이터는 더 넓다.**

**화면 설계**: 「BOM 소요량 불러오기」로 BOM 기반 라인을 채우되 **「+ 품목 추가」로 BOM 밖도 허용**하고 **경고**(A-9 ⓑ)를 붙인다.

```
⚠ BOM에 없는 품목입니다. 투입 시 오투입 검증에 걸릴 수 있습니다 (P-02-03)
```

⚠ **`P-02-03`(자재 투입 스캔·오투입 검증 · 3차)이 BOM 기준으로 막는다면** BOM 밖 품목은 출고돼도 투입이 안 된다. **두 화면의 판정 기준이 같은지 확인 필요** → §8-2.

### §5-4. 도착 위치가 여기서는 **FK**다

```
material_issue_request.destination_location_id   bigint NOT NULL → mdm.location   ✅ FK
logistics.goods_issue.destination_type_code + destination_id     ⚠ 다형(A-10)
```

**4차 `M-01-08` §5-6에서 남긴 것이 여기서 확인된다** — 요청은 위치를 FK로 정확히 가리키고, 출고 전표는 다형이다.

**A-10 규칙 3**(다형과 FK 병존 시 둘이 같은 대상인지 먼저 확인) 적용:

| | |
| --- | --- |
| 요청의 도착 | ✅ `mdm.location` |
| 출고의 도착 | ⚠ **같은 위치를 가리키는가**가 미정(`M-01-08` §8-4) |

**화면은 요청의 FK를 정본으로 두고**, 출고 전표의 다형은 서버가 채우게 한다.

### §5-5. 「무절차 반출 금지」를 화면이 말한다

확정이 **「무절차 창고 반출 금지」**를 명시했다. **이 화면의 존재 이유가 그것이다.**

**G-5 적용** — 확정 번호를 문구에:

```
ⓘ 무절차 창고 반출은 금지입니다. 부족분도 정식 출고를 경유합니다.
  (2026-07-14 확정 #4·#5·#7·#8)
```

⚠ **화면이 있다고 반출이 막히지는 않는다** — 현장에서 그냥 가져가는 것을 시스템이 막을 수 없다. **문구는 규칙을 알리는 것이지 강제가 아니다.**

1. ⚠ **이 미결은 폐기됐다(2026-08-30)** — 「컬럼이 없어서 §I에 등재한다」가 아니라, 계약이 확정대로 `reasonCode`를 정의하고 데이터 모델에는 통지만 하는 것이 맞았다 (§5-1)
2. **집계 불가가 곧 기능 무력화인 경우가 있다** — 이 기능의 존재 이유가 「무절차 반출을 정식 경유로 돌리고 **그 빈도를 보는 것**」인데, 사유가 자유 텍스트면 볼 수 없다. **A-11의 「물러난 수준」에 「그래서 이 기능이 무엇을 못 하게 되는가」를 적는다** (§5-1)
3. **같은 대상을 한 화면은 FK로, 다른 화면은 다형으로 가리킨다** — 요청의 도착(FK) vs 출고의 도착(A-10 다형). **A-10 규칙 3을 적용해 요청 쪽을 정본으로 두고 다형은 서버가 채운다** (§5-4)
