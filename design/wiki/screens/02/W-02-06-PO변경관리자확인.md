# W-02-06 · P/O 변경 관리자 확인

## §0. 요약

- **개요**: 관리웹에서 생산관리자가 ERP발 P/O 변경 이벤트(수량·납기·중단)를 확인해 「변경 반영」 또는 「기존 유지(강행)」로 판정하는 화면. P/O 자체는 수정 불가(R07)이며, 두 갈래 모두 메인 W/O로 복귀한다(강행 시 불일치 플래그 유지).
- **주요 데이터**: 변경 알림(`integration.integration_message` — `payload` jsonb), P/O(`planning.production_order` — `version_no`), 영향 W/O(`production.work_order`).
- **핵심 액션**: 변경 알림 선택 → 판정 선택(반영/강행 — 강행 시 사유 입력 필수) → 확인 처리.

> ✅ **정정(2026-08-30)** — R09의 「불일치 플래그」(`WorkOrder.poMismatch`)와 R08의 「확인 이력」(`ProductionOrder.acknowledgedAt/By`·`acknowledgeDecisionCode` · `POST :acknowledge`)은 이미 계약에 있었다. 계약을 확인하지 않은 채 「컬럼이 없다」로 적었던 것이 원칙 위반이었다. 이 화면은 **B-1 충돌 원인 2번(ERP 배치)이 정면으로 걸리는** 첫 화면이다.

## §5. 액션·상태

### §5-1. ⚠ 변경은 **이미 반영된 뒤에** 화면에 온다

**R07이 「P/O = ERP 발행·MES 수신본」**이라 MES는 ERP가 보낸 것을 그대로 받아 저장한다. 즉 화면이 열릴 때 **`production_order.order_qty`는 이미 4,000**이다.

**그러면 「기존(MES) 5,000」을 무엇으로 보이나.**

| 안 | 출처 |
| :-: | --- |
| **① `integration_message.payload`** *(권고)* | 수신 원문이 jsonb로 남는다. **이전 값이 payload에 있으면** 비교 가능 |
| ② `audit.audit_event` | `before_value`/`after_value` jsonb — ⚠ **사용 규약이 없다**(§I-5 · #68) |
| ③ W/O의 수량 | W/O는 아직 3,000이라 **간접 비교**는 된다 |

**①을 권고**하되 **payload에 이전 값이 담기는지가 미정**이다 — ERP가 변경분만 보내면 이전 값이 없다. **③이 확실한 fallback**이다(W/O가 옛 계획을 갖고 있다).

#### ✅ 해소(2026-09-01) — 넷째 길을 냈다. 위 세 안은 전부 「변경 개체가 없다」는 전제 위였다

⛔ **없던 것은 변경 전 «값»이 아니라 「변경」이라는 «기록» 자체였다.** P/O 관련 스키마는 `ProductionOrder`·`ProductionOrderAcknowledge` 둘뿐이었고, 확인 기록조차 P/O 행의 «필드»라 마지막 하나만 남았다. ERP 메시지를 적용할 때 P/O 행을 덮어써 그 순간 이전 값이 사라진다.

⭐ **그런데 서버는 그 순간 양쪽을 다 쥐고 있다.** `unacknowledgedOnly` 설명이 「마지막 변경 수신이 그 뒤인 것만 내린다」라 **서버가 수신 시점을 추적함을 스스로 증언**하고, `:acknowledge` 의 409 문구도 「남이 고쳤다」가 아니라 「ERP 가 다시 보냈다」다. 없는 것은 서버의 지식이 아니라 **그것을 담아 내릴 계약의 자리**였다.

그래서 ① ② ③ 어느 것도 고르지 않고 **자리를 세웠다** — `ProductionOrder.lastChange`(`receivedAt` + `changedFields[]`). 저장 자리는 데이터 모델 담당에게 통지했다 — 기다리지 않는다(공유계약 A-11 · `omf-mes-server#73`).

| 옛 안 | 지금 | 왜 |
| --- | --- | --- |
| ① `integration_message.payload` | ⛔ 쓰지 않는다 | 전산담당 전용이고 payload 노출 범위 미결(B-4-1 ④) · ERP 가 변경분만 보내면 이전 값이 아예 없다 |
| ② `audit.audit_event` | ⛔ 쓰지 않는다 | `before_value` 는 「키·값 구조가 정해져 있지 않다」 — 규약(구 `omf-mes#68`)이 아직 없다 «(정합주: 2026-09-03 — 2026-09-01 에 함께 든 「`target_type_code` 값 목록 미정」은 지금 맞지 않는다. 계약이 `enum` 7값(`APP_USER`·`ROLE`·`WORKER`·`TERMINAL`·`ITEM`·`ROUTING`·`INSPECTION_PLAN_VERSION`)으로 닫았다. ⭐ **그런데 그 일곱에 P/O 가 없다** — 감사 이벤트는 「변경 이력이 남아야 하는 마스터」만 담는 축이라 P/O 변경은 애초에 이 표에 오르지 않는다. 물러난 결론은 그대로이고 이유가 더 굳어졌다)» |
| ③ W/O 수량 간접 비교 | ⛔ 쓰지 않는다 | 수량만 되고 **납기·중단을 말하지 못한다.** 화면 §3 이 요구하는 세 행 중 둘이 빈다 |

⭐ **이력을 쌓지 않는 것이 확정이다(사용자 확정 2026-09-01)** — 이 화면은 판정 중 ERP 재변경이 오면 `409` 로 막고 **다시 불러와 새 변경분으로 다시 판정**한다(§5-3). 관리자는 언제나 「지금 상태」로 판단하므로 지나간 변경은 판정 대상이 아니다. **마지막 한 건이면 세 구획이 다 선다.**

⛔ **항목은 열거 셋이다** — `ORDER_QTY`·`DUE_DATE`·`STATUS_CODE`. 그 밖이 바뀌면 `changedFields` 가 **빈 배열**로 오고, 화면은 「이 변경의 항목을 낼 수 없습니다 — 원문은 연계 동기화 현황(`W-06-10`)에서 봅니다」를 그린다(공유계약 G-9 · A-11 보강: 물러난 사실은 결과가 나오는 자리에 적는다). ⚠ 「중단·수량」은 확정(REQ-PR-0024)이고 **납기는 이 화면 스펙이 근거**다(§3·§5-5).

→ §8-1.

### §5-2. ✅ 「불일치 플래그」는 이미 계약에 있었다 — 정정(2026-08-30)

**확정**(R09 · ✓확정 2026-07-04 QA #23): 「'변경 반영 vs 기존 유지(강행)' 선택 · **강행 시 불일치 플래그**」

`WorkOrder.poMismatch`(boolean, 서버가 세운다)가 이 확정을 그대로 구현한다.

| 확정 | 실재 |
| --- | --- |
| 강행 시 **플래그로 표시** | ✅ `poMismatch = true` |
| 불일치 W/O **목록 조회** | ✅ 가능 — `poMismatch`로 필터 |
| 마감 시 불일치 확인 | ✅ `W-02-05`가 이 값을 읽는다 |

⚠ **이전 버전이 「컬럼이 없다」로 적은 것은 계약을 확인하지 않은 오류였다** — A-13이 경고한 실패 형태의 실례다.

### §5-3. B-1 충돌 원인 2번(ERP 배치)이 처음 화면에 걸린다

**B-1 확장**(v0.4)이 충돌 원인 3종을 든다: **사용자 / ERP 배치 / 워커 리스**.

**이 화면이 ERP 배치와 부딪치는 첫 화면이다.**

```
관리자가 화면을 열어 판정하는 사이  →  ERP가 같은 P/O 를 또 바꿔 보낸다
                                    →  production_order.version_no 가 오른다
```

| | 처리 |
| --- | --- |
| 판정 저장 시 충돌 | `409` + **「그 사이 ERP가 다시 변경했습니다」** — G-1의 「저장 충돌」 |
| 다음 행동 | **다시 불러오면 풀린다** — 새 변경분으로 다시 판정 |

⚠ **문구가 「남이 고쳤다」가 아니라 「ERP가 다시 보냈다」여야 한다.** G-1은 저장 충돌을 「내가 보는 사이 남이 고쳤다」로 설명하는데, **여기서는 사람이 아니다** → §9-2.

### §5-4. ✅ 「모두 관리자 확인」의 확인 이력 — 이미 계약에 있었다(정정 2026-08-30)

**R08**: 「P/O 변경 시 W/O 전파(중단·수량 변경, **모두 관리자 확인**)」

`ProductionOrder.acknowledgedAt`·`acknowledgedBy`·`acknowledgeDecisionCode`가 확인 시각·확인자·판정(반영/강행)을 전부 담는다 — `POST /planning/production-orders/{id}:acknowledge`가 세운다.

**§J는 적용하지 않는다.** J-5(「일어나지 않는 것」 명시)의 정신대로, **이것은 승인 워크플로우가 아니라 확인 행위**다 — 계약도 별도 결재선 없이 단일 액션으로 되어 있어 이 판단과 일치한다.

### §5-5. 「중단(취소)」 변경은 성격이 다르다

목록 예시의 `PO-…0019 중단(취소)`는 수량·납기 변경과 다르다.

| 변경 | 반영하면 | **무엇을 보내나** |
| --- | --- | --- |
| 수량 | W/O 수량 조정 | `:acknowledge` 본문 `workOrderAdjustments[].orderQty` — **한 트랜잭션** |
| 납기 | W/O 계획 시각 조정 | 동상 `.plannedStartAt`·`.plannedEndAt` |
| **중단·취소** | **W/O를 취소해야 한다** — 예외 E-4 ④는 **2026-08-12 종결**됐다: 취소 상태 신설·회수 규칙 **둘 다 확정**(DR-007) | `:cancel` 을 **건별로** — 선발행 슬롯 전건 즉시 폐번(DR-007) |

⭐ **선발행 LOT 회수는 취소가 스스로 한다**(DR-007 ✓확정 2026-08-12) — 마감에 위임하지 않는다. `POST /production/work-orders/{workOrderId}:cancel` 이 취소 상태로 옮기면서 선발행 슬롯을 **전건** 즉시 폐번한다(R27 과 같은 모양이고, R82 의 「마감 시점 전용 · 실적 없는 슬롯만」과는 대상 집합이 다르다). 화면은 저장 전에 그 파급을 말한다(G-19).

⛔ **서버가 자동으로 나누지 않는다.** P/O 5,000→4,000 인데 영향 W/O 가 셋(각 3,000)이면 「어느 것을 얼마나」는 업무 판단이고, 실적이 이미 붙은 W/O 가 섞인다(§6). **화면이 W/O 별로 정해 보낸다.**

⚠ **수량·납기는 한 요청, 취소는 건별** — 가르는 기준은 「되돌릴 수 없는 부수 효과가 있는가」와 「건마다 다른 업무 입력을 받는가」다(공유계약 B-8-1). 취소는 둘 다 「예」다.

### §5-6. 액션

| 액션 | 활성 조건 |
| --- | --- |
| 변경 알림 선택 | 목록에서 |
| **영향 W/O 조회** | **알림 선택됨** — 자동 |
| 판정 선택(반영/강행) | 알림 선택됨 |
| **W/O 조정 입력(수량·계획 시각)** | **판정 = 반영 선택됨 AND 영향 W/O 가 1건 이상** |
| 사유 입력 | **강행 선택 시 필수**(화면 규칙 — DB는 강제하지 않는다) |
| **확인 처리** | 판정 선택됨 AND (반영 **또는** 사유 입력됨) |

⛔ **「확인 처리」의 활성 조건은 바꾸지 않는다.** 반영인데 조정을 하나도 안 한 상태로도 저장할 수 있어야 한다 — 중단·취소 반영이 그 경우다(조정할 수량이 없고 후속이 `:cancel` 이다). 막으면 취소 갈래가 아예 못 지나간다. 대신 §6 이 경고를 진다.

## §9. 이 장에서 나온 공유 계약 후보

1. ⚠ **이 패턴 항목은 폐기됐다(2026-08-30)** — 불일치 플래그·확인 이력은 애초에 「자리가 없던」 것이 아니라 계약에 이미 있었는데 확인하지 않은 것이었다 (§5-2)
2. **B-1 저장 충돌의 문구는 충돌을 일으킨 주체에 따라 달라진다** — G-1은 「내가 보는 사이 **남이** 고쳤다」로 설명하는데 ERP 배치·워커 리스는 사람이 아니다. **B-1이 든 충돌 원인 3종에 각각의 문구를 계약이 정한다** (§5-3)
3. **「확인」과 「승인」을 섞지 않는다** — R08의 「모두 관리자 확인」에 §J(승인 워크플로우)를 적용하면 결재선·한도·번복 불가가 딸려 온다. **J-5(「일어나지 않는 것」 명시)의 정신을 확인 행위에도 적용**해, 승인이 아님을 스펙이 밝힌다 (§5-4)
4. **열거로 닫을 수 있으면 다형·자유 형식을 만들지 않는다** — `audit_event.before_value` 는 「키·값 구조가 정해져 있지 않다」로 못 쓰는 자리가 됐다. P/O 변경은 항목이 셋으로 닫혀 `enum` + 표시 문자열로 세울 수 있었다. **닫히는지 먼저 세어 본다** (§5-1)
