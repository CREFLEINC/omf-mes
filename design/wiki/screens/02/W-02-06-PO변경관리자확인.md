# W-02-06 · P/O 변경 관리자 확인

## §0. 요약

- **개요**: 관리웹에서 생산관리자가 ERP발 P/O 변경 이벤트(수량·납기·중단)를 확인해 「변경 반영」 또는 「기존 유지(강행)」로 판정하는 화면. P/O 자체는 수정 불가(R07)이며, 두 갈래 모두 메인 W/O로 복귀한다(강행 시 불일치 플래그 유지).
- **주요 데이터**: 변경 알림(`integration.integration_message` — `payload` jsonb), P/O(`planning.production_order` — `version_no`), 영향 W/O(`production.work_order`).
- **핵심 액션**: 변경 알림 선택 → 판정 선택(반영/강행 — 강행 시 사유 입력 필수) → 확인 처리.

> 작성일: 2026-08-05 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **R09가 요구하는 「불일치 플래그」를 담을 컬럼이 없다.** 그리고 이 화면은 **B-1 충돌 원인 2번(ERP 배치)이 정면으로 걸리는** 첫 화면이다.

## §5. 액션·상태

### §5-1. ⚠ 변경은 **이미 반영된 뒤에** 화면에 온다

**R07이 「P/O = ERP 발행·MES 수신본」**이라 MES는 ERP가 보낸 것을 그대로 받아 저장한다. 즉 화면이 열릴 때 **`production_order.order_qty`는 이미 4,000**이다.

**그러면 「기존(MES) 5,000」을 무엇으로 보이나.**

| 안 | 출처 |
| :-: | --- |
| **① `integration_message.payload`** *(권고)* | 수신 원문이 jsonb로 남는다. **이전 값이 payload에 있으면** 비교 가능 |
| ② `audit.audit_event` | `before_value`/`after_value` jsonb — ⚠ **사용 규약이 없다**(§I-5 · #68) |
| ③ W/O의 수량 | W/O는 아직 3,000이라 **간접 비교**는 된다 |

**①을 권고**하되 **payload에 이전 값이 담기는지가 미정**이다 — ERP가 변경분만 보내면 이전 값이 없다. **③이 확실한 fallback**이다(W/O가 옛 계획을 갖고 있다).

→ §8-1.

### §5-2. ⛔ 「불일치 플래그」를 담을 컬럼이 없다

**확정**(R09 · ✓확정 2026-07-04 QA #23): 「'변경 반영 vs 기존 유지(강행)' 선택 · **강행 시 불일치 플래그**」

**실측**: `mismatch`·`discrepancy`·`_flag` 류 컬럼이 **전 파일에서 `inspection_item_spec.required_flag` 하나뿐**이고 그것은 무관하다.

**A-11 적용 — 물러난 수준**:

| 확정 | 물러난 수준 |
| --- | --- |
| 강행 시 **플래그로 표시** | **`work_order.remarks` 자유 텍스트** |
| 불일치 W/O **목록 조회** | ⛔ **불가** — 「강행한 W/O가 몇 건인가」를 셀 수 없다 |
| 마감 시 불일치 확인 | ⛔ **`W-02-05`가 볼 것이 없다** |

⚠ **파급이 `W-02-05`(W/O 마감)까지 간다** — 마감할 때 「이 W/O는 P/O와 다르다」를 알려야 하는데 근거가 없다.

→ **§I 신규 후보** §9-1. **`M-01-07`(적치 사유)·`M-01-10`(불량 반출 사유)·`W-02-10`(출고 사유)에 이은 「기록하라는데 자리가 없다」 4번째**다.

### §5-3. B-1 충돌 원인 2번(ERP 배치)이 처음 화면에 걸린다

**B-1 확장**(v0.4)이 충돌 원인 3종을 든다: **사용자 / ERP 배치 / 워커 리스**.

**이 화면이 ERP 배치와 부딪치는 첫 화면이다.**

```
관리자가 화면을 열어 판정하는 사이  →  ERP가 같은 P/O 를 또 바꿔 보낸다
                                    →  production_order.version_no 가 오른다
```

| | 처리 |
| --- | --- |
| 판정 저장 시 충돌 | `409` + **「그 사이 ERP가 다시 변경했습니다」** — G-1의 「저장 충돌」 |
| 다음 행동 | **다시 불러오면 풀린다** — 새 변경분으로 다시 판정 |

⚠ **문구가 「남이 고쳤다」가 아니라 「ERP가 다시 보냈다」여야 한다.** G-1은 저장 충돌을 「내가 보는 사이 남이 고쳤다」로 설명하는데, **여기서는 사람이 아니다** → §9-2.

### §5-4. 「모두 관리자 확인」의 확인 이력을 담을 곳이 없다

**R08**: 「P/O 변경 시 W/O 전파(중단·수량 변경, **모두 관리자 확인**)」

**확인했다는 사실을 어디에 남기나.**

| 후보 | 판단 |
| --- | --- |
| `integration_message.completed_at` | ⚠ **전송 완료**이지 사람의 확인이 아니다 |
| `app.approval_request` | ⚠ **승인이 아니다** — R09가 「선택」이라 했지 승인이라 하지 않았다. §J를 끌어오면 결재선이 생긴다 |
| `audit.audit_event` | ⚠ 규약 없음(#68) |
| **`work_order.remarks`** | **물러난 수준** — §5-2와 같은 자리 |

**§J를 적용하지 않는다.** J-5(「일어나지 않는 것」 명시)의 정신대로, **이것은 승인 워크플로우가 아니라 확인 행위**다. 결재선·한도·번복 불가가 전부 과하다.

→ §5-2와 함께 이슈로 낸다.

### §5-5. 「중단(취소)」 변경은 성격이 다르다

목록 예시의 `PO-…0019 중단(취소)`는 수량·납기 변경과 다르다.

| 변경 | 반영하면 |
| --- | --- |
| 수량 | W/O 수량 조정 |
| 납기 | W/O 계획 시각 조정 |
| **중단·취소** | **W/O를 취소해야 한다** — 예외 E-4 ④는 **2026-08-12 종결**됐다: 취소 상태 신설·회수 규칙 **둘 다 확정**(DR-007) |

⭐ **선발행 LOT 회수는 취소가 스스로 한다**(DR-007 ✓확정 2026-08-12) — 마감에 위임하지 않는다. `POST /production/work-orders/{workOrderId}:cancel` 이 취소 상태로 옮기면서 선발행 슬롯을 **전건** 즉시 폐번한다(R27 과 같은 모양이고, R82 의 「마감 시점 전용 · 실적 없는 슬롯만」과는 대상 집합이 다르다). 화면은 저장 전에 그 파급을 말한다(G-19).

## §9. 이 장에서 나온 공유 계약 후보

1. **⛔ 「기록하라는데 자리가 없다」가 4번째다** — `putaway_task`(적치 사유 · #84) · `stock_transfer`(불량 반출 사유 · #84) · **불일치 플래그·확인 이력** · `material_issue_request`(출고 사유 · `W-02-10`). **네 건이 전부 「사유·표식을 남긴다」는 확정**이다. 개별 이슈가 아니라 **패턴으로 봐야 한다** (§5-2)
2. **B-1 저장 충돌의 문구는 충돌을 일으킨 주체에 따라 달라진다** — G-1은 「내가 보는 사이 **남이** 고쳤다」로 설명하는데 ERP 배치·워커 리스는 사람이 아니다. **B-1이 든 충돌 원인 3종에 각각의 문구를 계약이 정한다** (§5-3)
3. **「확인」과 「승인」을 섞지 않는다** — R08의 「모두 관리자 확인」에 §J(승인 워크플로우)를 적용하면 결재선·한도·번복 불가가 딸려 온다. **J-5(「일어나지 않는 것」 명시)의 정신을 확인 행위에도 적용**해, 승인이 아님을 스펙이 밝힌다 (§5-4)
