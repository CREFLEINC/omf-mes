## §0. 요약

- **개요**: 모바일(360×720dp · 스캐너 일체형 PDA) 스캔형 화면. 현장반장·작업자가 공정 간 WIP LOT 인계(W/O 대 W/O)를 스캔으로 기록한다(확정) — ⛔ **온라인 전용**이며, 이 화면은 **인계 측만** 처리하고 수령 스캔은 없다.
- **주요 데이터**: `production.operation_handover`(11열) · `operation_handover_line`(10열) · `production.work_order` · `trace.lot`.
- **핵심 액션**: ① 생산LOT 스캔(포커스 고정) → ② 다음 공정 선택(`work_order_dependency`로 후보 제시) → 인계 수량 입력 → 인계 확정.

## §5. 액션·상태

### §5-1. ⛔ 「온라인 전용」인데 §C가 그 상태를 다루지 않는다

**C-1 규칙 4**: 「연결 상태와 미동기 건수를 **상시 표시**」 — 오프라인 화면의 요건이다.

**이 화면은 오프라인이 아니다.** 그렇다면 연결이 끊겼을 때 무엇을 하나:

| 안 | 동작 |
| :-: | --- |
| **① 진입 차단** *(권고)* | 홈에서 타일 비활성 + 사유 표시(F-1 원리) |
| ② 진입은 되고 저장만 차단 | 작업자가 스캔을 다 하고 나서 막힌다 |
| ③ 로컬에 담아 두었다 나중에 | ⛔ **확정 위반** — 온라인 전용이 아니게 된다 |

**①을 권고**한다. 근거: **스캔은 연속 작업**이라 ②는 작업을 통째로 버리게 만든다.

**화면 표현**(G-2·G-3 원리 — 「할 수 없다」를 감추지 않고 경로를 보인다):

```
[ WIP 공정 이동 ]  (비활성)
 ⓘ 연결이 필요한 작업입니다 (✓확정 2026-07-24 #3)
```

⚠ **왜 온라인 전용인가를 문구가 담아야 한다**(G-5 — 확정 번호를 문구에). 작업자에게는 「왜 다른 스캔은 되는데 이건 안 되나」가 이상하게 보인다.

→ **§C 신규 조항 후보** §9-1.

### §5-2. 다음 공정을 어떻게 고르나 — W/O 두 개가 필요하다

```
from_work_order_id  NOT NULL
to_work_order_id    NOT NULL
CHECK (from_work_order_id <> to_work_order_id)
```

**공정 이동이 W/O 대 W/O다.** 스캔한 LOT에서 출발 W/O는 나오지만, **도착 W/O를 무엇으로 찾나.**

`planning.routing_operation_dependency`(실측)가 공정 순서를 갖고 `production.work_order_dependency`(실측)가 W/O 간 의존을 갖는다. **후자로 후속 W/O를 찾을 수 있다.**

```
work_order_dependency → 이 W/O 다음에 오는 W/O 목록
                      → 화면이 선택지로 제시
```

⚠ **후속이 여럿이면 작업자가 고른다.** 하나면 자동 선택하되 **바꿀 수 있게 둔다**(외주·재작업 분기가 있을 수 있다).

### §5-3. R78 — W/O가 안 끝나도 LOT은 넘어간다

> **R78**: 「W/O 마감 전이라도 **생산 완료 처리된 LOT는 다음 공정 이동 가능**」(도식 태그 545:5620)

화면은 실제 후속 W/O 상태로 선택 가능 여부를 보여 주고 서버도 인계 확정 시 실제 대상 관계·LOT 완료·도착 상태를 재검증한다. 조회 때 허용됐다는 이유로 쓰기를 무조건 허용하지 않는다. 서버 거부 시 입력·선택을 보존하고 후속 목록 재조회 및 대상 확인을 안내한다.

| 검사 | 등급 |
| --- | :-: |
| LOT이 **생산 완료** 상태인가 | **ⓐ 차단** — 완료 안 된 LOT은 넘길 수 없다 |
| **출발** W/O가 마감되었는가 | **검사하지 않는다** — R78 |
| **도착 W/O가 `CANCELLED`(취소) 상태인가** | **ⓐ 차단** — 취소는 되돌아오지 않는다 |
| **도착 W/O가 `SUSPENDED`(중단) 상태인가** | **ⓑ 경고** — 재개될 수 있다 |
| 도착 W/O가 시작되었는가 | **ⓑ 경고** — 아직 안 시작한 공정에 미리 보낼 수 있다 |

**「생산 완료」는 `Lot.completedAt`으로 판정한다** — 값이 있으면 완료, 비어 있으면 미완료다. `Lot.statusCode`는 품질 판정 축이며 생산 완료를 나타내지 않는다(§8-3). 생산 완료가 아닌 LOT의 인계를 막는 기존 조건은 그대로다. «(정합주: 2026-09-07 · `omf-mes#213` — 구표기 「trace.lot.status_code가 맨몸 … P-02-06이 만드는 상태값이 여기서 쓰인다」는 완료 시각과 품질 상태를 가른 현행 계약을 반영하지 못했다)»

**도착 W/O 상태에 따른 차단·경고를 구분한다.** 계약이 후속 목록에
`statusCode` 를 함께 실으므로 화면이 추가 호출 없이 판정한다(`GET /production/work-orders?successorOfWorkOrderId=`
— 응답 `WorkOrder.statusCode` 는 `required` 다).

| 도착 W/O 상태 | 등급 | 화면이 말하는 것 |
| --- | :-: | --- |
| `COMPLETED`(완료)·`CLOSED`(마감) | **ⓐ 차단** | 완료된 도착 작업에 추가 인계하지 않는다. 목록에서 지우지 않고 다른 후속 선택을 안내한다(2026-09-10 자율 정합 결정) |
| `PLANNED`(편성)·`CONFIRMED`(확정)·`RELEASED`(배포) | **ⓑ 경고** | 아직 시작 전이지만 사전 인계는 허용한다. 확인 후 진행 |
| `IN_PROGRESS`(진행) | 정상 | 기존 수량·품질·후속 관계 조건을 만족하면 인계 가능 |
| 미제공·알 수 없는 상태 | 차단 | 상태를 확인할 수 없으므로 재조회한다. 정상 상태로 추정하지 않는다 |
| **`CANCELLED`(취소)** | **ⓐ 차단** | 「**취소된 작업지시입니다.** 취소는 되돌아오지 않고(✓설계확정 **결정 14** 상태 전이 그래프 — 취소에서 나가는 전이가 없다), 취소 시 **선발행 생산LOT 슬롯이 전건 폐번**됩니다(**DR-007** ✓확정 2026-08-12). **다른 다음 공정을 고르거나 생산관리에 확인하세요.**」 |
| **`SUSPENDED`(중단)** | **ⓑ 경고** | 「**중단 중인 작업지시입니다.** 재개되기 전까지는 받는 사람이 없습니다(결정 14 — 중단↕재개 반복 가능). 그대로 넘기려면 확인하세요.」 |

⛔ **취소된 후속을 목록에서 «빼지» 않는다.** 「할 수 없다」는 감추지 않고 이유와 함께 보인다 —
**G-2·F-1 의 결정 기록(2026-08-02 사용자 확정)**이 「감춘다」 대안을 검토한 뒤 **비활성 + 사유
표시**로 확정했고, 그 이유가 「한 화면 안에서 규칙이 갈리지 않게」와 「작업자가 **기능 부재로
오해하지 않게**」다. 감추면 **「후속이 없다」와 「후속이 있는데 취소됐다」가 같은 모양이 된다**
(G-9 · G-26). 그때 화면은 §6 의 「다음 공정이 없습니다 — 최종 공정이면 04(제품출하)로」를
그리게 되고, **작업자가 앞 공정의 취소를 못 들었으면 최종 공정으로 오인해 출하로 보낸다.**
인계는 되돌릴 수 없다 — 인계·인수를 한 시각에 함께 찍고(§5-4) 계약에 인계 취소·정정
오퍼레이션이 없다.

⚠ **`open` 축으로 거르지 않는다.** `GET /production/work-orders` 의 `open=true` 는 취소만
빼는 것이 아니라 **완료·마감과 배포 전(편성·확정)까지 함께 뺀다** — 바로 위 표와 아래 행이
ⓑ 경고로 «통과시키기로» 한 「아직 안 시작한 공정」의 일부가 말없이 사라진다.

⚠ **중단을 막지 않는 이유** — 이 표는 이미 「아직 안 시작한 공정에 미리 보낼 수 있다」를 ⓑ 로
통과시킨다. 중단은 **시작했다가 멈춘** 것이라 미시작보다 뒤에 있어, 미시작을 통과시키면서
중단을 막으면 **한 화면 안에서 등급이 앞뒤로 뒤집힌다**(A-9 ⚠ — 「등급을 화면마다 다르게
정하면 같은 성격의 오류가 화면에 따라 다르게 굴러간다」). 다른 화면도 중단을 선택지에 둔다 —
`P-02-01` 의 목록 축 `open=true` 가 「배포 대기와 **중단 중**이 함께 나온다」이고 그 화면이
[재개]까지 시킨다. 중단을 「**사람이 판단하도록 정보만 준다**」로 다룬 선례는 `W-05-04`
§5-6 이다.

⭐ **취소·중단의 «사유»는 말하지 않는다** — 목록 응답 `WorkOrder` 에 취소·중단 사유 칸이 없고
(실측 39칸), 사유는 취소·중단을 «만드는» 요청 본문(`WorkOrderCancel.reasonCode` ·
`WorkOrderHold.reasonCode`)에만 있다. 사유를 보이려면 계약에 읽기 칸을 새로 내야 하는데 이
화면이 요구하지 않는다. **상태 표시명**은 `GET /mdm/code-values?codeGroupCode=WORK_ORDER_STATUS`
로 받는다(G-32 — 계약은 코드만 내리고 표시명을 안 내린다).

### §5-4. 인계·인수 동시 확정 — 통보 159 반영

현행 `POST /production/operation-handovers`는 버튼 한 번으로 인계와 인수를 같은 트랜잭션에서 확정한다. `receivedAt = handedOverAt`이며 각 라인의 수령량도 `handoverQty`와 같다. `P-02-03`에 후속 수령 확정 책임을 주거나 수령 대기 행을 생성하지 않는다.

이는 개발팀 통보 159의 결정 전파다(2026-09-10). 이전의 수령 화면 신설·투입 스캔 겸용 권고는 현행 동작이 아니다. 실제 별도 수령 확인·부분 수령을 도입할 경우 별도 계약 변경이 필요하며, 현재 확정 이력에서 미수령 여부를 소급 추론할 수 없다. 실제 서버 실행을 이번 문서 검토로 확인했다는 뜻은 아니다.

### §5-5. R77 — 홀드품 이동은 별개 기록이다

> **R77**: 홀드품 이동 = **재고이동 트랜잭션 별개 기록**(✓설계확정 결정 14)

`M-01-10` §5-3에서 쓴 것과 같은 근거다. **홀드된 LOT도 이동할 수 있고, 그 이동은 별개로 남는다.**

이 화면은 **공정 인계**이지 재고 이동이 아니므로 홀드품 인계가 성립하는지는 별개 판단이다.

**권고**: **차단**한다. 근거 — 다음 공정이 홀드품을 투입하면 불량이 확산된다. `P-02-03`(자재 투입 스캔·오투입 검증 · 3차)이 이미 그 검증을 갖는다.

⚠ **R77이 「이동 가능」을 말하는데 이 화면에서 막는 것**이라 근거를 문구에 적는다 — §8-4.

## §9. 이 장에서 나온 공유 계약 후보

1. **★ 「온라인 전용」 화면이 오프라인에 들어갔을 때를 §C가 다루지 않는다** — C-1은 오프라인 화면의 요건만 정한다. **진입 자체를 막고 사유와 확정 번호를 보이는 것**을 표준 형태로 세운다(F-1·G-2·G-5의 결합) (§5-1)
2. **DB가 반쪽 상태를 허용하는데 그것을 닫는 화면이 없는 경우가 늘고 있다** — `operation_handover.received_at`(수령 화면 없음) · `stock_transfer_line.received_qty`(`M-01-10`은 있음). **「누가 이 컬럼을 채우나」를 스펙이 명시**하고, 답이 없으면 미결로 남긴다 (§5-4)
3. **확정 규칙을 화면이 좁히는 경우 근거를 함께 적는다** — R77은 홀드품 이동 가능을 말하는데 이 화면은 막는다(공정 인계 ≠ 재고 이동). **좁히는 판단과 그 이유를 스펙에 남겨야** 나중에 재검토할 지점을 찾는다 (§5-5)
