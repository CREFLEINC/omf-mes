# M-02-01 · WIP 공정 이동 스캔

> 작성일: 2026-08-05 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)

## §0. 요약

- **개요**: 모바일(360×720dp + BLE 스캐너) 스캔형 화면. 현장반장·작업자가 공정 간 WIP LOT 인계(W/O 대 W/O)를 스캔으로 기록한다(확정) — ⛔ **온라인 전용**이며, 이 화면은 **인계 측만** 처리하고 수령 스캔은 없다.
- **주요 데이터**: `production.operation_handover`(11열) · `operation_handover_line`(10열) · `production.work_order` · `trace.lot`.
- **핵심 액션**: ① 생산LOT 스캔(포커스 고정) → ② 다음 공정 선택(`work_order_dependency`로 후보 제시) → 인계 수량 입력 → 인계 확정.

## §5. 액션·상태

### §5-1. ⛔ 「온라인 전용」인데 §C가 그 상태를 다루지 않는다

**C-1 규칙 4**: 「연결 상태와 미동기 건수를 **상시 표시**」 — 오프라인 화면의 요건이다.

**이 화면은 오프라인이 아니다.** 그렇다면 연결이 끊겼을 때 무엇을 하나:

| 안 | 동작 |
| :-: | --- |
| **① 진입 차단** *(권고)* | 홈에서 타일 비활성 + 사유 표시(F-1 원리) |
| ② 진입은 되고 저장만 차단 | 작업자가 스캔을 다 하고 나서 막힌다 |
| ③ 로컬에 담아 두었다 나중에 | ⛔ **확정 위반** — 온라인 전용이 아니게 된다 |

**①을 권고**한다. 근거: **스캔은 연속 작업**이라 ②는 작업을 통째로 버리게 만든다.

**화면 표현**(G-2·G-3 원리 — 「할 수 없다」를 감추지 않고 경로를 보인다):

```
[ WIP 공정 이동 ]  (비활성)
 ⓘ 연결이 필요한 작업입니다 (✓확정 2026-07-24 #3)
```

⚠ **왜 온라인 전용인가를 문구가 담아야 한다**(G-5 — 확정 번호를 문구에). 작업자에게는 「왜 다른 스캔은 되는데 이건 안 되나」가 이상하게 보인다.

→ **§C 신규 조항 후보** §9-1.

### §5-2. 다음 공정을 어떻게 고르나 — W/O 두 개가 필요하다

```
from_work_order_id  NOT NULL
to_work_order_id    NOT NULL
CHECK (from_work_order_id <> to_work_order_id)
```

**공정 이동이 W/O 대 W/O다.** 스캔한 LOT에서 출발 W/O는 나오지만, **도착 W/O를 무엇으로 찾나.**

`planning.routing_operation_dependency`(실측)가 공정 순서를 갖고 `production.work_order_dependency`(실측)가 W/O 간 의존을 갖는다. **후자로 후속 W/O를 찾을 수 있다.**

```
work_order_dependency → 이 W/O 다음에 오는 W/O 목록
                      → 화면이 선택지로 제시
```

⚠ **후속이 여럿이면 작업자가 고른다.** 하나면 자동 선택하되 **바꿀 수 있게 둔다**(외주·재작업 분기가 있을 수 있다).

### §5-3. R78 — W/O가 안 끝나도 LOT은 넘어간다

> **R78**: 「W/O 마감 전이라도 **생산 완료 처리된 LOT는 다음 공정 이동 가능**」(도식 태그 545:5620)

**DB가 막지 않는다** — `operation_handover`는 W/O 상태를 보지 않는다. **화면이 판정한다**(A-9).

| 검사 | 등급 |
| --- | :-: |
| LOT이 **생산 완료** 상태인가 | **ⓐ 차단** — 완료 안 된 LOT은 넘길 수 없다 |
| W/O가 마감되었는가 | **검사하지 않는다** — R78 |
| 도착 W/O가 시작되었는가 | **ⓑ 경고** — 아직 안 시작한 공정에 미리 보낼 수 있다 |

⚠ **「생산 완료」를 무엇으로 판정하나** — `trace.lot.status_code`가 `code_t` 맨몸이다(#64 계열). `P-02-06`(생산LOT 완료 처리 · 3차)이 만드는 상태값이 여기서 쓰인다.

### §5-4. 반쪽 인계 — `M-01-10`과 같은 형태

```
handed_over_at  timestamptz NOT NULL     ← 반드시 있다
received_at     timestamptz              ← nullable
received_qty    qty_t DEFAULT 0          ← CHECK (received ≤ handover)
```

**인계는 됐는데 수령이 안 된 상태를 DB가 허용한다.** `M-01-10`(반출됨·미도착)과 같은 형태다.

**그런데 이 화면은 인계 측만 한다.** 프로세스 S11의 태스크가 「WIP 이동 스캔」 **하나**(그룹 내 유일 행위 노드)라 **수령 스캔이 없다.**

| | 인계 | 수령 |
| --- | :-: | :-: |
| `M-01-10` 재고이동 | ① 반출 스캔 | ② 도착 스캔 |
| **`M-02-01` WIP 이동** | ✅ 이 화면 | ⛔ **화면 없음** |

⚠ **`received_at`·`received_qty`를 누가 채우나.** 셋 중 하나다:

1. **다음 공정의 자재 투입 스캔**(`P-02-03`)이 수령을 겸한다 — 3차에서 확인한 대로 `P-02-03`은 LOT을 스캔한다
2. 인계 시점에 **자동으로 수령 처리**(`received_qty = handover_qty`)
3. 수령 화면 신설

**1을 권고**하되 `P-02-03` 스펙에 그 연결이 없다 → §8-2. **2는 데이터가 거짓말을 하게 된다**(받지 않았는데 받았다고 기록).

### §5-5. R77 — 홀드품 이동은 별개 기록이다

> **R77**: 홀드품 이동 = **재고이동 트랜잭션 별개 기록**(✓설계확정 결정 14)

`M-01-10` §5-3에서 쓴 것과 같은 근거다. **홀드된 LOT도 이동할 수 있고, 그 이동은 별개로 남는다.**

이 화면은 **공정 인계**이지 재고 이동이 아니므로 홀드품 인계가 성립하는지는 별개 판단이다.

**권고**: **차단**한다. 근거 — 다음 공정이 홀드품을 투입하면 불량이 확산된다. `P-02-03`(자재 투입 스캔·오투입 검증 · 3차)이 이미 그 검증을 갖는다.

⚠ **R77이 「이동 가능」을 말하는데 이 화면에서 막는 것**이라 근거를 문구에 적는다 — §8-4.

## §9. 이 장에서 나온 공유 계약 후보

1. **★ 「온라인 전용」 화면이 오프라인에 들어갔을 때를 §C가 다루지 않는다** — C-1은 오프라인 화면의 요건만 정한다. **진입 자체를 막고 사유와 확정 번호를 보이는 것**을 표준 형태로 세운다(F-1·G-2·G-5의 결합) (§5-1)
2. **DB가 반쪽 상태를 허용하는데 그것을 닫는 화면이 없는 경우가 늘고 있다** — `operation_handover.received_at`(수령 화면 없음) · `stock_transfer_line.received_qty`(`M-01-10`은 있음). **「누가 이 컬럼을 채우나」를 스펙이 명시**하고, 답이 없으면 미결로 남긴다 (§5-4)
3. **확정 규칙을 화면이 좁히는 경우 근거를 함께 적는다** — R77은 홀드품 이동 가능을 말하는데 이 화면은 막는다(공정 인계 ≠ 재고 이동). **좁히는 판단과 그 이유를 스펙에 남겨야** 나중에 재검토할 지점을 찾는다 (§5-5)
