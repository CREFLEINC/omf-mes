# W-02-05 · W/O 마감·ERP 실적 송신

## §0. 요약

- **개요**: 관리웹에서 생산관리자가 W/O를 마감 판정(미달/정상/초과 3분류)하고, 미달 잔량의 이월/소멸을 선택한 뒤 ERP로 생산 실적을 송신하는 화면. 도메인 02(생산실행)의 출구이며 **마감 재오픈은 없다**(R83 — 정정은 상쇄식 보정 트랜잭션).
- **주요 데이터**: 작업지시(`production.work_order` — `completion_variance_reason_code`·`closed_at`), 생산실적(`production.production_result` — `corrects_production_result_id`), 생산LOT(`trace.lot.status_code`), ERP 연계 메시지(`integration.integration_message`).
- **핵심 액션**: W/O 선택 → 판정 확인(자동 3분류) → 미달 시 잔량 처분(이월/소멸)·사유 선택 → **마감**(되돌릴 수 없음) 한 번으로 ① 마감 시각 기록 ② 선발행 미등록 슬롯 자동 폐번 ③ ERP 실적 송신 메시지 적재(생산 실적 필수, 기타 항목 on/off, 검사 결과 비연계)가 함께 일어난다.

> 작성일: 2026-08-05 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 도메인 02의 출구. **B-8(트랜잭션 경계)·C-4(outbox 동형)가 처음 「송신하는 쪽」에서 검증**된다. `W-06-10`은 받는 쪽이었다.

## §5. 액션·상태

### §5-1. R80 3분류가 **컬럼에 그대로 있다** — 다만 판정은 화면이 한다

```
work_order.completion_variance_reason_code   app.code_t
-- [M] 미달·초과 완료 사유 (2-1 FR-WO-032)
```

**주석이 R80을 그대로 적었다.** 「모델이 앞섬」 사례다.

**단 3분류 판정 자체는 DB가 하지 않는다** — 화면이 계산한다.

```
양품 합계 vs order_qty  →  미달 / 정상 / 초과
```

**A-9 등급**: 판정은 **표시**(ⓒ)이고 차단하지 않는다. **초과도 실적으로 인정**한다(R81).

⚠ **「정상」의 폭이 정해지지 않았다** — 2,999개는 미달인가 정상인가. **허용 오차가 미정**이다. `app.operation_policy`가 그런 파라미터를 담는 자리다(실측 — 「초과생산 정책」 주석) → §8-1.

### §5-2. 「이월/소멸」을 담을 곳이 없다

**R81**: 「미달 잔량 = 관리자 **이월/소멸**·초과분 = 실적 인정」(✓확정 QA #27)

**이월이면 잔량이 새 W/O로 가야 하고, 소멸이면 종결된다.** 둘은 **결과가 완전히 다른데** 저장할 컬럼이 없다.

| 후보 | 판단 |
| --- | --- |
| `completion_variance_reason_code` | ⚠ **사유이지 처분이 아니다** — 「자재 결품」이 사유고 「이월」이 처분 |
| **이월 → 새 `work_order`(`parent_work_order_id`)** | ✅ **이월은 표현된다** — 잔량으로 새 W/O를 만들고 원본을 가리킨다 |
| 소멸 | ⚠ **아무것도 안 만든다** — 「소멸을 선택했다」는 사실이 안 남는다 |

**A-11 물러난 수준**:

| 확정 | 물러난 수준 |
| --- | --- |
| 이월/소멸 **선택 기록** | **이월은 새 W/O로 표현**(자식이 `parentWorkOrderId` 로 원본을 가리킨다) · **소멸은 마감 본문 `remarks`** — ✅ 계약에 자리를 냈다 |
| 소멸 건 집계 | ⛔ **불가** |

⚠ **`W-02-06`의 불일치 플래그와 같은 형태**다 — **「기록하라는데 자리가 없다」 6번째.** → §8-2.

### §5-3. R82 자동 폐번 — 값이 없어 실행할 수 없다

**R82**: 「선발행 미등록 슬롯 **자동 폐번**(재사용 금지·**마감 시점 전용**)」

```
trace.lot.lifecycleStatusCode   app.code_t NULL(생산LOT 한정) DEFAULT 'WAITING'(안)
```

~~**「폐번」 값이 정의되지 않았다**~~ ⚠ **정정(2026-08-25 · 공유계약 §I-49)** — 2026-08-07에는 「폐번」을 `trace.lot.status_code`에 둔다고 확정했으나(#46), 그 컬럼은 이후 품질 판정 축(정상·불량·검사 대기·폐기)으로 확정돼(2026-08-21 이후 quality-03 계약) 두 확정이 부딪쳤다. **결정 10의 「한 필드에 섞지 않는다」를 지키는 방법은 컬럼을 나누는 것이다** — 「폐번」은 별도 신설 컬럼 `trace.lot.lifecycleStatusCode`(생명주기 축 — 대기/활성/폐번, 생산LOT 한정)에 둔다. §I-32가 이미 품질 판정(`lot.status_code`)과 보류 문서 진행(`lot_hold.status_code`)을 나눈 것과 같은 형태로, 세 번째 축이 갈린 것이다. **물리 컬럼 신설은 데이터모델 담당 소관.**

**화면 설계**: 폐번 대상을 **집계해 보이고**(§3의 「실적 없음 1 → 자동 폐번」) 값이 정해지면 서버가 전이한다. **값이 없으면 마감은 되고 폐번만 안 된다.**

⚠ **부작용** — 폐번이 안 되면 그 슬롯이 **`ACTIVE`인 채로 남아** 「실물 없는 활성 LOT」이 쌓인다. `W-01-07`(재고 조회)에 잡힐 수 있다 → §8-3.

✅ **취소 경로도 닫혔다** — `POST /production/work-orders/{workOrderId}:cancel` 이 「취소 상태로 옮기고 선발행된 생산LOT 슬롯을 자동 폐번한다」로 확정했다(**DR-007** 2026-08-12 · R27 과 같게 즉시 폐번). R82 는 여전히 「마감 시점 전용」이고, 취소는 별도 오퍼레이션이 받는다.

### §5-4. ★ R83 상쇄식 보정이 **착지해 있다** — B-10의 실증

**R83**: 「마감 **재오픈 금지** · 정정 = **상쇄식 보정 트랜잭션** · LOT 정정 3종」

```
production_result.corrects_production_result_id
    bigint REFERENCES production.production_result
-- [M] 정정·취소 시 원본 실적 참조 (2-3 FR-PR-033/034/045)
```

**B-10(정정·교체·대체 구분 · 3차 신설)의 `corrects_*` 형태가 그대로다.**

**화면 규칙**

1. **마감 버튼에 「재오픈 불가」를 명시**한다(G-5 — 확정 번호 병기)
2. 마감 후 정정은 **`POST /production/production-results/{productionResultId}:correct`(실적 정정)로만 기록한다** — 원본을 지목해야 `correctsProductionResultId` 가 남는다. ⛔ **`P-02-04` 의 일반 저장(`POST /production/production-results`)으로는 안 된다** — 그 본문 `ProductionResultCreate` 에 원본 참조 칸이 없어(실측) 정정 연결이 **빈 채로 저장되고 오류도 나지 않는다**(B-3·B-10 이 요구한 연결이 사라진다). **이 액션을 어느 화면이 갖는지는 아직 정해지지 않았다** → §8-5. 이 화면은 재오픈을 제공하지 않는다
3. ⚠ **마감된 W/O에 상쇄 실적을 넣을 수 있는가**가 미정이다. `production_result.work_order_id`에 상태 제약이 없어 **데이터상으론 가능**하나, R83의 「재오픈 금지」와 어떻게 다른지 정리되지 않았다 → §8-5

⚠ **예외 E-12 ②가 「실행·승인 권한 주체·UNIERP 역분개성 재송신 수용 방식 잔여(U6)」**를 남겼다.

### §5-5. ERP 송신 — B-8·C-4가 **보내는 쪽**에서 처음 검증된다

**B-8 트랜잭션 경계**: 업무 엔티티는 전부 안, **외부 시스템 호출은 밖**(outbox 적재까지가 안).

```
┌ 트랜잭션 ─────────────────────────────────┐
│ ① work_order.closed_at · status_code 갱신 │
│ ② 선발행 LOT 폐번 전이 (§5-3)             │
│ ③ integration_message INSERT (적재까지)   │
└───────────────────────────────────────────┘
   ④ 실제 ERP 호출                    ← 트랜잭션 밖 · 워커가 집어간다
```

**마감은 ERP 응답을 기다리지 않는다.** 프린터가 죽어도 발행 기록이 남는 것(K-4)과 같은 구조다.

**C-4(outbox 동형)** — `message_key`를 **화면이 만들어** 넣고, 재전송은 같은 키로. `W-06-10`(연계 현황)이 재처리 화면이다.

**화면 표시**: 마감 직후 상태는 **「송신 대기」**이지 「송신 완료」가 아니다.

```
마감되었습니다. ERP 송신은 별도로 진행됩니다.  [연계 현황 → W-06-10]
```

⚠ **C-7(저장 피드백 2등급 · 4차 신설)의 관리웹 판**이다 — 오프라인이 아니어도 **「즉시 성공」이 아닌 것**이 있다.

⚠ **강조 인라인 297:5490·5491이 「위반 금지」로 표시된 항목**이다. 물러난 수준을 반드시 명시한다.

## §9. 이 장에서 나온 공유 계약 후보

1. **「즉시 성공이 아닌 것」은 오프라인만의 문제가 아니다** — 마감은 되고 ERP 송신은 outbox로 간다. C-7(저장 피드백 2등급)이 **관리웹에도 적용**된다. **외부 시스템 호출이 딸린 저장은 「완료」와 「접수」를 구분해 보인다** (§5-5)
2. **「사유」와 「처분」은 다른 컬럼이다** — `completion_variance_reason_code`는 왜(자재 결품)이고 이월/소멸은 무엇을 할지다. **한 컬럼에 둘을 담으면 집계가 무너진다** — 확정이 둘을 함께 요구하면 스펙이 나눠서 확인한다 (§5-2)
3. **「위반 금지」로 강조된 확정이 물러날 때는 특별히 표시한다** — R84의 「개발품 제외, 필수 송신」은 도식에 **강조 인라인(297:5490·5491)**으로 표시된 항목인데 판정 근거가 없어 전건 송신으로 물러난다. **A-11의 물러난 수준에 「원문의 강조 여부」를 함께 적는다** (§5-6)
