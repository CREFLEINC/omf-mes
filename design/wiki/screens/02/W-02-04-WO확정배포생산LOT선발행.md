# W-02-04 · W/O 확정·배포·생산LOT 선발행

## §0. 요약

- **개요**: 관리웹에서 생산관리자가 배정 완료된 W/O를 확정·배포하고, 그 자리에서 생산LOT을 선발행(번호 슬롯 예약)하는 화면. 확정 시 Routing Rev가 스냅샷으로 고정되며, POP 배포와 자재 출고요청 자동 발행까지 한 트랜잭션에 묶인다.
- **주요 데이터**: 작업지시(`production.work_order` — `operation_settings_snapshot` jsonb·`released_at`), 생산LOT(`trace.lot` — 선발행 슬롯 N개), 자재출고요청(`logistics.material_issue_request`, 화면 없이 자동 발행).
- **핵심 액션**: LOT 크기 입력(품목 기본값 없음) → 전달사항 등록 → **확정·배포**(배정 Validation 통과 시 활성) 한 번으로 ① W/O 확정·Rev 스냅샷 고정 ② POP 자동 배포(조회 전환) ③ 생산LOT N슬롯 선발행 ④ 자재 출고요청 자동 발행(긴급 W/O 제외)이 동시에 일어난다.

> 작성일: 2026-08-04 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 생산 실행의 **관문**. 관리웹에서 확정하면 POP 11화면이 그 위에서 돈다. 이 장에서 **선발행(번호 슬롯 예약)**과 **Rev 스냅샷 고정**을 다룬다.

### §5-2. Rev 스냅샷이 여기서 고정된다

**R12** — 「W/O 전개 시 Routing Rev 스냅샷 고정(**이후 개정 비소급**)」

```
work_order.operation_settings_snapshot   jsonb
```

**확정 시점의 공정 설정이 jsonb로 통째로 박힌다.** 이후 Routing이 개정돼도 진행 중인 W/O는 당시 설정으로 돈다.

화면은 **어느 Rev로 고정되는지 확정 전에 보여준다**(레이아웃의 `Routing IP-07 Rev 3`). 확정 후에는 바꿀 수 없으므로 미리 확인해야 한다.

> ⚠ **jsonb 키 규약이 없다.** 무엇을 스냅샷에 담는지 정해지지 않았다 — 화면이 그 내용을 보여줄 수 없다. §8-3.

### §5-3. ★ 선발행 — 「번호 슬롯 예약」을 데이터가 어떻게 담는가

**R26** — 「생산LOT = MES 발행 정본 · W/O 배포 시 **선발행**(번호 슬롯 예약 · **완료 전 실물 미귀속**)」

**개념과 데이터가 어긋난다.**

| 개념(R26) | `trace.lot` |
| --- | --- |
| 번호만 예약 · 실물 미귀속 | `initial_qty` **`CHECK (initial_qty > 0)`** — 0으로 만들 수 없다 |
| 완료 시 실물 귀속 | 상태 컬럼은 있으나 **「예약」 값이 정의되지 않았다** |

즉 **슬롯을 `initial_qty = 계획 LOT 크기`로 만들고 상태로 「아직 실물 없음」을 표시**하는 수밖에 없다. `initial_qty`가 「계획 수량」인지 「실제 수량」인지 이름이 말하지 않는다.

**R27이 여기에 얹힌다** — 「N = **계획값**이지 상한이 아니다」.

```
초과 생산  →  추가 발번 (슬롯보다 많이 만든다)
미달       →  남은 슬롯 = S12 마감에서 자동 폐번
```

**「폐번」은 `lot.status_code`(품질 판정 축)의 값이 아니다** — 생명주기 축(대기/활성/폐번)은 별도 컬럼 `lot.lifecycleStatusCode`(신설 대상)에 둔다(공유계약 §I-49 · §I-32의 lot_hold.status_code 분리와 같은 형태). 이 화면이 그 근거 화면이고, 물리 컬럼 신설은 이슈 #46이 요청 중이다.

화면은 **「계획값입니다 — 초과 시 추가 발번 · 미달 시 폐번」**을 명시한다. 사용자가 N을 상한으로 오해하면 초과 생산 시 시스템이 막는다고 생각한다.

### §5-4. 기본 위치 3종을 여기서 정하면 POP이 묻지 않는다

```
default_wip_location_id      재공 위치
default_fg_location_id       완제품 위치
default_scrap_location_id    불량 위치
```

셋 다 nullable이지만, **비워 두면 POP 화면이 매번 위치를 물어야 한다.** POP은 1024×768에 세로 여유 119px(E-1)이라 선택 UI를 얹을 자리가 없다.

**화면은 셋을 채우도록 권고한다** — 필수는 아니되 비어 있으면 경고를 보인다.

### §5-5. 확정 한 번에 넷이 움직인다

```
┌─ 한 트랜잭션 ────────────────────────────────────┐
│ ① work_order      상태 → 확정 · snapshot 고정    │
│                   released_at 기록               │
│ ② (배포)          POP이 조회로 가져간다 §5-6      │
│ ③ trace.lot × N   슬롯 선발행                     │
│ ④ material_issue_request  출고요청 자동 발행      │
└──────────────────────────────────────────────────┘
```

**공유계약 B-8 적용.** ③이 부분 실패하면 슬롯 수가 계획과 어긋나고, ④가 빠지면 자재가 라인에 안 온다.

> ⚠ **④는 「BOM 소요량 자동 산정」**인데 **긴급 W/O는 제외**된다(R29). `P-02-12`가 그 경로다. ⛔ **긴급 W/O 제외(R29) — 계약에도 앉혔다.**

### §5-6. 「자동 배포」는 밀어내기가 아니다

프로세스는 「자동 현장 배포(POP)」라 하지만, **POP이 조회로 가져가는 것**으로 본다.

- `released_at`이 기록되면 POP의 W/O 목록에 나타난다
- **서버가 POP에 밀어 넣지 않는다** — POP은 Electron 키오스크이고 상시 연결을 전제하지 않는다(오프라인 시나리오 존재)

> ⚠ **배포 확인 여부를 추적하는가** — 예외 E-4 ③ 「전달사항 미확인 채 작업 시작」이 🟠로 남아 있다. 확인 여부를 담을 컬럼이 `work_order`에 없다. §8-4.

## §9. 이 장에서 나온 공유 계약 후보

1. **스냅샷 컬럼이 있으면 「무엇이 언제 고정되는가」를 확정 전에 보인다** — `operation_settings_snapshot`처럼 확정 후 못 바꾸는 것은 미리 확인시킨다 (§5-2)
2. **계획값과 상한을 화면이 구분해 말한다** — N개 선발행이 상한으로 읽히면 초과 생산 시 사용자가 시스템을 의심한다. 「계획값이며 초과·미달 시 어떻게 되는가」를 적는다 (§5-3)
3. **상류 화면이 기본값을 채우면 하류 화면이 묻지 않는다** — `default_*_location_id` 3종을 여기서 채우면 POP이 위치를 묻지 않아도 된다. **POP의 화면 예산(E-1)을 상류가 아낀다** (§5-4)
4. **「자동 배포」는 밀어내기가 아니라 조회 가능 상태 전환이다** — 상시 연결을 전제하지 않는 셸(POP·모바일)에 서버가 밀어 넣지 않는다 (§5-6)
