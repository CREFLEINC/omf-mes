# W-02-07 · 긴급 W/O 발행

## §0. 요약

- **개요**: 관리웹 생산실행 화면. 허가된 권한자(생산관리자)가 P/O 없이 긴급 W/O를 직접 발행한다 — 발행 즉시 내부 P/O·생산계획이 자동 생성되고 BOM·Routing이 자동 전개되며, 별도 승인 없이 무배정으로 배포된다. 현장 실행은 `P-02-12`(POP)가 맡는다.
- **주요 데이터**: 작업지시(`production.work_order` — `production_plan_id` NOT NULL·`work_order_type_code`=긴급 고정), 발행 시 자동 생성되는 생산오더(`planning.production_order` — `erp_order_no` NULL)·생산계획(`planning.production_plan`). 그리고 배포가 함께 만드는 생산LOT 슬롯(`trace.lot` — 1 슬롯 §4-C).
- **핵심 액션**: 품목 검색·선택 → 수량·납기·사유 입력 → BOM·Routing 자동 전개 확인 → **발행·배포**(품목·수량·사유 입력 AND BOM·Routing 존재 AND 권한 있음일 때 활성).

> **§I-15(#76)의 진짜 당사자.** `P-02-12`는 긴급 W/O를 *쓰는* 화면이었고, 이 화면이 *만드는* 화면이다. **`W-02-01`에서 찾은 `erp_order_no` nullable이 해법 후보다.**

### §4-C. ⛔ 배포가 생산LOT 슬롯을 함께 만든다

이 화면은 배포 오퍼레이션(`:release`)을 부른다. 그 오퍼레이션은 확정·배포·**선발행**이 한 트랜잭션이다(R26·R27) — 그래서 이 화면에도 `trace.lot`이 걸린다(§0 주요 데이터).

슬롯 수 N = 올림(지시수량 ÷ LOT 크기)이고, 이 화면은 **LOT 크기 = 지시수량**을 보내므로 항상 **1 슬롯**이다. §3 레이아웃의 「LOT수 1」 열이 그 결과다 — **파생이지 입력이 아니다**(§5-7).

긴급도 선발행이 필요한 이유: 현장 실행(`P-02-12`)이 정상 경로 화면을 재사용하므로(`P-02-12` §5-1) 생산LOT이 있어야 완료·인식표 발행이 돈다.

## §5. 액션·상태

### §5-1. ⛔ §I-15 — P/O 없이 W/O를 만들 수 없다

**확정**(02-S-D): 「긴급 W/O 발행 — **P/O 비귀속**·발행자 직접 전개·별도 승인 없음」

**실측 체인**:

```
production.work_order.production_plan_id      bigint NOT NULL
    └ planning.production_plan.production_order_id   bigint NOT NULL
          └ planning.production_order
```

**두 단계가 다 NOT NULL이라 P/O 없이 내려갈 수 없다.**

> 이것이 **#76**이고, `P-02-12`가 「화면 존재 근거가 걸린다」로 **차단** 등급을 매겼다가 **사용자 지적으로 조정으로 하향**된 건이다. 해석 3안이 셋 다 화면을 바꾸지 않기 때문이었다.
> **이 화면은 만드는 쪽이라 파급이 더 직접적**이다 — 그럼에도 **화면 골격(품목·수량·납기·사유·자동 전개·발행)은 어느 해석에서도 같다.** **조정** 등급을 유지한다.

### §5-2. ★ `W-02-01`에서 찾은 것이 해법 후보다

`W-02-01` §5-2에서 확인했다:

```
planning.production_order.erp_order_no   varchar(100)     ← nullable
```

**R07이 「P/O = ERP 발행」이라고만 했는데 ERP 번호가 nullable이다.** 즉 **ERP에서 오지 않은 P/O를 데이터가 이미 허용한다.**

**해법 3안**

| 안 | 방법 | 판단 |
| :-: | --- | --- |
| **① 내부 P/O 자동 생성** *(권고)* | 발행 시 `erp_order_no = NULL`인 P/O + 계획을 서버가 한 트랜잭션으로 만든다 | ✅ **모델 변경이 필요 없다.** 「P/O 비귀속」을 **「ERP P/O에 귀속되지 않는다」**로 읽으면 확정과도 맞는다 |
| ② `production_plan_id` nullable화 | 모델 변경 | ⚠ 파급이 크다 — 계획 없는 W/O가 모든 조회에서 예외가 된다 |
| ③ 긴급 전용 테이블 | 모델 변경 | ⛔ 같은 업무에 테이블이 둘 |

**①을 권고한다.** 근거:

- **`bom_level`·`parent_production_order_id`가 이미 「ERP가 안 보낸 P/O」를 상정한다** — 반제품 오더는 MES가 전개해 만들 수 있는 것이고, 그것도 `erp_order_no`가 없다
- **B-8(트랜잭션 경계)**대로 P/O·계획·W/O 생성이 **한 트랜잭션 안**이다 — 중간에 끊기면 고아 P/O가 남는다

⚠ **①이면 화면이 사용자에게 이 사실을 보여야 한다.** 「P/O 비귀속」이라 배웠는데 P/O 번호가 생기면 혼란스럽다.

```
ⓘ 내부 관리번호 PO-…0099 가 생성됩니다. ERP P/O 에는 귀속되지 않습니다.
```

→ **#76에 이 해법을 코멘트로 제안**한다 — §8-1.

### §5-3. 「사유」를 담을 곳이 없다 — 5번째

**02-S-D는 사유를 명시적으로 요구하지 않지만**, 예외 흐름이고 **승인이 없으므로**(「별도 승인 없음」) 사유 기록이 유일한 통제 수단이다.

`work_order`에 사유 컬럼이 있는가:

```
completion_variance_reason_code   ← 미달·초과 완료 사유 (마감용)
remarks text                       ← 자유 텍스트
```

**발행 사유용 컬럼은 없다.** `completion_variance_reason_code`는 **마감 시 쓰는 것**이라 용도가 다르다.

⛔ **되살리기 잔여** — 이 축소의 근거는 물리 모델 결손이었고 A-11 v4.6 이 그 근거를 철회했다. 되살리려면 계약 신설이 따르므로 별건으로 추적한다(변경 통지 판단 포함). 지금은 `remarks`에 담고 **사유별 집계 불가**를 명시한다 — 공유계약 §I-41 계열이다.

⚠ **「기록하라는데 자리가 없다」 5번째**다(`W-02-06` §9-1의 4건 + 이것). 다만 **이 건은 확정 문구가 사유를 명시하지 않아** 앞의 넷보다 근거가 약하다 — **§I에 올리지 않고 미결로만** 둔다.

### §5-4. 「긴급 고정」·「승인 없음」·「출고요청 제외」를 **구조로 표현한다**

**G-4** — 확정이 「끌 수 없다」·「하지 않는다」일 때 기본값 on/off로 구현하면 확정이 무너진다.

| 확정 | 잘못된 표현 | 옳은 표현 |
| --- | --- | --- |
| 유형 = 긴급 | `[유형 ▾]` 드롭다운(기본 긴급) | **선택 불가 · 「긴급」 고정 표시** |
| 별도 승인 없음 | `[✓] 승인 요청` 체크박스 | **컨트롤 없음** + 안내 |
| 자동 출고요청 **제외** | `[ ] 출고요청 자동 발행`(기본 끔) | **컨트롤 없음** + 「부족 시 `W-02-10`」 안내 |
| 자원 배정 없음 | 배정 구획(비활성) | **구획 자체를 두지 않는다** + 안내 |

**G-5 적용** — 확정 번호를 문구에:

```
자재 출고요청을 자동 발행하지 않습니다 (2026-07-14 확정 #4·#5·#7·#8)
부족분은 「추가 자재 출고 요청」으로 정식 경유하세요 → W-02-10
```

### §5-5. 권한 — F-2의 **관리웹 축**이다

02-S-D: 「**허가된 권한자**(생산관리자)」

**F-2**: 권한 게이팅은 축이 둘이고 폼팩터마다 다르다 — **관리웹은 `app.role_permission.permission_code`**.

⚠ **권한 값 목록이 회신 E-9 대기**다(F-3 표). 화면은 **권한 판정을 서버에 맡기고** 없으면 **버튼 비활성 + 사유**(F-1 원리).

⚠ **이 화면은 승인이 없는 대신 권한이 유일한 통제다.** 권한 값이 정해지기 전에는 **누구나 발행할 수 있는 상태**가 된다 → §8-3.

### §5-6. *(비어 있다 — 액션표는 §5-11로 옮겼다)*

⚠ **번호를 다시 매기지 않는다.** 계약이 §5-7·§5-8·§5-9·§5-10을 근거로 이름을 달고 있어(`omf-mes#258`·`#259` 반영분) 재번호는 그 인용을 전부 깨뜨린다. 자리만 비워 둔다.

### §5-7. LOT 크기를 묻지 않는다

배포 본문은 `lotSize`를 **필수**로 받는다. 확정·배포 화면(`W-02-04`)은 그것을 사용자에게 묻는다(`W-02-04` §8-2 — 품목 기본값이 없어 매번 입력).

**이 화면은 묻지 않는다.** 확정 셋이 이미 컨트롤을 걷어냈고(§5-4 — 유형·승인·출고요청·배정), 다섯 번째를 얹으면 「빨리 낸다」는 이 화면의 성격이 바뀐다. 02-S-D가 「별도 승인 없음 · 배정 없이 투입」이다.

**지시수량 전량을 한 슬롯으로 보낸다.** 화면이 그 사실을 보인다 — 「LOT 1개로 배포됩니다」. 화면이 대신 정한 값이면 정했다는 사실이 보여야 한다(A-11).

⛔ **비우고 서버 기본값에 맡기지 않는다** — 「비우면 계획값」은 원천 없는 기본값이라 이미 한 번 걷어낸 자리다(`omf-mes#206`).

⚠ **§3 레이아웃의 「LOT수 1」이 근거가 아니다** — 그것은 구조 기술의 예시값이다. 근거는 위 프로세스 확정이다.

### §5-8. 배포 안 된 W/O를 이어받는다

「발행·배포」는 두 호출이고 그 사이는 한 트랜잭션이 아니다. 발행이 성공하고 배포가 실패하면 **배포되지 않은 작업지시가 남는다.**

화면은 그것을 「발행 완료」라 말하지 않는다. 만들어진 번호를 보이고 「만들어졌으나 배포되지 않았습니다」를 밝히며 **배포만 재시도**한다. 멱등(여러 번 불러도 결과가 같다) 키를 유지해 이중 배포를 막는다.

⛔ **되돌리지 않는다.** 취소 액션은 이 화면에 없고(§5-11), 취소 오퍼레이션은 선발행 슬롯 자동 폐번이 부수 효과라 배포 전 작업지시에 쓰면 다른 일을 하는 액션을 빌려 쓰게 된다. 그 취소도 잠금 토큰이 필수라 **같은 실패 창이 하나 더 생긴다.**

⭐ **화면을 떠나도 잃지 않는다.** 진입할 때 `GET /production/work-orders?workOrderTypeCode=EMERGENCY&released=false`를 한 번 불러, 있으면 목록으로 보이고 [배포 재시도]를 낸다. **서버가 정본이므로** 새로고침·다른 단말·다른 사용자에게도 보인다.

⛔ **화면에 저장소를 두지 않는다** — 스펙에 없는 저장을 화면이 발명하면 그 사용자의 그 브라우저에만 남는다.

⚠ 빈 목록이 정상이다 — 있을 때만 구획을 보인다.

### §5-9. 개정을 고르는 자리

「자동 전개」는 서버가 다 해 주는 것이 아니다 — 발행 본문이 공정 식별자를 **필수**로 받는다. 화면이 Routing 개정을 고른다.

⛔ **화면이 상태 문자열로 거르지 않는다**(G-8). 대신 조회에 「쓸 수 있는 것만」 참·거짓을 실어 **서버가 판정한 목록**을 받는다.

개정이 둘 이상 남으면 자동 선택하지 않고 사용자가 고른다 + 경고 — `W-02-02` §5-6과 같은 처리다. 자재 명세(BOM)는 기본 지정이 있어 자동 선택된다. **둘의 동작이 갈리는 이유를 문구로 설명한다.**

목록이 비면 차단하고 사유를 보인다 — 「지금 쓸 수 있는 개정이 없습니다」. §6의 「Routing 없음 ⛔ 차단」과 같은 자리다.

서버도 막는다 — 목록을 받은 뒤 저장까지 사이에 폐기될 수 있어 발행이 400으로 거절할 수 있다. 화면은 그 오류를 그대로 보인다.

### §5-10. 유형 값

유형 칸에 `EMERGENCY`를 **반드시 실어 보낸다.**

⛔ **칸을 빼고 보내지 않는다** — 서버 기본값 `NORMAL`이 붙어 화면은 「유형: 긴급」이라 적어 놓고 양산 작업지시를 만든다. 오류가 나지 않아 아무 데서도 드러나지 않고, 긴급 현장 투입 화면(`P-02-12`)의 목록에도 뜨지 않는다.

값 집합은 셋이다 — `NORMAL`(양산) · `EMERGENCY`(긴급) · `REWORK`(재작업). 그룹 이름은 `WORK_ORDER_TYPE`(G-32).

⛔ **화면이 이 값을 로직에 흩어 박지 않는다** — 한 곳에 모아 두고 그 한 곳만 참조한다.

### §5-11. 액션

| 액션 | 활성 조건 |
| --- | --- |

## §9. 이 장에서 나온 공유 계약 후보

1. **§I 항목의 해법이 다른 화면에서 나올 수 있다** — #76(P/O 없이 W/O 불가)의 해법 후보가 `W-02-01`의 `erp_order_no` nullable이었다. **§I 대장에 「해법 후보」 열을 두어** 차수를 넘어 발견된 것을 잇는다 (§5-2)
2. **승인이 없는 화면에서는 권한이 유일한 통제다** — 02-S-D가 「별도 승인 없음」을 확정했으므로 §J를 적용하지 않는다. **그러면 F-2(관리웹 권한 축)의 값 목록이 운영 전 필수 조건**이 된다 — 미결 등급을 「조정」이 아니라 **운영 차단**으로 따로 표시할 필요가 있다 (§5-5)
3. **「하지 않는다」가 여럿 겹치는 화면은 안내가 화면의 절반이 된다** — 이 화면은 승인 없음·배정 없음·출고요청 없음·유형 고정 넷이 겹친다. **G-4(구조로 표현)를 넷 다 적용하면 컨트롤이 사라지고 안내만 남는다.** 안내를 배너로 흩지 말고 **한 구획에 모으는** 표준형이 필요하다 (§5-4)
4. **남의 화면을 위해 쓰인 오퍼레이션을 빌려 쓰면 그 화면의 입력이 따라온다** — 배포 오퍼레이션은 확정·배포 화면(`W-02-04`)을 근거로 쓰였고 설명·필드 설명·잠금 정책이 전부 그 화면을 인용한다. 이 화면이 그것을 부르는 순간 그 화면의 입력(LOT 크기)과 부수 효과(선발행)가 함께 온다. **계약에 「부르는 화면이 둘이다」를 적지 않으면 두 번째 화면은 스펙에 없는 일을 하게 된다** (§5-7)
