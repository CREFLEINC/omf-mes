# W-02-02 · W/O 전개·편성

## §0. 요약

- **개요**: 관리웹 생산실행 화면. 생산관리자(+전산담당)가 ERP P/O 한 건에 대해 BOM(ERP 정본)·Routing(MES 정본) 마스터 점검(내부 패널)을 거쳐 생산계획을 편성하고, MES Routing 기준 세부공정 W/O로 전개(1 P/O→N W/O)한다. 러닝체인지 대비 분할 생성 안내도 포함하며, 자원배정은 별도 화면(`W-02-03`)이 맡는다.
- **주요 데이터**: 생산계획(`planning.production_plan` — `bom_id`·`routing_id` NOT NULL), 작업지시(`production.work_order` — `operation_settings_snapshot` jsonb·`parent_work_order_id`), 공정 의존(`production.work_order_dependency`), 공정 라우팅(`planning.routing_operation`).
- **핵심 액션**: 마스터 점검(BOM·Routing 확인, Rev 후보 2건 이상 시 수동 선택) → 생산계획 추가·편성(계획일·수량·BOM/Routing Rev·라인) → W/O 전개 표 확인(순서·공정·수량·선행·기본 위치) → **저장** / **전개 확정 →** `W-02-03`.

> 작성일: 2026-08-05 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **R13 「Routing 부재 = BOM 기반 fallback」이 `production_plan.routing_id NOT NULL`에 막힌다.** 프로세스가 말하는 「1 P/O → N W/O」도 실제로는 3단 체인이다.

## §5. 액션·상태

### §5-1. 「1 P/O → N W/O」가 실제로는 **3단 체인**이다

프로세스 R14가 「**1 P/O → N W/O**」라고 하는데 데이터는 중간에 하나가 더 있다.

```
production_order   1
   └ production_plan   N     ← 프로세스가 말하지 않는 계층
        └ work_order      N
```

`work_order.production_plan_id`가 **NOT NULL**이라 **계획을 건너뛸 수 없다.**

**계획이 무엇을 담는가**(실측): `plan_date`(언제 만들 것인가) · `planned_qty`(얼마나) · `bom_id`·`routing_id`(어느 개정으로) · `planned_line_id`(어느 라인).

**즉 「5,000개를 08-10에 3,000 · 08-12에 2,000으로 나눈다」가 계획이고, 그 각각이 공정별 W/O로 갈라진다.**

**화면은 이 계층을 숨기지 않고 §3 ②로 드러낸다.** 숨기면 「왜 W/O가 6개인가」(계획 2 × 공정 3)를 설명할 수 없다.

⚠ **계획을 하나만 만드는 경우가 대부분이면 UI가 번거로워진다** — 기본으로 **계획 1건을 자동 생성**해 두고 나눌 때만 추가하게 한다 → §8-1.

### §5-2. 계획 수량 합계 검증은 **화면이 진다**

```
production_order.order_qty    5,000
production_plan.planned_qty   3,000 + 2,000 = 5,000   ← DB가 검증하지 않는다
```

**합계 제약이 없다.** 계획 합이 P/O 수량을 넘거나 모자라도 DB는 통과시킨다.

**A-9 등급**:

| 상황 | 등급 |
| --- | :-: |
| 계획 합 **> P/O 수량** | **ⓑ 경고** — 초과 생산 정책이 `app.operation_policy`에 있다(실측 — 「초과생산·FIFO 위반·초과투입 정책」 주석) |
| 계획 합 **< P/O 수량** | **ⓒ 표시만** — 나눠서 계획하는 중일 수 있다 |
| 계획 0건 | **ⓐ 차단** — 전개할 것이 없다 |

**A-3 적용** — 실시간 합계·잔여를 표시하고 §3 ②의 「합계 5,000 / 5,000」처럼 보인다.

### §5-3. ⛔ R13 「Routing 부재 시 BOM fallback」이 성립하지 않는다

**확정**(REQ-PR-0026 · R13): 「Routing 부재 = **BOM 기반 4M 계획 fallback** + MES 공정 등록」

**실측**:

```
production_plan.routing_id   bigint NOT NULL REFERENCES planning.routing
work_order.routing_operation_id  bigint NOT NULL REFERENCES planning.routing_operation
```

**둘 다 NOT NULL이다.** Routing 없이는 **계획도 W/O도 만들 수 없다.**

프로세스 예외 ①도 「Routing 미등록(예외 E-2) — **BOM fallback 확정**」이라고 확정으로 표시하는데 **데이터가 받지 않는다.**

**A-11 적용 — 물러난 수준**:

| 확정 | 물러난 수준 |
| --- | --- |
| Routing 없어도 BOM으로 계획 | ⛔ **불가** |
| 대신 | **Routing을 먼저 등록해야 한다** — R13의 후반부(「+ MES 공정 등록」)만 남는다 |

**화면 설계**: 마스터 점검 체인(§3 ①)에서 **Routing이 없으면 「Routing 등록 →」 경로를 안내**하고 전개를 막는다. fallback 분기를 만들지 않는다.

⚠ **R13의 앞뒤를 나눠 읽으면 모순이 아닐 수도 있다** — 「BOM 기반 4M 계획 fallback **+ MES 공정 등록**」이 「**공정을 등록해서** 계획한다」는 뜻이면 순서만 강제되는 것이다. **문구가 두 가지로 읽힌다** → §I 등재하되 **해석 확인이 먼저**다 — §8-2.

### §5-4. ★ R12 Rev 스냅샷이 **그대로 착지해 있다**

```
work_order.operation_settings_snapshot  jsonb
-- [M] 생성 당시 라우팅 공정설정 스냅샷 (2-1 FR-WO-005):
--     기준정보 in-place 변경이 기존 지시에 소급되지 않도록 고정
```

**주석이 R12를 그대로 적었다.** 「모델이 앞섬」 사례다.

**화면 규칙**

1. **전개 시점에 스냅샷을 뜬다** — 서버가 채운다. 화면은 보내지 않는다
2. **전개 후 Routing이 개정돼도 기존 W/O는 안 바뀐다** — 화면은 「Rev 2 (전개 시점 고정)」로 표기
3. ⚠ **스냅샷의 jsonb 키 규약이 없다** — `audit_event`의 `before/after`와 같은 문제다(§I-5 · #68). **화면이 스냅샷을 읽어 보이려면 규약이 필요**하다 → §8-3

⚠ **`operation_settings_snapshot`은 `routing_operation`의 설정만 담는다** — **BOM 스냅샷은 없다**(§I-16 · `P-02-11`에서 확인). 러닝체인지가 여기 걸린다(§5-5).

### §5-5. 러닝체인지 분할 — W/O가 아니라 **생산LOT을 나눈다**

**02-S-B 구조 원칙**: 「**W/O 무분할 · 생산LOT만 BOM 스냅샷별 분할**」(R42) · 투입 Validation = 해당 LOT BOM 기준(R43)

**그런데 프로세스 S2 태스크 4는 「러닝체인지 대비 계획 **부품별 분할 생성**」이라고 한다.** 무엇을 나누는가가 두 문서에서 갈린다.

| 문서 | 무엇을 나누나 |
| --- | --- |
| S2 태스크 4 | 「계획 **부품별 분할 생성**」 — 계획? W/O? |
| 02-S-B · R42 | **「W/O 무분할 · 생산LOT만 분할」** |

**R42가 더 구체적이고 나중 확정이므로 R42를 따른다** — 이 화면은 **W/O를 나누지 않는다.**

⚠ **그런데 `work_order.parent_work_order_id`가 실재한다**(주석: 「분할 원본 지시 (FR-WO-013/032, BR-WO-005)」). **W/O 분할이 다른 이유로 쓰인다**는 뜻이다(수량 분할 등). **러닝체인지용이 아님을 화면이 구분**해야 한다 → §8-6.

**그리고 §I-16이 여기서 다시 걸린다** — 생산LOT별 BOM 스냅샷 자리가 없어 R43이 W/O BOM 기준으로 후퇴한다. **이 화면이 분할을 안 하므로 여기서는 영향이 없고, `W-02-04`·`P-02-11`가 진다.**

### §5-6. Routing 기본 Rev 플래그가 없다 — §I-7

유효 기간이 겹치는 Rev가 둘일 때 **어느 것을 쓸지 정할 수 없다**(§I-7 · #64 — `planning.bom`에는 `is_default`가 있는데 `planning.routing`에는 없다).

**화면 설계**: 후보가 둘 이상이면 **자동 선택하지 않고 사용자에게 고르게 한다** + 경고 표시.

```
⚠ 유효 기간이 겹치는 Routing Rev가 2건입니다. 사용할 개정을 고르세요. (#64)
```

**BOM은 `is_default`가 있으므로 자동 선택**한다 — **같은 화면에서 둘의 동작이 갈리는 것**을 문구로 설명한다.

| --- | --- |

## §9. 이 장에서 나온 공유 계약 후보

1. **프로세스가 말하지 않는 데이터 계층이 있으면 화면이 드러낸다** — 「1 P/O → N W/O」인데 실제는 `production_plan`이 낀 3단이다. **숨기면 「왜 W/O가 6개인가」를 설명할 수 없다.** 계층을 접어 두되 존재는 보인다 (§5-1)
2. **합계 제약이 DB에 없으면 등급을 나눠 화면이 진다** — 계획 합 vs P/O 수량은 초과=ⓑ경고(정책 테이블이 있다) · 미달=ⓒ표시만 · 0건=ⓐ차단. **A-3(합계 제약의 UI)과 A-9(등급)를 함께 적용**하는 첫 사례 (§5-2)
3. **같은 화면에서 두 마스터의 Rev 선택 동작이 갈린다** — BOM은 `is_default`가 있어 자동, Routing은 없어 수동(§I-7). **갈리는 이유를 문구가 설명**하지 않으면 사용자는 화면 결함으로 본다 (§5-6)
