# W-06-10 · 연계 동기화 현황·실패 재처리

> 작성일: 2026-08-03 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> I/F 3장의 셋째이자 **데이터 면이 가장 튼튼한 화면**이다. 앞의 둘(`W-06-09`·`W-06-12`)은 정의 테이블이 없었는데, **실행 로그는 완비돼 있다**(§3).

## §0. 요약

- **개요**: 관리웹에서 전산담당이 ERP-MES 연계 동기화 현황을 조회하고 실패 건을 재처리하는 조회·상세 화면이다(§1). 신뢰도는 미정(자동 파이프라인 무배지·E1 유형 목록 회신 대기)이나, `integration.integration_message`(outbox 패턴)가 완비돼 있어 화면의 본질이 「목록 조회」가 아니라 **「비동기 워커의 상태를 사람이 읽고 개입하는 창」**임이 데이터로 드러난다(§2·§3).
- **주요 데이터**: 조회 조건은 기간(필수)·상태·I/F·방향·대상·재시도 횟수이고, 표시 열은 상태·I/F·방향·대상·생성·다음 시도(`available_at`)·시도 횟수·보냄/완료·처리 중(`locked_by`·`locked_at`)·마지막 오류이며, 상세 패널에서 `payload`(jsonb) 전문과 시각 6종 타임라인을 본다(§4).
- **핵심 액션**: 조회·상세 보기·재처리(단건/선택 일괄)·즉시 시도(대기 건)·중단·폐기·내보내기·알람 설정 보기(이동만, 규칙 소관은 `W-CO-03`)이며, 재처리는 `message_key` UNIQUE로 중복이 아님을 보장하고 `locked_by`(워커 리스) 상태에서는 버튼이 비활성된다(§5).

## §3. 데이터 면이 말해 주는 것 — 이 화면은 「워커를 들여다보는 창」이다

`integration_message`의 컬럼 구성이 **처리 방식을 이미 정하고 있다**(실측 해석).

| 컬럼 | 무엇을 뜻하나 | 화면에 어떻게 나타나야 하나 |
| --- | --- | --- |
| `message_key` UNIQUE | **멱등 키** — 같은 키 재전송은 서버가 흡수 | 재처리가 **중복 전송이 아님**을 사용자에게 보장 |
| `available_at` | **다음 시도 예정 시각**(백오프) | 「대기 중」이 아니라 **「HH:MM에 자동 재시도」**로 보인다 |
| `retry_count` | 시도 횟수 · **상한이 DB에 없다** | 상한은 워커·화면 책임 → §8-2 |
| `locked_at` · `locked_by` | **워커가 잡고 있는 중**(리스) | **이 상태에서는 수동 재처리 버튼을 비활성**해야 한다 → §5-4 |
| `sent_at` / `completed_at` | 보냄 / 상대가 받아 완료됨 — **두 시점이 다르다** | 「보냈는데 완료 안 됨」이 **별도 상태**로 보여야 한다 |
| `last_error_message` | 마지막 실패 사유 | 목록에 요약, 상세에 전문 |
| `payload jsonb` | 실제 전송 내용 | 진단에 필요하나 **대외비 노출 위험** → §8-4 |

**즉 이 화면의 본질은 「목록 조회」가 아니라 「비동기 워커의 상태를 사람이 읽고 개입하는 창」**이다. C-1(오프라인 outbox 규약)이 POP·모바일에서 세운 것과 **같은 패턴이 서버 측에 있는 것**이며, 규약을 재사용할 수 있다 → §9-1.

## §4. 필드 — 조회 조건과 표시 열

입력 필드가 없다(조회 + 재처리 액션만). `W-06-11`과 같은 형태다.

### §4-A. 조회 조건

| 조건 | 출처 컬럼 | 비고 |
| --- | --- | --- |
| **기간** | `created_at` | **필수** — 로그성 조회의 공통 규약(`W-06-11` §9-4) |
| 상태 | `status_code` | 공통코드 — **값 목록 미정 §8-3** · 최소 구분: 대기 / 처리중 / 완료 / 실패 |
| I/F | `interface_code` | ⚠ `W-06-09`의 정의 테이블이 없어 **선택 목록을 만들 수 없다** — 로그에 실제 나타난 값을 `DISTINCT`로 뽑는다 `[추정]` → §8-1 |
| 방향 | `direction_code` | 수신 / 송신 |
| 대상 | `target_type_code` · `target_id` | ⚠ **FK가 아니다** — 표시명 해석은 화면 책임(`W-06-11` §8-2와 **같은 결손**) |
| 재시도 횟수 | `retry_count` | 「N회 이상」 필터 — **반복 실패 건을 찾는 주 경로** |

### §4-B. 표시 열

| 열 | 출처 컬럼 | 표시 규칙 |
| --- | --- | --- |
| 상태 | `status_code` | `Chip` — G-1 상태 토큰(실패=error · 대기=info · 완료=success · 처리중=warning) |
| I/F · 방향 | `interface_code` · `direction_code` | |
| 대상 | `target_type_code` + `target_id` | 해석 실패 시 **코드+ID 그대로**(행을 숨기지 않는다 — `W-06-11` §6) |
| 생성 | `created_at` | |
| **다음 시도** | `available_at` | 미래면 「HH:MM 자동 재시도」 · 과거인데 미처리면 **「지연」 강조** |
| 시도 | `retry_count` | 임계 초과 시 강조 §8-2 |
| 보냄 / 완료 | `sent_at` / `completed_at` | **둘 다 보인다** — 「보냈으나 미완료」 식별 |
| 처리 중 | `locked_by` · `locked_at` | 값이 있으면 **자물쇠 표식** + 잡은 시각 |
| 마지막 오류 | `last_error_message` | 1행 요약(전문은 상세) |

### §4-C. 상세 패널

`payload`(jsonb) · `last_error_message` 전문 · `message_key` · 시각 6종 타임라인.

**⚠ `payload` 표시는 권한을 따로 본다** → §8-4.

## §5. 액션·상태

### §5-1. 액션

| 액션 | 활성 조건 | 비고 |
| --- | --- | --- |
| 조회 | **기간 지정됨** | 로그 규약 |
| 상세 보기 | 행 선택 | |
| **재처리(단건)** | `status_code`=실패 **AND `locked_by` IS NULL** | 같은 `message_key`로 재시도 — **중복 아님을 문구로 보장** §5-4 |
| **재처리(선택 일괄)** | 위 조건 만족 행 1건 이상 선택 | **부분 실패 허용** — 전체 롤백 없음(C-2 원리) |
| 즉시 시도(대기 건) | `status_code`=대기 **AND** `available_at` 미래 | 백오프를 앞당긴다 `[추정]` — 검증: 운영 요구 확인 |
| **중단·폐기** | 실패 건 | ⚠ **폐기하면 그 데이터는 ERP에 영원히 안 간다** — 결과를 문장으로 보인 뒤 확인 §8-5 |
| 내보내기 | 결과 1건 이상 | 원인 분석·고객 공유용 `[추정]` |
| 알람 설정 보기 | 항상 | **알람 규칙 소관은 `W-CO-03`**(알림센터) — 이동만 §8-3 |

### §5-2. 화면 상태

`초기(조회 전 — EmptyState)` → `조회 중(Skeleton)` → `결과 있음` / `결과 없음(EmptyState)` / `조회 실패(AlertBanner)` → `재처리 중(해당 행만 진행 표시)` → `재처리 결과(Toast + 실패분 목록)`

### §5-3. 낙관적 잠금 — **해당 없음, 대신 리스 충돌**

`integration_message`에 `version_no`가 **없다**(실측). 대신 `locked_at`·`locked_by`가 **워커 리스**다.

**충돌 형태가 B-1과 다르다**: 「다른 사용자가 먼저 수정했다」가 아니라 **「워커가 이미 처리 중이다」**. 문구를 나눠야 한다 — `W-06-05` §9-1이 제기한 「충돌 원인 구분」의 **세 번째 형태**다(사용자 / ERP 배치 / **워커 리스**).

### §5-4. 재처리의 안전 규약

1. **중복 걱정을 화면이 해소한다** — `message_key`가 UNIQUE이므로 재처리는 새 메시지를 만들지 않는다. 「**같은 건을 다시 보냅니다. 중복 전송되지 않습니다.**」를 확인 문구에 넣는다.
2. **처리 중(`locked_by` 있음)이면 버튼 비활성 + 사유** — 「워커가 처리 중입니다(HH:MM 시작)」.
3. **리스가 오래된 경우**(워커가 죽어 락이 남음)는 **화면이 임의로 풀지 않는다** — 운영 조치 사항으로 안내만 → §8-2.

## §6. 예외

| 상황 | 처리 |
| --- | --- |
| 권한 없음 | 전산담당 전용 — 진입 차단 + 배너 |
| 기간 미지정 | 조회 버튼 비활성 + 사유 |
| 결과 과다 | 페이지네이션 + 조건 좁히기 안내 |
| **재처리 중 리스 충돌** | 서버가 거부 → 해당 행만 「처리 중으로 바뀌었습니다」 갱신. **오류가 아니다** |
| **일괄 재처리 부분 실패** | **전체 롤백 없음** — 성공/실패 건수 + 실패 행 목록(C-2) |

| `payload` 조회 권한 없음 | 상세에서 payload 구획만 **비활성 + 사유** §8-4 |
| 오프라인 | **해당 없음** — 관리웹은 온라인 전제(결정 17) |

| **4** | **`payload` 노출 범위** | 설계 결정 | 진단에는 필요하나 **거래처·단가·수량 등 대외비가 그대로 들어 있다.** 권한을 따로 둘지, 마스킹할지, 전산담당 전용으로 충분한지 결정 필요. ⚠ **내보내기 기능과 함께 판단**해야 한다(파일로 나가면 통제가 끝난다) |
| 5 | **「중단·폐기」를 제공할 것인가** | 설계 결정 | 폐기하면 해당 데이터는 ERP에 영구 미반영이다. 제공하지 않으면 잘못된 메시지가 영원히 재시도된다. **둘 다 위험** — 결정권자 확인 |
| 6 | **Temp Table 적재 오류(WF06 S7 Exception ④)의 가시성** | 확인 필요 | `integration_message`는 **MES 측 outbox**다. **ERP↔Temp Table 구간의 실패**가 여기 잡히는지 불명 — DB 중계 방식(QA #18)의 실패는 outbox 이전 단계일 수 있다. 인벤토리 근거란의 「**Temp Table**」이 이 화면 범위임을 전제하는데 **데이터 면이 이를 뒷받침하지 않는다** |
| 7 | **신뢰도 「미정」의 근거가 이 장에서 바뀐다** | 정합 | 인벤토리 v1.4는 「자동 파이프라인 무배지·E1 대기」로 **미정** 판정했다. 그런데 **데이터 면은 가장 튼튼하다**(outbox 완비). 신뢰도 기준이 **도식 앵커 유무**라 등급은 유지되나(인벤토리 v1.4 원칙), **「데이터 면 충실도」라는 다른 축이 있음**을 기록한다 → §9-3 |

## §9. 이 장에서 나온 공유 계약 후보

1. **outbox 규약(C-1)은 서버 측에도 그대로 있다 — 규약을 한 벌로 쓴다.**
   C-1이 POP·모바일 오프라인을 위해 세운 것(**클라이언트 생성 멱등 키 · 즉시 성공 피드백 · 미동기 건수 상시 표시 · 같은 키로 재전송**)이 `integration_message`에 **그대로 구현돼 있다**(`message_key` UNIQUE · `available_at` 백오프 · `retry_count` · `locked_by` 리스). **같은 개념을 두 이름으로 부르지 않는다** — 용어·상태 어휘·재시도 표현을 한 벌로 정의하고, 세 셸과 서버 화면이 같은 말을 쓴다.
2. **저장 충돌의 세 번째 원인 — 워커 리스.**
   `W-06-05` §9-1이 「사용자 / ERP 재동기화 배치」 둘을 구분하자고 했는데, 이 장에서 **「워커가 처리 중」**이 추가됐다. `version_no`가 없는 테이블에서는 **리스 충돌이 낙관적 잠금을 대신**한다. **API 파급 항목에 세 원인을 모두 명시**한다(현재 API 파급 5건 → 이 건 포함).
3. **신뢰도에 「데이터 면 충실도」 축을 병기한다.**
   인벤토리의 신뢰도(확정/추정/미정)는 **도식 앵커 유무**로 매긴다 — 정당한 기준이고 바꾸지 않는다. 다만 상세 스펙 단계에서는 **다른 축이 실무를 지배**한다: 이 화면은 신뢰도 「미정」인데 데이터 면이 가장 튼튼해 스펙이 잘 써졌고, `W-06-08`(예비품)은 「추정」인데 **데이터 면이 통째로 비어 필드표를 못 썼다.** **데이터 면 충실도로 다시 정렬**해야 착수 후 멈추는 일이 없다.
