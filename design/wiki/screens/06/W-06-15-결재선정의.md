# W-06-15 · 결재선 정의

> 작성일: 2026-08-07 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ⭐ **승인 워크플로우 전체의 시작점이다.** 결재선이 비면 **상신 자체가 거부**되므로 `W-CO-09` 결재함은 물론 `W-01-02`·`06`·`11`·`12` 넷이 전부 이 화면에 막힌다.
> ⛔ **이 장이 §J-3의 미해결을 닫는다** — 「승인자를 요청 시점에 사람으로 확정한다」가 `DEPARTMENT`·`ROLE` 결재선에서 **모델상 성립하지 않음**을 실측으로 확인하고, **1차는 `USER` 하나만 연다**(사용자 확정 2026-08-07).

## §0. 요약

- **개요**: 관리웹에서 시스템 관리자·운영관리자가 결재선(승인 유형·사업부별 결재 절차)을 정의하는 설정·마스터 화면. 결재선이 비어 있거나 꺼져 있으면 해당 유형의 상신 자체가 막히는 **승인 워크플로우의 시작점**이며, 결재선 **정의**만 다루고 진행 중인 요청의 조회·결재는 `W-CO-09` 소관이다.
- **주요 데이터**: 결재선 `app.approval_route`(승인 유형·사업부·값 구간·사용 여부) + 결재 단계 `app.approval_route_step`(순서·승인자 구분·승인자). 승인자 구분은 **1차에 `USER`만 열고**, `ROLE`·`DEPARTMENT`는 사람을 좁힐 데이터가 모델에 없어 비활성으로 둔다.
- **핵심 액션**: 결재선 추가/수정, 사용/사용 안 함(끄면 해당 유형 상신 차단을 미리 경고), 결재 단계 추가/삭제/순서 재배치, 승인자(사용자) 선택, 저장(결재선 단위 한 트랜잭션).

## §5. 액션·상태

### §5-1. ⭐ 이 화면이 §J-3의 미해결을 닫는다

§J-3은 v0.5부터 「요청 시점에 승인자를 **사람으로 확정**한다」였고, 그 근거는 **「데이터가 사람만 받는다」**였다.

```
app.approval_step.approver_id   bigint NOT NULL REFERENCES app.app_user
```

그런데 #72 회신(2026-08-04)은 **「담당부서 관리자 · 관리자의 권한 설정으로 처리」**였다. 「권한 설정으로」는 `approver_type_code`가 `ROLE` 또는 `DEPARTMENT`라는 뜻이다. **둘이 부딪쳤다.**

**2026-08-07 확정 — 결론(`USER`만 연다)을 2026-08-30 사용자가 재확인했다.** 상신 시 규칙으로 한 사람을 골라 `approver_id`에 넣는다. ⭐ 재확인 근거는 개발 비용·기존 화면 변경 최소화 — `ROLE`·`DEPARTMENT`는 §5-2처럼 비활성 선택지로 남긴다. 공유계약 J-3 참조. **재검토 종결.**

### §5-2. ⛔ 그런데 「한 사람을 고를」 입력이 모델에 없다 — **`USER`만 연다**

①을 택했으므로 「부서에 관리자가 여럿일 때 누구를 고르는가」의 **입력 데이터**를 찾아야 한다. **전수 실측했다.**

| 갈래 | 사람을 좁힐 수 있나 | 실측 |
| :-: | --- | --- |
| `DEPARTMENT` | ⛔ **불가** | **`mdm.department`에 관리자 컬럼이 0건**(`manager`·`is_manager`·`head_` 전수 검색). `app_user.department_id`로 **부서원 전원**은 찾지만 그중 누가 관리자인지 가릴 값이 없다 |
| `ROLE` | ⛔ **불가** | `app.user_role`로 보유자는 찾는다. 그러나 **`app.role`에 부서·사업부 축이 없다** — 「품질부 관리자」가 아니라 **「관리자 역할 전원(전사)」**이 된다. 좁혀도 여럿이면 같은 문제가 남는다 |
| **`USER`** | ✅ **가능** | 결재선이 사람을 직접 가리킨다. `approval_step.approver_id`에 그대로 넣는다 |

> **판정 — 1차 결재선은 `USER` 하나만 연다**(사용자 확정 2026-08-07). 나머지 둘은 **선택지를 지우지 않고 비활성**으로 두고 사유를 보인다(G-10).

**「고정이 아니라 권한 설정으로」라는 회신 취지는 살아 있다.** 고정된 것은 **코드**가 아니라 **이 화면의 데이터**이고, 운영자가 여기서 바꾸면 다음 상신부터 따라간다.

⚠ **대가는 하나다** — **부서 개편·인사 이동 때 결재선을 사람이 손으로 고쳐야 한다.** 화면이 그것을 숨기지 않는다(§6).

### §5-3. ⛔ 결재선 중복을 **DB가 막지 않는다** — 화면이 막는다

```
app.approval_route     UNIQUE 제약 없음 · INDEX 0건 (실측)
```

같은 `approval_type_code` + 같은 `business_unit_id`로 **활성 결재선을 몇 개든** 만들 수 있다. 그러면 상신 시 서버가 **어느 것을 고를지 정해지지 않는다** — 계약에도 규칙을 쓸 수 없다.

**1차는 값 구간을 쓰지 않으므로**(§5-4) 유일해야 하는 조합이 명확하다:

```
(approval_type_code, business_unit_id) 당 활성 결재선 1건
```

**화면이 강제한다.**

| 상황 | 처리 |
| --- | --- |
| 같은 유형·같은 사업부로 새 결재선 추가 | ⛔ 저장 거부 — 「이미 결재선이 있습니다. 기존 것을 수정하세요」 + **해당 행으로 이동** |
| 사업부 지정본과 전 사업부 공통본이 함께 활성 | ✅ 허용 — **구체적인 것이 이긴다**(사업부 지정 > 전 사업부) |

⚠ **「구체적인 것이 이긴다」는 우리가 정한 규칙이고 DB에는 없다.** 서버가 같은 규칙으로 고르지 않으면 화면 설명과 실제가 갈린다 → **계약이 명시한다**(§9-1) · **유일 제약 신설은 이슈**(§8-1).

### §5-4. 값 구간은 1차에 쓰지 않는다 — **비워 두면 전 구간이다**

```
min_value / max_value   numeric(20,6)   둘 다 nullable
```

**2026-08-07 사용자 확정** — 1차에서는 구간으로 결재선을 가르지 않는다. 근거 둘:

1. **비교할 값이 `approval_request`에 없다** — 수량 컬럼이 0건이다(실측). 대상 문서를 열어 봐야 알 수 있고, 대상 유형마다 「무엇이 그 값인가」가 다르다
2. **금액 결재선은 성립하지 않는다** — `price`·`amount`·`cost`·`unit_price`·`currency` 컬럼이 물리 모델에 **0건**(실측). **값의 성격은 수량이다**

**입력란은 둘 다 둔다.** 지우면 나중에 열 때 화면이 바뀌고, 무엇보다 **컬럼이 실재한다**. 선택 입력이고 비우면 전 구간이다.

⚠ **한쪽만 채우는 것도 허용된다** — `ck_approval_route_range`는 **둘 다 있을 때만** `max >= min`을 본다.

### §5-5. 단계 저장 — **결재선 단위 한 트랜잭션**

`approval_route_step`에 `version_no`가 없다(B-6 — 부여·회수 형). 그리고 `uq_approval_route_step UNIQUE(route, step_no)`가 있다.

**행마다 저장하면 순서를 바꾸는 중간 상태가 유일 제약을 위반한다** — 1↔2 교환이 잠깐 `step_no`를 겹치게 한다. **A-5 그대로다.**

| | |
| --- | --- |
| 클라이언트 | 결재선 하나의 **단계 전체**를 최종 순서로 모아 보낸다 |
| 서버 | 한 트랜잭션에서 차분 적용(삭제 → 삽입) |
| 충돌 판정 | **`approval_route.version_no`로 한다** — 단계 표에 토큰이 없으므로 **마스터의 토큰을 대표로** 쓴다 |

`W-CO-06` §5-3이 올린 계약 후보(부여 테이블은 마스터의 토큰으로 판정)의 **두 번째 사용처**다.

### §5-6. ⛔ 결재선을 비우거나 끄면 **상신이 막힌다** — 이 화면이 그것을 만든다

01 계약이 이미 이렇게 썼다:

> `POST /logistics/goods-issues/{id}:request-approval` — **결재선이 없으면 400이다.** 상신할 곳이 없는 품의를 만들지 않는다.

**즉 이 화면의 `is_active` 해제 한 번이 다른 화면의 버튼을 막는다.** 저장은 막지 않되 **무엇이 막히는지 먼저 보인다.**

```
⚠ 「폐기 품의」 결재선을 끕니다
   W-01-06 폐기 품의·기타 출고 화면에서 상신이 막힙니다.
   진행 중인 요청 3건은 그대로 진행됩니다(§5-7).
   [ 취소 ]  [ 끄기 ]
```

G-3(비활성 사유는 「어떻게 풀 것인가」)의 역방향이고 `W-CO-06` §5-2와 같은 형태다 — **「지금 저장하면 저쪽 화면이 막힌다」**를 미리 알린다.

⚠ **막히는 화면 목록을 화면이 지어내지 않는다** — 승인 유형 ↔ 업무 화면의 대응은 **계약이 내려 준다**(§9-2).

### §5-7. 결재선을 바꿔도 **진행 중인 요청은 바뀌지 않는다**

`approval_step`은 **상신 시점에 전개**되고 **기록 전용**이다(J-6 — 되돌릴 수 없다). 결재선을 나중에 고쳐도 **이미 만들어진 단계는 그대로**다.

**규칙**: 결재선 편집 화면에 **「진행 중 N건」을 표시**하고, 그것들이 **옛 결재선으로 끝난다**는 것을 적는다. 이 문장이 없으면 운영자는 「고쳤으니 지금 것부터 바뀐다」고 믿는다.

### §5-8. ⛔ 승인자가 부재하면 **결재가 멈춘다** — 화면이 말한다

**2026-08-07 사용자 확정 — 1차 범위로 감수한다.** 대리 결재·위임은 범위 밖이다.

| 우회 | 왜 안 되나 |
| --- | --- |
| 대리 결재 | **대리 컬럼이 없다**(실측) |
| 승인자 교체 | `approval_step`이 **기록 전용**(`created_at`만 · `version_no` 없음) — 감사상 문제가 된다 |
| 후보 전원에게 단계 생성 | `uq_approval_step UNIQUE(request_id, step_no)` — 같은 단계에 둘을 못 넣는다 |

**A-11을 적용한다** — 결재선 편집 구획에 상시 문구를 둔다.

```
ⓘ 승인자가 휴가·퇴사로 결재할 수 없으면 그 요청은 멈춥니다.
   결재선을 고쳐도 진행 중인 요청에는 반영되지 않습니다(§5-7).
   반려 후 다시 상신하는 것이 현재의 유일한 경로입니다.
```

⚠ **성공 토스트에 붙이지 않는다**(A-11 v0.9 보강) — 상시 자리에 둔다.

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **§J-3을 다시 쓴다 — 「상신 시 규칙으로 사람을 고른다」가 아니라 「1차 결재선은 사람을 직접 가리킨다」** — 「규칙으로 고른다」는 **고를 입력이 있어야** 성립하는데 `mdm.department`에 관리자 컬럼이 0건이고 `app.role`에 부서 축이 없다(실측). ⛔ **J-3의 미해결 표시를 지우고 확정으로 바꾼다** — `USER`만 열고 나머지 둘은 모델이 받쳐 줄 때 연다 (§5-1·§5-2)
2. **결재선 선택 규칙을 계약이 명시한다 — 「구체적인 것이 이긴다」** — `business_unit_id`가 nullable이라 지정본과 전 사업부 공통본이 함께 활성일 수 있는데 **DB에 우선순위가 없다.** 화면 설명과 서버 동작이 갈리지 않으려면 **계약이 정본**이어야 한다. 아울러 **승인 유형 ↔ 업무 화면 대응**도 계약이 내려 준다 — 화면이 「무엇이 막히는가」를 지어내지 않기 위해서다 (§5-3·§5-6)
3. **결재선을 바꿔도 진행 중인 요청은 옛 결재선으로 끝난다 — 화면이 그것을 말한다** — `approval_step`이 상신 시점 전개 + 기록 전용이라 소급이 없다. **J-6(결재는 되돌릴 수 없다)의 정의 쪽 판**이다. 편집 화면이 「진행 중 N건」을 보이지 않으면 운영자는 소급된다고 믿는다 (§5-7)
4. **부여·회수 테이블에 유일 제약이 있으면 마스터 단위 한 트랜잭션이 필수다** — `W-CO-06` §5-3이 「부여 테이블은 마스터의 토큰으로 충돌을 판정한다」를 올렸는데, `approval_route_step`은 거기에 **`uq(route, step_no)`가 더해져** 행 단위 저장이 **중간 상태에서 제약을 위반**한다. A-5(순서 재배치)와 B-6(부여 테이블)이 겹치는 자리다 — **두 번째 사용처** (§5-5)
