# W-06-14 · 적치 규칙 마스터

> 작성일: 2026-08-07 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ⚠ **이 표가 비면 통제가 성립하지 않는다.** `M-01-05` §5-2-1이 **권장 위치를 차단 기준으로 확정**(2026-08-06)하면서 파급이 「권장이 안 뜬다」에서 **「아무 데나 놓아도 통과한다」**로 올라갔다.

## §0. 요약

- **개요**: 관리웹 화면. 물류담당·전산담당이 창고·품목·위치 단위의 적치 규칙(`logistics.putaway_rule`)을 등록·관리하는 설정·마스터 유형 화면이다. `M-01-05`가 권장 위치를 차단 기준으로 확정해, 이 표가 비면 해당 품목은 현장에서 위치 검증 없이 통과한다(§5-1).
- **주요 데이터**: `logistics.putaway_rule`(품목·창고·위치·용량·용량단위·우선순위·비고·사용여부 — DB **유일 제약 0건**) + 파생 표시(현재 적재·위치 자체 용량·중복 경고, §4-B). 우선순위 방향(작을수록 먼저)과 중복 판정은 DB가 아니라 화면·계약이 정한다(§5-2).
- **핵심 액션**: 규칙 추가·수정, 사용/사용 안 함 전환(물리 삭제 없음 — B-4), 창고·품목·사용 여부 필터 조회, 규칙 없는 품목 보기(§5-1). 계약은 이미 3경로가 서 있고 대조 결과 어긋남 0건이며, `uncovered-items` 조회·`:activate` 재사용 경로 2건만 신설 요청했다(§5-6).

## §5. 액션·상태

### §5-1. ⚠ 이 표가 비면 **통제가 성립하지 않는다**

`M-01-05` §5-2-1이 확정한 세 갈래를 그대로 옮긴다.

| 창고 상태 | 품목 규칙 | 현장(`M-01-05`) 동작 |
| --- | --- | --- |
| 위치 관리 함 | **권장 있음** | ⛔ **그 위치만 허용** — 다른 위치 스캔은 차단 |
| 위치 관리 함 | **권장 없음** | ⚠ 확인 후 통과 — 「관리 위치가 없는 품목입니다」 |
| 위치 관리 안 함 | — | 위치 스캔 자체가 없다 |

**즉 규칙을 등록하지 않으면 둘째 줄로 떨어지고, 그것은 「아무 데나 놓아도 통과」다.** 화면이 그것을 말한다.

```
ⓘ 이 창고에 적치 규칙이 없는 품목은 현장에서 위치 검증 없이 통과합니다.
   (원자재창고 · 규칙 없는 품목 34건)
```

⚠ **「규칙 없는 품목 34건」은 이 화면이 계산할 수 있다** — 그 창고에 입고 이력이 있는데 규칙이 없는 품목이다. **비어 있는 것을 보이지 않으면 아무도 채우지 않는다.**

### §5-2. ⛔ 중복을 **DB가 막지 않는다** — `priority_no`의 방향도 정의되지 않았다

```
logistics.putaway_rule    UNIQUE 제약 0건 (실측 — PK 외에 없다)
priority_no  integer NOT NULL DEFAULT 100    ← 크고 작음의 뜻이 없다
```

같은 (품목, 창고, 위치)로 **활성 규칙을 몇 개든** 만들 수 있고, 우선순위까지 같으면 **어느 규칙이 권장을 내는지 정해지지 않는다.** `putaway_task.applied_putaway_rule_id`가 「어느 규칙이 적용됐는가」를 남기게 돼 있는데, **그 값이 실행할 때마다 달라질 수 있다는 뜻**이다.

**두 가지를 화면이 정한다.**

| | 판정 |
| --- | --- |
| **방향** | **작을수록 먼저**(`priority_no` 오름차순). 근거 = `DEFAULT 100`이 **중간값**이라 나중 규칙을 위아래로 끼울 여지를 둔 형태다. `putaway_task.priority_no`도 같은 기본값이다 |
| **중복** | 같은 (품목, 창고, 위치, 우선순위)로 **활성 규칙 2건 이상이면 저장 거부** |

⚠ **둘 다 우리가 정한 것이고 DB에는 없다.** 서버가 다르게 고르면 화면 설명과 실제가 갈린다 → **계약이 명시**(§9-1) · **부분 유일 인덱스 신설은 이슈**(§8-1).

> `W-06-15` §5-3과 **똑같은 형태**다 — 마스터에 유일 제약이 없어 선택이 정해지지 않는 것이 **두 번째**다.

### §5-3. 창고의 관리수준이 위치 입력을 가른다

`warehouse.management_level_code`(「창고·구역·랙·셀 관리수준」)가 **`W-06-07`의 편집 대상**이고, 이 화면은 그 값을 **읽기만** 한다.

| 관리수준 | 위치 입력 |
| --- | --- |
| 위치까지 관리 | ✅ 위치 선택 가능. 비우면 **창고 수준 규칙** |
| 창고 단위만 | ⛔ **위치 입력 비활성 + 사유** — 「이 창고는 위치를 관리하지 않습니다(`W-06-07`에서 설정)」 |

**G-10 적용** — 잠금 사유와 **어디서 푸는지**를 함께 보인다.

⚠ **`management_level_code`의 값 목록이 미정이다**(`W-06-07` §8-2 · `W-06-06` 소관). 확정 전까지는 **모든 창고에서 위치 입력을 열어 둔다** — 막을 근거가 없다.

### §5-4. 「용량」은 현재 적재와 나란히 놓아야 뜻이 생긴다

`inventory_balance.location_id`가 **NOT NULL**이다(실측). 위치별 현재 적재를 **정확히** 낼 수 있다.

```
inventory_balance   warehouse_id · location_id · item_id · on_hand_qty · uom_id
```

| 표시 | 계산 |
| --- | --- |
| 현재 적재 | 그 (창고, 위치, 품목)의 `on_hand_qty` 합 |
| 사용률 | 현재 ÷ `capacity_qty` — **100% 이상이면 ⚠** |
| 창고 수준 규칙 | 그 창고의 해당 품목 전체 합 |

⛔ **단위가 다를 수 있다** — `putaway_rule.uom_id`와 `inventory_balance.uom_id`가 별개 컬럼이다. 다르면 `mdm.item_uom_conversion`으로 환산해야 하는데 **환산 정의가 없는 조합이 있을 수 있다.**

**계산하지 않고 그대로 보인다** — 환산할 수 없으면 **사용률을 계산하지 않고 두 값을 단위와 함께 보인다.** 근거는 **억지로 맞춘 숫자가 사람을 속인다**는 것이다. ⚠ **구판 A-11 인용을 정정한다** — v4.6 이 「물러난 수준을 명시한다」를 「확정대로 반영하고 모델 결손은 통지한다」로 바꿨다. 데이터 모델은 설계 결정을 앞설 수 없다.

```
용량 500 KG · 현재 1,200 EA   ⚠ 단위가 달라 사용률을 계산할 수 없습니다
```

### §5-5. ⛔ 용량이 **두 곳에 있다** — 어느 것이 이기는지 정하지 않았다

```
putaway_rule.capacity_qty   NOT NULL CHECK > 0     품목별 · 이 화면
mdm.location.capacity_qty   nullable               위치 자체 · W-06-07
```

**규칙 용량이 위치 자체 용량보다 클 수 있다.** 「A-01-03에 수지A를 500 KG까지」인데 그 위치 자체가 300 KG이면 모순이다.

**막지 않고 경고한다.**

| | 왜 |
| --- | --- |
| 막지 않는다 | `location.capacity_qty`가 **nullable**이라 많은 위치가 비어 있을 것이고, 막으면 위치 용량부터 전부 채워야 규칙을 만들 수 있다 |
| 경고한다 | ⚠ 「이 위치 자체 용량은 300 KG입니다」 — 운영자가 의도한 것인지 확인한다 |

⚠ **둘 중 무엇이 적치 판정에 쓰이는지는 우리가 정하지 않는다** — `M-01-05`는 **권장 위치의 일치 여부**만 보고 용량은 보지 않는다(실측 — §5-2-1의 세 갈래에 용량이 없다). **용량은 지금 어디에서도 판정에 쓰이지 않는다.** → §8-3.

### §5-6. ⚠ 계약이 먼저 쓰였다 — 대조 결과 **어긋남 0건**

`mdm-기준정보.json`이 이미 3경로를 갖고 있다(경로 76 중 3).

| 계약 | 이 화면 | 판정 |
| --- | --- | :-: |
| `GET /logistics/putaway-rules` | 목록·필터(창고·품목·사용) | ✅ |
| `POST /logistics/putaway-rules` | 규칙 추가 | ✅ |
| `GET·PUT /logistics/putaway-rules/{id}` | 상세·수정 | ✅ |
| `POST …:deactivate` | 사용 안 함 | ✅ — **B-4**(삭제 대신 끈다) |

**화면이 계약보다 더 요구하는 것 — ⛔ 초안은 둘이라 적었으나 실측하니 하나였다.**

| 요구 | 계약 | |
| --- | --- | :-: |
| **현재 적재** | ✅ **01 계약이 이미 갖고 있다** — `GET /inventory/balances?warehouseId=&locationId=&itemId=&groupBy=LOCATION` | 결손 아님 |
| **규칙 없는 품목 수** | ⛔ **없었다** → `GET /logistics/putaway-rules/uncovered-items` **신설** | 결손 |

> ⭐ **「계약에 없다」고 적기 전에 다른 파일을 봐야 했다.** 이 화면은 **두 계약을 부른다** — 마스터는 `mdm-기준정보.json`, 재고는 `logistics-01자재창고.json`이다. 화면 하나가 한 계약만 부른다고 가정하면 있는 것을 없다고 적게 된다.

**⛔ 재사용 경로도 없었다** — `:deactivate`만 있고 `:activate`가 없었다. 이 화면은 목록에 「사용 안 함」 행을 보이고 **다시 켜는 것이 정상 운용**이다 → **`POST …:activate` 신설**. 다른 mdm 마스터에는 두지 않는다 — 그 화면들이 요구하지 않았다(`W-06-07` 액션은 「사용 중지」뿐).

### §7-1. ⛔ **정정 — `Progress`가 있고, 이 화면에 딱 맞는 prop 까지 있다** *(2026-08-07 발행 직전 실물 확인)*

> **초안은 「`Progress`·`Gauge` 계열을 찾지 못했다」였다. 틀렸다** — 고정 커밋 `a554d11` 설치본에 **둘 다 있다**(`src/components/Progress/Progress.tsx` · `Gauge.tsx`).

```ts
export interface ProgressProps {
  value?: number
  showValue?: boolean          // 트랙 끝에 "NN%"
  thresholds?: ThresholdStop[] // { upTo, tone } — 구간마다 색이 바뀐다
  tone?: ProgressTone
}
```

**`thresholds`가 이 화면이 필요한 바로 그것이다** — 사용률 100% 초과를 **경고 톤으로 자동 전환**한다. 화면이 조건 분기를 쓰지 않는다.

| 이 화면이 필요한 것 | `Progress` |
| --- | --- |
| 용량 대비 현재 | ✅ `value` + `min`/`max` |
| 「320 KG (64%)」 | ✅ `showValue`(%) + 수량은 옆 열에 |
| **100% 초과 강조** | ✅ **`thresholds`** — 색 전환이 컴포넌트 안에 있다 |
| 단위가 달라 계산 불가(§5-4) | ⚠ **막대를 그리지 않고 두 값만 텍스트로** — A-11 그대로 |

**판정을 `c` → `a`로 뒤집는다.**

⚠ **결론(「막대가 필요 없다」)까지 틀린 것은 아니지만 근거가 틀렸다** — 「없어서 안 쓴다」와 「있는데 이 값엔 과하다」는 다른 판단이고, **뒤엣것이면 쓰는 편이 낫다.** `thresholds`가 조건 분기를 없애 준다.

### §7-2. ⚠ 원인 — **판정 절차 ①을 건너뛰었다**

`ds-gap.md`의 절차는 **① DS 인벤토리 전수 조회 → ② 조합 시도 → ③ 갭 판정**이다. 이 장은 ①을 하지 않고 **기억으로 「없다」고 적었다.** `W-CO-09`에서도 같은 일이 났다(그쪽은 `Stepper`·`Badge` 2건).

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **마스터에 유일 제약이 없으면 「어느 행이 이기는가」를 계약이 정한다** — `putaway_rule`(품목·창고·위치·우선순위)과 `approval_route`(유형·사업부) **둘 다 UNIQUE 제약이 0건**이고, 둘 다 **런타임에 한 행을 골라야** 한다. 화면이 중복을 막는 것만으로는 API 직접 호출로 뚫리고, **`priority_no`의 방향처럼 데이터에 뜻이 없는 값**은 계약이 정본이어야 한다 — **두 번째 사용처**(`W-06-15` §9-2) (§5-2)
2. **화면이 계약보다 더 요구하면 그것이 계약 결손이다 — 단, 「없다」고 적기 전에 다른 계약 파일을 본다** — 「규칙 없는 품목 수」는 실제 결손이었고 `uncovered-items`로 신설했다. 그러나 **「현재 적재」는 01 계약이 이미 갖고 있었다** — ⭐ **화면 하나가 여러 계약 파일을 부른다**(마스터는 `mdm`, 재고는 `logistics`). **한 계약만 보고 결손을 판정하면 있는 것을 없다고 적는다.** 아울러 **재사용 경로 부재**(`:activate`)도 이 화면이 드러냈다 (§5-6)
3. **단위가 다르면 환산해 보이지 말고 두 값을 그대로 보인다** — `putaway_rule.uom_id`와 `inventory_balance.uom_id`가 별개라 환산 정의가 없는 조합이 나올 수 있다. **억지로 맞춘 사용률은 틀린 숫자**이고, 운영자는 그것을 근거로 용량을 고친다. A-11의 수치 판이다 (§5-4)
4. **비어 있음을 보이는 것이 마스터 화면의 일이다** — 규칙이 없는 품목은 현장에서 **검증 없이 통과**하는데, 마스터 화면이 「등록된 것」만 보이면 **비어 있다는 사실이 아무 데서도 드러나지 않는다.** 규칙이 통제의 근거인 마스터는 **미등록 대상 수를 함께 보인다** (§5-1)
