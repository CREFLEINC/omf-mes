## §0. 요약

- **개요**: 관리웹에서 설비담당이 금형·지그를 포함한 모든 도구(REQ-PR-0003 요구 — 기존 '금형' 중심에서 확대)를 MES에 직접 마스터 등록하고 QR 라벨 이미지를 생성하는 화면. 테이블은 기존 `mdm.mold`를 그대로 쓰되 `tool_type_code`(금형/지그/그 밖의 도구)를 더해 확대된 범위를 반영한다.
- **주요 데이터**: 툴 마스터 `mdm.mold`(툴유형·캐비티 수·적정타수·누계타발수·운용상태·PM 주기 3필드 포함)와 QR 라벨 발행 기록 `app.document_issue_log`(읽기 전용 목록).
- **핵심 액션**: 툴 추가·저장/취소·사용 중지·폐기 처리·엑셀 업로드(DX 마이그레이션)·QR 라벨 이미지 생성(물리 인쇄는 범위 밖)·발행 이력 보기·변경 이력 조회.

## §3. ⛔ 요구는 「모든 도구」인데 테이블은 「금형」이다

REQ-PR-0003 이 **「금형, 지그를 포함한 모든 도구」**를 요구했고 WF05 S1 이 「기존 범위 '금형' 중심에서 **확대**」라고 명시했다. 그런데 하류는 확대 전 이름으로 서 있다.

### §3-1. A-13 4단 — 이번에는 네 단 다 없다

| 단 | 확인 | 결과 |
| :-: | --- | :-: |
| ① 한 층 아래 | `mdm.mold` 안에 유형 컬럼이 있나 | **없음** |
| ② 다른 파일 | | 단일 파일 |
| ③ 다른 스키마 | `tool`·`jig`·`fixture` 검색 | **0건** |
| ④ 다른 이름 | `mdm.equipment` 가 도구를 겸하나 | **아니다** — 참조처가 갈린다(§3-2) |

→ **⑤ 원칙 1) 적용**(`W-05-12` §9-3). **화면이 정의하고 모델이 따라온다.**

### §3-2. `mdm.equipment` 로 합치지 않는 이유 — 하류가 이미 둘을 갈라 놨다

**네 곳이 설비와 금형을 나란히 두 컬럼으로 갖는다**(실측).

| 테이블 | 설비 | 금형 |
| --- | --- | --- |
| `production.work_order`(SQL 796·797) | `planned_equipment_id` | `planned_mold_id` |
| `production.work_session`(852·853) | `equipment_id` | `mold_id` |
| `production.production_result`(1645·1646) | `equipment_id` | `mold_id` |
| `quality.defect_record`(1942·1943) | `equipment_id` | `mold_id` |

**한 작업에 설비 1대와 금형 1세트가 함께 붙는다** — 같은 축이면 컬럼이 하나였을 것이다. **둘은 다른 축이고, 합치면 이 네 곳을 전부 고쳐야 한다.**

### §3-3. 확정 — **유형 코드 하나를 더한다**

**결정 06 이 계측기 이력에서 쓴 것과 같은 패턴**이다(단일 엔티티 + 유형 코드 — 유형별 테이블 분리는 과설계).

```
툴 마스터  =  현 mdm.mold  +  tool_type_code (금형 / 지그 / 그 밖의 도구)
```

| 안 | 뜻 | 판정 |
| :-: | --- | :-: |
| 가 | 유형별 테이블(금형·지그·검사구…) | ⛔ **유형 추가마다 스키마 변경** — 결정 06 이 같은 이유로 기각한 (b) 안 |
| **나** | **단일 테이블 + 유형 코드** | ✅ **확정** — 결정 06 의 (c) 패턴 재사용 |

⚠ **유형에 따라 의미가 없어지는 컬럼이 생긴다** — 캐비티 수·적정타수는 금형에만 있고 지그에는 없다. **공유계약 A-2**(조건부 필수·짝 제약의 표시)로 다룬다(§4 주).

⛔ **테이블 이름을 바꿔 달라고 하지 않는다.** `mdm.mold` 라는 이름으로 지그를 담아도 화면과 계약은 성립한다 — **이름 변경은 참조 4곳을 함께 고치는 일**이고, 그 값이 유형 코드 하나를 더하는 것보다 크지 않다. **17장 완료 후 #67 회신에 「이름은 그대로 두고 유형 축을 더한다」로 적는다.**

### §5-2. ⛔ 누계타발수를 이 화면이 고치지 않는다 — B-13

`current_shot_count` 는 **마스터에 있지만 마스터가 정하는 값이 아니다.**

| 누가 | 무엇을 |

| **이 화면** | ⛔ **읽기만 한다** |

공유계약 **B-13**(한 컬럼을 여러 경로가 바꾸면 「누가 정하고 누가 반영하는가」를 가른다) 그대로다. **마스터 화면에서 누계를 손으로 고칠 수 있으면 실적과 마스터가 조용히 어긋난다.**

⚠ **누계 리셋의 시점·권한은 여기서 정하지 않는다** — WF05 S7 Exception ② 가 남긴 미결이고, **웹-툴PM실적-등록(`W-05-03`) 설계 시**(DR-001 §7 3단계) 정한다. → §8-3

### §5-3. 적정타수가 비어 있으면 **PM 트리거가 서지 않는다**

QA #11 이 PM 트리거를 「타발수 + 날짜 주기 **겸용 설정형**」으로 확정했다. 타발수 축은 **적정타수가 있어야** 판정된다.

공유계약 **G-12**(통제의 근거가 되는 마스터는 **「비어 있음」을 함께 보인다**)를 적용한다.

- 목록에 **「적정타수 미등록」 필터**를 둔다
- 미등록 행은 사용가능타수 칸에 **「산출 불가」**로 표시한다(G-9 — 「0」으로 그리지 않는다)

⛔ **「0으로 채워 두자」는 하지 않는다.** 0 은 「다 썼다」는 뜻이 되어 **PM 이 즉시 도래한 것처럼 보인다.** 컬럼이 `NULL` 허용인 것이 그 의도다.

### §5-4. QR 라벨 — **이미지를 만드는 데까지**

**리더 확정: 마스터 라벨 = 이미지 생성까지.** 물리 인쇄는 개발 범위 밖이다.

| 무엇 | 어디 |
| --- | --- |
| 라벨 **도안·렌더링** | ✅ **서버**(결정 18 · K-5 「라벨은 서버가 그린다」) |
| 이미지 **제공**(미리보기·내려받기) | ✅ **이 화면** |
| **물리 인쇄** | ⛔ **범위 밖** |

**왜 POP 인쇄 화면을 만들지 않는가** — 결정 18 의 POP 인쇄는 「**프린터가 배치되는 스테이션**의 패널 PC」가 전제인데, 툴 QR 은 그 스테이션에서 발행되지 않는다. **기준정보 등록 시 발급 · 일회성 · 내구성 라벨 스톡**이 필요하다(인벤토리 v1.3 판정).

**발행 규약** — 출력물 계약(K 계열)을 그대로 따른다.

| 조항 | 이 화면에서 |
| --- | --- |
| **K-1** 회차로 쌓고 이전 것을 지우지 않는다 | `issue_seq` 증가 |
| **K-2** 재발행에는 **사유가 필수** | 회차 2+ 에서 사유 선택 강제(`ck_document_reissue_reason` 이 DB에서도 막는다) |
| **K-3** 단말을 남긴다 | `terminal_id` · **프린터는 비운다**(인쇄 안 함) |
| **K-4** 인쇄는 트랜잭션 밖이다 | 이미지 생성 실패가 마스터 저장을 되돌리지 않는다 |
| **K-6** 물리적으로 유통되는 출력물은 **회차를 인쇄면에도** | 라벨 도안에 회차 포함 — **재부착 시 어느 것이 최신인지** 현장에서 구분된다 |
| **K-7** 기록은 남고 인쇄만 실패하는 경우 | 여기서는 「이미지 생성 성공·내려받기 실패」가 그 자리 — 재발행 사유 목록이 이를 받아야 한다 |

⚠ **툴코드 수정이 특히 위험하다.** QR 라벨에 인쇄되어 **현장 금형에 물리적으로 붙어 있다.** B-4(참조 0일 때만 코드 수정)가 이미 잠그지만, **참조가 0이어도 라벨이 이미 발행됐으면 잠근다** — 발행 기록이 1건 이상이면 코드 입력란을 비활성하고 사유를 보인다(G-3). → §9-1

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐ **물리적으로 부착된 식별자는 참조 건수가 0이어도 잠근다**

B-4 는 「참조가 0이면 코드를 고칠 수 있다」로 확정돼 있다. **그 전제가 성립하지 않는 경우가 있다.**

```
참조 0  =  시스템 안에서 아무도 안 쓴다
        ≠  현장에 아무것도 없다        ← 라벨이 이미 금형에 붙어 있다
```

**규칙안**: 코드가 **발행된 라벨·인쇄물에 실려 현장에 나간 경우**, 참조 건수와 무관하게 **코드 수정을 잠근다.** 판정 근거 = `app.document_issue_log` 에 그 대상의 발행 기록이 **1건 이상** 있는가.

**해당 후보**: 툴 QR(이 화면) · 창고 Location 코드(`W-06-07`) · 자재/제품 LOT 라벨.

**왜 계약인가**: B-4 의 「참조 0」 판정은 **DB가 세어 주는 것만 본다.** 물리 세계로 나간 것은 DB가 세지 않는다. **B-4 에 단서를 붙이지 않으면 화면마다 다르게 판단**한다.

### 9-2. **다형 참조 대상이 늘 때는 계약이 먼저 값을 갖는다** — A-10 의 운영 규칙

`app.document_issue_log.target_type_code` 와 `audit.audit_event.target_type_code` 는 **FK가 아닌 문자열**이다. 화면이 값을 정해 넣는다.

**규칙안**: 새 대상이 생기면 **화면이 문자열을 정하기 전에 계약의 대응표에 등재**한다. 등재 없이 넣은 값은 **조회하는 쪽이 모른다** — 발행 이력이 안 보이고 변경 이력이 안 걸린다.

⚠ **이 화면이 그 첫 사례다** — 툴은 `document_issue_log` 의 새 대상이다.

### 9-3. **「비어 있으면 판정이 서지 않는 필드」는 저장을 막지 말고 목록에서 보인다**

적정타수가 그 형태다(§5-3). **등록 시점에는 모를 수 있고, 없으면 PM 이 안 돈다.**

**규칙안** — 세 가지를 함께 한다.

1. **저장은 막지 않는다** — 막으면 등록 자체가 미뤄지고 마스터에 아예 안 들어온다
2. **파생값은 `0` 이 아니라 「산출 불가」**로 그린다(G-9)
3. **목록에 「미등록」 필터**를 둔다(G-12) — 채워야 할 것이 몇 건인지 한눈에 보인다

**왜 계약인가**: 같은 형태가 여러 곳에 있다 — 적정타수(PM 트리거) · 점검 주기(점검 트리거 · `W-05-12`) · 검교정 주기(게이트 · `W-05-11`). **세 곳이 다르게 처리하면 「비어 있는 마스터」가 조용히 쌓인다.**
