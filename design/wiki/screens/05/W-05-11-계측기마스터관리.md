# W-05-11 · 계측기 마스터 관리

> 작성일: 2026-08-10 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> DR-001 §7 진행 순서 1단계(마스터 3장)의 마지막.
> ⭐ **이 화면이 만드는 데이터가 다른 도메인 세 곳의 검사를 막는다** — 수입검사(01)·공정검사(02)·출하검사(04)가 「**검교정 유효 시만 사용**」 게이트로 이 마스터를 본다. 마스터 3장 중 **다른 도메인에 직접 영향을 주는 유일한 화면**이다.
> ⚠ **소속은 설비툴관리다** — 2026-07-20 03 품질섹션 재정의로 이관됐고, **DR-001 1-C 가 그 이관을 유지**하기로 확정했다(2026-08-10).

## §0. 요약

- **개요**: 관리웹에서 품질담당이 계측기(검교정 대상 장비)를 관리하는 화면. 별도 테이블이 아니라 `mdm.equipment`를 `equipment_type_code = 계측기`로 걸러 보는 화면이며, 설비·설비그룹 마스터(`W-05-12`)와 **같은 테이블을 다른 눈으로** 본다(§3).
- **주요 데이터**: 계측기(`mdm.equipment` 서브셋 — 계측기번호·명·유형·소속공정·운용상태(운용/폐기)·검교정 대상 스위치·검교정 주기[신설]·정밀도[신설]·최근/차기 검교정일은 읽기 전용) + 검교정 이력(`quality.equipment_calibration` — 읽기 전용 목록, 등록은 `W-05-10` 소관).
- **핵심 액션**: 계측기 추가 → 저장/취소, 사용 중지, 폐기 처리, 검교정 이력 등록 화면(`W-05-10`)으로 이동, 변경 이력 조회. 이 화면은 수입·공정·출하검사 세 화면이 쓰는 「검교정 유효」 게이트의 **근거만 만들고 집행하지 않는다**(§5-3).

## §3. ⭐ 「계측기 마스터가 없다」는 틀렸다 — **설비 마스터가 계측기를 겸한다**

A-13 4단의 **④ 다른 이름**에서 또 걸렸다. **두 번째**다(`W-05-12` §3 이 첫 번째).

### §3-1. 하류 다섯 곳이 그렇게 서 있다 (실측)

| 근거 | 무엇을 말하나 |
| --- | --- |
| `mdm.equipment.calibration_required`(SQL 465) — 주석 「**[M] 검사장비 교정관리**」 | 설비 마스터가 **검사장비를 담는다고 명시**했다 |
| `mdm.equipment.last_calibration_date` · `calibration_due_date`(466·467) | **차기 검교정 예정일이 이미 있다** — 결정 06 이 마스터에 두라고 한 그 항목 |
| `quality.equipment_calibration.equipment_id → mdm.equipment`(2063) | 검교정 이력이 **설비를 가리킨다** |
| `quality.inspection_item_spec.default_inspection_equipment_id`(1799) — 주석 「**[M] 지정 검사장비**」 | **검사 기준이 기본 계측기를 지정**한다 |
| `quality.inspection_measurement.inspection_equipment_id`(1882) | **시료별 측정치가 사용 계측기를 기록**한다 |

⭐ **개념모델의 「검사결과—계측기 N:1(계측값 자동 연계)」이 하류에서 `inspection_measurement → mdm.equipment` 로 착지했다.** 계측기는 별도 테이블이 아니라 **설비 마스터의 한 종류**다.

### §3-2. 그래서 이 화면과 설비 마스터는 **같은 테이블을 다른 눈으로 본다**

```
mdm.equipment
   ├── equipment_type_code = 계측기   → 웹-계측기-마스터관리 (이 화면)
   └── equipment_type_code = 그 밖    → 웹-설비설비그룹-마스터 (W-05-12)
```

⚠ **`calibration_required` 로 가르지 않는다.** 두 축은 다른 것을 말한다.

| 컬럼 | 무엇을 가르나 |
| --- | --- |
| `equipment_type_code` | **이것이 계측기인가** — 화면·메뉴가 갈리는 축 |
| `calibration_required` | **검교정 게이트의 판정 대상인가** — 생산 설비도 대상일 수 있다 |

**둘을 하나로 묶으면** ①검교정을 안 하는 계측기(단순 게이지)를 담을 수 없고 ②검교정하는 생산 설비가 계측기 화면에 나타난다.

#### ⭐⭐ 가르는 것은 «값 하나»가 아니라 «계열»이다 — 목록 조건이 값 여럿을 싣는다 **[2026-08-24 `#219` 확정]**

위 그림은 「`equipment_type_code` = 계측기」라고 **값 하나**로 적었는데, 세부 유형이 확정되며(`#216`) **계측기 계열이 3값**이 됐다. **전제가 깨진 자리다.**

| | 무엇을 실어 보내나 |
| --- | --- |
| **이 화면**(`W-05-11`) | `INSTRUMENT_TYPE` 그룹의 **값 전체** — 지금은 `CALIPER`·`MICROMETER`·`GAUGE` |
| **설비 마스터**(`W-05-12`) | `EQUIPMENT_TYPE` 그룹의 **값 전체** — ⚠ 값 목록 미정이라 아직 못 싣는다 |

⭐ **화면이 값을 외우지 않는다** — 자기 계열의 그룹을 통째로 받아 그대로 조건에 싣는다. 그래서 고객이 공통코드 관리(`W-06-06`)에서 계측기 유형을 늘려도 **화면 코드는 그대로**다.

⛔ **받아 온 목록을 화면에서 다시 거르지 않는다.** 서버가 페이지 단위로 잘라 주므로 그 안에서 또 걸러 내면 **건수와 「더 있음」 안내가 통째로 거짓**이 된다(`L-1` — 요약은 필터 전체, 목록은 페이지). 조건은 서버에 건다.

⚠ **조건을 걸기 «전»에는 계측기가 아닌 설비도 함께 선다** — 감추지 말고 밝힌다(`G-2`·`G-9`). 다만 위 규약대로 화면은 **첫 조회부터 3값을 실어 보내므로** 그 상태는 값 목록을 못 받았을 때만 생긴다.

**등록은 웹-계측기검교정이력-등록(`W-05-10`)이 한다.** 이 화면은 최근 이력을 보여 주기만 한다.

| 검교정 확장 — **교정 기관(내부/외부)** | — | ⛔ **미착지** |
| 검교정 확장 — 차기 예정일 | `valid_until` + `equipment.calibration_due_date` | ✅ |

⛔ **하류가 결정 06 이 명시적으로 기각한 안에 서 있다.** 결정 06 은 세 대안 중 「**(b) 유형별 별도 테이블(검교정이력·수리이력…) — 유형 추가마다 스키마 변경**」을 기각하고 **(c) 단일 이력 + 유형 코드**를 확정했는데, 하류는 검교정 전용 테이블 하나만 만들었다.

**원칙 1)에 따라 결정 06 을 유지한다** — 뒤집을 새 근거가 없고, **「고장」 이력이 없으면 §5-2 의 사용 가부 판정이 서지 않는다**(§5-2).

⚠ **이력 테이블의 최종 형태는 이 화면이 확정하지 않는다** — **웹-계측기검교정이력-등록(`W-05-10`)** 소관이며 DR-001 §7 **4단계**다. 여기서는 **마스터가 판정에 무엇을 필요로 하는지**만 확정한다. → §8-1

## §5. 액션·상태

### §5-1. 액션

| 액션 | 활성 조건 |
| --- | --- |
| 계측기 추가 | 편집 권한 |
| 저장 / 취소 | 변경분 존재 · 필수 충족 |
| **사용 중지** | `is_active=true` · 물리 삭제 버튼 없음(B-4) |
| **폐기 처리** | `status_code=운용` · 확인 다이얼로그 |
| **검교정 이력 등록으로 이동** | 계측기 선택 — ⛔ **등록은 `W-05-10` 이 소유**(중복 구현 금지 · B-4-1 ④ 와 같은 취지) |
| 변경 이력 | 항상 — `audit.audit_event`(B-5) · 기간 필수 |

⛔ **엑셀 업로드를 두지 않는다.** 계측기 대장의 현행 매체에 대한 확정이 없다 — 툴은 「엑셀 관리·ERP 미사용」이 REQ-PR-0003 으로 확정됐지만(`W-05-13` §5-5), 계측기에는 그런 근거가 없다. **설비 마스터와 같은 판단**(`W-05-12` §5-1).

### §5-2. ⭐ 상태 3값(정상/만료/고장)을 **2값으로 고친다** — A-14

**두 곳이 「정상/만료/고장」 3값을 적었다.**

| 어디 | 무엇이라 적었나 |
| --- | --- |
| **WF03 S9 Result** *(프로세스 정본)* | 「계측기 상태(**정상/만료/고장**) — 계측기 마스터에는 현재 상태·차기 검교정 예정일만 유지」 |
| 도식스펙-05 §2.5 MES-11 스티키 | 「현재 상태 (정상/만료/고장)」 |

**그대로 만들면 안 된다.**

공유계약 **A-14** 가 정확히 이 형태를 막는다.

> **A-14**: 같은 상태에 이르는 길이 여럿이면 **상태 값을 늘리지 말고 조건을 따로 관리**한다.

**세 값을 뜯어 보면 축이 셋이다.**

| 도식의 값 | 실제로 무엇인가 | 어디서 오나 |
| --- | --- | --- |
| **만료** | ⛔ **상태가 아니라 날짜 파생 조건** | `calibration_due_date < 오늘` |
| **고장** | ⛔ **상태가 아니라 열린 이력** | 계측기이력(수리 유형) — 결정 06 |
| **정상** | 위 둘이 아닌 나머지 | 파생 |

**확정 — 마스터가 갖는 것은 자산 수명주기 축뿐이다**(`W-05-12` §5-2 와 같은 규칙).

```
status_code  =  운용 | 폐기          ← 마스터가 갖는다

사용 가능  =  is_active
           AND status_code = 운용
           AND (calibration_required = false  OR  검교정 유효기한 ≥ 오늘)
           AND 열린 수리 이력이 없다
```

**왜 뒤집는가** — 세 값을 그대로 두면 **날짜가 지날 때마다 누군가 마스터를 갱신해야 한다.** 「정상 → 만료」는 사람의 행위가 아니라 **달력이 만드는 변화**다. 컬럼에 넣으면 **매일 도는 배치가 필요**하고, 배치가 멈추면 만료된 계측기가 정상으로 보인다.

⚠ **결정 06 자체는 값을 열거하지 않았다** — 「계측기 마스터에는 **현재 상태**·차기 검교정 예정일만 유지」라고만 했다. **3값은 WF03 S9 Result 와 도식이 적은 것**이다. 결정 06 을 뒤집는 것이 아니라 **그 「현재 상태」가 무엇인지를 정하는 것**이다.

⚠ **그래서 #67 회신 대상이 둘이다** — 도식스펙-05 §2.5 만이 아니라 **WF03 S9 Result** 도 함께 적는다. → §8-1

### §5-3. ⭐ 검교정 유효 게이트 — **F-3 을 충족하는 게이트**

공유계약 **F-3**은 「게이트는 **판정 근거 컬럼의 실재를 확인해야** 성립한다」이고 현재 **⚠ 미충족** 표시가 붙어 있다(수신본 판정 컬럼 부재). **여기는 다르다 — 근거가 실재한다.**

⚠ **이것은 새 발견이 아니다.** **확대 6차 완료보고**(2026-08-06)가 「모델이 앞선 것」 1번으로 이미 적었다 — 「**교정 만료 장비 판별이 가능하다** — `inspection_measurement.inspection_equipment_id` + `mdm.equipment.calibration_due_date` + `measured_at`」. **이 장은 그것을 게이트 판정 규칙으로 정리한다.**

| 필요한 것 | 실재 |
| --- | :-: |
| 이 장비가 검교정 대상인가 | `equipment.calibration_required` ✅ |
| 유효기한이 언제까지인가 | `equipment_calibration.valid_until` ✅ · `equipment.calibration_due_date` ✅ |
| 검사 항목이 어느 장비를 쓰나 | `inspection_item_spec.default_inspection_equipment_id` ✅ |
| 실제로 어느 장비로 쟀나 | `inspection_measurement.inspection_equipment_id` ✅ |

**게이트를 보는 화면 셋** — 웹-IQC수입검사판정(`W-01-01`) · POP-PQC공정검사(`P-02-13`) · 웹-OQC출하검사판정(`W-04-03`).

⚠ **이 화면은 게이트를 「집행」하지 않는다** — 게이트의 **근거를 만든다.** 집행 문구·차단 여부는 그 세 화면 소관이다.

⛔ **만료 계측기로 검사할 때 막을 것인가 경고할 것인가는 아직 안 정해졌다** — 도식스펙-05 §4.2 M8 마커 「① **만료 계측기 검사 통제(차단 여부)**·고장 시 대체」가 그것이다. **이 화면의 결정 대상이 아니다.** → §8-5

### §5-4. 차기 예정일은 **서버가 산출한다**

```
차기 검교정 예정일  =  최근 검교정일  +  검교정 주기
```

공유계약 **L-2**(파생 값은 서버가 계산한다). 화면은 표시만 한다.

⚠ **`calibration_due_date` 는 컬럼으로 저장돼 있다** — 파생값인데 저장한다. **그래서 갱신 주체를 못박아야 한다**(B-13): **웹-계측기검교정이력-등록(`W-05-10`)이 이력을 저장할 때 함께 갱신**한다. 이 화면은 읽기만 한다.

**결정 06 의 「만기 임박 알람 트리거」**가 이 컬럼을 본다 — DR-003 확정에 따라 **알림센터(`W-CO-03`)가 정본**이고 Zalo 는 부가 전달이다. 알람 이벤트 목록은 **코드 상수**(DR-003 3-C)이므로 여기서 설정하지 않는다.

### §5-5. ⭐ 네 가지 모양으로 그린다 — G-13 확장

공유계약 **G-13**은 「**대상 아님**·**아직 안 함**·**했음**을 세 모양으로 그린다」이다. 여기는 **넷**이다.

| 모양 | 조건 | 표시 |
| --- | --- | --- |
| **대상 아님** | `calibration_required = false` | 회색 `Chip` 「검교정 대상 아님」 — **빈칸으로 두지 않는다** |
| **아직 안 함** | 대상인데 `last_calibration_date IS NULL` | 경고 `Chip` 「검교정 이력 없음」 + 목록 필터 |
| **했음 · 유효** | `calibration_due_date ≥ 오늘` | 정상 `Chip` + 남은 일수 |
| **했음 · 만료** | `calibration_due_date < 오늘` | 오류 `Chip` 「만료 — N일 경과」 |

⛔ **「아직 안 함」과 「대상 아님」을 같은 회색으로 그리면 안 된다.** 앞은 **채워야 할 것**이고 뒤는 **정상**이다. 공유계약 **G-9**(모르는 값과 없는 값을 같은 모양으로 그리지 않는다)가 같은 취지다.

### §5-6. 화면 상태

`초기(EmptyState)` → `조회` → `편집` → `저장 중` → `성공(Toast)` / `실패` / `충돌(B-1)`

**낙관적 잠금**: `equipment.version_no` 실재 → B-1 적용.

**B-4 참조 건수 — 산출 가능**(전부 FK · 실측 7곳 — `W-05-12` §5-4 와 같은 표). ⚠ **계측기에서 특히 중요한 참조 둘**: `inspection_item_spec.default_inspection_equipment_id`(검사 기준이 지정) · `inspection_measurement.inspection_equipment_id`(측정 기록이 참조). **검사 기록은 지워지지 않으므로 운영 중 계측기의 코드는 사실상 영구 잠금**이다.

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐ **달력이 만드는 변화를 컬럼에 넣지 않는다**

A-14 의 **시간 축 판**이다. §5-2 가 실증했다.

**규칙안**: 상태 값이 **사람의 행위 없이 시간만 지나도 바뀐다면**, 그것은 상태가 아니라 **날짜 비교로 파생되는 조건**이다. 컬럼에 넣지 않는다.

**판별 질문 하나** — 「**아무도 아무것도 하지 않아도 이 값이 바뀌는가?**」 그렇다면 조건이다.

| 해당 | 파생식 |
| --- | --- |
| 계측기 「만료」 | `calibration_due_date < 오늘` |
| 검사기준·공통코드 「유효기간 밖」 | `effective_to < 오늘` (`W-06-06` §8-5 가 같은 문제를 남겼다) |
| 툴 「PM 도래」 | `누계타발수 ≥ 적정타수` 또는 주기 도래 |
| 특채 「승인 만료」 | `concession.valid_to < 오늘` |

**왜 계약인가**: 컬럼에 넣으면 **매일 도는 배치가 필요**하고, 배치가 멈추면 **틀린 값이 정상으로 보인다.** 그리고 **여러 화면이 그 컬럼을 갱신하려 경합**한다(B-13). ⚠ **`W-06-06` §8-5 가 이미 같은 문제를 「판정 주체가 화면인지 서버인지 규칙이 없다」로 남겨 뒀다** — 그 미결의 답이 이것이다.

### 9-2. **게이트를 만드는 화면과 집행하는 화면을 나눈다**

이 화면은 게이트의 **근거**를 만들고, 검사 화면 셋이 **집행**한다. §5-3 이 그 형태다.

**규칙안**

1. **근거 화면**은 판정에 필요한 데이터가 **다 있는지**를 책임진다 — 비어 있으면 「아직 안 함」으로 보이고 필터에 잡는다(G-12·G-13)
2. **집행 화면**은 **차단·경고·통과**를 책임진다 — 문구와 통제 수준은 집행 쪽이 정한다
3. **근거 화면은 집행 문구를 쓰지 않는다** — 쓰면 집행 화면과 두 벌이 되고 어긋난다

**왜 계약인가**: F-3(게이트는 판정 근거 컬럼의 실재를 확인해야 성립한다)이 **근거의 실재**만 다룬다. **누가 무엇을 책임지는가**가 빠져 있어 근거 화면이 통제 문구까지 쓰려는 유혹이 생긴다.

### 9-3. **G-13 을 네 모양으로 확장한다**

G-13 은 「대상 아님·아직 안 함·했음」 **셋**이다. §5-5 가 넷째를 만들었다 — **「했음 · 유효」와 「했음 · 만료」**.

**규칙안**: 「했음」이 **유효기간을 갖는 경우** 셋이 아니라 넷으로 그린다. 넷째는 **가장 위험한 상태**다 — 「했음」으로 보이지만 **쓸 수 없다**.

**해당**: 검교정(이 화면) · 작업자 자격(`worker_qualification` — 유효기간 실재) · 검사기준 Rev · 특채 승인.
