## §0. 요약

- **개요**: 모바일(Capacitor Android PDA)에서 현장 오퍼레이터·반장이 설비 고장을 발견 즉시 접수하는 화면. 고장(사건)과 비가동(구간)을 소유 클러스터가 다른 별도 기록으로 나누고, 이 화면은 고장 「접수」만 만든다 — 비가동 기록은 POP 화면(`P-05-02`)이 만든다.
- **주요 데이터**: 신설 고장 기록(설비 FK·증상·발생 상태·정지 시각(선택)·보고 시각·보고자·처리 상태) + 사진 첨부(`app.attachment` **실재** — 다형 참조로 고장 기록에 연결).
- **핵심 액션**: 설비 QR 스캔/목록 선택 → 증상 입력(필수) → 발생 상태 선택(멈췄다 / 돌지만 이상하다) → 정지 시각 입력(선택) → 사진 촬영(0~3장) → 설비담당 알림(기본 켬) → 고장 보고.

## §3. ⭐ 고장과 비가동을 **나눈다** — 도식 마커 M6 에 대한 답

도식 B13 이 「고장 현상·비가동 사유·정지 시각 기록(**사이드 D와 공유**)」이라 적었고, 마커 **M6**(「비가동 N:M」)이 「점검/보전이력 ↔ 비가동 N:M 연계 구조 **미결**(내부 설계)」로 남아 있다.

**화면이 둘로 갈려 있다는 사실 자체가 첫 근거다.**

| 화면 | 단말 | 확정 |
| --- | --- | --- |
| **모바일-설비고장-현장보고**(이 화면) | 모바일 | ✓확정 2026-07-24 **#6** |
| **POP-비가동실적-입력**(`P-05-02`) | POP | ✓확정 2026-07-24 **#7** |

**한 기록이면 단말이 갈릴 이유가 없다.**

### §3-1. 셋이 다르다

| | **고장** | **비가동** |
| --- | --- | --- |
| 무엇인가 | **사건** — 「무엇이 어떻게 고장났다」 | **구간** — 「언제부터 언제까지 안 돌았다」 |
| 누가 언제 | 발견 즉시 · 순회 중 → **모바일** | 작업 중 설비 앞에서 → **POP** |
| 뒤에 무엇이 | **보전 트리거**(사이드 B) | **OEE 집계**(`W-05-08`) |
| 소유 | 설비(C5) | ⭐ **품질/현장(C4)** — WF05 S4 Rule 명시 |

⭐ **네 번째 줄이 결정적이다** — WF05 S4 Rule 이 「**비가동 소유 = 품질/현장(C4)**, 보전이력/점검이력(C5)과 **N:M 연계**」라고 소유 클러스터를 **다르게** 지정했다. **소유가 다른 것을 한 테이블에 담을 수 없다.**

### §3-2. 확정 — **두 기록 · N:M**

```
고장 기록  ─┐
점검 이력(NG) ─┼─ N:M ─▶ 비가동 기록
계획 정지    ─┘
```

| 관계 | 왜 |
| --- | --- |
| 고장 1 → 비가동 **N** | 수리하다 다시 서고, 부품 대기로 또 선다 |
| 비가동 1 → 고장 **0 또는 1** | **자재 대기·금형 교체·계획 정지는 고장 없이도 비가동**이다 |
| 점검 NG → 비가동 | WF05 S4 Rule 이 「점검이력 ↔ 비가동 N:M(**고장점검 시**)」로 명시 |

⚠ **M6 이 물은 것이 정확히 이 관계**이고, **「내부 설계」로 넘겨져 있었다**(WF05 S4 Open-Issue). **원칙 1)에 따라 여기서 정한다.**

### §3-3. 그래서 이 화면은 **비가동 시각을 필수로 받지 않는다**

WF05 S4 Action 이 「비가동 사유·**시간** 기록」을 고장과 함께 적었지만, **현장에서 고장을 발견한 사람은 언제 멈췄는지 정확히 모른다.**

| | 이 화면 | `P-05-02` |
| --- | --- | --- |
| 정지 **시각** | **선택** — 알면 적고 모르면 비운다 | ✅ **필수** — 구간이 데이터다 |
| 비가동 사유코드 | ⛔ **받지 않는다** | ✅ 필수 |

**고장 보고를 가볍게 유지하는 것이 목적**이다 — WF05 S4 Exception ① 이 「돌발 고장은 **선조치 후기록 → 기록 누락 위험**」을 경고했다. **입력이 무거우면 안 적는다.**

⚠ **비가동 사유코드·종료 시각은 이 표에 없다** — `P-05-02` 소관이다(§3-3).

### §5-1. 「처리 상태」는 **A-14 위반이 아니다**

**자산 마스터의 상태를 2값으로 묶었고**(B-16), 「고장」을 **트랜잭션이 만드는 조건**으로 밀어냈다. **그 트랜잭션이 이것이다.**

```
mdm.equipment.status_code   운용 / 폐기          ← 자산 수명주기 (B-16)
고장 기록.처리 상태          접수 / 처리중 / 완료   ← 이 사건의 진행
```

**둘은 다른 축이다.** 「열린 고장이 있다」가 설비의 사용 가부 판정에 들어가는 것은 B-16 의 판정식이 이미 정했다 — 「**열린 고장·보전 건이 없다**」.

⚠ **처리 상태 값을 늘리지 않는다**(A-14) — 「부품 대기」·「외주 의뢰」는 상태가 아니라 **처리 중의 사연**이고 `W-05-04` 의 처리 내역이 받는다.

### §5-2. 증상은 **필수이고 형식을 유도한다** — A-12

공유계약 **A-12**(남이 읽고 판단할 자유 텍스트는 화면이 필수로 만들고 형식을 유도한다)가 정면으로 걸린다. **설비담당은 이 한 줄만 보고 출동한다.**

| 하는 것 | 안 하는 것 |
| --- | --- |
| **필수**로 만든다 | ⛔ 최소 글자 수를 강제하지 않는다 |
| 힌트로 형식 유도 — 「**무엇이 어떻게** 되었는지 한 줄로」 | ⛔ 정형 코드 목록으로 대체하지 않는다 |
| 최근 입력 **재사용 제안**(같은 설비의 과거 증상) | |

⛔ **증상을 코드 목록으로 바꾸지 않는 이유** — WF05 S4 [Check] 가 「**사유코드 체계**」를 미확인으로 남겼고, **고장 현상은 사전에 열거할 수 없다.** 코드로 강제하면 전부 「기타」가 된다. 비가동 **사유코드**는 다른 얘기다(`P-05-02` — 시간 집계용이라 분류가 필요하다).

### §5-3. 「멈췄다」와 「돌지만 이상하다」를 가른다

WF05 S4 Trigger 가 「고장·**정지**·이상(돌발)」 셋을 적었다. **정지 여부가 뒤를 가른다.**

| 값 | 무엇이 달라지나 |
| --- | --- |
| **설비가 멈췄다** | 비가동이 **지금 발생 중**이다 → `P-05-02` 로 이어질 것을 안내 · 알림 우선순위 높음 |
| **돌지만 이상하다** | 비가동 없음 · **경미 정지(Chokotei)** 와 구분된다(WF05 S4 Exception ③) |

⚠ **이 화면이 비가동을 만들지 않는다** — 안내만 한다. 만드는 것은 POP(`P-05-02`)다.

### §5-4. 사진 — **저장처가 실재한다**

⭐ **A-13 ④ 가 또 걸렸다.** 「첨부 테이블이 없다」고 볼 뻔했으나 **`app.attachment`(SQL 2626)가 실재**한다 — `target_type_code`·`target_id`·`storage_key`·`mime_type`·`checksum_sha256`·`uploaded_by`.

| | |
| --- | --- |
| 다형 참조 | `target_type_code` 에 **고장 기록**이 추가된다 → ⭐ **A-16 적용**(계약이 먼저 값을 갖는다) |
| 촬영 | Capacitor 네이티브 카메라 — ds-gap G-9(파일 업로드)와 **별개**로 이미 판정돼 있다 |
| 오프라인 | ⚠ **사진은 큐 용량을 크게 먹는다** → §6-2 |

> ⚠ **이 장은 §3 을 판단 절로 써서 블록이 한 칸씩 밀렸고**(§4=레이아웃 · §5=필드) **액션 표가 밀려나며 빠져 있었다.** 새로 설계한 것이 아니라 **§4 레이아웃의 컨트롤과 §5-1~§5-4·§6 의 조건을 모은 것**이다.

| 발생 상태 선택 *(멈췄다 / 돌지만 이상하다)* | 설비 선택됨 · ✅ **필수**(§5-3) |

| **고장 보고** | 설비 선택 **AND** 증상 입력 **AND** 발생 상태 선택 |

**상태**: `초기` → `설비 선택됨` → `입력 중` → `저장 중` → `성공` / `실패` / **`미전송 큐`**(§6-2)

⚠ **이 화면이 만드는 것은 「접수」 하나다** — 처리 상태 전이(접수 → 처리중 → 완료)는 `W-05-04` 소관이고 여기에 버튼을 두지 않는다(§5-A).
⛔ **비가동을 만들지 않는다** — 「멈췄다」를 고르면 `P-05-02` 로 이어질 것을 **안내만** 한다(§5-3).
⚠ **알림 발송 실패는 보고를 실패시키지 않는다** — 알림센터가 정본이다(DR-003 · §6-1).

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐ **오프라인에서 「보낼 것」을 자동으로 끄지 않는다 — 보이게 둔다**

알림 체크를 오프라인이라고 자동으로 끄면 **보고자가 「알렸다」고 믿는다.** 켜 두고 **아직 못 갔음을 보이는 것**이 맞다.

**규칙안**: 오프라인에서 **외부로 나가는 행위**(알림·호출·송신)는

1. **의사 표시는 그대로 받는다** — 체크를 끄지 않는다
2. **아직 안 갔음을 그 자리에 보인다** — 「연결되면 알립니다」
3. **대안 경로를 안내한다** — 「급하면 직접 연락하세요」

⚠ **G-2**(미확정 코드는 감추지 않고 비활성 + 사유)와 같은 원리다 — 「할 수 없다」를 **감추지 않는다.** 다만 여기는 「지금은 못 하지만 나중에 된다」라 **비활성이 아니라 지연 표시**다.

### 9-2. ⭐ **한 건이 부분 전송되는 경우를 계약이 다루지 않는다**

C 계열은 「한 건이 통째로 큐에 들어갔다가 통째로 간다」를 전제한다. **첨부가 붙으면 깨진다.**

```
고장 보고 본문   수 KB   ← 먼저 가야 한다 (설비담당이 기다린다)
사진 3장        수 MB   ← 뒤따라 가도 된다
```

**규칙안**

1. **급한 부분과 무거운 부분을 나눠 보낸다** — 무엇이 먼저인지를 **스펙이 지정**한다
2. **부분 전송 상태를 보인다** — 「보고 전송됨 · 사진 2/3 전송 중」
3. **본문이 갔으면 「보고됨」으로 그린다** — 사진을 기다리며 미확정으로 두지 않는다

⚠ **C-10**(큐에 순서 의존이 있으면 묶음으로 거부한다)의 **반대 경우**다 — C-10 은 「함께 가야 한다」이고 이것은 「**따로 가도 된다**」다. **둘을 가르는 기준은 「받는 쪽이 기다리는가」**다.

**해당 후보**: 고장 보고 + 사진 · 입하 등록 + 거래명세서 촬영(`M-01-01`) · 검사 실적 + 측정 사진.

### 9-3. **소유 클러스터가 다르면 한 테이블에 담지 않는다**

§3-1 의 네 번째 줄이 판단을 갈랐다 — WF05 S4 Rule 이 **비가동 소유 = 품질/현장(C4)**, 보전·점검 이력 = **C5** 로 다르게 지정했다.

**규칙안**: 두 데이터를 합칠지 나눌지 판단할 때 **소유 클러스터를 먼저 본다.** 같은 화면에서 같이 입력된다고 같은 테이블이 아니다 — **누가 그 데이터에 책임지는가**가 다르면 나눈다.

⚠ **반대 사례와 짝이다** — `W-05-13` 은 **「하류 4곳이 설비와 금형을 나란히 두 컬럼으로 갖는다」**를 근거로 나눴다. **한쪽은 하류 구조가, 한쪽은 소유 클러스터가 근거**다. **둘 다 화면의 편의가 아니다.**
