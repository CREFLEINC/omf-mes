# W-05-05 · 보전 지시 발행

## §0. 요약

- **개요**: 관리웹에서 설비담당이 점검 NG·고장·PM 예정일 세 트리거를 받아 보전 지시를 발행하는 화면(도식 ⊕-2 합류). 계획 단계는 별도로 두지 않고 지시의 예정일로 흡수했으며(지시→실적 2단계·1:N), 보전유형(사후/예방/예지)은 사람이 고르지 않고 트리거 조합이 정한다 — 고장이 하나라도 섞이면 사후로 고정된다.
- **주요 데이터**: 보전 지시(**신설** — 지시번호·설비 FK·보전유형·예정일·담당자·지시상태·지시내용·발행자/발행시각), 지시 항목(**신설** — 보전 항목 FK·순번), 트리거 연결(**신설** · N:M 다형 참조 — 점검 이력/고장 기록/PM 도래, PM 도래는 가리킬 행이 없어 `trigger_id`가 `NULL`).
- **핵심 액션**: 트리거 다중 선택(같은 설비끼리만) → 보전유형(트리거 조합이 결정)·예정일·담당자·보전 항목 지정 → **지시 발행**(선택 설비 수만큼 지시가 개별 생성) · **취소**(실적 0건일 때만).

## §3. ⭐ 마커 M2 에 답한다 — **계획을 별도 단계로 두지 않는다**

도식 마커 **M2**(「계획지시구조」)가 「**점검·보전의 계획→지시→이력 3단계 분리/통합, 지시:이력 카디널리티 미결**(내부 설계)」로 남아 있다. WF05 S5 Open-Issue 도 「계획→지시→이력 **분리/통합·카디널리티는 내부 설계 재량으로 이관**」이라 적었다.

### §3-1. 3단계를 2단계로 줄인다

| 안 | 구조 | 판정 |
| :-: | --- | :-: |
| 가 | 계획 → 지시 → 실적 **3테이블** | ⛔ **과설계** |
| **나** | **지시 → 실적 2테이블** · 「계획」은 **지시의 예정일** | ✅ **확정** |

**근거 셋**

1. ⭐ **QA #10 이 「경량」을 못박았다** — 「MES **경량** 보유」이고 「비용·자산·발주·전용 신뢰성 분석은 범위 밖」이다. **계획 전용 테이블은 EAM 의 구조**다
2. ⭐ **계획과 지시를 가르는 것이 없다** — 3단계 구조에서 「계획」은 보통 **예산·인력 배분**을 담는데 그 둘이 다 범위 밖이다. 남는 것은 **예정일**뿐이고 그것은 지시의 속성이다
3. **하류에 같은 형태가 있다** — `production.work_order` 도 「계획(`production_plan`) → 지시(`work_order`)」로 **둘**이고, 계획은 **수량·납기**를 담는다. **보전에는 그 계획 층에 담을 것이 없다**

## §6. 액션·상태

### §6-1. ⭐ 트리거 셋을 한 화면이 받되 **묶는 규칙이 있다**

도식 ⊕-2 가 셋을 합류시킨다. **그런데 아무렇게나 묶을 수는 없다.**

| 규칙 | 왜 |
| --- | --- |
| **같은 설비끼리만 묶는다** | 지시는 **한 설비에 대한 작업 단위**다. 두 설비를 한 지시로 묶으면 **하나만 끝났을 때 마감이 안 선다** |
| **고장이 하나라도 섞이면 보전유형 = 사후** | 고장은 **이미 일어난 것**이다. 예방으로 분류하면 사후보전 비율이 왜곡된다 |
| **점검 NG + PM 도래는 「예방」으로 묶을 수 있다** | 둘 다 **아직 고장 나지 않았다** |

⭐ **보전유형을 사람이 자유롭게 고르지 않는다** — **트리거 조합이 정한다.** 화면은 결과를 보이고 사유를 적는다(「고장이 섞여 사후로 고정됩니다」 — G-3).

**왜 자유 선택을 막는가** — WF05 S5 Pain 이 「예방보전이 **사후보전에 치우침**」이고, `W-05-08`(비가동 집계)이 **사후/예방 비율**을 본다. **사람이 고르면 그 지표가 의미를 잃는다.**

### §6-2. 한 지시 = **한 설비**

§6-1 의 첫 규칙이 데이터 구조를 정한다 — `설비 FK` 를 헤더에 둔다(라인이 아니라).

⚠ **레이아웃 ③의 「PRS-01 외 1대」는 여러 지시를 한 번에 만드는 것**이다. **화면이 묶어 보이되 저장은 설비마다 한 건**이다. 그 사실을 발행 확인에 적는다 — 「지시 2건이 발행됩니다」.

### §6-3. 트리거 연결은 **다형 참조**다 — A-16 세 번째 적용

세 종류를 가리킨다.

```
trigger_type_code   POINT_CHECK_NG | BREAKDOWN | PM_DUE
trigger_id          점검 이력 / 고장 기록 / (PM 도래는 대상이 없다)
```

⚠ **PM 도래는 가리킬 행이 없다** — 「주기가 됐다」는 **파생 조건**이지 저장된 사건이 아니다(A-15). **그래서 `trigger_id` 가 `NULL` 이 될 수 있다.**

| 유형 | `trigger_id` |
| --- | --- |
| 점검 NG | 점검 이력 헤더 |
| 고장 | 고장 기록 |
| **PM 도래** | ⭐ **`NULL`** — 대신 **어느 항목의 주기가 도래했는지**를 지시 항목이 담는다 |

⭐ **A-10 규칙 2 를 그대로 쓴다** — 「대응표에 없는 유형 코드를 만나면 원본 코드를 그대로 보이고 링크를 만들지 않는다」. **PM 도래는 링크가 없는 것이 정상**이다.

**A-16 적용** — `document_issue_log`(11차 툴 QR) · `attachment`(12차 고장 사진)에 이어 **세 번째**. **계약 대응표에 먼저 등재**한다.

### §6-4. 지시 상태 — **3값**

```
발행 ──▶ 완료      (실적이 마감하면)
  └──▶ 취소
```

⚠ **「진행 중」을 두지 않는다** — **G-16**(「진행 중」을 상태 컬럼으로 두지 않는다)이 12차에 신설됐다. 실적이 하나라도 있으면 진행 중이고, **그것은 실적 존재 여부로 답이 난다.**

⛔ **완료는 이 화면이 시키지 않는다** — `W-05-06`(보전 실적)이 마감할 때 전이된다. **B-13** — 정하는 것은 실적, 반영은 서버.

### §8-3. 이 장에서 나온 공유 계약 후보

#### ⭐ **분류 값을 사람이 고르게 하면 그 값으로 만든 지표가 의미를 잃는다**

§6-1 이 그 사례다 — 보전유형(사후/예방/예지)을 **트리거 조합이 정하게** 했다.

**규칙안**

1. **집계·지표의 축이 되는 분류 값**은 **가능하면 시스템이 정한다**
2. 정할 근거가 데이터에 있으면 **사람에게 고르게 하지 않는다** — 결과를 보이고 **사유를 적는다**(G-3)
3. 사람이 정해야만 하는 값이면 **그 값으로 만든 지표에 「사람이 정한 값」임을 표시**한다

**왜** — WF05 S5 Pain 이 「예방보전이 사후보전에 치우침」이고, **그 비율이 개선 지표**다. 사람이 고르면 **좋아 보이는 쪽으로 기운다.**

**해당 후보**: 보전유형(이 화면) · 불량 원인 추정/확정 · 비가동 사유 대분류 · 재작업/폐기 판정.

#### **다형 참조에 「가리킬 대상이 없는 유형」이 있을 수 있다**

§6-3 의 PM 도래가 그렇다 — **파생 조건이라 저장된 행이 없다.**

**규칙안**: 다형 참조 대응표에 **`{X}_id` 가 `NULL` 인 유형**을 명시한다. A-10 규칙 2(「대응표에 없으면 링크를 만들지 않는다」)와 다르다 — **대응표에 있는데 링크가 없는 것**이다.

⚠ **`{X}_id NOT NULL` 인 기존 16쌍과 형태가 다르다**(A-10 실측: 「16쌍 전부 `bigint NOT NULL`」). **새 다형 참조는 nullable 이 필요할 수 있다.**
