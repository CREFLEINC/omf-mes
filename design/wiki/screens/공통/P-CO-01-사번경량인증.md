# P-CO-01 · 사번 경량 인증

## §0. 요약

- **개요**: POP 진입점 화면. 생산 작업자·현장 관리자가 사번을 입력해 **현재 작업자를 지정**한다. 인증(단말 토큰)은 셸이 이미 통과한 상태이고 이 화면은 권한 판정을 하지 않는다 — 화면명과 달리 **인증이 아니라 귀속**을 하는 화면이다(§5-1).
- **주요 데이터**: `mdm.worker`(사번·이름·소속·재직 상태 — **읽기 전용**), `mdm.worker_qualification`(현재 0건, 미사용 §5-5), `production.work_session_worker`. **아무것도 저장하지 않는다** — 사번은 단말 메모리에만 있고 이후 요청 헤더(`X-Worker-No`)로 실린다.
- **핵심 액션**: 숫자 키패드로 사번 입력 → 확인(존재·재직 확인) → 현재 작업자 지정 또는 교대 → 작업 화면으로 이동.

> 작성일: 2026-08-06 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> POP 22화면의 진입점. ⭐ **화면명이 설계와 어긋난다** — 이 화면은 **인증이 아니라 귀속**이다(§5-1).

## §5. 액션·상태

### §5-1. ⭐ 이 화면은 **인증이 아니다** — 화면명을 고쳐야 한다

「POP 단말인증 설계검토」 **§3.1**이 3층으로 갈랐다:

| 층 | 질문 | 수단 | 성격 |
| --- | --- | --- | --- |
| **인증** | 이 요청이 우리가 설치한 단말에서 왔는가 | **단말 토큰** | **유일한 보안 경계** |
| **기능 구성** | 이 단말에 이 기능을 열어 둘 것인가 | `terminal_process` 8플래그 | 오조작 방지 |
| **귀속** | 누가 한 일로 기록할 것인가 | **사번** | **도용 리스크 수용** |

> 핵심은 **사번을 인증에 쓰지 않는 것**이다. … 사번을 인증으로 승격시키면 REQ-PR-0023이 요구한 「로그인 생략」을 우회로 되살리는 셈이 된다. (§3.1)

**이 화면은 셋째 층만 한다.** 단말은 이 화면이 뜨기 **전에** 이미 토큰으로 인증을 통과했다.

⚠ **「인증」이라는 이름이 실제 위험을 만든다.** 개발자가 화면명을 보고 만들 것들 —

```
⛔ 비밀번호 칸        ⛔ 로그인 실패 횟수 잠금        ⛔ 세션 만료 후 재로그인
```

**셋 다 REQ-PR-0023을 되돌리는 것**이고, 셋 다 **`app_user`에 담을 컬럼이 없다**(§I-3 — `password_hash`·`failed_login_count` 전무). 이름 하나가 없는 기능을 요구하게 만든다.

→ **개칭 후보: 「작업자 지정」.** 화면명은 인벤토리 소관이므로 **우리가 고칠 수 있다** — `[uiux→docs]` 이슈가 아니라 인벤토리 개정 건이다(§8-1).

### §5-2. 사번 형식은 **전부 화면 책임**이다

```
worker_no  app.code_t = varchar(50) CHECK (VALUE <> '')      ← 이것이 전부다
```

**실물 형식은 6자리 숫자**다 — ERP 사원 마스터 `EMP_CODE` 대표값 `900028`, 출문증 실물 신청자 사번 `903677`. 둘 다 `90****` 형태다(설계검토 §3.3 실측).

**A-9 등급을 나눈다**:

| 검증 | 등급 | 화면 동작 |
| --- | :-: | --- |
| 빈 값 아님 | ⓐ **DB가 막는다** | 확인 버튼 비활성 |
| **6자리 숫자** | ⓑ **화면이 막는다** | ⚠ **경고만** — 자릿수를 강제하지 않는다 §아래 |
| 실재·재직 | ⓑ 서버가 막는다 | 조회 실패 시 오류 |

⚠ **6자리를 강제하지 않는 이유**: 실물 786건의 **대표값 2개만** 확인했다. 전수가 아니다. 강제했다가 5자리 사번이 하나라도 있으면 **그 사람이 POP을 못 쓴다.** 자릿수가 다르면 경고를 띄우되 **확인은 눌리게** 한다.

`M-01-02`의 34자리 LOT과 같은 형태다 — **DB에 제약이 없다고 규칙이 없는 게 아니다.** 다만 이쪽은 **확신의 정도가 낮아 등급을 한 단계 낮춘다.**

### §5-3. `app_user_id`는 쓰지 않는다 — **작업자 ≠ 입력자**

`mdm.worker.app_user_id`는 **nullable**이고 「작업자↔입력자 구분」 주석이 달려 있다.

**POP은 작업자만 다룬다.** 사번으로 찾은 `worker_id`가 실적의 귀속 주체이고, 계정 연결 여부와 무관하다. **현장 작업자 대부분은 계정이 없다.**

⚠ **계정이 연결돼 있다고 권한을 주지 않는다.** 그렇게 하면 F-2의 두 축(사용자×기능 / 단말×공정)이 섞인다 — `W-CO-02` §9-5가 경고한 것과 같은 실수다.

### §5-4. 세션이 아니다 — **매 요청에 사번을 싣는다**

설계검토 §3.3:

```http
POST /api/pop/production-results
Authorization: Bearer <단말 토큰>       ← 인증
X-Worker-No: 900028                     ← 귀속. 인증 아님
Idempotency-Key: <UUID>
```

**서버가 사번 세션을 갖지 않는다.** 단말이 「현재 작업자」를 보유하고 매 쓰기 요청에 붙인다.

| | |
| --- | --- |
| 읽기 요청 | **사번 불요** — 단말 토큰만으로 기준정보를 읽는다(설계검토 §3.6) |
| 쓰기 요청 | **사번 필수** — 없으면 서버가 거부 |

**⛔ 그래서 「언제 지우나」가 화면 문제가 된다.** 사번이 남아 있으면 **다음 사람이 그 사번으로 기록된다.**

| 시점 | 확정 유무 | 이 화면의 처리 |
| --- | :-: | --- |
| 교대 시 | — | **「교대」 버튼**으로 사람이 바꾼다 |
| 유휴 시간 경과 | ⛔ **규약 없음** | §8-2 — **지우지 않는다**(작업 중 화면을 떠나는 일이 흔하다) |
| 단말 재시작 | ⛔ 규약 없음 | **지운다** — 메모리 보유이므로 자연히 사라진다 |
| 근무 종료 | ⛔ 규약 없음 | 사람이 「교대」를 눌러야 한다 |

**화면은 현재 사번을 항상 크게 보인다**(§3 우측). 이것이 「내가 아닌 사람으로 기록되는 것」을 막는 **유일한 장치**다 — 도용 리스크를 수용한 설계에서 화면이 할 수 있는 최선이다.

→ **§D 신규 조항 후보** §9-1.

### §5-5. 자격 검증은 **보류다** — 화면이 그것을 지어내지 않는다

설계검토 **§6-④**(2026-07-28 사용자 판단: **기준정보 API 완료 후 재개**):

- 요구는 있다 — **FR-WO-022**(작업 시작 시 「작업자가 해당 공정을 수행할 권한이 있는지」) · **FR-QM-014**(검사자 자격 없으면 입력 제한)
- 데이터도 있다 — `mdm.worker_qualification`(유형·공정·유효기간)
- **⛔ 지금 켜면 현장이 선다** — 고객이 정리해 넣어야 채워지는 데이터이고 **현재 0건**이다. 강제하면 **전원이 무자격**이 된다
- 재개 시 형태 = `app.operation_policy`에 `WORKER_QUALIFICATION_ENFORCEMENT` = `BLOCK`|`WARN`|`OFF`(기본) — QA #9의 3단계 설정형과 같은 꼴

**이 화면은 존재·재직만 확인한다.** 자격 표시도 하지 않는다 — 0건인 데이터를 보이면 「자격 없음」이 전원에게 뜬다.

⚠ **다만 자리는 비워 둔다.** 재개되면 확인 직후에 경고가 붙을 자리다(§3 우측 카드 아래).

### §5-6. 오프라인 — 작업자 목록을 **미리 받아 둔다**

**C-5 판정: 오프라인 허용.** POP은 오프라인 내성이 요구된다(결정 17 · QA #32).

**C-11(선행 데이터 명시)**:

| 미리 받을 것 | 왜 |
| --- | --- |
| **해당 공장 재직 작업자 목록**(`worker_no`·`worker_name`·`department`·`is_active`) | 오프라인에서 사번을 확인하려면 목록이 있어야 한다 |

**C-6(판정값은 캐시 금지)에 걸리지 않는다** — 재직 여부는 **판정이 아니라 표시**다. 오프라인 중 퇴사한 사람의 사번이 통과해도, 그 기록은 복구 시 서버가 받고 **어차피 귀속은 사후 확인 대상**이다(도용 리스크 수용).

⚠ **자격 검증이 재개되면 판정값이 된다** — 그때는 C-6이 걸린다. `worker_qualification.valid_to`는 **캐시하면 안 되는 값**이다. §8-3에 남긴다.

**단말 토큰은 장기라 오프라인 구간을 넘어 산다**(설계검토 §3.5) — 사람 토큰(8시간)이었다면 복구 시점에 outbox가 통째로 401이 났다. **이 화면이 그 이점의 근거다.**

### §5-7. F-1이 걸리지 않는다

8플래그 어디에도 「사번 입력」이 없다. **이 화면은 기능 구성의 대상이 아니다** — 단말에 붙어 있으면 누구나 자기 사번을 넣을 수 있어야 한다.

`W-CO-06` §5-1의 정정과 같은 맥락이다: **매트릭스는 보안 경계가 아니라 기능 구성**이므로, 진입 화면을 막는 데 쓰지 않는다.

## §9. 이 장에서 나온 공유 계약 후보

1. **귀속 정보는 세션이 아니라 「단말이 들고 매 요청에 싣는 값」이다 — 화면이 그것을 항상 보인다** — 서버가 사번 세션을 갖지 않고 `X-Worker-No` 헤더로 매 쓰기에 실린다(설계검토 §3.3). 그래서 **「언제 지우나」가 화면 문제**가 된다. 도용 리스크를 수용한 설계에서 **현재 귀속 대상을 크게 상시 표시하는 것이 유일한 방어**다. POP·모바일 전 화면 공통 (§5-4)
2. **DB 제약이 없고 실물 표본도 적으면 검증 등급을 한 단계 낮춘다** — `worker_no`는 `varchar(50)`에 「빈 문자열 아님」뿐이고 실물은 786건 중 **2건만** 확인됐다. `M-01-02`의 34자리 LOT은 강제했지만 **이쪽은 경고에 그친다.** A-9에 「**표본의 크기가 등급을 정한다**」를 더한다 (§5-2)
3. **오프라인 캐시 판정에서 「판정값」과 「표시값」을 가르는 기준은 「틀렸을 때 무엇이 일어나는가」다** — 재직 여부는 캐시해도 된다(틀려도 사후 확인 대상). 자격 유효기간은 안 된다(틀리면 무자격자가 검사한다). **C-6에 이 판별 기준을 적는다** (§5-6)
