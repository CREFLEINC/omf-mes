# W-CO-04 · 공지·전달 게시/조회

> 작성일: 2026-08-11 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **DR-005 확정**(2026-08-10)으로 동결이 풀린 화면이다.
> ⭐ **받는 쪽이 먼저 정해진 화면**이다 — **G-14** 가 POP 22화면의 진입 동작을 이미 못박았고, **이 화면은 그것을 만드는 쪽**이다.

## §0. 요약

- **개요**: 관리웹에서 관리자가 공지·전달 사항을 작성해 게시하고 전 사용자가 열람하는 목록형 화면. DR-005 확정으로 동결이 풀렸으며, 현장 단말(POP)의 진입 시 미확인 공지 표시 규칙(G-14)이 요구하는 데이터를 이 화면이 만든다.
- **데이터**: 신설 테이블 2종 — 공지(제목·본문·범위·대상·게시기간·확인요구·작성자)와 공지 확인 이력(수신자별 확인 시각·확인 여부). 범위는 전사·작업지시(`production.work_order`) 둘뿐이고, 첨부는 `app.attachment`(다형 참조)를 그대로 쓴다.
- **핵심 액션**: 새 공지 작성(범위·게시기간·확인 요구 토글 설정) → 목록에서 상태(예정/게시/종료, 기간으로 산출)·확인 현황(전사=분자/분모, 작업지시=분자만) 조회 → 확인 요구 공지의 미확인자 보기. 게시 후 본문 수정은 막고 종료일만 당길 수 있으며 삭제는 없다.

## §3. ⭐⭐ 「알림과 같은 모양」은 **같은 테이블이 아니다**

DR-005 가 「**알림(DR-003)과 같은 모양**」이라 적었고 「**알림과 한 번에 설계한다 — 따로 만들면 같은 것을 두 번 만든다**」고 했다. **16차가 알림을 이미 정의했으므로, 이 장은 그 말을 실제로 검증해야 한다.**

### §3-1. 같은 것과 다른 것을 갈랐다

| | **알림**(`W-CO-03`) | **공지**(이 화면) |
| --- | --- | --- |
| 누가 만드나 | ⚙ **이벤트가 만든다** — 서버가 제목·본문 생성 | 👤 **사람이 쓴다** |
| 게시 기간 | ⛔ 없다(발생 시점 하나) | ✅ **있다** — 시작·종료 |
| 확인 강제 | ⛔ 없다 | ✅ **있다** — 「확인 요구」 토글(5-A) |
| 대상 | **다형 참조**(작업지시·설비·LOT…) | **범위 2종**(전사·작업지시) |
| 받는 사람 | 설정으로 전개(`W-CO-11`) | **범위가 정한다** |
| **1 : N 확인 이력** | ✅ | ✅ **같다** |

⭐ **같은 것은 수신 쪽 하나다.** 본체는 **절반이 서로 없는 컬럼**이다.

### §3-2. ⛔ 한 테이블로 합치지 않는다 — **그 절반이 늘 비어 있다**

```
합치면:  게시기간 · 확인요구 · 작성자    → 알림 행에서 항상 NULL
         이벤트코드 · 대상 다형 참조     → 공지 행에서 항상 NULL
```

⚠ **「같은 모양」은 「수신 구조를 같게 만든다」는 뜻으로 읽는다** — 그것이 DR-005 가 걱정한 「같은 것을 두 번 만든다」의 실체다. **두 번 만들면 안 되는 것은 「누가 언제 읽었나」이고, 그것을 같은 형태로 만든다.**

| 무엇 | 어떻게 |
| --- | --- |
| **본체** | ⭐ **나눈다** — 공지 1 · 알림 1 |
| **수신·확인 이력** | ⭐ **같은 컬럼 구성**(대상 사람 · 확인 시각 · 확인 여부) |

→ §9-1

### §3-3. ⭐ 「전사」를 **여기서는 둔다** — B-24 가 묻는 것에 답이 반대로 나온다

**16차 `W-CO-11`(알람 수신자 설정)은 「전사」 포괄 값을 두지 않기로 했다.** 같은 낱말인데 이 화면은 **둔다.** **B-24** 가 정한 물음이 그것을 가른다.

| 물음(B-24) | 알람 수신자 | **공지** |
| --- | :-: | :-: |
| **자동 포함이 의도인가** | ⛔ 아니다 — **명단**이다. 새 계정이 조용히 알람을 받으면 안 된다 | ✅ **그렇다** — 신규 입사자도 **당연히 공지를 봐야 한다** |

⭐ **같은 조항이 두 화면에서 반대 결론을 냈고, 그것이 조항이 제 일을 한 것이다.** ⚠ **「전사」라는 낱말이 같다고 같은 판단이 아니다** — 「겉모습이 같다고 같은 갭이 아니다」와 같은 형태.

| 무엇 | 왜 |
| --- | --- |
| **공지** | 제목·본문·범위·대상·게시기간·확인요구·작성자 |
| **공지 확인 이력** | **수신자별**(5-B) — 사람 · 확인 시각 · **확인 여부** |

⚠ **확인 이력의 컬럼 구성을 알림 수신 이력과 같게 맞춘다**(§3-2). ⛔ **「전사」를 사람으로 전개해 미리 행을 만들지 않는다** — 58명 × 공지 수만큼 행이 선다. **확인한 사람만 행이 생기고, 미확인은 「행이 없음」**이다.

⭐ **그래서 「확인하지 않았다가 이력에 남는다」(5-A)를 「닫은 기록」으로 남긴다** — 확인과 **닫음**을 구분해 적는다. → §5-2

### §5-B-1. ⚠ **분모는 「전사」에서만 셀 수 있다**

| 범위 | 분모 | 보이는 것 |
| --- | --- | :-: |
| **전사** | 활성 사용자 수 | **`42 / 58`** |
| **작업지시** | ⛔ **셀 수 없다** | ⭐ **`3명` — 분자만** |

⛔ **`production.work_order` 에 사람을 배정하는 컬럼이 없다**(`assignee`·`assigned_to` **0건** · 실측). **누가 대상인지 모르므로 분모가 없다.**

⛔ **`—` 로 두지 않는다** — 게시 예정 공지의 `—`(아직 아무도 못 봄)와 **구분이 안 된다**(**G-13** 취지).

### §5-1. 상태는 **컬럼이 아니라 기간이 정한다**

```
작성  ◻   게시 전(게시를 아직 누르지 않았다)
예정  ○   오늘 < 시작일
게시  ●   시작일 ≤ 오늘 ≤ 종료일
종료  ◌   종료일 < 오늘
```

⭐ **A-15**(달력이 만드는 변화를 컬럼에 넣지 않는다)를 그대로 따른다. ⛔ **`status_code` 를 두지 않는다** — 두면 매일 밤 누군가 갱신해야 하고, 안 돌면 종료된 공지가 계속 뜬다. ⚠ 다만 계약은 이 넷을 파생 상태값으로 «표현»한다 — 저장 컬럼이 아니라 서버가 매번 계산해 내려 준다.

⚠ **「내려버리기」는 별개다** — 기간 안이라도 즉시 내리고 싶을 때가 있다. **종료일을 오늘로 당긴다**(⛔ 상태 컬럼을 만들지 않는다 · **A-14**).

### §5-2. ⭐ 「확인」과 「닫음」을 나눈다 — G-14 가 요구한 것

**G-14 규칙 1** 이 「확인 없이 닫고 작업할 수 있다. 다만 **「확인하지 않았다」가 이력에 남는다**」다. **남기려면 닫은 것도 기록해야 한다.**

| 사람이 한 것 | 남는 것 | 확인 현황에서 |
| --- | --- | :-: |
| **확인** 을 눌렀다 | 확인 시각 · 확인=참 | ✅ **확인** |
| **닫기**만 눌렀다 | 확인 시각 · 확인=**거짓** | ⚠ **열람(미확인)** |
| 아무것도 안 했다 | **행이 없다** | ● **미확인** |

⭐ **G-13**(세 모양)이 여기서 그대로 쓰인다 — 셋을 같은 모양으로 그리면 **「봤는데 확인 안 함」과 「아예 안 봄」이 구분되지 않는다.** 그 둘은 관리자가 할 행동이 다르다.

⛔ **확인 요구가 켜진 공지에는 「닫기」가 없다**(5-A 예외) — 두 번째 줄이 생기지 않는다.

### §5-3. 액션·상태

| 액션 | 활성 조건 |
| --- | --- |
| 새 공지 | 작성 권한 |
| 게시 | 작성 중인 공지 · 작성 권한 — ⚠ 게시하면 본문이 잠긴다 |
| 수정 | ⚠ **게시 전에만** — 게시 후 본문 수정은 **이미 확인한 사람이 다른 것을 본 것이 된다**. ⭐ **확인 이력이 무엇에 대한 확인인지 알 수 없어진다** → **G-19**(고칠 수 없는 기록) |
| 종료일 당기기 | 게시 중 |
| 미확인자 보기 | 확인 요구 공지 · 관리자 |

⛔ **삭제를 두지 않는다** — 확인 이력이 딸려 있다(**G-19** — 고칠 수 없는 기록). 내리려면 **종료일**을 쓴다.

### §5-4. 조회 기본값 — **L-3 을 그대로 걸지 않는다**

**L-3**(기간 필터를 필수로 한다)은 **원장·파티션 테이블**의 조항이다(`inventory_transaction`·`audit_event`). **공지는 원장이 아니고 파티션도 아니다.**

⭐ **기본값은 「게시 중」**이다 — 관리자가 묻는 것은 「지금 무엇이 걸려 있나」다. 기간 필터는 **두되 비울 수 있게** 한다(기본 최근 1개월).

⚠ **확인 이력은 다르다** — 사람 × 공지라 커진다. **미확인자 목록은 한 공지를 골랐을 때만** 조회한다.

### §7-1. ⛔ 서식 편집기를 만들지 않는다

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐⭐ **「같은 모양」이라는 확정은 「같은 테이블」로 읽지 않는다**

**무엇이 같은지를 컬럼 단위로 갈라 본다.**

| 갈라 보는 법 | |
| --- | --- |
| 1 | 두 쪽의 컬럼을 **나란히 적는다** |
| 2 | **한쪽에서 늘 NULL 인 컬럼**을 센다 |
| 3 | 그 수가 많으면 **본체는 나누고, 같은 부분만 형태를 맞춘다** |

⚠ **확정의 의도는 「두 번 만들지 말라」이지 「한 테이블에 넣으라」가 아니다.** 두 번 만들면 안 되는 것이 **어느 부분인지**를 찾는 것이 설계다.

— `W-CO-04` §3 · DR-005 · **16차 `W-CO-10` §3-1 과 같은 형태**(뺀 이유를 보면 경계가 나온다)

### 9-2. ⭐ **「했음/안 했음」이 둘이 아니라 셋인 경우 — 「봤는데 안 했음」을 잃지 않는다**

**G-13** 의 **열람 판**이다.

```
확인함        ✅        행이 있다 · 확인=참
열람·미확인   ⚠        행이 있다 · 확인=거짓     ← 이것이 사라지기 쉽다
미확인        ●        행이 없다
```

⚠ **「행이 없음」과 「행이 있는데 거짓」을 같게 그리면** 관리자가 **누구에게 다시 알려야 하는지** 모른다.

— `W-CO-04` §5-2 · G-13 · G-14 규칙 1

### 9-3. **확정이 「다른 화면의 미결이 풀린다」고 적었으면 그 화면을 실제로 고친다**

⚠ **DR-005 가 명시적으로 적은 파급**이다. **적혀 있다고 반영된 것이 아니다** — 차수 마감 시 대상 화면 §8 을 갱신한다.

— DR-005 · **A-13 의 반대 방향**(B-19)
