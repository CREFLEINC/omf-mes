# W-CO-09 · 결재함(승인 요청 목록)

> 작성일: 2026-08-07 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ⭐ **판정 ≠ 결재.** 판정(한도승인의 「허용할 것인가」)은 업무 화면 안이 맞지만, **결재는 대상이 무엇이든 행위가 같다** — 승인·반려·의견뿐이다. 그래서 모아 둔다.
> ⛔ **선행 = `W-06-15`.** 결재선이 비면 상신이 거부되어 이 화면에 아무것도 오지 않는다.
> **이 화면이 업무 화면의 결재 대기 탭을 대체한다** — `W-01-06`·`W-01-12`·`W-03-09` 셋 다 **아직 미발행**이라 재작업이 0이다.

## §0. 요약

- **개요**: 관리웹 상단 전역(도메인 메뉴 아님)에서 결재선에 지정된 승인자가 자신의 결재 대기 요청을 모아 조회·승인·반려·의견을 처리하는 화면. 대상이 무엇이든(폐기 품의·재고조정·신규 P/O 등) 승인·반려·의견이라는 같은 행위만 모으고, **대상 문서의 내용은 그리지 않고** 원 화면 링크로 넘긴다.
- **주요 데이터**: 승인 요청 `app.approval_request`(요청번호·유형·대상 다형참조·상신자·상태·**사유** — 목록에 보일 유일한 업무 값) + 결재 단계 `app.approval_step`(순서·승인자·결재·결재 일시·의견 — 기록 전용, 되돌리기 없음).
- **핵심 액션**: 탭(내 결재 대기/내가 올린 것/전체)·유형·상태·기간 필터 조회 → 요청 선택 → 대상 화면에서 보기(원 화면 링크) → 의견 입력 → **승인**(선택 의견) 또는 **반려**(의견 필수) — 내 차례(앞 단계 전부 승인)일 때만 버튼 활성, 실행 전 확인 다이얼로그 필수.

### §3-1. IA 위치 — **도메인 메뉴가 아니라 전역 진입**

결재함은 **한 도메인의 화면이 아니다.** 자재창고·품질·제품출하의 요청이 한 목록에 섞인다. 도메인 메뉴 아래 두면 **승인자가 매일 어디로 들어가야 하는지**가 흐려진다.

**규칙**: 관리웹 셸 상단에 **대기 건수 배지와 함께 상시 노출**한다. `W-CO-03`(알림센터)이 생기면 알림에서 이 화면으로 온다.

⚠ **대기 건수는 「내가 `approver_id`이고 아직 결재하지 않은 단계」의 수**다(§5-4).

## §5. 액션·상태

### §5-1. ⭐ 이 화면이 소유하는 것과 소유하지 않는 것

| | |
| --- | --- |
| **소유한다** | 요청 목록 · 결재선 진행 표시 · **승인 · 반려 · 의견 작성** |
| **소유하지 않는다** | **대상 문서의 내용**(§5-2) · 결재선 정의(`W-06-15`) · **승인 후의 실제 처리**(§5-7) |

**업무 화면의 결재 대기 탭을 대체한다.**

| 화면 | 있던 것 | 처리 |
| --- | --- | --- |
| `W-01-06` 폐기 품의 | 「결재 대기」 탭 + `[승인] [반려]` | **탭 제거** — 이 화면으로 |
| `W-01-12` 재고조정 | 「승인 대기」 탭 | **탭 제거** — 이 화면으로 |
| `W-03-09` 특채·한도승인 | (미작성) | 처음부터 두지 않는다 |

> **셋 다 착수 통지가 아직 나가지 않았다 — 재작업 0이다.** `W-01-06`·`W-01-12`는 스펙에 정정 주를 단다.

⚠ **`W-01-02`(긴급 IQC 생략 한도승인)는 예외다.** 그 화면은 **판정**이 주 기능이다 — 「한도를 넘는 생략을 허용할 것인가」는 대상(입하 건·LOT·수량)을 보아야 하고 대상 없이는 판단이 성립하지 않는다. **판정은 업무 화면, 결재는 결재함**이라는 경계가 여기서 갈린다.

### §5-2. ⛔ 대상 상세를 그리지 않는다 — **그래서 #68 해소 전에도 성립한다**

`approval_request`는 대상을 **다형 참조**로 가리킨다.

```
target_type_code + target_id      ← 유형 값이 어느 테이블을 가리키는지 규약이 없다 (#68)
```

**대상 내용을 결재함이 그리려 하면 #68이 차단이 된다** — 유형마다 다른 테이블을 조인해야 하고, 유형별 화면 구성이 다 달라진다. 결재함이 업무 화면 20장의 축약본이 된다.

**대신 원 화면을 연다.**

```
┌ 대상 ─────────────────────────┐
│ 기타 출고 · 문서 #4412         │
│ [ 대상 화면에서 보기 ↗ ]       │
│ ⓘ 내용은 원 화면에서 확인합니다│
└────────────────────────────────┘
```

⚠ **유형 → 화면 라우팅을 화면이 지어내지 않는다.** 「`GOODS_ISSUE`는 `W-01-06`」 같은 표를 프런트가 하드코딩하면 유형이 늘 때마다 배포가 필요하고, 무엇보다 **#68이 정할 규약을 우리가 먼저 발명하는 것**이 된다.

**규칙**: **계약이 대상 표시명과 열 경로를 함께 내려 준다.** 규약이 정해지면 서버만 바뀐다 → §9-1.

> **#68(다형 참조 규약)이 해소되면 「대상 요약을 인라인으로」가 가능해진다.** 지금 링크로 두는 것은 **되살리기 잔여**이고 §8에 적는다. ⚠ 이 규약은 **우리 소관**이라 다른 팀을 기다리는 자리가 아니다.

### §5-3. ⛔ 목록에 보일 업무 값이 **사유 하나뿐**이다

`approval_request`의 컬럼을 전수 확인했다. **수량·금액·품목·창고가 하나도 없다.**

```
approval_request_no · approval_type_code · target_type_code · target_id
requested_by · requested_at · status_code · reason      ← 업무 값은 reason 뿐
```

즉 목록에서 **「폐기 품의 12건 · 3,400 EA」 같은 요약을 보일 수 없다.** 승인자가 목록만 보고 우선순위를 정할 수 없다는 뜻이다.

⛔ **되살리기 잔여** — 이 축소의 근거는 물리 모델 결손이었고 A-11 v4.6 이 그 근거를 철회했다. 되살리려면 계약 신설이 따르므로 별건으로 추적한다(변경 통지 판단 포함). 지금은 목록이 **사유를 요약 자리에 놓고** 그것이 요약임을 화면이 말한다. ⚠ 막고 있는 것은 물리 컬럼이 아니라 **다형 참조 규약(#68)** 이고, 그 규약은 **우리가 쓸 것**이다.

⚠ **이것이 A-12를 결정적으로 만든다.** 사유가 요약 노릇을 하므로 **상신 화면이 사유의 형식을 유도해야 한다**. 「폐기」 두 글자만 적힌 요청은 결재함에서 아무 정보가 아니다 → §9-2.

### §5-4. 「내 차례」의 판정 — **순차 결재를 계약이 정한다**

`approval_step`에 `step_no`가 있고 `uq(request, step_no)`가 있다. 그러나 **「앞 단계가 승인돼야 다음이 결재한다」는 제약이 DB에 없다** — `decision_code`는 어느 행에나 먼저 들어갈 수 있다.

**우리는 순차로 본다.** 근거: `approval_route_step`이 순서를 정의하고 있고(`step_no`), 순서를 정의해 놓고 병렬로 도는 것은 정의를 무의미하게 만든다.

| 조건 | 표시 |
| --- | --- |
| 내가 `approver_id` **AND** 내 앞 단계가 전부 승인 **AND** 내 `decision_code`가 null | **● 대기 ← 내 차례** · `[승인] [반려]` **활성** |
| 내가 `approver_id`이지만 앞 단계가 미결 | ○ 대기 — 「앞 단계 결재를 기다리는 중입니다」 · 버튼 **비활성 + 사유**(G-3) |
| 내가 `approver_id`가 아님 | 진행만 보인다. 버튼 없음 |

⚠ **서버가 같은 규칙으로 막지 않으면 화면 설명과 실제가 갈린다** — **계약이 정본**이다(§9-1). 화면 검증만으로는 API를 직접 부르면 뚫린다.

### §5-5. 반려는 의견이 필수다 — **A-12 적용**

`decision_comment`는 **nullable**이다. 그러나 **반려된 요청을 상신자가 고치려면 왜 반려됐는지 알아야 한다.**

**J-6이 이 요구를 강하게 만든다** — 결재는 되돌릴 수 없고 **번복은 새 요청**이다. 반려 사유가 없으면 상신자는 **같은 요청을 그대로 다시 올린다.**

| 행위 | 의견 |
| --- | --- |
| **반려** | ⛔ **필수** — 비우면 저장 거부 |
| 승인 | 선택 |

A-12(남이 읽고 판단할 자유 텍스트는 화면이 필수로 만들고 형식을 유도한다)의 두 번째 사용처다.

### §5-6. 결재는 한 번이다 — **되돌리기를 두지 않는다**

`approval_step`은 기록 전용이다(`created_at`만 · `version_no` 없음). **J-6 그대로다.**

| | |
| --- | --- |
| 화면 | 「수정」·「결재 취소」를 **두지 않는다** |
| 확인 | 승인·반려 전에 `Dialog`로 한 번 확인 — **되돌릴 수 없음을 문구에 담는다** |
| 번복 | **새 요청**이다. 상신자가 대상 화면에서 다시 올린다 |
| 낙관적 잠금 | `approval_request.version_no`로 판정 — **B-1**. 두 승인자가 동시에 누르면 뒤가 409 |

### §5-7. ⭐ 승인은 **문을 열 뿐 실행하지 않는다** — J-5의 결과 구획

J-5는 「승인 화면은 **승인하면 무엇이 일어나는가**를 명시하고, 특히 **일어나지 않는 것**을 적는다」이다.

**결재함의 답은 대상이 무엇이든 같다.**

```
ⓘ 승인하면 요청이 승인 상태가 됩니다.
   실제 처리(전기·출고·조정 반영)는 대상 화면에서 별도로 합니다.
```

**실측 근거** — 01 계약이 이미 그렇게 썼다:

| | |
| --- | --- |
| `W-01-06` §5-5 | 「기타출고 처리 = **승인 완료 후에만**」 |
| 01 계약 | `POST /logistics/goods-issues/{id}:post` — **승인 전이면 400** |

즉 **승인 ≠ 전기**다. 승인은 `:post`의 자물쇠를 풀 뿐이고 **사람이 다시 눌러야** 재고가 움직인다.

> ⚠ **이 문장이 없으면 승인자는 「처리했다」고 믿고 화면을 떠난다.** `W-01-02`가 남긴 실례(한도승인을 해도 ERP G/R 전표는 나가지 않는다)와 같은 종류의 오해다.

## §9. 이 장에서 나온 공유 계약 후보

1. ⭐ **다형 대상은 계약이 「표시명 + 열 경로」를 함께 내려 준다 — 화면이 유형↔화면 표를 갖지 않는다** — `target_type_code`의 값이 어느 테이블·어느 화면을 가리키는지 규약이 없는데(#68), 프런트가 매핑표를 하드코딩하면 **유형이 늘 때마다 배포가 필요하고 우리가 #68의 답을 먼저 발명하는 것**이 된다. 같은 형태로 **순차 결재 규칙**도 계약이 정본이어야 한다 — 화면만 막으면 API 직접 호출로 뚫린다 (§5-2·§5-4)
2. **요약할 컬럼이 없는 목록에서는 필수 자유 텍스트가 요약을 겸한다 — 상신 화면이 형식을 유도한다** — `approval_request`에 업무 값이 `reason` 하나뿐이라 결재함 목록의 정보량이 **전적으로 상신자가 무엇을 적었는가**에 달린다. **A-12를 「형식 유도」까지 강화**한다 — 상신 화면이 자리표시자·최소 길이·예시로 유도하지 않으면 결재함이 무력해진다 (§5-3)
3. ⭐ **승인은 자물쇠를 풀 뿐 실행하지 않는다 — 결재 화면이 그것을 말한다** — 01 계약이 이미 `:post`를 「승인 전이면 400」으로 썼고 `W-01-06` §5-5가 「승인 완료 후에만」이다. 즉 **승인 ≠ 전기**인데, 승인자는 눌렀으니 처리됐다고 믿기 쉽다. **J-5의 「일어나지 않는 것」을 결재함은 유형과 무관하게 한 문장으로 갖는다** (§5-7)
4. **결재·판정은 다른 행위다 — 대상을 보아야 정해지는 것은 업무 화면에 남는다** — 승인·반려·의견은 대상이 무엇이든 같아서 모을 수 있지만, **한도승인처럼 「허용할 것인가」를 대상 값으로 판단하는 것은 업무 화면**이다(`W-01-02`). 이 경계가 없으면 결재함이 업무 화면 20장의 축약본이 된다 (§5-1)
