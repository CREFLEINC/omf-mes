# W-CO-11 · 알람 수신자 설정

> **2026-09-08 사용자 확정:** 계측기 검교정 만료 알림은 이번 버전 이벤트 목록·수신설정·발생·대상 이동에서 제외한다. 다른 이벤트와 사용자 전화번호 기반 Zalo 설정은 유지한다. 기존 알림·계측기 데이터는 삭제하지 않는다.

> 작성일: 2026-08-11 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ⭐ **DR-003 이 신설한 화면**이다 — 3-B 「이벤트 알람을 **누가 받을지 설정하는 화면을 만든다**」(인벤토리 114 → 115).
> ⭐ **05 가 남긴 알람 이벤트 2건이 여기서 자리를 얻는다** — 「설비 고장 발생」·「적정타수 초과」.

## §0. 요약

- **개요**: 관리웹에서 시스템 관리자·운영관리자가 알람 이벤트별로 수신자를 설정하는 화면. 이벤트 목록은 코드 상수라 읽기 전용이고(관리자가 추가 불가), 수신자는 「조직×역할」과 「개인 지정」 2축으로 지정하며 한 이벤트에 둘을 섞을 수 있다.
- **주요 데이터**: 알람 이벤트(코드 상수 — 화면이 만들지 않는다) + 수신자 설정(`[신설]` — 지정 유형·조건부 사업부/역할 또는 사용자·이벤트 단위 Zalo 발송 여부). 참조 대상 `mdm.business_unit`·`app.role`·`app.app_user`는 전부 실재하나, 수신자 설정 자체를 담을 테이블은 아직 없다(§8-1).
- **핵심 액션**: 이벤트 선택 → 조직×역할 또는 개인 수신자 추가/해제 → 「지금 받는 사람」 미리보기로 전개 결과 확인 → 이벤트 단위 Zalo 발송 토글(기본 끔) → 저장.

## §3. ⭐ 수신 대상 지정은 **2축**이다 — DR-003 이 내 권고보다 넓혔다

DR-003 이 이렇게 적었다.

> ⛔ **내 권고(「역할로 정해 둔다」)보다 넓다** — **조직 범위 축과 개인 지정이 더해졌다.** 조직이 여럿이면 「임원급 관리자」만으로는 **어느 사업부의 임원인지 갈리지 않는다.** 그 지적이 맞다.

| 축 | 예 | 참조 |
| --- | --- | --- |
| **조직 범위 × 역할** | 「부품사업부」의 「임원급 관리자」 | `business_unit` × `role` |
| **개인 지정** | 「XXX 상무」 | `app_user` |

⭐ **한 이벤트에 둘을 섞을 수 있다** — 「부품사업부 임원급 **+ 김상무(다른 사업부)**」.

## §5. 필드·규칙

### §5-A. 수신자 설정 — **`[신설]`**

| 라벨(한 / 베) | 출처 | 필수 | 검증·비고 |
| --- | --- | :-: | --- |
| **이벤트 코드** | **코드 상수**(DR-003 3-C) | ✅ | ⛔ **`mdm.code_value` 가 아니다** — `W-CO-03` §5-1 |
| **지정 유형** | **`[신설]`** | ✅ | **조직×역할 / 개인** — §5-2 |
| 사업부 | `mdm.business_unit` | 조건부 | 조직×역할일 때(A-2) |
| 역할 | `app.role` | 조건부 | 동상 |
| 사용자 | `app.app_user` | 조건부 | 개인 지정일 때 |
| **Zalo 발송** | **`[신설]`** boolean | ✅ | 이벤트 단위 · 기본 **끔** §5-5 |

### §5-1. ⭐ 이벤트 목록은 **읽기 전용**이다 — 관리자가 못 만든다

DR-003 3-C: 「확장 기능을 **사용자에게 제공하는 것은 아니고** … **개발 수준에서 추가**한다.」

| | |
| --- | --- |
| ① 목록 | ⛔ **읽기 전용** — **G-10**(읽기 전용 + 사유) · 「목록은 개발이 정합니다」 |
| ② 수신자 | ✅ 편집 |

⛔ **「+ 이벤트 추가」 버튼을 두지 않는다** — 회색으로도 두지 않는다(**G-19** 규칙 4 의 취지 — 있으면 찾는다).

⭐ **05 가 남긴 두 이벤트가 여기서 자리를 얻는다** — 12차 `M-05-02` §8-5(「설비 고장 발생」) · 13차 `W-05-02` §7-2 5번(「적정타수 초과」). **둘 다 목록에 넣는다.**

### §5-2. 지정 유형 — **A-2 조건부 짝**

알림 통보 099(`omf-mes#515`)의 서버 카탈로그는 다음 **6종**으로 확정됐다. 이번 버전 화면은 사용자 확정(2026-09-08)에 따라 검교정 항목을 숨겨 **5종만 선택·설정**한다. 검교정 발생·수신설정·대상 이동을 복원하지 않는다.

| 이벤트 코드 | 뜻·이번 버전 화면 |
| --- | --- |
| `EQUIPMENT_BREAKDOWN_OCCURRED` | 설비 고장 발생 |
| `MOLD_RECOMMENDED_SHOTS_EXCEEDED` | 적정타수 초과 |
| `CALIBRATION_EXPIRY_APPROACHING` | 검교정 만료 임박 — 화면 제외 |
| `PURCHASE_ORDER_CHANGE_RECEIVED` | 발주 변경 수신 |
| `INTEGRATION_FAILED` | 연계 실패 |
| `APPROVAL_ACTION_REQUIRED` | 승인 요청·결재 도착 |

목록 확정은 알림 발생기·외부 Zalo 전송의 구현 완료를 뜻하지 않는다. 설정 저장 성공을 전송 성공으로 안내하지 않는다.

```
조직 × 역할   사업부 FK + 역할 FK    (사용자 FK 는 비운다)
개인 지정     사용자 FK              (사업부·역할은 비운다)
```

⚠ **「사업부 없이 역할만」을 허용하나** — ⛔ **아니다.** DR-003 이 「조직이 여럿이면 **어느 사업부의 임원인지 갈리지 않는다**」로 지적한 그 지점이다. **둘 다 필수**.

⚠ **전사 공통 수신자가 필요하면** — **개인 지정**으로 넣는다. **「전사」 값을 두지 않는다** — 사업부가 늘면 자동으로 포함되는 것이 **의도인지 아닌지 모른다.**

### §5-3. ⭐ 「지금 받는 사람」 미리보기 — **B-17 보완**

14차 **B-17 보완**(해석 규칙을 쓰는 설정 화면은 **결과 미리보기**를 둔다)이 그대로 걸린다.

```
설정   부품사업부 × 설비담당 · 부품사업부 × 임원급 관리자 · 김상무
  ↓ 지금 전개하면
결과   이설비 · 박설비 · 최임원 · 김상무   (4명)
```

| 왜 필요한가 | |
| --- | --- |
| **규칙만 보면 몇 명인지 모른다** | 역할에 사람이 0명일 수 있다 |
| **중복이 안 보인다** | 김상무가 임원급 관리자이기도 하면 **한 번만** 받는다 |
| ⭐ **활성 수신자 0명이면 아무도 안 받는다** | 미리보기 `totalCount=0`으로 판정해 「활성 수신자 없음」을 표시한다. ①의 `(0)` 배지는 **규칙 없음**만 뜻하며 인원 판정에 쓰지 않는다 — **G-12** |

### §5-4. ⚠ 규칙을 바꿔도 **이미 보낸 알림은 안 바뀐다**

`recipients.length`는 **설정 규칙 수**이며 수신 인원이 아니다. 미리보기 `users`는 중복 제거한 활성·비활성 사용자 전체를 표시하고 비활성 표식을 유지한다. `totalCount`만 실제 활성 수신 인원이다. 규칙이 0건인 상태와 규칙은 있지만 활성 수신자가 0명인 상태를 구분해 안내한다. 전화번호 미등록 경고는 활성 실제 수신자 기준 `missingPhoneNumberCount`를 사용한다(통보 101).

`W-CO-03` §5-4 가 「발생 시점에 사람으로 전개해 저장」으로 정했다. **설정 화면이 그 사실을 말한다.**

```
⚠ 규칙이 바뀌어도 이미 보낸 알림의 수신자는 바뀌지 않습니다
```

⭐ **J-9**(결재선을 바꿔도 진행 중인 요청은 옛 결재선으로 끝난다)가 **같은 문구를 요구**했다 — 「결재선 편집 화면이 **「진행 중 N건」을 보이고**, 그것들이 옛 결재선으로 끝난다고 적는다. **이 문장이 없으면 운영자는 「고쳤으니 지금 것부터 바뀐다」고 믿는다**」.

⚠ **알림은 「진행 중」이 없다** — 보낸 것은 끝난 것이다. **그래서 건수는 안 보이고 문장만** 둔다.

### §5-5. Zalo 발송은 **이벤트 단위 · 기본 끔**

DR-003 3-A: Zalo 는 **부가 전달**이고 **실패는 로그만**.

| | |
| --- | --- |
| 단위 | **이벤트별** — 「설비 고장」은 보내고 「P/O 변경 수신」은 안 보낸다 |
| 기본 | ⭐ **끔** — 켜는 것이 명시적 선택이어야 한다(C11 · 인터넷 비보장) |
| 안내 | 「실패해도 **알림센터는 받습니다**」 |

⛔ **수신자별로 켜고 끄지 않는다** — DR-003 이 그렇게 정하지 않았고, **조합이 늘면 아무도 관리 못 한다.**

**사용자 확정(2026-09-08)** — 사용자관리(W-CO-02)의 선택 전화번호 `phoneNumber`가 Zalo 수신처다. 별도 연락처 마스터 없이 사용하며, 미등록 경고는 설정 저장·계정 사용을 막지 않는다.

### §5-6. 액션·상태

저장 토큰은 **단일 이벤트를 지정한 GET**의 `ETag`에서 얻는다. 전체 조회에는 저장 토큰이 없다. 알려진 이벤트의 미설정 구독은 빈 `recipients`, `zaloEnabled=false`, 버전 1 토큰을 반환한다. 첫 PUT 성공은 버전 2이며 이후 PUT에서 `zaloEnabled`를 생략하면 기존 값을 유지한다. 알 수 없는 이벤트의 GET은 빈 목록·토큰 없음이고 PUT은 400이다(통보 100).

이벤트별 규칙 전체와 Zalo 설정은 함께 저장되거나 함께 실패한다. 같은 요청 키·같은 요청을 다시 보내면 기존 결과를 반환하며 같은 키에 다른 내용이면 409다. 충돌 시 해당 이벤트를 다시 조회해 최신 토큰으로 편집한다(통보 103).

| 액션 | 활성 조건 |
| --- | --- |
| 이벤트 선택 | 항상 |
| 조직×역할 추가 · 개인 추가 | 이벤트 선택됨 |
| 해제 | 행 선택 |
| Zalo 토글 | 이벤트 선택됨 |
| 저장 | 변경분 존재 |

**상태**: `초기` → `이벤트 선택됨` → `편집` → `저장 중` → `성공` / `실패` / `충돌(B-1)`

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐ **「무엇으로 받는가」를 정했으면 「어디로 보내는가」도 확인한다**

**2026-09-08 수신처 확정** — 사용자관리의 선택 전화번호를 사용한다. 미등록 경고는 미리보기 인원수로 표시한다.

**규칙안**: 외부 전달 수단을 확정하는 결정은 **수신처(주소)가 어디 있는지**를 함께 확인한다.

| 수단 | 수신처 | 실재 |
| --- | --- | :-: |
| 알림센터 | `app_user` 자체 | ✅ |
| 이메일 | `app_user.email` | ✅ |
| **Zalo** | 사용자관리 `phoneNumber` | ✅ 2026-09-08 설계 신설 |

⚠ **결정이 틀린 것이 아니다** — **한 층 더 내려가 보지 않은 것**이고, **B-19**(「이미 있는 것을 쓴다」는 단계별로 확인)의 **수신처 판**이다.

### 9-2. **「전사」 같은 포괄 값을 두지 않는다**

수신자 조직 축에 **「전사」를 두지 않고** 개인 지정으로 넣기로 했다.

**규칙안**: 범위 지정에 **포괄 값**(전사·전체·ALL)을 둘 때는 **「나중에 늘어나는 것이 자동으로 포함되는 것이 의도인가」**를 먼저 묻는다.

| | 포괄 값 | 개별 지정 |
| --- | --- | --- |
| 사업부가 하나 늘면 | ⭐ **자동 포함** — 의도인지 모른다 | 안 바뀐다 |
| 감사 | 「누가 받았나」가 시점마다 다르다 | 설정이 곧 답 |

⚠ **`app.operation_policy` 의 범위 축은 반대다** — 거기는 **비면 전체**가 의도다(B-22 · 「더 좁은 것이 이긴다」). **성격이 다르므로 규칙도 다르다** — 정책은 **기본값**을 두는 것이고, 수신자는 **명단**이다.
