## §0. 요약

- **개요**: 관리웹에서 경영진·생산관리자가 로그인 직후 첫 화면으로 보는 통합 대시보드. 기준 축은 날짜·공장 둘뿐이며(§5-1) KPI 카드 5장(생산량·양품률·성능가동률·시간가동률·미처리 알람)과 일일 생산실적 추이, 미처리 알람, 진행 중 작업지시를 한 화면에서 넓게 보여 준다. 좁혀 보려면 각 카드에서 소유 화면으로 드릴다운한다.
- **주요 데이터**: `production.production_result`(생산량 5종) · `planning.routing_operation.standard_cycle_time_sec`·`standard_yield_rate` · `production.work_session`(실제 가동시간) · `mdm.WorkCalendar`+`WorkCalendarDay`+`WorkCalendarApplication`(계획 조업시간 분모 — 되살림 2026-08-30)를 다룬다. 양품률·성능가동률·시간가동률 세 항에 더해 OEE(곱)도 보인다(§3-4).
- **핵심 액션**: 카드 클릭 시 소유 화면으로 드릴다운(기준 날짜·공장 전달) · 알람 항목 클릭 시 알림센터(`W-CO-03`) 이동 · 「자세히」로 일일 생산실적 조회 · 수동 갱신. 위젯 편집·배치 저장은 만들지 않는다(§5-5).

## §3. ✅ 14차가 넘긴 OEE — **되살렸다(2026-08-30)**

14차 `W-05-08` §5-1 이 이렇게 넘겼다.

> ⚠ **OEE 를 낼 수 없다는 뜻이 아니다** — **통합 대시보드(`W-CO-05`)처럼 세 도메인을 함께 보는 자리**가 그것을 맡는 것이 맞다.

### §3-1. 14차의 이유는 이 화면에서 해소된다

14차가 못 그린 이유는 「**소유가 셋으로 갈린다**」였다(시간가동률=05 · 성능가동률=02 · 양품률=03). **이 화면은 셋을 다 보인다.**

### §3-2. ✅ 시간가동률의 분모 — `WorkCalendar`로 되살렸다(정정 2026-08-30)

```
시간가동률 = 실제 가동시간 ÷ 계획 조업시간
```

계획 조업시간은 `WorkCalendarDay.dayTypeCode`(`WORKING`·`HOLIDAY`·`PARTIAL`) + `startTime`/`endTime`에서 구한다. 어느 공장·설비 그룹이 어느 캘린더를 따르는지는 `WorkCalendarApplication`이 정한다(결정 03 「계획 비가동 = WorkCalendar 계층형」).

⚠ **이전 버전은 계약을 확인하지 않고 「테이블이 없다」로 적었다** — `mdm-기준정보.json`에 `WorkCalendar`·`WorkCalendarDay`·`WorkCalendarApplication`이 이미 있었다(A-13이 경고한 실패 형태).

### §3-3. `ALLOW_PRODUCTION_ON_HOLIDAYS` 정책의 판정 근거가 섰다

```sql
-- SQL 3359, mdm.code_group('OPERATION_POLICY') 시드
('ALLOW_PRODUCTION_ON_HOLIDAYS',  '휴일 생산 허용',  100),
```

「휴일에 생산을 허용할 것인가」의 판정 근거(어느 날이 휴일인가)가 `WorkCalendarDay.dayTypeCode=HOLIDAY`로 선다 — F-3(판정 근거 컬럼의 실재) 충족.

### §3-4. 결론 — **네 항을 나란히 보인다, OEE 포함**

| | 그리나 | 이름 |
| --- | :-: | --- |
| **양품률** | ✅ | 재료 완비(1634~1638) |
| **성능가동률** | ✅ | `standard_cycle_time_sec`(648) |
| **시간가동률** | ✅ **캘린더 기준** | `WorkCalendarDay` 되살림 — 캐비어트 문구 제거 |
| **OEE(곱)** | ✅ **되살림**(2026-08-30) | 양품률×성능가동률×시간가동률 |

L-14(집계는 낼 수 있는 것만 내고 이름을 빌리지 않는다)를 그대로 따른다 — 이제 넷 다 낼 수 있다.

## §5. 필드·규칙

### §5-1. 기준 축은 **둘뿐**이다 — 날짜 · 공장

⛔ **필터를 늘리지 않는다.** 대시보드는 **좁히는 화면이 아니라 넓게 보는 화면**이다. 좁히려면 **드릴다운**으로 각 도메인 화면에 간다.

⚠ **공장 선택지는 사용자의 귀속 범위로 제한**된다(**D-5** — 현재 귀속을 셸 헤더가 상시 보인다).

### §5-2. 지표 6장 — **출처를 적는다**

| 지표 | 분자 | 분모 | 소유 화면 |
| --- | --- | --- | --- |
| 생산량 | `good_qty` 합(1634) | — | `W-02-*` |
| **양품률** | `good_qty` | 수량 5종 합(1634~1638) | **03** `W-03-05` |
| **성능가동률** | `standard_cycle_time_sec` × 생산량(648) | 실제 가동시간(`work_session`) | **02** |
| **시간가동률** | 실제 가동시간 | ✅ **계획 조업시간**(`WorkCalendarDay`) | **05** `W-05-08` |
| **OEE** | 양품률 × 성능가동률 × 시간가동률 | — | 이 화면(파생) |
| 미처리 알람 | 알림(16차 `W-CO-03`) 미확인 건수 | — | `W-CO-03` |

⭐ **각 카드가 자기 소유 화면으로 드릴다운한다** — 값이 이상하면 **누구에게 물어야 하는지가 화면에 있다.**

### §5-3. ✅ 시간가동률 캐비어트를 걷었다 — 정정(2026-08-30)

분모(계획 조업시간)가 `WorkCalendarDay`로 섰으므로 「교대 시간 기준」 캐비어트 문구는 더 필요 없다. 카드 아래 본문 표시 규칙(G-20 취지 — 「빼지도 숨기지도 않는다」) 자체는 유효한 원칙으로 남겨 두되, 이 지표에는 적용하지 않는다.

### §5-4. 집계 기준 시각 — **「언제 것인가」를 항상 적는다**

```
기준 2026-08-11 14:32 · 5분마다 갱신
```

⚠ **C-17**(오프라인 집계는 「내가 아는 만큼」으로 줄이고 그 범위를 말한다)의 **온라인 판**이다. 대시보드는 오프라인이 아니지만 **집계 시점이 화면과 어긋난다** — 같은 이유로 범위를 말한다.

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐⭐ **곱으로 만든 지표는 가장 약한 항의 신뢰도를 물려받는다 — 항을 나란히 보인다**

**L-14**(이름을 빌리지 않는다)의 **합성 지표 판**이다.

| 물음 | |
| :-: | --- |
| 1 | **항 중 하나라도 분모·분자에 결손이 있는가** |
| 2 | 있으면 ⛔ **곱을 만들지 않는다** — 항을 나란히 보인다 |
| 3 | 없으면 ✅ 곱을 만들되 **항을 함께 보인다** |

✅ **2026-08-30 되살림 — 결손이 사라져 규칙 3이 적용된다.** 시간가동률의 분모(`WorkCalendarDay`)가 서면서 넷(양품률·성능가동률·시간가동률·OEE)을 함께 보인다. **항은 계속 나란히 둔다** — 곱만 내고 항을 숨기지 않는다(OEE 값이 낮을 때 「어느 항이 낮은가」를 바로 봐야 한다).

— `W-CO-05` §3 · L-14 · 14차 `W-05-08` §5-1

### 9-2. ⭐ **확정이 있는데 계약이 놓쳤으면, 화면이 그것을 발견하는 자리다**(정정 2026-08-30)

```
✓설계확정 결정 03    계획 비가동 = WorkCalendar 계층형
계약(mdm-기준정보.json)  WorkCalendar·WorkCalendarDay·WorkCalendarApplication  이미 있었다
정책 시드            ALLOW_PRODUCTION_ON_HOLIDAYS  있다   ← 이제 판정 근거와 함께
```

⚠ **셋이 서로 어긋나 있고, 그것이 드러난 곳은 집계를 그리는 화면**이다. **B-19**(「이미 있는 것을 쓴다」를 단계별로 확인)의 **상류 판** — **확정이 있다고 자리가 있는 것이 아니다.**

— `W-CO-05` §3-2·§3-3 · F-3 · B-19

### 9-3. ⭐ **DS 판정 절차 ① 을 보완한다 — 한 층 아래를 본다**

```
① git ls-tree --name-only <SHA> src/components/          ← 지금까지
② git ls-tree -r --name-only <SHA> src/components/<유사>/  ← 더한다
```

⭐ **`Gauge` 가 `Progress/` 안에 있었다.** 절차 ① 만 돌리면 「**없다**」가 나오고, **`d` 유형(새 원시 요소)으로 잘못 올라간다.**

⚠ **A-13 이 코드·컬럼에 대해 말한 것을 DS 에도 같게 적용한다.**

— `W-CO-05` §7-2 · A-13 · DS 판정 절차

### 9-4. **범용 정책 테이블의 코드 목록은 「새로 만드는 것」이 아니라 「이어붙이는 것」이다**(B-22 보완)

⭐ **`OPERATION_POLICY` 코드 그룹 시드가 물리 모델에 이미 있다** — **14건**(SQL 3341~3366). **B-22 규칙 1**(정책 코드 목록을 계약이 갖는다)은 **목록이 없다는 뜻이 아니었고**, 우리가 더할 코드는 **그 14건 뒤에 붙는다.**

| 확인할 것 | |
| :-: | --- |
| 1 | **이미 있는 코드로 되는가** — 예: 사후입력 허용시간은 `LATE_ENTRY_ALLOWED_HOURS` 가 이미 있다 |
| 2 | 없으면 **이름을 시드 관례에 맞춘다**(대문자·스네이크·단위를 이름에) |
| 3 | ⚠ **값 형·범위 축**은 계약이 계속 갖는다(B-22 규칙 1·4는 유효) |

⚠ **B-22 를 세울 때 시드의 실재를 확인하지 않았다** — **B-19 를 세운 우리가 B-19 를 안 돌린 자리**다.

— `W-CO-05` §3-3 · B-22 · B-19
