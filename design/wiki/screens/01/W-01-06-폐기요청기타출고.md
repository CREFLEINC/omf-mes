> MES 에서 실제 품의서 승인을 득했는지 관심갖지 않는다. **사용자에게 맡긴다.**
> 그럼 MES 에서는 **작업자가 요청하고 승인하는 방식**으로 정리한다.」
>

> ⭐ **2026-08-13 DR-010** — ① 폐기 대상은 **2단**이다(전표 → 라인). 01 계약에 라인 전역 목록 경로가 없고, **입고일·원천이 필요해** 재고 축으로 바꾸지 않는다. `W-01-05` 와 같은 구성.
>
> ⭐ **골격은 그대로다** — 요청 → 승인 → 기타출고 3단과 「승인 완료 후에만 출고」 잠금은
> **MES 내부 승인 기준**으로 그대로 선다. 아래 본문의 「품의」는 이 기준으로 읽는다.

## §0. 요약

- **개요**: 관리웹에서 물류담당(+품질담당, 품의 승인권자)이 불량창고 입고분 중 폐기 대상을 골라 폐기 요청(내부 승인)을 올리고, 승인 완료 후에만 기타출고(폐기)를 처리하는 화면. 요청 → 승인 → 기타출고 3단 골격에 「승인 완료 후에만 출고」 잠금이 선다.
- **주요 데이터**: 승인 요청(`app.approval_request`)·결재 단계(`app.approval_step`)·결재선 정의(`app.approval_route`/`approval_route_step`)와 기타출고 전표(`logistics.goods_issue`)를 다루며, 폐기 대상은 불량창고 입고 전표(1단) → 그 라인(2단)의 2단 구조로 고른다.
- **핵심 액션**: 불량창고 입고 전표 조회 → 라인(LOT) 다중 선택 → 사유 입력 → 폐기 거래처 선택(또는 자체 폐기 체크) → 승인 요청 → (승인 완료 후) 기타출고 처리.

## §5. 액션·상태

### §5-1. §J 2차 검증 — **6조항 중 4건이 그대로 선다**

2차 `W-01-02`(긴급 IQC 생략 한도승인)에서 세운 §J를 두 번째 화면으로 검증한다.

| 조항 | 이 화면에서 | 판정 |
| :-: | --- | :-: |
| **J-1** 4테이블 한 벌 | 정의(`route`+`route_step`) / 실행(`request`+`step`) 그대로 | ✅ |
| **J-2** 「한도」=`min_value`/`max_value` | ⚠ **무엇의 값인지 미정** §5-3 | ⚠ |
| **J-3** 요청 시점에 승인자를 **사람으로 확정** | ⛔ **#72 회신과 부딪친다** §5-2 | ⛔ |
| **J-4** 사유 필수 | `reason text NOT NULL` — **DB가 강제** | ✅ |
| **J-5** 「일어나지 않는 것」 명시 | 폐기 승인은 **재고를 차감하지 않는다** §5-5 | ✅ |
| **J-6** 결재 번복 불가 | `approval_step`이 기록 전용 | ✅ |

**J-2·J-3 둘이 남는다.**

### §5-2. ⛔ J-3 ↔ #72 회신이 부딪친다

**J-3**(2차 신설): 「**요청 시점에 승인자를 사람으로 확정**」 — 근거는 `approval_step.approver_id bigint **NOT NULL** REFERENCES app_user`.

**#72 회신**(사용자 확정): 「승인 주체는 **담당부서 관리자**」 · 「명확히 고정된 것이 아니라 **관리자의 권한 설정으로 처리**」

**권한 설정으로 처리한다 = `approver_type_code`가 `ROLE` 또는 `DEPARTMENT`다.** 그런데 **`approval_step`은 사람만 받는다.**

```
approval_route_step.approver_type_code = 'DEPARTMENT'
    → approver_department_id = 품질부
        → 품질부에 관리자가 3명이면?
            → approval_step.approver_id 에 누구를 넣나  ⛔
```

**해법 3안**

| 안 | 방법 | 판단 |
| :-: | --- | --- |
| **① 상신 시 한 사람으로 확정** | 규칙(최상위 1명·순번 등)으로 골라 `approver_id`에 넣는다 | ⚠ **그 사람이 부재하면 결재가 멈춘다** |
| **② 후보 전원에게 단계 생성** | `step_no`를 나눠 여러 행 | ⛔ **`UNIQUE(요청, step_no)`라 같은 단계에 둘을 못 넣는다** |
| **③ 대리 결재로 우회** | ①로 넣되 대리자가 처리 | ⛔ **대리 컬럼이 없다** |

**①을 권고**하되 **부재 시 경로가 필요**하다. `approval_step`에 행을 **바꿔 넣는 것**(승인자 교체)은 기록 전용이라 감사상 문제가 된다.

⚠ **J-3을 세운 근거가 「데이터가 사람만 받는다」였는데, 업무 확정은 「역할로 처리한다」다.** **둘 중 하나가 바뀌어야 한다.**

→ **§I 신규 후보** §9-1 · **#72에 코멘트**로 회신 반영 결과를 알린다 §8-1.

### §5-3. J-2 「한도」가 무엇의 값인지 정해지지 않았다

```
approval_route.min_value  numeric(20,6)
approval_route.max_value  numeric(20,6)
ck_approval_route_range   CHECK (max >= min)
```

주석: 「업무유형·사업부·**수량(금액)** 구간별 승인단계 설정」

**「수량(금액)」이라 둘 다 가능하다.** 2차 `W-01-02`(한도승인)에서는 **수량**으로 읽었는데, **폐기는 금액이 자연스럽다**(폐기 손실이 회계 사안이므로).

| 화면 | 무엇의 구간인가 |
| --- | --- |
| `W-01-02` 긴급 IQC 생략 한도승인 | **수량** — 몇 개까지 검사 없이 |
| **`W-01-06` 폐기 품의** | ⚠ **금액?** — 얼마어치까지 부서장 전결 |

**금액이면 산정 근거가 필요한데 MES에 단가가 없다.** `mdm.item`에 원가·단가 컬럼이 **없다**(실측).

**수량 기준으로 운용**하고 금액 구간은 쓰지 않는다. ⏳ **회신 대기**가 맞는 자리다 — 금액 구간은 **회신 E-4(폐기 계정)로 사람이 정할 사안**이지 모델 결손이 아니다(A-11 v4.6 과 무관) → §8-2.

⚠ **`approval_type_code`별로 의미가 갈릴 수 있다** — 같은 컬럼이 화면마다 다른 것을 재면 결재선 설정이 혼란스럽다. **계약이 유형별 의미를 표로 갖는다** → §9-2.

| **`trace.lot`** | ⚠ **여러 LOT을 한 품의로** 올리면 하나만 가리킨다 |
| **`logistics.goods_issue`** *(권고)* | 출고 전표를 **먼저 만들고**(미확정 상태) 그것을 승인 대상으로 |
| 별도 폐기 헤더 | ⛔ 없다. ⭐ **폐기는 출고 «유형»이 아니라 기타출고의 «사유»다**(✓확정 2026-08-31 사용자) — `issueTypeCode=OTHER` + `reasonCode=폐기`. 설계 메모의 「출고 유형 확장」안은 채택하지 않았다 |

**②를 권고**한다 — 설계 메모의 「**품의 참조**」가 `goods_issue`에 붙는다는 뜻으로 읽히고, 여러 LOT을 라인으로 담을 수 있다.

⭐ **화면은 「이 출고가 어느 승인으로 나왔나」를 보인다** *(2026-08-18 사용자 확정)*. 승인 쪽에서 출고를 가리키는 방향은 있으나 **되짚는 길이 없으면 「승인 없이 나간 폐기 출고」를 화면에서 찾을 수 없어 통제가 성립하지 않는다.**

✅ **계약이 이미 내려준다** — `GoodsIssue.approvalRequestId`(비어 있으면 승인을 타지 않은 출고).
📨 **모델에는 그 컬럼이 아직 없다**(실측 — `reason_code`·`replacement_expected`·`remarks`뿐). **남의 작업이고 우리를 막지 않는다** — 계약은 화면 요구대로 쓰고 기다리지 않는다(§8-3).

⛔ **「품의 참조」와 「계정」은 다르다 — 그 둘은 없어야 정상이다**(DR-009). 설계 메모의 「사유·품의 참조·계정 속성 통합」 중 **살아남는 것은 사유와 «승인 요청 참조»**다.

→ **§I-29** *(v2.9 — 절반 철회 · 승인 참조만 남음)*.

### §5-5. J-5 — 폐기 승인은 **재고를 차감하지 않는다**

**J-5**(2차 신설): 승인 시 「**일어나지 않는 것**」을 명시한다.

| 승인 시 | |
| --- | :-: |
| 재고 차감 | ⛔ **일어나지 않는다** |
| 기타출고 전표 확정 | ⛔ 일어나지 않는다 |
| **승인 상태 전이만** | ✅ |

**출고는 별도 액션**이다(§3 ③). REQ-PR-0028이 「승인 **후** 기타 출고」라고 순서를 못박았다.

**화면 문구**:

```
승인되었습니다. 재고는 아직 차감되지 않았습니다 — 「기타출고 처리」를 진행하세요.
```

⚠ **승인 후 출고를 안 하면 어떻게 되나** — 승인만 되고 방치된 품의가 남는다. **촉구 수단이 없다** → §8-4.

### §5-6. ⭐ 폐기 **거래처** — 자체 폐기면 비운다 *(DR-013 확정 2026-08-13)*

> ⛔ **2026-08-16 시점 정정 — 두 컨트롤은 《③ 승인 후》가 아니라 《① 요청 작성》에 둔다.**
>
> 초판은 §3 레이아웃에서 자체 폐기 체크와 거래처 선택을 **《③ 승인 후 — 기타출고》 구획**에 그렸다. **그 시점에는 고른 값을 보낼 계약 통로가 없다** — 도착지 짝은 **전표 생성 본문에서만** 실리고 전표 헤더를 고치는 경로가 없다(프론트 실측 · client#128).
>
> **요청 작성 시점 결정으로 확정**했다(2026-08-16). 두 컨트롤이 발의 폼으로 가고, 「체크 없이 거래처도 안 고르면 막는다」 잠금은 **「승인 요청」 버튼으로 앞당겨진다.** ⭐ **체크박스의 존재 이유는 그대로 성립한다** — 「아직 안 골랐다」와 「자체 폐기라 없다」의 구분은 시점이 앞당겨져도 필요하다.
>
> 《③ 승인 후》 구획은 그 전표의 도착지를 **읽어 보인다**(자체 폐기 / 거래처 이름).

⛔ **구 「폐기 계정」 절을 폐기했다** — DR-009 확정으로 **회계 계정은 MES 밖**이고 화면에서 필드를 뺐다. 대신 **「누가 가져갔나」는 MES 가 적는다.**

| | MES | ERP |
| --- | :-: | :-: |
| 무엇을 몇 개 폐기했나 | ✅ | |
| ⭐ **누가 가져갔나**(폐기 거래처) | ✅ | |
| **회계 계정** | ⛔ | ✅ |

```
☐ 자체 폐기(외부 업체 없음)
폐기 거래처  [ 선택 ▾ ]   ← 체크하면 비활성 · 값 비움
```

**저장 형태** — `goods_issue.destination_type_code`+`destination_id` 짝이다(A-10).

| 경우 | 저장 |
| --- | --- |
| 폐기 업체가 가져간다 | `destinationTypeCode = DISPOSAL_SITE` · `destinationId` → `mdm.partner` |
| ⭐ **자체 폐기** | **둘 다 비운다** — 나가서 없어지는 물건에 도착지는 없다 |

⭐ **체크박스를 두는 이유** — 짝을 nullable 로만 두면 **「아직 안 골랐다」와 「자체 폐기라 없다」가 같은 모양**이 된다. 체크 없이 비우면 저장을 막는다.

**거래처 목록** — `GET /mdm/partners?roleTypeCode=<폐기처리>`. ⭐ **역할은 `mdm.partner_role`** 이 가른다(테이블 실재 · 컬럼 신설 0). 거래처 본체는 **ERP 수신**이고 역할만 MES 가 관리한다(`W-06-06` 「거래처 역할」 탭).

⚠ **`roleTypeCode` 값 목록 미확정** — G-2 대로 「선택지 준비 중」으로 두고, 값이 오면 필터가 산다(`#145`). «(정합주: 2026-09-01 — 이 문장은 옛 상태 기록이다)»

✅ **확정돼 있다**(2026-08-16 업무 확정 · 2026-09-01 재실측) — `roleTypeCode` 는 `CUSTOMER`·`SUPPLIER`·`SUBCONTRACTOR`·`DISPOSAL`·`OTHER` 다섯이고 폐기 업체는 `DISPOSAL` 이다. `#145` 대상이 아니다.

⭐ **계약은 이미 선택으로 완화했다** — 물리 모델이 아직 `NOT NULL` 이지만 **모델이 계약을 따라온다**(2026-08-10 확정 작업 방식). 모델 변경 요청 = **`#147`**.

## §9. 이 장에서 나온 공유 계약 후보

1. **⛔ J-3을 세운 근거(데이터가 사람만 받는다)와 업무 확정(역할로 처리한다)이 부딪친다** — #72 회신이 「담당부서 관리자·권한 설정으로 처리」인데 `approval_step.approver_id`는 `app_user` FK다. **결재선 정의는 역할·부서를 받는데 실행은 사람만 받는** 비대칭이다. **J-3을 「상신 시 규칙으로 한 사람을 고른다」로 고쳐 쓰고, 부재 시 경로를 함께 정한다** (§5-2)
2. **§J-2의 「한도」가 무엇의 값인지는 승인 유형마다 다르다** — `W-01-02`는 수량, 폐기는 금액이 자연스럽다. **한 컬럼이 화면마다 다른 것을 재면 결재선 설정이 혼란스럽다** — 계약이 **유형별 의미 표**를 갖는다 (§5-3)
3. **설계 메모가 「통합 방향」을 말한 것은 확정이 아니라 방향이다 — 그래도 대조한다** — 「출고 트랜잭션 유형 확장 + 사유·품의 참조·계정 속성 통합」에서 **사유만 착지**했다. **방향성 문구도 §I 대조 대상**으로 삼되 확정과 무게를 달리 적는다 (§5-4)
