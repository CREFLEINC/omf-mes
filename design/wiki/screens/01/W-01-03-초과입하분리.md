# W-01-03 · 초과 입하 분리

> 작성일: 2026-08-04 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 입하 검증 [수량 초과] 분기의 착지점. 이 장에서 **한 도착을 두 입하로 쪼개는 처리**를 다룬다.

## §0. 요약

- **개요**: 관리웹에서 물류(창고)담당이 입하 검증 중 발주 수량을 초과한 한 건의 도착을 정량분(P/O 귀속)·초과분(P/O 비귀속) 두 건의 입하로 분리 등록하는 화면. 좌측 원 도착(읽기 전용) + 우측 분리 결과 미리보기(정량분·초과분)로 구성된 좌우 2단 레이아웃.
- **데이터**: 입하(`logistics.inbound_receipt`)·입하 라인(`logistics.inbound_receipt_line`)을 정량분·초과분 각 1건씩 총 2건 생성하며, 구매발주 라인(`logistics.purchase_order_line`)의 `ck_po_line_received` 제약이 분리가 필요한 근거다.
- **핵심 액션**: 초과분 수량 조정 → 예외 유형·사유 입력 → **분리 등록**(입하 2건을 한 트랜잭션으로 생성) / 취소. 등록 후에는 [공급사 반품]·[입고 진행] 두 갈래를 안내만 하고 종료한다(자동 분기 없음).

## §3. 레이아웃 (관리웹 — 구조 기술)

좌우 2단. 좌측이 원 도착, 우측이 분리 결과 미리보기.

```
┌ PageHeader  자재창고 > 초과 입하 분리                                     ┐
├───────────────────────────────────────────────────────────────────────────┤
│ ⚠ 발주 수량을 초과했습니다. 두 건의 입하로 나눠 등록합니다.               │
├──────────────────────────────┬────────────────────────────────────────────┤
│ 《원 도착》 (읽기 전용)      │ 《분리 결과》 (미리보기)                   │
│                              │                                            │
│  입하번호  IB-…-002          │  ① 정량분  ─────────────────  P/O 귀속    │
│  공급사    (주)…             │     PO-…-3 · ABC-123                       │
│  품목      ABC-123           │     500 EA        ← 발주 500 + 허용 0     │
│                              │                                            │
│  발주      500 EA            │  ② 초과분  ─────────────  ⚠ P/O 비귀속    │
│  초과 허용   0 EA            │     ABC-123                                │
│  ────────────────            │     [   100  ] EA                          │
│  실도착    600 EA            │     예외 유형 [ ▾              ]           │
│  초과      100 EA            │     사유      [                ]           │
│                              │                                            │
│                              │  ⚠ 초과분은 P/O에 붙일 수 없습니다.        │
│                              │     발주(500) + 허용(0) 을 넘기 때문입니다.│
├──────────────────────────────┴────────────────────────────────────────────┤
│                        [ 취소 ]        [ 분리 등록 ]                      │
└───────────────────────────────────────────────────────────────────────────┘
```

**우측 하단의 설명은 장식이 아니다.** 사용자가 「왜 그냥 600으로 못 받는가」를 묻게 되므로, **DB 제약이 막는다는 사실을 화면이 말해 준다**(§5-2).

## §4. 필드

### §4-A. 분리 결과 — `logistics.inbound_receipt` **2건**

두 건 모두 `M-01-01`의 헤더 구조를 그대로 쓴다(§4-A 참조). 이 화면이 정하는 것은 **어느 값이 갈리는가**다.

| 항목 | ① 정량분 | ② 초과분 |
| --- | --- | --- |
| `inbound_receipt_no` | MES 채번 | **별도 채번** — 노트B 「입하 번호 2건」 |
| `supplier_id` · `plant_id` | 원 도착에서 승계 | 동일 |
| `receipt_datetime` | 원 도착 시각 | 동일 |
| `delivery_note_no` | 원 명세서 | 동일 |
| **`exception_type_code`** | — (정상) | ⚠ **설정한다** — P/O 비귀속은 「P/O 없는 예외입하」다 §5-3 |
| `exception_reason` | — | 입력 |
| `approval_request_id` | — | ⚠ 승인 절차 미정 §8-2 |

### §4-B. 분리 결과 — `logistics.inbound_receipt_line`

| 항목 | ① 정량분 라인 | ② 초과분 라인 |
| --- | --- | --- |
| `purchase_order_line_id` | **P/O 라인 FK** | ⚠ **NULL** — P/O 비귀속 |
| `asn_line_id` | 입하예정 라인 | NULL 가능 |
| `item_id` | 동일 | 동일 |
| **`received_qty`** | 발주 + 초과허용 이내 | **초과분 수량** (> 0) |
| `supplier_lot_no` · `supplier_lot_missing` | 원 도착 승계 | 동일 |
| `inspection_required` | 원 판정 승계 | ⚠ **초과분도 검사 대상인가** §8-3 |

**⚠ 이 제약이 분리의 이유다**

```
ck_po_line_received:  received_qty <= ordered_qty + tolerance_over_qty
```

초과분을 원 P/O 라인에 더하면 **DB가 저장을 거부한다.** 그래서 붙일 수 없고, `purchase_order_line_id`를 비운 **별도 입하**로 만든다. 확정(QA #36)이 요구한 「P/O 비귀속」이 데이터 제약과 정확히 맞물린다.

### §5-2. 왜 그냥 600으로 받지 못하는가 — 화면이 설명한다

`ck_po_line_received`는 **DB 레벨의 물리 제약**이라 우회할 수 없다. 사용자에게는 「시스템이 이상하다」로 보이므로 화면이 이유를 적는다.

```
발주 500 + 초과 허용 0 = 최대 500 EA 까지 이 P/O에 받을 수 있습니다.
초과분 100 EA 는 별도 입하로 등록됩니다.
```

**초과 허용치를 늘리면 되지 않는가** — 되지만 그것은 P/O 수정이고, **「P/O = ERP 발행 정본 · MES에서 수정 없음」**(REQ-PR-0024)이 막는다. 그래서 분리가 유일한 경로다.

### §5-3. 초과분은 「예외입하」다

`M-01-01` §5-5에서 확인한 무발주 예외입하 구조를 **초과분이 그대로 쓴다.**

```
exception_type_code    -- [L] P/O 없는 예외입하 유형
exception_reason
approval_request_id    -- [L] 예외입하 승인
```

초과분은 정의상 **P/O 없는 입하**이므로 같은 필드가 맞다. 별도 메커니즘을 만들지 않는다.

> ⚠ 다만 `exception_type_code` 값 목록에 「초과분」이 있는지는 미확정이다 — 무발주와 초과분은 **원인이 다르다.** §8-2.

### §5-4. 두 건이 한 트랜잭션이다

노트B가 「KEY = **입하 번호 2건**」이라 못박는다. 둘 중 하나만 저장되면 안 된다.

| 부분 실패 | 결과 |
| --- | --- |
| 정량분만 저장 | 초과분 100 EA가 **어디에도 없다** — 물리적으로는 창고에 있는데 시스템에 없다 |
| 초과분만 저장 | 발주분이 미입고로 남아 P/O가 닫히지 않는다 |

**둘 다 실패다.** `W-01-10`이 세울 트랜잭션 원자성 조항의 두 번째 사례다(§9-1).

### §5-5. 등록 후 — 분기는 이 화면 밖

**상태: 입하 완료**(노트B). 그다음 분기(OR 225:5707)는 담당자 판단이다.

| 분기 | 후속 |
| --- | --- |
| [공급사 반품] | 01-S-I → `W-01-05` |
| [입고 진행] | **`W-01-11` 신규 P/O 등록** → 초과분을 그 P/O에 귀속 |

화면은 등록 후 **두 갈래를 안내**하고 종료한다. 자동으로 넘기지 않는다 — 반품이냐 입고냐는 상거래 판단이다.

## §9. 이 장에서 나온 공유 계약 후보

1. **한 화면이 여러 레코드를 만들면 전부 한 트랜잭션이다** — 입하 2건이 부분 저장되면 양쪽 다 사고다. `M-01-01` §9-1에 이은 두 번째 사례 (§5-4)
2. **DB 제약이 사용자 행동을 막을 때는 그 이유를 화면이 설명한다** — 「저장할 수 없습니다」만으로는 사용자가 우회를 시도한다. 무엇이 왜 막는지 적는다 (§5-2)
3. **같은 성격의 예외는 같은 필드를 쓴다** — 초과분·무발주가 모두 「P/O 없는 입하」이므로 `exception_type_code`를 공유한다. 화면마다 새 메커니즘을 만들지 않는다 (§5-3)
4. **다음 행동이 상거래 판단이면 자동으로 넘기지 않는다** — 반품이냐 입고냐는 시스템이 정할 수 없다. 두 갈래를 안내하고 멈춘다 (§5-5)
