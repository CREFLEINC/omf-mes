# M-01-05 · 적치·입고 완료

> 작성일: 2026-08-05 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **처음 재고를 움직이는 화면**이다. 오프라인 멱등키가 어디에 붙는지가 여기서 정해지고, **`UNIQUE(idempotency_key, business_date)`가 날짜 경계에서 뚫린다**는 것이 드러난다.

## §0. 요약

- **개요**: 모바일(360×720dp · 스캐너 일체형 PDA) 스캔형 화면. 물류(창고)담당이 적치 지시를 소화해 위치 → LOT 순으로 스캔하고 적치를 완료 처리한다(확정).
- **주요 데이터**: `logistics.putaway_task`(20열) · `logistics.putaway_rule`(13열) · `mdm.location`(위치 제약 읽기) · `inventory.inventory_transaction`(오프라인 멱등키).
- **핵심 액션**: 위치 스캔(비관리 창고는 위치 선택) → LOT 스캔 → 건별 적치 저장 → 적치 완료(일괄).

### §3-1. 스캔이 두 단계다

`M-01-02`(파일럿)는 스캔 필드가 **하나**였는데 이 화면은 **위치 → LOT 순서로 둘**이다. 순서를 바꾸면 프로세스가 무너진다(위치를 먼저 검증해야 「오적치」를 막는다 — 예외 E-4 ②).

**포커스는 ①이 통과해야 ②로 넘어간다.** ②에서 오류가 나면 ②에 머무르고, 위치를 바꾸려면 명시적으로 ①로 돌아간다.

## §5. 액션·상태

### §5-1. B-9 — 이 화면은 입고 전표 없이 성립하지 않는다

```
putaway_task.goods_receipt_line_id   bigint NOT NULL
```

적치 지시는 **입고 라인에서 파생**된다. 입고 전표를 만드는 화면은 **`W-01-10` 정상품 입하 처리**다.

| 선행 | 이 화면 |
| --- | --- |
| `W-01-10`이 `goods_receipt` + `_line` 생성 | ✅ 지시가 생긴다 |
| 입고 전표 없음 | ⛔ **적치할 것이 없다** — 빈 목록 |

**B-9 그대로다**(`P-02-10`에서 세운 조항). `P-02-10`과 다른 점은 **선행 화면이 이미 존재한다**는 것. 의존이 끊기지 않았다.

⚠ **지시를 누가 만드는가는 별개다.** `W-01-10`이 입고 전표를 만들 때 적치 지시까지 생성하는지, 별도 배치인지가 정해지지 않았다 — §8-1.

### §5-2. 권장 위치는 **모델이 화면 설계보다 앞서 있다**

REQ-OA-0001은 「적치 Location **안내**」만 요구했는데 물리 모델은 그보다 많다:

```
putaway_task.recommended_location_id      권장 위치
putaway_task.applied_putaway_rule_id      그 권장을 낸 규칙 역참조
putaway_rule (품목 × 창고 × 위치 · capacity_qty · priority_no)
```

**8건 나왔던 「모델이 앞섬」이 있다.** 화면은 권장 위치를 **보이기만 하는 것이 아니라 「왜 이 위치인가」를 함께 보일 수 있다.**

```
권장  A-01-03      ⓘ 규칙: ABC-123 · 1공장 자재창고 (우선순위 10)
```

### §5-2-1. ⛔ **권장 위치는 강제한다** — 2026-08-06 사용자 확정 *(구 「경고만」 폐기)*

> **정정 기록.** v0.1은 「권장을 강제하지 않는다 · 다르면 **경고만**(A-9 ⓑ)」로 적고 §8-2에 「강제 여부 미결 — **경고로 시작**」을 남겼다. 근거는 ① REQ-OA-0001이 「적치 Location **안내**」만 요구 ② DB가 막지 않는다 였다.
>
> **②는 근거가 아니었다** — 서식 §5가 「**DB 제약이 없다고 규칙이 없는 게 아니다**」라고 이미 못박았다. 그리고 **프로세스는 처음부터 강제 쪽이었다** — `01-S-D`(임시 위치 적재)가 **별도 사이드 플로우**로 있고 태스크에 **「적치 사유 입력」**이 들어 있다. 「권장 외 적치 = 예외 경로 + 사유 기록」이 이미 설계돼 있었는데 화면이 경고로 물러난 것이다.

**규칙 — 세 갈래로 갈린다.**

| 창고 상태 | 품목 규칙 | 화면 동작 |
| --- | --- | --- |
| **위치 관리 함** | **권장 있음** | ⛔ **그 위치만 허용.** 다른 위치 스캔은 **차단**(A-9 ⓐ) |
| **위치 관리 함** | **권장 없음** | ⚠ **확인 후 통과** — 「관리 위치가 없는 품목입니다. 여기 적치합니까?」 → 예 → **적치 위치 저장** |
| **위치 관리 안 함** | — | 위치 스캔 자체가 없다(§5-3). 대표 Location |

**둘째 줄이 핵심이다.** 규칙이 없다고 막으면 **미등록 품목이 적치 자체를 못 해 현장이 선다.** 통과시키되 **어디에 놓았는지는 반드시 남긴다** — `actual_location_id`가 `ck_putaway_completed`로 이미 강제된다.

```
LOT 스캔  →  위치 코드 스캔
              ├ 권장과 일치        →  그대로 저장
              ├ 권장과 다름        →  ⛔ 「권장 위치 A-01-03 이 아닙니다」 · 저장 불가
              │                        임시 적치가 필요하면 → M-01-07 경로
              └ 권장 없음(규칙 미등록) →  ⚠ 「관리 위치가 없는 품목입니다. 여기 적치합니까?」
                                          예 → 저장 (위치는 남는다)
```

**임시 적치가 발생하면 관리자에게 알린다** — ⛔ **승인이 아니다**(2026-08-06 사용자 확정 — 승인은 두지 않는다). ⚠ **지금은 알림을 보낼 곳이 없다**(알림 엔티티 전 파일 **0건** · §I-30 · **#90**). **A-11 적용** — 알림은 엔티티 확정 후이고, 그때까지는 **임시 적치 건이 목록에 남는 것으로 물러난다.**

⚠ **「위치 관리 함/안 함」을 무엇으로 판정하나가 이 규칙의 전제**가 됐다 — §5-3.

### §5-3. `ck_putaway_completed` — 완료하려면 실제 위치가 반드시 있다

```
CONSTRAINT ck_putaway_completed
    CHECK (completed_at IS NULL OR actual_location_id IS NOT NULL)
```

**⚠ 「위치 관리 안 함」 분기와 부딪친다.** 프로세스 S5 태스크 4는 위치를 관리하지 않는 창고를 상정하는데, 이 CHECK는 **완료에 위치를 요구**한다.

`M-01-04` §5-2에서 정리한 대로 **「선택적」은 대표 Location으로 흡수하는 방식**이므로 모순은 아니다. 다만 화면 동작이 갈린다:

| 창고 | ① 위치 스캔 | ② LOT 스캔 |
| --- | --- | --- |
| **위치 관리함** | 스캔·검증 | 스캔 |
| **위치 관리 안 함** | **건너뜀** — 대표 Location 자동 | 스캔 → 위치 **직접 선택**(219:4556) |

프로세스의 「직접 선택」은 **관리 안 하는 창고에서도 위치를 고른다**는 뜻이라 완전히 건너뛰지는 않는다. 화면은 **스캔 대신 선택**으로 바꾼다.

→ **무엇으로 이 분기를 판정하나** — **`warehouse.management_level_code`로 확정한다** *(2026-08-06)*.

```
mdm.warehouse.management_level_code   app.code_t NOT NULL
   논리 모델링 §262 —  「창고 · 구역 · 랙 · 셀 관리수준」
```

**창고 단위로 위치 관리를 끄고 켜는 축이 이미 있다.** 「창고」 수준이면 위치를 관리하지 않고, 「구역·랙·셀」이면 관리한다.

> **이 축이 있어야 두 가지가 구분된다** *(2026-08-06 사용자 지적)* — **「위치 관리가 애초에 필요 없는 창고」**와 **「관리는 하는데 이 품목만 규칙이 없는 것」**. 앞은 §5-3의 셋째 줄, 뒤는 §5-2-1의 둘째 줄이고 **화면 동작이 다르다.**

⚠ **값 목록이 여전히 미정**이다(§8-3). 그런데 **등급이 올라갔다** — 전에는 표시 분기였고 지금은 **차단 판정의 근거**다. `W-06-06` 소관 · **#145**.

**편집 화면은 `W-06-07`**(창고·Location 마스터)이 이미 이 필드를 갖고 있다(§4 실측).

### §5-4. ⛔ 오프라인 멱등키가 **날짜 경계에서 뚫린다**

물리 모델 전체에서 `idempotency_key`는 **4곳뿐**(실측):

| 테이블 | 제약 |
| --- | --- |
| `inventory.inventory_transaction` | **`UNIQUE (idempotency_key, business_date)`** |
| `production.material_consumption` | `NOT NULL UNIQUE` |
| `production.production_result` | `NOT NULL UNIQUE` |
| `quality.inspection_result` | `NOT NULL UNIQUE` |

**`putaway_task`에는 없다.** 적치 완료는 재고를 움직이므로 `inventory_transaction`을 거치고, **멱등키는 거기에 붙는다.** 재고 화면 전부(적치·출고·이동·실사 조정)가 같은 경로다.

**그런데 하나만 UNIQUE 범위가 다르다.**

```
inventory_transaction:  UNIQUE (idempotency_key, business_date)   ← 날짜가 키의 일부
나머지 셋:              UNIQUE (idempotency_key)                   ← 전역
```

**시나리오**:

```
08-04 23:50   오프라인 적치 완료 → 로컬 큐 (키 K)
08-05 00:10   연결 복구 → 전송
              서버가 business_date 를 수신일(08-05)로 잡으면
              → (K, 08-05) 로 저장.
              혹시 08-04 자에 (K, 08-04) 가 이미 있었다면 둘 다 통과 = 이중 전기
```

C-1은 「**재전송 시 서버가 중복을 흡수한다**」를 전제하는데, **`business_date`가 클라이언트가 정한 값이 아니면 흡수가 성립하지 않는다.**

**규칙**: 클라이언트가 `occurred_at`과 함께 **`business_date`도 보낸다**(발생일 기준). 서버가 수신 시각으로 다시 잡으면 안 된다.

→ **§C 신규 조항 후보** §9-1. ⚠ 이것은 **`W-01-04` 재고실사**·**`M-01-10` 재고이동**에도 그대로 걸린다.

### §5-5. 분산 적치 — 한 지시가 여러 위치로 나뉜다

> `putaway_task` 주석(실측): 「분산적치(FR-IM-022)는 같은 입고 Line에 **여러 task 행**으로 표현한다」

**행을 나누는 주체가 정해지지 않았다.** 작업자가 「120개 중 80개는 A-01-03, 40개는 B-02-01」이라고 판단하는 순간이 이 화면인데, **화면이 지시 행을 쪼갤 수 있는지**가 미정이다.

두 안:

1. **화면이 분할** — 「분할 적치」 버튼 → 수량 입력 → 지시 2행
2. **분할은 관리웹** — 이 화면은 받은 행을 그대로 소화

**1을 권고**한다 — 분산이 필요한 것을 아는 사람이 현장에 있다. 다만 **`task_qty`를 화면이 바꾸는 것이 되므로** 지시 무결성 규칙이 필요하다(합이 원 수량과 같아야 한다) — §8-4.

### §5-6. B-1 낙관적 잠금과 오프라인이 부딪친다

`putaway_task.version_no`가 있으므로 A-4에 따라 B-1(`ETag` → `If-Match`)을 구현해야 한다. **그런데 오프라인 큐에 담긴 건은 전송 시점에 `version_no`가 이미 낡았다.**

| | 온라인 | 오프라인 큐 |
| --- | --- | --- |
| `If-Match` | 조회 시 받은 ETag | **몇 시간 전 것** |
| 충돌 시 | 다시 불러오기(G-1) | ⚠ **작업자가 이미 자리를 떴다** |

**규칙**: 오프라인 큐 전송에는 **`If-Match`를 싣지 않는다.** 대신 **멱등키로 중복만 막고**, 서버가 상태 전이 규칙으로 판정한다(이미 완료된 지시면 `400 STATE_LOCKED`, C-2에 따라 **해당 건만** 오류 목록으로).

→ **§9-2.**

## §9. 이 장에서 나온 공유 계약 후보

1. **오프라인 멱등키는 `business_date`까지 클라이언트가 정한다** — `inventory_transaction`만 유일 제약 범위에 날짜가 들어 있어(`UNIQUE(idempotency_key, business_date)`) 날짜 경계에서 재전송이 중복 흡수를 통과한다. **발생일을 함께 보내고 서버가 수신일로 다시 잡지 않는다** (§5-4)
2. **오프라인 큐 전송에는 낙관적 잠금 토큰을 싣지 않는다** — 큐에 담긴 `version_no`는 이미 낡았고 충돌 화면을 보여 줄 사용자가 없다. **멱등키로 중복만 막고 상태 전이는 서버가 판정**하며, 거부는 C-2대로 건별로 되돌린다 (§5-6)
3. **오프라인 작업 화면은 「무엇을 미리 받아 두어야 하는가」를 스펙이 명시한다** — 지시 목록·마스터·검증 규칙이 전부 서버에 있으면 오프라인에서 화면이 성립하지 않는다. C-1은 저장만 다루고 **선행 데이터를 다루지 않는다** (§8-5)
