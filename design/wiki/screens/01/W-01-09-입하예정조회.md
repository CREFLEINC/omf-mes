# W-01-09 · 입하 예정 조회

> 작성일: 2026-08-04 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 입하·검사·입고 흐름의 **첫 화면**. 이 장에서 **ASN(입하예정) 구조와 무발주 도착의 표현**을 다룬다.

## §0. 요약

- **개요**: 관리웹에서 물류(창고)담당·전산(ERP 연계)담당이 입하 예정(ASN) 목록을 조회하는 화면. 상하 2단 레이아웃 — 위가 예정 목록, 아래가 선택 건의 라인이다. **등록·수정은 하지 않는 조회 전용** 화면이다.
- **주요 데이터**: 입하 예정 헤더(`logistics.asn`)·입하 예정 라인(`logistics.asn_line`)을 조회하고, 구매발주(`logistics.purchase_order`·`purchase_order_line`)와 연계해 P/O 변경 이벤트를 인지한다. 무발주 도착은 `asn_line.purchase_order_line_id`가 nullable로 데이터에 표현된다.
- **핵심 액션**: 기간·공급사·상태·품목 조회 → 예정 건 선택 → 하단에 라인(품목·예정수량·P/O 라인·진행률) 표시. 입하 등록(`M-01-01`)·P/O 변경 관리자 확인(`W-02-06`)은 이 화면 소관이 아니다 — 조회·인지까지만 한다.

## §4. 필드

### §4-A. 입하 예정 헤더 `logistics.asn` (조회 전용)

| 라벨 | 출처 컬럼 | 타입 | 필수 | 검증·비고 |
| --- | --- | --- | :-: | --- |
| ASN 번호 | `asn_no` | `business_no_t` | ✅ UNIQUE | 표시 키 |
| 공급사 | `supplier_id` | FK → `mdm.partner` | ✅ | 필터 축 |
| 공장 | `plant_id` | FK → `mdm.plant` | ✅ | 다공장 시 필터 축 |
| **도착 예정일** | `expected_arrival_date` | date | ✅ | **기본 정렬·기간 필터의 축** |
| 명세서 번호 | `delivery_note_no` | varchar(100) | — | 거래명세서 번호. **비어 있을 수 있다** — `M-01-01`에서 촬영·등록 |
| 상태 | `status_code` | `code_t` | ✅ | ⚠ **값 목록 미확정** §8-1 |
| 비고 | `remarks` | text | — | |

> 감사 컬럼 5종과 `version_no`는 표에 넣지 않는다(공유계약 A-4).

### §4-B. 입하 예정 라인 `logistics.asn_line` (조회 전용)

| 라벨 | 출처 컬럼 | 타입 | 필수 | 검증·비고 |
| --- | --- | --- | :-: | --- |
| # | `line_no` | integer > 0 | ✅ | `UNIQUE(asn_id, line_no)` — **표시는 목록 내 위치**(공유계약 A-5 조항 2) |
| 품목 | `item_id` | FK → `mdm.item` | ✅ | |
| 예정수량 | `expected_qty` | `qty_t` > 0 | ✅ | |
| 단위 | `uom_id` | FK → `mdm.uom` | ✅ | |
| **공급사 LOT** | `supplier_lot_no` | varchar(100) | — | **사전부착 경로의 근거**(§재정의 #4) — 공급사가 MES 표준 양식대로 부여한 번호 |
| **P/O 라인** | `purchase_order_line_id` | FK → `purchase_order_line` | — | ⚠ **nullable이다** — §5-2 |

**⚠ `asn_line`에는 감사 컬럼이 `created_at`·`created_by`뿐이다.** `updated_at`·`updated_by`·`version_no`가 없다 — **수정을 전제하지 않은 테이블**이다. 이 화면이 조회 전용인 것과 일치한다(§5-3).

**「진행」 열의 출처** — `asn_line`에 입고 수량 컬럼이 없다. `purchase_order_line.received_qty / ordered_qty`로 계산한다. **P/O 라인이 없는 행(무발주)은 진행률을 계산할 수 없다** — §5-2.

## §5. 액션·상태

### §5-1. 액션

| 액션 | 활성 조건 | 비고 |
| --- | --- | --- |
| 조회 | 항상 | 기간·공급사·상태·품목 필터 |
| 예정 건 선택 | 항상 | 하단 라인 표시 |
| 정렬 | 항상 | 도착예정일 기본 오름차순 · **화면 내 처리** |
| 입하 등록으로 이동 | 선택 건 있음 | **없음 — 소관 이동.** 등록은 `M-01-01`(모바일) |
| P/O 변경 확인 | 변경 이벤트 있음 | **없음 — 소관 이동.** `W-02-06` |

### §5-2. ⚠ `purchase_order_line_id`가 nullable이라는 것의 뜻

**무발주 도착이 데이터에 설계돼 있다.** 예외 E-1 ①「무발주 도착 인지(예정표 부재→누락 위험)」가 이 nullable로 표현된다.

화면은 **P/O 라인이 없는 행을 눈에 띄게 표시한다**(위 레이아웃의 `⚠ (무발주)`). 그러지 않으면 「예정표에 있으니 발주된 것」으로 오인한다 — 예외 E-1이 지목한 바로 그 누락 위험이다.

> 다만 **무발주 건이 애초에 ASN으로 들어오는가**는 미결이다 — 발주 없이 도착한 것을 누가 언제 ASN에 등록하는지 프로세스가 정하지 않았다. §8-2.

### §5-3. 이 화면은 쓰지 않는다

`05` S1 규칙이 못박는다 — **「P/O = ERP 발행 정본 · MES 수신 · MES에서 수정 없음」**(✅REQ-PR-0024 · D10 해소).

따라서 이 화면에 **등록·수정·삭제가 없다.** 조회와 필터뿐이다. `asn_line`에 `version_no`가 없는 것이 이 규칙과 일치한다.

> ⚠ **예외가 하나 있다** — `W-01-11`(신규 P/O 등록)이 초과 입하분에 대해 **사후 P/O를 등록**한다. 그 화면이 이 규칙과 어떻게 양립하는지는 `W-01-11` §5-2에서 다룬다.

## §9. 이 장에서 나온 공유 계약 후보

1. **nullable FK가 업무 예외를 표현하는 경우, 화면은 그 빈칸을 눈에 띄게 표시한다** — 빈칸을 조용히 두면 「정상」으로 읽힌다. `asn_line.purchase_order_line_id`(무발주)가 첫 사례 (§5-2)
2. **감사 컬럼 구성이 그 테이블의 편집 가능성을 알려 준다** — `created_at`·`created_by`만 있고 `updated_*`·`version_no`가 없으면 **수정을 전제하지 않은 테이블**이다. 화면을 조회 전용으로 설계하는 근거가 된다 (§4-B)
3. **저장 값이 아닌 계산 값(진행률·잔여)은 출처를 명시한다** — 어느 테이블의 어느 컬럼으로 계산하는지 적지 않으면 화면마다 다르게 구현된다 (§3 · §4-B)
