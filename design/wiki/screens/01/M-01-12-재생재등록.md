# M-01-12 · 재생재 등록

> 작성일: 2026-08-11 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **DR-006 확정**(2026-08-10)으로 **마지막 동결이 풀린** 화면이다.
> ⭐ **모델에 자리가 있는데 「쓰지 않는다」로 확정된 첫 화면**이다 — 계보 컬럼이 실재하는데 DR-006 이 추적을 불필요로 정했다.

## §0. 요약

- **개요**: 모바일(Capacitor Android PDA) 입력형 화면. 생산(현장)담당이 재생재 발생 시 스캔 우선으로 자재를 선택하고 신재/재생재 구분(기본 재생재)·수량·창고/위치를 입력해 등록한다. DR-006 확정에 따라 재생재는 신규 자재 LOT으로 발행되며, 원료 계보(어디서 어떻게 만들어졌는지)는 추적하지 않되 등록 기록(감사 추적)은 남긴다.
- **주요 데이터**: 기존 품목(`itemId`) · 새 LOT별 `mesCategoryCode`(신재/재생재 구분) · `trace.lot`(`initial_qty` CHECK>0 · `lot_no` 서버 발번 · `source_type_code`/`source_id` · `parent_lot_id`는 비움) · `inventory.inventory_balance`.
- **핵심 액션**: 자재 스캔·검색 → 구분(신재/재생재) 선택 → 수량·창고·위치 입력 → 등록(서버가 새 LOT 번호를 발번).

## §3. ⭐⭐ 이 화면의 설계 지점은 **「무엇을 안 쓰는가」**다

DR-006 은 **두 가지를 동시에 확정**했다 — 「구분한다」와 「추적하지 않는다」.

### §3-1. 계보 자리가 **실재하는데 채우지 않는다**

**A-13 4단을 돌린 결과, 계보를 적을 곳이 두 군데 있다.**

| 자리 | 실재 | 이 화면 |
| --- | :-: | :-: |
| `trace.lot.parent_lot_id`(SQL 1054) | ✅ 있다 | ⛔ **비운다** |
| `trace.lot_relation`(SQL 2078) | ✅ 있다 — 「**계보의 원천**」(1055 주석) | ⛔ **행을 만들지 않는다** |

⛔ **「자리가 있으니 채운다」로 가지 않는다.** DR-006 이 「**어디서 어떻게 만들어진 건지 추적하는 건 불필요**」로 확정했고, 그 확정은 **문답 31번의 「내부 이력 완전 기록」을 명시적으로 뒤집은 것**이다.

⚠ **채우면 손해가 있다** — 계보가 **일부만 채워진 상태**가 된다. 재생재 LOT 에만 부모가 있고 다른 경로에는 없으면, **계보 조회 화면이 「추적 가능」으로 오해**한다. **비워 두는 것이 「추적하지 않는다」를 정직하게 표현**한다. → §9-1

### §3-2. 기존 품목을 재사용하고 새 LOT별로 구분한다

2026-09-08 사용자 승인: 기존 품목을 선택하고 MES 신재/재생재 구분으로 새 자재 LOT을 등록한다. 현장에서 새 품목 마스터를 만들지 않으며 신재·재생재를 위해 별도 `itemId`를 만들지 않는다.

구분은 새 LOT과 등록 기록에 남긴다. 기존 품목의 구분을 재생재로 덮어쓰면 그 품목의 신재까지 바뀌므로 그렇게 하지 않는다. 원료 계보를 추적하지 않는 결정은 그대로다.

### §3-3. 품목 키와 실물 키를 구분한다

`itemId`는 자재 종류, `lotId`는 실물 묶음, 재고잔액 식별자는 재고 줄을 가리킨다. 동일 품목의 신재·재생재는 LOT별 구분으로 구별하며 품목을 두 행으로 나누거나 복합 유일 조건을 새로 요구하지 않는다. 과거 `Item.mesCategoryCode`는 호환용으로 보존하지만 새 LOT 구분의 정본이 아니다.

기존 LOT의 개별 구분을 알 수 없으면 `Lot.mesCategoryCode`는 null이다. 품목 분류를 자동 복사하거나 기존 데이터를 일괄 변경하지 않는다. 재고 조회는 LOT 구분으로 먼저 필터한 뒤 기존 집계를 적용한다. 필터를 지정하면 구분 미상 LOT은 제외하고, 지정하지 않으면 기존처럼 포함한다.

### §5-B. 새 LOT에 기록하는 구분

| 필드 | 무엇 | 값 |
| --- | --- | --- |
| `mesCategoryCode` | 새 LOT과 등록 기록의 MES 구분 | `NEW`(신재) / `RECYCLED`(재생재) · 화면 기본 및 요청 생략 기본 `RECYCLED`(재생재) |

기존 `itemId`를 그대로 사용한다. ERP 품목코드와 기존 품목 정보는 변경하지 않으며 MES 구분은 ERP에 송신하지 않는다. `RecycleEntry` 응답은 등록된 구분을 반드시 제공한다. 이동·투입·출고에서 LOT 구분을 품목의 현재 값으로 덮어쓰지 않는다.

등록할 때마다 서버가 새 LOT 번호를 만들며 같은 품목·창고·위치라도 기존 LOT에 합치지 않는다.
새 LOT은 `INSPECTION_PENDING`(검사 대기) 상태와 수입검사 보류로 시작한다. 재생재 원천
`RECYCLE_ENTRY`(재생재 등록)는 입하 원천 전용 IQC 생략 요청의 대상이 아니므로 급행 우회가 없다.
품질에서 모든 열린 보류를 해제하고 마지막 보류의 합격 해제로 `NORMAL`(정상) 전이가 완료된 뒤에만
자재 투입할 수 있다. 부분 해제이거나 다른 열린 보류가 남아 LOT 상태 전이가 생략되면 계속 투입할 수 없다. 서버의 현재
미지원이 이 필수 품질 보호를 없애는 근거가 되지 않는다.

### §5-1. LOT 번호는 **서버가 발번한다** — 화면이 미리 보이지 않는다

`trace.lot.lot_no` 는 `uq_lot UNIQUE (plant_id, lot_no)`(SQL 1063)다. **번호를 클라이언트가 정하면 오프라인 두 단말이 같은 번호를 만든다**(**C-2**).

⭐ **그래서 화면이 「번호는 저장 후 정해집니다」라고 먼저 말한다**(**C-7** 두 등급 피드백 · **G-19** 저장 전에 파급을 말한다).

### §5-2. `source_type_code` — **다형 참조에 값이 하나 는다**

`trace.lot.source_type_code`·`source_id`(SQL 1051·1052)는 **FK 가 없는 다형 참조**다. 재생재 LOT 은 **입고 전표도 작업지시도 아니다.**

⭐ **A-16** 이 정한 대로 **계약이 먼저 값을 갖는다** — `RECYCLE_ENTRY`(이 화면의 등록 건). → §9-2

⚠ **`source_id` 가 `NOT NULL`**(1052)이다. **가리킬 행이 있어야 한다** — 등록 건 자체를 남길 자리가 필요하다. ⛔ **그런데 「추적 불필요」다.** 모순처럼 보이나 아니다:

| 무엇 | 필요한가 |
| --- | :-: |
| **누가 언제 얼마를 등록했나** | ✅ **필요** — 감사 추적이고, `NOT NULL` 이 요구한다 |
| **이 재생재가 어느 LOT 에서 나왔나** | ⛔ **불필요** — DR-006 이 뺀 것 |

⭐ **DR-006 이 뺀 것은 「원료 계보」이지 「등록 기록」이 아니다.** → §9-3

### §5-2-a. 등록과 수불 원장은 함께 기록한다

재생재 등록 한 번은 **등록 기록·새 LOT·수불 원장 1건과 라인 1건·재고 증가**를 한 트랜잭션으로 처리한다. 하나라도 실패하면 전체를 반영하지 않는다. 같은 요청을 같은 `Idempotency-Key`(중복 방지 키)로 다시 보내면 기존 등록 결과를 돌려주며 LOT·원장·재고를 중복 생성하거나 증가시키지 않는다.

원장의 `sourceDocumentTypeCode`는 `RECYCLE_ENTRY`(재생재 등록), `sourceDocumentId`는 해당 등록 결과의 `recycleEntryId`다. 새 LOT의 원천도 같은 등록 건을 가리킨다. 원장과 라인의 영업일은 등록 `businessDate`, 라인의 품목·LOT·수량·단위는 등록한 품목·새 LOT·등록 수량·품목 기본 단위다. 출발 창고·위치는 없으며 도착 창고·위치는 등록한 창고·위치다. 수불 이력에는 이 재고 증가가 남는다.

**원료 계보를 추적하지 않는다는 결정은 유지한다.** 원재료 LOT과의 계보 연결 없이 재생재 등록으로 생긴 재고의 증가 이력만 기록한다. 별도 입고 전표나 재생재 등록 취소 동작은 추가하지 않는다. 근거: 재생재 원장 검토 요청 `omf-mes#512`의 사용자 승인.

### §5-3. 액션·상태

| 액션 | 활성 조건 |
| --- | --- |
| 스캔 | 항상 |
| 등록 | 자재·구분·수량(>0)·창고·위치 **전부** |

**상태**: `초기` → `자재 선택됨` → `입력 중` → `저장 중` → **`성공(LOT 번호 표시)`** / `대기(오프라인 큐)` / `실패`

⛔ **연속 등록으로 만들지 않는다** — 분쇄는 **독립 사건**(DR-006 6-C)이고 한 번에 한 건이다. 저장 성공 후 **입력을 비우고 같은 화면에 머문다**. 창고·위치도 비워 다음 등록에서 재선택한다. 기본 구분 `RECYCLED`(재생재)는 별개로 유지한다.

창고·위치가 명시 선택되고 사용 가능함을 확인해야 등록할 수 있다.

| 선택 품목이 없거나 사용 불가 | 등록을 막고 유효한 기존 품목을 다시 선택하도록 안내한다. 별도 재생재 품목 생성은 요구하지 않는다 |
| 등록 직후 자재 투입 | 검사 대기·보류 상태이므로 투입 거부. IQC 생략으로 우회하지 않고 품질 합격 해제 뒤 재시도한다 |
| 저장 뒤 비고 확인 | 현재 응답·조회 지원 없음 안내. 입력값을 응답에 있다고 가정하거나 별도 조회 API를 만들지 않는다 |
| 통신 실패 | **큐에 담는다** — 아래 |

### §6-1. ⭐ 오프라인 — **담기지만 번호는 나중에 온다**

**C-14**(판정값을 쓰는가)로 판정한다.

| 물음 | 답 |
| --- | :-: |
| 이 화면이 **판정값**을 쓰는가 | ⛔ 아니다 — 재고를 **늘리기만** 한다 |
| 내가 만든 것이 **남의 판정 근거**인가(**C-15**) | ⚠ **그렇다** — 재고가 는다 |

⭐ **C-18**(생산자와 소비자는 오프라인 정책이 반대다)의 사례다. **등록은 허용하되 「아직 서버가 모른다」를 말한다.**

```
⏳ 등록 대기 1건 — 연결되면 전송됩니다
   LOT 번호는 전송 후 정해집니다
```

⛔ **오프라인 상태에서 라벨을 인쇄할 수 없다** — **K-5**(라벨은 서버가 그린다) + 번호가 아직 없다. **화면이 그렇게 말한다**(**G-20** — 버려지는 것이 아니라 **미뤄지는 것**임을 구분해 적는다).

이미 큐에 담긴 요청의 창고·위치·원 귀속·키·영업일은 화면 초기화나 사용자 전환으로 바꾸지 않는다.

⚠ **멱등키는 `business_date` 까지 클라이언트가 정한다**(**C-8**) — 같은 등록이 두 번 전송돼도 LOT 이 둘 생기지 않는다.

## §9. 이 장에서 나온 공유 계약 후보

### 9-1. ⭐⭐ **「기록하지 않기로 한 것」은 컬럼을 비우고, 비운 이유를 스펙이 적는다**

**G-24**(만들지 않기로 한 것을 목록으로 적는다)의 **데이터 판**이다.

| 상황 | 하는 것 | ⛔ 안 하는 것 |
| --- | --- | --- |
| 자리가 있고 채우기로 함 | 채운다 | |
| **자리가 있는데 안 채우기로 함** | ⭐ **비우고, 스펙에 「왜 비우는가」를 적는다** | 「있으니까」 채우기 |
| 자리가 없고 필요함 | 신설 요구 | |

⚠ **일부만 채워진 계보가 빈 계보보다 위험하다** — **「추적 가능」으로 오해**되기 때문이다. 「없음」은 정직하고 「일부 있음」은 거짓말에 가깝다.

— `M-01-12` §3-1 · G-24 · A-13

### 9-2. **다형 참조 값 목록에 `RECYCLE_ENTRY` 를 더한다**(A-16 운영)

`trace.lot.source_type_code` 의 값 목록에 **여섯째**가 붙는다. **A-16** 이 정한 대로 계약이 먼저 갖는다.

### 9-3. ⭐ **「추적하지 않는다」와 「기록하지 않는다」는 다르다**

DR-006 이 뺀 것은 **원료 계보**이고, **누가 언제 얼마를 등록했나는 남는다**(`source_id NOT NULL` 이 요구하기도 한다).

| 구분 | 무엇 | 이 확정에서 |
| --- | --- | :-: |
| **감사 추적** | 누가 언제 무엇을 했나 | ✅ **남는다** |
| **계보 추적** | 이것이 무엇에서 나왔나 | ⛔ **빼기로 함** |

⚠ **확정을 넓게 읽어 둘 다 빼면 감사가 불가능해지고, 좁게 읽어 둘 다 남기면 확정을 어긴다.**

— `M-01-12` §5-2 · **16차 `W-CO-10` §3-1 과 같은 형태**(뺀 이유를 보면 경계가 나온다)

### 9-4. 기존 조회에서 LOT별 구분을 필터한다

전용 통계 화면을 만들지 않는다. 재고 현황·상태 조회 화면(W-01-07)의 `GET /inventory/balances`가 LOT별 `mesCategoryCode`로 필터한 뒤 기존 `groupBy`를 적용한다. 응답 행 키·합계 구조는 유지하며 구분별 새 행을 임의로 만들지 않는다.

투입·출고 등 다른 조회에 필터를 추가할 전체 목록은 별도로 정리할 대상이다. 재고 필터가 있다고 모든 통계 화면 반영이 끝난 것으로 보지 않는다.
