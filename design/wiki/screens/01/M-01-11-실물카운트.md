# M-01-11 · 실물 카운트

> 작성일: 2026-08-05 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **C-1 규칙 3(발생 시각 ≠ 서버 수신 시각)이 데이터로 뒷받침되는 첫 화면**이다. 동시에 **「아직 세지 않았다」와 「세었더니 0이다」를 구분할 수 없다.**

## §0. 요약

- **개요**: 모바일(360×720dp · 스캐너 일체형 PDA) 스캔형 화면. 물류(창고)담당이 진행 중인 실사를 선택해 위치→품목 순으로 스캔하고 실물 수량을 입력한다. **카운트만** 하며 조정은 관리웹 `W-01-04`(인벤토리 명시) 소관이다(확정).
- **주요 데이터**: `inventory.inventory_count`(11열 — `blind_count`) · `inventory.inventory_count_line`(14열 — `counted_at` NOT NULL · `variance_qty` GENERATED · `uq_inventory_count_line`).
- **핵심 액션**: 실사 선택 → 위치 스캔 → 수량 입력(+목록에 없는 재고 추가 · 직접 입력) → **이 위치 완료**.

## §5. 액션·상태

### §5-1. 블라인드 실사 — 장부를 감춘다

```
inventory_count.blind_count   boolean NOT NULL DEFAULT false
```

**확정이 데이터에 있다.** 참이면 **`system_qty`를 화면에 보이지 않는다** — 작업자가 장부 수를 보고 그대로 적는 것을 막는 실사 기법이다.

| | `blind_count = false` | `blind_count = true` |
| --- | --- | --- |
| 장부 수량 | `120 EA` | **`▪▪▪`** (가림) |
| 차이 | 실시간 표시 | **보이지 않음** |
| 차이 사유 | 즉시 입력 | ⚠ **입력할 근거가 없다** §8-1 |

⚠ **블라인드에서 차이 사유를 어떻게 받나** — 차이를 모르는데 사유를 물을 수 없다. **사유는 `W-01-04`(관리웹)에서 받는 것**으로 설계한다. `variance_reason_code`가 nullable이라 성립한다.

⚠ **API가 `system_qty`를 아예 내려보내지 않아야 한다.** 화면에서 가리는 것으로는 부족하다 — 응답 본문에 있으면 개발자 도구로 보인다. **블라인드는 서버가 지킨다** → §9-1.

### §5-2. ⛔ 「아직 안 셌다」와 「세었더니 0이다」가 같은 값이다

```
counted_qty   app.qty_t NOT NULL     -- qty_t 는 ≥ 0
```

⛔ **근거를 바꾼다**(2026-08-18) — 앞서 「**`NOT NULL` 이라 비워 둘 수 없고, 0 이 유효값이다**」로 모델에서 결론을 끌어냈다. **모델은 설계를 정하지 못한다**(`00-화면스펙서식.md` v1.1).

⭐ **설계가 먼저 말하는 것** — **「아직 세지 않음」은 실사에 반드시 있는 상태다.** 창고를 순회하는 도중에는 언제나 안 센 라인이 있고, `W-01-04` 는 그것을 **「미실사」 탭으로 이미 보이고 있다.** 즉 **표현 불가가 아니라 표현해야 하는 것**이다.

| 상태 | 설계 |
| --- | --- |
| **아직 세지 않음** | ⭐ **실재하는 상태다.** 이 화면은 **센 라인만 전송한다** — 안 센 것은 「0 으로 세었다」가 **아니다** |
| 세었더니 0개 | 수량 **0** 으로 전송 — **의미 있는 값**이다 |

📨 **모델이 이 둘을 못 가른다**(수량 컬럼이 널을 못 받는다) — **작업 통지**이고 우리를 막지 않는다. 설계는 「센 것만 전송한다」로 두 상태를 가르므로 **화면은 지금 지어도 된다.**

**창고를 순회하는 실사에서 이것이 문제가 된다** — 120 라인 중 38개를 센 상태에서 전송하면, 나머지 82개가 「0개로 확인됨」인지 「아직 안 감」인지 서버가 모른다. **`W-01-04`가 조정을 만들 때 82건을 전량 손실로 잡을 수 있다.**

**세 안**:

| 안 | 동작 | 대가 |
| :-: | --- | --- |
| **① 센 라인만 전송** *(권고)* | 미실사 라인은 아예 안 보낸다 | 서버가 「없음 = 미실사」로 해석해야 한다 |
| ② 별도 상태 컬럼 | `line_status_code` 신설 | **컬럼이 없다** |
| ③ 헤더 상태로 | 실사 완료 전엔 조정 금지 | 부분 실사가 안 된다 |

**①로 설계**하고 **「없는 라인 = 미실사」를 API 규약으로 못박는다.** 그렇지 않으면 오프라인 부분 전송이 데이터를 망친다.

→ **§8-2 · §9-2.**

### §5-3. 계획에 없던 재고를 셀 수 있나

```
uq_inventory_count_line  UNIQUE (inventory_count_id, line_no)
line_no  integer NOT NULL CHECK (line_no > 0)
```

라인은 **번호를 갖는 계획 항목**이다. 실사 계획을 만들 때 장부 기준으로 라인이 생성된다(`system_qty NOT NULL`이 그 증거 — 계획 시점에 이미 채워진다).

**그런데 순회하다 보면 장부에 없는 물건이 나온다.**

| 상황 | 처리 |
| --- | --- |
| 장부에 있고 실물도 있다 | ✅ 계획 라인에 입력 |
| 장부에 있는데 실물이 없다 | ✅ `counted_qty = 0` |
| **장부에 없는데 실물이 있다** | ⚠ **라인이 없다** — `system_qty`에 무엇을 넣나 |

**`system_qty = 0`으로 라인을 추가하면 성립한다**(`qty_t`가 0 허용). `line_no`는 서버가 다음 번호로 채번한다.

⚠ **모바일이 라인을 추가할 수 있는가**가 미정이다. 화면에는 버튼을 두되 **오프라인에서는 `line_no` 채번을 할 수 없으므로**(서버 채번) **온라인일 때만 활성**한다 → §8-4.

### §5-4. ★ `counted_at`이 C-1 규칙 3을 데이터로 뒷받침한다

**C-1 규칙 3**: 「`occurred_at`(발생)과 `recorded_at`(서버 수신)을 **분리** — 오프라인 지연이 실적 시각을 왜곡하지 않는다」

```
inventory_count_line.counted_at   timestamptz NOT NULL      ← 발생 (작업자가 센 시각)
inventory_count_line.created_at   timestamptz NOT NULL      ← 서버 수신
                                  DEFAULT clock_timestamp()
```

**두 컬럼이 실재하고 의미가 정확히 갈린다.** `production_result`·`work_session_event`에서 봤고, **이 화면이 재고 계열에서 첫 사례**다.

**규칙**: 화면은 **`counted_at`을 로컬 시각으로 채워 큐에 담는다.** 서버가 받은 시각으로 덮어쓰면 안 된다.

⚠ **PDA 시계가 틀어져 있으면 어떻게 하나** — 오프라인이라 서버 시각으로 보정할 수 없다. **연결 시 서버 시각과의 차이를 보정**하는 것이 일반적 처리이나 ⛔ **그렇게 하지 않는다** — 공유계약 **C-12**(v2.7)가 「화면은 시각을 보정하지 않는다 · 서버가 덮지 않는다」로 확정했다. 이 화면은 **언제 셌나**를 적을 뿐이라 몇 분 오차가 수량을 바꾸지 않는다.

### §5-5. 실사 동결 — (U-D1) 미정이고 오프라인이 악화시킨다

예외 E-8 ①: 「실사 중 입출고 발생(**동결 안 됨**) → 카운트 왜곡 — 동결 여부 **(U-D1)**」

**오프라인이면 문제가 더 커진다.**

```
09:00  A-01-03 카운트 (120개)         ← 오프라인 큐
10:30  다른 단말이 A-01-03 에서 출고 (20개)
11:00  연결 복구 → 카운트 전송
       → 서버의 system_qty 는 이미 100
       → variance = 120 - 100 = +20  (실제로는 차이가 없었다)
```

**`system_qty`가 언제 기준인가가 정해지지 않았다.**

| 안 | `system_qty` |
| :-: | --- |
| **① 계획 시점 고정** *(권고)* | 실사 계획 생성 시 스냅샷. **`counted_at`과 짝이 맞는다** |
| ② 전송 시점 | 오프라인 지연이 그대로 차이가 된다 |

**①이 데이터와 맞다** — `system_qty`가 라인에 저장되어 있고 계획 시점에 채워지므로 이미 스냅샷이다. 화면은 그것을 전제한다.

⚠ **동결 여부는 여전히 미정**이다. 동결하지 않으면 ①이어도 실사 기간 중 이동분이 차이로 잡힌다 → `W-01-04`가 판단할 몫으로 넘긴다.

## §9. 이 장에서 나온 공유 계약 후보

1. **감춰야 하는 값은 서버가 내려보내지 않는다** — 블라인드 실사의 `system_qty`를 화면에서만 가리면 응답 본문에 남는다. **「표시하지 않는다」와 「전송하지 않는다」를 계약이 구분**한다 (A-4는 표시 규칙이고 전송은 막지 않는다고 확정했다 — **이 조항은 그 반대 방향이라 별개다**) (§5-1)
2. **부분 전송이 있는 화면은 「보내지 않은 것」의 의미를 API 규약이 정한다** — 미실사와 0을 구분할 컬럼이 없으므로 **「없는 라인 = 미실사」**를 규약으로 못박아야 한다. 그러지 않으면 오프라인 부분 전송이 조정을 망친다 (§5-2)
3. **오프라인이 채우는 발생 시각은 단말 시계에 의존한다** — C-1 규칙 3이 `counted_at`으로 뒷받침된다. ✅ **C-12 로 확정됐다**(v2.7) — 화면이 보정하지 않고 서버가 덮지 않는다 (§5-4)
