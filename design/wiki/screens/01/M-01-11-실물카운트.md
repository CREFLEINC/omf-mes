## §0. 요약

- **개요**: 모바일(360×720dp · 스캐너 일체형 PDA) 스캔형 화면. 물류(창고)담당이 진행 중인 실사를 선택해 위치→품목 순으로 스캔하고 실물 수량을 입력한다. **카운트만** 하며 조정은 관리웹 `W-01-04`(인벤토리 명시) 소관이다(확정).

## §5. 액션·상태

### §5-1. 블라인드 실사 — 장부를 감춘다

```
inventory_count.blind_count   boolean NOT NULL DEFAULT false
```

**블라인드이며 아직 세지 않은 라인만 장부를 감춘다.** `blindCount=true`이고 `counted=false`이면 서버가 `systemQty`를 생략하고 `countedQty`·`varianceQty`는 0을 반환한다. 이 0은 표시용 자리값이며 실물 0개·차이 없음으로 해석하지 않는다. 근거: 블라인드 실사 통보 273(`omf-mes#521`).

| | 일반 실사 또는 카운트 완료 | 블라인드 미실사 |
| --- | --- | --- |
| 장부 수량 | 실제 장부 수량 | **`▪▪▪`** (응답 필드 생략) |
| 차이 | 카운트 완료 시 실제 차이 | **보이지 않음**(응답 0은 자리값) |
| 차이 사유 | 즉시 입력 | ⚠ **입력할 근거가 없다** §8-1 |

블라인드 미실사 라인(식별자가 없는 현장 신규 라인 포함)의 **첫 카운트 제출은 차이 사유 필수의 예외**다. 제출 후 `counted=true`가 되면 장부·실물·실제 차이를 공개하며 **사유는 `W-01-04`(관리웹)에서 보완**한다. 사후 보완 대기 중인 기존 블라인드 라인을 다음 위치 치환에 **수량·계수 시각을 바꾸지 않고 그대로 동봉**할 때도 미입력 사유를 유지할 수 있다. 이는 통보 274의 차이 사유 필수를 그대로 적용하면 첫 제출이나 다음 부분 카운트를 할 수 없는 충돌을 해소한 설계 보완이다(사용자의 자율 결정 승인). 기존 계수값 수정 등 그 외 차이가 있는 제출에는 사유가 필수이며, 입력된 사유는 예외 여부와 관계없이 활성 코드인지 검증한다.

**서버가 조건부 생략을 지킨다.** 블라인드 전체를 계속 숨기는 이전 정책은 통보 273에 따라 **미실사 라인에만** 적용하도록 바뀌었다. 카운트 완료 후에는 장부와 실제 차이를 표시한다.

### §5-2. 카운트 여부는 `counted`로 판정한다

`counted=false`는 미실사, `counted=true`는 실제 카운트 완료다. **실물 수량이 0이거나 담당 계정이 없어도 카운트를 완료할 수 있다.** `countedQty=0`·`countedBy=null`·시각으로 미실사를 추정하지 않는다. 기존 행도 근거 없이 완료 처리하지 않고 `counted=false`로 둔다(통보 273).

**위치별 전량 치환**이므로 해당 위치의 카운트 완료 상태로 남길 라인은 모두 함께 전송한다. 이번에 고친 라인만 보내면 빠진 기존 라인이 미실사로 돌아간다. 누락된 기존 라인은 삭제하지 않고 `counted=false`, 실물 수량 0, 사유·담당 계정 null로 되돌리며 기존 장부 스냅샷과 라인 번호는 보존한다. 다른 위치는 바꾸지 않는다.

제출한 라인은 `counted=true`로 기록한다. 위치·품목·LOT·단위가 중복된 요청은 400이며, 기존 `PLANNED`(계획) 실사는 첫 치환으로 `IN_PROGRESS`(진행중)가 된다. 신규 라인의 장부 기준은 §5-3, 사유의 블라인드 첫 제출 예외는 §5-1을 따른다(통보 274).

### §5-3. 계획에 없던 재고를 셀 수 있나

```
uq_inventory_count_line  UNIQUE (inventory_count_id, line_no)
line_no  integer NOT NULL CHECK (line_no > 0)
```

라인은 **번호를 갖는 계획 항목**이다. 실사 계획을 만들 때 장부 기준으로 라인이 생성된다(`system_qty NOT NULL`이 그 증거 — 계획 시점에 이미 채워진다).

**그런데 순회하다 보면 장부에 없는 물건이 나온다.**

| 상황 | 처리 |
| --- | --- |
| 장부에 있고 실물도 있다 | ✅ 계획 라인에 입력 |
| 장부에 있는데 실물이 없다 | ✅ `counted_qty = 0` |
| **장부에 없는데 실물이 있다** | ⚠ **라인이 없다** — `system_qty`에 무엇을 넣나 |

현장 신규 라인의 `system_qty`는 **등록 시점의 해당 창고 재고를 위치·품목·LOT·단위**(`locationId`·`itemId`·`lotId`·`uomId`)로 묶은 실제 잔액 합계다. 일치하는 잔액이 없을 때만 0이며, 음수이면 음수 그대로 보존한다. **일괄 0 처리하지 않는다.** `line_no`는 서버가 다음 번호로 채번한다. 실물 수량은 **0 이상**이고 차이는 서버가 **실물 − 장부**로 계산한다. 장부 −5·실물 0이면 차이는 **+5**다. 근거: 음수 재고 실사 검토 요청 `omf-mes#513`.

**모바일의 신규 라인 추가를 허용한다**(통보 274). 기존 화면 규칙에 따라 온라인에서만 활성화하며 서버가 라인 번호를 부여한다 → §8-4.

### §5-4. ★ `counted_at`이 C-1 규칙 3을 데이터로 뒷받침한다

**C-1 규칙 3**: 「`occurred_at`(발생)과 `recorded_at`(서버 수신)을 **분리** — 오프라인 지연이 실적 시각을 왜곡하지 않는다」

```
inventory_count_line.counted_at   timestamptz NOT NULL      ← 발생 (작업자가 센 시각)
inventory_count_line.created_at   timestamptz NOT NULL      ← 서버 수신
                                  DEFAULT clock_timestamp()
```

**두 컬럼이 실재하고 의미가 정확히 갈린다.** `production_result`·`work_session_event`에서 봤고, **이 화면이 재고 계열에서 첫 사례**다.

**규칙**: 각 라인의 `countedAt`이 실제 카운트 시각의 정본이다. 화면은 로컬 시각으로 채워 큐에 담고 서버가 받은 시각으로 덮지 않는다. 상위 `businessDate`·`occurredAt`은 형식을 검증하지만 라인 시각을 덮거나 실사 헤더를 바꾸는 값으로 쓰지 않는다(통보 274).

작업자 헤더가 있으면 연결된 사용자 계정을 카운트 담당으로 기록하고, 연결 계정이 없으면 null이다. 작업자 헤더 생략이 허용된 관리웹 계정 토큰일 때만 세션 계정을 쓴다. 단말 토큰은 기존 D-5대로 사번 헤더가 없으면 거부하며 세션 계정으로 대체하지 않는다. 담당 계정이 null이어도 `counted=true`일 수 있다.

⚠ **PDA 시계가 틀어져 있으면 어떻게 하나** — 오프라인이라 서버 시각으로 보정할 수 없다. **연결 시 서버 시각과의 차이를 보정**하는 것이 일반적 처리이나 ⛔ **그렇게 하지 않는다** — 공유계약 **C-12**(v2.7)가 「화면은 시각을 보정하지 않는다 · 서버가 덮지 않는다」로 확정했다. 이 화면은 **언제 셌나**를 적을 뿐이라 몇 분 오차가 수량을 바꾸지 않는다.

### §5-5. 실사 동결 — (U-D1) 미정이고 오프라인이 악화시킨다

예외 E-8 ①: 「실사 중 입출고 발생(**동결 안 됨**) → 카운트 왜곡 — 동결 여부 **(U-D1)**」

**오프라인이면 문제가 더 커진다.**

```
09:00  A-01-03 카운트 (120개)         ← 오프라인 큐
10:30  다른 단말이 A-01-03 에서 출고 (20개)
11:00  연결 복구 → 카운트 전송
       → 서버의 system_qty 는 이미 100
       → variance = 120 - 100 = +20  (실제로는 차이가 없었다)
```

위 예시는 전송 시점의 재고로 장부를 다시 계산할 때 생기는 문제다. **개시 때 만들어진 라인은 개시 시점 장부 스냅샷을 유지한다.** 과거 비교안은 다음과 같다.

| 안 | `system_qty` |
| :-: | --- |
| **① 계획 시점 고정** *(권고)* | 실사 계획 생성 시 스냅샷. **`counted_at`과 짝이 맞는다** |
| ② 전송 시점 | 오프라인 지연이 그대로 차이가 된다 |

**기존 라인은 ①로 고정한다.** 개시 시점의 위치·품목·LOT·단위별 실제 잔액 합계를 보존하며, 음수도 0으로 자르지 않는다. 음수 묶음을 제외하거나 음수만으로 창고 전체 실사 개시를 거부하지 않는다. 이후 실물 입력·수정으로 장부를 재계산하지 않는다. **현장 신규 라인만 §5-3의 등록 시점 기준**을 적용한다(`omf-mes#513`).

⚠ **동결 여부는 여전히 미정**이다. 동결하지 않으면 ①이어도 실사 기간 중 이동분이 차이로 잡힌다 → `W-01-04`가 판단할 몫으로 넘긴다.

## §9. 이 장에서 나온 공유 계약 후보

1. **감춰야 하는 값은 서버가 내려보내지 않는다** — 블라인드 미실사 라인의 `systemQty`를 화면에서만 가리면 응답 본문에 남는다. 카운트 후 공개하는 조건은 §5-1을 따른다. **「표시하지 않는다」와 「전송하지 않는다」를 계약이 구분**한다 (A-4는 표시 규칙이고 전송은 막지 않는다고 확정했다 — **이 조항은 그 반대 방향이라 별개다**) (§5-1)
2. **부분 전송이 있는 화면은 「보내지 않은 것」의 의미를 API 규약이 정한다** — `counted`로 미실사와 실물 0을 구분한다. 위치 치환에서 빠진 기존 라인은 삭제가 아니라 미실사 복귀다. 그러지 않으면 오프라인 부분 전송이 조정을 망친다 (§5-2)
3. **오프라인이 채우는 발생 시각은 단말 시계에 의존한다** — C-1 규칙 3이 `counted_at`으로 뒷받침된다. ✅ **C-12 로 확정됐다**(v2.7) — 화면이 보정하지 않고 서버가 덮지 않는다 (§5-4)
