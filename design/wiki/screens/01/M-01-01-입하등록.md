# M-01-01 · 입하 등록

> 작성일: 2026-08-04 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 입하 흐름의 **진입 화면**. 이 장에서 **사전부착/미부착 분기 · 무발주 예외입하 · 거래명세서 촬영**을 다룬다.

## 0. 요약

- **개요**: 모바일(스캐너 일체형 PDA) 단말에서 공급사 도착을 등록하는 입하 흐름의 진입 화면이다. 자재LOT 사전부착/미부착 분기, 무발주 예외입하, 거래명세서 촬영·확인을 이 한 화면에서 처리한다.
- **주요 데이터**: 입하 헤더(`logistics.inbound_receipt`)·입하 라인(`logistics.inbound_receipt_line`)·거래명세서 첨부(`app.attachment`)를 저장하며, 등록과 동시에 **사전부착 라인의** 자재LOT(`trace.lot`)이 Hold 상태로 함께 생성된다 — 미부착 라인은 `P-01-01` 이 채운다.
- **핵심 액션**: 자재 LOT 스캔 → P/O 후보 선택(또는 무발주 예외 처리) → 거래명세서 촬영/직접 입력 → 품목·수량 확인 → 입하 등록.

## §3. 레이아웃 (모바일 — PDA 1080×2160 세로)

**스캔 퍼스트.** 화면 진입 즉시 스캔 대기 상태이고, 손가락이 아니라 스캐너가 첫 입력이다.

```
┌─────────────────────────────┐
│ ← 입하 등록          [⋯]    │
├─────────────────────────────┤
│  ┌───────────────────────┐  │
│  │  자재 LOT 스캔        │  │   ← 포커스 고정
│  │  ▮                    │  │      (M-01-02 규약)
│  └───────────────────────┘  │
│     [ LOT 번호 없음 ]        │   ← 미부착 경로
├─────────────────────────────┤
│  《P/O 선택》                │
│  ┌───────────────────────┐  │
│  │ ○ PO-…-3  ABC-123     │  │   ← 사전부착이면
│  │   (주)…  500 EA       │  │      후보만 표시
│  │ ○ PO-…-7  ABC-123     │  │
│  └───────────────────────┘  │
│     [ 전체 P/O 보기 ]        │
├─────────────────────────────┤
│  《거래명세서》              │
│   [ 📷 촬영 ]  [ 직접 입력 ] │
│   DN-2026-…            ✓    │
├─────────────────────────────┤
│  《품목·수량 확인》          │
│   품목    ABC-123           │
│   예정    500 EA            │
│   실입하  [   500   ] EA    │
│   포장수  [    10   ]       │
│   ─────────────────────     │
│   제조일  [ 2026-07-20  ]   │
```

## §5. 액션·상태

### §5-1. 분기 ① 자재LOT 부착 여부 (OR 946:6749)

| 경로 | 동작 | 데이터 |
| --- | --- | --- |
| **[사전부착]** | LOT 번호 스캔(946:6724) → **번호 파싱**({제품코드}→품목 · {공급사 성분}→거래처) → 미마감 P/O **후보 자동 필터**(946:6806) → 담당자 최종 선택(219:4519) | `supplier_lot_no` = 스캔 값 · `supplier_lot_missing` = **false** |
| **[미부착]** | 「LOT 번호 없음」 → **전체 P/O 목록**에서 직접 선택 | `supplier_lot_missing` = **true** · `substitute_lot_reason_code` 입력 |

**분기가 데이터에 그대로 있다** — `supplier_lot_missing` boolean과 `substitute_lot_reason_code`. 화면이 만든 구분이 아니라 물리 모델이 이미 가진 구분이다.

> ⚠ **후보 필터의 전제** — 자재 LOT No가 **고정 양식**이어야 파싱된다(인벤토리 근거 부기). 양식이 다르면 후보가 0건이 되고 「전체 P/O 보기」로 빠진다 — §6.

### §5-2. 분기 ② 입하 검증 (OR 219:4581)

`received_qty`(이번 도착분)를 **남은 예정 수량**과 비교해 3갈래로 나뉜다.

```
남은 예정 = ordered_qty − 누적 입하량(purchase_order_line.received_qty)
```

⛔ **발주 총량이 아니라 «남은» 예정이다.** 한 발주에 여러 번 도착할 수 있고, 그때 총량과 비교하면 **정확히 남은 만큼 온 도착이 「부족」으로 판정된다**(`omf-mes#347`).

| 분기 | 판정 | 후속 |
| --- | --- | --- |
| **[정상]** | 남은 예정 = 실입하 (허용치 이내) | 태스크 ④ 계속 → 입하 등록 |
| **[수량 초과]** | 실입하 > **남은 예정** + `tolerance_over_qty` | **→ 01-S-B** · `W-01-03` 초과 입하 분리 |
| **[수량 부족·품목 오류]** | 실입하 < **남은 예정** − `tolerance_under_qty` / 품목 상이 | 아래 §5-2-1 · 품목 상이는 **→ 01-S-A** · `M-01-06` |

⭐ **이 축은 물리 제약과 «같은 축»이다.**

```
ck_po_line_received:  received_qty(누적) <= ordered_qty + tolerance_over_qty
```

「실입하 > 남은 예정 + 허용치」는 「누적 + 실입하 > 발주 + 허용치」와 **같은 식**이다. 총량 축으로 판정하면 화면이 「정상」이라 한 등록을 **DB가 거부한다** — `W-01-03` §이 「사용자에게는 「시스템이 이상하다」로 보인다」고 적은 그 자리다. 더 나쁜 것은 **총량 축이 누적 초과를 「부족」으로 뒤집어** 확정(QA #36 · 초과분 P/O 비귀속 분리)의 경로에 아예 못 닿게 한다는 점이다.

**허용치는 P/O 라인이 갖고 있다** — `tolerance_over_qty` · `tolerance_under_qty`(`W-01-11` §4-B). ⛔ **`ordered_qty`·`received_qty`·허용치 둘은 P/O «라인»에만 있다** — 목록 응답에는 없다. 화면은 `GET /logistics/purchase-orders/{purchaseOrderId}` 의 `lines[]`에서 넷을 읽어 판정하고, 판정 결과를 **사용자에게 먼저 보여준 뒤** 다음 화면으로 넘긴다. 조용히 넘기면 사용자가 왜 다른 화면에 왔는지 모른다.

#### §5-2-1. [수량 부족]의 두 갈래 — 화면은 못 가르고 사람이 가른다

**2026-09-02 확정**(`omf-mes#347`) — 예외 E-1 ②이 남긴 「분할납품의 **차단 vs 가입고**·승인 주체 = 잔여 ⚠」에 대한 답이다.

⛔ **분할 납품은 차단하지도, 가입고로 두지도 않는다 — 정상 입하로 등록한다.**

| 근거 | 무엇 |
| --- | --- |
| 데이터 모델이 이미 여러 회차를 전제한다 | `received_qty`(누적·서버 갱신) · `ck_po_line_received`(누적 축) · `openOnly`(「아직 입하가 끝나지 않은 건만」) |
| 「가입고」는 이미 기각됐다 | 예외 E3 · ✓확정 2026-07-20 §재정의 #8 — 「입하 시 이미 등록(Hold)이므로 **가입고 식별 체계 불요**」 |
| 담을 자리가 없다 | 계약 7벌에 `provisional`·가입고 상태값 **0건** |

⭐ **화면은 「더 올 것인가」를 알 수 없다 — 트럭·거래명세서를 본 사람이 안다.** 그래서 판정은 자동으로 내되 **다음 행동은 사용자가 고른다.**

```
발주 300 · 누적 200 · 이번 100 · 남은 0     → [정상]  자동 진행
발주 300 · 누적   0 · 이번 100 · 남은 200   → [부족]  표시하고 두 길을 연다
        ├ [계속 등록]       분할 납품이다 — 정상 입하로 등록한다.
        │                   누적이 쌓이고 P/O 는 열린 채 남는다(`openOnly` 에 계속 뜬다)
        └ [입하 오류 등록]  이게 마지막인데 모자란다 → 01-S-A · `M-01-06`
```

화면은 판정과 함께 **네 수를 그대로 보인다** — 발주·누적·이번 도착·남은 예정. 그것 없이 고르라 하면 사용자가 무엇을 고르는지 모른다.

⭐ **승인 주체는 «분할납품 축에 한해» 소멸한다.** 예외 E-1 ②이 승인 주체를 함께 잔여로 둔 것은 「차단·가입고를 누가 허가하나」였다. 분할 납품은 둘 다 하지 않으므로 승인이 필요 없다 — 정상 입하다.

⛔ **나머지 셋은 그대로 잔여다.** 예외 E-1 ②은 「부족·품목 상이·미등록·분할납품」 넷에 걸려 있고, 이번에 닫은 것은 **분할납품 하나뿐**이다. [입하 오류 등록]으로 간 뒤의 차단 여부·승인 주체는 `M-01-06` §8 미결 2 에 남아 있다.

### §5-3. 거래명세서 — 촬영이 기본, 수기가 대안

✅REQ-PR-0006 · ✓확정 QA #29 — 「거래명세서 **문서 분석 자동 등록**(수기=대안)」.

- **촬영** → `attachment` 저장 → **온프레 OCR**(결정 19 — AI Agent 전면 제외, OCR은 온프레) → 인식 결과를 화면에 채운다
- **직접 입력** → 명세서 번호만 수기
- ⚠ **인식 실패·부분 인식 시 무엇을 신뢰하는가**가 미결 — §8-2

> 「IQC 생략·별도 입고 경로가 아니다」(QA #29) — 명세서 처리 방식이 검사 여부를 바꾸지 않는다.

### §5-4. 등록의 결과 — 자재LOT이 Hold로 생긴다

✓확정 §재정의 #5 — **「자재LOT 등록 = 입하 시점 · Lot Status = Hold · 가용 재고 아직 아님」**

등록 한 번에 셋이 함께 일어난다.

```
inbound_receipt + line   저장
trace.lot                등록 (Lot Status = Hold)
inspection_required      라인별로 결정 → IQC 대상/생략 분기의 입력
```

**이것이 한 트랜잭션이어야 한다.** 입하는 저장됐는데 **사전부착 라인의** LOT이 없으면 이후 흐름이 통째로 막힌다 — `W-01-10`이 다룰 트랜잭션 원자성의 첫 사례다(§9-1). ⚠ **미부착 라인은 LOT 없이 저장된다** — `P-01-01` 이 `POST /trace/lots`(MES 발번)로 나중에 채운다(`P-01-01` §3-6).

> `inspection_required`가 **라인 컬럼**이라는 것은 IQC 대상 여부가 **입하 라인 단위로** 정해진다는 뜻이다. 같은 입하 안에서 어떤 품목은 검사하고 어떤 품목은 생략할 수 있다. **무엇이 이 값을 정하는가**(품목 속성? 공급사? 정책?)는 미결 — §8-3.

### §5-5. 무발주 예외입하 — 데이터에 설계돼 있다

`inbound_receipt`에 셋이 함께 있다.

```
exception_type_code    -- [L] P/O 없는 예외입하 유형 (주석 실측)
exception_reason
approval_request_id    -- [L] 예외입하 승인 (late FK -> app.approval_request)
```

**예외 E-1 ①「무발주 도착 인지」·② 「P/O 없이 입고」가 데이터에 있다.** `purchase_order_line_id`가 nullable인 것과 짝을 이룬다.

화면은 P/O를 고르지 않고 진행하는 경로를 **막지 않는다.** 예외 유형과 사유를 받는다.

#### ⛔ 발주가 없으면 «승계할 곳»이 없다 — 담당자가 고른다

**2026-09-02 확정**(`omf-mes#348`). 종전 필드표가 공급사·품목·단위를 전부 「P/O에서 승계」로만 적어, **무발주 경로에서 채울 방법이 없었다.** 계약에는 마스터 조회가 처음부터 있었고 우리가 지목하지 않았을 뿐이다.

| 항목 | 발주가 있을 때 | **무발주일 때** |
| --- | --- | --- |
| 공급사 | P/O 헤더에서 승계 | `GET /mdm/partners?roleTypeCode=SUPPLIER` — **역할이 「공급사」인 거래처만** 보인다 |
| 품목 | 발주 라인에서 승계 | `GET /mdm/items?q=` |
| 단위 | 발주 라인에서 승계 | `GET /mdm/uoms?q=` |
| 공장 | 단말 토큰 클레임 `plantId` | **같다** — 발주와 무관하다 |

⭐ **거래처 역할 값은 확정돼 있다** — 고객사·**공급사**·외주 제작사·폐기 업체·기타 다섯. 「공급사」로 걸러 고르므로 고객사를 공급사 자리에 넣는 실수가 안 난다.

#### ⛔ 별도 «승인»을 걸지 않는다

**2026-09-02 확정**(사용자 · `omf-mes#348`). 종전 서술은 「예외 유형과 사유를 받고 **승인을 건다**」였는데, **계약이 그것을 뒷받침하지 않는다.**

```
승인 유형 값 목록 — ✅ 사용자 확정 2026-09-01 (omf-mes#336) · 8값
  GOODS_ISSUE_DISPOSAL · INVENTORY_ADJUSTMENT · PURCHASE_ORDER ·
  INBOUND_RECEIPT_CANCEL · GOODS_RECEIPT_CANCEL · GOODS_ISSUE_CANCEL ·
  SHIPMENT_CANCEL · IQC_SKIP
```

⛔ **무발주 입하가 이 여덟에 없다.** 그리고 그 값 집합의 정본은 「승인 요청을 **만드는** 상신 오퍼레이션 전수」인데, 입하 계열 상신 경로는 **취소 요청 하나뿐**이고 «등록»을 상신하는 경로가 없다.

⭐ **통제는 이미 둘로 서 있다 — 승인을 또 걸 이유가 없다.**

| # | 통제 | 근거 |
| :-: | --- | --- |
| ① | **예외 유형·사유가 필수다** — 왜 발주 없이 받았는지가 반드시 남는다 | `exceptionTypeCode`·`exceptionReason` |
| ② | **자재LOT이 Hold로 생긴다 — 가용 재고가 아니다** | ✓확정 §재정의 #5 |

⚠ ②가 결정적이다. 무발주로 받아도 **그 물건은 쓸 수 없다.** 검사 전·긴급 입고에서 「입하 시 이미 등록(Hold)이므로 가입고 식별 체계 불요」로 판정한 것과 **같은 형태**다(✓확정 2026-07-20 §재정의 #8).

⚠ **물리 모델의 `approval_request_id`는 이 자리를 위한 것이 아니다** — 지금 그 자리를 채우는 상신 경로가 없다. 📨 데이터 모델 통지 대상이지 우리 차단이 아니다.

## §9. 이 장에서 나온 공유 계약 후보

1. **한 번의 저장이 여러 엔티티를 만들면 한 트랜잭션이어야 한다** — 입하 등록이 `inbound_receipt` + `line` + **사전부착 라인의** `trace.lot`(Hold)을 함께 만든다. 부분 성공은 이후 흐름을 막는다. `W-01-10`에서 조항으로 세운다 (§5-4)
2. **분기가 데이터 컬럼으로 있으면 화면은 그 컬럼을 따른다** — `supplier_lot_missing`처럼 물리 모델이 이미 가진 구분을 화면이 다시 발명하지 않는다 (§5-1)
3. **화면이 판정해 다른 화면으로 넘길 때는 판정 결과를 먼저 보인다** — 조용히 이동하면 사용자가 왜 왔는지 모른다 (§5-2)
4. **자동 인식(OCR·파싱)은 채우기까지만 하고 확정은 사람이 한다** — 인식 결과를 폼에 채우되 저장 전 확인을 받는다 (§5-3)
5. **예외 경로를 막지 않고 사유와 승인을 건다** — 무발주 입하처럼 「정상은 아니지만 실제로 일어나는」 경로는 차단이 아니라 기록·승인으로 다룬다 (§5-5)
