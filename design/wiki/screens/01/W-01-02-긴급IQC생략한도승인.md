# W-01-02 · 긴급 IQC 생략 한도승인

> 작성일: 2026-08-04 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ★ **승인 워크플로우의 첫 사례.** 공유계약에 조항이 없는 면이고, 이 장에서 세운 규약을 `M-01-01`(무발주)·`M-01-06`(입하 오류)·`W-01-03`(초과분)이 참조한다.

## §0. 요약

- **개요**: 관리웹에서 권한자(MES 권한 보유 관리자)가 작업자의 긴급 IQC 생략 요청을 검토해 승인·반려하는 화면. 좌측 승인 대기 큐 + 우측 선택 건 상세(대상·요청·결재선·승인 시 결과)로 구성된 좌우 2단 레이아웃이다.
- **데이터**: 승인 요청(`app.approval_request`)·결재 단계(`app.approval_step`)·결재선 정의(`app.approval_route`/`approval_route_step`, 읽기 전용)를 다루며, 대상은 자재LOT(`trace.lot`)다.
- **핵심 액션**: 승인 대기 큐에서 요청 선택 → 대상 LOT·요청 사유·결재선 진행 확인 → 승인 시 결과 안내(Lot Status→한도승인, ERP G/R 전표 미발행) 확인 → 의견 입력(선택) → 승인 또는 반려(어느 쪽이든 되돌릴 수 없다).

## §5. 액션·상태

### §5-1. 「한도」승인의 한도는 `approval_route`가 갖고 있다

화면명의 **「한도」**가 무엇인지 지금까지 문서에 정의가 없었는데, 데이터가 답한다.

```
approval_route.min_value / max_value   -- numeric(20,6)
```

**값 구간에 따라 결재선이 달라진다.** 소량이면 1단계, 대량이면 2단계 — 이런 식이다. `business_unit_id`로 사업부별 차등도 가능하다.

> ⚠ **무엇의 값인가는 미정이다** — 수량(EA)인지 금액인지 컬럼명이 말하지 않는다. `numeric(20,6)`은 둘 다 담을 수 있다. §8-2.

⛔ **1차는 값 구간을 화면에 쓰지 않는다**(✅확정 2026-08-07 · 요구서 §3-21). `approval_route.min_value`/`max_value` 는 «결재선을 고르는 서버 쪽 축»이고 승인 상세 응답(`ApprovalRequestDetail` = `request` + `steps`)에 실리지 않는다 — 화면이 그리면 없는 값을 지어내게 된다. 승인자에게는 대신 `steps[]` 의 `isMine`·`isCurrent` 로 「내 차례인가」를 보인다. ⚠ 값 구간을 화면에 쓰기로 하면 그때 `ApprovalRequestDetail` 에 `appliedRoute{minValue,maxValue,unit}` 를 신설한다 — 지금 신설하지 않는 이유는 「무엇의 값인가(수량인가 금액인가)」가 §8-2 미결이기 때문이다.

### §5-2. ⚠ `target_type_code` + `target_id`는 다형 참조다 — FK가 아니다

`approval_request`는 **어떤 대상이든** 가리킬 수 있게 설계돼 있다.

```
target_type_code   app.code_t   -- 무엇을 가리키는가
target_id          bigint       -- FK 아님. 유형별로 다른 테이블
```

**`audit.audit_event`와 같은 구조이고, 같은 문제를 갖는다**(#68). 유형 코드와 테이블의 대응 규약이 없으면 화면이 대상을 표시할 수 없다.

이 화면의 대상은 **자재LOT**(`trace.lot`)이다. 다만 `M-01-01`(입하 헤더)·`M-01-06`(입하 오류)·`W-01-03`(초과분)이 각각 다른 대상을 가리키므로, **유형 코드 목록과 대응 테이블을 계약이 정해야 한다** — §9-1.

> **`approval_step.approver_id`가 `NOT NULL`**이라는 것은 **요청 시점에 승인자가 사람 단위로 확정**된다는 뜻이다. `route_step`이 ROLE·DEPARTMENT로 정의돼 있어도, 요청이 만들어질 때 **실제 사람으로 전개**된다. 「그 역할의 누구나」가 아니다.

### §5-3. `reason`이 `NOT NULL`이다

**사유 없는 승인 요청이 데이터에 들어갈 수 없다.** 요청 화면이 사유를 필수로 받아야 한다.

긴급 IQC 생략은 **검사를 건너뛰는 것**이라 사후 추적이 중요하다. `reason`이 NOT NULL인 것은 그 요구가 데이터에 반영된 것으로 읽힌다.

> ⚠ **요청 화면이 어디인가** — 「작업자 요청」(§재정의 #8)인데 작업자용 요청 화면이 인벤토리에 없다. §8-3.

### §5-4. 승인의 결과 — Lot Status 전이 + G/R 제외

```
approval_step.decision_code = 승인
   ↓
trace.lot.status_code       = 한도승인
   ↓
ERP G/R 전표                 나가지 않는다 (합격품 한정)
```

**세 가지가 함께 일어나고, 셋째가 중요하다.** ✓확정 — 「G/R "합격품 한정"이 한도승인을 **자동 제외**」. 승인해도 ERP 입고 전표는 발행되지 않는다.

화면이 이것을 명시하지 않으면 승인자는 「입고 처리했다」고 오해한다. §3의 「승인 시 결과」 구획이 그래서 필수다.

**Lot Status 전이는 `W-01-10`(정상품 입하 처리)과 같은 지점에서 일어난다.** 한도승인 경로도 결국 그 화면을 거친다(05 S3 태스크 5 — 「→ 정상품 입하 처리(Lot Status=한도승인·G/R 제외)」). **이 화면은 승인까지, 전이는 `W-01-10`**으로 보는 것이 프로세스와 맞다 — §8-5.

### §5-5. ✅ 변경 이력 — 되살렸다(2026-08-30)

인벤토리가 이 화면의 데이터로 **「LotStatus변경이력」**을 든다. `GET /trace/lot-status-events`(`W-03-01` §5-1 신설)가 이 LOT의 승인 전이(C7·C8 등)를 사건별로 낸다 — `audit.audit_event` 규약 정비(#68)를 기다릴 필요가 없어졌다.

화면은 이력 구획을 정상 활성으로 그린다 — §8-6.

| **결재선 진행 표시** | `Stepper` | **a** — DS에 실재(ds-gap 「a」 목록) |
| 사유·의견 | `TextArea` | a |
| 승인 시 결과 안내 | `AlertBanner`(info) | a |
| 승인·반려 | `Button`(`filled` / `outlined`) | a |
| 비활성 사유 | `Tooltip` 또는 인라인 — 공유계약 F-1 | a |
| 이력(비활성) | `Table` — 자리만 | a |

### §7-2. 신규 갭 0건 — `Stepper`가 결재선을 그린다

결재선 진행 표시는 갭처럼 보이나 **DS에 `Stepper`가 실재한다**(ds-gap §7-1 「a — 그대로 있음」 목록). 단계·현재 위치·완료를 표현하는 데 충분하다.

> **「갭처럼 보였으나 실재」 사례**가 하나 더 나왔다. ds-gap 판정 절차 ①(인벤토리 전수 조회)이 또 값을 했다.

## §9. 이 장에서 나온 공유 계약 후보 — ★ 승인 워크플로우 신설

**공유계약에 승인 조항이 없다.** 이 장에서 다섯을 제안한다. `M-01-01`(무발주)·`M-01-06`(입하 오류)·`W-01-03`(초과분)이 모두 `approval_request_id`를 갖고 있어 **곧바로 셋이 참조한다.**

1. **승인은 4테이블 한 벌로 다룬다** — 정의(`approval_route` + `route_step`)와 실행(`approval_request` + `step`)이 분리돼 있다. 화면은 정의를 **읽기만** 하고, 정의 화면은 따로 둔다 (§4-C)
2. **다형 참조(`target_type_code` + `target_id`)의 유형 코드 ↔ 테이블 대응을 계약이 정한다** — FK가 없어 서버·화면이 각자 해석하면 갈린다. `audit_event`(#68)와 **같은 문제이므로 함께 정한다** (§5-2)
3. **승인 요청 시점에 승인자를 사람으로 확정한다** — `approval_step.approver_id`가 `NOT NULL`이다. 결재선이 ROLE·DEPARTMENT여도 요청 시 전개한다. 「그 역할의 누구나」가 아니다 (§5-2)
4. **승인 화면은 「승인하면 무엇이 일어나는가」를 명시한다** — 특히 **일어나지 않는 것**(한도승인 시 ERP G/R 미발행). 결과를 모르고 누르면 사후에 회계가 어긋난다 (§3 · §5-4)
5. **결재는 되돌릴 수 없다** — `approval_step`이 기록 전용(`created_at`만)이다. 취소·변경은 새 요청이며, 화면에 「수정」을 두지 않는다 (§4-B · §6)

### §9-A. A-5 대상 후보 발견

**`app.approval_route_step.step_no`에 `UNIQUE(approval_route_id, step_no)`가 있다.** 결재선 단계 순서를 사용자가 바꾸는 화면이 생기면 **A-5(순서 재배치 서버 일괄 치환) 대상**이다.

현재 A-5는 **2곳**(`routing_operation.operation_seq` · `inspection_item_spec.sequence_no`)이다 — `bom_component`는 v0.4.2에서 **ERP 원본이라 MES가 재배치하지 않는다**는 이유로 빠졌다. **결재선 정의 화면이 만들어지면 3번째가 된다.** 지금 그 화면이 없으므로 A-5 목록은 그대로 두고 **후보로만 기록**한다 — 공유계약 A-5에 주를 단다.
