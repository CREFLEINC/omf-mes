# M-01-04 · 자재 위치 확인

> 작성일: 2026-08-05 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **조회 전용 모바일 화면**이라 「오프라인에서 조회는 무엇을 보이나」가 처음 걸린다. §C 4조항이 전부 **입력**에 대한 것이라 답이 없다.

## §0. 요약

- **개요**: 모바일(스캐너 일체형 PDA) 조회 전용 화면. 물류(창고)담당이 자재 LOT을 스캔하면 현재 위치·수량을 보여주며, **아무것도 저장하지 않는다.**
- **주요 데이터**: 재고 잔액(`inventory.inventory_balance` — 창고·위치·품목·보유/예약/피킹/보류/가용 수량), 보류 정보(`trace.lot_hold` — 보류 사유·수량·해제 조건).
- **핵심 액션**: 스캔(암묵, 포커스 고정) · 직접 입력(대체 경로) · 다음 스캔(조회 결과 초기화). 저장 액션은 없다.

**세로 검산**: 64+48+56+32+48×2+40×4+48 = 504 / 592 — 통과(여유 88).

**스크롤 구획**(공유계약 E-4) — 앱바 56 = **셸 소유·고정** / 본문 592 = **이 구획만 스크롤한다** / 액션 72 = **하단 고정, 스크롤하지 않는다.** ⛔ 지정하지 않으면 구현이 화면 전체 스크롤을 택하고, 그러면 본문 예산 «밖»에 둔 「다음 스캔」이 흐름 안으로 밀려 내려간다(`omf-mes-client#582` 실측).

⭐ **보류 표시를 위치·수량보다 «위»에 둔다**(✓확정 2026-08-31 · `omf-mes#275` ② A안). 두 값의 성격이 반대이기 때문이다 — **수량**이 화면 밖으로 밀리면 「찾아야 한다」로 읽히고 작업자가 스스로 스크롤해 회복되지만, **보류 경고**가 밀리면 **「없다」로 읽히고 없는 것을 찾는 사람은 없어 회복되지 않는다.** 오프라인 캐시 표시 조항(C-6) 규칙 3 의 「빈칸으로 두면 없음으로 읽힌다」와 같은 자리다 — **스크롤 밖은 빈칸과 같다.** 요소 높이는 그대로라 세로 합은 504 그대로다.

### §3-1. 이 화면이 스캔 화면인데 아무것도 저장하지 않는다

유형은 「조회·상세」지만 **입력 방식은 스캔**이다(D-1 — 스캔은 폼팩터가 아니라 입력 방식). 포커스 고정·자동 제출·입력 후 클리어는 D-2 그대로 쓰되, **결과가 목록에 쌓이지 않고 화면이 통째로 바뀐다.** 연속 스캔이 아니라 **1건씩 보는 화면**이라 C-3(건별 저장 + 마지막 일괄 완료)이 적용되지 않는다.

## §5. 액션·상태

### §5-1. ⚠ A-7 첫 화면 검증 — 유일 인덱스가 11축이고 그중 둘이 접힌다

```
uq_inventory_balance_dim ON inventory.inventory_balance (
    legal_entity_id, business_unit_id, plant_id,
    warehouse_id, location_id, item_id,
    COALESCE(lot_id, 0),            ← 접힘
    quality_status_code, inventory_status_code, ownership_type_code,
    COALESCE(owner_partner_id, 0)   ← 접힘
);
```

**A-7 대상 9곳 중 하나가 여기서 처음 화면에 붙었다.** 규칙대로 **빈 축을 `(전체)`로 표기**한다.

| 축 | 값이 있을 때 | NULL일 때 |
| --- | --- | --- |
| `lot_id` | `…0007` | **`(LOT 무관)`** — 「없음」이 아니라 LOT 단위로 나누지 않는 재고 |
| `owner_partner_id` | `(주)대한부품` | **`(자사 소유)`** |

⭐ **소유처 축은 «반드시» 화면에 둔다.** 계약이 「소유 구분은 어떤 축에서도 합치지 않는다」(공유계약 L-7)로 못박아 `ownershipTypeCode` 가 `groupBy` 와 무관하게 «행을 나눈다» — 같은 LOT 이 같은 위치에 있어도 소유가 다르면 두 줄로 온다. 소유 칸이 없으면 **똑같아 보이는 두 줄**이 화면에 나오고 작업자가 이유를 알 수 없다. ⇒ **A-7 대상 축의 노출 기준 = 「그 축이 응답의 행을 나누는가」.** 나누면 노출하고, 나누지 않으면 표기 규칙(A-7 규칙 1)만 걸린다.

⚠ **빈칸으로 두면 「데이터가 빠졌다」로 읽힌다.** 이 화면은 조회 전용이라 오류 문구는 나오지 않으므로 A-7의 두 규칙 중 **표기 규칙만** 적용된다.

### §5-2. 위치가 없을 수 있다 — 그런데 컬럼은 `NOT NULL`이다

```
inventory_balance.location_id   bigint NOT NULL
```

REQ-PR-0005는 위치 관리를 **선택적**으로 두었고(B7② nullable/기본 Location) 프로세스 S5도 「위치 관리 여부 분기(OR 220:12187)」를 갖는다. 그런데 **잔액 테이블은 위치를 반드시 요구한다.**

**해석**: 「선택적」은 **기본 Location으로 흡수**하는 방식이다(B7② 원문의 「기본 Location」). 위치를 쓰지 않는 창고는 창고당 대표 Location 한 개를 두고 전부 거기에 매단다.

→ 화면은 그 위치가 **대표 Location이면 `(위치 미지정)`으로 표시**한다. 코드를 그대로 보이면 작업자가 실제 선반을 찾으러 간다. ✅ **판정할 자리가 섰다** — `mdm.location.location_type_code` 가 `DEFAULT`(대표)면 대표 Location 이다(코드 사전 `CD-LOCATION-TYPE` · §8-1). «(정합주: 2026-09-03 — 옛 서술은 「무엇이 대표 Location인지 판정할 컬럼이 없다」였다. 컬럼은 있었고 없던 것은 «값»이다)»

### §5-3. 보유 수량이 음수일 수 있다

```
on_hand_qty  app.signed_qty_t NOT NULL DEFAULT 0
-- [H-2] 음수 허용 여부는 item.negative_stock_allowed 기준으로
--       constraint trigger가 검증한다
```

**`item.negative_stock_allowed`(실측)** 가 참인 품목은 마이너스 재고가 정상이다. 화면은 **음수를 오류로 표시하지 않고 그대로 보이되 시각 구분**을 준다(G-1 `--semantic-warning`).

### §5-4. 가용 수량은 GENERATED — 화면이 빼지 않는다

```
available_qty = on_hand_qty - reserved_qty - picked_qty - blocked_qty   (STORED)
```

**화면이 같은 뺄셈을 다시 하면 안 된다.** 서버가 준 값을 그대로 그린다 — 규칙이 바뀌면 화면 4곳이 아니라 DB 한 곳만 바뀐다.

### §5-5. ⛔ 오프라인에서 이 화면은 무엇을 보이나 — §C에 답이 없다

**§C의 4조항이 전부 「입력」에 대한 것이다.**

| 조항 | 다루는 것 |
| --- | --- |
| C-1 오프라인 입력 규약 | 저장·큐·멱등키 |
| C-2 오프라인 유일성 판정 | 저장 시 중복 |
| C-3 연속 작업의 완료 모델 | 저장 반복 |
| C-4 outbox 동형 | 전송 |

**조회 화면은 저장할 것이 없다.** 그런데 이 화면은 모바일이고 창고 안쪽은 통신이 약하다 — 정확히 이 화면이 필요한 곳에서 연결이 끊긴다.

선택지 셋:

| 안 | 동작 | 위험 |
| :-: | --- | --- |
| **① 차단** | 「오프라인에서는 조회할 수 없습니다」 | 적치 작업이 멈춘다 |
| **② 캐시 표시** | 마지막 동기 시점 데이터 + **시각 명시** | 재고가 이미 움직였을 수 있다 |
| **③ 무캐시 재시도** | 재시도 안내만 | ①과 실질 같음 |

**②를 권고**한다 — 조회 전용이라 잘못된 값으로 데이터를 쓰지 않고, **「08-05 09:12 기준」을 항상 함께 보이면** 작업자가 판단할 수 있다. 다만 **§5-6의 예외**가 있다.

→ **§C 신규 조항 후보** §9-1.

### §5-6. ⚠ 그런데 보류(Hold) 표시는 캐시하면 안 된다

**결정 10**: 「출고·출하·Picking **차단 판정**은 Lot Status **단일 지점** 참조 · **캐시 없음**」.

이 화면은 차단을 하지 않지만 **보류 상태를 보인다**(§4-B). 캐시된 보류 표시를 보고 작업자가 「풀렸네」 하고 움직이면 결정 10이 막으려던 일이 그대로 일어난다.

**규칙**: 오프라인 캐시 표시에서 **보류 항목만 값을 감추고 「확인 불가」로 바꾼다.**

```
⚠ 보류 여부는 연결된 뒤에 확인하세요 (마지막 확인: 08-05 09:12)
```

→ **캐시해도 되는 것과 안 되는 것이 한 화면 안에서 갈린다.** §9-2.

## §9. 이 장에서 나온 공유 계약 후보

1. **오프라인에서 「조회」는 무엇을 보이는가** — §C 4조항이 전부 입력에 대한 것이라 조회 화면에 적용할 규칙이 없다. **캐시 표시 + 기준 시각 명시**를 기본으로 두되, 캐시 금지 항목을 계약이 지정한다 (§5-5)
2. **한 화면 안에서 캐시해도 되는 것과 안 되는 것이 갈린다** — 결정 10의 「차단 판정은 캐시 없음」이 조회 화면의 보류 표시에도 걸린다. **판정에 쓰이는 값은 캐시하지 않고 「확인 불가」로 바꾼다** (§5-6)
3. **GENERATED 컬럼은 화면이 다시 계산하지 않는다** — `available_qty`처럼 DB가 파생을 저장하면 화면은 받은 값을 그린다. 같은 식을 두 곳에 두면 규칙 변경이 한쪽만 반영된다 (§5-4)
