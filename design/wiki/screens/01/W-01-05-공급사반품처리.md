# W-01-05 · 공급사 반품 처리

> 작성일: 2026-08-05 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ✓확정 QA #15 「**전용 트랜잭션 불요**」가 데이터에 그대로 있고, 요구하지 않은 것까지 있다(`replacement_expected`). **가장 깨끗한 화면.**

## §0. 요약

- **개요**: 관리웹에서 물류담당(+품질담당)이 공급사 반품을 처리하는 화면. 반품 대상 LOT을 선택해 반품을 등록(Hold 유지)하고, 반출 기록을 생성한 뒤 ERP 반품 전표에 선택적으로 연계한다. **폐기는 `W-01-06`**으로 분리 유지된다.
- **주요 데이터**: 출고 전표 `logistics.goods_issue`(반품 유형 — `issue_type_code`·`reason_code`·`replacement_expected`)·반출 라인 `logistics.goods_issue_line`·`trace.lot_hold`·`inventory.inventory_transaction`. 반품 전용 테이블 없이 `goods_issue`에 유형·사유 코드로 표현된다.
- **핵심 액션**: 반품 대상 LOT 조회·선택 → 사유·대체입고 예정 선택 → 라인별 반품 수량 입력(보유 수량 이하) → ERP 반품 전표 송신 토글 → [반품 처리]. **반품 후에도 Hold는 유지**된다.

## §5. 액션·상태

### §5-1. ★ QA #15가 데이터에 그대로 있다 — **전용 트랜잭션이 없다**

**✓확정 QA #15**: 「공급사 반품 = **재고 차감 + 반출 기록이면 충분**(전용 트랜잭션 불요)」

**실측**: `goods_issue`에 `issue_type_code`가 있고 `reason_code`가 있다. **반품 전용 테이블이 없는 것이 정상이다.**

**「모델이 앞섬」이 아니라 「확정과 정확히 일치」한다.** **불일치가 하나도 안 나온 유일한 화면**이다.

```
반품 = goods_issue(issue_type_code = 공급사반품, reason_code = IQC불합격)
     + goods_issue_line(LOT · 수량)
     + inventory_transaction(재고 차감)
```

### §5-2. 요구하지 않은 컬럼이 있다 — `replacement_expected`

```
goods_issue.replacement_expected  boolean
-- [M] 공급사반품 시 대체입고 예정 여부 (FR-IM-067)
```

**프로세스·확정 어디에도 「대체입고 예정」이 없다.** 데이터모델이 요구서(FR-IM-067)를 보고 넣은 것이다.

**화면이 쓸 것인가** — 쓴다. 근거:

- **반품 후 후속이 갈린다** — 대체입고가 예정되면 P/O가 살아 있고, 아니면 P/O 잔량이 미납으로 남는다
- **`W-01-09`(입하예정조회 · 2차)가 이 값을 볼 수 있다** — 대체입고 예정 건이 예정 목록에 뜨면 자연스럽다

⚠ **연결이 검증되지 않았다** — `W-01-09` 스펙에 이 항목이 없다. **양쪽을 잇는 규칙이 미정** → §8-1.

### §5-3. 도착이 「공급사」다 — A-10의 새 대상 유형

```
goods_issue.destination_type_code + destination_id
```

4차 `M-01-08`(생산 출고)에서는 도착이 **위치·라인**이었는데, 여기서는 **공급사(`mdm.partner`)**다.

**A-10 규칙 4**(한 화면이 여러 대상 유형을 다루면 대상마다 판정) — **이 화면은 한 유형만** 다루므로 간단하다. 다만 **`destination_type_code` 값 집합에 「공급사」가 있어야** 한다.

| 화면 | `destination_type_code` |
| --- | --- |
| `M-01-08` 자재 출고 | 위치 · 라인 (미정) |
| **`W-01-05` 반품** | **공급사** |
| `W-01-06` 폐기 | ⚠ **무엇인가** — 폐기처? 없음? |

→ **세 화면이 같은 컬럼의 값 집합을 함께 요구**한다. #64 계열 §8-2.

### §5-4. 반품은 피킹을 거치지 않는다

```
goods_issue_line.picking_line_id   bigint     ← nullable
```

4차 `M-01-08`에서는 **피킹 라인이 출고 라인의 원천**이었다. 반품은 **관리웹에서 LOT을 직접 골라** 처리하므로 피킹이 없다.

**nullable이라 성립한다** — 「모델이 앞섬」의 한 형태다(같은 테이블이 두 경로를 받는다).

⚠ **실물은 누가 꺼내나** — 반품 처리 후 창고에서 물건을 빼는 것은 사람이 한다. **모바일 화면이 없다**(01-S-I가 관리웹 전용). 4차의 「흐름이 닫히지 않는 곳」과 같은 성격이나, **반품은 건수가 적고 관리웹에서 지시서를 뽑아 처리하는 것이 자연스럽다** → 미결로만 둔다 §8-4.

### §5-5. Hold는 유지된다 — 반품해도 풀지 않는다

**✓확정 §재정의 #3**: 「상태변화: 재고 감소 — **Hold 유지 상태의 자재LOT 반품**」

```
trace.lot_hold.released_at   ← 채우지 않는다
```

**직관과 반대라 화면이 밝혀야 한다.**

```
⚠ 반품 후에도 Hold 는 유지됩니다 (✓확정 §재정의 #3)
```

**G-5 적용** — 확정 번호를 문구에. 「왜 안 풀리나」를 물을 때 근거가 화면에 있어야 한다.

⚠ **재고가 0이 된 LOT의 Hold가 남는다** — `W-01-07`(재고 조회)에 「보유 0 · 보류 중」인 행이 보인다. **정상이나 오해를 산다** → `W-01-07` §8에 반영 대상.

### §5-6. ERP 연계 — 선택(on/off)이나 방식이 미정

**✓확정 QA #6**: ERP 반영 = **항목별 선택(on/off) 연계** · ⚠ **방식 상세 = 회신 E-10 대기**

**`W-02-05` §5-6과 같은 구조**다 — 토글은 두되 **정본은 전역 설정**이다(`W-06-12` · 2026-08-18 계약 착지). 건별 토글은 전역과 논리곱이다.

**화면 설계**: 토글을 두고 **기본 켬**으로 하되, 설정 테이블이 없으므로 **화면 단위 임시 설정**이다. `integration_message`에 적재하는 것까지가 트랜잭션(B-8).

## §9. 이 장에서 나온 공유 계약 후보

1. **확정이 「전용 구조가 불요하다」고 한 것은 데이터가 없는 것이 아니라 맞는 것이다** — QA #15의 「전용 트랜잭션 불요」를 근거 부족으로 읽으면 안 된다. **§I 판정 시 「없어야 정상인 것」과 「없어서 문제인 것」을 가른다** (§5-1)
2. **요구하지 않은 컬럼을 발견하면 쓸지 말지를 스펙이 판정한다** — `replacement_expected`는 확정 어디에도 없으나 업무상 의미가 있다. **버리지 말고 「쓴다/안 쓴다 + 근거」를 적고, 연결될 화면을 지목**한다 (§5-2)
3. **직관과 반대인 확정은 화면이 근거 번호와 함께 밝힌다** — 「반품해도 Hold 유지」는 물어볼 만한 일이다. G-5(확정 번호를 문구에)의 대상은 「바꿀 수 없는 것」뿐 아니라 **「이상해 보이는 것」**까지다 (§5-5)
