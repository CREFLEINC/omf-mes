# W-01-11 · 신규 P/O 등록

> 작성일: 2026-08-04 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 이 장에서 **「MES는 P/O를 만들지 않는다」는 규칙과 이 화면의 양립**을 다룬다. 규칙과 화면이 정면으로 부딪히는 첫 사례다.

## §0. 요약

- **개요**: 관리웹에서 물류(창고)담당이 초과 입하분에 대해 사후로 P/O를 등록하는 입력 화면. 대상 초과분(읽기 전용, `W-01-03`에서 승계) 아래 P/O 헤더 + P/O 라인을 한 폼에서 입력하고, 등록 후 담당부서 관리자 승인을 거친다. 일반 구매 발주는 이 화면이 아니라 초과 입하분의 사후 등록에 한정된다.
- **데이터**: P/O 헤더(`logistics.purchase_order`)와 P/O 라인(`logistics.purchase_order_line`)을 한 트랜잭션으로 저장한다. `erp_purchase_order_no`는 nullable(MES 선등록·ERP 사후 매칭)이고, `ck_po_line_received`(입고수량 ≤ 발주수량+초과허용)가 초과 입하 흐름 전체의 근거다.
- **핵심 액션**: 라인 추가/삭제 → 필수 항목 입력 후 등록(헤더·라인 한 트랜잭션) → 등록 완료 시 승인 요청(`app.approval_request` 생성, 공유계약 §J 승인 워크플로우) → 승인 완료 후 초과분 입하를 이 P/O에 귀속(`W-01-03` 소관).

### §4-B. P/O 라인 `logistics.purchase_order_line`

| 라벨 | 출처 컬럼 | 타입 | 필수 | 검증·비고 | 입력 |
| --- | --- | --- | :-: | --- | --- |
| # | `line_no` | integer > 0 | ✅ | `UNIQUE(purchase_order_id, line_no)` — **표시는 목록 내 위치**(A-5 조항 2) | 자동 |
| 품목 | `item_id` | FK → `mdm.item` | ✅ | 초과분에서 승계 | 선택 |
| 발주수량 | `ordered_qty` | `qty_t` > 0 | ✅ | CHECK > 0 | 입력 |
| 단위 | `uom_id` | FK → `mdm.uom` | ✅ | 품목 기준단위 기본 | 선택 |
| **초과 허용** | `tolerance_over_qty` | `qty_t` 기본 0 | ✅ | ⬇ 입고 상한을 정한다 | 입력 |
| **부족 허용** | `tolerance_under_qty` | `qty_t` 기본 0 | ✅ | | 입력 |
| 입고수량 | `received_qty` | `qty_t` 기본 0 | ✅ | **이 화면에서 입력하지 않는다** — 입고가 갱신 | 자동 |

**⚠ 이 제약이 초과 입하 흐름 전체의 이유다**

```
ck_po_line_received:  received_qty <= ordered_qty + tolerance_over_qty
```

**허용치를 넘는 입고를 DB가 물리적으로 막는다.** 그래서 초과분을 원 P/O에 붙일 수 없고, `W-01-03`이 별도 입하로 분리하며(P/O 비귀속), 입고하려면 이 화면이 새 P/O를 만들어야 한다. **확정(QA #36)과 물리 모델이 일치한다.**

화면은 `초과 허용`을 입력받되, **초과분 수량이 곧 발주수량**이 되는 것이 기본이다(허용치 0). 허용치를 다시 주면 같은 문제가 반복된다 — §6.

### §5-2. ⚠ 「MES는 P/O를 만들지 않는다」와 이 화면

**규칙과 화면이 부딪힌다.**

> `05` S1 규칙 — 「**P/O = ERP 발행 정본 · MES 수신 · MES에서 수정 없음**」 (✅REQ-PR-0024 · D10 해소)

그런데 이 화면은 MES에서 P/O를 **등록**한다. 세 가지로 읽을 수 있다.

| 해석 | 뜻 | 데이터가 지지하는가 |
| --- | --- | --- |
| **가. 번호만 받아 적는다** | ERP가 이미 발행한 P/O의 **번호를 MES에 입력**해 초과분을 귀속시킨다. 「등록」 = 「매칭」 | ✅ `erp_purchase_order_no`가 있다. 다만 **`purchase_order_no`(MES 번호)가 `NOT NULL UNIQUE`**라 MES 레코드는 어차피 생긴다 |
| **나. MES가 만들고 ERP가 뒤따른다** | MES가 P/O를 만들고 `erp_purchase_order_no`를 **비운 채** 저장. 나중에 ERP 번호가 오면 채운다 | ✅ **`erp_purchase_order_no`가 nullable이다.** 데이터는 이 형태를 허용한다 |
| **다. MES가 만들어 ERP로 보낸다** | MES 발행 → ERP 송신 | ⛔ S1 규칙 정면 위반. 송신 I/F도 없다 |

**데이터는 가·나 둘 다 허용하고, 프로세스 주석은 나에 가깝다** — 「**사후** P/O 번호 등록 · P/O 수신 I/F = 02 도식 소관」. 즉 **MES에 먼저 만들어 두고 ERP 번호를 나중에 매칭**하는 것으로 읽힌다.

**화면은 나로 설계하되 가를 막지 않는다** — `ERP P/O 번호`를 입력 가능하되 필수로 두지 않는다. 어느 쪽으로 확정되든 필드는 그대로 선다.

> ✅ **2026-08-04 확정으로 갈렸다** — 승인 주체가 **MES 안에 있다**(§5-6). 즉 **나**(MES 선등록·ERP 사후 매칭)다. ERP 발행이 곧 승인인 **가**였다면 MES 안에 승인 단계가 필요 없었을 것이다.

### §5-3. `erp_purchase_order_no`가 비어 있는 동안

**이 P/O는 ERP와 대조되지 않은 상태**다. 화면은 이것을 숨기지 않는다.

- 목록·상세에서 **「ERP 미매칭」 배지**를 붙인다
- 매칭 전에도 입고는 가능하다 — `ck_po_line_received`가 막는 것은 수량이지 ERP 번호가 아니다
- **매칭을 누가 언제 하는지**는 이 화면 밖이다(02 도식 소관)

### §5-4. 등록 후

`W-01-03`으로 복귀해 초과분 입하를 이 P/O에 귀속시킨다. **귀속 처리 자체는 `W-01-03` 소관**이다 — 이 화면은 P/O를 만들 뿐이다.

### §5-6. ✅ 승인 — 담당부서 관리자 (2026-08-04 확정)

**사용자 확정** — 「승인 주체 = **담당부서 관리자**. **명확히 고정된 것이 아니라 관리자의 권한 설정으로 처리**한다.」

**공유계약 §J(승인 워크플로우)를 그대로 탄다.** 이 화면이 별도 승인 구조를 만들지 않는다.

| §J 조항 | 이 화면의 적용 |
| --- | --- |
| **J-1** 정의/실행 분리 | 결재선 정의는 **읽기만** — 정의 화면은 별도(⚠ **#74** 부재) |
| **J-2** 「한도」= 값 구간 | 초과분 **수량·금액 구간**으로 결재선이 갈릴 수 있다 |
| **J-3** 요청 시점에 사람으로 확정 | `approval_route_step.approver_type_code` = **`DEPARTMENT`** — 「담당부서 관리자」가 이 값으로 표현된다 |
| **J-4** 사유 필수 | `approval_request.reason` NOT NULL |
| **J-5** 「일어나지 않는 것」 명시 | 승인 전까지 **초과분이 이 P/O에 귀속되지 않는다** |
| **J-6** 결재 번복 불가 | |

**「고정이 아니라 권한 설정으로」가 핵심이다.** 화면에 승인자를 하드코딩하지 않는다 — `approval_route`·`route_step`이 정한 대로 전개하고, 운영 중에 결재선을 바꾸면 화면은 그대로 따른다.

```
W-01-11 등록  →  approval_request 생성 (target = 이 P/O)
                 approval_route 조회 → route_step 전개 → approver_id 확정
                    ↓ 승인 완료
              초과분 입하를 이 P/O 에 귀속 (W-01-03 소관)
```

> ⚠ **결재선이 정의돼 있지 않으면 요청이 만들어지지 않는다**(J-1 ⬜). **#74**(결재선 정의 화면 부재)가 이 화면의 실질 선행 조건이다 — 다만 **화면 골격에는 영향이 없다.**

| 동시 편집 | `version_no` 낙관적 잠금 — 공유계약 B-1 |
| 저장 실패 | 헤더·라인이 한 트랜잭션. 부분 저장 없음 — 공유계약 신설 후보 §9-1 |

## §9. 이 장에서 나온 공유 계약 후보

1. **헤더–라인 한 화면은 한 트랜잭션으로 저장한다** — 헤더만 저장되고 라인이 실패하는 부분 저장을 만들지 않는다. `W-01-10`(트랜잭션 원자성)에서 본격적으로 다룰 것의 첫 사례 (§6)
2. **규칙이 금지한 일을 하는 화면은 그 이유를 화면 안에 적는다** — 이 화면은 「MES는 P/O를 만들지 않는다」의 예외다. 배너로 범위를 못박지 않으면 일반 발주 등록으로 쓰인다 (§3 · §5-2)
3. **nullable 외부 키(ERP 번호 등)가 비어 있는 상태를 배지로 드러낸다** — 「미매칭」이 보이지 않으면 대조된 것으로 오인한다. `W-01-09` §9-1(nullable FK 표시)의 확장 (§5-3)
4. **허용치(tolerance)를 화면이 입력받을 때는 그 값이 만드는 후속 비용을 경고한다** — 크게 주면 다음 초과가 같은 경로를 탄다 (§6)
