# P-01-01 · 자재LOT 등록·라벨 발행

## §0. 요약

- **개요**: 미부착 입하 자재에 대해 **서버가 34자리 LOT 번호를 채번하고**(MLOT #16 · 화면은 번호를 만들지 않는다), 서버가 그린 라벨 이미지를 프린터로 인쇄하는 화면이다(사전부착 경로는 `M-01-01`이 처리). 물류(창고)담당이 쓰며, 발행·재발행 이력 관리와 ⭐ **단말 게이팅이 걸리지 않는 POP의 첫 사례**다 — 창고 단말은 공유계약 F-1의 적용 범위 밖이고, 출력 권한은 서버가 403으로 집행한다(§5-5).
- **주요 데이터**: 발행 기록(`app.document_issue_log`)과 자재LOT(`trace.lot`) — 문서/대상 유형, 발행 회차·재발행 사유, 발행 단말·프린터를 기록하고 LOT은 Hold 상태로 생성된다.
- **핵심 액션**: 입하 건 선택 → **등록·인쇄**(LOT 생성 + 발행 기록 + 인쇄, `can_print_label` 필요) → 필요 시 **재인쇄**(회차 증가, 사유 필수).

## §3. 레이아웃 (POP — 1024×768 실측 제약)

**세로 여유가 119px뿐이다**(E-1). 구획을 쌓지 않고 좌우로 편다. 터치 타겟은 크게(G-5).

├──────────────────────────────┬───────────────────────────────────────────┤
│ 《입하 라인》 (미부착)       │ 《채번 대상》                             │
│ ┌──────────────────────────┐ │   품목    ABC-123                         │
│ │ IB-…002  ABC-123  500EA │ │   수량    500 EA                          │
│ │ (주)…    08-04           │ │   공급사  (주)…                           │
│ ├──────────────────────────┤ │                                           │

> **번호는 등록 전에 보일 수 없다.** 서버가 등록 시점에 매기므로(§5-2) 화면이 미리 만들면 그것이
> 실제 번호와 달라진다. 등록에 성공하면 그 자리에 응답으로 받은 번호를 크게 보인다.
>
> ⚠ **34자리를 붙여 쓰지 않는다.** `0001234500000012002607310001230007`을 그대로 보이면 작업자가
> 실물 라벨과 화면을 눈으로 대조할 수 없다. **저장은 원문·표시는 분절 그룹핑**한다 —
> `000123450 · 000001200 · 260731 · 000123 · 0007`. (작업실적 등록 화면(`P-02-04`) §3-3 · 공유계약 후보 6)

**프린터·단말 상태를 머리에 상시 표시한다.** 인쇄가 안 될 때 사용자가 가장 먼저 보는 곳이고, 그것이 없으면 「등록이 안 됐다」고 오해한다.

### §3-6. ⚠ 발번 단위는 「입하 건」이 아니라 「입하 라인」이다

`supplier_lot_missing`도 `lot_id`도 **`inbound_receipt_line`의 속성**이다. 한 입하 건에 미부착
라인이 셋이면 LOT도 셋이고 라벨도 석 장이다. 좌단 목록의 행은 **라인**이어야 페이지네이션과 발번
개수가 맞는다.

목록 원천 = `GET /logistics/inbound-receipts?supplierLotMissing=true&labelIssued=false` 로 건을
좁히고, 선택한 건에서 `GET .../{id}/lines?supplierLotMissing=true&labelIssued=false` 로 라인을
받는다(둘 다 omf-mes#245 에서 신설).

## §4. 필드

### §4-A. 발행 기록 `app.document_issue_log`

| 라벨 | 출처 컬럼 | 타입 | 필수 | 검증·비고 | 입력 |
| --- | --- | --- | :-: | --- | --- |
| 문서 유형 | `document_type_code` | `code_t` | ✅ | `LABEL`(주석 「LABEL \| COA \| TRACE_REPORT 등」) | 자동 |
| **대상 유형** | `target_type_code` | `code_t` | ✅ | ⚠ **다형 참조 — 네 번째** §5-4 | 자동 |
| **대상 ID** | `target_id` | bigint | ✅ | FK 아님 | 자동 |
| 자재LOT | `lot_id` | FK → `trace.lot` | — | **여기만 진짜 FK다** §5-4 | 자동 |
| **발행 회차** | `issue_seq` | integer > 0 기본 1 | ✅ | **1=최초 · 2+=재발행**(주석) | 자동 |
| **재발행 사유** | `reissue_reason_code` | `code_t` | 조건부 | ⬇ CHECK가 강제한다 | 선택 |
| 발행자 | `issued_by` | FK → `app_user` | ✅ | 로그인 사용자 | 자동 |
| 발행 시각 | `issued_at` | timestamptz | ✅ | | 자동 |
| **단말** | `terminal_id` | FK → `mdm.terminal` | — | 어느 POP에서 찍었는가 | 자동 |
| **프린터** | `printer_name` | varchar(100) | — | 어느 프린터로 찍었는가 | 자동 |
| 비고 | `remarks` | text | — | | 입력 |

**두 제약이 재발행 규칙을 강제한다**

```
uq_document_issue_log      UNIQUE (document_type_code, target_type_code, target_id, issue_seq)
ck_document_reissue_reason CHECK  (issue_seq = 1 OR reissue_reason_code IS NOT NULL)
```

- **같은 대상의 같은 회차는 하나뿐이다** — 재발행하면 회차가 오른다
- **2회차 이상은 사유가 필수다** — 사유 없이 재인쇄할 수 없다

**기록 전용이다** — 감사 컬럼이 `created_*`도 아니고 `issued_*`뿐이다. 발행 기록은 수정하지 않는다.

### §5-2. 등록·인쇄가 하는 일 — ⚠ 한 트랜잭션이 아니다

```
① POST /trace/lots            LOT 생성 · 서버 채번 · 입하 보류 자동
                              ↓  (여기서 끊길 수 있다 — 아래 표)
② POST /app/document-issues   발행 기록 (seq=1)
                              ↓  별도 (K-4)
③ GET …/rendition → 셸이 프린터로 전송 → POST …:report-print
```

⛔ **①과 ②는 한 트랜잭션으로 묶을 수 없다.** 발행 기록의 `target_id`가 LOT을 가리키므로 **LOT이
먼저 존재해야 `targets`에 담을 수 있다** — 계약이 그 이유를 명시했다(`POST /trace/serial-numbers`
description · `POST /app/document-issues` description). 두 계약 파일(01 자재창고 · app 공통)이
갈려 있는 것도 같은 사정이다.

> *(기존 서술 폐기 — v0.1 §5-2의 「┌─ 한 트랜잭션 ─ ① `trace.lot` 생성 ② `document_issue_log`
> 발행 기록 ─┐」 그림. 계약이 두 호출로 확정돼 있고 원자성을 보장하는 경로가 없다. omf-mes#245)*

**`W-01-10` §9-2의 조항은 그대로 적용된다** — 프린터는 외부 장치이므로 ③은 트랜잭션 밖이다.
프린터가 죽어 있어도 LOT은 생성되고 기록은 남는다. 인쇄 실패로 LOT 생성을 롤백하면 같은 자재에
대해 채번을 다시 해야 하고, 그사이 다른 단말이 번호를 가져갈 수 있다.

#### ★ ①은 됐는데 ②가 안 된 상태 — 오류가 아니라 표현 가능한 상태다

**되돌리지 않는다.** 롤백하지 않는 이유는 위와 같다.

| ②의 응답 | 다시 부르면 풀리나 | 화면 |
| --- | :-: | --- |
| 응답 없음(네트워크·타임아웃) | ✅ | 「LOT은 등록됐습니다 — 라벨 발행 기록을 만들지 못했습니다」 + **[ 발행 다시 시도 ]**(G-3). 같은 `Idempotency-Key`를 유지해 회차가 두 번 오르지 않게 한다 |
| `403` 이 단말에 출력 권한이 없다 | ⛔ | 「이 단말에서는 라벨을 발행할 수 없습니다. **라벨 프린터가 있는 단말에서 인쇄하세요**」(F-7 — 무엇이 틀렸는지가 아니라 무엇을 하면 되는지). 재시도 버튼을 주지 않는다 |
| `422` 대상이 발행 대상이 아님 | ⛔ | 서버가 준 사유를 그대로 보인다. 재시도 버튼을 주지 않는다 |

**다음 진입 시 다시 나온다.** 그 라인은 `lotId`가 채워지고 `labelIssued = false`이므로, 화면은
**「등록·인쇄」가 아니라 「인쇄」**를 보인다(§5-1). ①을 다시 부르면 LOT이 두 개 생긴다 — 그것이
이 구분이 필요한 이유다.

> **라벨은 서버가 그린다**(결정 18) — POP은 이미지를 받아 프린터로 보낼 뿐이다. 클라이언트가
> 레이아웃을 그리지 않으므로 **단말마다 라벨이 달라지지 않는다.**

### §5-3. ★ 재발행 — 회차와 사유

```
1회차   등록·인쇄        reissue_reason_code = NULL
2회차   재인쇄 (라벨 훼손)  reissue_reason_code = 필수 ← CHECK가 강제
3회차   재인쇄 (분실)      reissue_reason_code = 필수
```

화면은 재인쇄 시 **사유를 반드시 받는다.** 데이터가 강제하므로 화면이 빠뜨리면 저장이 실패한다.

**왜 사유가 필수인가** — 라벨이 여러 장 돌아다니면 같은 LOT이 두 곳에서 스캔될 수 있다. 재발행 이력이 있어야 「이 라벨이 몇 번째인가」를 추적한다.

> ⚠ **이전 라벨의 무효화**는 데이터에 없다. 3회차를 찍어도 1·2회차 라벨은 물리적으로 남아 있고 스캔된다. **무효 처리 규칙이 미정** — §8-2.

### §5-4. ⚠ 다형 참조가 **네 번째·다섯 번째**다

```
approval_request.target_type_code + target_id       W-01-02
audit_event.target_type_code + target_id            #68
goods_receipt.source_document_type_code + _id       W-01-10
document_issue_log.target_type_code + target_id     ← 네 번째
trace.lot.source_type_code + source_id              ← 다섯 번째
```

**한 도메인에서 다섯 곳이다.** `W-01-10` §9-2가 세 곳 규칙으로 승격시킨 조항이 여기서 다섯 곳이 됐다 — 계약에 반드시 들어가야 한다.

> `document_issue_log`는 특이하게 **`lot_id`를 별도 FK로 따로 갖는다.** 대상이 LOT일 때는 진짜 FK로도 연결된다는 뜻이다. 다형 참조와 FK가 공존하는 유일한 사례이고, **대상이 LOT인 발행이 압도적으로 많을 것**을 데이터가 예상한 것으로 읽힌다.

### §5-5. ⚠ 단말 게이팅이 **걸리지 않는다** — 창고 POP은 F-1 적용 범위 밖이다

> *(기존 서술 폐기 — v0.1 §5-5의 「화면은 진입 시 이 플래그를 확인하고, 없으면 「등록·인쇄」를
> 비활성하고 사유를 보인다」 및 「★ 단말 게이팅 첫 사례」 선언. 이 장은 2026-08-04에 쓰였고, 공유계약
> F-1의 **적용 범위 정정은 2026-08-06(v0.9)**이다 — 이 장이 이틀 앞서 쓰여 정정을 반영하지 못했다.
> omf-mes#245)*

`mdm.terminal_process`는 (단말 × **공정**) 매핑이고 `mdm.process`는 **생산 공정 마스터**다.
확대 6차가 전수 실측했다(공유계약 F-1 · `W-CO-06` §5-1) — `mdm.process` 참조 14곳에 **창고 작업
(입하·적치·피킹·이동·재고조사) 0건**, `terminal_id` 컬럼 7곳에 **`logistics` 0 · `inventory` 0**.

**창고 전용 단말은 이 표에서 공정 행 0건으로 남는 것이 정상이다.** 조회 경로를 새로 만들어도 0건이
돌아온다 — **읽을 경로가 없는 것이 아니라 읽을 행이 없다.** 공유계약 F-3(게이트는 판정 근거의
실재를 확인해야 성립한다)이 여기서 미충족이므로 게이트를 세우지 않는다.

**⛔ 그러면 아무나 찍는가 — 아니다. 게이트는 서버가 갖는다.**

```
POST /app/document-issues  →  403 「이 단말에 출력 권한이 없다」
```

공유계약 **F-5**(게이트를 만드는 화면과 집행하는 화면을 나눈다)의 배치다. 근거 화면은 `W-CO-06`,
집행은 서버, 이 화면은 **둘 다 아니다.** 그래서 **F-6 위반이 아니다** — F-6은 게이트를 소유한
화면이 판정에 실패했을 때의 조항인데, 이 화면은 판정하지 않는다.

**403을 받았을 때의 처리는 §5-2의 표에 있다.** LOT은 이미 생겼으므로 부분 실패 복구 경로를 탄다.

> ⚠ **프린터 유무를 대체 게이트로 쓰지 않는다.** `GET /app/printers`가 0건이면 인쇄는 못 하지만
> **등록은 되어야 한다** — §5-2가 「프린터가 죽어 있어도 LOT은 생성되고 기록은 남는다」로 확정했다.
> 프린터 상태는 게이트가 아니라 **머리의 상시 표시**다(§3).

## §9. 이 장에서 나온 공유 계약 후보 — ★ 발행·재발행 신설

1. **발행은 회차로 쌓고 이전 것을 지우지 않는다** — `issue_seq`가 오르고 `UNIQUE(유형, 대상, 회차)`가 중복을 막는다. 재발행은 새 기록이다 (§5-3)
2. **★ 재발행에는 사유가 필수다** — `ck_document_reissue_reason`이 강제한다. 화면이 사유를 받지 않으면 저장이 실패한다 (§5-3)
3. **발행 기록에 단말과 프린터를 남긴다** — `terminal_id`·`printer_name`. 「어디서 몇 번째로 찍었는가」가 추적의 단위다 (§4-A)
4. **인쇄는 트랜잭션 밖이다 — 실패해도 업무 기록은 유효하다** — `W-01-10` §9-2의 두 번째 적용. 프린터 때문에 발번을 롤백하지 않는다 (§5-2)
5. **★ 게이트를 소유하지 않는 화면은 선차단하지 않고 서버 응답을 처리한다** — 판정 근거 행이
   0건인 축(창고 단말 × 생산 공정)에 게이트를 세우면 「판정」이 아니라 「추측」이 된다. 그런 화면은
   게이트를 서버에 두고(403) 화면은 **무엇을 하면 되는지**만 말한다. F-5의 세 번째 역할 —
   근거 화면도 집행 화면도 아닌 「집행 결과 수신 화면」 (§5-5)
6. **물리적으로 유통되는 출력물은 회차를 인쇄면에도 넣는다** — 데이터에만 회차가 있으면 현장에서 구분할 수 없다 (§8-2)
7. **★ 두 호출로 갈린 업무는 「중간 상태」를 데이터로 표현할 수 있어야 한다** — 원자성을 못 주는
   대신 `lotId`(생겼는가)와 `labelIssued`(찍었는가) 두 축으로 세 상태를 가른다. 중간 상태를
   표현할 축이 없으면 부분 실패가 「알 수 없음」이 되고 화면이 ①을 다시 불러 중복을 만든다 (§5-2)
