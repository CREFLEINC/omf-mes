# W-01-01 · IQC 수입검사·판정

> 작성일: 2026-07-31 · 서식: `00-화면스펙서식.md` v0.1 · 작성 주체: CREFLE OMF 팀 (UI/UX)

## §0. 요약

- **개요**: 관리웹에서 품질담당(IQC 담당자)이 입고 LOT을 스캔해 수입검사(IQC)를 진행하고 합격·불합격·보류를 판정하는 화면. 좌측 검사 대기 큐(Hold LOT 목록) + 우측 진행 중 1건의 점검·판정 상세로 구성된 좌우 2단 레이아웃이다.
- **데이터**: 검사 의뢰(`quality.inspection_request`)·검사 결과(`quality.inspection_result`)·항목별 측정치(`quality.inspection_measurement`)를 다루며, 판정에 따라 LOT 상태(Release/Hold 유지)가 전이된다.
- **핵심 액션**: LOT 스캔 → 검사기준 항목별 측정치 입력 → 합격/불합격/보류 수량 3분할 입력(합계는 검사수량과 반드시 일치) → 종합 판정 선택 → 임시 저장 또는 판정 확정(입력과 확정은 2단계로 분리되며, 확정 시점에만 LOT 상태가 전이된다).

| 라벨 | 출처 컬럼 | 타입 | 필수 | 검증·비고 | 입력 |
| --- | --- | --- | :-: | --- | --- |

| **합격수량** | `accepted_qty` | `qty_t` 기본 0 | ✅ | ⬇ 합계 제약 | 입력 |
| **불합격수량** | `rejected_qty` | `qty_t` 기본 0 | ✅ | ⬇ | 입력 |

**⚠ 합계 제약이 UI를 지배한다**

```
ck_inspection_result_qty:  accepted_qty + rejected_qty + held_qty = inspected_qty
```

세 칸의 **합이 검사수량과 정확히 일치해야만 저장된다.** 화면은 실시간으로 합계와 잔여를 보여주고, 불일치 상태에서 확정 버튼을 비활성화한다. 「합격만 입력하면 나머지가 자동」 같은 편의는 **어느 칸을 자동 계산할지 규칙이 정해진 뒤에** 얹는다 — §8-4.

### §4-C. 항목별 측정치 `quality.inspection_measurement`

검사기준 버전의 항목 수만큼 행이 생기는 **반복 입력 그리드**다. 3계층(검사실적 → 검사결과 → 검사측정치, ✓설계확정 결정 01)의 3층.

## §5. 액션·상태

### §5-1. 판정 분기 — 4갈래 (OR 226:5724)

| 분기 | 결과 | 후속 |
| --- | --- | --- |
| **[양품]** | **Lot Status = Release** (Hold 해제) | 메인 복귀 → 정상품 입하 처리(545:6596 · `W-01-10`) |
| **[부분 입고 허용]** | **LOT 수량 정정**(226:5738) + 불량분 분리 | → 01-S-I ⚠ **고객사 협의 대기** §8-2 |
| **[불량]** | Hold 유지 | → 01-S-I 반품 |
| **[의심자재]** | 입고 대기·지연 | 01-SC1 마커 · 의심자재등록 엔티티 |

**생략 경로 2종**(이 화면 밖에서 결정되어 들어옴): [샘플링 미대상] → Release(그룹 판정 승계) / [긴급승인] → **한도승인**(G/R 자동 제외 · 권한자=MES 권한 보유 관리자·매체=관리웹, ✓확정 2026-07-27)

### §5-2. ⚠ 입력과 확정이 2단계다

`confirmed_at`이 별도 컬럼이라는 것은 **「결과 입력」과 「판정 확정」이 같은 순간이 아님**을 뜻한다.

- **임시 저장** — 측정치·수량을 저장하되 Lot Status는 **전이하지 않는다**
- **판정 확정** — `confirmed_at` 기록 + **Lot Status 전이(Release/Hold 유지)** + `lot_hold.released_at`·`released_by` 기록

> Lot Status 전이가 정확히 확정 시점인지, 권한이 분리되는지(검사자 ≠ 확정자)는 미결 — §8-3.

### §5-3. 재검사

`inspection_round`와 `previous_result_id`가 있으므로 **재검사가 데이터에 설계돼 있다.** 화면은 이전 회차를 읽기 전용으로 보여주고 새 회차를 추가한다. **이전 회차는 수정하지 않는다.**

## §7. DS 매핑

### §7-1. 갭 아님 — **편집 그리드는 `c`(조합)다**

항목별 측정치 입력은 「편집 가능한 표」가 필요해 갭처럼 보이나, **`Table`의 컬럼이 커스텀 렌더러를 지원한다**:

```ts
TableColumn.render?: (row: T, rowIndex: number) => ReactNode
```

→ 셀에 `TextField`·`Select`를 넣으면 된다. **`c`(조합) — DS 이슈 없음.**

> **세 번째로 「갭처럼 보였으나 조합」인 사례**다(검색 바 · 스캔 · 편집 그리드).

### §7-2. 구성

| 용도 | 컴포넌트 | 유형 |
| --- | --- | --- |
| 검사 대기 큐 | `Table`(compact·sort) + `SearchInput`+`Select` 필터 | a + c |
| LOT 스캔 | `TextField` 포커스 고정 (= `ScanField` 제품 공용) | **c** |
| 항목별 측정치 | `Table` + `render`(`TextField`·`Select`) | **c** |
| 수량 3분할 입력 | `TextField` ×3 + 실시간 합계 표시 | c |
| 판정 선택 | `Select` | a |
| 대상 정보 | `Card` | a |
| 확정·임시저장 | `Button`(`filled` / `outlined`) | a |
| 합계 불일치·미검교정 경고 | `AlertBanner` | a |
| 재검사 이력 | `Tabs` 또는 `Dialog`+`Table` | c |

**이 화면에서 새로 발견한 갭 없음** *(2026-07-31 실측 기준)*. 기존 G-1(계층)·G-5(터치)·G-6(키패드)는 이 화면에 해당하지 않는다.

### §7-3. ⚠ **`ds-gap` G-14**(여러 줄 텍스트 입력) — **만드는 곳과 쓰는 곳이 다르다**

*(2026-08-21 추가 — 구현팀 질의 `omf-mes#170` 이 §7-2 를 「신규 DS 갭 없음」으로 읽고 client#85 와 어긋난다고 물었다.)*

> ⛔ **`ds-gap` 을 반드시 앞에 붙여 읽는다.** **공유계약에도 G-14 가 있고 전혀 다른 조항**이다 — 공유계약 G-14 는 「현장 단말은 진입 시 미확인 공지를 먼저 보인다」이고, 여기서 말하는 것은 **`ds-gap` G-14 「여러 줄 텍스트 입력」**이다.

⛔ **위 「갭 없음」은 이 화면의 «매핑»에 대한 말이고, 2026-07-31 시점의 스냅샷이다.** 그 뒤 **2026-08-12 에 `ds-gap` G-14(여러 줄 텍스트 입력)가 신설**됐다 — DS 고정 커밋 `2891ae8` 에 `TextArea` 도 `TextField` 의 `multiline`·`rows` 도 **없다**(전수 검색 `textarea` 0건). 유형 **`d`**(진짜 새 원시 요소) · **DS #74 OPEN** · 그때까지는 **토큰을 입힌 `<textarea>` 로 제품에서 먼저 만든다.**

⭐ **그런데 이 화면은 `ds-gap` G-14 를 쓰지 않는다.**

**`ds-gap` 은 화면 108건 전부를 대조해 채우므로, 없다는 것이 누락이 아니라 판정이다.**

⭐ **그러면 client#85 §6 은 무엇을 지시했나** — **공용 부품을 «만들라»**는 것이지 이 화면이 **쓴다**는 말이 아니다. 03 품질 착수 순서에서 이 화면이 첫 번째라 **17곳이 함께 쓸 부품의 제작을 여기에 붙인 것**이다. **만드는 곳 ≠ 쓰는 곳.**

> ⚠ **「신규 DS 갭 없음」 같은 문장은 반드시 시점과 범위를 달고 써야 한다.** 범위 없이 쓰면 **화면 매핑에 대한 말이 저장소 전체에 대한 말로 읽힌다** — #170 이 정확히 그렇게 읽었다.

## §9. 이 장에서 나온 공유 계약 후보

1. **합계 제약의 UI 표현** — `CHECK(a+b+c = total)` 류는 **실시간 잔여 표시 + 불일치 시 확정 비활성**. 자동 계산은 규칙 확정 후에만 (§4-B)
2. **「입력」과 「확정」의 2단계 분리** — `confirmed_at` 류 컬럼이 있는 화면은 저장과 상태 전이를 분리한다. 판정·승인 13건 공통 후보 (§5-2)
3. **회차 이력 불변** — 이전 회차·이전 실적은 수정하지 않고 새 레코드를 쌓는다 (§5-3 · `P-02-04` 정정 실적과 같은 패턴)
4. **스캔은 폼팩터가 아니라 입력 방식** — 웹 화면에도 스캔 규약이 적용된다 (§3)
5. **미확정 코드 목록의 화면 처리** — 회신 대기로 선택지가 빈 필드를 어떻게 보일지 통일 규칙 필요 (§8-1)
