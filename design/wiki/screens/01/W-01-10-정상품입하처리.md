# W-01-10 · 정상품 입하 처리 (입고 확정·Release·G/R 송신)

> 작성일: 2026-08-04 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> ★ **트랜잭션 원자성의 첫 사례.** 한 번의 확정이 5가지를 움직이고, 그중 하나는 **트랜잭션 밖**이다. 이 장이 그 경계를 정한다.

## §0. 요약

- **개요**: 관리웹에서 물류(창고)담당·품질담당이 IQC 합격·샘플링 미대상·한도승인으로 판정이 끝난 자재LOT의 입고를 확정하는 화면. 좌측이 확정 대기 큐, 우측이 확정 폼인 좌우 2단 레이아웃이며, 확정 시 LOT 상태가 Hold에서 가용(Release) 또는 한도승인으로 전이된다.
- **주요 데이터**: 입고 전표(`logistics.goods_receipt`)·입고 라인(`goods_receipt_line`)·수불원장(`inventory.inventory_transaction`)·재고 잔고(`inventory.inventory_balance`)·연계 메시지(`integration.integration_message`)·자재LOT(`trace.lot`).
- **핵심 액션**: 확정 대기 큐에서 LOT 선택 → 입고 창고·적치 위치 선택(둘 다 필수) → 입고 확정. 확정 한 번이 한 트랜잭션 안에서 입고 전표 생성·LOT 상태 전이·수불원장 기록·재고 가용 수량 갱신을 처리하고, ERP G/R 메시지를 대기열에 적재한다(실제 전송은 트랜잭션 밖 · 한도승인 건은 제외).

## §5. 액션·상태

### §5-1. 이 화면이 닫는 공백

인벤토리 근거가 이 화면의 존재 이유를 못박는다 — **「IQC 생략 경로가 화면 없이 Release되던 공백을 닫는다」**.

세 경로가 **모두 이 화면으로 모인다.**

| 진입 | 판정 | 결과 재고 상태 |
| --- | --- | --- |
| IQC 합격(`W-01-01`) | 합격 | **가용(Release)** |
| 샘플링 미대상(545:6632) | 그룹 판정 승계 | **가용(Release)** |
| 긴급승인→한도승인(`W-01-02`) | 조건부 | **한도승인** · ⚠ G/R 제외 |

**Release가 화면 없이 일어나면 누가 언제 창고·위치를 정했는지 기록이 없다.** 그래서 이 화면이 신설됐다.

### §5-2. 창고와 위치를 **여기서** 정한다

`warehouse_id`와 `destination_location_id`가 **둘 다 `NOT NULL`**이다. 입고 확정 없이는 정해질 수 없다.

이것이 앞서 확정된 **「창고는 제약이 아니라 건별 입력값이다」**와 정확히 맞물린다 — 품목유형 × 창고유형을 제한하는 제약이 물리 모델에 **0건**이고, 입고 시점에 담당자가 고른다.

> 적치 위치가 `NOT NULL`이므로 **입고 확정 시 위치가 확정된다.** 이후 `M-01-05`(적치·입고 완료)가 실물을 옮기고, 다르면 `M-01-07`(임시 위치 적재)·`M-01-10`(재고이동)으로 조정한다.

### §5-3. ⚠ 다형 참조가 **세 번째**다

```
goods_receipt.source_document_type_code + source_document_id   ← 여기
approval_request.target_type_code + target_id                  ← W-01-02
audit_event.target_type_code + target_id                       ← #68
```

**같은 패턴이 셋이고 모두 FK가 없다.** 유형 코드와 테이블의 대응 규약이 없으면 **화면이 원천 문서를 표시할 수 없다.** `W-01-02` §9-2에서 제안한 계약 조항이 여기서 세 번째 사용처를 얻는다 — 이제 「세 곳 규칙」을 충족한다.

### §5-4. ★ 확정 한 번에 다섯이 움직인다 — 그중 하나는 트랜잭션 밖

```
┌─ 한 트랜잭션 ─────────────────────────────────────────┐
│ ① goods_receipt + line          입고 전표 생성        │
│ ② trace.lot.status_code         Hold → 가용/한도승인  │
│ ③ inventory_transaction + line  수불원장 기록         │
│ ④ inventory_balance             가용 수량 갱신        │
│ ⑤ integration_message           G/R 메시지 **적재**   │
└───────────────────────────────────────────────────────┘
                                          ↓ 별도 워커
                                    ERP 실제 전송
```

**⑤가 「적재」이지 「전송」이 아닌 것이 핵심이다.**

`integration_message`가 **outbox 패턴**으로 설계돼 있다(실측).

| 컬럼 | 역할 |
| --- | --- |
| `message_key` UNIQUE | 멱등 — 같은 건이 두 번 쌓이지 않는다 |
| `available_at` | 언제부터 보낼 수 있는가 |
| `locked_at` · `locked_by` | 워커 선점 |
| `retry_count` · `last_error_message` | 재시도 |
| `sent_at` · `completed_at` | 전송·완료 시각 |

**외부 시스템 호출을 트랜잭션 안에 넣으면 안 된다.** ERP가 느리면 DB 트랜잭션이 그만큼 잡혀 있고, ERP가 실패하면 입고까지 롤백된다. 그래서 **메시지를 큐에 넣는 것까지가 트랜잭션**이고 전송은 밖이다.

> ✓확정 **QA #1**이 「ERP G/R = **건별 즉시**」라 했으나, **「즉시」는 전송 시도의 즉시성이지 트랜잭션 포함을 뜻하지 않는다.** outbox의 `available_at`을 현재로 두면 워커가 곧바로 집어간다 — 요구는 충족되고 트랜잭션은 짧게 유지된다.

**화면은 이것을 정직하게 말한다** — §3의 결과 구획에 「**ERP G/R 송신 대기열에 적재** ⚠ 즉시 전송 아님」. 확정 직후 ERP에서 조회해도 없을 수 있다.

### §5-5. 한도승인 건은 ⑤가 없다

✓확정 QA #1 — 「G/R = **합격품 한정**」. `W-01-02` §5-4에서 확인한 「G/R 자동 제외」가 여기서 실행된다.

```
IQC 합격 · 샘플링 미대상  →  ①②③④⑤
한도승인                  →  ①②③④    (⑤ 없음)
```

화면은 대상 선택 시 **결과 구획을 바꾼다.** 한도승인 건에서 ⑤를 그대로 보이면 승인자가 ERP에 반영된 줄 안다.

### §5-6. 1:N 혼적

✓확정 QA #14 — 「입고—자재LOT **1:N 혼적** 실재」. 한 입고 전표에 여러 LOT 라인이 붙는다. `goods_receipt_line`이 여러 행이 되는 것으로 표현된다.

화면은 **여러 LOT을 한 번에 확정**할 수 있어야 한다. 다만 창고·위치가 LOT마다 다를 수 있으므로 **라인별 위치 지정**이 필요하다 — §8-4.

> ⚠ 같은 확정에 「LOT 수량 비고정 — 품목별 보관단위 기본값 + 개별 override」(QA #14)가 딸려 있는데, **품목 확장속성이 모델 미반영**(#64)이라 기본값을 읽을 곳이 없다. §8-5.

## §9. 이 장에서 나온 공유 계약 후보 — ★ 트랜잭션 원자성 신설

**공유계약에 원자성 조항이 없다.** `M-01-01` §9-1 · `W-01-03` §9-1이 예고한 것을 여기서 세운다.

1. **한 확정이 여러 엔티티를 움직이면 전부 한 트랜잭션이다** — 부분 성공을 만들지 않는다. 입고 확정은 전표·LOT 상태·수불원장·잔고를 함께 움직인다 (§5-4)
2. **★ 외부 시스템 호출은 트랜잭션 밖이다 — outbox에 적재까지가 안이다** — ERP·프린터 같은 외부 호출을 트랜잭션에 넣으면 상대가 느릴 때 DB가 잡히고 상대가 실패할 때 우리 업무까지 롤백된다. `integration_message`가 이미 outbox로 설계돼 있다(`available_at`·`locked_by`·`retry_count`) (§5-4)
3. **「즉시」는 전송 시도의 즉시성이지 트랜잭션 포함이 아니다** — 확정 기록의 「건별 즉시」를 트랜잭션 동기 호출로 읽지 않는다 (§5-4)
4. **화면은 「무엇이 아직 안 됐는가」를 말한다** — 확정 직후 ERP에 없을 수 있다는 것을 결과 구획에 적는다. 「완료」라고만 하면 사용자가 ERP를 보고 혼란스러워한다 (§3 · §5-4)
5. **경로마다 결과가 다르면 결과 구획도 달라진다** — 한도승인 건은 ERP 송신이 없다. 같은 화면이 같은 안내를 보이면 오해한다 (§5-5)
6. **트랜잭션 기록은 정정하지 않고 역분개한다** — `inventory_transaction.reversal_of_transaction_id`가 그 형태다. `W-01-01` §9-3(회차 이력 불변)의 재고 판 (§6)

### §9-2. 다형 참조 조항 — 세 곳 규칙 충족

`approval_request` · `audit_event` · `goods_receipt` **세 곳**에서 같은 패턴이 나왔다. **계약 조항으로 승격한다.**

> **`{X}_type_code` + `{X}_id` 형태의 다형 참조는 유형 코드와 대상 테이블의 대응표를 계약이 정한다.** FK가 없으므로 규약이 없으면 서버·화면이 각자 해석해 갈린다. 화면은 대응표에 없는 유형 코드를 만나면 **원본 코드를 그대로 보이고 링크를 만들지 않는다.**
