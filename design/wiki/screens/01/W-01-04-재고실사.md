# W-01-04 · 재고실사

> 작성일: 2026-08-05 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> 유일한 **관리웹** 화면이고 **오프라인이 금지**된 화면이다. `M-01-11`(모바일·오프라인 허용)과 **같은 실사 레코드를 다루는데 오프라인 정책이 반대**다.

## §0. 요약

- **개요**: 관리웹에서 물류담당(+회계/관리)이 창고 재고실사를 개시(정기/수시, 블라인드 여부는 개시 시에만 결정)하고, 목록에서 실사를 선택해 요약 카드(계획/카운트/미실사/차이) + 탭(전체·차이 있음·미실사) + 라인 표로 진행 상황을 조회하며 차이 사유를 입력·마감하는 화면. 오프라인이 금지된 관리웹 유일 화면이며, 모바일 화면(`M-01-11`)과 같은 실사 레코드를 다루지만 오프라인 정책은 반대다.
- **데이터**: 실사 헤더 `inventory.inventory_count`(11열)·카운트 라인 `inventory.inventory_count_line`(14열)을 다루며, 조정(`inventory.inventory_adjustment`)은 `W-01-12` 소관이라 참고만 한다.
- **핵심 액션**: 실사 개시(창고·유형·계획일 입력, 라인은 서버가 장부에서 생성) → 조회·실사 선택 → 차이 사유 입력·(②안 채택 시) 실물 수량 수정 → 미실사 0건 AND (차이 0건 또는 조정 완료) 시 실사 마감. 차이 1건 이상이면 `W-01-12`로 조정 등록을 안내한다.

## §5. 액션·상태

### §5-1. ★ 같은 레코드를 두 화면이 다루는데 오프라인 정책이 반대다

```
W-01-04  (관리웹)  ⛔ 오프라인 금지   ← 결정 08
M-01-11  (모바일)  ✅ 오프라인 허용   ← C-1
        ↑ 둘 다 inventory_count / _line 을 다룬다
```

**§C 어디에도 「어느 화면이 오프라인을 허용하는가」의 목록이 없다.** C-1~C-4는 「오프라인이면 이렇게 한다」만 정하고 **누가 오프라인인지는 정하지 않는다.**

세 갈래가 다 나왔다:

| 정책 | 화면 | 근거 |
| --- | --- | --- |
| **오프라인 허용** | `M-01-04`·`05`·`07`·`08`·`09`·`10`·`11` | C-1 |
| ⛔ **오프라인 금지** | **`W-01-04`** | 결정 08 |
| ⛔ **온라인 전용** | `M-02-01`·`M-02-02` | ✓확정 2026-07-24 #2·#3 |

⚠ **「금지」와 「온라인 전용」이 같은 말인가**가 정리되어 있지 않다. 배지 정본은 웹에 「오프라인 금지」, 02 모바일에 「온라인 전용」이라고 서로 다르게 적었다.

**해석**: 같은 뜻이고 **표현만 갈렸다**. 다만 이유가 다르다 —

| | 이유 |
| --- | --- |
| `W-01-04` 오프라인 금지 | **관리웹은 애초에 오프라인을 만들지 않는다**(셸 성격) |
| `M-02-01`·`M-02-02` 온라인 전용 | **모바일인데 예외로 금지**(업무 성격 — 실시간 인계) |

**후자가 계약이 다뤄야 할 것이다** — 전자는 셸 규격이라 화면마다 적을 일이 없다.

→ **§C 신규 조항 후보** §9-1.

### §5-2. 블라인드는 개시 시에만 정한다

```
blind_count  boolean NOT NULL DEFAULT false
```

**실사가 시작된 뒤 바꾸면 안 된다** — 일부 라인은 장부를 보고 세고 일부는 안 보고 센 상태가 되어 결과의 성격이 섞인다.

**DB가 막지 않는다**(그냥 boolean 컬럼). **화면이 진다**(A-9 ⓐ 차단):

| 상태 | 블라인드 |
| --- | :-: |
| 개시 전(계획) | ✅ 편집 |
| **진행 중** | ⛔ **잠김** — G-3대로 사유 + 경로 표시 |
| 완료·마감 | ⛔ 잠김 |

```
진행 중에는 바꿀 수 없습니다. 새 실사를 개시하세요.
```

⚠ **`M-01-11` §5-1의 「서버가 `system_qty`를 안 내려보낸다」와 짝이다** — 이 화면이 블라인드를 켜면 모바일 API 응답이 달라진다.

### §5-3. 웹에서 실물 수량을 고칠 수 있나

프로세스는 카운트를 **모바일 소관**으로 두었다(219:5551). 인벤토리도 「조정은 관리웹 `W-01-04`」라고 **역할을 갈랐다.**

**그런데 현장에서 실수가 나오면 어디서 고치나.**

| 안 | 동작 |
| :-: | --- |
| **① 웹 편집 불가** | 모바일에서 다시 센다 — 역할 분리가 깨끗하다 |
| **② 웹 편집 가능** *(권고)* | 재실사가 어려운 경우(먼 창고·야간)를 위해 · **누가 고쳤는지 남긴다** |

**②를 권고**하되 **`counted_by`를 바꾸지 않는다** — 실제로 센 사람은 그대로 두고 **수정 이력은 `audit.audit_event`**에 남긴다.

감사 키 규약은 공유계약 B-5에 있지만 **실사 라인 수정 이력의 기록 방법은 별도 미결**이다 → §8-2. 통보 274의 카운트 담당 귀속과 수정 이력 보존은 구분한다.

### §5-4. 「차이 없음」과 「미실사」를 화면이 갈라야 한다

`counted`가 카운트 여부의 정본이다(통보 273 · `omf-mes#521`). `counted=false`는 미실사이며 수량·담당 계정·시각으로 추정하지 않는다. `counted=true`이고 차이가 0이면 카운트됨·차이 없음, 0이 아니면 카운트됨·차이 있음이다. 담당 계정이 null이거나 실물 수량이 0이어도 카운트를 완료할 수 있다.

블라인드 미실사 라인만 장부 수량을 생략하고 실물·차이의 응답 0은 자리값으로 취급한다. 카운트 후에는 장부와 실제 차이를 공개한다. 블라인드 첫 카운트 제출은 차이 사유 필수의 예외이며 이 화면에서 사유를 보완한다(`M-01-11` §5-1). 위치 치환 시 완료 상태를 유지할 라인은 모두 함께 보내야 한다. 누락한 기존 라인은 삭제하지 않고 미실사로 돌아가며 다른 위치는 바꾸지 않는다.

### §5-4-a. 음수 장부 수량도 실사 기준으로 보존한다

실사 개시 시 해당 창고의 재고를 **위치·품목·LOT·단위**(`locationId`·`itemId`·`lotId`·`uomId`)로 묶어 실제 잔액을 합산한다. 합계가 음수여도 그 값을 장부 수량으로 보존한다. **0으로 자르거나 음수 묶음을 실사에서 제외하지 않으며, 음수 재고가 있다는 이유만으로 창고 전체의 실사 개시를 거부하지 않는다.** 근거: 음수 재고 실사 검토 요청 `omf-mes#513`.

개시 때 만들어진 라인의 장부 수량은 이후 실물 입력·수정 시에도 개시 스냅샷을 유지한다. 현장에서 새로 추가한 라인은 **등록 시점**에 같은 네 축의 재고 잔액을 합산해 고정하며, 일치하는 잔액이 없을 때만 0이다. 음수도 그대로 보존한다.

실물 수량은 기존대로 **0 이상**만 받는다. 서버가 계산하는 차이는 **실물 수량 − 장부 수량**이다. 장부가 −5이고 실물이 0이면 차이는 **+5**이며, 0으로 바꾸어 차이를 없애지 않는다. 블라인드 공개 범위와 미실사 판정은 §5-4의 통보 273 반영 규칙을 따른다.

위 문단은 음수 허용 품목을 실제 운용할 때의 **업무 요구**로 유지한다. 현재 서버는 실사 개시
스냅샷에서 음수 합계를 하나라도 찾으면 400 `INVALID`(`field=warehouseId`)로 창고 전체 개시를
거부한다. 음수 묶음만 제외하거나 0으로 바꾸지 않으며, 실사 헤더·라인·멱등 완료 기록은 같은
트랜잭션에서 0건으로 롤백된다. 채번은 트랜잭션 전에 이루어져 번호 공백은 생길 수 있지만 부분
실사가 만들어졌다는 뜻은 아니다. 실사 점유·동결도 시작되지 않는다. 기존 실사의 현장 신규 라인도
등록 시점 장부 합계가 음수이면 그 위치 치환 전체를 거부한다. 이미 저장된 음수 `systemQty`는
조회·실물 입력 과정에서 0으로 고치지 않는다.

### §5-5. 조정은 이 화면 밖이다 — 그러나 경계가 얇다

**v1.2 범위 축소**로 조정 등록(219:5554)이 `W-01-12`로 갔다. 근거는 「독립 메뉴: **ERP 조정 전표 + 승인 마커 (U-D1)**」 — 결재선과 전표 종류가 달라 화면을 가른 것이다(`W-01-05`·`W-01-06` 분리와 같은 기준).

**이 화면은 「조정 등록 →」 링크만 둔다.**

**미실사 0건이며 차이가 없거나 차이 라인의 조정이 완료돼야 마감한다.** 차이 라인마다 연결된 조정 라인이 하나 이상 있고 그 부모 조정이 `POSTED`(전기완료)일 때만 조정 완료로 센다. 등록·승인중·반려는 완료가 아니다. 특정 수량을 비교해 조정 완료 여부를 새로 추정하지 않는다(통보 275).

마감 차단 사유는 **`ALREADY_CLOSED`(이미 마감) → `STATE_LOCKED`(상태 잠김) → `COUNT_REMAINING`(미실사 잔여) → `VARIANCE_UNADJUSTED`(미조정 차이)** 순서다. 화면에 보인 마감 가능 여부와 관계없이 서버는 저장 잠금 안에서 다시 판정한다. 성공하면 `COMPLETED`(완료)로 바뀐다. 동결 정책과 웹 수량 수정 이력의 미결은 그대로다.

### §5-6. 집계·조회 성능 — 주제가 여기서 먼저 걸린다

창고 하나의 실사 라인은 **수백~수천 건**이다. `variance_qty`가 GENERATED STORED라 정렬·필터는 인덱스로 가능하나, **요약 4칸(계획/카운트/미실사/차이)은 집계 쿼리**다.

**규칙**: 요약은 **서버가 계산해 내려보낸다.** 화면이 전체 라인을 받아 세지 않는다 — 페이지네이션과 어긋난다.

→ (`W-02-08`·`W-01-07`)의 「집계·조회 응답 설계」와 **같은 요구**다. §9-3.

### §5-6-a. 개시·조회 규칙

개시 시 창고 재고를 위치·품목·LOT·단위로 합산하고 **합계 0인 묶음만 제외**한다. 음수 합계가 하나라도 있으면 §5-4-a의 현재 지원 경계대로 창고 전체 개시를 거부한다. 음수가 없을 때 네 축의 안정적인 순서로 `lineNo`를 1부터 부여하며 실사 번호는 공장·계획일을 기준으로 `IC` 번호를 서버가 발번한다. 신규 실사 상태는 `IN_PROGRESS`(진행중)다. `PLANNED`(계획)는 기존·외부 적재 행에 유지하고 첫 위치 치환 때 진행중으로 바꾼다(통보 272·274).

목록의 계획일 기간은 **양 끝 날짜를 포함**한다. `plannedDate DESC`, 같은 날이면 실사 식별자 내림차순으로 고정 정렬한다. 요약의 카운트·미실사는 `counted`를 기준으로 집계한다.

## §9. 이 장에서 나온 공유 계약 후보

1. **★ §C가 「어느 화면이 오프라인인가」를 정하지 않는다** — 세 정책이 다 나왔다(허용 7 · 금지 1 · 온라인 전용 2). **셸 성격상 오프라인이 없는 것**(관리웹)과 **모바일인데 업무상 금지한 것**(`M-02-01`·`M-02-02`)은 다르다. **후자를 계약이 목록으로 갖고 이유를 함께 적는다** (§5-1)
2. **같은 레코드를 두 셸이 다루면 편집 권한을 화면이 아니라 **컬럼 단위**로 가른다** — `counted_qty`는 모바일이 쓰고 `variance_reason_code`는 웹이 쓴다. 화면 단위로 「이 화면은 조회 전용」이라 하면 실무가 막힌다 (§5-3)
3. **요약·집계는 서버가 계산해 내려보낸다** — 화면이 전체 라인을 받아 세면 페이지네이션과 어긋난다. 조회 화면 주제가 먼저 나왔다 (§5-6)
