# M-01-08 · 자재 출고·피킹

> 작성일: 2026-08-05 · 서식: `00-서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **결정 10의 「Hold 차단 판정은 캐시 없음」과 C-1의 오프라인 허용이 정면으로 부딪친다.** 규칙 둘 다 확정인데 한 화면에서 동시에 지킬 수 없다.

## §0. 요약

- **개요**: 물류(창고)담당이 모바일(360×720dp · 스캐너 일체형 PDA)에서 출고요청을 소화해 자재 LOT를 피킹하고 출고를 확정하는 스캔형 화면이다. 출고 QR 발행은 `P-01-02`(POP)가 담당한다.
- **주요 데이터**: 피킹 라인(`logistics.picking_line`), 출고 전표(`logistics.goods_issue`·`goods_issue_line`), 자재 출고 요청(`logistics.material_issue_request`·`_line`), 재고 예약(`inventory.inventory_reservation`), 품목 선출 정책(`mdm.item.fifo_policy_code`)·LOT 유효기한(`trace.lot.expiry_date`)·LOT 보류(`trace.lot_hold`).
- **핵심 액션**: 출고요청 선택 → 라인 선택(보류 라인 비활성) → LOT 스캔 → 수량 입력(키패드) → 출고 확정(1건 이상, 오프라인이면 「미확정」 표식 유지).

## §5. 액션·상태

### §5-1. B-9 — 출고요청과 피킹 지시가 선행이다

```
picking_line.picking_order_id             NOT NULL
material_issue_request.work_order_id      NOT NULL
```

**출고요청은 W/O 발행 시 자동 생성**된다(REQ-PR-0022 — 「작업계획 기반 필요 수량 자동 산정」). 프로세스는 그 지점을 **`화면없음:시스템자동`**(219:5458)으로 못박았다.

| 선행 | 상태 |
| --- | --- |
| `W-02-04` W/O 확정·배포 | ✅ 작성됨 — 출고요청 자동 발행 경로 |
| `W-02-10` 추가 자재 출고 요청 | ⏳ **수동 발행 경로가 아직 없다** |
| 피킹 지시 생성 | ⚠ **누가 만드는지 미정** §8-1 |

⚠ **긴급 W/O는 자동 발행에서 제외**된다(✓확정 2026-07-14 #4·#5·#7·#8). 긴급은 **기출고 라인 재고를 교차 투입**하고 부족분만 수동 요청한다 → 이 화면은 긴급 건을 **일반 요청과 같게** 다룬다(사유 코드로만 구분).

### §5-2. ⛔ 「Hold 차단」과 「오프라인 허용」이 동시에 성립하지 않는다

**두 확정이 부딪친다.**

```
결정 10   출고·출하·Picking 차단 판정은 Lot Status 단일 지점 참조 · 캐시 없음
C-1       로컬 저장 후 즉시 성공 피드백 — 통신을 기다리지 않는다
```

오프라인이란 **서버를 볼 수 없다**는 뜻이고, 「캐시 없음」이란 **서버를 봐야만 한다**는 뜻이다.

**게다가 볼 대상이 없다.** §I-11이 이미 기록한 대로 **Lot Status 현재 상태 테이블이 물리 모델에 없다.** 실재하는 것은 `trace.lot_hold`(보류 **이력**)와 `trace.lot.status_code`(수명주기)뿐이다.

| 결정 10이 말하는 것 | 실재 |
| --- | --- |
| 판정 정본 = Lot Status **현재 1행** | ⛔ 없음 |
| Lot Status **변경이력 1:N** | ⛔ 없음(`previous_status` 류 0건) |
| 화면이 조회할 **단일 지점** | `trace.lot_hold`의 `status_code`·`released_at`로 **유추**해야 한다 |

**A-11 적용 — 물러난 수준을 명시한다.**

| | 확정 | 물러난 수준 |
| --- | --- | --- |
| 판정 근거 | Lot Status 단일 지점 | `lot_hold` **미해제 행 존재 여부** |
| 캐시 | 금지 | **온라인에서만 금지 · 오프라인은 §5-3** |

### §5-3. 그래서 오프라인에서 출고를 어떻게 하나 — 세 안

| 안 | 동작 | 대가 |
| :-: | --- | --- |
| **① 출고 화면을 오프라인 금지** | 「연결 후 사용하세요」 | 창고 안쪽에서 출고가 멈춘다. **결정 17 시나리오 2가 무너진다** |
| **② 캐시 판정 + 서버 재검증** *(권고)* | 마지막 동기 시점의 보류 목록으로 화면이 막고, **서버가 최종 판정**해 거부 건만 되돌린다(C-2) | 이미 실물이 나간 뒤에 거부가 온다 |
| ③ 무판정 출고 | 서버만 판정 | 작업자가 보류품을 들고 라인까지 간다 |

**②를 권고**한다. 근거:

- **C-2가 이미 같은 구조를 확정했다** — 「로컬은 큐 내 중복만 선검사 · 서버가 거부하면 **해당 건만** 되돌린다 · **전체 롤백 금지**」. 유일성 판정에 쓴 방식을 보류 판정에 그대로 쓴다
- **결정 17 시나리오 2**가 오프라인 출고를 전제한다 — 「정상 시 출고(01-S-E)·입고(01-S-F) 별개 단말 → 통신 두절 시 **단일 단말 큐로 축퇴**」(✓확정 2026-07-24 #8). 출고가 오프라인 금지면 이 확정이 성립하지 않는다

**⚠ ②의 대가를 화면이 지어야 한다.** 거부가 오면 **실물이 이미 라인에 가 있다** — 되돌리는 것은 화면이 아니라 사람이다. 그러므로:

1. 오프라인 출고 건은 **「미확정」 표식을 유지**한다(C-1의 「즉시 성공 피드백」의 **예외**)
2. 거부 시 **회수 지시**를 만든다 — ⚠ **그 화면이 인벤토리에 없다** §8-2

→ **§C 신규 조항 후보** §9-1. **C-1의 「즉시 성공」이 모든 화면에 같게 적용되지 않는다**는 것이 발견이다.

### §5-4. LOT 미지정 출고가 불가능하다

```
picking_line.lot_id        bigint NOT NULL
goods_issue_line.lot_id    bigint NOT NULL
```

예외 E-6 ③이 「**LOT 미지정 출고** 🟠」를 남겼는데 **DB가 이미 막고 있다.** 「모델이 화면 설계보다 앞선」 경우다 — 예외를 설계할 필요가 없다.

⚠ 다만 `inventory_balance.lot_id`는 **nullable**이다(A-7 접힘 축). **LOT 단위로 관리하지 않는 재고가 잔액에는 있는데 출고 라인에는 담을 수 없다.** 그런 품목이 실재하면 출고가 막힌다 → §8-3.

### §5-5. 예약이 출고의 선행 상태다

```
inventory_balance.reserved_qty   예약분
inventory_balance.picked_qty     피킹분
available_qty = on_hand - reserved - picked - blocked   (GENERATED)
picking_line.inventory_reservation_id → inventory_reservation
```

**출고요청 생성 시 예약이 걸리고, 피킹하면 `picked_qty`로 옮겨 간다.** 화면은 이 이동을 직접 쓰지 않고 서버 전기에 맡긴다(`M-01-04` §5-4 — GENERATED는 화면이 계산하지 않는다).

`inventory_reservation`의 `ck_reservation_qty CHECK (released_qty + consumed_qty <= reserved_qty)` — 예약 소진을 DB가 지킨다.

### §5-6. 「도착」이 다형 참조다 — 그런데 무엇을 가리키는지 모른다

```
goods_issue.destination_type_code   app.code_t NOT NULL
goods_issue.destination_id          bigint NOT NULL     ← FK 없음
```

**A-10 다형 참조의 실측 사례가 하나 늘었다**(기존 5곳 → 6곳). 프로세스가 말하는 도착은 **생산창고(라인사이드)** 이고 `material_issue_request.destination_location_id`는 **`mdm.location` FK**다.

⚠ **같은 「도착」이 한 곳은 FK, 한 곳은 다형 참조다.** A-10 보완 조항 그대로 — **둘이 같은 대상인지 먼저 확인**한다.

| 컬럼 | 대상 |
| --- | --- |
| `material_issue_request.destination_location_id` | ✅ `mdm.location` FK |
| `goods_issue.destination_type_code` + `destination_id` | ⚠ **위치? 라인? W/O?** — 값 목록 미정 |

화면은 **요청의 `destination_location_id`를 그대로 보이고**, 출고 전표의 다형 참조는 서버가 채우는 것으로 둔다 → §8-4.

### §5-7. 결품 — (U-A1) 미정의

프로세스가 「[결품 시] → **(U-A1)**」로 보내는데 **(U-A1)이 미정의**다(§3.4 미결 4번 — 「부족분·대체자재 처리 미정의 — S7 피킹 분기 **행선지 공백**」).

**모델은 부분 소화를 받아 준다:**

```
picking_line:                  CHECK (picked_qty <= planned_qty)
material_issue_request_line:   CHECK (issued_qty <= requested_qty)
```

**요청 수량보다 적게 출고해도 DB가 막지 않는다.** 화면은 **부분 출고로 처리하고 부족분을 남긴다** — 대체자재(`planning.material_substitution_rule` 실재)는 **이 화면 밖**으로 둔다.

⚠ 부족을 **누구에게 알리나** — REQ-OA-0009(관리자 알람)가 있으나 채널만 확정이고 이 케이스의 트리거는 미정 → §8-6.

## §9. 이 장에서 나온 공유 계약 후보

1. **⛔ 「캐시 없이 판정」과 「오프라인 허용」은 한 화면에서 동시에 성립하지 않는다** — 결정 10과 C-1이 정면으로 부딪친다. **C-2가 유일성에 쓴 구조(로컬 선검사 → 서버 확정 → 건별 되돌리기)를 판정에도 적용**하고, 그 대가로 **오프라인 건은 「미확정」 표식을 유지**한다 (§5-2·§5-3)
2. **C-1의 「즉시 성공 피드백」이 모든 화면에 같게 적용되지 않는다** — 되돌릴 수 없는 실물 이동(출고)에서는 즉시 성공이 위험하다. **화면 유형별로 피드백 수준을 계약이 나눈다**: ⓐ 즉시 성공(기록성) / ⓑ **미확정 표식 유지**(실물 이동) (§5-3)
3. **A-10 다형 참조 6번째 — 같은 「도착」이 한 곳은 FK, 한 곳은 다형이다** — `material_issue_request.destination_location_id`(FK) vs `goods_issue.destination_type_code`+`destination_id`. **A-10 보완 조항대로 둘이 같은 대상인지 먼저 확인**한다 (§5-6)
