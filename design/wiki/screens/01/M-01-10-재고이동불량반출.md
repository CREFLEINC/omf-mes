### §3-1. 스캔 둘 사이에 **시간이 있다**

`M-01-05`(위치→LOT)의 두 스캔은 **연속**이지만, 이 화면의 ①반출과 ②도착 사이에는 **작업자가 물건을 들고 이동하는 시간**이 있다. 몇 분에서 수십 분이다.

**화면이 그 사이 유지되어야 한다** — 앱이 백그라운드로 가거나 화면이 꺼져도 ①의 결과가 살아 있어야 한다. **§5-4의 오프라인 문제가 여기서 나온다.**

## §5. 액션·상태

### §5-1. 임시 적치 복귀 — 기존 적치 지시 완료 경로(#454)

**임시 적치 복귀 모드**는 `M-01-07`에서 서버 확정된 `COMPLETED_TEMPORARY`(임시 적치 완료) 지시만 처리한다. `temporaryOnly=true` 목록에서 지시 선택 → 상세·ETag 조회 → 현재 `actualLocationId`의 임시 위치와 LOT 확인 → 같은 창고의 정위치 스캔 또는 목록 선택 → 지시 `taskQty` 전량 복귀 순서다. 원입고 위치 `fromLocationId`는 변경하지 않는다.

① 반출 스캔은 로컬 진행 저장이며 서버 반출을 만들지 않는다. ② 도착 확인 후 `POST /logistics/putaway-tasks/{id}:complete`를 한 번 호출한다. 서버 성공 전에는 복귀 미확정이다. 기존 창고 간 일반·불량 이동만 `stock-transfers` 생성/도착의 두 단계로 처리한다. **일반 창고 내 임의 위치 이동·파렛트 재편성·부분 분할은 아직 미해결이며 원장 직접 기록 기능을 제공하지 않는다.**

정상 완료는 `PENDING`(적치 대기) → `COMPLETED`(적치 완료), 임시 등록은 `PENDING`(적치 대기) → `COMPLETED_TEMPORARY`(임시 적치 완료), 복귀는 `COMPLETED_TEMPORARY`(임시 적치 완료) → `COMPLETED`(적치 완료)다. 완료된 지시에 새 키로 재실행하면 400 `STATE_LOCKED`(상태 잠금), 원키 재전송은 원응답이다. 임시 `TEMP`(임시) 위치에 다시 보내 정상 완료로 바꾸지 않는다.

**아래 동일 창고·전량·출발 현재 위치·총량 불변 조건은 복귀에만 적용하며 최초 대기 지시 적치 범위는 유지한다.** 권장 위치 강제·권장 없을 때 확인, 활성 위치·동일 창고·현재와 다른 위치, 혼적 차단·수용량 경고를 유지한다. 원임시 적치와 추적되는 동일 품목·LOT·소유·단위·품질 축 전량만 이동한다. 부분 수량·다른 재고 대체는 금지하며 예약·피킹 침해, 이미 소비·이동된 수량, 원천 추적 불명확은 400 `INVALID`(입력 오류, `field=putawayTaskId`, 설명 사유)다. 음수 허용 품목으로 부족을 통과시키지 않는다. Hold만으로 막지 않고 경고·품질 상태를 보존하며, 보류 차감된 `availableQty`를 복귀 판정 정본으로 쓰지 않는다.

출발 차감·도착 증가와 지시 상태·현재 위치·완료 시각·버전·감사·멱등은 원자적이며 품목·LOT 총량은 변하지 않는다. 원임시 위치·사유·시각·작업자와 원장은 불변 이력으로 남고 현재 완료 시각은 최종 복귀 `occurredAt`이다. 신규 임시/복귀 원장은 `PUTAWAY_TASK`(적치 지시) + `putawayTaskId`로 추적한다. 입고 이중 전기·새 취소 유형·과거 원장 재작성은 없다. 원입고 취소의 기존 후속 처리 판정에는 임시/복귀 적치 이력도 포함한다.

오프라인은 서버가 확정한 임시 지시·상세·위치/검증 정보 캐시가 있을 때만 시작한다. 미동기 임시 등록에서 복귀를 시작하지 않는다. 새 복귀 업무는 새 멱등키를 만들고 재전송에서는 키·영업일·발생 시각을 유지한다. 다른 단말 처리의 400 `STATE_LOCKED`(상태 잠금), 재고 업무 검증의 400 `INVALID`(입력 오류), 버전·멱등 충돌의 409는 해당 건 오류와 입력을 보존한다. 자동 위치 보정·지시 재발행은 하지 않는다.

### §5-2. 파렛트는 이동 그룹핑이지 재고 잠금 단위가 아니다

✓확정 QA #16: 「**파렛트=이동 그룹핑**(재고 잠금 단위 아님)·확인=**자재별** 출고 QR 스캔」

```
inventory.handling_unit           파렛트 자체
inventory.handling_unit_content   그 안의 품목 × LOT × 수량
inventory_transaction_line.handling_unit_id   (late FK 실재)
```

**확정이 정확히 데이터에 있다.** `handling_unit`은 `warehouse_id`·`location_id`를 갖되 **재고 잔액을 갖지 않는다** — 잔액은 `inventory_balance`가 위치·LOT 축으로 관리한다. 그룹핑일 뿐이라는 확정이 그대로다.

**화면 규칙**: 파렛트 단위를 선택해도 **확인 스캔은 자재별**이다(확정 문구). 파렛트 QR 한 번으로 끝내지 않는다.

| 단위 | ① 반출 | ② 도착 |
| --- | --- | --- |
| **자재별** | LOT QR ×N | 위치 QR ×1 |
| **파렛트** | 파렛트 QR ×1 → **내용 자재별 확인 스캔 ×N** | 위치 QR ×1 |

⚠ **「상황별 혼용(설정형)」** — 어느 단위를 쓸지 설정으로 정한다. `app.operation_policy`가 그런 파라미터를 담는 자리다(실측). 정책 코드 값은 미정 §8-2.

### §5-3. Hold LOT 이동 — (U-C1) 허용 정책 미정

프로세스: 「이동 대상 선택(219:5523 — **[Hold LOT 이동 시] → (U-C1)**)」 · 예외 E-7 ③ 「차단 판정 위치=Lot Status 조회 **확정**(결정 10)·**허용 정책 자체는 잔여** ⚠」

**어디서 판정하는지는 정해졌고 무엇을 할지는 안 정해졌다.**

| | 상태 |
| --- | --- |
| 판정 위치 | 현재 품질 상태는 `Lot.statusCode`, 변경 이력은 LOT 상태 이벤트 조회 계약으로 구분한다. 이력으로 현재 상태를 재계산하지 않는다. 「그 테이블이 없다」는 `M-01-08` §5-2에서 철회됐다. 보류 경고·진행 잠정 정책은 그대로이며 품질 해제나 다른 행위 허용을 추론하지 않는다 |
| 허용 여부 | ⬜ **미정** |

**화면은 「경고 + 진행 가능」으로 시작**한다. 근거: **결정 14가 「홀드품 이동=재고이동 트랜잭션 **별개 기록**」을 확정**했다(WF02 S11 R77) — 이동 자체는 일어난다는 뜻이다.

⚠ **차단이 아니라 경고인 이유를 화면에 적는다**(G-5 — 확정 번호를 문구에):

```
보류 중인 LOT입니다. 이동은 별개로 기록됩니다 (✓설계확정 결정 14)
```

| --- | --- |
| ① 반출 저장 → 오프라인 → ② 도착 저장 | ✅ 큐에 둘 다 — 순서 유지 필요(`M-01-09` §5-1) |
| ① 반출 저장 → **작업자가 그만둠** | ⚠ **`shipped_qty > 0, received_qty = 0`인 행이 남는다** |
| ① 반출 저장 → 앱 종료 → 재실행 | ⚠ **미완 이동을 화면이 되살려야 한다** |

**`ck_stock_transfer_qty CHECK (shipped ≤ requested AND received ≤ shipped)`** 는 **반쪽 상태를 허용**한다(`received_qty = 0`). DB가 막지 않으므로 **화면이 미완 목록을 보여야** 한다.

**규칙**: 화면 진입 시 **미완 이동(반출됨·미도착)을 먼저 보인다.** 없으면 새 이동으로 시작한다.

현재 도착 확정은 **한 번만** 받는다. 일부 수량만 도착해도 `receivedAt`이 채워져 둘째 도착은 400 `STATE_LOCKED`(상태 잠김)이고, `inTransitOnly=true` 목록에서도 빠진다. 남은 수량은 운송중 재고로 남지만 이 화면에는 재도착·취소 경로가 없다. 부분 도착을 전량 완료나 재처리 가능 상태로 표시하지 않는다.

반출 등록 때 원장이 먼저 전기되므로 문서 진행 조회의 「전기 완료」와 실물 도착 완료는 같은 뜻이 아니다. 도착은 반출 원장의 품질 상태를 그대로 유지하고 재고 상태만 반출 전 상태로 복원한다. `ON_HOLD`(보류)·`BLOCKED`(차단)를 `AVAILABLE`(가용)로 바꾸지 않는다.

⚠ **그 목록을 오프라인에서 어떻게 얻나** — 로컬 큐에 있는 것은 보이나, **다른 단말이 반출한 건은 못 본다.** §8-3.

### §5-5. 불량 반출은 이동 뒤에 03으로 넘어간다

프로세스: 「[불량 반출 시] 불량창고 적치(219:5519) → **판정 → 03 전이도**(219:5520)」

**이 화면은 불량창고까지만** 한다. 재작업/폐기 판정은 03 소관이고 화면은 `W-01-06`(폐기 품의)·`W-03-*`이다.

**불량 반출 사유의 입력 경로는 아직 정해야 한다.** `StockTransfer.reasonCode` 응답 존재와 생성·도착·라인 갱신 입력 지원은 별개다. 현재 요청 계약에 없는 입력을 보내거나 다른 품질 기록으로 대체 저장하지 않는다.

**응답 축은 있지만 입력 경로는 미정이다.** 적치 사유 입력이 이미 있는 `M-01-07`과 동일한 결손으로 취급하지 않는다 → §8-4.

## §9. 이 장에서 나온 공유 계약 후보

1. **임시 적치 복귀는 적치 지시로 추적한다** — #454로 해소했으며 일반 창고 내 위치 이동·파렛트 재편성은 §I-19에 남긴다.
2. **두 스캔 사이에 시간이 있는 화면은 「반쪽 상태」를 화면이 되살려야 한다** — DB가 `received_qty = 0`을 허용하므로 미완이 남는다. **진입 시 미완 목록을 먼저 보이는 것이 이 유형의 표준 형태** (§5-4)
3. **응답 필드 존재가 입력 지원을 뜻하지 않는다** — 적치 사유 입력은 이미 계약에 있으나 이동 사유는 응답만 존재한다. 불량 반출·분실/손상 입력 경로는 §8-4·6에 남긴다 (§5-5)
