# W-01-12 · 재고조정

> 작성일: 2026-08-05 · 서식: `00-화면스펙서식.md` v1.0 · 작성 주체: CREFLE OMF 팀 (UI/UX)
> **`inventory_adjustment`가 헤더만 있고 라인이 없다.** `W-01-04`가 넘긴 (U-D1)을 받는 화면이다.

## §0. 요약

- **개요**: 관리웹에서 물류담당(+승인권자)이 재고 조정을 등록·승인하고 ERP 조정 전표를 연계하는 화면. 조정 원천은 실사 차이(`W-01-04`)·호퍼 실측(`M-01-09`)·직접 등록 셋이며, 실사는 `W-01-04` 소관이고 호퍼 실측도 이 화면을 경유한다.
- **데이터**: 조정 헤더 `inventory.inventory_adjustment`(10열 — 라인 없음, `approval_request_id` late FK)를 다루지만, 결정 08에 따라 조정의 실체는 `inventory.inventory_transaction`+`_line`(수불 원장)이다. 실사 경유분은 `inventory.inventory_count_line`을 참조한다.
- **핵심 액션**: 조정 원천 선택(실사 결과/직접 등록) → 조정 대상 라인 확인(장부·실물·차이) → 사유 입력 → 조정 상신(라인 1건 이상 AND 헤더 사유 입력) → 승인 후 전기(또는 결재선 없으면 즉시 전기). ERP 송신 선택값은 현재 저장·송신되지 않는다.

## §5. 액션·상태

### §5-1. ⛔ 조정 라인 테이블이 없다 — 무엇을 얼마나 조정했는지가 헤더에 안 남는다

**실측**: `inventory_adjustment` 10열 — 번호·실사참조·사유·승인참조·상태·조정시각 + 감사 4. **대상이 없다.**

**결정 08이 답을 준다**: 「조정 = **수불 원장 트랜잭션으로 기록**(잔량 직접 덮어쓰기 금지)」

즉 **조정의 실체는 `inventory_transaction` + `_line`**이고, `inventory_adjustment`는 **업무 헤더**다.

```
inventory_adjustment                      업무 헤더 (사유·승인·ERP)
    ↕ ⛔ 잇는 컬럼이 없다
inventory_transaction (source_document_type_code + source_document_id)
    └ inventory_transaction_line          실제 조정 내역
```

**A-10 다형 참조로 잇는다** — 현행 `InventoryTransaction.sourceDocumentTypeCode`의 닫힌 값 목록에 `INVENTORY_ADJUSTMENT`(재고조정)가 있으며, 해당 원천의 `sourceDocumentId`는 재고조정 식별자를 가리킨다. «(정합주: 2026-09-07 — 구표기 「재고조정 값이 있으면 … 잇는다 / 확인한 16쌍 중 하나」는 값 존재를 조건으로 남긴 설명이었다. 현재 판별자 존재를 반영하며, 승인 전 내역 보존이나 저장 컬럼 신설을 확정하는 것은 아니다)»

**A-11 물러난 수준**:

| | 확정·기대 | 물러난 수준 |
| --- | --- | --- |
| 조정 내역 조회 | 헤더 → 라인 | **헤더 → 수불 원장 역조회**(A-10 다형) |
| **라인별 사유** | 라인 컬럼 | ⛔ **불가** — 헤더 `reason_code` 하나뿐 |
| 상신 시점에 내역 보존 | 라인에 저장 | ⚠ **승인 전에는 어디에도 없다** §5-2 |

→ **§I 신규 후보** §9-1.

### §5-2. ⚠ 승인 전 내역을 담을 곳이 없다 — 이것이 진짜 문제다

**REQ-PR-0028 계열의 순서**(폐기와 같다): **상신 → 승인 → 전기**.

**그런데 수불 원장은 「전기」의 결과**다. 승인 전에 `inventory_transaction`을 만들면 **재고가 이미 움직인다**(결정 08의 「수불 원장=정본」).

| 시점 | 조정 내역이 어디 있나 |
| --- | --- |
| **상신** | ⛔ **없다** — 헤더만 만들어진다 |
| 승인 대기 | ⛔ **승인자가 무엇을 승인하는지 볼 수 없다** |
| 승인 후 전기 | ✅ 수불 원장 |

**승인자가 「이 조정을 승인한다」고 할 때 대상이 화면에만 있고 데이터에 없다.**

**해법 3안**

| 안 | 방법 | 판단 |
| :-: | --- | --- |
| **① 실사 라인을 원천으로** | `inventory_count_line`의 차이를 그대로 승인 | ✅ **실사 경유는 해결** — ⛔ **직접 등록·호퍼 실측은 안 됨** |
| **② 미확정 수불 트랜잭션** | `inventory_transaction.status_code`를 「대기」로 두고 승인 시 확정 | ⚠ **결정 08의 「정본」 성격이 흐려진다** |
| **③ 조정 라인 신설** | 모델 변경 | ✅ **가장 깨끗** |

**①로 실사 경유분을 처리하고, 직접 등록분은 ②를 임시로 쓴다.** ③을 이슈로 요청한다 → §8-1.

⚠ **`M-01-09`(호퍼 실측)가 이 경로를 탄다** — 실사 없는 조정이라 ①이 안 된다.

⚠ **승인 자체가 필요한지도 미정이다** — (U-D1)은 「조정 권한·승인」을 통째로 미결로 두었다. **승인 없이 조정하는 운영도 가능**하다.

**화면 설계**: `approval_request_id`가 **nullable**이므로 **승인 없는 조정도 데이터가 받는다.** 화면은 **결재선이 있으면 상신, 없으면 즉시 전기**로 갈린다 → §8-2.

### §5-4. 「잔량 직접 덮어쓰기 금지」를 화면이 지킨다

**결정 08**: 「조정 = 수불 원장 트랜잭션으로 기록(**잔량 직접 덮어쓰기 금지**)」

**화면이 `inventory_balance.on_hand_qty`를 직접 고치는 컨트롤을 두지 않는다.** 조정은 **차이 수량**을 입력하는 것이지 **결과 수량**을 입력하는 것이 아니다.

| | |
| --- | --- |
| ⛔ 잘못된 UI | 「보유 수량 [ 180 ]」 — 덮어쓰기로 읽힌다 |
| ✅ 옳은 UI | 「장부 200 · 실물 **180** · **차이 −20**」 — 차이가 트랜잭션이 된다 |

**G-5 적용** — 확정 번호를 문구에:

```
ⓘ 조정은 수불 원장에 기록됩니다. 잔량을 직접 고치지 않습니다 (✓설계확정 결정 08)
```

| **실사 차이** | ✅ 있음 | `W-01-04`에서 넘어옴 |

### §5-6. 액션

| 액션 | 활성 조건 |
| --- | --- |
| 원천 선택(실사/직접) | 항상 |
| 실사 차이 불러오기 | 실사 선택됨 |
| 라인 추가·수정 | 직접 등록 시 |
| 사유 선택 | 라인당 ⚠ **저장 자리 없음**(§5-1) · 헤더 사유는 필수 |
| ERP 송신 토글 | **비활성** — 현재 요청값을 저장하지 않고 ERP 메시지를 만들지 않음 |
| **조정 상신** | 라인 1건 이상 AND 헤더 사유 입력 |
| **전기** | 승인 후(또는 승인 불요 시 상신 즉시) |

등록·라인 치환은 각 라인의 위치·품목·LOT과 조직 축에 맞는 **잔액 행이 정확히 1건**일 때만 받는다. 잔액이 없으면 증가는 `400 INVALID`, 감소는 `400 NEGATIVE_BALANCE`, 같은 키의 품질·재고 상태 등 잔액 차원이 여러 건이면 `400 INVALID`다. 빈 차원에 새 재고를 만드는 입력은 지원하지 않는다. 조정량 0도 `400 INVALID`다.

조정 헤더에는 공장 입력칸이 없다. 서버는 `locationId → warehouse → plant`로 각 라인의 공장을 해소하고, 한 전표가 둘 이상의 공장에 걸치면 등록 `lines[i].locationId`, 치환 `items[i].locationId`를 짚어 `400 INVALID`로 거절한다. 이 검사는 공장까지만 하며 사업부·법인 동일성을 별도로 요구하지 않는다. 전기 때 저장 라인으로 다시 검사하고 첫 라인의 공장을 원장 헤더에 기록한다.

### §5-7. 취소 대신 새 반대 조정

전기된 조정을 취소하거나 원복하는 API는 없다. 오류를 바로잡을 때는 원조정과 **같은 재고 차원**에 부호가 반대인 새 조정을 등록·전기한다. 새 조정과 새 수불 원장은 별도 감사 기록으로 남고 원조정은 `POSTED`(전기완료) 상태로 보존된다.

반대 조정은 모든 경우의 롤백을 보장하지 않는다. 실행 시점에도 정확히 한 잔액 차원이 있어야 하고, 단일 공장·승인·재고 부족·예약/피킹/보류·품목의 음수 재고 허용 등 일반 전기 규칙을 다시 통과해야 한다. 원조정 뒤 출고 등으로 잔액이 달라졌다면 반대 조정이 거절될 수 있으므로, 원조정 번호와 새 조정 번호를 함께 안내해 검토한다.

> ⛔ **2026-08-07 — 「승인 · 반려」를 이 표에서 뺐다.** `W-CO-09` 결재함으로 이관했다(§3 정정 주). **취소선으로 남기지 않는다** — 생성기가 표를 읽으므로 취소선 행도 살아 있는 요구로 나간다.

## §9. 이 장에서 나온 공유 계약 후보

1. **⛔ 헤더만 있고 라인이 없는 업무 문서가 있다** — 같은 계열 넷(`inventory_count`·`goods_receipt`·`goods_issue`·`stock_transfer`)은 전부 라인을 갖는데 `inventory_adjustment`만 없다. **결정 08이 「수불 원장에 기록」이라 해서 라인이 불필요한 것이 아니다** — **승인 전 내역을 담을 곳이 사라진다** (§5-1·§5-2)
2. **「승인 → 전기」 순서를 갖는 화면은 승인 대상이 데이터에 있어야 한다** — 승인자가 무엇을 승인하는지 볼 수 없으면 승인이 형식이 된다. **J-5(일어나지 않는 것)의 뒷면**: 승인 시 재고가 안 움직인다면, **그때 내역은 어디에 있는지**를 계약이 정한다 (§5-2)
3. **「직접 덮어쓰기 금지」는 UI 형태까지 규정한다** — 결과 수량을 입력받으면 사용자는 덮어쓰기로 이해한다. **「장부 · 실물 · 차이」 3열로 보이고 차이가 트랜잭션이 되는 형태**를 계약이 표준으로 둔다 (§5-4)
