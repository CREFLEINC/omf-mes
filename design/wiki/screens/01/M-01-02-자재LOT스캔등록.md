# M-01-02 · 자재LOT 번호 스캔·등록 (발번)

## 요약

- **개요**: 모바일(스캐너 일체형 PDA) 전용 화면. 물류(창고)담당이 **입하 등록 때 LOT을 못 붙인 사전부착 라인**을 나중에 스캔해 채운다 — **보완 경로**다 «(정합주: 2026-09-02 — 종전 「입하 시 자재LOT 번호를 스캔해 등록(발번)한다 — **사전부착 경로를 다룬다**」였다. ⛔ 사전부착 라인의 LOT 은 입하 등록(`M-01-01`)이 «본 경로»로 만든다 — 등록과 한 트랜잭션이다(`M-01-01` §5-4 · 계약 `InboundReceiptLine.lotId`). 두 화면이 같은 경로를 각자 자기 것으로 적어 **같은 LOT 이 두 번 만들어질 수 있었다** · `omf-mes#354`)». 미부착(MES 채번)은 자재LOT 등록·라벨 발행 화면(`P-01-01`)이 처리한다.
- **주요 데이터**: 자재 LOT(`trace.lot` — 34자리 LOT No·수량·품목·**원천 입하 라인**), 공급사 자체 번호(`lot_external_identifier`), Hold 사유(`lot_hold`) — 등록 즉시 Lot Status=Hold로 생성된다 «(정합주: 2026-09-02 — 종전 「원천 P/O」였다. 원천 짝은 `sourceTypeCode = INBOUND_RECEIPT_LINE` + `sourceId = inboundReceiptLineId` 다 — 발번 단위가 «건»이 아니라 «라인»이다 · `omf-mes#326`)».
- **핵심 액션**: **입하 건·라인 선택**(LOT 이 비어 있는 사전부착 라인) · 스캔(포커스 고정 암묵 입력) · 직접 입력(대체 경로) · 건별 등록 · 등록 완료(일괄) · 목록 행 삭제(미동기 건 한정).

> 유형 「스캔」(16건) 대표 · 폼팩터 **모바일**(스캐너 일체형 PDA). 이 장에서 **스캔이 진짜 DS 갭인지** 판정한다.

### §3-1. 이 화면이 다른 두 폼팩터와 다른 점

- **스캔이 주 입력**이다. 키보드·키패드가 아니라 **일체형 스캐너가 입력을 밀어 넣는다** → 포커스가 스캔 필드에서 벗어나면 입력이 유실된다. **포커스 고정이 기능 요구**다.

### §4-1. ⚠ 34자리 규칙은 화면이 지킨다

`trace.lot.lot_no`는 `varchar(100)`이고 **자릿수·숫자 전용 제약이 DB에 없다.** 따라서 **입력 검증이 화면 책임**이다:

| 검사 | 문구 |
| --- | --- |
| 길이 ≠ 34 | 「자재 LOT 번호는 34자리입니다 (현재 N자리)」 |
| 숫자 외 문자 포함 | 「숫자만 입력할 수 있습니다」 |
| 5분절 파싱 | 제품코드9[1-9] / 수량9[10-18] / 날짜6 YYMMDD[19-24] / 공급사6[25-30] / 번호4[31-34] |
| 제품코드 ↔ **입하 라인** 품목 불일치 | 「이 입하 라인의 품목과 다른 LOT입니다」 |
| 날짜 유효성 | YYMMDD 파싱 실패 시 거부 |
| `UNIQUE(plant_id, lot_no)` | 「이미 등록된 LOT 번호입니다」 |

> **상세 채번 설계(도출·검증·유일성)는 별도 후속 과제**로 남아 있다(MLOT #16). 자릿수만 확정 입력값이다 → §8-2.

## §5. 액션·상태

### §5-1. ⭐ 이 화면은 «보완»이다 — 사전부착의 본 경로가 아니다

✓확정 2026-09-02(`omf-mes#354`) — 사전부착 자재의 LOT 을 만드는 화면이 **셋으로 읽히던 것을 하나로 정했다.**

| 라인 | LOT 을 언제·누가 만드나 | 화면 |
| --- | --- | --- |
| **사전부착 · 도착 때 스캔했다** | 입하 등록과 **한 트랜잭션** — 서버가 만든다 | **`M-01-01`**(본 경로) |
| **사전부착 · 도착 때 못 스캔했다** | 나중에 라인을 골라 스캔해 채운다 | **이 화면**(보완) |
| **미부착** | 서버 채번 + 라벨 발행이 한 화면 안 | **`P-01-01`** |

```
[보완]      입하 건 선택 → LOT 이 비어 있는 사전부착 라인 선택
            → 스캔 → 34자리 검증 → 제품코드 ↔ 라인 품목 대조 → 등록(Hold)
[미부착]    ⛔ 이 화면 밖이다 — `P-01-01`이 처리한다. 등록과 채번이 한
            호출이고(서버 채번) 라벨은 그 뒤에 나오므로 「발번 → 라벨 → 재스캔」
            순서가 성립하지 않는다. 자재LOT 등록·라벨 발행 화면(`P-01-01`) §5-2
```

⛔ **P/O 를 고르지 않는다** «(정합주: 2026-09-02 — 종전 「스캔 → 34자리 검증 → 제품코드로 P/O 후보 필터(#16) → 담당자 P/O 확인(#6) → 등록(Hold)」이었다. 그 흐름은 입하 등록(`M-01-01` §5-1 [사전부착])이 **이미 하는 일**이고, 여기서 다시 하면 같은 LOT 이 두 번 만들어진다 · `omf-mes#354`)». 이 화면이 여는 시점에는 **입하 라인이 이미 있고**, 원천 짝(`sourceId`)이 그 라인을 가리킨다.

⚠ **대상 라인을 계약이 그대로 준다** — `GET /logistics/inbound-receipts?supplierLotMissing=false` 로 사전부착 건을 받고, `GET …/{inboundReceiptId}/lines?supplierLotMissing=false` 의 응답에서 **`lotId` 가 비어 있는 라인**이 이 화면의 대상이다. ⭐ **추정이 아니라 응답에 든 값으로 거른다** — 계약이 안 주는 축을 화면이 흉내 내는 것과 다르다.

⚠ **미부착 경로는 발번·라벨·등록이 `P-01-01` 한 화면 안에서 이뤄진다.** 라벨 발행 지점은 `P-01-01`의 POP 프린터로 정해졌다(§5-2·§5-5).

- ⚠ 오프라인에서는 **`UNIQUE(plant_id, lot_no)` 중복을 서버에서만 확정 판정할 수 있다** → 로컬은 **큐 내 중복만** 선검사하고, 서버 거부 시 해당 건만 오류 목록으로 되돌린다. 전체 롤백하지 않는다

| 오프라인 | 정상 동작 §5-3 |

## §7. DS 매핑

### §7-1. ⚠ 예측 정정 — **스캔은 `d`가 아니라 `c`였다**

착수 전 「스캔 16건이 d 유형(새 원시 요소) 최대 후보」로 보았으나, **실측하니 아니다.**

**일체형 단말의 바코드 스캐너는 스캔값을 키보드 입력처럼 흘려보낸다**(omf-mes-client#442 확정 — 어댑터의 키보드 입력 구현체). 즉 스캔은 「특수 입력 장치」가 아니라 **포커스가 고정된 텍스트 입력**이다. `TextField` + 포커스 관리 + 자동 제출로 구현된다.

| 구성 요소 | 판정 |
| --- | --- |
| 스캔 입력 = `TextField`(포커스 고정·자동 제출·입력 후 클리어) | **c** |
| 진행·자릿수 표시 = `Progress` 또는 텍스트 | a |
| 등록 목록 = `Table`(compact) 또는 `Card` 목록 | a |
| 오류 피드백 = `AlertBanner` + 오류음 | a |
| 스캐너 준비 상태 = `Chip` | a |

→ **`c`(조합) — 제품이 소유하고 DS 이슈를 내지 않는다.** 다만 스캔 화면이 16건이라 **제품 내부 공용 컴포넌트**(`ScanField`)로 묶을 가치는 크다. 이건 DS 승격 대상이 아니라 `omf-mes-client` 내부 정리다.

### §7-2. 모바일 터치 타겟 — G-5 파급 범위 정정

POP은 터치 규격이 명시돼 있고, 그 요구는 디자인 시스템이 `xl`(60픽셀, 2026-08-04)과 `2xl`(72픽셀, 2026-08-25)을 들이며 버튼류에 한해 채워졌다 — 근거는 터치 규격 조항(E-3). «(정합주: 2026-08-31 — 옛 서술은 「DS 최대치(48px)에 미달」이었다. 48픽셀은 두 판 낡은 수치다. 아래 결론은 영향받지 않는다)» **모바일은 터치 규격이 별도로 주어지지 않았다.** Android 표준 권장(48dp)을 따른다면 **DS `lg`=48px로 충족**된다.

→ **G-5(터치 타겟 갭)의 사용처를 「POP·모바일 41건」에서 「POP 22건」으로 정정**한다. 모바일은 규격 확정 후 재판정 — §8-4.

## §9. 이 장에서 나온 공유 계약 후보

1. **스캔 입력 규약** — 포커스 고정·자동 제출·입력 후 클리어·**오류 시 입력 칸 처리는 `D-2`**·오류음. **스캔 16건 공통** (§5-2·§6)
   ⭐ 이 후보는 **`D-2` 로 확정됐다**(2026-08-02). 확정 과정에서 초안의 「필드 유지」가 「필드를 비우되 포커스 유지」로 바뀌었다 — 인용은 `D-2` 를 따른다.
2. **직접 입력 대체 경로 의무** — 스캐너 실패는 현장에서 흔하다. 모든 스캔 화면에 수동 입력을 둔다 (§5-2)
3. **오프라인 유일성 판정 규약** — 로컬은 큐 내 중복만 선검사, 서버 거부 건만 되돌린다. **전체 롤백 금지** (§5-3)
4. **연속 스캔 작업의 완료 모델** — 건별 저장 + 마지막 일괄 완료 (§3-1)
