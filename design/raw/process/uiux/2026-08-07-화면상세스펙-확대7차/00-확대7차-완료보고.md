## 2. ⭐⭐ 이 차수의 성과 — **§J의 미해결 둘이 닫혔다**

§J는 v0.5(2026-08-04)에 신설된 뒤 **미해결을 계속 안고 있었다.** v0.8에서 J-3이 ⛔로 격상되기까지 했다.

| | v0.9까지 | **v1.0** |
| --- | --- | --- |
| **J-1** | ⬜ 결재선 정의 화면이 인벤토리에 없다 | ✅ **`W-06-15` 신설로 해소** |
| **J-2** | ⬜ 「한도」가 수량인지 금액인지 미정 | ✅ **1차엔 값 구간을 쓰지 않는다**(값 성격 = 수량) |
| **J-3** | ⛔ **회신과 정면 충돌** | ✅ **1차 결재선은 `USER`만 연다** |

**절이 신설된 이래 처음으로 §J에 ⬜·⛔가 0건이다.**

### 2-1. J-3이 닫히는 데 **두 번의 확정과 한 번의 실측**이 필요했다

```
#72 회신(2026-08-04)  「승인 주체 = 담당부서 관리자 · 관리자의 권한 설정으로 처리」
                             ↕  정면 충돌
approval_step.approver_id   bigint NOT NULL REFERENCES app.app_user
```

**① 2026-08-07 사용자 확정 — 「업무를 데이터에 맞춘다」.** 모델을 바꾸지 않고 **상신 시 규칙으로 한 사람을 고른다.**

**② 그런데 「고를 입력」이 모델에 없었다.** ①을 실행하려면 「부서에 관리자가 여럿일 때 누구」를 좁힐 값이 있어야 하는데:

| 갈래 | 실측 |
| :-: | --- |
| `DEPARTMENT` | ⛔ **`mdm.department`에 관리자 컬럼 0건** — 부서원 전원은 찾지만 관리자를 가릴 값이 없다 |
| `ROLE` | ⛔ **`app.role`에 부서·사업부 축이 없다** — 「품질부 관리자」가 아니라 「전사 관리자 역할」이 된다 |
| **`USER`** | ✅ 결재선이 사람을 직접 가리킨다 |

**③ 2026-08-07 사용자 확정 — `USER`만 연다.**

> ⭐ **①만으로는 닫히지 않았다.** 「규칙으로 고른다」는 방향은 맞았지만, **그 규칙이 딛고 설 데이터가 있는지는 별개 질문**이었다. 실측하지 않고 계약을 썼으면 **「부서 관리자를 고른다」는 구현 불가능한 문장**이 계약에 들어갔을 것이다.

**남은 것 하나 — 부재 시 결재가 멈춘다.** 대리·위임이 범위 밖이라 우회가 없다(대리 컬럼 없음 · `approval_step` 기록 전용 · `uq(request, step_no)`). **사용자 확정으로 감수**하고 **A-11로 화면이 상시 말한다.**

## 3. ⭐ 순서를 뒤집었다 — **화면 없이 계약을 쓰면 지어내는 것이다**

애초 계획은 **「승인 계약 → 착수 통지 → 화면 스펙 3장」**이었다. 착수 직전에 뒤집었다.

| | 문제 |
| --- | --- |
| 계약 먼저 | **결재선 CRUD의 근거가 될 화면 스펙이 없다.** `approval_route` CRUD를 무엇을 보고 쓰나 |
| 이미 있던 규칙 | 「화면 없는 오퍼레이션을 만들면 프론트가 부를 데가 없고, 진짜 화면이 생기면 버린다」 — `06-API-요구서-01자재창고.md` §5-1 |

**01 트랙이 스스로 세운 규칙을 다음 트랙이 어길 뻔했다.** 산출물은 같고 순서만 바뀌었다.

> ⭐ **뒤집고 나서 얻은 것이 있다** — 화면을 쓰는 과정에서 **§I 4건과 계약 조항 9건**이 나왔고, 그중 **§I-36(부서 관리자 컬럼 부재)이 계약의 핵심을 바꿨다.** 계약을 먼저 썼으면 이 발견이 **계약을 고쳐 쓰는 일**이 됐다.

## 4. 무엇을 발견했나 — §I 신규 4건

### 4-1. ⛔ **런타임에 한 행을 골라야 하는 마스터 2개에 유일 제약이 0건**(§I-35)

| 테이블 | 골라야 하는 상황 | 유일 제약 | 갈라 줄 컬럼 |
| --- | --- | :-: | --- |
| `app.approval_route` | 상신 시 결재선 1건 | ⛔ **0건** | `business_unit_id`(nullable) · 값 구간 |
| `logistics.putaway_rule` | 적치 시 권장 위치 1건 | ⛔ **0건** | `priority_no`(**방향 미정의**) |

⚠ **`putaway_task.applied_putaway_rule_id`가 「어느 규칙이 적용됐는가」를 남기게 돼 있다** — **한 행이 정해진다는 전제**인데 그 전제가 성립하지 않는다.

→ **B-12 신설** · **이슈 후보 1**(부분 유일 인덱스 2건).

### 4-2. ⛔ **물류 문서 12테이블에 취소 흔적 컬럼이 0건**(§I-38)

`cancel*` 전 파일 검색 **0건**. 취소의 **누가·언제·왜**가 어디에도 안 남는다.

**그런데 취소를 승인 대상으로 만들면 FR-IM-080이 요구하는 7항목 중 4개가 채워진다.**

| 보존 항목 | 어디에 |
| --- | --- |
| 정정사유 | `approval_request.reason` **NOT NULL** |
| 요청자 | `approval_request.requested_by` |
| **승인자** | `approval_step.approver_id` + `decision_at` |
| 정정일시 | 역트랜잭션 `occurred_at` |

> ⭐ **사용자가 말한 흐름이 요구를 절반 채웠다** — 「실무자가 취소 → 관리자가 승인 요청 목록에서 승인/반려/의견」. 이것이 **데이터 변경 없이** FR-IM-080의 4항목을 담는다.

**역으로 규칙이 나온다** — **승인 없는 취소 경로를 두지 않는다.** 두면 **흔적 없는 취소**가 생긴다. → **A-11 보강**.

### 4-3. `mdm.department` 관리자 컬럼 부재(§I-36) · 외주 2문서 `status_code` 부재(§I-37)

36은 §2-1에서 다뤘다. 37은 **FR-IM-086(P0)이 외주출고·입고를 진행현황 대상으로 요구하는데 상태 컬럼 자체가 없다** — 나머지 10문서는 전부 있다.

## 5. 화면별 요지

### 5-1. `W-06-15` 결재선 정의

- **1차 승인자는 `USER`만** — 나머지 둘은 **선택지를 지우지 않고 비활성 + 사유**(G-10). 지우면 나중에 열 때 화면이 바뀐다
- **값 구간 입력란은 두되 선택 입력** — 컬럼이 실재하고, 비우면 전 구간이다
- **단계 저장은 결재선 단위 한 트랜잭션** — `uq(route, step_no)` 때문에 **행 단위 저장이 원리적으로 불가능**하다(1↔2 교환이 중간에 제약을 위반) → **B-11 보강**
- **결재선을 끄면 상신이 막힌다** — 저장은 막지 않되 무엇이 막히는지 먼저 보인다

### 5-2. `W-CO-09` 결재함

- ⭐ **대상 상세를 그리지 않는다** — 그래서 **#68(다형 참조 규약) 해소 전에도 성립**한다. 대상은 **원 화면 링크**
- ⛔ **목록에 보일 업무 값이 `reason` 하나뿐** — `approval_request`에 수량·금액·품목이 0건. **사유가 요약을 겸한다** → **A-12 보강**
- ⭐ **승인 ≠ 전기** — 01 계약의 「`:post`는 승인 전이면 400」이 근거다. **J-5의 「일어나지 않는 것」을 유형과 무관한 한 문장으로 고정** → **J-8 신설**
- **업무 화면 결재 대기 탭 3장을 대체**하되 **`W-01-02`는 예외** — 판정 ≠ 결재 → **J-10 신설**

### 5-3. `W-01-13` 물류 문서 진행현황·취소

- **한 화면이 P0 둘을 채운다** — FR-IM-086(진행현황) + FR-IM-076~078(취소)
- **취소는 3단 관문** — 후속 유무 → 전기 여부 → 승인
- ⭐ **승인을 기다리는 사이에 후속이 생길 수 있다** — 그래서 **자동 실행하지 않고 실행 시점에 다시 판정**한다. **J-8의 결정적 근거**
- **출하 취소(FR-IM-079)는 04 소관** — 「실제 반출됐으면 반품 절차」라 성격이 다르다

### 5-4. `W-06-14` 적치 규칙 마스터

- **계약이 먼저 쓰인 첫 화면** — 3경로 대조 결과 **어긋남 0건**
- ⭐ **「규칙 없는 품목 수」를 화면이 보인다** — 이 표가 비면 현장이 **위치 검증 없이 통과**하는데, 등록된 것만 보이면 그 사실이 드러나지 않는다 → **G-12 신설**
- **화면이 계약보다 더 요구한다** — 현재 적재 · 규칙 없는 품목 수. **파생 조회 2건이 계약 결손**이다

## 6. DS — 신규 갭 0건(7차 연속)

**⭐ 이번 차수는 「조합을 시도했는가」보다 한 걸음 앞에서 두 번 멈췄다** — **애초에 그 컴포넌트가 필요한 요구인가**.

| 후보 | 판정 | 왜 |
| --- | :-: | --- |
| 결재 진행 `Stepper` | **`c` — `Table`** | 각 단계에 **자유 텍스트 의견**이 붙는다. 세로로 세우면 결국 표다 |
| 용량 사용률 막대 | **`c` — 텍스트** | `Progress` 부재는 맞지만 **막대가 필요한 값이 아니다** |

> **DS를 망가뜨리는 흔한 경로가 「`c`를 DS로 올리는 것」인데, 그보다 한 걸음 앞에 「필요하지도 않은 것을 갭으로 올리는 것」이 있다.**

**G-11(측면 패널)이 네 곳이 됐다** — `W-02-08`·`W-03-01`·`W-01-07`·**`W-01-13`**. 요청 형태는 그대로다(`Dialog`에 `placement` 추가).
