## §0. 요약

## §2. 공유계약 v0.5 — 신규 조항 14건

### §2-1. §J 승인 워크플로우 (신설 6건)

**왜 급했나** — `approval_request_id`를 가진 테이블이 도메인 01에만 **셋**(`inbound_receipt` 무발주 · `inbound_variance` 입하 오류 · 한도승인 대상)이다. 화면마다 승인을 다시 발명하면 갈린다.

| 조항 | 핵심 |
| --- | --- |
| **J-1** | 승인은 **4테이블 한 벌** — 정의(`route`+`route_step`)와 실행(`request`+`step`)이 분리. 화면은 정의를 **읽기만** |
| **J-2** | **「한도」의 실체 = `approval_route.min_value`/`max_value`** — 값 구간에 따라 결재선이 갈린다 |
| **J-3** | **요청 시점에 승인자를 사람으로 확정**(`approver_id` NOT NULL) — 결재선이 ROLE이어도 「그 역할의 누구나」가 아니다 |
| **J-4** | 사유 필수(`reason` NOT NULL) |
| **J-5** | 승인 화면은 **「일어나지 않는 것」**을 명시 — 한도승인은 ERP G/R 제외 |
| **J-6** | 결재는 되돌릴 수 없다(기록 전용) |

**가장 값진 발견은 J-2다.** 화면명이 「**한도**승인」인데 지금까지 어느 문서에도 「한도」의 정의가 없었다. 물리 모델에 있었다.

### §2-2. §K 출력물 발행·재발행 (신설 6건)

**왜 필요한가** — `app.document_issue_log`가 라벨·인식표·QR·성적서를 **한 테이블로** 다루고, 라벨 화면이 도메인 01·02에 다섯이다(`P-01-01`·`P-01-02`·`P-02-05`·`P-02-07`·`P-02-09`).

| 조항 | 핵심 |
| --- | --- |
| **K-1** | 발행은 **회차로 쌓고** 이전 것을 지우지 않는다 |
| **K-2** | ★ **재발행 사유를 DB가 강제**(`ck_document_reissue_reason`) |
| **K-3** | 단말·프린터를 기록 |
| **K-4** | 인쇄는 트랜잭션 밖 |
| **K-5** | 라벨은 **서버가 그린다**(결정 18) |
| **K-6** | 물리적으로 유통되는 출력물은 **회차를 인쇄면에도** |

### §2-3. B-8 트랜잭션 경계 (신설)

**이번 차수의 가장 큰 발견이다.**

`integration_message`가 **outbox 패턴**으로 설계돼 있다(`available_at`·`locked_at`·`locked_by`·`retry_count`·`message_key` UNIQUE). 즉 **ERP 송신이 트랜잭션 밖**이다.

확정 QA #1의 「ERP G/R = **건별 즉시**」를 동기 호출로 읽었으면 위험했다 — ERP가 느릴 때 DB가 잡히고, **ERP가 실패할 때 입고까지 롤백**된다.

> **「즉시」는 전송 시도의 즉시성이지 트랜잭션 포함이 아니다.**

`W-01-10` 입고 확정은 다섯을 움직이는데 **⑤(ERP 메시지)만 밖**이고, **한도승인 건은 ⑤가 아예 없다**(G/R 합격품 한정). 그래서 화면이 경로별로 결과 안내를 바꾼다.

### §2-4. A-10 다형 참조 (신설)

`{X}_type_code` + `{X}_id` 형태가 **도메인 01에서만 5곳**이고 전부 FK가 없다.

```
app.approval_request      target_type_code + target_id
audit.audit_event         target_type_code + target_id      ← #68이 이미 요청 중
logistics.goods_receipt   source_document_type_code + _id
app.document_issue_log    target_type_code + target_id      (+ lot_id FK 병존)
trace.lot                 source_type_code + source_id
```

**#68과 같은 문제다.** 하나만 정하면 나머지 넷이 또 갈린다 — **함께 정해야 한다.**

### §2-5. 기존 조항 갱신 2건

- **A-5** — `approval_route_step.step_no`가 **3번째 후보**(현재 2곳). 결재선 정의 화면이 생기면 대상이 된다
- **F-1** — `can_print_label`이 `P-01-01`로 **실증**됐다. 기본값이 `false`라 **명시적 허용이 없으면 막힌다**. 8플래그 중 2종 실증(나머지 6종은 3차)

## §3. 데이터가 화면을 앞서간 사례

**이번 차수의 성격이 확대 1차와 반대다.** 1차는 「확정이 물리 모델에 착지하지 못한 것」(§I 14건)을 찾았는데, **2차는 「물리 모델이 화면 설계보다 앞서 있는 것」**이 계속 나왔다.

| 화면이 설계하려던 것 | 데이터에 이미 있던 것 |
| --- | --- |
| 사전부착/미부착 분기 로직 | `supplier_lot_missing` boolean + `substitute_lot_reason_code` |
| 무발주 예외 처리 | `exception_type_code` + `exception_reason` + `approval_request_id` |
| 「한도」의 의미 | `approval_route.min_value` / `max_value` |
| 재발행 규칙 | `issue_seq` + `ck_document_reissue_reason` |
| 라벨 발행 이력 | `app.document_issue_log`(`terminal_id`·`printer_name`까지) |
| ERP 송신 방식 | outbox 패턴 전체 |
| 의심자재 | `trace.lot_hold` |
| 비가동 기록 | `production.work_session_event` |

**교훈** — 화면 로직을 설계하기 전에 **컬럼 주석까지 읽는다.** 「P/O 없는 예외입하」 같은 주석이 프로세스 문서보다 정확했다.

### §4-1. ✅ 차단 1건 → 해소 (2026-08-04)

**`W-01-11` §8-2 — 초과 입하분 사후 P/O의 승인 주체(01-SB1)**

**#72 회신** — 「승인 주체 = **담당부서 관리자**. **고정이 아니라 관리자의 권한 설정으로 처리**한다.」

이 확정으로 **§5-2 해석이 「나」(MES 선등록·ERP 사후 매칭)로 갈렸고**, 화면은 **공유계약 §J를 그대로 탄다** — `approver_type_code = DEPARTMENT`로 「담당부서 관리자」가 표현된다. 별도 승인 구조를 만들지 않는다.

**⚠ ERP 매칭 시점은 여전히 미결**이라 #72는 그 건으로 열려 있다. 선행으로 **#74**(결재선 정의 화면)가 필요하나 **골격에는 영향 없다.**

**→ 확대 2차 8장 전부 차단 0건.**
