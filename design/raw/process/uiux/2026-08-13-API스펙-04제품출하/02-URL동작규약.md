## 2. 규약 — 앞 다섯 트랙 그대로

| 규칙 | |
| --- | --- |
| 명사 | 복수 · kebab-case |
| 수정 | **`PUT`** — ⛔ PATCH 0 |
| `:동사` | **상태 전이에만** |
| 잠금 | `version_no` 있으면 `If-Match` |
| ⛔ **오프라인 `202`** | **쓰지 않는다**(2026-08-12 철회 · C-7 주석) |

## 3. ⭐ 판정 1 — **`sales_order` 는 쓰기 경로를 두지 않는다**

`W-04-01` §5-6 이 답을 갖고 있었다.

> **둘 다 성립하고 배타적이지 않다.** 화면은 **연계 수신을 기본**으로 두고(**목록에 그냥 나타난다**), 파일 업로드를 보조 진입으로 둔다.
> ⚠ **파일 업로드의 형식이 정해지지 않았다** — 고객사마다 다르다.

| 갈래 | 계약 |
| --- | --- |
| **ERP 연계 수신**(기본) | ⭐ **서버가 만든다** — `W-02-01` P/O 수신과 같은 형태. 화면은 목록만 본다 |
| 파일 업로드(보조) | ⛔ **형식 미정이라 요청 본문을 정할 수 없다.** 화면도 **비활성 + 사유**다 |

→ **`GET` 둘만 낸다.** ⛔ `POST /logistics/sales-orders` 를 만들지 않는다.

⚠ **`disposition_decision` 과 다르다** — 저쪽은 **아무도 안 만들어 목록이 빈다**. 이쪽은 **연계가 채운다.**

## 4. ⭐ 판정 2 — 출하 3층은 **리소스 셋이고 쓰기는 둘뿐**

```
sales_order        읽기만          연계가 만든다
shipment_request   POST            W-04-01 「편성」·「단독 생성」
shipment           POST + :동사 3  W-04-04·05 「출하 처리」 · W-04-12 확정·취소
```

### 4-1. `salesOrderId` 를 **필수로 두지 않는다**

「ERP 출하지시 계층은 사실상 부재」·「**무지시 standalone 이 예외가 아니라 상시 구조**」가 확정이고, `W-04-01` 에 **「단독 생성」 버튼**이 있다.

⛔ **`salesOrderId` 를 required 로 두면 단독 생성이 막힌다.** nullable 이다.

### 4-2. ⛔ 편성 취소·확정 취소를 두지 않는다

| 화면이 적은 것 | |
| --- | --- |
| `W-04-01` 「편성 취소」 | ⛔ **두지 않는다** — 출하작업지시 취소는 범위 밖 |
| `W-04-12` 「확정 취소」 | ⛔ **두지 않는다** — 예외 경로 없음 |
| `W-04-04`·`M-04-01`·`W-04-05` 「되돌리기」 | ⛔ **두지 않는다** — `W-01-13` 계열 |

⭐ **취소는 미확정 구간에서만 된다** — `:cancel` 은 `shipment` 에만 붙는다.

## 5. ⭐ 판정 3 — `W-04-12` 는 **`:동사` 셋**이다 (01 형태 그대로)

```
POST /logistics/shipments/{shipmentId}:confirm          확정
POST /logistics/shipments/{shipmentId}:request-cancel   취소 요청 — 사유 필수
POST /logistics/shipments/{shipmentId}:cancel           취소 실행 — 승인 완료 후
```

**01 이 이미 같은 삼중주를 쓴다** — `goods-issues`·`goods-receipts`·`inbound-receipts` 에 `:cancel`·`:request-cancel` 이 있다. **새 형태가 아니다.**

⚠ **`:cancel` 은 실행 시점에 다시 판정한다**(J-8) — 「승인 완료」만으로 통과시키지 않는다. `x-internal-note` 에 적는다.

⛔ **자동 확정 설정은 이 계약이 아니다** — 「이 화면에서 켜고 끄지 않는다. 설정은 `W-06-06` 계열 소관」.

## 6. ⭐ 판정 4 — **반품 입고는 01 계약을 쓴다**

`W-04-06` 이 새 경로를 요구하는 것처럼 보이나 **01 이 이미 덮는다.** 실측:

```
POST /logistics/goods-receipts
  required: receiptTypeCode · plantId · warehouseId · receiptDatetime
            sourceDocumentTypeCode · sourceDocumentId · businessDate · lines
  reasonCode: 사유. 확정된 값 목록이 아직 없다 — 서버가 내려주는 선택지를 쓴다(G-2)
```

**화면도 그렇게 설계돼 있다** — 「원천 구분 선택 | ⚠ **`reason_code` 에 접어 넣는다**(§5-2)」.

→ ⛔ **04 가 반품 입고 경로를 만들지 않는다.** 다만 **`nonconformance` 등록은 04 가 낸다**(같은 화면이 두 계약을 쓴다).

## 7. ⭐ 판정 5 — 출력물이 미룬 빚은 **하나뿐이고 배분에 붙는다**

**1단계에서 셋 중 둘이 01 에 이미 있음을 확인했다.** 남은 하나:

| 부르는 화면 | 필요 | 붙일 곳 |
| --- | --- | --- |
| `P-04-02` 납품 포장 라벨 | 「대상 선택 — **합격 건 목록**」 | ⭐ **`GET /logistics/shipment-lot-allocations`** |

**근거** — `P-04-02` §4 의 대상이 **「포장 단위 · 출하 배분」 다형**이고, 포장 단위는 01(`handling_unit`)이며 **출하 배분이 04**다.

⚠ **「합격」 필터가 필요하다** — 「납품라벨을 고르면 대상 목록이 **「합격」만 활성**」. OQC 판정 결과로 거른다 → `?oqcPassed=true`.

## 9. ⭐⭐ 04 는 **자기 경로보다 남의 경로를 더 많이 쓴다**

**16화면 중 04 경로를 하나도 안 쓰는 화면이 넷이다.**

| 화면 | 쓰는 계약 |
| --- | --- |
| `W-04-03` OQC 출하검사 판정 | ⭐ **03 전부** — 검사 3계층. 04 가 낼 것이 0건 |
| `W-04-08` 완제품 재고 조회 | **01**(`/inventory/balances`) + **03**(`/quality/lot-statuses`) |
| `M-04-04` 제품입고·적치 | **01 전부** — `goods_receipt`·`putaway_task`·`handling_unit` |
| `W-04-10` 제품 폐기 품의 | **01**(`goods-issues` + `:request-approval`) + **공통**(`:approve`) + 04 읽기 |

⭐ **`W-04-03` 이 특히 그렇다** — 03 이 만든 검사 계약을 **그대로** 쓴다. 03 이 「04 가 쓴다」고 예고한 것이 맞았다.

⚠ **그래서 역방향 ②가 결정적이다** — 이 트랙의 요구서는 **인용이 자기 경로보다 많을 것**이다.

## 10. ⭐ 04 가 03 의 마지막 미결을 푼다

```

    W-03-09 특채·한도승인 승인 처리
    이유 — 「부적합 열기」가 04 계약에 걸린다
```
