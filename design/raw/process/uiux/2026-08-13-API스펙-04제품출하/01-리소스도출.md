## 2. ⛔⛔ **처분 결정을 만드는 화면이 없다** — 이 트랙의 가장 큰 발견

### 2-1. 03 과 04 가 서로에게 미뤘다

| 어디 | 무엇이라 적혀 있나 |

⭐ **03 은 04 것이라 했고, 04 화면은 03 이 만든다고 한다.**

### 2-2. 「소유는 쓰기를 가진 쪽」으로 풀어 봤다 — **쓰는 쪽이 없다**

`F04` 정합 확정(2026-07-07)이 「재작업/폐기 **판정**은 전 도메인에서 **03 소관** 통일」이라 했는데, **03 도메인 5화면 중 그 화면이 없다**(조회 2 · Lot Status 전이 1 · 의심자재 등록 1 · 특채 승인 1).

### 2-3. ⚠ 스펙이 이미 알고 넘겼다

## 3. ⛔ `nonconformance` 는 구간 형이 **아니다** — 화면이 갈랐다

**테이블 모양만 보면 구간 형으로 보인다.**

```
quality.nonconformance
    opened_at  timestamptz NOT NULL      ← 시작 필수
    closed_at  timestamptz               ← 끝 없을 수 있다
    CHECK (closed_at IS NULL OR closed_at >= opened_at)
```

⭐ **`work_session`·`lot_hold` 와 3종 세트가 정확히 같다.**

### 3-1. 그런데 규칙 1 에서 걸린다

```
사. 구간 형 규칙 1 — 열린 것 조회가 기본이다
                     ⛔ ?status=RUNNING 아님 → ?open=true
```

**`W-04-07` 의 필터를 보면 상태로 조회한다.**

```
조회·필터 | 창고 · 상태(의뢰 전 / 판정 대기 / 판정 완료)
```

⛔ **세 값짜리 진행 단계다.** 「열렸나 닫혔나」 두 값이 아니다. **끝 시각의 부재로는 「의뢰 전」과 「판정 대기」를 못 가른다.**

→ **라. 업무 문서 형.** `opened_at`·`closed_at` 은 **생애주기 시각**이지 판정 기준이 아니다.

### 3-2. ⚠ `status_code` 의 유무로 가르려다 틀릴 뻔했다

처음에 「`work_session` 은 `status_code` 가 없어서 구간 형」이라 생각했는데 **실측하니 있다**(SQL 851).

```
production.work_session
    started_at   timestamptz NOT NULL
    ended_at     timestamptz
    status_code  app.code_t NOT NULL      ← ⭐ 있다
```

⭐ **구간 형의 정의는 「상태 컬럼이 없다」가 아니라 「진행 중을 끝 시각의 부재로 판정한다」다.** 컬럼의 유무가 아니라 **화면이 무엇으로 조회하느냐**가 가른다.

⚠ **테이블 모양으로 판정하려다 걸렸다** — 2단계 규칙(「테이블이 아니라 화면 버튼을 센다」)이 **1단계에도 걸린다.**

## 4. `shipment` 도 구간 형이 아니다 — **시작 시각이 필수가 아니다**

```
logistics.shipment
    loaded_at   timestamptz     ← nullable
    shipped_at  timestamptz     ← nullable
```

⛔ **둘 다 nullable 이라 「시작 시각이 필수」가 성립하지 않는다.** 상차·출하 시각은 **상태 전이의 부수 기록**이다.

→ **라. 업무 문서 형.** 생애주기는 `status_code` 가 갖는다(예정 → 상차 → 출하 → 확정 / 취소).

## 5. 출하 3층 — **리소스 셋이지 하나가 아니다**

```
sales_order          고객사 지시서 수신본     W-04-01 「지시서 가져오기」
    ↓ 편성
shipment_request     MES 출하작업지시        W-04-01 「편성」 · W-04-02 조회
    ↓ 출하 처리
shipment             실물 출하               W-04-04 · W-04-05 · W-04-12
```

**셋 다 자체 번호·상태·잠금을 갖는다**(실측 — `status_code` + `version_no`). **라인이 아니다.**

⭐ **상위지시가 nullable 인 것이 확정이다** — 「ERP 출하지시 계층은 사실상 부재」·「무지시 standalone 이 예외가 아니라 **상시 구조**」. `W-04-01` 에 **「단독 생성」 버튼**이 있는 근거다.

⚠ **그래서 `sales_order` 없이 `shipment_request` 를 만들 수 있어야 한다** — 계약이 `salesOrderId` 를 필수로 두면 안 된다. 2단계에서 확인한다.

## 6. `shipment_lot_allocation` — **나. 부여·회수 형**

```
version_no 없음 · status_code 없음 · created_at·created_by 만
```

`M-04-01` 「피킹 확정」이 만들고, `P-04-01` 이 **배분 잔여**를 읽는다(「수량 입력 | ≤ 배분 잔여」).

⭐ **잔여는 서버가 파생한다**(L-2) — 화면이 배정 수량에서 빼지 않는다.

## 7. 라인 넷 — **리소스로 올리지 않는다**

| 라인 | 헤더 |
| --- | --- |
| `sales_order_line` · `shipment_request_line` · `shipment_line` | 각 헤더 |
| `nonconformance_lot` | `nonconformance` |

⚠ **앞의 셋 중 둘에 `version_no` 가 있다**(`sales_order_line`·`shipment_request_line`). 01 에도 같은 것이 있어(`purchase_order_line`·`inbound_receipt_line`) **저장소 관행이다** — 라인 단위 잠금이 필요하다는 뜻이지 **리소스로 올릴 근거는 아니다.**
