## §2. 왜 「몇 권인가」가 본질이 아닌가

제안받은 넷(고객 요구사항 · 소프트웨어/하드웨어 스펙 · 의사결정·정책 명세 · 기능 명세)은 **셋이 이미 실물로 있다.** `deliverables/` 에 편람 8종이 있고 번호가 거의 그대로 대응한다.

**문제는 그 편람이 낡았다는 것이다.**

```
deliverables/ 편람 8종      2026-07-30 「전량 신규 작성」으로 만듦
3주 뒤 실측                  API 요구서 머리말 6/8 이 실물과 어긋남
```

**원인은 복사다.** 원본이 바뀌어도 **복사본에는 갱신 의무가 아무에게도 없다.** 정리보고 §5-1 의 판정이 이것을 한 줄로 말한다 —

> ⭐⭐ **스크립트가 정본인 자리는 하나도 안 갈렸고, 손으로 쓴 수치는 예외 없이 낡았다.**

| | |
| --- | --- |
| **안 갈린 것** | 조항 150 · 화면 117 · 계약 규모 · 통지 89 · 인용 327 · 업무 코드 — **전부 스크립트가 정본** |
| **갈린 것** | 요구서 머리말 6/8 · 통합 정보구조 산문 · README 6수치 · 메모리 31건 — **전부 손으로 씀** |

→ **이번 결정의 축은 「몇 권으로 나누나」가 아니라 「무엇을 복사하지 않나」다.** 권 수는 그 다음 문제다.

**③ 99 인계 대장을 부속으로 넣었다.**
미결 601행 + 업무 코드 미확정 + 다형 참조(한 칸이 상황에 따라 여러 표를 가리키는 방식) 대응표 결손 22곳. **최종 인도물에 「아직 안 정해진 것」 자리가 없으면 그것이 조용히 사라진다.**

## §4. ⭐ 각 권이 **새로 쓰는 것은 셋뿐**이다

이것이 이 설계의 핵심이다. §2 의 판정을 그대로 적용한다.

| 새로 쓴다 | 무엇 |
| :-: | --- |
| ① **표지** | 이 권이 답하는 물음 · **무엇이 정본인가** · 읽는 순서 |
| ② **지도** | 「이걸 찾으면 저기」 — **경로만.** ⛔ 내용 복사 금지 |
| ③ **사람이 판단한 것** | 왜 그렇게 정했나 · 택하지 않은 안 · **못 센 것과 그 이유** |

**숫자·목록·차집합은 전부 명령이다.** 문서에 상수로 박지 않는다.

### 4-1. 검증된 서식이 이미 하나 있다

`deliverables/06-API-요구서-01자재창고.md` 가 **요구서 8장 중 유일하게 실물과 일치**하고, 이유가 명시돼 있다 —

> **숫자 + 실측일 + 세는 명령.** 셋이 다 있으면 **낡아도 낡은 것이 보인다.**

⭐ **다섯 권의 머리말은 전부 이 서식을 따른다.** 나머지 일곱 요구서도 같이 고친다.

### 4-2. 무엇을 문서로 두고 무엇을 뽑나

**가르는 기준 = 「사람이 판단한 것인가, 실물을 세면 나오는 것인가」** (정리보고 §5-4 그대로).

| 문서로 둔다 | 명령으로 뽑는다 |
| --- | --- |
| 확정문 · 조항 · 서식·규약 | **모든 개수** — 화면·경로·오퍼레이션·스키마·조항·통지·미결·갭·업무 코드 |
| **왜 그렇게 정했나** | **집합 차집합** — 미통지 화면 · 계약 없는 화면 · 추적 표지 없는 미결 |
| 화면 이름 · 설계 의도 | 산출물 목록 · 검사기 목록 |
| 등급의 **정의** | 등급의 **분포와 목록** |
| **못 센 것과 그 이유** | |

## §5. 신설물 셋

### 5-1. Ⅲ·Ⅴ 표지 2장

각각 §4 의 셋(표지·지도·판단)만 담는다. **본문을 옮기지 않는다.**

⚠ **Ⅲ 표지가 먼저 풀어야 할 것** — `02` §7 설계 결정 대장이 **「몇 건인가」를 세는 명령이 없다.** README 는 「142행」이라 적는데 그 기준을 재현하지 못했다(§9). Ⅲ 표지를 쓰기 전에 **세는 기준을 정하고 명령을 만든다.**

### 5-2. ⭐ 화면 → 스펙 파일 경로 색인 (생성기)

**지금 이것이 하나도 없다.** 실측 —

```
grep -c '화면상세스펙' deliverables/04-통합-IA.md   →  0
스펙 118장이 흩어진 폴더                          →  20
```

즉 **개발이 화면 하나의 상세 스펙을 찾으려면 날짜 폴더 20곳을 뒤져야 한다.** 통합 정보구조 문서는 화면 번호만 적고 파일 경로를 안 적는다.

⭐ **개발 인수용 세트에서 이것이 빠지면 나머지가 아무리 정확해도 안 읽힌다.** 화면 번호 → 스펙 경로 → 계약 경로 → 착수 통지 번호를 한 줄로 잇는 **생성물**로 만든다. 손으로 쓰지 않는다 — 스펙이 새 차수 폴더로 늘어날 때마다 낡기 때문이다.

⛔⛔ **이것을 새로 만들지 않는다 — 이미 제안돼 있다.** 정리보고 §5-5 가 **`화면-진도표.md` + 생성기**를 신설 목록에 올려 두었고, 내용이 「화면 117 ↔ 요구서 §3 ↔ 계약 ↔ 통지 **네 집합의 차집합**」으로 여기서 필요한 것과 같은 물건이다.

> **판정 — 하나로 만든다.** 이 색인은 `화면-진도표.md` **그 자체**이고, 여기서 더할 것은 **스펙 파일 경로 열 하나**뿐이다. 둘로 만들면 정리보고 §3 이 잡아낸 **이중 기록**을 우리가 새로 하나 더 만드는 셈이 된다.

### 5-3. 99 인계 대장 (생성기 확장)

기존 `deliverables/collect-open-items.py` 를 확장한다. 미결 709행은 이미 나온다. 여기에 업무 코드 미확정분과 다형 참조 대응표 결손을 합류시킨다.

⚠ **생성기가 「무엇을 안 보는가」를 함께 적는다** — 미결의 내용이 맞는지 · 표지가 가리키는 곳이 살아 있는지는 이 대장이 못 본다. 이 규칙이 옳다는 증거가 이미 있다(정리보고 §5-2 — 이번에 찾은 구멍이 전부 그것을 안 적은 쪽에서 나왔다).

## §7. 택하지 않은 안

### 7-1. 전량 신규 통합 작성 (다섯 권을 처음부터 다시 씀)

읽기는 제일 좋다. **택하지 않은 이유** — 정확히 그 방식으로 만든 것이 지금의 편람 8종이고, **3주 만에 6/8 이 낡았다.** 이번엔 원본 부피가 훨씬 크다(요구서 8장 · 계약 7종 · 스펙 118장 · 조항 150). 더 빨리 갈린다.

### 7-2. 4권 — Ⅲ 의사결정·정책을 Ⅱ 설계 사양서에 흡수

권 수는 줄지만 **Ⅱ가 두꺼워지고 공유계약 150조항이 아키텍처 서술 속에 묻힌다.** 개발이 「만들 때 지킬 규약」을 찾는 동선이 나빠진다. 이 둘은 **읽는 시점이 다르다** — Ⅱ는 착수 때 한 번, Ⅲ은 만드는 내내 계속이다.

### 7-3. 도메인 축 분권 (01 자재창고 … 06 기준정보로 나눔)

개발자가 한 도메인만 맡을 때 편하다. **택하지 않은 이유** — **전역 규약(공유계약 150조항)이 갈 자리가 없어진다.** 도메인마다 복사하면 §2 의 실패를 그대로 재현한다. 도메인 축은 분권이 아니라 **§5-2 색인의 정렬 축**으로 제공한다.

### 8-3. ⛔ 구현 계획은 **지금 짜지 않는다** (사용자 확정 2026-08-18)

아래 표는 **순서의 뼈대**이고 **실행 계획이 아니다.** 상세 계획은 **05 설비툴 계약이 끝난 뒤** 짠다.

**왜 미루나** — 05 계약이 만들어 낼 것이 이 편성의 입력을 바꾼다. 계약 파일 1종이 늘고(6→7), 경로·오퍼레이션·스키마 총계가 바뀌고, 착수 통지가 17장 늘고(89→106), 05 화면 17장의 미결 행이 대장에서 해소로 옮겨 간다. **지금 짠 계획은 그 넷을 전부 추정으로 적게 되고, 이 저장소에서 추정으로 적은 수치는 예외 없이 낡았다**(§2).

⚠ **미루는 것이 잊히지 않게 재개 조건을 적는다** — 「05 설비툴 계약 6단계(통지 17장 발행)가 끝났는가」. 그때 이 문서 §3 구성을 입력으로 계획을 짠다.
