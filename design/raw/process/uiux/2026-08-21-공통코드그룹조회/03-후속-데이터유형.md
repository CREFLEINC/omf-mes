## 무엇

**측정치 그리드가 「어느 칸에 입력을 담을지」를 알 수 있게 했다.**

| 대상 | 바뀐 것 |
| --- | --- |
| `InspectionItemSpec.dataTypeCode` **2곳** | 그룹 코드·값·**칸 대응** 명시 · ⛔ 틀린 예시값 `"STANDARD"` 정정 |
| 측정치 값 칸 **6곳** | `numericValue`·`textValue`·`booleanValue` 가 **어느 유형과 짝인지** 명시 |
| 측정치 스키마 **2곳** | **「셋 중 하나만 · 셋 다 비어도 됨」** 규칙을 내부 주석에 |
| 공유계약 `G-32` | 소절 신설 — 「고객이 정할 마스터에 **동작이 걸리는 값**이 섞이지 않게 한다」 |
| `99-인계대장.md` §2 | **분류 착오를 기록** + 후속 남김 |
| 화면 스펙 `W-06-02` | `[추정]` 표기 제거 · 받는 법 명시 |

## 어떻게

### 무엇이 막혔나

계약이 이렇게만 적고 있었다.

```
"공통코드 — 수치/텍스트/불리언 [추정]"     ← 계약이 «스스로» [추정] 이라 적었다
example: "STANDARD"                       ← ⛔ 데이터 유형이 아니다
```

측정치는 세 칸 중 **하나만** 채울 수 있으므로(`num_nonnulls ≤ 1`), 항목마다 **어느 칸을 쓰는지** 알아야 입력을 그린다.

### ⭐ 구현팀이 값의 «모양»으로 추론하지 않았다

「상하한·단위가 있으면 수치, 없으면 텍스트」로 가르면 **불리언 항목이 텍스트로 떨어져** 사용자가 `OK`/`NG` 를 `text_value` 에 적게 된다. **자료의 모양이 틀어지고, 나중에 되돌릴 수 없다.**

### 실측 — 근거는 전부 이미 있었다

| 무엇 | 어디 |
| --- | --- |
| `data_type_code` 가 **검사기준 항목 한 곳에만** 있다 | 계약 7벌 전수 — `mdm-기준정보.json` 2곳뿐 |
| **필수**다 | `InspectionItemSpec.required` |
| 세 칸이 **전부 선택**이다 | `InspectionMeasurement.required` 에 값 칸 없음 |
| 「**수치형일 때만 의미**」 | `uomId` 의 설명문 — ⭐ 세 유형이 실재한다는 방증 |
| 화면 스펙도 **`[추정]`** 이었다 | `W-06-02` §4 「데이터 유형 / *(미정)*」 |

## 왜

### ⭐ 값을 지어내지 않았다 — 물리 모델이 세 칸을 이미 이름 짓고 있다

```
inspection_measurement.numeric_value   →  NUMERIC
inspection_measurement.text_value      →  TEXT
inspection_measurement.boolean_value   →  BOOLEAN
```

⭐ **값 이름이 곧 칸 이름이라 대응표가 따로 필요 없다.** 구현팀의 물음 ②(어느 칸에 대응하나)가 **이름 짓기로 구조적으로** 풀린다. 판정 셋을 수량 세 칸에서 딴 것과 **같은 원리**다.

⚠ **세 값뿐인 것도 구조가 정한다** — 담을 칸이 셋이라 넷째 값을 만들면 담을 곳이 없다. 값 목록이 늘 수 있는 다른 코드들과 **이 점이 다르다.**

**그룹 이름**은 `G-32` 규칙 그대로다 — `data_type_code` → `DATA_TYPE` 은 「무엇의」 데이터 유형인지 모르므로 테이블 이름을 앞에 붙여 **`INSPECTION_ITEM_SPEC_DATA_TYPE`**.

### ⛔ 뿌리는 **분류 착오**였다

이 값이 **「고객사가 자기 분류 체계를 정해야 하는 값 46종」**(`99-인계대장.md` §2)에 들어 있었다. 그런데 **바로 그 자리의 가르는 기준**과 어긋난다.

> 「화면·계약의 **동작**이 그 값에 걸리는가. 걸리면 설계가 정하고, 안 걸리면 마스터다.」 — `G-31`

**입력 위젯의 종류와 저장할 칸이 걸린다.** 설계가 정했어야 할 값이다.

⚠ **왜 섞였나** — 그 46종은 **「`enum` 이 없다」는 기계적 기준**으로 뽑은 목록이고(`count-undecided-codes.py`), 「고객이 정할 값인가」로 가른 것이 아니다. **두 목록이 같지 않은데 같은 것처럼 읽혔다.**

⚠ **수치 46 은 그대로다** — `enum` 을 넣지 않았으므로 기계적 계수는 안 바뀐다. 바뀐 것은 **「누가 정하나」**이지 「정해졌나」가 아니다.

### ⛔ `enum` 을 넣지 않았다

넣으면 자유 문자열이 값 목록으로 좁아져 **⛔ 등급 통지**가 되고 이미 만든 코드가 틀린다. 판정과 같은 방식으로 **설명 + 공통코드**로 두고, 대신 **모르는 값이 왔을 때 화면이 무엇을 하는지**(비활성 + 사유 · `G-2`)를 설명에 적었다.

### ⚠ 값을 「반드시」 채우게 만들지 않았다

`num_nonnulls ≤ 1` 은 **「많아야 하나」**이지 「적어도 하나」가 아니다. **육안 항목은 판정만으로 성립한다**(`P-02-13` §5-9 「항목 판정(합격/불합격) | 육안 항목」). 판정은 이미 필수다.
