## 개발팀에 전달 사항

**ⓐ 입니다 — 설비·설비그룹 마스터 화면(`W-05-12`) 안에서 만듭니다.** 새 화면을 세우지 않습니다.

⛔ **다만 「두 근거가 다르게 읽힌다」가 아니라 저희 표 하나가 덜 적혀 있던 것입니다.** 액션 표를 고쳤습니다.

---

### 1. 왜 ⓐ 인가 — **근거 넷이 이미 이 화면에 서 있었습니다**

| 근거 | 점검 항목 마스터가 |
| --- | :-: |
| 화면 스펙 §4-C-1 — 항목코드·항목명·점검 유형·판정 방식·단위·상하한·필수 여부·점검부위·표시 순서 **8행을 근거와 강도까지 붙여 정의** | ✅ 이 화면이 정의했다 |
| 화면 스펙 §7 디자인 시스템 매핑 — **「점검 항목 목록」**(`Table`) · **「점검 항목 순서 재배치」**(`reorderable`) | ✅ 이 화면에 걸려 있다 |
| API 요구서 05 §4 | ✅ **「점검 항목 마스터 CRUD — `W-05-12` 가 쓴다」** |
| 화면 스펙 §8 미결 2 | ✅ 「**정의했다**(§4-C) — 항목 마스터 + 부여 2종」 |
| **화면 스펙 §5-1 액션 표** | ⛔ **없었다** ← 여기 하나만 |

⭐ **「순서 재배치」가 결정적입니다.** 부여에는 표시 순서가 없습니다(부여가 갖는 것은 대상·항목·주기·사용 여부뿐 — §4-C-2). **표시 순서는 마스터의 칸**이므로, 그 매핑이 이 화면에 걸려 있다는 것은 **마스터 편집을 이 화면 안에 두고 그린 것**입니다.

---

### 2. 자리 — **부여 창 «안»이 아니라 그룹·설비와 «나란한 셋째 목록»입니다**

걱정하신 「탭이 넷이 되고 창 안에 창이 생긴다」를 피합니다.

```
W-05-12  설비·설비그룹 마스터
   ├── 설비 그룹      (목록 + 편집)
   ├── 설비           (목록 + 편집)
   └── 점검 항목      (목록 + 편집)   ← 마스터. 여기서 만든다
          ↑
       부여 창은 이 목록에서 «고르기»만 한다
```

⛔ **부여 창 안에 「새 항목 만들기」를 두지 않습니다.** 창 안에 창이 생기고, **만들다 만 항목이 부여와 한 트랜잭션에 얽힙니다.** 공유계약 `B-6`(마스터 테이블과 부여 테이블을 구분한다)을 **화면에도 그대로** 적용합니다 — 만드는 자리와 고르는 자리를 나눕니다.

⚠ **빈 목록 문구에 길을 붙여 주십시오.** 지금 「등록된 점검 항목이 없습니다」에서 멈추는데, **어디서 등록하는지**를 함께 말해야 합니다(`G-3` — 「어떻게 풀 것인가」를 함께 적는다). 이제 그 자리가 같은 화면 안이므로 **점검 항목 목록으로 가는 길**이면 됩니다.

---

### 3. 액션과 경로 — **다섯 줄을 요구서 매핑에 넣었습니다**

| 액션 | 경로 |
| --- | --- |
| 점검 항목 추가 | `POST /mdm/equipment-inspection-items` |
| 점검 항목 저장 / 취소 | `PUT /mdm/equipment-inspection-items/{equipmentInspectionItemId}` — 토큰은 같은 경로 상세 조회의 `ETag` |
| 점검 항목 목록·상세 | `GET /mdm/equipment-inspection-items` · `/{equipmentInspectionItemId}` |
| **점검 항목 사용 중지** | `PUT …/{equipmentInspectionItemId}` 에 `isActive=false` — ⛔ **전용 경로도 물리 삭제도 없습니다**(`B-4`) |
| 점검 항목 순서 재배치 | `PUT …/{equipmentInspectionItemId}` 에 `displayOrder` |

⛔ **짝 제약을 화면이 겁니다** — 판정 방식이 `MEASUREMENT`(측정값)이면 **단위(`uomId`)·하한·상한이 함께 필요**합니다(`#186` 회신과 같은 규칙).

⭐ **수정 가부는 화면이 세지 않습니다** — 상세 응답의 `editability` 와 부여 건수(`assignmentCount`)가 **가부와 사유를 함께** 내려 줍니다(`B-4`).

---

### 4. 물어보신 것 하나 더 — **여러분 판단이 옳았습니다**

「물리 모델에 테이블이 없으니 데이터 모델 반영 뒤에」라는 `#186` 의 단서를 무릅쓰고 착수하신 판단 말입니다. **옳습니다.**

- **클라이언트는 계약을 상대로 만듭니다.** 물리 테이블이 나중에 들어와도 그 코드는 바뀌지 않습니다 — 정확합니다.
- 저희 설계 원칙이 그것을 뒷받침합니다 — **설계가 먼저 정하고 데이터 모델이 따라옵니다.** 이 화면 §3-3 이 그 원칙이 처음 적용된 자리라고 적어 두었습니다.
- ⚠ **`#186` 의 그 문장은 「안전합니다」라는 권고였지 차단이 아니었습니다.** 대조하신 세 가지(계약 6경로 정의됨 · 미결 대장에서 빠짐 · 소비 화면 `M-05-01` 착수 열림)가 **정확히 맞는 확인 절차**입니다.

---

### ⭐ 짚어 주신 것이 옳았습니다

**「화면 ID 신설은 설계 결정이라 정하지 않고 여쭙는다」** — 그 선이 맞습니다. 화면을 늘리면 저희 쪽 정본이 둘(통합 정보구조·화면 인벤토리) 움직이고 생성기 기대 계수도 함께 고쳐야 합니다. **임의로 늘리셨다면 저희가 모르는 화면이 생겼을 것**입니다.

⛔ **그리고 저희 요구서의 표 하나가 결손을 정상으로 읽히게 하고 있었습니다.** 「계약에 있는데 화면이 안 부르는 경로」(§4) 표에 이 네 경로가 서 있었는데, **화면은 부르고 있었고 매핑표(§3-1)가 안 적고 있던 것**입니다. 「역방향」이라는 이름 때문에 **빈자리가 설명된 것처럼** 보였습니다 — 그 경위도 요구서에 적어 두었습니다.

---

### ⚠ 아직 정해지지 않은 것 하나

**표시 순서를 실제로 쓸 것인지**는 열려 있습니다(화면 스펙 §8 미결 8 — 현행 일상점검표 실물을 봐야 확정됩니다). **칸과 경로는 지금 있으니 만드셔도 되고**, 확정되면 그대로 굳습니다.
