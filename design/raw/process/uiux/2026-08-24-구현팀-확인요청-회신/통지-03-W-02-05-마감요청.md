## 무엇이 바뀌었나

**W-02-05 W/O 마감·ERP 실적 송신** — **마감 요청의 모양이 둘 바뀌었습니다.**

`omf-mes#208`·`#209` 로 물어 주신 것의 답이고, 두 분 다 「답변 전에는 구현하지 않겠다」고 멈춰 주셨습니다. **지금 만드시는 중일 자리라 묶지 않고 즉시 보냅니다.**

```
POST /production/work-orders/{workOrderId}:close
  헤더  Idempotency-Key · If-Match            ← If-Match 가 «필수»로 들어왔습니다
  본문  remainderDispositionCode              ← 필수에서 «조건부»로 내려왔습니다
        reasonCode
        erpSendItems
```

## 코드에 무엇을 해야 하나

### 1. `If-Match` 를 싣습니다 (필수)

토큰 원천은 물으신 그대로 **`GET /production/work-orders/{workOrderId}` 의 `ETag`** 입니다. 불투명 문자열이라 파싱하지 않습니다. `409` 면 배너 + **「최신 불러오기」** 입니다.

⭐ 형제 전이 `:hold`·`:resume` 가 **선택**인 것을 보고 헷갈리실 수 있어 적어 둡니다 — 그 둘은 **현장 단말의 오프라인 대상**이라 보낼 것 보관함이 토큰을 싣지 못해서 선택입니다. 마감은 **관리웹 온라인 전제**이고 **되돌릴 수 없어**(재오픈 금지) 필수입니다.

### 2. 잔량 처분을 **미달일 때만** 보냅니다

```
미달          → remainderDispositionCode 를 «보낸다» (CARRY_OVER | WRITE_OFF)
정상 · 초과   → 이 칸을 «비운다»
미달 · 초과   → reasonCode 를 보낸다
정상          → 두 칸을 다 비운다
```

⛔ **정상·초과용 세 번째 값을 만들지 않았습니다** — 넘길 잔량도 없앨 잔량도 없어 두 값 중 어느 것도 뜻이 맞지 않습니다. **없는 업무 개념을 만들게 되므로 비워 보냅니다.** 「의미가 맞지 않는 둘 중 하나를 보내야 한다」는 지적이 정확했습니다.

**서버 검증 400 네 줄**

```
미달인데 remainderDispositionCode 가 없다        → 400
정상·초과인데 remainderDispositionCode 가 있다   → 400
미달·초과인데 reasonCode 가 없다                 → 400
정상                                             → 두 칸을 다 비운다
```

### 3. 판정은 **서버가 내린 값**을 씁니다

화면이 양품 합계와 지시 수량으로 다시 계산하지 마십시오. 같은 화면 건인 `omf-mes#207` 에서 **마감 3분류 판정**(`completionJudgmentCode` = `UNDER`·`NORMAL`·`OVER`)을 응답에 싣기로 했고, **서버가 그것과 본문을 대조해 검증**합니다. 화면이 따로 판정하면 두 판정이 갈립니다.

⚠ **「정상」의 폭(허용 오차)은 아직 미정입니다.** 규칙 네 줄은 그대로고 **미달의 경계만** 움직입니다 — 정해지면 서버 한 곳만 고칩니다.

## 아직 오지 않은 것 — 같은 화면에 ⚠ 가 있습니다

`omf-mes#207` 의 **실적 누계·선발행 슬롯 집계**는 응답 필드·질의 파라미터 추가라 기존을 깨지 않습니다. 규칙대로 **차수 마감 때 묶어서** 보내겠습니다. 다만 위 3번(판정을 서버가 준다)이 그것과 한 벌이라 **먼저 알려 둡니다.**
