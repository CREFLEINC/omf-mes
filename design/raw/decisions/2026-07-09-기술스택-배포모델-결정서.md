### 0.3 결정 순서 — 왜 배포가 스택에 선행하는가

WBS §8은 #1 기술 스택 → #2 배포 모델 순으로 나열하나, 본 문서는 **배포 모델을 먼저 결정한다.** 배포 위치가 네트워크 경로(C2·C3)·백업 구조(C4)·인터넷 의존 기능의 허용 범위(C11, 결정 19)를 규정하고, 그것이 다시 런타임·DB 선택의 제약이 되기 때문이다. 역순으로 결정하면 스택이 배포를 사후 정당화하게 된다.

**결정한 것**: MES 서버의 위치·이중화·백업·인터넷 의존·원격 운영. (WBS §8-2 종결)

| # | 항목 | 확정 내용 |
| --- | --- | --- |

| 2 | 백업 | **백업용 NAS 설치** |
| 3 | 인터넷 의존도 | **설치·유지보수 시에만 일시적으로 보장** (운영 중 비보장 = C11) |
| 4 | 서버 이중화 | **이중화 구성 필요** → 방식 = **웜 스탠바이** (질의 확정) |

**대안 비교 (v0.1 — 이력 유지)**: (a) 온프레 단일 / (b) 클라우드 단일 / (c) 클라우드+엣지 / (d) 온프레+오프사이트 백업·원격 채널 중 **(d) 채택**. 단, v0.1의 (d)는 상시 인터넷 채널(아웃바운드 터널·클라우드 복제)을 전제했으나 **C11 확인으로 조정**: 백업 격리=사내 NAS(+선택적 반출), 원격 운영=유지보수 창구 한정. (b)·(c)의 배제는 C11로 가정이 아닌 **확인된 사실**이 됐다 — 운영 중 인터넷이 없으므로 클라우드 정본은 아예 성립하지 않는다.

**운영 규격:**

- **서버**: 공장 내 서버 **이중화 — 웜 스탠바이** `[확정 2026-07-10 질의]`. 구성안(설계 제안 — 사양 협의와 함께 확정): **동일 사양 2대** + PostgreSQL 스트리밍 복제(주→예비) + 장애 시 **수동 전환**(목표 수십 분, 절차서+리허설). 자동 failover(HA 클러스터)는 구축·운영 복잡도 대비 이득이 없어 배제 — 전환 판단에 사람을 두는 것이 오동작(split-brain)보다 싸다. 서버 사양·설치 위치·UPS·RTO/RPO는 고객 협의 (§6 미결 #3).
- **백업(C4 충족)**: 일 단위 논리 백업 + WAL 연속 아카이빙(PITR) → **사내망 NAS로 연속 복제**(v0.1의 '주 단위 오프사이트'는 인터넷 대역폭 전제였음 — NAS는 사내망이므로 복제 주기 제약이 없다) → 연 단위 콜드 아카이브(NAS·외장 매체). 보존 5~10년은 "운영 DB에 10년치 적재"가 아니라 **트랜잭션 테이블 파티셔닝 + 콜드 아카이브 분리**로 충족(유지).
- **NAS 위치·재해 격리 = 고객사 선택 대기** `[🔹2026-07-10 질의 — 미정]`: ① 서버와 물리 분리 설치(다른 건물/공간 — CREFLE 권장) ② 주기적 암호화 외장 매체 반출 로테이션 ③ 유지보수 창구 시점 외부 복제 ④ 동일 공간 수용. **④ 선택 시 화재 등 국지 재해에서 원본·백업 동시 소실 위험이 C4의 갭으로 남는다** — 고객 고지 필수 (§4 리스크 8).
- **원격 운영**: **상시 원격 채널 없음**(C11). 유지보수 = **방문 기본** + 유지보수 창구(고객 승인 하 일시 인터넷 개통)에서의 원격 세션 보조. 인바운드 포트 상시 개방 금지 유지. 배포는 §2.4의 오프라인 설치 패키지 체계.
- **알림 채널(QA #24 조정)** `[확정 2026-07-10 질의]`: 정본 알림 = **사내망 채널**(관리 대시보드·알림센터·POP 표시, 고객사 지정 담당자 수신). 카카오톡/Zalo는 **인터넷 가용 시에만 동작하는 best-effort 보조 채널**로 격하 — QA #24의 채널 합의에 대한 조정이므로 **고객 고지 필요** (§6 미결 #12).
- **인터넷 의존 기능의 전면 배제**: 외부 AI API 없음(결정 19 — OCR 온프레 실행), 원격 관측 없음(§2.4), 상시 터널 없음. **운영 중 인터넷이 0이어도 전 기능이 동작한다.**
- **이식성 보존**: 전 구성요소 컨테이너 패키징 유지 — 클라우드 재배포 경로를 닫지 않는다(기획서 §11-2 SaaS 티어 옵션).

**근거**: v0.1 근거 1~6 유지(C1 결정적·C2 pull 방향·C3 사내망·C4 격리 요구·데이터 주권·(c) 배제). C11 추가로 클라우드 계열 배제가 설계 판단에서 **확인된 전제**로 승격. 데이터 주권 논점은 외부 복제 자체가 사라져 **외장 매체 국외 반출을 선택할 때만** 발생(§6 미결 #4 조건부 격하).

## 3. 부속 결정 — 스택에서 파생하나 후부착이 불가능한 것

### 결정 17 — 오프라인 내성 아키텍처 `[확정 2026-07-10 — 범위 재정의]`

**원칙 (🔹CTO 확정)**: 오프라인 내성은 **전체 기능에 대한 광범위한 적용이 절대 아니다.** MES 운영의 기본 전제는 서버와의 상시 통신 보장이며, 부득이한 오프라인 발생 시 **최소한의 운영** — 생산 공정 가동에 직접 영향을 주는 부분 — 이 이루어지게 하는 것이 목표다.

**오프라인의 정의 (🔹CTO)**: 오프라인 = **사내망에서 단말이 서버와 통신할 수 없는 상태.** 인터넷은 이 시스템에서 전혀 고려 대상이 아니다(운영 경로에 없음 — C11과는 별개의 축).

**확정 시나리오 2건 (🔹CTO — 이것이 오프라인 동작의 확정 계획):**

| # | 시나리오 | 동작 구조 |
| --- | --- | --- |
| 1 | **생산 실행** — 자재 투입 → 생산 실적 → 생산LOT 등록 | **W/O(제조 지시서) 발행 시점에 서버가 대상 POP에 W/O 내용 + 기발행 LOT 라벨(서버 렌더링 완료 이미지 — 결정 18 접점)을 선배포(로컬 보관)** → 통신 두절 시에도 해당 W/O의 생산 진행·실적 입력·라벨 출력 계속 |
| 2 | **생산 자재 입·출고** | **단일 단말기로 입측·출측 스캔을 모두 수행** — 이동 짝(출고↔도착, QA #16 양방향)의 정합이 한 단말의 큐 안에서 유지된 채 복구 시 일괄 동기화 |

**그 외 전 기능 = 오프라인 미지원.** v0.1의 금지 목록(품질 판정 Lot Status 전이·출하 확정 PGI·ERP 송신·실사 조정)은 이 일반 원칙의 예시가 된다 — 서버 통신 필수, 오프라인 시 버튼 비활성화+사유 표시. v0.1의 "화이트리스트 최종본 잔여"는 **시나리오 2건 확정으로 해소**.

**메커니즘 (v0.1 유지·축소):**

- **선배포(pre-sync)**: W/O 발행 이벤트 → 대상 POP에 W/O·Routing Rev 스냅샷·기발행 라벨을 push 배포. **라벨은 서버 렌더링 완료 이미지로 선배포**한다 — 렌더링이 서버 소관(결정 18)이라 오프라인 단말에는 렌더링 수단이 없으므로, 데이터만 선배포하면 시나리오 1의 '오프라인 라벨 출력'이 성립하지 않는다. v0.1의 '범용 사전발행 풀'은 **W/O 단위 선발행·선배포로 축소**(P3 패턴 정합 — 발행·활성·폐번 라이프사이클 유지).
- **outbox**: 실적·스캔 기록의 로컬 큐 — **앱 관리 SQLite**(Electron/Capacitor, §2.3 — 브라우저 IndexedDB 회수 위험 원천 제거). 순서 보존(seq)·지수 백오프·복구 시 순차 재생.
- **멱등성**: 전 쓰기 API `Idempotency-Key`(클라이언트 UUID) 필수 — 계약 표준 헤더(P0.4). 서버는 키→결과 보존으로 재전송 멱등 처리.
- **시각 분리**: `occurredAt`(단말 사건 시각) / `receivedAt`(서버 수신 시각) 분리 기록 — P0.3 스키마에 반영(후부착 불가 항목).
- **실패 3분류**: 네트워크(재시도) / 검증 실패 4xx(즉시 수동 검토 큐 — 후속 작업 차단 방지) / 충돌 409(사람 판단). 수동 검토 큐는 담당자 배정 필수(조용한 유실 금지 — 설계 원칙 ②).
- **표시 의무**: 단말 상단 `오프라인 · 미동기 N건` 상시 표시.

**정합 확인 (v0.1 핵심 통찰 유지)**: ① 오프라인 채번은 P3(선발행)가 해결 — CORE-1(발번)·CORE-4(라벨)는 **W/O 발행 시 일괄 발번+선배포 API**를 처음부터 갖춘다. ② 충돌 병합은 결정 08(원장 append-only·잔량 파생·캐시 없음)이 전제 — 재생 순서가 달라도 잔량은 재계산으로 수렴한다.

**영향**: CORE-1·CORE-4 명세에 선배포 API. P0.4 계약에 멱등 키·에러 3분류. P0.3 스키마에 시각 분리·선배포 상태.

### 결정 18 — 라벨 출력 경로 `[확정 2026-07-10 — 채택]`

**확정**: **서버에서 렌더링을 마친 라벨 이미지를 인쇄하는 방식 채택**(🔹CTO). 서버에 한국어·베트남어 지원 폰트를 탑재하므로 프린터 내장 폰트 의존이 사라진다 — **베트남어 라벨 실기 검증은 불요**(🔹CTO 확인, v0.1 ★해소).

**인쇄 경로 보완 (§2.3 연동)**: v0.1의 '로컬 프린트 에이전트(별도 상주 프로그램)'는 **POP 응용프로그램에 인쇄 기능을 내장**하는 것으로 대체한다 — 기존 '라벨 셋팅 프로그램'(HW스펙 §2.2, 크레플 제작·모듈 D 설치 계획)이 POP 앱으로 흡수된다. 프린터(B)가 배치되는 스테이션(조합 1·3)의 D 패널 PC가 POP 앱을 구동하므로 인쇄 지점과 앱 지점이 일치하며, Electron의 네이티브 권한으로 USB 프린터 제어(Windows 스풀러 또는 TSPL raw)가 가능하다.

**오프라인 접점(결정 17)**: 서버 렌더링 방식에서 오프라인 라벨 출력(시나리오 1)이 성립하려면 **선배포 페이로드가 렌더링 완료 이미지**여야 한다 — 결정 17 선배포 메커니즘에 명시.

**잔여**: 인쇄 속도·전송 데이터량은 **개발 중 자연 확인으로 격하**(별도 실기 검증 일정 불요 — v0.1 미결 #8 조정). 성능 미달 시 텍스트 커맨드 부분 회귀 옵션 유지. TTP-247 EoL 확인은 조달 트랙(트랙 H) 유지.

### 결정 19 — AI 계층의 위치와 1차 범위 `[확정 2026-07-10 — AI Agent 전면 제외]`

**확정 (🔹CTO)**: **이번 계획에서 AI Agent 사용은 완전히 제외한다.** v0.1의 "확정 2종 한정"에서 한 단계 더 축소 — 해당 2종도 AI Agent가 아닌 통상 기술로 구현한다.

- **거래명세서 분석(QA #29) = OCR** (CV 또는 딥러닝 모델, VLM 중 선정). **온프레미스 로컬 실행 전제** — C11(운영 중 인터넷 비보장)로 외부 API 호출이 불가능하므로 모델을 현장 서버에서 구동한다. 구현은 **Python 서비스**(별도 컨테이너 — §2.2, 팀 보유). 파싱 결과는 입하 등록 폼 프리필 → 작업자 확인 후 저장, 인식 실패·저신뢰 시 **수기 입력 폴백**(REQ-PR-0006 To-Be "선택적 기능/수기 입력 가능"과 정합). 엔진 선정·한/베 혼재 명세서 인식률 검증 = §6 미결 #9.
- **출하지시 = 결정론적 엑셀 파서** (고객사 지정 양식, REQ-PR-0029). LLM 불사용. 샘플(E5) 수령 후 매핑 확정.
- **RAG 정보 조회 = 포함 여지 있음** (🔹CTO 주의 표기). 범위·방식 미정 — 포함 확정 시 온프레 실행 전제(C11)로 **서버 사양(GPU 등)에 영향**이 크므로 서버 조달 확정 전 판단 필요 = §6 미결 #10.
- NLQ·일일 브리핑·FEFO 제안·자동 발행류 = OMF-AI 페이즈 이연(변동 없음 — QA #20 Analytics 이연과 정합).

**긴장 종결 (v0.1 ★해소)**: 기획서 §4.2 축1('AI 네이티브')과의 긴장은 **본 프로젝트 = 제품 1호 구축(레퍼런스), AI = 후속 OMF-AI 페이즈**로 정리 — AI Agent 전면 제외 확정이 그 명문화다. 축적되는 실데이터가 OMF-AI의 입력이 된다.

**영향**: WBS §8-3 종결. WBS §4.2 **트랙 AI 삭제** — OCR·엑셀 파서는 D01(입하)·D04(출하지시) 도메인 기능으로 이관.
