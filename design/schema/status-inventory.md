# 상태 코드 정의 추적 (#213)

상태 코드의 값·소유는 [코드 사전](code-dictionary.md)과 계약의 `x-code-key`가 정본이다.
`enum`이 없는 자리는 미정과 같지 않다. `registry-system`은 시스템이 정한 값과
표시명을 공통코드로 조회하고, `registry`는 고객이 확장 가능한 코드다.

## 재측정

```sh
python3 design/schema/generators/openapi/check-status-inventory.py
python3 design/schema/generators/openapi/check-status-inventory.py --json
python3 design/schema/generators/openapi/test-check-status-inventory.py
```

집계 대상은 계약 JSON의 `statusCode` 및 `*StatusCode` 속성과 파라미터 정의 위치다.
컴포넌트뿐 아니라 인라인 응답, 배열의 하위 속성, 조합 하위 속성도 포함한다.
같은 정의를 참조하는 횟수는 펼쳐 세지 않으며, 예시 데이터와 내부 주석은 제외한다.
전체 위치·사전 소유·값·제외 사유는 `--json` 출력으로 확인한다. 위치는 JSON Pointer다.
현재 건수를 손으로 복사해 고정하지 않는다.

검사기는 설명 누락, 사전 키/제외 사유 누락, 잘못된 사전 키와 참조를 막는다.
파라미터 설명과 키는 이 저장소 규약대로 파라미터 객체에 둔다(schema 안이 아니다).
상태 속성 자체를 감싼 `allOf`의 설명·분류는 읽되 분류 충돌은 실패한다.
상태 자체의 `oneOf`/`anyOf`는 자동 합치지 않고 수동 검토 필요로 실패한다.
사전의 값·소유·포인터 정합은 기존 `check-code-dictionary.py`가 함께 검사한다.
둘 모두 `runall.py`에 등록되어 있다. 설명의 업무적 정확성은 사람이 검토해야 한다.

## 별도 그룹 없음과 업무 보류를 구분한다

`x-no-code-key`는 별도 코드 그룹을 만들지 않는 **이유**이지, 모든 업무가 끝났다는
표시가 아니다. 예를 들어 피킹 라인 진행은 수량과 보류 여부로 표현한다.
시리얼은 #516의 통보 반영으로 신규 생성 초기값 `REGISTERED`(등록됨)를 명시했지만,
이것이 품질/생애 상태 기계나 추가 전이를 확정한 것은 아니다. 과거 값도 보존한다.
새 상태값을 임의로 채우거나 필드를 삭제해 이 차이를 감추지 않는다.

2026-09-10 통보 반영도 같은 기준으로 읽는다. #521의 실사는 신규 `IN_PROGRESS`(진행중)와
과거 `PLANNED`(계획됨)의 조회·첫 입력 동작을 구분했다. #518의 보전 지시 마감은 현재
`closed=true`를 422로 거부하는 경계를 명시한 것이며 정상 마감 상태 기계를 완성한 것이 아니다.
이 설명 추가를 상태 정의 위치 수 감소로 집계하지 않는다. 코드 문자열, 정의 위치 수,
실제 업무 완료 여부는 서로 다른 축이다.

물류 전표·실사·결재의 값 목록은 이미 정해져 있으므로 이를 기다리던 화면의 기록을
정정한다. 다만 제품 폐기 요청의 승인 게이팅 반영은 값 목록 확정과 다른 과제다.
기존 버튼 동작은 이번 정정으로 바꾸지 않는다. 화면 원본의 미결을 보존하고
`collect-open-items.py`로 대장을 재생성한다. #213은 잔여 업무를 확인한 뒤 종료한다.
