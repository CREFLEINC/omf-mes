# team-issue-protocol — 저장소 간 이슈 협업 공통 규약

`multi-agent-team-workflow-v2.md`(저장소 루트)가 정의하는 라벨·서식 규칙을 실측과 대조해
정리한다. 라벨 어휘가 세 저장소·세 스킬에 따로 복사되면 갈리기 때문에, **이 파일 하나만 정본으로
둔다.** 다른 스킬은 이 파일을 참조만 하고 규칙을 복제하지 않는다.

## 1. 저장소 3종 — 공개 경계와 이슈 실태

| 저장소 | 가시성 | 우리와의 관계 | 이슈 실태(2026-08-25 실측) |
| --- | --- | --- | --- |
| `CREFLEINC/omf-mes` | **PRIVATE** | 이 저장소 자신(설계팀) | 108건·OPEN 40 |
| `CREFLEINC/omf-mes-client` | **PUBLIC** | 아웃바운드 대상(프론트) | 153건·착수통지 107·변경통지 11 |
| `CREFLEINC/omf-mes-server` | PRIVATE | 데이터 모델링 소관(백엔드) | **이슈 0건·라벨 0개 — 협업 미가동** |

⚠ `omf-mes-server`가 미가동이라, `data-model-boundary.md`가 요구하는 "데이터 모델 담당에게
통지"할 채널이 지금 없다. 백엔드 건은 당분간 `omf-mes` 자기 저장소의 `[uiux→데이터모델]`·
`[docs→데이터모델]` 이슈로 남긴다(재분류하지 않는다 — 유산 채널을 유지).

`omf-mes`가 비공개이므로 **인바운드(검토 요청 회신)에는 공개 저장소 금지어 검사가 불필요**하다.
아웃바운드(`omf-mes-client`, 공개)에만 필요하며 `uiux-client-handoff`의 `check-issue.py`가
담당한다.

⛔ **단, 「인바운드 = 비공개」가 항상 참은 아니다.** 검토 요청이 **우리가 발행한 아웃바운드
이슈의 코멘트로** 올 수 있다 — 2026-08-26 `omf-mes-client#442`(모바일 셸 스캐폴딩)에 개발팀이
「스펙 머리말 갱신 여부는 설계팀 판단이 필요」라고 달아 온 것이 첫 사례다. 그 회신은 **공개로
나가므로 금지어 검사가 필수**이고 §8의 승인 게이트에 걸린다. **가시성은 저장소로 판단하지 말고
매번 확인한다**:
```
gh repo view <저장소> --json isPrivate -q .isPrivate
```

## 2. 라벨 — 인바운드만 남는다

⛔ **2026-09-03 개정 — 아웃바운드 팀 라벨 병기를 폐지했다.** `Agent : T{n}` 을 우리가
`omf-mes-client` 이슈에 «부착»하던 것은 **업무 배정 표시**였고, 배정은 더 이상 설계팀이 하는
일이 아니다. 아래 인바운드 표의 `Agent : *` 는 **개발팀이 스스로 붙여 온 「누가 물었나」의
표기**라 성격이 다르다 — 그것은 읽되 우리가 새로 붙이지 않는다.

### `omf-mes`(인바운드) — v2 그대로

| 라벨 | 뜻 | 실측 현황 |
| --- | --- | --- |
| `Agent : T{n}` | **요청한** 개발팀 번호(배정이 아니라 발신자 표기) | `T4`만 존재(설명 비어 있음). 다른 팀 이슈가 실제로 들어올 때 그때 만든다 — 안 쓰는 라벨을 미리 만들면 어휘만 는다 |
| `Agent : {type}` | 개발팀 유형(`Client`·`Backend` 등) | `Client`만 존재 |
| **처리 중** | 설계팀이 처리 중 | ⛔ **`in progress`를 새로 만들지 않는다 — `status:in-progress`가 이미 실재하고 사용 중이다**(2026-08-25 #232 처리 중 재확인 — 사용 2건). 뜻이 같은 라벨을 두 개 두면 §1의 존재 이유(라벨 어휘 분열 방지)에 스스로 걸린다. **`status:in-progress`를 쓴다** |
| `help wanted` | 설계팀이 처리를 미루고 지원 대기 | GitHub 기본 라벨로 이미 존재(사용 0건) |

**신설 필요**(`gh label create --repo CREFLEINC/omf-mes`): `Agent : T1`·`Agent : T2`·`Agent : T3`는
**그 팀 이슈가 실제로 들어올 때만** 만든다. `Agent : T4`의 빈 description은 채운다.
⛔ `in progress`는 만들지 않는다(위 표 참조).

### `omf-mes-client`(아웃바운드) — **변경 요약 통지는 `uiux→client` 하나만**

⛔ **`ready` 를 붙이지 않는다 — 2026-09-03 폐지.** 그 라벨은 「착수해도 된다」는 뜻이고,
착수 가능 통지가 폐지되면서 우리가 그 말을 할 자리가 없어졌다. 남는 아웃바운드는 **변경 요약
통지**뿐이고 라벨은 `uiux→client` 하나다(`check-issue.py` 의 `CHANGE_NOTICE_LABELS`).

⛔ **`Agent : T{n}` 병기도 폐지.** 배정 라벨을 우리가 붙이지 않는다(`--team` 옵션은 유산으로
남아 있을 뿐 쓰지 않는다).

⚠ **이미 붙어 있는 라벨은 떼지 않는다.** 기존 `uiux→client`+`ready` 가 **123/106건** 쌓여
있고, 소급해서 떼면 프론트의 기존 필터가 깨진다. **앞으로 붙이지 않을 뿐이다.**

## 3. 제목 접두 — 신/구 혼재를 그대로 인정한다

| 접두 | 방향 | 상태(2026-08-25 실측 108건 중) |
| --- | --- | --- |
| `[검토 요청]` | 개발팀 → 설계팀(신규, v2) | 1건(#232) |
| `[client→uiux]` | 개발팀 → 설계팀(구식) | 35건 — **`[검토 요청]`과 동격으로 취급한다**(아래 4장) |
| `[uiux→docs]`·`[docs→uiux]` | 설계팀 내부 구식 채널 | 각 4건·1건 OPEN 잔존 — 처리 대상 아님 |
| `[uiux→데이터모델]`·`[docs→데이터모델]` | 설계팀 → 백엔드(자기 저장소 임시 보관) | 3건·23건 |
| `[uiux→client]` | 설계팀 → 개발팀(아웃바운드). ⛔ 2026-09-03 이후로는 **변경 요약 통지 전용** — 착수 가능 통지는 폐지 | 착수 107(유산)·변경 11 |

⚠ **구식 접두를 새 접두로 일괄 개명하지 않는다.** 이미 링크·인용된 이슈 제목을 바꾸면 그 자체가
공개 저장소 상호 참조를 깨뜨릴 수 있다. 신규 이슈부터 `[검토 요청]`을 쓰고, 구식은 유산으로 둔다.

## 4. 인바운드 수집 — 2축 합집합, 좁게도 넓게도 걸지 않는다

라벨(`Agent : *`)만으로 거르면 라벨 없는 `[client→uiux]` 요청(실측 5건, #225·#227·#228·#229·
#230 — `question`·`priority:high`만 있고 Agent 라벨 없음)을 놓친다. 제목 접두만으로 걸러도
같은 문제다. **둘의 합집합**으로 수집한다:

```
라벨 Agent:* 매치  ∪  제목 접두 [검토 요청]|[client→uiux]|[backend→uiux] 매치
```

이 합집합 **밖에 있는 OPEN 이슈**는 처리 대상으로 삼지 말고 "채널 밖 후보"로만 보고한다.

⛔ **설계팀 자신이 발신한 이슈**(`[uiux→`·`[docs→` 접두)는 위 필터를 통과해도 하드 제외한다.
검토 요청 처리 절차로 잘못 들어가면 미결 추적 표지가 깨진다.

## 5. 적합성 8유형 (검토 요청 물음 단위 판정)

`design-review-analyst`가 Phase 2에서 이슈의 **물음(문장) 하나하나**에 적용한다. 이슈 전체를
한 번에 승인/기각하지 않는다 — 한 이슈에 여러 유형이 섞여 있을 수 있다.

| 유형 | 근거 | 처리 |
| --- | --- | --- |
| A. 데이터 모델(테이블·인덱스·타입·제약) | `design/schema/data-model-boundary.md` | 타입·길이만 통지, 필드 존재·필수성은 설계가 답함 |
| B. 코드 수준 결정(상태관리·캐싱·구현순서) | v2 §2-4-4 | "개발팀이 정합니다" + 설계가 거는 제약만 명시 |
| C. 이미 확정돼 있음 | — | 경로+절 인용 + "왜 안 보였나" 판정. 문서가 애매했다면 그 자리도 함께 고침 |
| D. 팀 간 직접 소통 요청 | v2 역할경계-4 | 설계팀이 중계, 직접 연결하지 않음 |
| E. 업무 배정 요청 | 2026-09-03 개정 | ⛔ **설계팀 소관이 아니다** — 배정은 개발팀이 스스로 정한다. 「우리는 정하지 않습니다」로 회신하고 그 물음은 여기서 끝난다(구 규칙의 「사람에게 넘긴다」도 폐지 — 넘길 자리가 없다) |
| F. 서식 불비(라벨 없음·화면 미지목·실측 없음) | v2 §2-3 | 반려 아닌 보완 요청, 이슈 유지 |
| G. 고객·팀 리더 확정 필요 | `uiux-design` §1-3 | "우리도 못 정합니다" + 임시조치 지시, 이슈 유지 |
| H. 채널 오인(설계팀 발신 이슈에 달린 답글) | — | 4장에서 이미 제외됨 |

## 6. 상태 라벨 전이

```
접수  →  status:in-progress  →  (완료: 코멘트+통지 후 닫음)
                             ↘  help wanted  (지원 대기, 닫지 않음)
```

**닫을 수 없는 검토 요청**(예: 데이터 모델링·백엔드 구현이 걸려 있고 `omf-mes-server`가 미가동)은
`status:in-progress`를 `help wanted`로 교체하고 사유 코멘트를 남긴다 — **닫지 않는다.** v2가
개발팀 쪽에서 쓰는 것과 대칭이라 학습 비용이 없다.

⚠ 단, "우리 답이 백엔드 결정을 기다려야 완성되는가"만 기준으로 삼는다. 소관을 백엔드로
**이관**했을 뿐 우리 회신 자체는 끝났다면(필드가 계약에 착지했고 조인 경로만 남았다면)
`help wanted`를 붙이지 않고 닫는다 — 안 그러면 개발팀이 "설계팀도 모른다"로 읽는다(#232
실사용에서 확인).

## 7. 회신 코멘트 — 머리 표기와 서식

### ⛔ 게시 수단 — 언제나 «코멘트»다

```
gh issue comment <요청 이슈 번호> --repo <요청이 온 저장소> --body-file <초안>
```

**회신으로 새 이슈를 만들지 않는다.** 새 이슈는 개발팀에게 ⚠ 이상의 변경 통지를 뜻하고,
받는 쪽이 **재작업 지시로 오해한다.** `gh issue create`는 `uiux-client-handoff`의
**변경 요약 통지 전용**이다 — 방향이 반대다(그쪽은 아웃바운드 신규 발행, 이쪽은 인바운드 응답).

검사: `check-issue.py <초안> --reply` — 회신 규약(머리 표기·자리표시자)과 공개 안전을 본다.
회신이 **비공개 저장소**로 갈 때는 `--reply --private`로 공개 안전 스캔만 끈다(머리 표기는
계속 본다). 가시성은 `gh repo view <저장소> --json isPrivate -q .isPrivate`로 확인한다.

### 머리 표기: `개발팀에 전달사항`으로 재확정 (2026-08-27) — `##`은 저자 재량

v2 문서가 한때 본문(line 62 "개발팀에 전달사항")과 예시(line 66 "개발팀 전달사항")에서 갈렸다.
2026-08-26에는 실측 14건(`개발팀 전달사항` 11건·`개발팀에 전달 사항` 3건·무헤더 2건) 기준으로
관행 다수인 `## 개발팀 전달사항`(조사 없음)을 정본으로 세웠으나, **2026-08-27 사용자가 v2 line 62
원문 그대로 "개발팀에 전달사항"(조사 있음)으로 재확정했고, v2 문서 line 66 예시도 같은 표기로
정정해 본문·예시 불일치 자체를 없앴다** — 관행보다 문서 원문을 우선한다.
⭐ **`##`은 강제하지 않는다** — 붙여도 되고 안 붙여도 된다(GitHub 렌더링상 가독성 판단은 작성자
재량). ⭐ **완전 일치가 아니라 접두다** — `— <한 줄 결론>`을 뒤에 붙여도 된다(선택). 검사기
(`check-issue.py`)도 `(##\s+)?개발팀에 전달사항`을 접두로 본다.

⚠ **이전 정본(`## 개발팀 전달사항`, 조사 없음)은 더 이상 유효하지 않다** — 2026-08-26~27 사이에
쓰인 회신(`#206` 등)은 그 표기를 썼으나, 지금 기준으로는 위반이다. 새로 쓰는 회신은 반드시 새
정본을 따른다.

⚠ **정본이 조용히 안 지켜지는 사고가 실제로 났었다** — 2026-08-26 실측: 당시 정본 기준으로도
`#232`는 `##`가 빠졌고 `#222`는 조사 위치가 다른 구 표기(`개발팀에 전달 사항` — "전달"과 "사항"
사이 공백)를 썼다. 사람의 주의에 맡기지 않고 **`check-issue.py --reply`가 첫 줄을 기계로
검사**한다(어긋나면 종료 코드 1로 게시를 막는다).

### 서식 — 이슈 종류·처리 결과에 맞춰 자유롭게 쓴다 (2026-08-27)

⭐ **정해진 골격을 강제하지 않는다.** 개발팀에게 "무엇을·왜·어떻게 처리했는지"가 명확히 전달되면
그것으로 충분하다 — 물음이 하나면 소절을 나눌 필요가 없고, 통지가 불요면 그 표를 아예 뺄 수 있다.
아래는 **과거 회신(#222·#206·#196)에서 공통으로 나온 요소**를 참고용으로 모은 것이지, 매 회신이
전부 채워야 하는 체크리스트가 아니다:

```markdown
개발팀에 전달사항 — <한 줄 결론(선택)>

<N>개 물음에 다 답합니다. 반영 PR #<번호> — 병합 완료 `<sha7>`(origin/main).

> 이 회신이 쓰는 표기: <화면 전체 이름(번호)> · <조항 전체 뜻(번호)> · <업무 약어 전체 이름>
  (표기가 필요 없는 짧은 회신이면 생략)

### 1 — <답을 제목에>
**무엇** <한 줄> / **어떻게** <근거 경로+절, 재현 명령 출력> / **왜** <이유 + 택하지 않은 안>
  (물음이 하나뿐이면 번호·소절 없이 바로 답해도 된다)
```
