# team-issue-protocol — GitHub 이슈 규약 (V3)

`multi-agent-team-workflow-v3.md`(저장소 루트, 2026-09-03 사용자 확정)가 정한 소통 규칙과
`multi-agent-team-workflow-v2.md` 가 정한 라벨 양식(V3 「사전 정보」 — 라벨 종류·형식은 V2 를 그대로
쓴다)을 실측과 대조해 정리한다. 라벨 어휘가 세 저장소·세 스킬에 따로 복사되면 갈리기 때문에
**이 파일 하나만 정본으로 둔다.** 다른 스킬은 이 파일을 참조만 하고 규칙을 복제하지 않는다.

## 0. V3 에서 GitHub 이슈는 두 종류뿐

V3 규칙 2 — 「설계팀과 개발팀의 직접 소통은 설계팀이 개발팀에 이슈를 발행하는 "설계 변동 공지"를
제외하면 원칙적으로 모두 금지한다. 필요한 게 있으면 무엇이든 자료를 만들어 사용자에게 전달
요청을하고 자신의 깃헙 저장소에 이슈를 발행하고 요청에 대한 회신을 대기 한다.」(원문 그대로)

| 종류 | 어디에 | 누가 만들고 닫나 | 접두 | 라벨 | 만드는 스킬 |
| --- | --- | --- | --- | --- | --- |
| **설계 변동 공지** (규칙 2·5) | 개발팀 저장소 2곳 — `omf-mes-client` · `omf-mes-server` 에 **같은 본문 1건씩** | 설계팀이 만든다. **닫지 않는다**(시점 기록) | `[설계 변동 공지] <YYYY-MM-DD> · <해시7>` | `설계 변동 공지` (+ 클라이언트 저장소는 `uiux→client` 도) | `design-change-notice` |
| **설계팀 자기 이슈** (규칙 4 — 「하는 일·처리할 일」 공개, 규칙 2(2) 회신 대기) | `omf-mes` | 설계팀이 만들고 설계팀이 닫는다 | `[요청 처리]` · `[설계]` · `[확인 요청]` | `Agent : Architect` + `status:in-progress` / `help wanted` | `design-request-intake`(요청 처리) · 자체 과제는 직접 |

그 외의 이슈·코멘트는 **어느 저장소에도 만들지 않는다.** 개발팀의 요청은 이슈로 오지 않는다 —
**사용자가 자료로 건네고**, 우리 답도 **답변서 파일로 사용자가 전한다**(§4·§7).

## 1. 저장소 3종 — 역할과 공개 경계 (2026-09-03 실측)

| 저장소 | 가시성 | V3 역할 | 실태 |
| --- | --- | --- | --- |
| `CREFLEINC/omf-mes` | **PRIVATE** | 이 저장소 자신 — 설계팀 **자기 이슈**·PR | 이슈 192건·OPEN 39 · 라벨 19종 |
| `CREFLEINC/omf-mes-client` | **PUBLIC** | **공지 발행처** ① — 공개 안전 스캔 필수 | 이슈 246건·OPEN 89 · `uiux→client` 부착 170건(유산 통지) |
| `CREFLEINC/omf-mes-server` | **PRIVATE** | **공지 발행처** ② | 이슈 21건·OPEN 18 — 접두 있는 17건은 전부 V3 이전에 설계팀이 낸 `[uiux→데이터모델]`·`[docs→데이터모델]`·`[uiux→server]` 유산 · 라벨은 GitHub 기본 9종 + `Agent : Backend`·`status:in-progress` 11종 — **`설계 변동 공지` 라벨은 첫 발행 때 만든다**(§8 승인) |

가시성 실측 명령(문서를 믿지 말고 발행 직전에 다시 본다 — 공개로 바뀌면 되돌릴 수 없다):
```
gh repo view CREFLEINC/omf-mes-server --json visibility,isPrivate
```

**공개 안전 스캔** — 공지는 **한 본문**을 두 저장소에 내므로 `omf-mes-client` 가 공개인 이상 그 본문은
언제나 `check-notice.py`(`design-change-notice/scripts/`)의 스캔을 통과해야 한다. 스캔은 본문
한 번이면 두 저장소를 다 덮는다 — `omf-mes-server` 가 뒤에 공개로 바뀌어도 규칙은 달라지지
않는다. 경계 자체는 `design-change-notice/references/public-boundary.md`.

**사용자에게 물을 것** — 우리가 정할 수 없는 것(고객·팀 리더 확정 필요, 요청 자료가 모호함,
데이터 모델 소관 질의)은 개발팀 저장소에 이슈를 세우는 것이 아니라 **`omf-mes` 에 `[확인 요청]`
자기 이슈를 세우고 `help wanted` 로 대기**한다(규칙 2(2)). V3 이전에 `omf-mes`·`omf-mes-server`
에 세우던 `[uiux→데이터모델]`·`[docs→데이터모델]` 임시 보관 채널은 **접는다** — 남은 열린 건은
유산이다(§3).

유산 한 줄 — 2026-08-26 「인바운드=비공개」 가정 정정(`omf-mes-client#442`, 공개 저장소 코멘트로
검토 요청이 와서 회신이 공개로 나간 사례)은 V3 로 **인바운드 자체가 없어져** 절로 남기지 않는다.
남는 교훈은 하나 — **가시성은 저장소 이름으로 판단하지 말고 매번 실측한다.**

## 2. 라벨 — V2 양식, 실측(2026-09-03)과 대조

V2 라벨 양식: 팀 유형 `Agent : {type}` · 팀 번호 `Agent : T{number}` · 진행 `in progress` · 중단
`help wanted`. V3 규칙 4 — 「처리하려는 이슈에 팀 라벨을 부착하고 실제로 하고 있는 일은 시작할 때
진행 중 라벨을 붙여야 한다」 — 를 설계팀 자신에게도 적용한다(2026-09-03 사용자 판정 Q5).

### `omf-mes` — 자기 이슈용

| 라벨 | 뜻 | 실측 |
| --- | --- | --- |
| `Agent : Architect` | 설계팀 팀 유형 라벨(V2 `Agent : {type}` 양식) — 자기 이슈 전건에 붙인다 | ⭐ **신설 예정 — 아직 없다.** 처음 쓰는 회차에 §8 승인 뒤 `gh label create "Agent : Architect" --repo CREFLEINC/omf-mes --description "설계팀 자기 이슈(V3 규칙 4)"` |
| `status:in-progress` | 진행 중 | 있음(설명 「진행 중」, 부착 8건). ⛔ **V2 의 `in progress` 는 이 저장소에 없고 새로 만들지 않는다**(2026-08-25 확정) — 뜻이 같은 라벨을 둘 두면 이 파일의 존재 이유(어휘 분열 방지)에 스스로 걸린다 |
| `help wanted` | **사용자 회신 대기** — `[확인 요청]` 이슈, 또는 요청 처리가 사용자 확인 없이는 끝나지 않을 때 | GitHub 기본 라벨(부착 2건) |

| 라벨 | 어디 | 뜻 | 실측 |
| --- | --- | --- | --- |
| `설계 변동 공지` | `omf-mes-client` · `omf-mes-server` 공통 | 공지 이슈 식별 | **둘 다 없음 — 첫 발행 때 만든다**(§8 승인). `gh label create "설계 변동 공지" --repo <저장소> --description "설계팀 → 개발팀 설계 변동 공지(V3 규칙 5)"` |

| 접두 | 당시 방향 | 실측(2026-09-03) | 처리 |
| --- | --- | --- | --- |
| `[검토 요청]` | 개발팀 → 설계팀(직접 인바운드) | `omf-mes` 57건 · **OPEN 23** | **사용자가 정리한다.** 이 번호로 「처리해 달라」고 해도 `design-request-intake` 는 받지 않는다 — 요청은 자료로 온다(§4) |
| `[client→uiux]` · `[backend→uiux]` | 개발팀 → 설계팀(구식) | 41건(OPEN 2) · 0건 | 위와 같다 |
| `[uiux→client]` | 설계팀 → 클라이언트(착수 통지·변경 요약 통지) | `omf-mes-client` 176건(OPEN 57) | 개발팀이 필터로 쓰던 **라벨** `uiux→client` 는 공지에 계속 붙인다(§2). **접두**는 쓰지 않는다 |

⚠ **구식 접두를 새 접두로 일괄 개명하지 않는다.** 이미 링크·인용된 이슈 제목을 바꾸면 그 자체가
저장소 간 상호 참조를 깨뜨린다. 유산은 유산으로 둔다.

## 4. 요청은 사용자가 자료로 건넨다 — 자기 이슈 본문

개발팀 요청은 **이슈로 오지 않는다.** 사용자가 파일 경로 또는 붙여넣기로 자료를 건네면
`design-request-intake` 가 `tmp/requests/<YYYY-MM-DD>-<식별자>/요청.md` 로 받는다(`tmp/` 는
gitignore). 이슈 목록을 훑어 요청을 «찾는» 절차는 **없다** — V3 규칙 2 가 그 경로를 닫았다.

**자기 이슈 본문 — 최소 항목**(손으로 쓴다, 짧게):

| 접두 | 반드시 적는 것 |
| --- | --- |
| `[요청 처리]` | 접수 날짜 · 요청 식별자(`tmp/requests/` 폴더 이름과 같다) · 요청 종류(정보 요청 / 설계 개선 — 규칙 2(1)) |
| `[설계]` | 과제 한 줄 · 착수 날짜 · 닿는 갈래(화면설계서·계약·요구서 등) |
| `[확인 요청]` | 물음 · 선택지 · 우리 기본안 · 답이 없으면 어떻게 진행할지 |

⛔ 자기 이슈 본문에 요청 자료 원문을 붙여 넣지 않는다 — 개발팀 자료는 사용자가 건넨 사본이고
정본은 개발팀 쪽에 있다. 식별자로 가리킨다.

**공지 본문은 손으로 쓰지 않는다** — `design-change-notice/scripts/build-notice.py` 가 git 이력에서
4항(① 공지 발행 날짜 ② 배포 버전 — 전체 해시+7자 ③ 설계 자료 목록 표 — 갈래 6줄·경로·최종 변경
해시 ④ 이전 버전과 달라진 지점 — **지점만**)을 만들고 `check-notice.py` 가 검사한다. 규칙 5 —
「이 공지에는 자세한 내용이 적히는 것을 금지한다 … 무슨 내용이 어떻게 변경되었는지
작성하지마라 … 백엔드, 클라이언트 개발팀을 구분해서 공지를 작성하지마라」.

## 5. 적합성 8유형 — 요청 자료의 물음 단위 판정

`design-review-analyst` 가 `design-request-intake` Phase 3 에서 요청 자료의 **물음(문장) 하나하나**에
적용한다. 자료 전체를 한 번에 승인/기각하지 않는다 — 한 자료에 여러 유형이 섞여 있을 수 있다.

| 유형 | 근거 | 처리 |
| --- | --- | --- |
| A. 데이터 모델(테이블·인덱스·타입·제약) | `design/schema/data-model-boundary.md` | 타입·길이는 답하지 않는다. 필드 존재·필수성은 설계가 답한다 |
| B. 코드 수준 결정(상태관리·캐싱·구현순서) | V3 규칙 3 상호 불가침 | 「개발팀이 정합니다」 + 설계가 거는 제약만 명시 |
| C. 이미 확정돼 있음 | — | 경로+절 인용 + 「왜 안 보였나」 판정. 문서가 애매했다면 그 자리도 함께 고친다 |
| D. 팀 간 직접 소통 요청 | V3 규칙 2 | 직접 연결하지 않는다. 답변서로 사실만 답하고, 다른 팀 몫이면 「그 팀에 물을 것」이라고 적는다 — 전달은 사용자가 한다 |
| E. 업무 배정 요청 | V3 규칙 3 · 2026-09-03 개정 | ⛔ **설계팀 소관이 아니다** — 「우리는 정하지 않습니다」로 답하고 그 물음은 여기서 끝난다 |
| F. 자료 불비(화면 미지목·실측 없음·물음이 문장으로 안 됨) | V3 규칙 2(2) | 반려가 아니라 보완 요청 — 답변서에 「무엇이 더 있어야 답할 수 있는지」를 적는다. 자기 이슈는 `help wanted` 로 열어 둔다 |
| G. 고객·팀 리더 확정 필요 | `uiux-design` §1-3 | 「우리도 못 정합니다」 + 임시조치 명시. **`[확인 요청]` 자기 이슈**로 사용자에게 묻는다 |
| H. 채널 오인 — V3 이전 이슈 번호(`[검토 요청]` 등)로 부르거나, 개발팀 저장소 이슈의 답글을 요청으로 읽으라는 경우 | §3 유산표 | 받지 않는다 — 「요청은 자료로 건네 달라」고 사용자에게 되묻는다 |

## 6. 상태 전이 — 자기 이슈만

```
만든다(Agent : Architect + status:in-progress)
   →  사용자 확인 대기 : status:in-progress → help wanted   ([확인 요청] 이거나 F·G 유형이 남았을 때)
   →  닫는다 : 답변서/결과 «전문»을 닫는 코멘트로 남기고 닫는다
```

- **닫는 조건** — `[요청 처리]` 는 `design-request-intake` 의 3중 잠금(PR 병합이 `origin/main` 조상 ·
  계약 diff 등급 판정 · 답변서에 병합 해시·근거 경로 실재)을 통과했을 때. `[설계]` 는 PR 병합.
  `[확인 요청]` 은 사용자 답을 받아 본문에 결론을 적었을 때.
- **`help wanted` 기준은 「우리 답이 사용자 확인 없이는 완성되지 않는가」 하나**다. 소관을 다른 팀으로
  이관했을 뿐 우리 답은 끝났다면 붙이지 않고 닫는다 — 안 그러면 「설계팀도 모른다」로 읽힌다
  (2026-08-25 `#232` 실사용에서 확인된 교훈, V3 에서도 유효).
- ⛔ **개발팀 저장소 이슈의 상태(라벨·닫기·코멘트)는 우리가 바꾸지 않는다.** 공지 이슈도 낸 뒤
  손대지 않는다 — 시점 기록이다.

## 7. 답변서 서식 · 공지 게시 수단

### 7-1. 답변서 — 사용자가 개발팀에 전한다

자리: `tmp/requests/<YYYY-MM-DD>-<식별자>/답변서.md`(gitignore). 정본은 **자기 이슈를 닫는 코멘트의
전문**과 반영 PR 이다 — 파일은 사본이다.

```markdown
# 개발팀에 전달사항 — <요청 식별자>

| 항목 | 값 |
| --- | --- |
| 요청 | <자료 제목> · 접수 <YYYY-MM-DD> |
| 판정 | 반영 / 부분 반영 / 반영하지 않음 / 정보 회신 |
| 반영 PR | CREFLEINC/omf-mes#<n> (없으면 「—」) |
| 병합 | <해시7> (origin/main 조상) |
| 근거 | design/wiki/... §... (게시 전 test -f 로 실재 확인) |

## 답변
<물음마다 사실과 판정. 처리 방법을 지시하지 않는다. DB 컬럼·제약을 근거로 인용하지 않는다>

## 다음 공지
다음 설계 변동 공지에 실린다 / 설계 변경 없음
```

- 머리 표기 `개발팀에 전달사항` 은 **V2 line 62(「코멘트는 반드시 "개발팀에 전달사항" 제목으로
  시작하여야 한다」)를 계승**한 것이다 — 2026-08-27 사용자 재확정(조사 있음 · `##` 은 저자 재량 ·
  `— <한 줄 결론>` 을 뒤에 붙여도 된다).
- 「반영/부분 반영/반영하지 않음/정보 회신」 네 값 밖의 판정을 만들지 않는다 — 받는 쪽이 표 한
  줄로 결과를 읽어야 한다.
- ⚠ **근거 경로는 게시 전 반드시 `test -f` 로 실재를 확인한다.** 2026-08-25 구조 삭제로 `uiux/`·
  `deliverables/` 경로가 대량으로 죽었고 과거 회신(`#222`)이 죽은 경로 3줄을 근거로 남겼다.
- ⚠ 표로 쓴 내용은 `check-report-language.py` 가 검사하지 않는다(`|` 로 시작하는 줄은 건너뜀).
  화면 번호·조항 번호·업무 약어는 표 밖 본문에서 한 번 전개한다.

**자기 이슈 닫기** — 답변서 전문을 닫는 코멘트로 남긴다. 별도 코멘트 명령 없이 `close --comment`
한 번으로 — 코멘트와 닫기가 갈라지면 「답은 달렸는데 열려 있는」 이슈가 남는다:
```
gh issue close <n> --repo CREFLEINC/omf-mes --comment "$(cat tmp/requests/<YYYY-MM-DD>-<식별자>/답변서.md)"
```

### 7-2. 공지 게시 수단 — `design-change-notice` 가 실행한다

순서: `build-notice.py` → `check-notice.py` → 사람 승인(§8) → `gh issue create` ×2 → `git tag` push.

```
# 라벨이 없으면 첫 발행 때(승인 뒤) — 두 저장소 각각
gh label create "설계 변동 공지" --repo CREFLEINC/omf-mes-client --description "설계팀 → 개발팀 설계 변동 공지(V3 규칙 5)"
gh label create "설계 변동 공지" --repo CREFLEINC/omf-mes-server --description "설계팀 → 개발팀 설계 변동 공지(V3 규칙 5)"

# 같은 본문 1건씩
gh issue create --repo CREFLEINC/omf-mes-client --title "[설계 변동 공지] 2026-09-03 · <해시7>" --label "설계 변동 공지" --label "uiux→client" --body-file tmp/notices/2026-09-03-<해시7>.md
gh issue create --repo CREFLEINC/omf-mes-server --title "[설계 변동 공지] 2026-09-03 · <해시7>" --label "설계 변동 공지" --body-file tmp/notices/2026-09-03-<해시7>.md

# 공지한 해시에 태그 — 다음 공지의 「직전 버전」이 된다(같은 날 둘째부터 -2)
git tag notice/20260903 <전체 해시> && git push origin notice/20260903
```

발행 뒤 `omf-mes` 자기 이슈(있으면)에 「공지 발행 `omf-mes-client#n` · `omf-mes-server#m`」 한 줄을
남긴다.

### 7-3. ⛔ 하지 않는 것

- ⛔ `gh issue create` 로 개발팀 저장소에 **공지 «외» 이슈를 만들지 않는다** — 확인 요청·질의·
  통지·「참고하세요」 전부. 그 자리는 `[확인 요청]` 자기 이슈 + 사용자 전달이다.
- ⛔ `gh issue comment` 로 개발팀 저장소 이슈에 쓰지 않는다 — 회신도, 「반영했습니다」도, 공지
  이슈에 대한 부연도. 회신은 답변서 파일로 사용자가 전한다.
- ⛔ `gh issue list` 로 개발팀 저장소나 `omf-mes` 의 옛 `[검토 요청]` 을 훑어 「처리할 요청」을
  찾지 않는다 — 요청은 사용자가 건넨 자료뿐이다.
- ⛔ 개발팀 저장소 이슈의 라벨을 붙이거나 떼거나 닫지 않는다(규칙 3).

## 8. 되돌리기 어려운 행위와 승인 지점

| 행위 | 가역성 | 승인 |
| --- | --- | :-: |
| 공지 발행 — `omf-mes-client`(**공개**)·`omf-mes-server` `gh issue create` | ⛔ 불가 — 인덱싱·포크는 회수 안 됨 | **필수** — 초안 전문을 보이고 받는다 |
| 라벨 생성 — `설계 변동 공지`(개발팀 저장소 2곳) · `Agent : Architect`(`omf-mes`) | 준-불가역(지우면 부착 이력이 함께 사라진다) | **필수** — 처음 쓰는 회차에 한 번 |
| git tag `notice/*` push | 준-불가역(지우면 「직전 공지」 기준점이 사라진다) | **필수** — 공지 발행 승인에 흡수 |
| PR 병합(`origin/main`) | 준-불가역 | **필수** |
| 자기 이슈 닫기 + 답변서 코멘트 | 준-불가역(코멘트 삭제 불가) | 답변서 승인에 흡수 |
| 자기 이슈 만들기·`status:in-progress`/`help wanted` 전이 | 가역 | 불필요 |
| 계약 JSON·화면 스펙 수정(병합 전) | 완전 가역(git) | 불필요 — PR 이 게이트 |
| main 직접 push | 준-불가역 | 금지, PR 필수 |

⛔ **2026-09-03 사용자 지시 — 「지금 개발팀/설계팀의 이슈를 건드리지는 마」.** 이 규약이 정한
`Agent : Architect` 라벨·자기 이슈·공지 라벨은 **문면만** 세워 둔 것이다. 실제 라벨 생성과 첫
발행은 처음 쓰는 회차에 위 승인 뒤 한다.
