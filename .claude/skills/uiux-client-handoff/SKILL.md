# 변경 요약 통지 — 설계에서 프론트로

설계 사항이 바뀐 사실을 **프론트 개발팀에 알리는** 절차다. 알리는 곳은 **공개 저장소**이고,
이슈는 **고치지 않는 시점 기록**이다.

## ⛔ 2026-09-03 개정 — 무엇이 바뀌었나

**「착수 가능 통지」를 폐지했다.** 설계팀은 개발팀의 업무 배정·진행에 관여하지 않고, 그 정보를
보유하지도 않는다. 이 스킬에 남는 아웃바운드는 **변경 요약 통지 하나뿐**이다.

⭐ **그래서 통지의 «성격»이 바뀌었다.** 착수 통지가 있던 때 변경 통지는 「**설계가 이미 전달된
뒤** 바뀐 것」이었다 — 착수 이슈가 「전달된 시점」을 못박아 주었기 때문이다. 착수 통지가 없으면
그 시점이 사라진다. 개정된 방식에서 개발팀은 설계 자료(`omf-mes`)를 **직접 열람**하므로,
전달 시점이라는 기준선 자체가 필요 없다. 변경 통지는 이제 **「전달 이후의 변경」이 아니라
「무엇이 언제 바뀌었나」의 정기 알림**이다 — 기준선은 이전 통지이고, 없으면 이번 통지가 첫 기준선이다.

**그래서 통지가 담는 것도 줄었다** — 무엇이·언제 바뀌었고 어디를 보면 되는지까지다.
**바뀐 내용 자체와 그것을 코드에서 어떻게 처리할지는 개발팀 몫**이다(아래 §변경 통지 본문 서식).

## 이 스킬이 실제로 하는 일

등급을 매기고 통지문을 쓰는 것 자체는 어렵지 않다. **어려운 것은 무엇이 ⛔ 이고 무엇이 ⚠ 인지,
그리고 무엇을 공개 저장소로 옮기면 안 되는지**다.

```
계약 JSON diff  ─┐
화면 스펙 §5·§8  ├─→  등급표(⛔/⚠/ℹ)  →  통지문 2토막  →  금지어 검사  →  발행
API 요구서 §3    ─┘
```

## ⛔ 폐지 — 「착수 가능 통지」 발행 절차 **[2026-09-03 개정]**

이 자리에 있던 세 가지(발행해도 되는 화면인가 · 스펙 §8 차단 미결이 있는가 · 중복 발행이 아닌가)와
폼 6항목 초안 작성 절차는 **전부 폐지됐다.** 이유 — 착수 통지는 「이 화면 만들어도 된다」는
**업무 개시 지시**이고, 개정된 방식에서 설계팀은 개발팀의 업무 진행에 관여하지 않는다.
**새 착수 이슈를 발행하지 않는다.**

⛔ **폐지 표시가 붙은 산출물** — 지우지 않았다(이미 발행된 이슈 107건이 이것들을 인용하고 있다):
`templates/착수가능-초안.md` · `templates/착수가능-예시-W-06-03.md` · `references/field-sources.md`
(폼 6항목 ↔ 우리 산출물 대응) · `check-issue.py` 의 **기본 모드**(폼 구조·중복·금지 화면·`--team`).

⭐ **살아 있는 것** — `check-issue.py --change-notice`(변경 통지) · `--reply`(회신 규약,
`design-review-intake` 가 쓴다) · `references/public-boundary.md`(공개 저장소 경계는 변경 통지에도
그대로 적용된다).

**현황 조회는 유산으로 남긴다**:

```bash
python3 .claude/skills/uiux-client-handoff/scripts/check-issue.py --status
```

이미 발행된 착수 이슈가 어떻게 되어 가는지 **보이기는 한다.** ⚠ **그러나 그 현황을 우리 판단의
입력으로 삼지 않는다** — 개정된 방식에서 설계팀은 개발팀의 진행 정보를 **보유하지 않으려 한다.**
`--status` 는 「우리가 뭘 보냈던가」를 되짚는 용도이지 진행 관리용이 아니다.

**우리 쪽에 발행 대장을 두지 않는다.** 정본은 상대 저장소이고, 대장을 따로 두면 갱신을 잊는 순간
틀린 답을 준다. **매번 조회하는 편이 싸고 정확하다.**

⚠ **조회에 `--search` 를 쓰지 않는다.** GitHub 검색은 인덱싱 지연이 있고 하이픈이 든
토큰(`W-06-03`)에서 헛돌 수 있다. **전건을 받아 제목을 직접 맞춘다.**

## 절차 — 변경 요약 통지

### ① 통지문을 쓴다

**폼이 없다. 본문을 직접 쓴다.** 서식은 아래 §변경 통지 ⛔/⚠ 의 「본문 서식」 두 토막이다.
등급을 먼저 매기고(등급표 전 행을 채운다) 통지문을 쓴다.

### ② 검사한다 — 발행 **전에**

```bash
python3 .claude/skills/uiux-client-handoff/scripts/check-issue.py <통지문.md> --change-notice --title "…"
```

`--change-notice` 는 **폼 구조 검증을 건너뛰고** 공개 저장소 금지어 검사와 미기입 자리표시 검사를
그대로 돌린다. 통과하면 `gh` 명령을 출력한다.

⛔ **`--change-notice` 를 빼지 않는다** — 빼면 폐지된 폼 6항목 구조로 검사해 「막지 않아도 되는
⛔」가 무더기로 뜬다.

⛔ **`--team` 을 쓰지 않는다 — 2026-09-03 폐지.** `Agent : T{n}` 은 **업무 배정 라벨**이고,
배정은 더 이상 설계팀이 하는 일이 아니다. 통지에 팀 라벨을 붙이지 않는다.

⚠ **순서를 바꾸지 않는다.** `design/schema/00-authoring-rules.md` 가 「본문 작성 → 금지어 검사 → 발행」으로 못박았고, 이 순서를 어겨 DS 저장소에 제품 용어 2건을 흘린 적이 있다(2026-08-04).

### ③ 발행한다

```bash
gh issue create --repo CREFLEINC/omf-mes-client \
  --title "[uiux→client] ⛔ 변경 — W-06-03 · <무엇이 바뀌었나 한 줄>" \
  --body-file <통지문.md> \
  --label "uiux→client"
```

⚠ **`--label` 을 반드시 넘긴다.** CLI 로 `--body-file` 을 쓰면 폼을 거치지 않아 라벨이 붙지 않는다.
라벨이 없으면 프론트의 필터에 걸리지 않는다.
⛔ **`ready` 를 붙이지 않는다** — 착수 이슈 전용 라벨이었고, 변경 통지에 붙이면 「착수해도 된다」로
읽힌다(검사기의 `CHANGE_NOTICE_LABELS` 도 `uiux→client` 하나뿐이다).

### ④ 발행 후

| 하는 것 | 하지 않는 것 |
| --- | --- |
| 설계가 또 바뀌면 **⛔/⚠ 변경 통지를 새 이슈로** 올리고 이전 통지를 링크 | ⛔ **본문 수정** — 아래 유산 예외를 «먼저 읽는다» |
| 프론트 코멘트(어긋남 실측)를 읽고 **설계 문서에 반영** | ⛔ **이슈 닫기** — 닫는 것은 프론트다 |
| | ⛔ **상태 라벨 부착** — 아래 §다른 스킬과의 경계 |
| | ⛔ **처리 방법 지시·진행 독촉** — 2026-09-03 개정. 어떻게 처리할지는 개발팀이 정한다 |

⭐ **통지에는 화면 코드와 «관련 이슈 번호»를 함께 적는다.** GitHub 은 `#78` 같은 «번호»를 보고
상호참조를 걸어 그 이슈 타임라인에 띄운다 — 화면 코드(`P-02-11`)만 적으면 **연결되지 않는다.**
실측(2026-09-01): `#563`·`#603` 은 번호를 적어 `#78` 에서 보이고, `#547` 은 코드만 적어 안 보인다.
⚠ 새 착수 이슈는 더 이상 없으므로, 링크 대상은 **그 화면의 이전 통지**이거나 **남아 있는 유산
착수 이슈**다. 둘 다 없으면 번호 없이 화면 코드만 적는다(이번 통지가 첫 기준선이다).

#### ⚠ 유산 — 착수 이슈 본문 개정 **[2026-09-01 신설 · 2026-09-03 유산 처리]**

⛔ **새 착수 이슈는 발행하지 않으므로 이 예외는 «이미 발행된» 착수 이슈에만 남는다.** 그 이슈들이
다 닫히면 이 절도 사라진다. 새 상황에 이 절차를 확장 적용하지 않는다.

⛔ **원칙은 그대로 금지다.** 착수한 사람의 발밑을 바꾸면 무엇이 달라졌는지 추적할 수 없다.

⭐ **그러나 «아직 시작하지 않은» 화면에서는 비용이 뒤집힌다.** 새로 맡는 사람은 위에서 아래로
읽으므로 **낡은 본문을 먼저 읽고 그대로 만든다.** 통지가 넷씩 붙은 화면에서 본문만 읽고 착수하면
재작업이 난다(실측 2026-09-01 — 미착수 착수 이슈 **28건**이 통지 1~4건을 이고 있다).

**허용 조건 — 넷을 «모두» 만족할 때만**

| | 조건 | 왜 |
| :-: | --- | --- |
| ① | 착수 코멘트가 없다(「착수」·「브랜치」·`feat/`·「PR #」) | 시작한 흔적 |
| ② | `in progress` 라벨이 없다 | 진행 표기 |
| ③ | 그 화면에 **변경 통지가 1건 이상** 붙어 있다 | 없으면 고칠 것이 없다 |
| ④ | 개정 내용이 **이미 통지로 나간 것**이다 | ⛔ 통지 없이 본문만 바꾸지 않는다 |

**절차 — 순서를 바꾸지 않는다**

```
1. 원문 «전문» 을 코멘트로 게시      ← 이것을 먼저 한다
2. 본문을 현재 상태로 개정
3. 개정 사실을 코멘트로 알린다        ← 무엇을 왜 바꿨는지 + 통지 번호
```

⛔ **1 을 건너뛰지 않는다.** GitHub 은 본문 편집 이력을 **UI 드롭다운에만** 남기고
**REST API 로는 주지 않는다**(실측 2026-09-01 — `/issues/{n}/timeline` 을 네 이슈에서 받아
보니 `commented`·`labeled`·`cross-referenced`·`referenced` 뿐이고 **본문 편집 이벤트가 없다**.
편집 이력은 GraphQL `userContentEdits` 에만 있다). 감사는 REST 로 돌기 때문에, 원문을 코멘트로 박제하지 않으면 **「그때 무엇을 보냈나」가
기계에게서 사라진다.** 이번 회차만 해도 그 질문이 판단 근거가 된 자리가 넷이었다
(`#602` 유출 문구 · `#626` 화면 2장 기재 · `#601` §4-3 오분류 · `#589` 3화면).

⚠ **①② 는 «추정»이다.** 라벨을 안 붙이고 시작한 사람은 못 잡는다. 그래서 3 의 알림 코멘트가
**오판의 안전망**이다 — 이미 읽고 있던 사람이 즉시 알아챈다. 3 을 생략하면 이 예외를 쓰지 않는다.

⛔ **3 에 「착수하셨으면 알려 달라 · 되돌리겠다」류를 적지 않는다.** 되돌리겠다는 말은 받는 쪽에서
**「개정본이 틀렸을 수도 있다」**로 읽혀 방금 고친 본문의 신뢰를 스스로 깎는다(2026-09-01 `#78`
적용 중 사용자 지적). 원문이 절차 1 로 «바로 위 코멘트에» 박제돼 있으므로 받는 쪽은 대조해서
스스로 판단할 수 있다 — **원문이 어디 있는지만 가리키면 충분하다.**

**3 이 담을 것** — ① 왜 개정했나(통지가 몇 건 쌓였나) ② 무엇이 어떻게 바뀌었나(전·후 표 + 근거
통지 번호) ③ 원문 위치 ④ 앞으로는 어떻게 하나. ⛔ 사과·유보·되돌림 제안은 넣지 않는다.

**프론트가 「스펙과 계약이 어긋났다」고 코멘트하면 그것이 우리 문서의 결함 신고다.** 그 코멘트를 근거로 스펙·계약을 고치고, 필요하면 `omf-mes` 에 `[uiux→docs]`·`[docs→데이터모델]` 이슈를 낸다.

## 변경 통지 ⛔/⚠ — **이제 유일한 아웃바운드 채널**

설계 사항이 바뀌었을 때 쓴다. **폼이 따로 없으므로 본문을 직접 쓴다.**

⚠ **2026-09-03 개정 — 발행 조건에서 「착수 이슈를 이미 보낸 화면인가」가 빠졌다.** 착수 통지가
없어져 그 전제가 성립하지 않는다. **바뀌었으면 알린다** — 프론트가 그 화면을 시작했는지 여부는
우리가 알지 못하고, 알려고 하지 않는다.

| 등급 | 뜻 | 발행 시점 |
| :-: | --- | --- |
| **⛔** | **이미 만든 것이 틀린다** — 조항 변경·철회, 경로 삭제, 필드 의미 변경 | **즉시 1건** |
| **⚠** | 새로 만들 것이 생긴다. 기존은 안 깨진다 | **차수 마감 때 묶어서 1건**(정기 알림) |
| ℹ | 문서만 바뀜 | **내지 않는다** |

#### ⛔ 「필수 여부」는 «방향»이 아니라 «누가 그 값을 읽는가»로 가른다 **[2026-08-31 신설]**

같은 「필수 해제」라도 요청과 응답에서 뜻이 **정반대**다.

| 어디서 | 무엇 | 등급 | 왜 |
| --- | --- | :-: | --- |
| **요청** 스키마 | `required` 제거 | ⚠ | 보내는 쪽이 덜 보내도 된다 — 안 깨진다 |
| **요청** 스키마 | `required` 추가 | ⛔ | 안 보내던 쪽이 400 을 받는다 |
| **응답** 스키마 | `required` 제거 | ⛔ | **항상 있던 값이 없어질 수 있다** — 널 가드 없는 소비자가 깨진다 |
| **응답** 스키마 | `required` 추가 | ⚠ | 더 보장하는 것이라 안 깨진다 |

⚠ `type` 이 널 허용으로 넓어지는 것(`"string"` → `["string","null"]`)도 **응답에서는 같은 사고**다 — `required` 에 남아 있어도 값이 `null` 로 온다.

⛔ **통지 본문에 「이 값이 `null` 로 올 수 있다」를 반드시 적는다.** 타입이 깨지지 않고 **동작만 틀리는** 자리라 컴파일러도 시험도 잡아 주지 않는다.
⚠ 2026-09-03 개정 — 여기까지가 **사실**이고, 「널 가드를 넣어 달라」는 **처리 지시**라 적지 않는다.
사실을 빠뜨리는 것과 지시를 더하는 것은 다른 문제다 — **사실은 반드시, 지시는 결코.**

**드러난 경위** — 2026-08-31 PR `#307` 리뷰가 잡았다. `GoodsReceipt`(응답)의 원천 문서 두 축이 `required` 에서 빠졌는데 **어느 검사기도 잡지 못했고** 이 등급표에도 항목이 없었다. 커밋 메시지는 「필수 완화라 안 깨진다」로 ⚠ 를 정당화했는데, 그것은 **요청 스키마에만 맞는 말**이었다. 걸리는 화면 넷이 전부 구현 완료 상태였다.

⭐ **검사기를 세웠다** — `design/schema/generators/openapi/check-required-change.py`. 기준 커밋 대비 `required`·널 허용 변경을 양방향으로 보고 요청·응답을 갈라 등급을 낸다.

### 본문 서식 — **두 토막** **[2026-09-03 개정]**

```
## 무엇이 · 언제 바뀌었나   ← 한두 줄 + 변경 일자·병합 sha7. 화면 ID·제품 용어는 써도 된다
## 근거 — 어디를 보면 되나  ← omf-mes 경로·절·이슈 번호만. 내용을 옮기지 않는다
```

⛔ **구 서식의 「## 코드에 무엇을 해야 하나」를 뺐다.** 개정으로 **처리 방법은 개발팀이 정한다** —
개발팀은 설계 자료를 직접 열람해 바뀐 내용을 확인하고 대응을 스스로 결정한다. 우리가 적을 것은
**무엇이 언제 바뀌었고 어디를 보면 되는지**까지다.

⚠ **「무엇이 바뀌었나」에 «언제»를 반드시 넣는다.** 착수 통지가 없어져 「전달된 시점」이라는
기준선이 사라졌다(머리말 §개정 참조). 날짜와 병합 커밋이 그 자리를 대신한다 — 그것이 없으면
받는 쪽은 이 변경이 자기가 본 판본보다 뒤인지 앞인지 가릴 수 없다.

⚠ **`design/schema/00-authoring-rules.md` 는 아직 세 토막으로 규정하고 있다** — 그 문서는
`design/` 담당 소관이라 이 회차에서 고치지 않았다. 갈리면 이 개정(두 토막)이 나중이다.

**관련 이슈가 있으면 링크한다** — `관련: #12`(이전 통지 또는 유산 착수 이슈). 없으면 생략한다.

⚠ 공개 저장소 검사는 **폐지 전 착수 이슈와 똑같이 적용**한다. `check-issue.py` 에 `--change-notice` 를 주면 구조 검증만 건너뛰고 금지어 검사는 그대로 돈다.

## ⚠ 다른 스킬과의 경계 — `team-issue-protocol` · `design-review-intake`

라벨·제목 접두·저장소 경계의 **정본은 `team-issue-protocol`**(공통 지식 베이스)이다. 이 스킬은
그 규칙을 `omf-mes-client`(아웃바운드) 발행에 구체화한 것이고, 규칙 자체를 복제하지 않는다 —
갈리면 `team-issue-protocol`을 따른다.

| | 아웃바운드(이 스킬 — **변경 요약 통지만**) | 인바운드(`design-review-intake`) |
| --- | --- | --- |
| **방향** | `omf-mes` → `omf-mes-client`(공개) | `omf-mes-client`/개발팀 → `omf-mes`(비공개) |
| **제목** | `[uiux→client] ⛔/⚠ 변경 — <화면 ID> · <무엇이>` | `[검토 요청]`·`[client→uiux]` |
| **라벨** | `uiux→client` 하나. ⛔ `ready`·`Agent : T{n}` 을 붙이지 않는다(2026-09-03 폐지) | `Agent : T{n}`·`Agent : {type}`·`status:in-progress`/`help wanted` |
| **추적** | ⛔ 갱신하지 않는다 — 진행 상태는 프론트의 것이고 **우리는 보유하지 않는다** | `status:in-progress`↔`help wanted` 전이 |
| **종료** | ⛔ 우리가 닫지 않는다 — 닫는 것은 프론트다 | 3중 잠금 통과 후 설계팀이 닫는다 |

**"프론트가 스펙과 어긋났다고 이슈를 올렸다"는 이 스킬이 아니라 `design-review-intake` 소관이다**
— 그 방향이 반대다. 이 스킬은 우리가 먼저 프론트로 내보내는 통지만 다룬다.

`omf-mes`(우리 저장소) 안의 이슈 — `[uiux→docs]`·`[docs→데이터모델]` — 는 이 스킬 소관이 아니다.
그쪽은 `design/schema/00-authoring-rules.md`를 따른다.
