# 착수 가능 통지 — 설계에서 프론트로

UI/UX 설계가 끝난 화면을 **프론트 개발팀에 넘기는** 절차다. 넘기는 곳은 **공개 저장소**이고, 이슈는 **고치지 않는 시점 기록**이다.

**규칙 정본**은 우리 것이 아니다 — `CREFLEINC/omf-mes-client` 의 [`docs/uiux-handoff.md`](https://github.com/CREFLEINC/omf-mes-client/blob/main/docs/uiux-handoff.md) 이고, 폼은 `.github/ISSUE_TEMPLATE/uiux-ready.yml` 이다. **이 스킬은 그 규칙을 우리 산출물에 연결하는 방법**을 담는다.

## 이 스킬이 실제로 하는 일

폼 6항목을 채우는 것 자체는 어렵지 않다. **어려운 것은 우리 문서 어디를 봐야 하는지, 그리고 무엇을 옮기면 안 되는지**다.

```
화면 상세 스펙 §1·§4~§9  ─┐
공유계약.md (버전·§I)     ├─→  폼 6항목  →  금지어 검사  →  발행
OpenAPI 계약(*.json)      │
ds-gap.md (실물 확인)     ─┘
```

## ⛔ 시작 전 세 가지 확인

### 1. 이 화면을 발행해도 되는가

| 화면 | 처리 |
| --- | --- |
| `W-06-07` 창고·Location 마스터 · `W-06-01` Routing 등록·관리 | ⛔ **착수 이슈 금지** — 이미 구현·병합됐다. 전할 것이 있으면 **⛔/⚠ 변경 통지**로 |
| `W-06-03` 불량·원인코드 · `W-06-10` 동기화 현황 | ✅ 발행한다(구현 전) — ⚠ **프론트가 이미 착수한 뒤라면 ⛔/⚠ 로 바꾼다** |
| 그 밖의 전 화면 | ✅ **준비되는 대로 하나씩** |

**한 이슈 = 한 화면.** 여러 개가 동시에 준비됐으면 이슈를 여러 개 열되 **5번 칸에 우선순위를 적는다** — 프론트는 한 번에 한 화면씩 처리한다.

### 2. 스펙 §8 에 **차단** 미결이 있는가

**차단이 하나라도 있으면 발행하지 않는다.** 차단은 「화면 골격이 바뀐다」는 뜻이고, 골격이 바뀔 화면을 착수시키면 통째로 다시 만들게 된다.

서식 §7 이 이미 같은 기준을 세워 두었다 — **「§8 에 차단 0건이면 개발 가능」**. 그 문장이 곧 이 이슈의 발행 조건이다.

### 3. 중복 발행이 아닌가 — **검사기가 자동으로 본다**

`check-issue.py` 가 초안에서 화면 ID 를 뽑아 **상대 저장소 이슈 전건을 조회해 대조**한다. 손으로 확인하지 않아도 되지만, **무엇을 막는지는 알고 있어야 한다.**

| 상황 | 판정 |
| --- | :-: |
| 같은 화면의 착수 이슈가 **열려 있다** | ⛔ **중복 발행** |
| 같은 화면의 착수 이슈가 **닫혀 있다**(프론트가 구현 완료) | ⛔ **완료된 화면** — ⛔/⚠ 로 가야 한다 |
| 같은 화면에 ⛔/⚠ 변경 통지만 있다 | ⚠ 확인 — 착수 이슈가 처음이면 진행 |
| `W-06-07` · `W-06-01` | ⛔ **발행 금지 화면**(스크립트에 박아 두었다) |
| `gh` 조회 실패 | ⚠ — **막지 않되 「중복 검사 못 했음」을 결과에 남긴다** |

⚠ **`--search` 를 쓰지 않는다.** GitHub 검색은 인덱싱 지연이 있고 하이픈이 든 토큰(`W-06-03`)에서 헛돌 수 있다. **전건을 받아 제목을 직접 맞춘다.**

**현황이 궁금하면**:

```bash
python3 .claude/skills/uiux-client-handoff/scripts/check-issue.py --status
```

**우리 쪽에 발행 대장을 두지 않는다.** 정본은 상대 저장소이고, 대장을 따로 두면 갱신을 잊는 순간 틀린 답을 준다. **매번 조회하는 편이 싸고 정확하다.**

## 절차

### ① 초안을 만든다

`templates/착수가능-초안.md` 를 복사해 채운다. **폼이 렌더하는 모양 그대로**이므로 CLI 로 올려도 웹 폼으로 올린 것과 같은 형태가 된다.

각 칸을 우리 산출물 어디에서 가져오는지는 **`references/field-sources.md`** 를 본다. 그 파일이 이 스킬의 핵심이다.

특히 두 가지는 기계적으로 옮기면 틀린다.

- **4번 미결** — 스펙 §8 의 등급(차단/조정/표시)을 폼의 처리 3방법으로 **번역**해야 한다. 대응표가 `field-sources.md` §4 에 있다
- **2번 디자인 시스템** — 「이슈가 닫혔다」가 아니라 **고정 커밋의 설치본에서 실물을 확인**한 결과를 적는다. 이 항목 때문에 규칙이 생겼다

### ② 검사한다 — 발행 **전에**

```bash
python3 .claude/skills/uiux-client-handoff/scripts/check-issue.py <초안.md> --title "…" [--team T4]
```

세 가지를 함께 본다 — **구조**(필수 8절·처리 방법 3종·자리표시 잔존) · **공개 저장소 금지어** · **중복·금지 화면**. 통과하면 `gh` 명령을 출력한다.

**`--team`** — `Agent : T{n}` 라벨을 `--label`에 병기한다. 주지 않으면 같은 화면·같은 도메인의
기존 이슈에서 이미 쓰인 `Agent : T{n}`을 조회해 「이런 값이 보인다」로만 제안한다(자동 부착하지
않는다 — 팀 배정 자체는 `design-work-assignment`의 승인을 거친 결정이어야 한다).

⚠ **순서를 바꾸지 않는다.** `design/schema/00-authoring-rules.md` 가 「본문 작성 → 금지어 검사 → 발행」으로 못박았고, 이 순서를 어겨 DS 저장소에 제품 용어 2건을 흘린 적이 있다(2026-08-04).

### ③ 발행한다

```bash
gh issue create --repo CREFLEINC/omf-mes-client \
  --title "[uiux→client] 착수 가능 — W-06-03 · 불량·원인코드 2계층 마스터" \
  --body-file <초안.md> \
  --label "uiux→client,ready"
```

⚠ **`--label` 을 반드시 넘긴다.** 웹 폼은 라벨을 자동으로 붙이지만 **CLI 로 `--body-file` 을 쓰면 폼을 거치지 않아 라벨이 붙지 않는다.** 라벨이 없으면 프론트의 필터에 걸리지 않는다.

### ④ 발행 후

| 하는 것 | 하지 않는 것 |
| --- | --- |
| 설계가 바뀌면 **⛔/⚠ 변경 통지를 새 이슈로** 올리고 착수 이슈를 링크 | ⛔ **본문 수정** — 시점 기록이 사라진다 |
| 프론트 코멘트(착수·PR·어긋남 실측)를 읽고 **설계 문서에 반영** | ⛔ **이슈 닫기** — 닫는 것은 프론트다 |
| | ⛔ **상태 라벨 부착** — 아래 §다른 스킬과의 경계 |

**프론트가 「스펙과 계약이 어긋났다」고 코멘트하면 그것이 우리 문서의 결함 신고다.** 그 코멘트를 근거로 스펙·계약을 고치고, 필요하면 `omf-mes` 에 `[uiux→docs]`·`[docs→데이터모델]` 이슈를 낸다.

## 변경 통지 ⛔/⚠ — 두 번째 채널

착수 이슈를 이미 보낸 화면의 설계가 바뀌었을 때 쓴다. **폼이 따로 없으므로 본문을 직접 쓴다.**

| 등급 | 뜻 | 발행 시점 |
| :-: | --- | --- |
| **⛔** | **이미 만든 것이 틀린다** — 조항 변경·철회, 경로 삭제, 필드 의미 변경 | **즉시 1건** |
| **⚠** | 새로 만들 것이 생긴다. 기존은 안 깨진다 | **차수 마감 때 묶어서 1건** |
| ℹ | 문서만 바뀜 | **내지 않는다** |

본문은 세 토막이면 된다(`design/schema/00-authoring-rules.md` 규정).

```
## 무엇이 바뀌었나        ← 한두 줄. 화면 ID·제품 용어는 써도 된다
## 코드에 무엇을 해야 하나  ← 구체적으로
## 근거                  ← omf-mes 경로·이슈 번호만. 내용을 옮기지 않는다
```

**착수 이슈를 링크한다** — `착수 이슈: #12`.

⚠ 공개 저장소 검사는 착수 이슈와 **똑같이 적용**한다. `check-issue.py` 에 `--change-notice` 를 주면 구조 검증만 건너뛰고 금지어 검사는 그대로 돈다.

## ⚠ 다른 스킬과의 경계 — `team-issue-protocol` · `design-review-intake`

라벨·제목 접두·저장소 경계의 **정본은 `team-issue-protocol`**(공통 지식 베이스)이다. 이 스킬은
그 규칙을 `omf-mes-client`(아웃바운드) 발행에 구체화한 것이고, 규칙 자체를 복제하지 않는다 —
갈리면 `team-issue-protocol`을 따른다.

| | 아웃바운드(이 스킬 — 착수 가능·변경 통지) | 인바운드(`design-review-intake`) |
| --- | --- | --- |
| **방향** | `omf-mes` → `omf-mes-client`(공개) | `omf-mes-client`/개발팀 → `omf-mes`(비공개) |
| **제목** | `[uiux→client] 착수 가능 — <화면 ID> · <이름>`(폼이 정한 접두) | `[검토 요청]`·`[client→uiux]` |
| **라벨** | `uiux→client`·`ready` + `Agent : T{n}` 병기(`check-issue.py --team`) | `Agent : T{n}`·`Agent : {type}`·`in progress`/`help wanted` |
| **추적** | ⛔ 갱신하지 않는다 — 진행 상태는 프론트의 코멘트로 남는다 | `in progress`↔`help wanted` 전이 |
| **종료** | ⛔ 우리가 닫지 않는다 — 닫는 것은 프론트다 | 4중 잠금 통과 후 설계팀이 닫는다 |

**"프론트가 스펙과 어긋났다고 이슈를 올렸다"는 이 스킬이 아니라 `design-review-intake` 소관이다**
— 그 방향이 반대다. 이 스킬은 우리가 먼저 프론트로 내보내는 통지만 다룬다.

`omf-mes`(우리 저장소) 안의 이슈 — `[uiux→docs]`·`[docs→데이터모델]` — 는 이 스킬 소관이 아니다.
그쪽은 `design/schema/00-authoring-rules.md`를 따른다.
