# design-request-intake — Consultant 전용, 개발팀 요청 자료 접수·처리

`multi-agent-team-workflow-v3.md` 규칙 1(설계팀 우선주의 — 개선 제안서) · 규칙 2(직접 소통
금지 — 자료 → 사용자 → 답변서) · 규칙 4(투명한 업무 공개 — 자기 이슈)와
`multi-agent-team-workflow-v3-design-team-structure.md`가 정의하는 **Consultant(상담원)** 역할을
절차로 세운 것이다. Consultant는 "가장 마지막 배포 버전의 자료 상태"를 보는
`.claude/worktrees/consultant`(최신 `notice/*` 태그 체크아웃)에서만 실행한다 — 다른 워크트리
에서 이 스킬을 돌리지 않는다. 사람 개입은 게이트 한 곳(접수 확인)으로 최소화한다 — 분석 승인
게이트는 재실측이 필요한 회차에 한해 `design-issue-resolution`(Architect) 쪽에 있다.

**입력**은 GitHub 이슈가 아니라 **사용자가 준 자료**(파일 경로 또는 붙여넣기)다. **출력**은
파일(`tmp/requests/<…>/답변서.md`)이고, 개발팀에 전달하는 것은 **사용자**다. 이 스킬이 GitHub 에
쓰는 자리는 **설계팀 자기 저장소(`CREFLEINC/omf-mes`)의 자기 이슈**뿐이다 — 반영 PR 은
`design-issue-resolution`(Architect)이 낸다.

⛔ **Phase 6b(자기 이슈 닫기)가 Architect의 PR 병합 확인보다 먼저 오면 안 된다.** V2 시절 이슈가
PR 병합 34~43분 **전에** 닫힌 사고(#206·#196)가 이 순서 위반에서 났다. 닫는 코멘트에 실리는
답변서는 «병합 해시»를 인용하는데, 병합 전에는 그 해시가 없다. 재실측이 필요한 회차는 이
불변식을 **두 스킬에 걸쳐** 지킨다 — `design-issue-resolution`이 자신의 Phase 4(PR 병합 확인)를
통과한 뒤에만 Phase 5(인계)에서 병합 해시를 코멘트로 남기고, 이 스킬의 Phase 6a는 **그 코멘트가
있어야만** 진행한다(없으면 아직 Architect 작업 중이라는 뜻 — 기다린다). 즉시 답변 회차(Phase
2에서 E/F/H만)는 애초에 PR이 없으므로 이 불변식이 「해당 없음」이다.

이 스킬은 `team-issue-protocol`(자기 이슈 라벨·접두·8유형·답변서 서식·핸드오프 절차)을 전제로
한다. 먼저 그 스킬을 `Skill` 도구로 읽는다.

## 무엇을 받고 무엇을 받지 않나

| 받는다 | 받지 않는다 |
| --- | --- |
| 사용자가 「이 자료 처리해줘」와 함께 준 **파일 경로** 또는 **붙여넣기** | `[검토 요청]`·`[client→uiux]` 이슈 번호 — V3 이전 유산. 사용자가 정리한다 |
| 요청 종류 3종 — **정보 요청**(설계 자료의 오류·누락) · **설계 개선**(요구사항 달성에 설계 변경 필요) — 규칙 2(1) · **개선 제안서** — 규칙 1 | `gh issue view` 로 개발팀 저장소·개발팀 이슈를 읽어 오는 것 — 규칙 2 가 금지한 직접 소통이다 |

⭐ **개선 제안서(규칙 1)도 같은 절차로 처리한다.** 다른 것은 답변서의 판정 어휘뿐이다 —
「반영 / 부분 반영 / 반영하지 않음 / 정보 회신」 대신 **「채택 / 부분 채택 / 채택하지 않음」**.
개발팀은 제안서를 냈다고 업무를 멈추지 않는다(규칙 1) — 그러니 답변서가 「채택」이어도 개발팀이
언제 어떻게 따라올지는 우리가 알거나 정하는 정보가 아니다.

## Phase 0 — 컨텍스트 확인

```
ROOT="$(git rev-parse --show-toplevel)"
```

1. **식별자**를 정한다 — 자료 제목을 kebab 으로(한글 가능 · 공백→`-` · 기호 제거). 제목이
   없으면 `req-<n>`(`$ROOT/tmp/requests/` 에 이미 있는 `req-*` 최댓값 +1, 없으면 `req-1`).
   접수 날짜는 오늘(`YYYY-MM-DD`)이다.
2. `$ROOT/.design-runs/<식별자>-*/` 존재 여부 확인:
   - **없음** → 초기 실행. `$ROOT/.design-runs/<식별자>-<YYYYMMDD>/` 생성.
   - **있고 사용자가 부분 수정 요청** → 부분 재실행. 기존 파일을 읽고 해당 Phase 만 재실행.
   - **있고 사용자가 새 자료(개정본)를 줌** → 기존 디렉토리를 `<...>_prev/` 로 이동 후 재생성.
3. ⛔ **런 디렉토리는 절대경로만 쓴다.** 상대경로 `_workspace/` 를 쓰지 않는다 — 구 하네스가
   그래서 산출물이 두 갈래로 쪼개졌다(`docs/_workspace/` 에 117파일이 실수로 커밋됨). 이름도
   `_workspace` 로 하지 않는다 — grep·훅이 오폭한다.
4. `.design-runs/`·`tmp/` 는 둘 다 `.gitignore` 에 등재돼 있다 — 커밋하지 않는다. 감사 추적의
   정본은 **자기 이슈 코멘트(답변서 전문) + 병합 커밋 SHA + 설계 변동 공지 이슈**다(런
   디렉토리와 `tmp/` 는 사본·스크래치일 뿐).

## Phase 1 — 접수 (`gh` 호출 0)

```
REQ="$ROOT/tmp/requests/<YYYY-MM-DD>-<식별자>"; mkdir -p "$REQ"
```

1. 자료를 `$REQ/요청.md` 에 저장한다 — **경로면 복사**(`cp`), **붙여넣기면 그대로 저장**.
   원본이 `.md` 가 아니면(docx·pdf·xlsx·txt 등) **원본도 `$REQ/` 에 옆에 두고** `요청.md` 에는
   텍스트로 옮긴다(옮길 수 없는 표·그림은 「원본 <파일명> p.N 참조」로 자리를 남긴다).
2. 런 디렉토리에 사본을 둔다 — `cp "$REQ/요청.md" "$RUN/00_request.md"`.
3. 자료를 훑어 **「무엇을 묻는가」 한 줄 요약**을 만든다. 화면 ID(`W-04-03`·`P-02-03`)·문서
   경로·계약 오퍼레이션(`GET /quality/inspections`)·조항(`A-21`)이 **인용돼 있는지**를 함께
   적는다 — 인용이 하나도 없으면 Phase 2 에서 유형 F(서식 불비)로 갈 후보다.
4. **요청 종류**를 자료 문면에서 식별한다 — 정보 요청 / 설계 개선 / 개선 제안서. 자료가
   스스로 밝히지 않았으면 문면으로 추정하되 「추정」이라고 적는다.

⛔ 이 Phase 에서 `gh` 를 부르지 않는다. 자료가 개발팀 이슈 URL 을 인용하고 있어도 **그 이슈를
읽으러 가지 않는다** — 자료에 적힌 것만이 요청이다(부족하면 답변서로 보완을 요청한다).

출력: `$REQ/요청.md`(+원본) · `$RUN/00_request.md` · 한 줄 요약과 요청 종류(Phase 0'·2 가 쓴다).

## Phase 0' — 자기 이슈 (규칙 4) — ★ 접수 확인 게이트

설계팀이 「지금 하고 있는 일」을 자기 저장소에 드러낸다. **개발팀 저장소가 아니라 `omf-mes`
자신**이므로 규칙 2 위반이 아니다.

먼저 사용자에게 **접수 요약**(식별자 · 요청 종류 · 한 줄 요약 · 인용된 화면/경로/오퍼레이션)을
제시하고 「이대로 접수해 자기 이슈를 세웁니다」 확인을 받는다. **확인 뒤에** 아래를 실행한다:

```
gh issue create --repo CREFLEINC/omf-mes \
  --title "[요청 처리] <자료 제목>" \
  --label "Agent : Consultant" \
  --body-file $RUN/00_issue_body.md
```

`00_issue_body.md` 는 세 줄이면 된다 — **접수 날짜 · 자료 식별자 · 요청 종류**(+ 한 줄 요약).
자료 본문을 옮겨 싣지 않는다(정본은 `요청.md`, 결과는 닫을 때 답변서 전문으로 남는다).

라벨은 항상 **`Agent : Consultant`로 시작**한다 — 판정(Phase 2)에서 재실측이 필요하다고 나오면
그때 `Agent : Architect`로 스왑해 넘긴다(3역할 도입 전에는 처음부터 `Agent : Architect`를 붙여
왔지만, 그 라벨은 이제 "지금 Architect 차례"라는 뜻으로 좁혀졌다). `Agent : Consultant`·
`Agent : Architect`·`Agent : Caster` 세 라벨은 모두 이미 저장소에 있다(`team-issue-protocol` §2).

⛔ **`status:in-progress` 를 접수 시점에 붙이지 않는다**(2026-09-05 사용자 확정). 그 라벨은
「**설계 담당자가 실제로 착수했다**」는 뜻이고 **접수는 착수가 아니다** — 붙이는 것은 Architect 가
이어받아 재실측을 시작할 때다(`design-issue-resolution` Phase 0). 즉시 답변 회차(Phase 2 에서
E/F/H 만)는 이 라벨이 **한 번도 붙지 않은 채** 닫힌다. ⛔ `in progress` 를 새로 만들지 않는다 —
붙일 때 쓰는 정본은 `status:in-progress` 다.

부분 재실행(Phase 0 의 둘째·셋째 경우)이면 이미 있는 자기 이슈를 그대로 쓴다 — 새로 세우지
않는다. 재개정 자료가 오면 그 이슈에 「개정본 접수 <날짜>」 코멘트 한 줄만 남긴다.

출력: 자기 이슈 번호(`$RUN/00_issue_no.txt` 에 적어 둔다 — 6b 가 닫을 대상).

## Phase 2 — 적합성 판정

자료를 **물음(문장) 단위**로 분해한다. 각 물음에 `team-issue-protocol` §5 의 8유형표를
적용하고, 판정 근거로 삼은 문장의 **주어를 원문 그대로** 옮겨 적는다(주어를 못 옮기면 판정
불가로 남긴다 — 확정문의 주어를 오독해 소관을 잘못 넘긴 선례가 있다).

**자료 기준 항목** — 옛 「인바운드 형식(이슈 폼·라벨)」 검사는 없다. 대신 **요청 종류(정보
요청 / 설계 개선 / 개선 제안서 — V3 규칙 1 · 2(1))가 식별되는가**를 본다. 식별되지 않고 화면·
경로도 지목하지 않았으면 유형 F(서식 불비)다 — 반려가 아니라 **답변서로 보완을 요청**한다.

자료가 화면 ID·조항·`DR-nnn` 을 인용했으면
```
python3 design/schema/generators/collect-open-items.py --issue <표지>
```
로 그 표지가 이미 미결로 걸린 화면이 있는지 확인한다(있으면 그 화면들을 분석 범위에 넣는다).
⚠ **표지가 0건이어도 그것이 「분석할 것이 없다」는 뜻은 아니다** — 표지는 권장일 뿐 의무가
아니라(Phase 8), 실측상 살아 있는 미결의 3분의 2에 표지가 없다. 분석 범위는 표지가 아니라
물음이 가리키는 화면으로 정한다.

**전 물음이 유형 E(업무배정)·F(서식불비)·H(채널오인)면 여기서 멈춘다** — 인계하지 않고 Phase
6a 로 건너뛰어 답변서(판정 「반영하지 않음」 또는 「정보 회신」)만 만든다. 그 경우에도 Phase 6b
의 자기 이슈 닫기는 거친다(PR 이 없으므로 잠금 ①·② 는 「해당 없음」으로 적는다).

**그 외(적합 물음이 하나라도 있으면)** — 재실측·반영이 필요하다. Consultant는 스스로 재실측
하지 않는다. 자기 이슈에 이 `01_scope.md` 요지(물음별 판정표)를 코멘트로 남기고 라벨을
`Agent : Consultant` → `Agent : Architect`로 스왑한 뒤 **여기서 정지한다**:
```
gh issue comment <자기 이슈> --repo CREFLEINC/omf-mes --body-file $RUN/01_scope.md
gh issue edit    <자기 이슈> --repo CREFLEINC/omf-mes \
  --remove-label "Agent : Consultant" --add-label "Agent : Architect"
```
`design-issue-resolution`(Architect)이 이 라벨을 보고 이어받는다 — 재실측부터 반영 PR·병합
확인까지는 그 스킬 소관이다. Architect가 병합을 마치면 자기 이슈에 인계 코멘트(병합 해시 포함)
를 남기고 라벨을 `Agent : Consultant`로 되돌린다 — 그 코멘트가 와야 이 스킬의 Phase 6a로
이어간다.

출력: `$RUN/01_scope.md`(머리에 한 줄 요약·요청 종류, 본문은 물음별 판정표).

## Phase 3~5b — Architect 소관 (`design-issue-resolution`)

재실측·사람 게이트(분석 승인)·반영 PR·병합 확인은 이제 이 스킬에 없다 —
`design-issue-resolution`(Architect 워크트리 전용)로 옮겼다. 바로 위 Phase 2가 라벨을
`Agent : Architect`로 스왑하고 정지하면, Architect가 그 이슈를 이어받아 처리하고 인계 코멘트
(병합 해시 포함)를 남긴 뒤 라벨을 `Agent : Consultant`로 되돌린다. 절차·검사기·게이트 서식
자체는 옮기기 전과 동일하다 — 궁금하면 `design-issue-resolution/SKILL.md`를 읽는다.

## Phase 6a — 답변서 작성 (닫지 않는다)

`03_reply.md` 를 확정해 **`$REQ/답변서.md`** 로 쓴다 — 이 파일의 출처는 두 갈래다:
- **즉시 답변(Phase 2에서 E/F/H만)** — Architect를 거치지 않았으므로 이 Phase 자신이 Phase 2의
  판정 근거로 `03_reply.md`를 새로 쓴다(「반영 PR」·병합 해시 칸은 「—」).
- **인계를 거친 경우** — 자기 이슈에서 Architect의 인계 코멘트(병합 해시·근거·답변 초안 포함)
  를 읽어 `03_reply.md`로 옮겨 적는다. **그 코멘트가 아직 없으면 Architect가 아직 작업
  중이라는 뜻 — 이 Phase 로 진행하지 않고 기다린다**(위 순서 불변식).

서식은 아래 그대로다(`team-issue-protocol` §7 이 같은 서식을 정본으로 둔다) — 첫 줄은
`# 개발팀에 전달사항 — <요청 식별자>` 로 **시작**한다(V2 line 62 규약 계승).

```markdown
# 개발팀에 전달사항 — <요청 식별자>

| 항목 | 값 |
| --- | --- |
| 요청 | <자료 제목> (접수 <YYYY-MM-DD>) |
| 판정 | 반영 / 부분 반영 / 반영하지 않음 / 정보 회신 |
| 반영 PR | `CREFLEINC/omf-mes#<n>` · 병합 `<해시7>` (반영 없으면 「—」) |
| 근거 | <경로 · 절> 목록 |

## 답변

<사실과 판정. 개발팀이 무엇을 어떻게 고쳐야 하는지는 적지 않는다(V3 규칙 3). DB 를 근거로 인용하지 않는다>

## 다음 공지

이 변경은 다음 「설계 변동 공지」에 실린다 / 설계 변경 없음 — 공지에 실리지 않는다
```

개선 제안서면 「판정」 칸의 어휘만 「채택 / 부분 채택 / 채택하지 않음」 이다.

확정 전 검사:
- `python3 .claude/skills/uiux-design/scripts/check-report-language.py $REQ/답변서.md` —
  화면 번호·조항 번호·업무 약어가 표 밖에서 한 번 전개돼 있는가.
- **근거 블록의 모든 경로를 `test -f` 로 확인**, 실재하지 않으면 그 줄을 제거하거나 대체 경로로
  교체한다(2026-08-25 구조 삭제로 죽은 경로를 근거로 남긴 회신 `#222` 선례).
- 「반영 PR」 칸에 PR 번호 + **병합 해시**(즉시 답변이면 「—」, 인계를 거쳤으면 Architect가
  남긴 인계 코멘트의 병합 해시)를 명시 — 자리표시자(`<n>`·`<해시7>`·`TODO`)를 남기지 않는다.
- 「답변」에 **DB 테이블·컬럼·제약**을 근거로 인용하지 않았는가 — DB 는 설계의 결과물이지
  근거가 아니다. 근거는 언제나 `design/wiki/` 의 경로·절이다.
- 「답변」에 개발팀이 **무엇을 어떻게 고쳐야 하는지**가 적혀 있지 않은가(규칙 3) — 「`null` 로
  올 수 있다」는 **사실**은 적되 「널 가드를 넣어 달라」는 **지시**는 적지 않는다.
- 답변서는 사용자가 어디로 전달할지 이 스킬이 모른다 — 단가·내부 주소 등 **공개 금지 항목**
  (`design-change-notice/references/public-boundary.md`)은 처음부터 싣지 않는다.

**전달은 사용자가 한다(규칙 2).** 이 스킬은 「답변서 경로 `$REQ/답변서.md`」를 사용자에게
보고하는 것으로 이 Phase 를 끝낸다.

⛔ **`gh issue comment` 로 개발팀 저장소·개발팀 이슈에 회신하지 않는다.** V2 에서는 「요청
이슈의 코멘트」가 게시 수단이었지만, V3 규칙 2 가 설계팀→개발팀 직접 소통을 공지 하나로
좁혔다 — 대상이 「개발팀 이슈」에서 「사용자에게 건네는 파일」로 바뀐 것이다. `gh issue create`
도 개발팀 저장소에는 쓰지 않는다 — 우리가 개발팀 저장소에 세우는 유일한 이슈는 설계 변동
공지(`design-change-notice`)다.

⛔ **이 Phase 에서 자기 이슈를 닫지 않는다.** 닫기는 6b 의 3중 잠금 뒤다.

## Phase 7 — 공지 (한 줄)

**이 변경은 다음 「설계 변동 공지」에 실린다 — 즉시 통지하지 않는다**(`design-change-notice`,
배포 선언 단위 — 직전 `notice/*` 태그 → HEAD 를 묶어 사용자가 「공지해」라고 할 때 1건).
답변서 「다음 공지」 절에 그 문장을 적는다. 설계 변경이 없었으면(정보 회신·반영하지 않음)
「설계 변경 없음 — 공지에 실리지 않는다」로 적는다.

## Phase 6b — 자기 이슈 닫기 (3중 잠금)

셋 다 통과해야 닫는다. 하나라도 실패하면 닫지 않고 사유를 `$RUN/05_close.md` 에 기록한다.

| 잠금 | 확인 | 통과 조건 |
|:-:|---|---|
| ① PR 병합 | `gh pr view <PR> --repo CREFLEINC/omf-mes --json mergedAt,mergeCommit` → `git merge-base --is-ancestor <mergeCommit.oid> origin/main` | `mergedAt` non-null **이고** oid 가 `origin/main` 조상(Architect의 Phase 4와 같은 조건을 재확인). PR 없는 회차(E·F·H 정지 · 정보 회신)는 「해당 없음」 |
| ② 계약 등급 | `git diff --name-only $(git merge-base origin/main <oid>^)..<oid> -- design/wiki/api-contracts/openapi/` | 비지 않으면 `design-change-notice/references/change-grades.md` 등급표로 ⛔/⚠ 판정이 **전 행 채워져** 있고, 답변서 「근거」에는 등급이 아니라 **경로·절**이 실려 있다. 비면 「해당 없음」 |
| ③ 답변서 실재 | 답변서의 병합 해시 `git cat-file -e <해시>^{commit}` · 근거 경로 전건 `test -f` · PR 번호 `gh pr view` 존재 | 셋 다 실재. 자리표시자 0 |

통과하면 **답변서 전문을 닫는 코멘트로** 남기고 닫는다 — 자기 저장소라 공개 비용이 0 이고,
`tmp/` 는 gitignore 라 이 코멘트가 답변서의 **유일한 영구 사본**(감사 추적)이다:
```
# 이 줄은 라벨이 «붙어 있을 때만» — Architect 가 착수했던 회차다. 즉시 답변 회차는 애초에
# 붙지 않으므로 건너뛴다(없는 라벨을 떼려 하면 gh 가 실패한다).
gh issue edit  <자기 이슈> --repo CREFLEINC/omf-mes --remove-label "status:in-progress"
gh issue close <자기 이슈> --repo CREFLEINC/omf-mes --comment "$(cat $REQ/답변서.md)"
```
(`team-issue-protocol` §7-1 과 같은 형태 — 코멘트와 닫기를 한 명령으로 묶어 «코멘트만 남고
안 닫힘»·«닫혔는데 코멘트 없음»을 막는다.)

닫을 수 없는 경우(사용자 확인 대기 · 반영 PR 미병합)는 `help wanted` 를 붙이고(`status:in-progress`
가 붙어 있으면 함께 뗀다) 사유 코멘트를 남긴 채 열어 둔다. 사용자에게 물을 것이 있으면 `[확인 요청] <제목>`
이슈(같은 저장소)로 세운다 — 그것도 자기 저장소라 규칙 2 위반이 아니다.

⛔ **옛 잠금 ④(「표지로 찾은 화면 0건」)는 2026-09-03 에 걷어냈다 — 되살리지 않는다.** 안 지켜진
데이터(표지 없는 미결 244/369행)에 건 게이트가 `#349` 에서 살아 있는 미결을 「해소」로 세었다.

## Phase 8 — 되먹임 (권장)

⭐ **추적 표지는 «권장»이다.** 반영한 화면의 스펙 §8 에 **요청 식별자**(예: `요청
2026-09-03-lot-hold-필드-누락`)를 심어 두면 나중에 그 결정을 되짚을 수 있다. 붙이면 편하지만
**없다고 게이트가 막지 않는다**(6b 에 그 잠금이 없다).

⚠ **왜 의무가 아닌가** — 표지는 「답이 오면 어디를 고칠지」를 **미리 적는 예측**이다. V3 는
설계팀이 개발팀의 진행을 예측·보유하지 않고 **사후에 무엇이 언제 바뀌었는지만** 공지하는
쪽이다. 예측을 의무로 걸면 안 지켜지고, 안 지켜진 표지에 게이트를 걸면 틀린 답이 나온다.

⚠ `collect-open-items.py` 의 표지 인식(`TRACKS`·`tag_issues`)은 아직 `#N`·`DR-nnn`·조항
형식만 읽는다 — kebab 식별자는 `--issue` 역조회에 잡히지 않는다. 생성기를 넓히기 전까지는
`grep -rn "요청 <식별자>" design/wiki/screens/` 로 되짚는다.

표지를 심었든 아니든 그 후:
```
python3 design/schema/generators/collect-open-items.py
python3 design/schema/generators/build-screen-progress.py
```
을 재생성한다.

## V3 이전 유산 — `[검토 요청]` 이슈

사용자가 「232번 검토 요청 처리해줘」처럼 **이슈 번호**로 부르면 이 스킬은 받지 않는다 — 열린
`[검토 요청]`·`[client→uiux]` 이슈는 V3 이전 유산이고 사용자가 정리한다. 「그 이슈의 내용을
자료로 만들어 주시면 처리합니다」로 답하고 멈춘다. 그 자료가 오면 보통 절차(Phase 0 부터)다 —
이슈 번호는 자료 제목의 일부로만 남고, 그 이슈에 코멘트를 달거나 닫지 않는다.

## 에러 핸들링

- `gh` 실패(네트워크·권한) — 재시도 1회, 재실패 시 "확인 불가"로 표시하고 그 Phase 를 완료로
  간주하지 않는다. `gh` 가 필요한 자리는 Phase 0'·2(인계)·6b 뿐이다.
- Architect에게 인계했는데 인계 코멘트가 오래 안 옴 — 이 스킬이 재촉하지 않는다(규칙 3, 개발팀
  업무처럼 Architect의 진행도 이 스킬이 보유·독촉할 정보가 아니다). 사용자가 물으면 자기 이슈
  상태를 `gh issue view`로 확인해 보고한다.
- Phase 0' 게이트에서 사용자가 반려 — 반려 사유를 `$RUN/` 에 기록하고 접수 자체를 반려하면
  자기 이슈를 세우지 않고 끝낸다.
- 사용자 확인이 필요해 멈춤 — `help wanted` + `[확인 요청]` 이슈(6b 참조). 대기 중에도 개발팀은
  업무를 멈추지 않는다(규칙 1) — 「기다려 달라」는 문장을 답변서에 쓰지 않는다.

코멘트를 남긴 뒤 라벨을 `Agent : Consultant`로 되돌림 → (이 스킬 재개) P6a 인계 코멘트를 읽어
`답변서.md`(판정 「부분 반영」 · 병합 해시 · 근거 경로) → 사용자에게 경로 보고 → P7 「다음

**즉시 답변 흐름** — 자료가 화면도 경로도 지목하지 않고 「일정을 정해 달라」만 담김: P2 에서 전
물음이 E·F → 인계하지 않고 P6a 로 — 이 스킬이 직접 `03_reply.md` 작성, 답변서 판정 「반영하지
않음」(E: 우리는 정하지 않는다 · F: 어느 화면·어느 절인지 보완 요청) → P6b 잠금 ①·② 「해당
없음」, ③ 통과 → 닫힘. Architect는 전혀 관여하지 않는다.

**개선 제안서 흐름** — 규칙 1 의 제안서: 절차는 정상 흐름과 같고, 답변서 「판정」 만
「채택 / 부분 채택 / 채택하지 않음」. 채택이면 반영 PR 이 있고 다음 공지에 실린다.

**유산 흐름** — 「232번 검토 요청 처리해줘」: 받지 않는다. 「이슈 내용을 자료로 주시면
처리합니다」로 멈춘다 — `gh issue view 232` 를 돌리지 않는다.

**인계 대기 흐름** — Phase 2에서 인계했는데 아직 Architect의 인계 코멘트가 없음: P6a로 진행하지
않고 사용자에게 "Architect 처리 대기 중"으로 보고, 재호출을 기다린다 — 재촉하는 `gh` 호출을
반복하지 않는다.
